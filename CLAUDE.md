# CLAUDE.md — procurement-allocator

Внутренний инструмент отдела закупок/монтажа Screen Factory Florida. В интерфейсе
может называться иначе (см. `docs/glossary.md` → "Именование") — это техническое
имя репозитория и системы.

Этот файл читается Claude Code в начале каждой сессии. Держи его коротким и стабильным —
детали, которые часто меняются, живут в `docs/`, а не здесь.

## О проекте

Внутренний веб-инструмент для отдела монтажа: формирование закупочных ордеров.
Три модуля: (1) обновление БД цен из PDF-прайсов поставщиков через ИИ-парсинг с ревью,
(2) создание проекта и подбор материалов, (3) оптимальное распределение закупки между
поставщиками с учётом доставки и генерация ордер-документов.

Полная спецификация: `docs/spec.md` (перенеси туда исходный документ спеки перед стартом).

## Архитектурные принципы — НЕ переопределять без нового ADR в docs/decisions/

1. **Подбор поставщика — детерминированный ILP-солвер (OR-Tools/PuLP), не LLM.**
   Это счётная задача с точным оптимумом; LLM здесь даёт нестабильный и необъяснимый результат.
2. **LLM используется только там, где вход — неструктурированный текст**: парсинг PDF-прайсов
   и матчинг названий материалов. Оба шага всегда заканчиваются экраном ревью для человека,
   ничего не пишется в боевые таблицы цен автоматически.
3. **Уникальность материала — по `internal_sku`**, никогда по строковому названию.
   Связь "как поставщик называет товар" — отдельная таблица `SupplierMaterialAlias`, не колонка.
4. Все денежные и количественные операции — только на backend (single source of truth),
   frontend не пересчитывает итоги самостоятельно.

## Структура репозитория

```
backend/       — API, ILP-сервис, парсинг/матчинг прайсов, БД-модели и миграции
frontend/      — React-приложение (3 экрана MVP: ревью прайса, конструктор проекта, ордер)
docs/
  spec.md              — полная продуктовая спецификация
  architecture.md       — диаграмма компонентов и потоков данных (Mermaid)
  data-model.md         — ER-диаграмма и описание таблиц (Mermaid)
  decisions/            — ADR: одно архитектурное решение = один файл
  glossary.md           — термины домена (BOM, allocation run, canonical material...)
  design/                — сырая выдача Claude Design (html/md по экрану), НЕ трогать руками
  ui-reference.md         — поведенческая логика экранов поверх design/ (см. правило ниже)
```

## Как использовать docs/design/ и docs/ui-reference.md

Это два разных источника, их нельзя смешивать:
- `docs/design/*.html` — отвечает только на "как это выглядит". Переиспользуй разметку/
  классы там, где уместно под наш стек (React), но НЕ считай его источником бизнес-логики.
- `docs/ui-reference.md` — отвечает на "как это себя ведёт": обязательные поля, пороги
  confidence, условия предупреждений, формат объяснения выбора поставщика.
- Если правки нужны в дизайне — не редактировать HTML руками, возвращаться в Claude Design
  и перегенерировать, чтобы `docs/design/` оставался единственным источником правды.

## Перед началом работы над задачей

1. Прочитать `docs/architecture.md` и `docs/data-model.md`.
2. Просмотреть последние 3–5 файлов в `docs/decisions/` — не переизобретать уже решённое.
3. Если меняешь архитектурное решение (алгоритм, схему данных, границы модулей) —
   сначала создать ADR по шаблону `docs/decisions/0000-template.md`, потом код.

## После завершения значимого куска работы

- Обновить `docs/architecture.md` / `docs/data-model.md`, если менялась структура.
- Добавить ADR, если было принято архитектурное решение, не описанное ранее.
- Не оставлять это "на потом" — следующая сессия начинается с чтения этих файлов,
  а не с истории чата.

## Тесты — обязательны для

- ILP allocation engine: покрыть edge cases из `docs/spec.md` §2.3 (нехватка стока,
  min order amount, порог бесплатной доставки, недоступность материала у всех поставщиков).
- Matching-логики при импорте прайса: тесты на неоднозначные/похожие названия.
