# ADR-0002: Постановка ILP-задачи подбора поставщика

Статус: Принято — реализовано в `backend/app/allocation/` (`solver.py` через
OR-Tools CP-SAT, `preprocess.py` для orphaned materials, `service.py` для
`project_id -> AllocationRun`).

## Контекст

`docs/spec.md` §4.2 описывает задачу распределения закупки между поставщиками
на словах и даёт неполную формализацию: переменные `x[m][s]`, `y[s]`,
ограничения на назначение и наличие, целевую функцию с ценой и доставкой.
Но по стоимости доставки спека прямым текстом оставляет пробел:

> Стоимость доставки `delivery_cost[s]`: плоская ставка, либо бесплатна при
> сумме заказа ≥ `free_shipping_threshold` (кусочно-линейная функция —
> потребуется доп. бинарная переменная).

Это не тривиальная деталь: `free_shipping_threshold` — единственный
нелинейный элемент во всей задаче (доставка зависит от того, наберёт ли
поставщик определённую сумму заказа, а сумма заказа сама зависит от того,
какие материалы ему назначены). Без явного решения, как эта зависимость
кодируется в ILP, движок не собрать. Согласно [[architecture]]
(`docs/architecture.md`), Allocation — "детерминированный сервис, без
вызовов LLM", поэтому весь смысл в точной и воспроизводимой формулировке.

Этот ADR фиксирует полную математическую постановку до написания кода
солвера — черновик для ручной вычитки, реализация не входит в объём.

## Решение

### Индексы и входные данные

- `m ∈ M_solvable` — материалы позиции BOM проекта (из `ProjectItem`),
  **после** предобработки, исключающей недостижимые материалы — см. раздел
  "Предобработка: недостижимые материалы" ниже. Везде далее в этом
  документе `M` без уточнения означает `M_solvable`, а не полный исходный
  список позиций проекта.
- `s ∈ S` — поставщики, у которых есть хотя бы одна актуальная цена (`Price`
  с `valid_to IS NULL`) на любой материал из `M_solvable`.
- `qty[m]` — требуемое количество материала `m` (из `ProjectItem.quantity`).
- `price[m][s]` — цена материала `m` у поставщика `s` (`Price.price`),
  определена только если у `s` есть актуальная цена на `m`.
- `available[m][s]` — доступное количество материала `m` у поставщика `s`
  (`Price.availability`).
- `flat_fee[s]`, `free_shipping_threshold[s]`, `per_order_min_amount[s]` —
  из `Supplier.delivery_policy`.

### Переменные решения

- `x[m][s] ∈ {0, 1}` — материал `m` закупается у поставщика `s`.
- `y[s] ∈ {0, 1}` — поставщик `s` задействован в закупке (у него заказана
  хотя бы одна позиция).
- `free[s] ∈ {0, 1}` — у поставщика `s` достигнут порог бесплатной
  доставки (вспомогательная переменная, см. ниже).

### Предобработка: недостижимые материалы (orphaned materials)

Ограничение 1 (см. ниже) — жёсткое равенство `Σ_s x[m][s] = 1`. Если для
какого-то материала нет вообще ни одной допустимой пары `(m, s)` (ни у
одного поставщика нет актуальной цены на `m`, либо есть цена, но
`available[m][s] < qty[m]` у всех `s`), то по Ограничению 2 переменная
`x[m][s]` исключена из модели для всех `s` разом — сумма по пустому
множеству переменных равна `0`, а ограничение требует `= 1`.
Противоречие делает **всю ILP-модель infeasible целиком**: солвер не
возвращает "всё посчитано, кроме одной строки", он не возвращает ничего.

Это прямо противоречит `docs/spec.md` §4.3: "Материал недоступен ни у
одного поставщика в нужном количестве → явный warning" — расчёт по
остальным материалам должен пройти, а проблемная позиция — подсветиться
отдельно, не обрушивать весь `AllocationRun`.

Поэтому перед сборкой ILP-модели выполняется предобработка над исходным
списком позиций `ProjectItem` проекта (обозначим его `M_all`, чтобы не
путать с `M_solvable`, участвующим в модели, — см. раздел "Индексы"
выше):

1. Для каждого `m ∈ M_all` проверить, существует ли хотя бы одна пара
   `(m, s)`, где у `s` есть актуальная цена на `m` и
   `available[m][s] ≥ qty[m]`.
2. Материалы без такой пары исключаются: `M_solvable = M_all \ M_orphaned`.
   ILP-модель строится только над `M_solvable`.
3. `M_orphaned` возвращается отдельным списком — материал, требуемое
   количество, лучшая частично доступная альтернатива (если есть
   поставщик с `0 < available[m][s] < qty[m]`, для UI-подсказки о
   частичном дефиците по spec.md §4.3 "Материал доступен только
   частично").

Это меняет саму постановку задачи (множество, над которым строится
модель, — не тождественно списку позиций проекта), а не является деталью
реализации солвера, поэтому фиксируется здесь.

### Ограничения

1. **Назначение.** Каждый материал закупается ровно у одного поставщика:
   `Σ_s x[m][s] = 1` для каждого `m ∈ M`.

2. **Доступность.** Нельзя назначить материал поставщику, у которого его
   нет или недостаточно в наличии:
   `x[m][s] = 0`, если `(m, s) ∉ price` или `available[m][s] < qty[m]`.
   На практике реализуется не как ограничение, а как исключение переменной
   `x[m][s]` из модели для недопустимых пар — так солвер не тратит время на
   заведомо нулевые ветви.

3. **Активация поставщика.** Поставщик считается задействованным, если ему
   назначена хотя бы одна позиция:
   `x[m][s] ≤ y[s]` для каждой пары `(m, s)`.

4. **Минимальная сумма заказа (опционально, если `per_order_min_amount[s] > 0`).**
   Если поставщик задействован, сумма его заказа должна быть не меньше
   минимальной:
   `Σ_m x[m][s] × price[m][s] × qty[m] ≥ per_order_min_amount[s] × y[s]`.

### Моделирование `free_shipping_threshold` (кусочно-линейная доставка)

Стоимость доставки поставщика `s` — кусочная функция от суммы его заказа
`order_total[s] = Σ_m x[m][s] × price[m][s] × qty[m]`:

```
delivery_cost[s] = 0,           если order_total[s] ≥ free_shipping_threshold[s]
                  = flat_fee[s], если 0 < order_total[s] < free_shipping_threshold[s]
                  = 0,           если order_total[s] = 0 (поставщик не задействован)
```

Это классический разрыв (не выпуклая, не гладкая функция), который ILP
сам моделировать не умеет — отсюда необходимость бинарной переменной
`free[s]`, о которой спека упоминает, но не формализует. Решение —
стандартный приём **big-M linking**:

- `order_total[s] ≥ free_shipping_threshold[s] − M[s] × (1 − free[s])`
  (если `free[s] = 1`, сумма обязана быть ≥ порога)
- `order_total[s] ≤ free_shipping_threshold[s] − ε + M[s] × free[s]`
  (если `free[s] = 0`, сумма обязана быть строго меньше порога;
  `ε` — минимальный шаг цены, например `0.01`, чтобы избежать равенства
  ровно на границе при `free[s] = 0`)
- `free[s] ≤ y[s]` (нет смысла говорить о пороге для незадействованного
  поставщика; без этого ограничения `free[s]` мог бы обнулять
  `delivery_cost` не задействованного поставщика произвольно, что не
  влияет на целевую функцию напрямую, но засоряет объяснение выбора для UI)

Где `M[s]` — достаточно большая константа, своя на каждого поставщика (не
единая глобальная на все `s`, чтобы не ослаблять ограничение сильнее
необходимого и не терять численную устойчивость солвера). Важно: `M[s]`
должен гасить обе стороны неравенства, а не только верхнюю границу
достижимой суммы заказа. При `free[s] = 0` ограничение
`order_total[s] ≥ threshold[s] − M[s]` обязано быть тривиально выполнено
(не мешать `order_total[s]` быть маленьким или нулевым) — для этого нужно
`threshold[s] − M[s] ≤ 0`, то есть `M[s] ≥ threshold[s]`.

Если взять `M[s] = Σ_m price[m][s] × qty[m]` (максимально достижимая сумма
заказа этого поставщика) без учёта самого порога, `M[s]` может оказаться
**меньше** `threshold[s]`: например, порог `$10 000`, а максимум, что
физически можно назначить поставщику в этом проекте — `$2 000`
(`M[s] = 2000`). Тогда при `free[s] = 0` ограничение требует
`order_total[s] ≥ 10000 − 2000 = 8000` — недостижимо (максимум `$2000`), и
солвер вынужден отвергнуть `free[s] = 0` для этого поставщика вообще, то
есть исказить решение, обязав `free[s] = 1` (бесплатная доставка), хотя
порог реально не достигнут и достигнут быть не может. Модель тихо выдаёт
заниженную стоимость доставки.

Фикс: `M[s] = free_shipping_threshold[s] + Σ_m price[m][s] × qty[m]` —
сумма порога и достижимого максимума. Это гарантирует `M[s] ≥ threshold[s]`
всегда (второе слагаемое неотрицательно), сохраняя ту же идею "своя
константа на поставщика", но с корректной нижней гарантией.

Итоговая стоимость доставки поставщика линейна относительно `free[s]`:

`delivery_cost[s] = flat_fee[s] × (1 − free[s])`

Так `free[s] = 1` (порог достигнут) обнуляет `flat_fee[s]` в целевой
функции, а `free[s] = 0` — начисляет её.

### Целевая функция

```
min  Σ_m Σ_s x[m][s] × price[m][s] × qty[m]
   + Σ_s flat_fee[s] × (1 − free[s]) × y[s]
```

Множитель `y[s]` во втором слагаемом **необходим, не избыточен**: без него
для незадействованного поставщика (`y[s] = 0`) ограничение
`free[s] ≤ y[s]` вынуждает `free[s] = 0`, и слагаемое
`flat_fee[s] × (1 − free[s])` превращается в `flat_fee[s] × 1 =
flat_fee[s]` — то есть незадействованному поставщику молча начислилась бы
доставка, хотя у него нет ни одной позиции и платить ему не за что.
Множитель `y[s]` глушит это слагаемое до нуля ровно тогда, когда
поставщик не участвует.

`flat_fee[s] × (1 − free[s]) × y[s]` — произведение трёх величин, из
которых `y[s]` и `free[s]` бинарны, что делает выражение нелинейным для
ILP-солвера в лоб. Линеаризуется стандартно через вспомогательную
`z[s] = y[s] × (1 − free[s])`:

`z[s] ≤ y[s]`, `z[s] ≤ 1 − free[s]`, `z[s] ≥ y[s] − free[s]`

и целевая функция использует `flat_fee[s] × z[s]` вместо прямого
произведения трёх переменных. Конкретная реализация линеаризации (эта
тройка неравенств или эквивалентный приём солвер-библиотеки) — деталь
кода, а не архитектуры; здесь фиксируется, что `y[s]` в формуле —
обязательная часть корректной модели.

## Альтернативы

**Не поддерживать `free_shipping_threshold` в MVP, только плоскую ставку.**
Отклонено — это как раз тот случай, ради которого вся задача выбора
поставщика вообще ставится как ILP, а не "минимальная цена за позицию"
(см. spec.md §4.2, "наивный подход... не работает"). Без порога бесплатной
доставки продукт не отличается от простого сравнения цен.

**Моделировать доставку как отдельную MILP-подзадачу / эвристику поверх
базового решения (сначала распределить материалы по минимальной цене,
потом локально пытаться консолидировать доставку).** Отклонено — теряется
гарантия глобального оптимума, а всё обоснование выбора ILP в
[[architecture]] построено на "точный оптимум, а не эвристика". Two-stage
эвристика могла бы пропустить решение, где чуть более дорогая позиция у
одного поставщика окупается бесплатной доставкой — именно тот сценарий,
который явно должен подсвечиваться пользователю по spec.md §4.2
("алгоритм пожертвовал минимальной ценой позиции ради консолидации
доставки, с объяснением экономии").

**Аппроксимировать порог доставки без big-M, например через SOS1/SOS2
constraints или встроенную поддержку кусочно-линейных функций в CP-SAT.**
Не отклонено, а отложено — OR-Tools CP-SAT имеет нативную поддержку
кусочно-линейных функций (`AddPiecewiseLinearExpression` и аналоги) и
условных ограничений через `OnlyEnforceIf`, что может оказаться чище, чем
ручной big-M. Выбор конкретного солвер-API — деталь реализации; сама
модель (переменные, ограничения, целевая функция) остаётся такой же
независимо от того, как именно `free[s]` линковано технически.

## Последствия

- Схема данных (`docs/data-model.md`, backend/app/models) уже содержит все
  нужные для этой формулировки поля: `Price.price`/`availability`,
  `Supplier.delivery_policy` (JSON с `flat_fee`/`free_shipping_threshold`/
  `per_order_min_amount`), `ProjectItem.quantity`. Изменений схемы не
  требуется.
- `AllocationRun.algorithm_version` (см. `docs/data-model.md`) должен
  фиксировать версию этой формулировки — если модель ограничений изменится
  (например, добавится split-поставка материала между несколькими
  поставщиками, сейчас explicitly вне MVP по spec.md §7), это будет новый
  ADR и новая версия алгоритма, а не молчаливое изменение.
- Результат работы солвера (`x[m][s]`, `free[s]`) должен транслироваться в
  `AllocationLine` и в объяснение выбора для UI (`docs/ui-reference.md`,
  экран 3): бейдж "не самая дешёвая цена" — когда для материала выбран не
  `argmin_s price[m][s]`; текст объяснения — сравнение цены с экономией на
  `free[s]`, что требует хранить/пересчитывать оба сценария (с консолидацией
  и без) для сообщения пользователю, а не только финальный `x`.
- `AllocationRun` должен возвращать не только `AllocationLine` по
  `M_solvable`, но и список `M_orphaned` (недостижимые материалы) — это
  напрямую питает блокирующий warning на экране 3 (`docs/ui-reference.md`,
  "Предупреждение о нехватке материала — красный блок... на уровне
  соответствующей позиции"), которого пока нет ни в `docs/data-model.md`,
  ни в текущей схеме `AllocationRun`. Решение: добавить JSON-поле
  `orphaned_materials` на `AllocationRun` (по аналогии с уже существующими
  `Supplier.delivery_policy`/`Material.attributes`), а не отдельную
  таблицу — эти данные чисто информационные для UI, не требуют FK-
  целостности и не участвуют в дальнейших расчётах, поэтому не оправдывают
  накладные расходы отдельной таблицы; при реализации потребуется отдельная
  Alembic-миграция, добавляющая колонку к уже применённой схеме.
- Реализация (OR-Tools CP-SAT или PuLP, выбор солвер-API для big-M/native
  piecewise) — предмет отдельной задачи и, при необходимости, отдельного
  ADR, если выбор солвера окажется архитектурно значимым (например, при
  проблемах с производительностью на реальных объёмах поставщиков).
