# ADR-0003: Явный статус `AllocationRun` при INFEASIBLE-модели

Статус: Принято — реализовано в `backend/app/allocation/service.py`,
`backend/app/models/allocation.py`, миграция
`alembic/versions/ed0e345c17e0_add_status_to_allocation_runs.py`.

## Контекст

`run_allocation` (`backend/app/allocation/service.py`) вызывает `solve_allocation`
(`backend/app/allocation/solver.py`), который уже корректно возвращает
`AllocationResult(status="INFEASIBLE")` с пустыми `lines` при
`solver.solve(model)` → `cp_model.INFEASIBLE` (`solver.py:129-133`). Баг не в
солвере — солвер честно говорит "не могу".

Баг в том, что `run_allocation` **не читает `result.status`**: он безусловно
строит `AllocationRun` из `result.lines` (пустой список) и
`orphaned.materials` от предобработки (`preprocess.split_orphaned_materials`,
тоже пустой — предобработка проверяет только *наличие*, `available[m][s] >=
qty[m]`, а не выполнимость модели в целом), коммитит и возвращает 200.

Конкретный воспроизводимый случай: материал `M` имеет ровно одного
поставщика `S` с достаточным наличием (`available >= qty`), поэтому
`split_orphaned_materials` относит `M` к `M_solvable`. Но
`per_order_min_amount[S] > order_total[S]` при заказе только `M` — Ограничение
4 (`order_total[s] >= min_amount * y[s]`) делает `y[S] = 1` невыполнимым при
единственно возможном назначении `x[M][S] = 1`, а по Ограничению 1
(`Σ_s x[m][s] = 1`) `x[M][S] = 1` обязателен — вся модель CP-SAT становится
infeasible целиком, не по одной позиции.

Итог: клиент получает `200 OK` с `AllocationRun{lines: [], orphaned_materials:
[], supplier_summaries: []}` — неотличимо от "проект решён, просто там
случайно ничего нет" (такого валидного состояния в системе не существует,
`EmptyProjectError` уже блокирует пустой `ProjectItem`-список раньше, но
результат "все позиции есть, паросочетание невозможно" выглядит так же).
Пользователь не получает сигнала "закупку в принципе нельзя рассчитать
такими данными".

`preprocess.split_orphaned_materials` — предобработка, не защита от этого
класса ошибок: она моделирует только Ограничение 2 (доступность), не
Ограничение 4 (мин. сумма заказа) и не глобальную совместность модели.
Инфизибельность из-за `per_order_min_amount` — свойство *комбинации*
назначений на конкретного поставщика, а не свойство одного материала,
поэтому предобработка в её нынешнем виде принципиально не может её
предсказать без частичного повторения работы солвера.

## Решение

`AllocationRun` получает персистентное поле `status` — по аналогии с уже
существующей статусной моделью `Order.status` (`draft/approved/sent`,
`backend/app/models/order.py`), а не одноразовое исключение, которое
превращается в HTTP-ответ и теряется.

### Значения `status`

- `"ok"` — модель решена (`OPTIMAL` или `FEASIBLE` в терминах CP-SAT),
  `lines`/`supplier_summaries` заполнены как сейчас.
- `"infeasible"` — `solve_allocation` вернул статус, отличный от `OPTIMAL`
  или `FEASIBLE` (`INFEASIBLE`, `MODEL_INVALID`, `UNKNOWN`), **или**
  `"NO_SOLVABLE_MATERIALS"` (все позиции проекта попали в `M_orphaned` на
  этапе предобработки — сейчас это тоже молча даёт пустой "успешный"
  `AllocationRun`, тот же класс бага). `lines` и `supplier_summaries` —
  пустые списки (не null — см. известный баг в `docs/known-issues.md`, эта
  работа заодно закрывает и его). `orphaned_materials` сохраняет то, что уже
  вычислила предобработка (может быть пустым — это отдельный сигнал от
  "почему инфизибельно").

Third-статус (`"partial"`/что-то среднее) не вводится: у CP-SAT в этой
модели нет промежуточного состояния между "нашёл допустимое назначение всех
`M_solvable`" и "не нашёл" — Ограничение 1 (`Σ_s x[m][s] = 1`) требует
назначить *все* материалы из `M_solvable`, частичное решение по построению
модели невозможно.

### Изменение `run_allocation`

```
result = solve_allocation(...)

run = AllocationRun(
    project_id=project_id,
    algorithm_version=ALGORITHM_VERSION,
    status="ok" if result.status in ("OPTIMAL", "FEASIBLE") else "infeasible",
    orphaned_materials=[asdict(o) for o in orphaned],
    supplier_summaries=[...] if result.status in (...) else [],
)
db.add(run)
db.flush()

if result.status in ("OPTIMAL", "FEASIBLE"):
    for line in result.lines:
        db.add(AllocationLine(...))

db.commit()
db.refresh(run)
return run
```

`run_allocation` продолжает **всегда возвращать `AllocationRun`** (никогда
не бросает исключение на infeasible) — попытка расчёта остаётся в БД как
полноценная строка, а не теряется как проваленный HTTP-запрос без следа.
Это явное отличие от уже существующего `EmptyProjectError`: тот — ошибка
входных данных до всякой попытки расчёта (нечего считать), это —
результат попытки расчёта, который стоит хранить для последующего разбора
(например, когда разберёмся с реальными прайсами после Excel-импорта и
захотим посмотреть, что именно случалось инфизибельным).

### Изменение API-слоя

`POST /projects/{id}/allocate` и `GET /projects/{id}/allocations/{run_id}`
(`backend/app/api/allocation.py`) продолжают отдавать `200` с телом
`AllocationRunOut` в обоих случаях (`ok` и `infeasible`) — `AllocationRun`
создан и существует, это не 4xx/5xx ситуация на уровне HTTP. `status` в
`AllocationRunOut` (`backend/app/api/schemas/allocation.py`) — новое
обязательное поле, фронтенд обязан его проверять перед рендером как
успешного результата (сейчас — задача фронтенда экрана `/projects/:id/
allocation`, ещё не реализованного; текущая заглушка ничего не читает из
`AllocationRun`, так что изменение контракта её не задевает).

Понятное сообщение пользователю ("не удалось построить план закупки — часть
условий поставщиков делает расчёт невыполнимым, проверьте минимальные суммы
заказа") — забота UI-слоя allocation-result экрана при `status ===
"infeasible"`, не API. API не пытается объяснить *почему* (см. "Не в
объёме" ниже) — только сообщает факт.

### Схема БД

Alembic-миграция: добавить колонку `status: Mapped[str]` (`String(20)`,
`nullable=True` на шаге добавления), затем **условный бэкафилл**, не слепой
дефолт `"ok"` — существующие строки `AllocationRun` в базе не гарантированно
успешны именно из-за бага, который фиксирует этот ADR: строка могла быть
создана `run_allocation`-версией без проверки `result.status` и быть
инфизибельной, просто выглядящей как "успех без позиций". Бэкафилл должен
отличать эти случаи от настоящих `"ok"`-строк:

```sql
UPDATE allocation_runs
SET status = CASE
    WHEN NOT EXISTS (
        SELECT 1 FROM allocation_lines
        WHERE allocation_lines.allocation_run_id = allocation_runs.id
    )
    AND orphaned_materials::text = '[]'
    THEN 'infeasible'
    ELSE 'ok'
END;
```

(`orphaned_materials` сравнивается через `::text`, не `::json` — у обычного
Postgres-типа `json` (не `jsonb`) нет оператора равенства, только `jsonb` его
имеет; `orphaned_materials` в модели — `sa.JSON()`, что маппится на `json`.)
Затем `ALTER COLUMN status SET NOT NULL`.

**Условие бэкафилла not exists(lines) AND orphaned_materials = [] — тот же
предикат, что описывает баг в разделе "Контекст"**: пустые `lines` при
пустых `orphaned_materials` до этого ADR не могли возникнуть иначе как через
эту дыру (либо через `EmptyProjectError`, но та бросает исключение до
создания `AllocationRun`, так что такая строка физически не попадает в
таблицу). После деплоя миграции: `SELECT id, orphaned_materials FROM
allocation_runs r WHERE status = 'ok' AND NOT EXISTS (SELECT 1 FROM
allocation_lines WHERE allocation_run_id = r.id)` должен вернуть пустой
результат — если нет, бэкафилл где-то ошибочно пометил инфизибельную строку
как `'ok'`, и это нужно расследовать до деплоя в проде, не после.

## Не в объёме (сознательно отложено)

**Атрибуция конкретного материала/поставщика, из-за которого модель
инфизибельна** (raised as "Option A" при обсуждении этого ADR) — итеративно
находить виновный материал/группу материалов у одного поставщика, выносить
их в `orphaned_materials` с отдельным reason-кодом (не "недоступен", а
"недостижим по условию минимальной суммы заказа") и пересчитывать модель
над оставшимися `M_solvable`, аналогично тому, как уже работает
`split_orphaned_materials` для обычной недоступности (`docs/spec.md §4.3`).

Отложено, не отклонено. Причина: атрибуция для `per_order_min_amount`
качественно сложнее атрибуции для доступности — недоступность
проверяется независимо по каждой паре `(material, supplier)`, а
min-order-инфизибельность — свойство *подмножества* материалов, назначенных
одному поставщику одновременно (убрать один материал из подмножества может
не хватить, если `per_order_min_amount` всё ещё не набирается оставшимися;
см. черновой набросок сложности при обсуждении: нужен bucket-по-поставщику
fallback поверх пробного одиночного исключения). Раскрывать эту логику
сейчас — на синтетических тестовых данных, без единого реального прайса из
Excel-импорта (`docs/spec.md §3`, блок 1 ещё не в проде) — означает
проектировать эвристику вслепую: неизвестно, насколько часто реальные
`per_order_min_amount` будут конфликтовать с реальными объёмами закупки,
насколько типична ситуация "единственный поставщик материала не хватает по
минимуму", стоит ли вообще пытаться разбивать заказ или бизнес-процесс
проще — "увеличьте количество или уберите позицию".

Зафиксировано в `docs/known-issues.md` как явно отложенная работа с
условием возврата: первый реальный (не тестовый) случай
min-order-инфизибельности после того, как в системе появятся настоящие
прайсы поставщиков.

## Альтернативы

**Типизированное исключение → 4xx на уровне API, без персистентности**
(исходный "Option B" при обсуждении). Отклонено пользователем явно: попытка
расчёта не должна теряться как проваленный HTTP-запрос без следа —
`AllocationRun` должен существовать в БД для последующего разбора, так же
как `Order` существует в статусе `draft` до одобрения, а не создаётся только
в момент финального успеха.

**Считать `NO_SOLVABLE_MATERIALS` отдельным от `INFEASIBLE` статусом.**
Отклонено — с точки зрения пользователя оба случая означают одно и то же
("посчитать нечего/не из чего"), различие чисто техническое (пусто на входе
в солвер vs. солвер сказал "нет" на непустом входе) и не несёт разной
UI-семантики. Если появится разница в объяснении для UI — это тривиальное
расширение `status`, не пересмотр этого ADR.

## Последствия

- Требуется Alembic-миграция с условным бэкафиллом (см. "Схема БД") — не
  `ALTER TABLE ... ADD COLUMN status ... DEFAULT 'ok'` слепо на все строки,
  это воспроизвело бы баг данными вместо кода. После миграции проверить
  `SELECT id FROM allocation_runs r WHERE status = 'ok' AND NOT EXISTS
  (SELECT 1 FROM allocation_lines WHERE allocation_run_id = r.id)` — должно
  быть пусто.
- `AllocationRunOut` (Pydantic-схема) — новое обязательное поле `status`,
  ломает контракт для любого существующего клиента, который не ожидает
  этого поля (сейчас клиентов нет — фронтенд-экран результата ещё не
  реализован).
- `run_allocation` перестаёт полагаться на "пустые `lines` == успех без
  позиций"; любой код, читающий `AllocationRun` напрямую из БД (а не через
  API), должен проверять `status`, а не только `len(lines)`.
- Заодно фиксируется соседний известный баг из `docs/known-issues.md`
  ("Нет теста, что `supplier_summaries == []` (не null) на infeasible-пути")
  — новый код явно строит `supplier_summaries=[]` на infeasible-ветке.
- Атрибуция инфизибельности (Option A) — предмет отдельного будущего ADR,
  когда появятся реальные данные для проектирования эвристики; см.
  `docs/known-issues.md`.
