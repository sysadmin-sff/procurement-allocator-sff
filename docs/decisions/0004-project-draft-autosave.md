# ADR-0004: Автосохранение черновика проекта, единый экран create/draft-edit

Статус: Принято

## Контекст

`ProjectBuilderPage` (`/projects/new`) до этого ADR — чисто клиентский черновик:
пользователь вводит название и позиции спецификации в React state, и ничего не
попадает в БД, пока не нажата кнопка "Рассчитать закупку" (которая одним махом
создаёт `Project`, добавляет все `ProjectItem` и сразу запускает allocation). Если
закрыть вкладку раньше — ввод пропадает без возможности вернуться.

Существующая модель уже фактически поддерживает "недосчитанный" проект:
`Project.status` по умолчанию `"draft"`, `ProjectWithItemsOut` уже отдаёт пустой
`items: []`, `GET /projects` уже отображает все проекты вне зависимости от того,
считалась ли по ним allocation. Единственное, чего не хватало — API-путь для
правки `title` после создания (`backend/app/api/schemas/project.py` явно
декларировала "Проект как таковой (title/status) — только create/read") и
frontend-поток, который создаёт `Project`/`ProjectItem` по мере ввода, а не одним
батчем в конце.

## Решение

1. **`Project` создаётся рано** — при первом содержательном вводе (title или первая
   заполненная строка спецификации), не при клике "Рассчитать". До этого момента
   ввод живёт только в React state, как и раньше (не создаём пустые `Project` на
   голый заход на `/projects/new`).

2. **После неявного создания `Project` URL меняется на `/projects/:id` через
   `navigate(..., { replace: true })`, не push.** Это не косметика — это условие,
   без которого весь смысл автосохранения не работает в основном сценарии, ради
   которого его вводили: "заполнил часть спецификации, закрыл вкладку, вернулся
   позже". Пока пользователь остаётся на `/projects/new` (адрес без `:id`),
   обновление страницы или возврат по прямой ссылке не может найти черновик —
   `ProjectBuilderPage` в create-режиме не знает, какой `Project` подгружать.
   `replace`, а не `push`: при `push` URL становится `/projects/new` →
   `/projects/:id` двумя записями в истории, и кнопка "Назад" после этого ведёт
   обратно на пустой `/projects/new`, а не туда, откуда пользователь пришёл до
   начала ввода — обманывает ожидание от "Назад". `replace` держит один слот в
   истории на весь черновик, как будто пользователь и открыл сразу
   `/projects/:id`.

3. **Title и позиции автосохраняются по мере ввода**, debounced (500мс), без
   видимой кнопки "Сохранить". `title` получает write-путь после создания:
   `PATCH /projects/{id}` + `ProjectUpdate { title: str }` — новый endpoint,
   единственное поле, без diff-семантики (по аналогии с `update_project_item`).
   Позиции используют уже существующий CRUD (`POST/PATCH/DELETE
   /projects/{id}/items`).

   Debounce для позиций — **независимый таймер на каждую строку**
   (`usePerKeyDebounce`, `frontend/src/hooks/usePerKeyDebounce.ts`), не один
   общий таймер на весь грид. Один общий таймер (первая реализация, исправлено
   до релиза этого ADR) означал, что правка строки Б в течение 500мс после
   правки строки А отменяет (`clearTimeout`) ещё не отправленное сохранение
   строки А целиком — оно не переносится, а теряется молча, пока строку А не
   тронут повторно. При независимом ведении по строкам это невозможно в
   принципе, не только "маловероятно при типичном вводе".

   **Кнопка "Рассчитать закупку" обязана принудительно вытолкнуть (flush) все
   висящие debounce-таймеры перед запуском allocation, а не только дождаться
   уже запущенных запросов.** Дожидаться `pendingSaves === 0` недостаточно:
   если правка (title или количество) ещё сидит в 500мс-окне и физически не
   ушла на backend, `pendingSaves` про неё ничего не знает — она не "in
   flight", она просто ещё не начата. `handleCalculate`
   (`frontend/src/routes/ProjectBuilderPage.tsx`) поэтому делает
   `debouncedSaveTitle.flush()` и `rowSaveDebounce.flushAll()` первым шагом —
   вызывает отложенный колбэк немедленно и синхронно регистрирует его промис в
   `inFlightSavesRef` — и только потом ждёт `waitForInFlightSaves()` (в цикле,
   т.к. `saveRow`'s `addItem`/`updateItem` регистрируется только после того как
   резолвится её собственный `ensureProjectCreated`-await — одного снэпшота
   промисов недостаточно, если новые появляются "второй волной"). И
   `useDebouncedCallback`, и `usePerKeyDebounce` поэтому возвращают не только
   отложенный вызов, но и `flush`/`cancel`.

4. **`ProjectBuilderPage` становится единым экраном** для `/projects/new` и
   `/projects/:projectId`, пока по проекту ни разу не запускалась allocation
   (`latest_allocation_run == null`). При наличии `:projectId` подгружает
   существующий черновик и продолжает автосохранение в том же гриде — вместо
   отдельного redirect-экрана или дублирования grid-UI в `ProjectDetailPage`.
   Как только у проекта появляется `latest_allocation_run` (allocation была
   запущена хотя бы раз), `/projects/:projectId` рендерит `ProjectDetailPage`
   (обзорная таблица + результат расчёта, без изменений) — выбор экрана
   определяется этим полем, не отдельным флагом.

5. **Черновики с нулём позиций видны в `/projects` как есть** — доп. фильтрация не
   вводится. `status = "draft"` уже отличает их от рассчитанных, этого достаточно.

## Альтернативы

**Явная кнопка "Сохранить черновик".** Отклонено пользователем — выбрано
автосохранение без видимого действия сохранения, ближе к тому, как уже ведёт себя
`ProjectDetailPage` (quantity сохраняется по blur без отдельной кнопки).

**Отдельный экран для draft-редактирования, `ProjectDetailPage` дорабатывается под
grid-UI.** Отклонено — потребовало бы переносить клавиатурный grid (`Tab`/`Enter`
навигация, `MaterialCombobox`) в `ProjectDetailPage`, увеличивая связность вместо
переиспользования уже готового `ProjectBuilderPage`.

**Отдельный роут `/projects/:id/edit`.** Отклонено — усложняет роутинг без
выигрыша; выбор экрана по `latest_allocation_run` на одном и том же URL проще для
пользователя (один адрес на проект вне зависимости от его стадии).

## Последствия

- `ProjectUpdate`/`PATCH /projects/{id}` — новый API-контракт, ломает докстринг
  `backend/app/api/schemas/project.py` ("title/status — только create/read");
  докстринг обновлён вместе с этим ADR.
- Инвариант "`Project` создан ⇒ пользователь закончил ввод" больше не действует —
  `Project` может существовать частично заполненным сколь угодно долго. Никакой
  существующий код на этот инвариант не полагался (см. проверку в ходе
  проектирования: `Project.status` нигде не читается для ветвления логики, кроме
  как для отображения; allocation по-прежнему требует непустой список items
  независимо от `status`).
- `ProjectBuilderPage` получает опциональные `projectId`/`initialProject` пропы —
  расширение существующего компонента, не новый экран. `ProjectDetailPage` не
  изменяется.
- Debounced-автосохранение вводит два независимых механизма ожидания, оба
  обязательны перед запуском allocation, не только один из них:
  (1) `pendingSaves`/`inFlightSavesRef` — запросы, которые уже ушли на backend,
  но ещё не завершились; (2) `flush()`/`flushAll()` — правки, которые ещё не
  начали отправляться, потому что сидят в debounce-окне. Кнопка "Рассчитать
  закупку" без явного flush может запустить allocation по набору items,
  который не включает последнюю правку прямо перед кликом — не гипотетическая
  гонка, а гарантированно воспроизводится, если правка была сделана быстрее
  500мс до клика.
- **Условие приёмки, специфичное для п. 2 (replace-навигация):** ввести title
  или заполнить первую строку на `/projects/new`, дождаться автосохранения,
  нажать F5 — черновик должен восстановиться с тем же содержимым, а не привести
  на пустой `/projects/new`. Если этот сценарий не проходит, значит либо
  `navigate` не вызван, либо вызван без `replace: true` (URL не сменился до
  перезагрузки) — сам факт наличия `Project` в БД недостаточен, если адресная
  строка его не отражает.
