# ADR-0005: `availability = NULL` не блокирует расчёт — трактуется как "доступно"

Статус: Принято

## Контекст

ADR-0002 и `docs/spec.md` §4.2 формализуют Ограничение 2 как
`x[m][s] = 0`, если `available[m][s] < qty[m]` — материал нельзя назначить
поставщику без подтверждённого достаточного наличия. Реализация
(`backend/app/allocation/preprocess.py: split_orphaned_materials`,
`backend/app/allocation/solver.py:41`) трактует `availability IS NULL`
идентично "наличия недостаточно" (`price.availability is not None and
price.availability >= material.quantity` — `None` проваливает первую
часть условия). Это соответствовало исходной спеке: наличие — реальный,
поддерживаемый остаток на складе поставщика.

Реальный процесс Screen Factory Florida — другой. Цепочка такая:

1. Формируется проект (BOM) → расчёт распределения по ценам и условиям
   доставки → генерируется и отправляется ордер поставщику.
2. **Только после этого** поставщик подтверждает фактическое наличие. До
   отправки ордера в системе нет и не может быть актуального остатка —
   его никто не поддерживает вручную на каждый SKU каждого поставщика.

После недавнего импорта реальных прайсов (`backend/app/scripts/
import_real_data.py`) все 769 строк `Price.availability` — `NULL`
(в исходном CSV поставщиков этой колонки не было вовсе, задокументировано
явно при импорте). Итог: **каждый** материал в первом реальном проекте
попал в `orphaned_materials` (наличие "недостаточно" по построению — оно
нигде не подтверждено), и вся ILP-модель ушла в `status: "infeasible"`,
хотя формально у всех 28 позиций проекта есть актуальная цена от
нескольких поставщиков. Расчёт заблокирован данными, которые в принципе
не будут заполнены на этом этапе процесса — не из-за реальной нехватки
товара.

## Решение

`availability IS NULL` трактуется как "доступность не проверялась и не
блокирует расчёт" — **не** как "0 единиц в наличии". Инвертируется только
условие для `NULL`; явно указанное `availability = 0` или любое
недостаточное число по-прежнему исключает материал как раньше (это
осталось честным сигналом "поставщик заявил, что не хватает").

Меняются два места, оба обязаны остаться согласованными (одно и то же
правило допустимости пары `(m, s)`, ADR-0002 не вводит для них разную
семантику):

- `preprocess.split_orphaned_materials` (`has_sufficient` предикат):
  `price.availability is None or price.availability >= material.quantity`.
- `solver.py` (сборка `price[(m, s)]` для модели):
  `if p.availability is not None and p.availability < qty[p.material_id]:
  continue` — условие exclusion инвертируется симметрично: пропускать пару
  только когда `availability` явно задан и его недостаточно.

`_best_partial_offer` (частичное предложение для UI-подсказки в
`orphaned_materials`) не меняется — при `NULL` материал больше не попадает
в `orphaned` вообще, так что "лучшее частичное предложение" для него не
считается; это ветка кода теперь достижима только когда `availability`
явно проставлен, но недостаточен хотя бы у одного поставщика.

### Что не меняется

- `Price.availability` как поле — остаётся nullable `int`, схема БД не
  трогается. Это по-прежнему место для реального остатка, когда/если
  компания начнёт его поддерживать (например, после интеграции с ответом
  поставщика на ордер — см. "Не в объёме" ниже).
- `per_order_min_amount` (Ограничение 4 ADR-0002) не затрагивается —
  минимальная сумма заказа остаётся жёстким ограничением, это не про
  наличие.
- `docs/spec.md` §4.3 ("Материал недоступен ни у одного поставщика в
  нужном количестве → явный warning") продолжает работать как раньше —
  просто "недоступен" теперь означает "поставщик явно указал
  недостаточное количество", а не "количество не было указано вовсе".

## Не в объёме (сознательно отложено)

**Постфактум-корректировка заказа**, когда поставщик после отправки
ордера сообщает о нехватке конкретной позиции — пользователь хочет
пересчитать/перенести эту позицию на другого поставщика, не начиная
проект заново. Это отдельная будущая задача: требует либо a) редактируемого
`Order`/`OrderItem` с возможностью частичного перераспределения, либо
b) повторного запуска allocation над остатком проекта с временным
исключением проблемного `(material, supplier)`. Оба варианта — реальные
архитектурные решения, которые надо проектировать на конкретном сценарии
("что именно значит поменять уже отправленный заказ" — новый `Order`,
правка существующего, версионирование), не задним числом здесь. Условие
возврата: первый реальный случай отказа поставщика после отправки ордера,
когда будет видно, что именно должен уметь пользователь в этот момент.

## Альтернативы

**Дефолтить `availability` в БД на большое число (например, 999999) при
импорте вместо `NULL`.** Отклонено — искажает данные (утверждает
конкретное, заведомо неверное наличие) вместо честного "неизвестно". Также
не решило бы проблему для будущих цен, введённых вручную без указания
availability — пришлось бы помнить про дефолт в каждом месте записи
`Price`, а не один раз в правиле допустимости.

**Убрать availability-гейт полностью, включая явные `0`/недостаточные
значения.** Отклонено — если поставщик прямо сообщил о недостаточном
наличии (через ревью прайса или ручной ввод), это осмысленный сигнал,
который стоит уважать; проблема только в отсутствующих данных, не в
самой концепции проверки наличия.

## Последствия

- `backend/app/allocation/preprocess.py` и `backend/app/allocation/
  solver.py` — оба меняют один и тот же предикат синхронно; тест
  `test_material_with_null_availability_price_does_not_satisfy_and_is_not_partial`
  (`backend/tests/allocation/test_preprocess.py`) переименовывается и
  инвертируется под новое поведение (NULL → solvable, не orphaned).
- `AllocationRun.orphaned_materials` для существующих реальных данных
  (все `availability = NULL`) должен опустеть при следующем расчёте —
  прямая, наблюдаемая проверка того, что фикс сработал.
- `algorithm_version` (см. ADR-0002 "Последствия") должен отразить это
  изменение модели допустимости — это меняет, какие `(material, supplier)`
  вообще участвуют в оптимизации, не только детали реализации.
