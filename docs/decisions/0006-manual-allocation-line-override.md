# ADR-0006: Ручное переопределение поставщика на строке `AllocationLine`

Статус: Предложено

## Контекст

`docs/spec.md` §4.2 требует "возможность вручную переопределить назначение по
любой строке", и `docs/ui-reference.md` §3 уже описывает поведение на экране
результата (`/projects/:id/allocation`): select прямо в строке, индикатор
"изменено вручную" после правки, суммы по карточкам поставщиков
"пересчитываются на клиенте (без нового ILP-расчёта — просто арифметика)".
Экран сейчас (`frontend/src/routes/AllocationResultPage.tsx`) — только
отображение `AllocationRun`/`AllocationLine`, без какого-либо механизма
правки; backend не имеет emit-пути для изменения строки после
`run_allocation` (`backend/app/allocation/service.py`).

Это не новая идея, которую нужно придумывать с нуля — она заложена в дизайне
заранее. Не хватает: (1) где хранится факт override, (2) какому набору
поставщиков разрешено переопределение, (3) что происходит с бейджем
"не самая дешёвая цена" (сейчас вычисляется на клиенте сравнением
`line.unit_price` с `buildCheapestPriceIndex(prices)` —
`AllocationResultPage.tsx:117,237`), (4) точная формула пересчёта карточек
поставщиков, (5) персистентность.

ADR-0004 уже фиксировал урок на похожей границе "клиентское состояние vs
потеря при F5" (автосохранение черновика проекта) — тот баг класс не должен
повториться здесь молча.

Вне объёма этого ADR: повторный запуск ILP с "заморозкой" переопределённой
строки и пересчётом остального проекта — самостоятельная и более сложная
фича (возможно не нужна вовсе, если локальный перенос закрывает реальный
сценарий использования); проектирование Order (генерация ордер-документов) —
фиксируется здесь только как требование к будущей задаче, не проектируется.

## Решение

### 1. Где хранится факт override

Новые поля прямо на `AllocationLine` (`backend/app/models/allocation.py`):

```python
overridden_at: Mapped[datetime | None] = mapped_column(DateTime(timezone=True))
original_supplier_id: Mapped[uuid.UUID | None] = mapped_column(
    UUID(as_uuid=True), ForeignKey("suppliers.id")
)
original_unit_price: Mapped[float | None] = mapped_column(Numeric(12, 2))
```

По аналогии с `Price.source_import_id` — это атрибут происхождения текущего
значения строки (кто/что назначило текущего поставщика), а не независимая
сущность со своим жизненным циклом. `overridden_at` вместо `overridden: bool`
— заодно даёт "когда" бесплатно, что понадобится для объяснения в UI
("переопределено 14 марта") без дополнительного поля; `bool` пришлось бы
позже расширять тем же способом, каким `AllocationRun.status` избежал
третьего значения (ADR-0003) — здесь наоборот, поле уже осмысленно тройное
(`None` = не переопределялось, задано = когда), лишнего состояния не вводится.

`original_supplier_id`/`original_unit_price` дублируют то, что и так было в
строке до PATCH — сознательно: без них после переноса невозможно восстановить
"как это выглядело до override" для тултипа бейджа (см. п.3) и для
потенциального "отменить override" (не проектируется сейчас, но поля делают
его тривиальным добавлением UI без миграции).

**Отклонено: отдельная сущность `AllocationOverride`.** Понадобилась бы,
если нужна история *нескольких* переопределений одной строки (переопределили,
затем переопределили снова на третьего поставщика) — сейчас `PATCH`
семантически "замени текущее назначение", не "добавь запись в журнал", и ни
спека, ни ui-reference не описывают экран истории правок. `original_*` поля
всегда указывают на *исходное* ILP-решение, не на предыдущее состояние перед
последним PATCH — если пользователь переопределяет уже переопределённую
строку, `original_supplier_id`/`original_unit_price` не перезаписываются (см.
п.5, endpoint), иначе бейдж "не самая дешёвая цена" потерял бы возможность
сравнить с настоящим алгоритмическим решением после второй правки подряд.

### 2. Валидация нового поставщика

Обязательное условие: у нового поставщика есть активная `Price`
(`valid_to IS NULL`) на этот `material_id` — без цены переопределение
физически не может посчитать `unit_price`/`line_total`. Проверяется на
backend при `PATCH` (см. п.5), а не только в UI-select (React не должен быть
единственной защитой от несуществующей пары `(material, supplier)`).

По availability — override **разрешён поверх** явной недостаточности, не
блокируется:

- `availability IS NULL` — не блокирует и не требует предупреждения. Это
  симметрично ADR-0005 ("не проверялось" ≠ "недостаточно"): то же правило
  допустимости пары `(material, supplier)`, которое использует солвер,
  должно оставаться единым для автоматического и ручного назначения — иначе
  два пути допустимости расходятся без причины.
- `availability` явно указан и `< quantity` — backend всё равно принимает
  PATCH (пользователь может располагать контекстом, которого нет у солвера:
  звонил поставщику, знает о поступлении на этой неделе), но строка получает
  отдельный признак риска, независимый от "изменено вручную" — см. п.3.
  Фронтенд обязан показать это как видимое предупреждение на строке, не
  проглатывать молча.

**Отклонено: жёстко блокировать override при недостаточном availability**,
то же правило, что и для ILP (Ограничение 2, ADR-0002). Отклонено
пользователем явно: ручное решение человека не обязано подчиняться тому же
ограничению, что автоматический солвер — весь смысл ручного override в
задаче — исключение из автоматики для случаев, которые солвер не может
знать. Жёсткая блокировка вернула бы пользователя к "иди меняй `Price` в БД
вручную, чтобы обойти проверку", что хуже явного предупреждения.

### 3. Судьба бейджа "не самая дешёвая цена"

Бейдж не исчезает — меняется формулировка и природа сообщения, как уже
зафиксировано в `docs/ui-reference.md` §3 ("индикатор 'изменено вручную'").
Различаются два независимых факта на строке, оба могут быть true
одновременно:

- **"не самая дешёвая цена"** — алгоритмический факт: `unit_price` строки
  выше `min_s price[material][s]` среди актуальных цен. Вычисляется как
  сейчас, на клиенте (`buildCheapestPriceIndex`), не зависит от override.
- **"изменено вручную"** — факт наличия `overridden_at != null`. Новый
  бейдж/индикатор, показывается независимо.

Если строка одновременно дороже минимума и переопределена вручную —
показываются оба индикатора, но текст первого меняется: не "алгоритм
пожертвовал ценой ради консолидации доставки" (это было объяснение решения
солвера, которое здесь больше не действует — пользователь мог выбрать этого
поставщика вообще не из-за доставки), а нейтральное "дороже на $X за
единицу, чем у {supplier с минимальной ценой}" без утверждения о причине.
Причина в тултипе бейджа "изменено вручную" — "было: {original_supplier},
${original_unit_price}/ед.".

**Отклонено: бейдж исчезает после override.** Отклонено — сам факт "эта
строка не по минимальной цене" остаётся физически верным независимо от того,
кто принял решение (солвер или человек); скрыть его значило бы прятать
релевantную для контроля затрат информацию именно в момент, когда её
проверка важнее всего (человек только что вручную выбрал не самое дешёвое).

### 4. Пересчёт сумм

`PATCH` меняет одну строку и запускает пересчёт **обеих** затронутых карточек
поставщика (`SupplierAllocationSummaryOut` — старой и новой), не только
дельту по одной позиции. На backend (не на клиенте — см. п.5, почему), из
`Supplier.delivery_policy` (`flat_fee`, `free_shipping_threshold`,
`per_order_min_amount`):

Для затронутого поставщика `s` (старого и нового — применяется симметрично к
обеим карточкам):

1. Пересобрать множество строк, назначенных `s`, **из текущего состояния
   `AllocationLine` после PATCH** (не инкрементально "было + дельта" —
   слишком легко разойтись с реальностью, если когда-нибудь появится
   групповой PATCH нескольких строк за раз).
2. `goods_total[s] = Σ line_total` по этому множеству.
3. `free_shipping_achieved[s] = goods_total[s] >= free_shipping_threshold[s]`
   — пересчитывается с нуля, не патчится. Это прямо отвечает на риск,
   отмеченный в задаче: у старого поставщика `free_shipping_achieved` могла
   держаться именно на переносимой позиции — после пересчёта это может стать
   `false`, и `delivery_fee[old]` вырастет с `0` до `flat_fee[old]`. У нового
   поставщика симметрично обратное — добавленная позиция может перевести его
   через порог, `delivery_fee[new]` падает до `0`.
4. `delivery_fee[s] = 0 if free_shipping_achieved[s] else flat_fee[s]`.
5. Если у поставщика после переноса не осталось ни одной строки —
   `SupplierAllocationSummaryOut` для него убирается из ответа целиком (не
   строка с нулями) — совпадает с текущим поведением
   `AllocationResultPage.tsx:170` (`lines.filter` по `supplier_id`), где
   карточка без строк не имела бы смысла показывать.

**Что не пересчитывается автоматически, но проверяется как предупреждение:**
`per_order_min_amount[s]`. Если после переноса `goods_total[s] <
per_order_min_amount[s] * (кол-во строк s > 0)` — это не блокирует PATCH (в
отличие от ILP-ограничения 4 ADR-0002, здесь нет солвера, который отверг бы
решение целиком), но `SupplierAllocationSummaryOut` получает новое поле
`below_min_order: bool`, аналогично `free_shipping_achieved`, обязывающее UI
показать предупреждение на карточке. Причина не блокировать: у ILP это
жёсткое ограничение модели, потому что модель не может "почти" его
удовлетворить — а ручное решение человека имеет право временно нарушить
условие поставщика (например, он планирует добавить туда ещё позиций
следующим PATCH до генерации Order).

Это не "просто арифметика" в тривиальном смысле одной цифры — пересчитываются
`goods_total`, `free_shipping_achieved`, `delivery_fee`, `below_min_order`
для обеих карточек как результат пересборки суммы заново, а не патч дельтой.

**Визуальное представление `below_min_order`** (зафиксировано здесь и в
`docs/ui-reference.md` §3, чтобы не оставлять реализацию с "покажи
предупреждение" без конкретики): отдельная текстовая строка **под**
`supplierHeader` (между заголовком карточки и таблицей строк), на всю ширину
карточки, в стиле `warningRow`/`color-danger-text` — тот же цветовой язык,
что уже используют `warningBlock` (нехватка материала) и красный/зелёный
текст `supplierDelivery`, но без полноразмерного блочного padding
`warningBlock` (это не отдельное информационное событие уровня страницы, а
контекст одной карточки). Формат текста: "⚠ Сумма заказа {goods_total} меньше
минимальной {per_order_min_amount} — поставщик может отклонить заказ."
Причины именно такого размещения, а не альтернатив:

- **Не бейдж внутри `supplierHeader` рядом с суммой.** `supplierHeader` уже
  несёт три элемента (имя, "Доставка: …", итоговая сумма) в одну строку;
  добавление четвёртого условного элемента туда рискует переполнением строки
  при длинных именах поставщиков (`supplierName` уже не имеет `max-width`)
  ровно в тот момент, когда предупреждение наиболее важно показать целиком,
  не обрезанным.
- **Не изменение цвета/бейдж на `supplierTotal`.** `supplierDeliveryFree`
  (зелёный) читается однозначно как "хорошо" без подписи — этот паттерн
  работает для позитивного сигнала с одним значением. `below_min_order` требует
  указать *числа* (сколько не хватает до минимума), чтобы предупреждение было
  действием, а не просто тревогой без контекста — одного изменения цвета
  недостаточно, нужна отдельная строка с текстом.

Это добавляет новый CSS-класс в `AllocationResult.module.css` (например
`.belowMinOrderNotice`, аналог `.warningRow`, но в контексте `.supplierCard`,
не `.warningBlock`) — деталь реализации, но сам факт "отдельная строка под
хедером, не бейдж, не изменение цвета суммы" — часть этого решения, не
оставляется на импровизацию при кодировании.

### 5. Персистентность

`PATCH` на backend, обязателен — не отображение только на клиенте.

```
PATCH /projects/{project_id}/allocations/{run_id}/lines/{line_id}
{ "supplier_id": "<uuid нового поставщика>" }
```

Single-field PATCH без diff-семантики, тем же стилем, что `ProjectUpdate`
(ADR-0004) — единственное редактируемое поле, `quantity`/`material_id`
строки не меняются override'ом (перенос назначения, не редактирование состава
BOM).

Backend при обработке:
1. Валидирует новую пару `(material_id, supplier_id)` — активная `Price`
   существует (п.2).
2. Если `original_supplier_id IS NULL` на строке (первый override) —
   записывает туда текущие `supplier_id`/`unit_price` **до** их замены.
   Если уже не `NULL` (повторный override той же строки) — не трогает
   `original_*`, обновляет только `supplier_id`/`unit_price`/`overridden_at`.
3. Пересчитывает и возвращает обновлённые `SupplierAllocationSummaryOut` для
   старого и нового поставщика (п.4) — либо как часть ответа на `PATCH`, либо
   клиент делает `GET` всего `AllocationRun` заново; выбор конкретного
   contract — деталь реализации, не архитектурное решение.

Пересчёт (п.4) выполняется **на backend**, не на клиенте, в отличие от
формулировки в `ui-reference.md` §3 ("пересчитываются на клиенте — просто
арифметика"). Это осознанное отступление от того текста: раз PATCH всё равно
обязателен (см. ниже, почему), backend — источник истины по деньгам согласно
CLAUDE.md принципу 4 ("все денежные и количественные операции — только на
backend"), и если пересчёт на клиенте и backend когда-нибудь расходится
(например, из-за устаревшего `delivery_policy` в кэше фронтенда), это скрытый
источник неверных сумм ровно там, где пользователь принимает решение вручную.
`ui-reference.md` §3 обновляется вместе с этим ADR, чтобы не противоречить.

**Почему PATCH обязателен, а не отображение на клиенте:** ADR-0004 уже
зафиксировал урок на этой же границе (черновик проекта, потерянный при F5
без `replace`-навигации и персистентности). Здесь тот же класс риска —
хуже: если override не сохраняется на backend, F5 откатывает строку к
исходному ILP-решению молча, и пользователь не может отличить "override
пропал" от "override всё еще применяется, просто это визуальный баг" — оба
выглядят одинаково (страница показывает исходные данные). Худший исход —
пользователь считает, что переопределение действует, уходит подтверждать
Order, а Order генерируется по исходным (не переопределённым) данным, потому
что визуальное состояние никогда не попало в БД.

**Отклонено: чисто клиентское состояние (React state), без PATCH.**
Отклонено по причине выше — повторение ADR-0004 класса бага, только с
денежными последствиями (неверный Order) вместо потерянного черновика.

### 6. Генерация Order (требование к будущей задаче)

Не проектируется в этом ADR. Фиксируется как обязательное требование:
генерация `Order`/`OrderItem` (будущая задача, не реализована) должна читать
**текущее** состояние `AllocationLine` (`supplier_id`/`unit_price` после
возможных override), не исходный результат `run_allocation()`. Раз override
персистентен (п.5) и читает/пишет ту же таблицу, это происходит естественно
при условии, что задача генерации Order не будет ошибочно кэшировать
"исходный" `AllocationLine` где-то по пути — явно проверить при
проектировании той задачи.

## Альтернативы

Альтернативы для каждого под-решения перечислены инлайн в соответствующих
разделах "Решение" (1–5) — они специфичны к конкретному вопросу, а не к ADR
как целому, и вынесение их в общий список ниже потеряло бы привязку к
обоснованию.

Единственная альтернатива на уровне ADR целиком: **не делать локальный
override, вместо этого сразу проектировать "перезапуск ILP с заморозкой
одной позиции"** (пользователь фиксирует материал за поставщиком, остальное
пересчитывается). Отклонено для этой задачи — явно вынесено в "Не в объёме"
в `docs/spec.md`-контексте выше: это качественно другая фича (нужно решить,
что происходит с ограничением 4 ADR-0002 для *остальных* материалов после
заморозки одной пары, возможна повторная инфизибельность), не расширение
текущей. Если понадобится позже — отдельный ADR, не пересмотр этого.

## Последствия

- Миграция Alembic: три новых nullable-колонки на `allocation_lines`
  (`overridden_at`, `original_supplier_id` FK, `original_unit_price`) — без
  бэкафилла, существующие строки получают `NULL` (означает "не
  переопределялось", корректно для всех строк, созданных до этого ADR).
- `SupplierAllocationSummaryOut` получает новое поле `below_min_order: bool`
  — расширение существующей схемы (`backend/app/api/schemas/allocation.py`),
  ломает контракт для любого клиента, который валидирует точный набор полей
  (сейчас единственный клиент — `AllocationResultPage.tsx`, не валидирует
  строго).
- `AllocationLineOut` получает новые опциональные поля
  (`overridden_at`/`original_supplier_id`/`original_unit_price`) для тултипа
  бейджа.
- Новый endpoint `PATCH /projects/{project_id}/allocations/{run_id}/lines/{line_id}`
  — `backend/app/api/allocation.py`, вложен под тот же `prefix="/projects/{project_id}"`,
  что и весь остальной allocation-роутер (не отдельный top-level `/allocation-runs/...`,
  как в первом черновике этого ADR) — так endpoint получает `project_id` в пути и может
