# ADR-0007: Order — снимок при создании, сверка `quoted_price` vs `confirmed_price`

Статус: Предложено

## Контекст

`docs/spec.md` §5 и текущая модель (`backend/app/models/order.py`,
`docs/data-model.md`) описывают `Order`/`OrderItem` как финальный документ:
`status(draft/approved/sent)`, `OrderItem{material_id, quantity, unit_price}`
— один `unit_price` на позицию, без различия "что мы посчитали" и "что
подтвердил поставщик". Кнопка "Подтвердить и создать ордера" на
`AllocationResultPage.tsx:265` — disabled-заглушка (`title="Генерация
ордеров — скоро"`), backend не имеет endpoint для создания `Order`.

Реальный процесс компании (описан пользователем, не задокументирован раньше
нигде в `docs/`): сотрудник по каждому проекту формирует список материалов на
поставщика (= карточка поставщика на экране результата аллокации,
`SupplierAllocationSummaryOut`), отправляет поставщику, поставщик присылает
**свои** цены в ответ — они могут отличаться от того, что рассчитала система
(прайс в БД устарел, поставщик даёт другую цену по телефону/email, ошибка
данных). Сотрудник сравнивает и решает, что делать с расхождением. Ни спека,
ни текущая схема не покрывают этот шаг вообще — он просто не существовал в
системе до этого ADR.

Два архитектурных прецедента, которые это решение обязано соблюдать:

- **ADR-0006, "снапшот, не кэш".** `AllocationLine.original_*` уже применяет
  этот принцип к переносу поставщика: сохранить, что было, не пересчитывать
  из живой связи. Order — снимок на ещё один уровень глубже: не просто "что
  было в `AllocationLine` до override", а "что было в `AllocationLine` в
  момент, когда Order создан", независимо от всех последующих правок.
- **CLAUDE.md принцип 4** — денежные операции только на backend. Сравнение
  `quoted` vs `confirmed`, дельта в $/%, порог "существенно" — весь расчёт на
  backend, frontend только отображает готовые числа.

Не в объёме этого ADR (см. "Не в объёме" в задаче): автоматическая отправка
Order поставщику (email/API) — вручную; массовый импорт `confirmed_price` из
файла/письма поставщика — структурно та же задача, что ingestion прайсов,
отдельный ADR при необходимости.

## Решение

### 1. Схема `OrderItem`

```python
class OrderItem(UUIDPKMixin, Base):
    __tablename__ = "order_items"

    order_id: Mapped[uuid.UUID] = mapped_column(ForeignKey("orders.id"), nullable=False)
    material_id: Mapped[uuid.UUID] = mapped_column(ForeignKey("materials.id"), nullable=False)
    quantity: Mapped[int] = mapped_column(nullable=False)

    quoted_price: Mapped[float] = mapped_column(Numeric(12, 2), nullable=False)
    confirmed_price: Mapped[float | None] = mapped_column(Numeric(12, 2))
    confirmed_at: Mapped[datetime | None] = mapped_column(DateTime(timezone=True))
```

`unit_price` (существующее поле) переименовывается в `quoted_price` — не
остаётся как алиас. Причина переименовать, а не добавить поле рядом со
старым именем: `unit_price` без квалификатора становится двусмысленным в ту
же секунду, как в таблице появляется второе число — любой будущий код,
который прочитает `item.unit_price`, не может знать без похода в схему,
имеется в виду "что мы посчитали" или "что подтвердил поставщик". Тот же
инстинкт, что уже привёл к `original_supplier_id`/`original_unit_price` в
ADR-0006 (явные, не обобщённые имена).

- **`quoted_price: Numeric(12,2) NOT NULL`** — снимок `AllocationLine.unit_price`
  на момент создания `Order`. Обязательное, потому что `Order` не может
  существовать без цены, по которой его создали.
- **`confirmed_price: Numeric(12,2) NULL`** — то, что реально подтвердил
  поставщик. `NULL` = "ещё не сверено", не "подтверждено с ценой 0" —
  та же логика различения отсутствия данных от нулевого значения, что уже
  применена к `availability` (ADR-0005) и `overridden_at` (ADR-0006): триста
  раз использованный в этом проекте паттерн "nullable-поле как признак
  состояния", не изобретается заново, а продолжается.
- **`confirmed_at: DateTime | NULL`** — когда сотрудник ввёл `confirmed_price`.
  Не `confirmed: bool` — по той же причине, что `overridden_at` вместо
  `overridden: bool` в ADR-0006: "когда" бесплатно достаётся из timestamp,
  и если позже понадобится "кто" (в текущей однопользовательской системе
  избыточно, см. `docs/known-issues.md` про масштаб), `confirmed_at`
  расширяется до пары (`confirmed_at`, `confirmed_by`) без миграции самого
  факта подтверждения.

**Отклонено: `confirmed_price` как обязательное поле с дефолтом
`= quoted_price`.** Это стёрло бы различие "поставщик подтвердил именно эту
цену" от "мы ещё не спрашивали" — весь смысл сверки в том, чтобы отличать
позиции, где ответ уже получен, от тех, где сотрудник ещё ждёт. `NULL`
обязателен для этого, не 0 и не копия `quoted_price`.

**Отклонено: хранить дельту (`price_delta`/`price_delta_pct`) как
персистентную колонку.** Вычисляемое значение из двух других колонок —
хранить его отдельно означает либо пересчитывать при каждом PATCH
`confirmed_price` (тогда это не более надёжно, чем считать на лету), либо
рисковать рассинхроном, если пересчёт когда-то забудут вызвать. Дельта
считается на backend при чтении (API-слой, п.4), не в БД.

### 2. Генерация `Order` — снимок, не живая ссылка

`POST /projects/{project_id}/allocations/{run_id}/orders` (создаёт по одному
`Order` на каждого поставщика из текущего `supplier_summaries` этого run —
после всех override, симметрично тому, как уже читается текущее состояние
для отображения карточек). Для каждого поставщика:

1. Собрать все `AllocationLine` этого run с `supplier_id = s` **из текущего
   состояния таблицы** (та же логика выборки, что уже строит
   `SupplierAllocationSummaryOut`, ADR-0006 п.4) — не из какого-либо
   закэшированного списка со страницы результата.
2. Создать `Order{project_id, supplier_id: s, status: "draft",
   total_amount, delivery_fee}` и по одному `OrderItem` на каждую строку:
   `quoted_price = AllocationLine.unit_price` в момент записи. `quantity`
   копируется, не связывается foreign key на `AllocationLine` — умышленно
   (см. ниже).
3. `AllocationLine` получает новое поле `ordered_at: DateTime | NULL` —
   проставляется на все строки, вошедшие в созданные Order, в той же
   транзакции.

**`OrderItem` не хранит `allocation_line_id`.** Копирует
`material_id`/`quantity`/`quoted_price` как значения, не как ссылку.
Обоснование — то же самое "снимок, не кэш", доведённое до конца: если
`OrderItem` держит FK на `AllocationLine` и код где-то по пути (отчёт,
будущий экран) джойнит через эту связь вместо чтения собственных полей
`OrderItem`, он молча перечитывает **текущую**, а не историческую c`unit_price`
— в точности тот баг-класс, который этот ADR должен исключить. Явно
скопированные значения физически не могут "утечь" в живое состояние.

**`AllocationLine.ordered_at` — маркер "по этому расчёту уже создан Order",
не блокировка.** Отвечает на явно поставленный в задаче вопрос: да,
`AllocationLine` помечается. `ordered_at` (не `bool`) — тот же паттерн
timestamp-как-признак, что и `overridden_at`, `confirmed_at`. Он **не
запрещает** дальнейший PATCH-override той же строки (ADR-0006) — блокировать
override после создания Order лишило бы пользователя возможности
скорректировать план для *следующего* заказа по этому же проекту, а такой
сценарий (доразмещение, повторная закупка) спека не исключает. Вместо
блокировки — предупреждение (следующий абзац).

**Механизм предупреждения о расхождении Order/AllocationLine после
override.** Если пользователь делает PATCH на строку, у которой
`ordered_at IS NOT NULL`, PATCH выполняется как обычно (ADR-0006 не
переопределяется), но ответ `AllocationLineOut` и экран результата
показывают дополнительный признак: `ordered_at` само по себе уже достаточный
сигнал для фронтенда — если `ordered_at != null` **и** строка была
переопределена **после** этого (`overridden_at > ordered_at`), это и есть
условие расхождения, вычисляется на клиенте из двух timestamp'ов, без нового
поля на backend. Это не нарушение CLAUDE.md принципа 4: принцип запрещает
клиенту пересчитывать *деньги* (суммы, дельты, итоги — арифметику, которая
может разойтись с backend при устаревшем кэше или иной формуле); сравнение
двух timestamp'ов, оба уже посчитанные и отданные backend'ом как есть
(`overridden_at`, `ordered_at` — не производные, а прямые колонки), это
не денежная операция и не может дать иной результат, чем тот же `>`-тест на
backend — в отличие от `price_delta` (п.4), который *является* денежной
величиной (вычитание/деление цен) и поэтому явно вынесен на backend. Строка
получает видимый бейдж "изменено после отправки ордера" (отдельный от "изменено вручную" — тот показывает сам факт
override, этот — что Order уже существует и не отражает текущее состояние).
Тултип: "Ордер для {supplier} уже создан {ordered_at}; это изменение в него
не попадёт — при необходимости обновите вручную или создайте новый Order."
Не блокирует, не откатывает Order автоматически — тот же принцип, что уже
применён к `below_min_order` в ADR-0006 (предупреждение, не запрет, потому
что человек может иметь контекст, которого нет у системы).

**Отклонено: блокировать создание нового Order, если для этого run уже
существуют Order-а с непустым пересечением поставщиков.** Не в объёме —
компания может физически захотеть дозаказ по тому же проекту тем же
поставщиком (частичная поставка, добавление позиции). Ничего в спеке или
`ui-reference.md` не описывает такой запрет; вводить его сейчас — придумывать
ограничение, не подтверждённое реальным процессом. Кнопка на экране
результата просто создаёт Order-а заново по текущему состоянию каждый раз,
когда нажата (как `run_allocation` уже создаёт новый `AllocationRun` при
каждом заходе — см. `docs/known-issues.md`, тот же прецедент необязательной
дедупликации).

### 3. Ввод `confirmed_price` — построчное редактирование (MVP)

Новый экран/секция `OrderDetailPage` (`/orders/:id`, ещё не существует) —
таблица `OrderItem` с редактируемой ячейкой `confirmed_price` по аналогии с
редактированием `quantity` на `ProjectDetailPage` (inline, сохранение по
`blur`/`Enter`, `PATCH` одного поля). Endpoint:

```
PATCH /orders/{order_id}/items/{item_id}
{ "confirmed_price": 12.50 }
```

Backend проставляет `confirmed_at = now()` при получении непустого
`confirmed_price`; если пришло `null` явно (снять подтверждение — опечатался,
хочет отменить) — `confirmed_at` тоже сбрасывается в `null`, не оставляется
висеть с устаревшим timestamp при пустой цене.

**Отмечено как "не в объёме сейчас", не спроектировано:**
- Вставка списка цен (paste из Excel/письма поставщика построчно) —
  удобнее для реального объёма позиций в ордере, но требует парсинга
  вставленного текста и сопоставления строк по порядку/названию — не
  тривиальный inline-edit, ближе по сложности к ingestion-задаче.
  Кандидат для отдельного ADR, если построчный ввод окажется на практике
  слишком медленным (десятки позиций на ордер).
- Массовый импорт из файла/ответа поставщика — явно исключено в
  постановке задачи, та же причина.

### 4. Визуальное сравнение quoted vs confirmed

На экране `OrderDetailPage`, построчно: `quoted_price`, `confirmed_price`
(редактируемая ячейка), дельта `confirmed_price − quoted_price` в $ и %
рядом — считается на backend, отдаётся как часть `OrderItemOut`
(`price_delta`, `price_delta_pct`, оба `null` пока `confirmed_price IS
NULL` — нет базы для сравнения, дельта неопределена, не 0).

**Порог "существенное расхождение": `|price_delta_pct| > 10%`, константа,
не настраиваемая в MVP.** Не тот же порог, что `>20%` для роста цены прайса
на экране ревью (`docs/spec.md` §3, `docs/ui-reference.md` §1) — умышленно
другое число, а не заимствование "раз есть прецедент 20%, возьмём тот же".
Обоснование разницы:

- Порог `>20%` в ревью прайса — фильтр на *данные, которые в принципе
  попадут в БД и повлияют на все будущие расчёты*: у него высокая цена
  ложного срабатывания в другую сторону (пропустить реальный скачок цены
  портит все последующие allocation), поэтому порог выбран сравнительно
  высоким — не заваливать ревьюера паникой на каждую мелкую правку.
- Порог здесь — сигнал на *единичную позицию единичного заказа, уже
  отправленного*, который сотрудник и так листает вручную (сверка — по
  определению построчный процесс, п.3). Более низкий порог (10%) уместнее,
  потому что цена ложного срабатывания ниже (это подсветка внимания на
  экране, который и так открыт для просмотра, не автоматическое действие),
  а расхождение поставщика при подтверждении заказа — типично более частый
  и более мелкий шум (округления, локальные корректировки), чем скачок
  цены между PDF-прайсами через месяцы.

Строка подсвечивается (тот же язык, что `--color-danger-text` /
`warningRow`, уже используемый в ADR-0006 п.4 для `below_min_order` —
переиспользование установленного визуального словаря, не новый паттерн) при
`|price_delta_pct| > 10`. Карточка Order в целом получает сводный
индикатор "N позиций с расхождением >10%", если таких больше нуля —
по аналогии с тем, как `AllocationResultPage` уже суммирует предупреждения
на уровне карточки поставщика, не только на уровне строки.

**Отклонено: настраиваемый порог (поле в UI или конфиге).** Явно указано в
задаче как предпочтение для MVP — константа. Backend-константа
(`SIGNIFICANT_PRICE_DELTA_PCT = 10`, рядом с местом расчёта дельты, по
аналогии с тем, как `ALGORITHM_VERSION` уже живёт как константа в
`service.py`), не БД-настройка — превратить в настройку тривиально позже,
если понадобится, без изменения структуры данных.

### 5. Влияние на `Price` — без автоматической связи

Расхождение `confirmed_price` от `Price.price` в БД **не порождает никакого
автоматического действия** — ни предложения обновить `Price`, ни очереди на
ревью, ни уведомления. Это явное решение, не умолчание: сотрудник видит
расхождение на экране Order, и если считает нужным поправить цену в базе —
делает это вручную через существующий `/prices`-экран, отдельным,
несвязанным действием.

Обоснование: связка "расхождение в Order → предложение обновить Price" —
структурно ещё один matching/review pipeline (тот же класс задачи, что
прайс-импорт, принцип 2 CLAUDE.md — "ничего не пишется в боевые таблицы
автоматически"), только с другим источником входа (не PDF, а ручной ввод
сотрудника). Проектировать его сейчас означало бы решать задачу, для
которой пока нет данных о частоте и характере реальных расхождений (то же
рассуждение, что уже отложило атрибуцию min-order-инфизибельности в
ADR-0003 — не готовы проектировать вслепую). Если систематические
расхождения окажутся частым паттерном на практике — отдельный будущий ADR
с реальными данными о том, как именно они происходят (единичные опечатки?
устаревший прайс конкретного поставщика? сезонный рост цен?).

### 6. Документ для поставщика — минимальный вариант, отдельный от сверки

Генерация документа происходит **сразу при создании Order** (в рамках
операции из п.2), не откладывается до сверки. Для MVP: HTML-страница
`/orders/:id/print` (React route, отдельный от `OrderDetailPage`,
или тот же экран с `@media print` стилями) — таблица позиций (материал,
кол-во, `quoted_price`, сумма), итого, доставка, реквизиты поставщика
(`Supplier.name`/контакты). Отправка — печать в PDF средствами браузера
(`Ctrl+P` → "Save as PDF") или прямая отправка ссылки/скриншота, вручную
сотрудником. Не генерируется файл на backend, не сохраняется `file_ref` в
MVP — поле `Order.file_ref` в текущей схеме (`docs/spec.md` §5) остаётся
неиспользуемым до отдельной задачи "настоящий PDF/DOCX-шаблон", явно
зафиксировано как несделанное, не забытое.

Показывает **`quoted_price`, только его** — на момент генерации документа
`confirmed_price` ещё не существует по построению (сверка происходит
позже, после ответа поставщика, п.7). `OrderDetailPage` (внутренний экран
сверки, п.3–4) и `/orders/:id/print` (внешний документ для поставщика) —
физически разные роуты/компоненты, не один экран с переключателем режима:
они обслуживают разных читателей (поставщик снаружи vs сотрудник внутри) в
разные моменты жизненного цикла Order, смешение усложнило бы оба сценария
ради экономии одного файла.

**Отклонено для MVP: серверная генерация PDF (шаблонизация →
WeasyPrint/аналог).** Соответствует `docs/spec.md` §6 ("шаблонизация → PDF/
DOCX") как будущее направление, но не обязательно для того, чтобы кнопка
"Подтвердить и создать ордера" перестала быть заглушкой — печать из браузера
закрывает реальную потребность ("уходит поставщику документ") с кратно
меньшим объёмом работы. Явно оставлено как будущее расширение, не
пересмотр.

### 7. Статусная модель — без нового статуса

`Order.status` остаётся `draft/approved/sent` (`docs/spec.md` §5), без
добавления `"awaiting_confirmation"`/`"reconciled"` или аналогичного.
"Жду ответа поставщика" и "сверено" читаются из существующих/новых полей
`OrderItem`, не из отдельного статусного поля на `Order`:

- **"Жду ответа поставщика"** — производное состояние: `status = "sent"` и
  хотя бы один `OrderItem.confirmed_price IS NULL`. Не персистентное поле —
  вычисляется на чтении (тот же принцип, что и `price_delta`, п.1: не
  хранить то, что тривиально выводится из существующих данных).
- **"Сверено"** — производное: все `OrderItem` этого `Order` имеют
  `confirmed_price IS NOT NULL`. Тоже не отдельное поле на `Order`.

Обоснование, ссылаясь на ADR-0003 (как явно запрошено в задаче): ADR-0003
отказался вводить третий статус `AllocationRun` ("partial"), потому что у
модели физически нет промежуточного состояния между "решено" и "не решено"
— решение было бинарным по природе задачи. Здесь другая форма того же
урока: "сверено" — не независимый факт о жизненном цикле Order, а чистая
агрегация уже существующего состояния его позиций (`confirmed_price` на
каждой). Ввести отдельное поле `Order.reconciled: bool` означало бы держать
вычисляемое значение как персистентное — тот же класс риска рассинхрона,
что уже отклонён для `price_delta` в п.1: PATCH одной позиции (`OrderItem`)
обязан был бы не забыть пересчитать и обновить поле на родителе (`Order`),
а конкурирующий источник истины (реальные значения `confirmed_price`) и так
уже отвечает на вопрос без него.

`status` продолжает означать ровно то, что уже означает (стадия
человеческого одобрения самого документа — черновик/одобрен/отправлен
поставщику), сверка цен — ортогональная ось состояния, не следующая ступень
той же лестницы статусов. Смешать их в одну статусную машину
(`draft → approved → sent → awaiting → reconciled`) добавило бы состояние,
которое не описывает переход документа, а описывает прогресс по чужому
подмножеству данных — именно то избыточное разрастание, от которого
предостерегает прецедент ADR-0003.

**Отклонено: `status = "reconciled"` как терминальное состояние после
`"sent"`.** Отклонено по причине выше — превращает агрегацию в
персистентный факт, вводит риск рассинхрона без выигрыша (UI и так может
посчитать агрегацию на каждый рендер списка ордеров, это не дорогая
операция при MVP-масштабе, `docs/known-issues.md` уже фиксирует прецедент
"не оптимизировать раньше времени": нет пагинации на нескольких списковых
endpoint'ах).

## Альтернативы

Альтернативы для каждого под-вопроса перечислены инлайн в "Решение" (1–7) —
та же структура, что уже принята в ADR-0006, по той же причине: обоснования
специфичны к конкретному под-решению, общий список ниже потерял бы привязку
к контексту отклонения.

Единственная альтернатива на уровне ADR целиком: **не разделять
`quoted`/`confirmed`, вместо этого держать один `unit_price` и отдельную
таблицу `OrderPriceRevision` (журнал изменений цены во времени)**.
Отклонено — избыточно для реального процесса (один раунд "отправили →
ответили", не многократные ревизии одной цены), тот же класс решения, что
уже отклонён в ADR-0006 п.1 (`AllocationOverride` как отдельная сущность):
нужна, только если требуется история *нескольких* значений, а не текущее
"было/стало" из двух полей.

## Последствия

- Миграция Alembic: переименование `order_items.unit_price` →
  `order_items.quoted_price` (данных в проде нет — таблица пустая, кнопка
  создания Order ещё не работала никогда, поэтому это `ALTER COLUMN
  RENAME`, не требует backfill/совместимости); плюс новые колонки
  `confirmed_price NUMERIC(12,2) NULL`, `confirmed_at TIMESTAMPTZ NULL`.
  Отдельная миграция: `allocation_lines.ordered_at TIMESTAMPTZ NULL`
  (nullable, без бэкафилла — все существующие строки не были ни в одном
  Order, `NULL` корректен для всех).
- Новые endpoints:
  `POST /projects/{project_id}/allocations/{run_id}/orders` (создание,
  п.2), `PATCH /orders/{order_id}/items/{item_id}` (ввод confirmed_price,
  п.3). Существующая заглушка кнопки на `AllocationResultPage.tsx:265`
  становится реальным вызовом первого endpoint.
- Новый экран `OrderDetailPage` (`/orders/:id`) и печатный вид
  (`/orders/:id/print`) — не существуют сейчас, требуют дизайна в Claude
  Design (`docs/design/`) перед реализацией по правилу CLAUDE.md ("не
  редактировать HTML руками, генерировать заново").
- `OrderItemOut`/`OrderOut` (Pydantic-схемы, ещё не существуют или
  минимальны) получают поля `quoted_price`, `confirmed_price`,
  `confirmed_at`, вычисляемые `price_delta`/`price_delta_pct`.
- `docs/data-model.md`: `OrderItem.unit_price` → `quoted_price` +
  `confirmed_price`/`confirmed_at`; `AllocationLine` получает `ordered_at`
  как поле "добавлено сверх исходной диаграммы", по образцу уже
  задокументированных `status`/`orphaned_materials`/`overridden_at`.
- `docs/ui-reference.md` получает новый раздел (следующий по номеру после
  §5 "Генерация ордера") с поведением `OrderDetailPage`: построчный ввод,
  подсветка `>10%`, бейдж "изменено после отправки ордера" на
  `AllocationResultPage`, когда `overridden_at > ordered_at` строки.
- Реализация (endpoints, миграции, оба новых экрана, дизайн в Claude
  Design) — предмет отдельной задачи после вычитки этого ADR, как и было с
  предыдущими ADR в этом проекте.
