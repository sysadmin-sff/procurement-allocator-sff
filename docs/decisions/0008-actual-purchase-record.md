# ADR-0008: `PurchaseRecord` — фактическая закупка как отдельный, несвязанный с планом журнал

Статус: Предложено

## Контекст

ADR-0007 решает более узкую задачу: `OrderItem.confirmed_price` — поставщик
подтверждает **цену** по той же паре `material_id`+`supplier_id`, что уже
зафиксирована в `AllocationLine`/`Order`. Пользователь показал реальный
пример (Excel-скриншот), который эту предпосылку не соблюдает:

- План (`Order` для одного поставщика) — 12 строк, наши канонические
  названия материалов (`Material.canonical_name`).
- Факт ("заказали по факту") — 9 строк, названия такие, как их пишет
  сотрудник, глядя на переписку/счёт поставщика (`84" PREMIER SCREEN
  18/14"` вместо `.18/14 Regular x 100' Rolls x 84"`) — не обязаны
  матчиться ни на `Material.canonical_name`, ни на существующий
  `SupplierMaterialAlias`.
- Количество строк не совпадает — часть позиций объединилась при реальном
  заказе (укрупнение партии, слияние двух похожих позиций в одну строку
  счёта поставщика).
- Часть позиций из плана по факту ушла **другому поставщику**, не тому, для
  которого их считал `AllocationRun`/`Order`.

Это ломает не только "цена может отличаться" (ADR-0007), а саму привязку:
факт может не иметь ни `material_id`, ни того же `supplier_id`, ни даже
того же количества строк, что план. `OrderItem` физически не может принять
такую запись — он живёт внутри одного `Order` (один `supplier_id` на весь
документ, `docs/data-model.md`), а факт по определению может пересекать
границы нескольких `Order` одного проекта.

Не в объёме этого ADR (см. "Не в объёме" в задаче):
- Автоматическое сопоставление строк плана и факта по похожести текста —
  структурно та же задача, что matching прайс-импорта (принцип 2
  CLAUDE.md: LLM только на неструктурированном входе, всегда с ревью
  человеком) — не проектируется здесь, см. п.3.
- Влияние факта на `Price`/будущие allocation-расчёты — по аналогии с тем,
  как ADR-0007 §5 уже отложил тот же вопрос для `confirmed_price`: сотрудник
  видит расхождение, правит `Price` вручную через `/prices`, если считает
  нужным, без автоматической связи.

## Решение

### 1. Новая сущность `PurchaseRecord` — не расширение `OrderItem`

```python
class PurchaseRecord(UUIDPKMixin, Base):
    __tablename__ = "purchase_records"

    project_id: Mapped[uuid.UUID] = mapped_column(
        ForeignKey("projects.id"), nullable=False
    )
    supplier_id: Mapped[uuid.UUID] = mapped_column(
        ForeignKey("suppliers.id"), nullable=False
    )
    raw_description: Mapped[str] = mapped_column(String, nullable=False)
    quantity: Mapped[int] = mapped_column(nullable=False)
    unit_price: Mapped[float] = mapped_column(Numeric(12, 2), nullable=False)

    material_id: Mapped[uuid.UUID | None] = mapped_column(
        ForeignKey("materials.id")
    )

    created_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True), server_default=func.now()
    )
```

`raw_description` — обязательное свободное поле, ровно то, что сотрудник
видит у поставщика (`84" PREMIER SCREEN 18/14"`). Никакой валидации против
`Material`/`SupplierMaterialAlias` — по построению, это facts as reported,
не facts as canonicalized.

`material_id` — **опциональная** ссылка, не обязательная и не блокирующая:
сотрудник может (если узнаёт материал и есть время) явно связать строку
факта с каноническим материалом для будущей аналитики "сколько реально
потратили на материал X за всё время, а не только по плану". Она не
участвует ни в каком расчёте в этом ADR — чисто аннотация для будущего
использования. Заполняется вручную через select на экране (п.5), не
через matching-пайплайн (это и был бы п.3, явно не в объёме).

**Почему не поле/набор полей на `OrderItem`.** `OrderItem` привязан к
одному `Order`, у которого один `supplier_id` на весь документ
(`docs/data-model.md`: `Order{project_id, supplier_id, ...}`). Пример
пользователя прямо нарушает это: позиция, которую планировали у
поставщика A, по факту ушла к поставщику B. Если бы факт хранился как
поле на `OrderItem` поставщика A, для этого случая пришлось бы либо (а)
переносить `OrderItem` между `Order` разных поставщиков (искажает Order
как "снимок отправленного документа", тот же принцип "снимок, не кэш",
который ADR-0007 п.2 уже защищает для `quoted_price` — Order обязан
оставаться тем, что реально ушло поставщику A, независимо от того, что
случилось по факту), либо (б) заводить дублирующую строку в "чужом"
`Order`, что бессмысленно — `Order` для поставщика B никогда не
создавался и создавать его задним числом только чтобы приютить одну
строку факта — искусственно. Отдельная сущность без FK на `OrderItem`
снимает вопрос целиком: факт просто указывает, к какому поставщику он
реально относится, независимо от того, существует ли для этого поставщика
`Order` в этом проекте вообще.

**Отклонено: `PurchaseRecord.order_id` (nullable FK на `Order`) как
опциональная привязка "если совпало".** Рассматривалось как компромисс —
заполнять, когда факт очевидно относится к тому же `Order`, оставлять
`NULL`, когда ушло к другому поставщику. Отклонено: вводит два разных
режима чтения одной и той же сущности (иногда факт привязан к документу,
иногда нет) без алгоритма, который бы решал, когда это делать — сотрудник
делал бы то же самое сравнение "план vs факт", которое и так делает
визуально на экране (п.3), только заранее и без явного запроса задачи на
это. `project_id` + `supplier_id` уже дают достаточную группировку для
всех сценариев контроля в п.4, третье измерение привязки не добавляет
ничего, кроме риска, что поле останется `NULL` из лени и данные станут
непоследовательными (одни записи привязаны, другие нет, без понятной
причины разницы).

### 2. Гранулярность — project-level, не order-level

`PurchaseRecord.project_id` — обязательное поле верхнего уровня привязки;
`Order`/`AllocationLine` не участвуют вообще. Обоснование:

- Пример пользователя прямо демонстрирует, что факт **пересекает границы**
  плановых `Order` (позиция ушла другому поставщику) — если бы факт
  требовал `order_id`, этот сценарий был бы непредставим без описанного
  выше искусственного создания "чужого" `Order`.
- `supplier_id` на самой записи (не выведенный из `Order.supplier_id`)
  делает факт самодостаточным: запись сама говорит "у этого поставщика
  реально купили это", не полагаясь на существование планового документа
  для этого поставщика в этом проекте. Поставщик, у которого по факту
  что-то купили, но который не участвовал в `AllocationRun`/`Order`
  вообще (сотрудник заказал у нового/незапланированного поставщика "с
  колёс") — обычный случай для этой модели, не крайний.
- Проект — естественная единица бюджетного контроля (п.4): "сколько
  потратили на этот проект всего" и "сколько потратили у этого поставщика
  по этому проекту" — обе метрики строятся из `project_id`+`supplier_id`
  без необходимости в `order_id`.

### 3. Сопоставление план↔факт — только визуальное, не проектируется алгоритмически

Явное ограничение объёма, не забытая деталь: этот ADR **не вводит** никакой
логики автоматического сопоставления строки плана (`AllocationLine`/
`OrderItem`) со строкой факта (`PurchaseRecord`) — ни по похожести текста,
ни по количеству, ни по эвристике "та же позиция, скорее всего". Причина —
прямая аналогия с принципом 2 CLAUDE.md: сопоставление свободного текста
("как поставщик/сотрудник называет товар") с каноническим материалом — это
LLM-matching задача, экземпляр того же класса, что уже сознательно вынесен
за MVP-приоритет для ingestion прайс-листов. Данных о том, насколько часто
и в каком виде реально возникают расхождения (сколько строк объединяется,
какой стиль переименования типичен), пока нет — то же рассуждение, что
уже откладывает атрибуцию инфизибельности в ADR-0003 и связь
`confirmed_price`→`Price` в ADR-0007 §5: не проектировать вслепую.

Экран (п.5) показывает план и факт **рядом** для проекта — план
сгруппирован по поставщику (как сейчас на `AllocationResultPage`/
`OrderDetailPage`), факт сгруппирован по поставщику из `PurchaseRecord`
— визуальная сверка человеком, не построчное автоматическое связывание.
Единственная явная (не автоматическая) связь — опциональный `material_id`
из п.1, который сотрудник ставит сам, если хочет.

**Условие возврата к этому вопросу**: после накопления практики (несколько
проектов с заполненными `PurchaseRecord`) станет видно, стабилен ли формат
расхождений (типична ли переформулировка названия, типично ли слияние N
позиций в одну) — тогда полуавтоматическое сопоставление ("похоже на
строку плана X, подтвердите") можно спроектировать отдельным ADR с
реальными данными, тем же путём, каким ADR-0002 появился только после
того, как задача выбора поставщика была понятна количественно.

### 4. Итоги/контроль — суммарно по project/supplier, не построчно

"Контролировать", как это описал пользователь, разбирается на:

- **`purchased_total[project]`** — `Σ PurchaseRecord.quantity × unit_price`
  по всем записям проекта. Сравнивается с `Σ Order.total_amount` по всем
  `Order` этого проекта. Дельта в $ и % — тот же паттерн, что
  `price_delta`/`price_delta_pct` в ADR-0007 п.4, считается на backend, не
  на клиенте (принцип 4 CLAUDE.md).
- **`purchased_total[project][supplier]`** — та же сумма, разбитая по
  `supplier_id`, сравнивается с `Σ Order.total_amount` по `Order` этого
  поставщика в этом проекте (если по поставщику несколько `Order` —
  дозаказ, ADR-0007 п.2 явно допускает несколько `Order` на одного
  поставщика за run — суммируются все). Отвечает на "уложились ли в
  бюджет по этому поставщику", а не только по проекту в целом — важно
  именно потому, что позиции могут переходить между поставщиками (п.2):
  агрегат по поставщику может показать перерасход у B и недорасход у A
  одновременно, даже если сумма по проекту сошлась.
- Построчная сверка (эта позиция плана = эта позиция факта, цена сошлась
  или нет) **не строится** — она требует сопоставления, явно не в объёме
  (п.3). Контроль — намеренно агрегатный уровень, не транзакционный.

**План для сравнения — `Order.total_amount` (снимок), не живой
`SupplierAllocationSummaryOut`.** Явное решение, не деталь реализации:
`PurchaseRecord` фиксирует ответ на уже **отправленный** поставщику
документ (`Order`, статус `sent` — тот самый физический артефакт, который
поставщик держал в руках, формируя свой ответ). Сравнивать факт нужно с
тем, что было в этом документе на момент отправки, а не с текущим
состоянием `AllocationLine`/`SupplierAllocationSummaryOut`, которое могло
уйти вперёд независимо от факта: пользователь мог сделать override строки
(ADR-0006) уже **после** того, как Order ушёл поставщику и поставщик по
нему ответил (ADR-0007 п.2 explicitly не блокирует override после
`ordered_at`, только предупреждает про расхождение). Если бы план для
сравнения в п.4 брался из живого плана, число "перерасход/недорасход"
плавало бы от последующих правок плана, никак не связанных с тем, что
реально произошло в закупке — то же рассуждение "снимок, не кэш", что
ADR-0007 п.2 уже применяет к `OrderItem.quoted_price`, продолженное на
следующий уровень (сравнение агрегатов, не только хранение одной цены).

Прямое следствие: если для проекта/поставщика **нет** ни одного `Order`
(allocation ещё не подтверждён, кнопка "Создать ордера" не нажата) —
плановая сумма для сравнения отсутствует, `purchased_total` показывается
без дельты (не `0` — база для сравнения не существует, та же логика
"нет данных ≠ ноль", что уже применена к `price_delta` при отсутствующем
`confirmed_price`, ADR-0007 п.4). Это ожидаемо: `PurchaseRecord` не
требует существования `Order` (п.1–2), но контроль расхождения
предполагает, что было что сравнивать.

**Отклонено: сравнение с живым `SupplierAllocationSummaryOut`.**
Рассматривалось как альтернатива — "план" читать из текущего состояния
`AllocationLine`, а не застывшего `Order`. Отклонено по причине выше:
превратило бы бюджетный контроль в сравнение факта с постоянно
меняющейся целью, что не отвечает на реальный вопрос пользователя
("уложились ли в то, что заказали" — заказали = `Order`, не "что план
сейчас говорит после того, как кто-то потом подвинул строку").
Дополнительно: `Order` не существует без нажатия "Создать ордера", а
`AllocationLine` существует всегда после любого `AllocationRun` — если
бы сравнение шло с `AllocationLine`, `purchased_total[project]` мог бы
получить дельту ещё до того, как что-либо было физически отправлено
поставщику, что не соответствует смыслу "контроля факта закупки против
плана, который был предложен поставщику".

Оба агрегата — вычисляемые значения при чтении (тот же принцип, что
`price_delta` в ADR-0007 п.1 и агрегация "сверено" в ADR-0007 п.7: не
хранить то, что тривиально выводится из существующих строк), не
персистентные колонки на `Project`.

### 5. UI — новый project-level экран "Фактическая закупка"

Отдельный экран/роут (`/projects/:id/purchases`, по аналогии с тем, как
`OrderDetailPage` уже отдельный роут от `AllocationResultPage`), не
секция внутри `OrderDetailPage`. Обоснование, следуя из п.2: раз
`PurchaseRecord` привязан к `Project`, а не к конкретному `Order`, размещение
внутри `OrderDetailPage` подразумевало бы (ошибочно), что факт относится к
одному поставщику/документу — тому самому предположению, которое пример
пользователя опровергает. Экран `OrderDetailPage` остаётся про один
`Order` одного поставщика (сверка `quoted`/`confirmed`, ADR-0007);
экран "Фактическая закупка" — про весь проект, все поставщики, план и
факт рядом (п.3), с итогами (п.4) наверху.

Ввод записи: простая форма/инлайн-строка (по аналогии с `ProjectItem` на
`ProjectDetailPage` — свободный inline-add) — `raw_description` (текст),
`quantity`, `unit_price`, `supplier_id` (select из существующих
`Supplier`), опционально `material_id` (select, по умолчанию не выбран).
`POST /projects/{project_id}/purchase-records`. Никакого построчного
paste-импорта из Excel в этом ADR — та же причина, по которой ADR-0007
п.3 отложил paste для `confirmed_price`: отдельная задача по сложности
сопоставимая с ingestion, не MVP для контроля, описанного в задаче.

### 6. Статус/жизненный цикл — без отдельного статуса, простой журнал

`PurchaseRecord` не получает поле `status`. MVP — это просто
append-only-по-намерению журнал записей (реально допускает `PATCH`/`DELETE`
отдельной строки, если сотрудник опечатался, но не имеет workflow
"черновик → подтверждено → сверено с бухгалтерией").

Обоснование, тем же рассуждением, что уже закрыло аналогичный вопрос в
ADR-0007 п.7 (там — не вводить `Order.status = "reconciled"`, потому что
"сверено" — агрегация состояния позиций, не независимый факт): здесь
"сверено с бухгалтерией" **тем более** не имеет фактической основы для
хранения в MVP — сверка была бы человеческим действием вне системы
(бухгалтер сверяет с банковской выпиской/счетами), которое эта система не
наблюдает и не может знать, произошло ли оно на самом деле. Ввести булево
поле, которое сотрудник должен не забыть проставить вручную и которое
ничем не верифицируется системой — то же самое "необязательное поле,
которое останется забытым в NULL/false навсегда", что уже отклонено в
рассуждении п.1 про `order_id`. Если бухгалтерская сверка станет реальным
формализованным процессом внутри этой системы (не просто "человек посмотрел
таблицу") — отдельный ADR, когда появится конкретный workflow с реальными
переходами состояния, не гадание сейчас.

## Альтернативы

Альтернативы для каждого под-вопроса перечислены инлайн в "Решение" (1–6),
по той же структуре, что уже принята в ADR-0006/ADR-0007 — обоснования
специфичны к конкретному под-решению.

Единственная альтернатива на уровне ADR целиком: **расширить `OrderItem`
полями `actual_quantity`/`actual_unit_price`/`actual_supplier_id`
(nullable) вместо новой сущности.** Отклонено на этапе первого чтения
контекста задачи, не только в п.1 — сама постановка ("9 строк вместо 12",
"объединились", "ушло к другому поставщику") описывает факт как
независимый список с собственной кардинальностью, не поэлементную
модификацию существующих 12 строк `OrderItem`. Расширение `OrderItem'
могло бы представить максимум "факт для этой же строки, тот же
материал/количество, но другая цена/поставщик" — именно то, что уже
делает `confirmed_price` в ADR-0007 для цены; расширение `OrderItem`
структурно не может
представить "две строки плана слились в одну строку факта" или "факт
без соответствующей строки плана вообще" без искусственных ограничений
кардинальности 1:1, которых в реальном процессе нет.

## Последствия

- Новая таблица Alembic: `purchase_records` (`id`, `project_id` FK,
  `supplier_id` FK, `raw_description` `TEXT NOT NULL`, `quantity INTEGER
  NOT NULL`, `unit_price NUMERIC(12,2) NOT NULL`, `material_id` FK
  nullable, `created_at TIMESTAMPTZ`). Не трогает существующие таблицы
  (`orders`, `order_items`, `allocation_lines`) — независимая сущность,
  без миграции существующих данных.
- Новые endpoints: `POST /projects/{project_id}/purchase-records`,
  `PATCH /projects/{project_id}/purchase-records/{id}`,
  `DELETE /projects/{project_id}/purchase-records/{id}`,
  `GET /projects/{project_id}/purchase-records` (список + агрегаты п.4,
  либо агрегаты отдельным полем в существующем `GET /projects/{id}`
  — деталь реализации).
- Новый экран `/projects/:id/purchases` — требует дизайна в Claude Design
  (`docs/design/`) перед реализацией, по правилу CLAUDE.md.
- `docs/data-model.md`: добавить `PurchaseRecord` как новую сущность

  `PriceListImport`/`PriceListEntry`, ADR-0001), со связями
  `Project ||--o{ PurchaseRecord`, `Supplier ||--o{ PurchaseRecord`,
  `Material ||--o{ PurchaseRecord "опционально аннотирована как"`.
- `docs/ui-reference.md` получает новый раздел с поведением экрана

  поставщику, агрегаты `purchased_total` на уровне проекта и поставщика.
- `docs/glossary.md`: добавить термин **PurchaseRecord** — "запись о

- Явно не в объёме, зафиксировано как будущее расширение, не забытое:
