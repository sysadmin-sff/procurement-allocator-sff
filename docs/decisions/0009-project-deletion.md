# ADR-0009: Удаление проекта — каскад по связанным данным, запрет при отправленных Order

Статус: Принято — реализовано в `backend/app/api/project.py`
(`delete_project`, `DELETE /projects/{id}`), `frontend/src/routes/
ProjectsListPage.tsx`, тесты в `backend/tests/allocation/
test_project_deletion.py`.

## Контекст

Экран списка проектов (`ProjectsListPage.tsx`) сейчас не даёт удалить
проект — ни в UI, ни в API (`app/api/project.py` не имеет `DELETE
/projects/{id}`, только `DELETE /projects/{id}/items/{item_id}` для
отдельных строк BOM). Тестовые/черновые проекты, созданные при разработке
и ручной проверке (см. пример пользователя — три `"Test Project"` в
списке), накапливаются без возможности убрать их из интерфейса.

`Project` — корень довольно длинной цепочки зависимых сущностей
(`docs/data-model.md`): `ProjectItem` (BOM), `AllocationRun` →
`AllocationLine` (результаты расчётов), `Order` → `OrderItem` (ордера
поставщикам, ADR-0007), `PurchaseRecord` (факт закупки, ADR-0008). Простое
`DELETE FROM projects WHERE id = ...` упадёт на FK-ограничениях (ни одна
из связанных таблиц не имеет `ON DELETE CASCADE` — все `ForeignKey`
объявлены без этого параметра, что означает `RESTRICT` по умолчанию в
Postgres), поэтому это не тривиальная строка кода, а решение о том, что
именно происходит с пятью таблицами одновременно, и в каком случае это
вообще должно быть разрешено.

Ключевое ограничение, заданное пользователем явно при обсуждении:
`Order` в статусе `approved`/`sent` — это не просто строка в БД, а
представление физического документа, который реально ушёл поставщику
(тот же принцип "снимок отправленного", на котором стоит ADR-0007 п.2:
`Order`/`OrderItem` не должны молча переставать отражать то, что было
на самом деле отправлено). Удаление проекта не должно иметь возможность
бесследно стереть эту историю.

## Решение

### 1. Условие запрета — Order вне статуса `draft`

`DELETE /projects/{project_id}` проверяет: существует ли хотя бы один
`Order` этого проекта со `status != "draft"`. Если да — `409 Conflict`,
удаление не выполняется целиком (ни для одной таблицы, не частично).
Если у проекта только `draft`-ордера или их нет вообще — удаление
разрешено.

Обоснование порога именно на `Order.status`, а не на что-то другое
(например, наличие `PurchaseRecord`): `Order.status` — единственное
поле в модели, которое уже кодирует "физически покинуло систему"
(`draft` — существует только в БД, ещё ничего не отправлено; `approved`/
`sent` — по значению самого статуса подразумевает внешний шаг). Это не
новое понятие, а переиспользование существующей статусной модели
(`docs/spec.md §5`: `draft → approved → sent`) для нового решения —
тот же инстинкт, что уже применялся в ADR-0007 п.7 (не вводить лишний
статус, если существующее поле уже отвечает на вопрос).

**Отклонено: запрет по наличию `PurchaseRecord`.** `PurchaseRecord` —
это как раз данные, которые пользователь мог бы захотеть стереть вместе
с ошибочным тестовым проектом (сам факт их существования не означает
"проект нельзя трогать" — это внутренний журнал, ADR-0008 п.6, без
собственного понятия "отправлено вовне"). Блокировать на нём было бы
строже, чем нужно, и не по адресу — реальная причина для осторожности
(документ ушёл поставщику) относится только к `Order`.

**Отклонено: запрет по статусу `AllocationRun`/наличию `AllocationLine`.**
`AllocationRun` — внутренний результат расчёта, не физический артефакт
вовне системы; ничто не мешает удалить проект вместе с историей его
расчётов, если ни один `Order` не был отправлен. Блокировка здесь была
бы избыточной осторожностью без реального риска, который она бы
предотвращала.

### 2. Каскад — всё, что относится к проекту, включая `draft`-ордера

Если проверка (п.1) пройдена, удаление каскадно сносит **все** записи,
ссылающиеся на `project_id` этого проекта, в порядке, уважающем FK
(дети раньше родителей):

1. `PurchaseRecord` (`project_id`)
2. `OrderItem` (через `order_id` всех `Order` этого проекта), затем `Order` (`project_id`)
3. `AllocationLine` (через `allocation_run_id` всех `AllocationRun` этого проекта), затем `AllocationRun` (`project_id`)
4. `ProjectItem` (`project_id`)
5. `Project`

Шаги 2 и 3 не зависят друг от друга и не обязаны идти именно в этом
порядке — между `OrderItem`/`Order` и `AllocationLine`/`AllocationRun`
нет FK в обе стороны: `OrderItem` хранит `material_id`/`quantity`/
`quoted_price` по значению, не ссылкой на породившую его
`AllocationLine` (сознательное решение ADR-0007 п.2, "снимок, не
кэш" — именно чтобы `Order` не оставался живой ссылкой на
allocation-таблицы). Единственная реальная FK-зависимость внутри
каскада — родитель/потомок на каждом уровне (`Order`→`OrderItem`,
`AllocationRun`→`AllocationLine`, `Project`→всё остальное); нумерация
1–5 отражает единственное **обязательное** ограничение — `PurchaseRecord`/
`ProjectItem` перед `Project`, и `OrderItem`/`AllocationLine` перед
своими родителями — а не сквозную цепочку через все пять пунктов.

Явно включены `draft`-ордера (не только "проект без единого Order
вообще") — п.1 блокирует удаление только при `sent`/`approved`, значит
`draft`-заготовки, оставшиеся от несостоявшегося оформления, — то же
самое "мусорное" состояние, что и сам проект, и должны уйти вместе с
ним, а не остаться висеть осиротевшими записями без `project_id`
(FK не допускает такого сиротства в любом случае — но идея та же: не
пытаться "спасти" `draft`-ордера отдельно).

Выполняется в одной транзакции — либо всё, либо ничего (стандартное
поведение `Session.commit()`, без дополнительного кода: если какой-то
шаг упадёт по неучтённой связи, вся транзакция откатывается, `Project`
не остаётся в частично удалённом состоянии).

**Отклонено: мягкое удаление (`Project.status = "archived"`,
скрытие из списка вместо физического `DELETE`).** Рассматривалось как
альтернатива, отклонено пользователем явно в пользу настоящего удаления
— цель в том числе освободить БД от тестового мусора, а не просто
убрать его из UI (архивный статус оставил бы все каскадные таблицы
нетронутыми, что не решает исходную жалобу "не засорять"). Если позже
понадобится "мягкое" скрытие для реальных завершённых проектов — это
отдельная, качественно другая задача (жизненный цикл `status`), не
пересмотр этого решения.

### 3. UI — подтверждение, тот же паттерн `ConfirmButton`

`ProjectsListPage.tsx` получает кнопку удаления в каждой строке списка,
через уже существующий `ConfirmButton` (`components/ConfirmButton.tsx`,
тот же компонент, что использует `ProjectDetailPage` для строк BOM и
`PurchaseRecordsPage` для записей факта закупки — переиспользование
установленного паттерна, не новый диалог).

Если `DELETE` вернул `409` (заблокировано отправленным Order) — текст
ошибки от `ErrorBanner` с понятным сообщением (см. п.4), кнопка не
запускает удаление молча в никуда. Явного отдельного предупреждения
"у этого проекта есть отправленные ордера" на уровне списка *до* клика
на удаление не вводится в MVP — список проектов не тянет по каждому
проекту сводку по ордерам ради этого (стоимость лишнего запроса на
каждую строку списка ради предупреждения, которое пользователь и так
увидит по факту клика через `409`, не оправдана).

### 4. Сообщение при 409

`HTTPException(409, detail="У проекта есть отправленные поставщику
ордера — удаление недоступно.")` — тот же формат `detail`, что уже
использует остальной API (`ErrorBanner` уже умеет читать `error.detail`
как строку, `frontend/src/components/ErrorBanner.tsx`), никакого нового
контракта ошибки не вводится.

## Альтернативы

Альтернативы для каждого под-решения — инлайн в "Решение" (1–3), по
структуре, уже принятой в ADR-0006/0007/0008.

Альтернатива на уровне ADR целиком: **не поддерживать удаление вообще,
вместо этого дать пользователю переименовывать/помечать тестовые
проекты вручную и игнорировать их в списке.** Отклонена пользователем
явно — жалоба именно в засорении списка и БД тестовыми данными, обходной
путь ничего не решает по существу.

## Последствия

- Новый endpoint: `DELETE /projects/{project_id}` (`app/api/project.py`),
  `204` при успехе, `404` если проекта нет, `409` если заблокировано
  отправленным `Order` (п.1).
- Новая функция в сервисном слое (`app/allocation/order_service.py`
  соседствует по духу, но каскад трогает не только Order — вероятно
  отдельная `delete_project` в `app/api/project.py` рядом с остальными
  хендлерами, без выделения нового модуля ради одной функции — деталь
  реализации).
- Frontend: кнопка удаления через `ConfirmButton` в `ProjectsListPage.tsx`,
  обработка `409` через `ErrorBanner`.
- `docs/ui-reference.md`: новая запись в разделе про список проектов
  (или новый раздел, если его ещё нет) — поведение кнопки удаления и
  условие блокировки.
- Не в объёме, сознательно не проектируется: мягкое удаление/архивация
  (п.2, отклонено пользователем); предупреждение на уровне списка до
  клика (п.3); атрибуция "почему именно этот Order блокирует" в самом
  сообщении об ошибке за пределами общего текста (если понадобится —
  тривиальное расширение текста `detail`, не пересмотр).
- Реализация (endpoint, каскад, миграции — миграции не требуются, схема
  не меняется, — фронтенд) — предмет отдельного шага после вычитки
  этого ADR, как и с предыдущими ADR в этом проекте.
