# ADR-0010: Расширение справочника поставщиков — офисы, контакты, справочные поля

Статус: Предложено

## Контекст

Компания ведёт отдельную Excel-таблицу с гораздо более богатыми данными о
поставщиках, чем хранит текущая модель (`docs/data-model.md`:
`Supplier{name, currency, delivery_policy}` + свободнотекстовое
`contacts`). Пользователь прислал скриншот реального листа. Структура —
не плоская, не одна строка на поставщика:

- **Компания**: название, вебсайт, регион работы, ссылка на прайс/каталог
  (обычно Google Drive), статус сотрудничества (свободные формулировки в
  примерах: "Активные закупки", "Объём закупок уменьшился из-за
  невыгодных цен"), условия оплаты ("NET 30", "NET 15" — не хранится
  нигде сейчас и не то же самое, что `Supplier.delivery_policy`, который
  про стоимость/порог доставки, а не про платёжные условия), ссылка на
  личный кабинет поставщика, комментарии — свободный текст с историей
  заметок (изменения цен, минимальные суммы заказа, дедлайны приёма
  заказов за день).
- У **одной** компании — несколько контактов: имя, роль/должность
  (свободный текст в примерах: "Inside Sales Representative", "Credit
  department", "Outside Sales Representative"), телефон, email.
- Контакты в реальных данных сгруппированы по адресу офиса — у одной
  компании (Lansing Building Products) 8 разных адресов, под каждым свои
  контакты. Пользователь явно подтвердил: адрес — отдельная сущность
  (`Office`), не текстовое поле на контакте, потому что офисы относятся
  к поставщику как таковому (несколько офисов в разных регионах) и это
  закладывается на будущее уже сейчас, даже если первая версия UI
  использует это не полностью.

Не в объёме этого ADR: импорт существующей Excel-таблицы поставщиков как
задача массового переноса (отдельная задача, по аналогии с тем, как уже
был перенос прайса — потребует такой же реструктуризации и, возможно,
ручной проверки дублей). Здесь проектируется только модель данных и
экран ручного ввода/редактирования.

## Решение

### 1. Новые поля на `Supplier`

```python
website: Mapped[str | None] = mapped_column(String(500))
region: Mapped[str | None] = mapped_column(String(255))
catalog_link: Mapped[str | None] = mapped_column(String(500))
status: Mapped[str | None] = mapped_column(String(255))
payment_terms: Mapped[str | None] = mapped_column(String(100))
portal_url: Mapped[str | None] = mapped_column(String(500))
comments: Mapped[str | None] = mapped_column(Text)
```

Все поля nullable — справочник заполняется постепенно, ручным вводом, не
одномоментной миграцией (см. п.5 и "не в объёме").

**`status` — свободный текст, не enum.** В реальных данных видно только
2 разных значения, но это не гарантирует закрытый список: формулировки
("Объём закупок уменьшился из-за невыгодных цен") — это заметки о
состоянии отношений с поставщиком, а не фиксированные категории. Enum
потребовал бы завести "Другое" + доп. текст или частые миграции схемы
при появлении нового варианта. Тот же принцип, что уже применён к
`PurchaseRecord.raw_description` (ADR-0008 п.1) — не структурировать то,
что не обязано быть структурированным.

**`payment_terms` — отдельное поле, не расширение `delivery_policy`.**
Явное разграничение, см. п.3.

**`comments` — `Text`, единое свободное поле.** По аналогии с
`PurchaseRecord.raw_description` — никакой попытки распарсить историю
заметок (даты, суммы, дедлайны) на структурированные записи. Если в
будущем понадобится история изменений цен/минимальных сумм как
отдельная лента событий — это отдельный ADR, когда будет понятно, какой
workflow эта лента обслуживает (то же рассуждение, что уже откладывало
матчинг план/факт в ADR-0008 п.3: не проектировать вслепую).

### 2. Новые сущности `Office` и `SupplierContact`

```python
class Office(UUIDPKMixin, Base):
    __tablename__ = "offices"

    supplier_id: Mapped[uuid.UUID] = mapped_column(
        ForeignKey("suppliers.id"), nullable=False
    )
    address: Mapped[str] = mapped_column(String, nullable=False)
    region: Mapped[str | None] = mapped_column(String(255))


class SupplierContact(UUIDPKMixin, Base):
    __tablename__ = "supplier_contacts"

    supplier_id: Mapped[uuid.UUID] = mapped_column(
        ForeignKey("suppliers.id"), nullable=False
    )
    office_id: Mapped[uuid.UUID | None] = mapped_column(ForeignKey("offices.id"))
    name: Mapped[str] = mapped_column(String(255), nullable=False)
    role: Mapped[str | None] = mapped_column(String(255))
    phone: Mapped[str | None] = mapped_column(String(50))
    email: Mapped[str | None] = mapped_column(String(255))
```

**`Office.region` отдельно от `address`.** В примере регион ("West Coast
of Florida") иногда шире одного конкретного адреса — офис физически
находится по одному адресу, но обслуживает более широкий регион.
Хранить это как отдельное поле, а не выводить из адреса текстовым
парсингом.

**`SupplierContact.office_id` — nullable.** В примере есть контакты без
чёткой привязки к одному адресу ("General email, they accept orders").
Обязательный `office_id` заставил бы заводить фиктивный офис для такого
контакта — искусственно.

**`SupplierContact.supplier_id` дублирует то, что можно вывести через
`office_id → Office.supplier_id`.** Это намеренная денормализация, не
недосмотр: раз `office_id` может быть `NULL` (контакт без офиса), путь
"контакт → офис → поставщик" не всегда существует. Прямой `supplier_id`
делает "все контакты поставщика X" простым запросом без условного join
и не зависящим от того, у скольких контактов есть офис.

### 3. Граница с `delivery_policy` — явная, не подразумеваемая

Все новые поля из п.1–2 (`payment_terms`, `comments`, `website`,
`status`, контакты, офисы) — справочная информация для людей. Ни одно
из них не читается ILP-солвером (ADR-0002) и не участвует в постановке
задачи allocation. Единственное поле `Supplier`, влияющее на расчёт —
уже существующий `delivery_policy`. Это разграничение фиксируется явно,
потому что `payment_terms` ("NET 30") концептуально соседствует с
финансовыми условиями закупки и его легко по ошибке протащить в модель
солвера при будущей правке — здесь прямо зафиксировано, что этого не
происходит.

### 4. UI — отдельная карточка `/suppliers/:id`, не расширение списка

Текущий `/suppliers` (`SuppliersPage.tsx`) — плоская таблица с инлайн-
формой (name/contacts/currency/delivery_policy) поверх списка. С учётом
объёма новых данных (до 8 контактов на поставщика, офисы, комментарии)
инлайн-форма в списке стала бы громоздкой и плохо читаемой — то же
рассуждение, по которому `OrderDetailPage`/`ProjectDetailPage` уже
выделены в отдельные роуты от своих списков, а не встроены в них.

**Список `/suppliers`** остаётся лёгким обзором: колонки
name/status/currency/сводка по delivery, плюс переход "Открыть" на
карточку. Создание нового поставщика — по-прежнему короткая форма
(минимум: name), редактирование деталей — уже на карточке.

**Карточка `/suppliers/:id`**, секции:
- **Основная информация** — name, website, region, catalog_link, status,
  payment_terms, portal_url. Редактируется как единая форма (PATCH-
  семантика, как сейчас у `PUT /suppliers/{id}`).
- **Офисы** — список офисов поставщика (address, region), добавление/
  удаление строки. Простая under-carousel таблица, не отдельный экран —
  количество офисов на поставщика (до 8 в примере) укладывается в
  карточку без пагинации.
- **Контакты** — таблица (name, role, phone, email, офис), сгруппированная
  по офису + отдельная группа "без офиса". Добавление/удаление строки;
  select офиса при добавлении контакта берётся из списка офисов этого же
  поставщика (включая пустое значение "без офиса").
- **Условия доставки** — существующая форма `delivery_policy`, без
  изменений.
- **Комментарии** — одно большое текстовое поле (`comments`), сохраняется
  вместе с основной информацией.

Дизайн карточки — через Claude Design (`docs/design/`) перед реализацией,
по правилу CLAUDE.md; здесь фиксируется только структура секций и
поведение, не разметка.

### 5. Миграция `Supplier.contacts`

Поле остаётся как есть, без изменений схемы и без автоматической
миграции в `SupplierContact`. Обоснование: `contacts` — свободный текст
без структуры (нет разделителей "имя/роль/телефон/email", которые можно
было бы надёжно распарсить программно); попытка автоматического разбора
потребовала бы того же класса задачи, что уже сознательно вынесен из
MVP — LLM-парсинг неструктурированного текста с обязательным экраном
ревью (принцип 2 CLAUDE.md), что явно избыточно для одного текстового
поля. `SupplierContact` — новая таблица для структурированных
персональных контактов, вводимых вручную вперёд; `contacts` продолжает
существовать параллельно как есть (не помечается deprecated в схеме),
остаётся видимым в существующей форме создания поставщика как
"общий контакт/примечание". Если в будущем накопится достаточно записей
`SupplierContact`, чтобы `contacts` стало явно избыточным — отдельное
решение об удалении поля, не часть этого ADR.

## Альтернативы

Альтернативы для каждого под-вопроса перечислены инлайн в "Решение"
(1–5), по структуре, уже принятой в ADR-0006/0007/0008.

Единственная альтернатива на уровне ADR целиком: **хранить контакты как
JSON-массив прямо на `Supplier`** (без отдельных таблиц `Office`/
`SupplierContact`). Отклонено: пользователь явно подтвердил, что офис —
отдельная сущность, к которой привязаны контакты, а не атрибут контакта
или JSON-блоб на поставщике. JSON-массив не дал бы честного FK между
контактом и офисом, затруднил бы будущие запросы вида "все контакты
этого офиса" и не соответствовал бы уже принятому в проекте паттерну
(структурированные связи — отдельные таблицы с FK, JSON — только для
действительно неструктурированных данных вроде `delivery_policy`,
который является набором простых скалярных настроек, а не списком
сущностей переменной длины).

## Последствия

- Новые колонки на `suppliers`: `website`, `region`, `catalog_link`,
  `status`, `payment_terms`, `portal_url` (все `VARCHAR NULL`),
  `comments` (`TEXT NULL`). Существующие `name`, `contacts`, `currency`,
  `delivery_policy` не меняются.
- Новые таблицы Alembic: `offices` (`id`, `supplier_id` FK NOT NULL,
  `address TEXT NOT NULL`, `region VARCHAR NULL`), `supplier_contacts`
  (`id`, `supplier_id` FK NOT NULL, `office_id` FK NULL, `name VARCHAR
  NOT NULL`, `role VARCHAR NULL`, `phone VARCHAR NULL`, `email VARCHAR
  NULL`).
- Новые endpoints (детали — отдельная задача реализации): CRUD для
  `Office` и `SupplierContact`, вложенные под `/suppliers/{supplier_id}`
  (по аналогии с `/projects/{project_id}/purchase-records` из ADR-0008),
  плюс расширение `SupplierOut`/`SupplierUpdate` новыми скалярными
  полями.
- Новый экран `/suppliers/:id` — требует дизайна в Claude Design перед
  реализацией; `/suppliers` упрощается до обзорного списка со ссылкой на
  карточку.
- `docs/data-model.md`: добавить `Office`, `SupplierContact` как новые
  сущности сверх исходной диаграммы (по образцу того, как уже помечены
  `PriceListImport`/`PurchaseRecord`), новые поля на `Supplier`, связи
  `Supplier ||--o{ Office`, `Supplier ||--o{ SupplierContact`,
  `Office ||--o{ SupplierContact "опционально группирует"`.
- `docs/ui-reference.md` получает новый раздел с поведением карточки
  `/suppliers/:id`: секции, добавление/удаление офиса и контакта, связь
  выбора офиса с контактом.
- `docs/glossary.md`: добавить термины **Office** ("физический адрес
  поставщика, к которому могут быть привязаны контакты; один поставщик
  может иметь несколько офисов в разных регионах") и **SupplierContact**
  ("персональный контакт поставщика — имя, роль, телефон, email;
  опционально привязан к конкретному Office").
- Явно не в объёме, зафиксировано как будущее расширение, не забытое:
  массовый импорт существующей Excel-таблицы поставщиков; структурирование
  истории `comments` в отдельную ленту событий; удаление/депрекация
  `Supplier.contacts`.
- Реализация (миграция, endpoints, новый экран, дизайн в Claude Design) —
  предмет отдельной задачи после вычитки этого ADR, backend и frontend
  раздельно, как и с предыдущими ADR.
