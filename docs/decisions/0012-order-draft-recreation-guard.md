# ADR-0012: Предупреждение о повторном создании draft-ордеров

Статус: Принято, реализовано частично — backend в
`backend/app/allocation/order_service.py` и `backend/app/api/order.py`,
frontend (модалка `OrderDraftConflictModal`, `replace_drafts` в
`ordersApi`) — оба 2026-08-20. **Реализация не покрывает решение
целиком**: путь «Создать дополнительно» (§1, §2, §4) не реализован —
см. раздел «Отклонение реализации от принятого решения» в
«Последствия» и `docs/known-issues.md`.

## Контекст

Реальный случай (не гипотетика): пользователь пересчитал проект, у которого
уже были `draft`-ордера от предыдущего расчёта, и нажал «Подтвердить и
создать ордера» — получил дублирующиеся ордера (тот же поставщик,
идентичные суммы) вместо предупреждения.

`create_orders_for_run()` (`backend/app/allocation/order_service.py:45`)
создаёт по одному `Order` на каждого поставщика из текущих
`supplier_summaries` рана безусловно, при каждом вызове — комментарий в коде
прямо документирует это как сознательное решение: «Not deduplicated against
prior Order creation for the same run — see ADR-0007 п.2 "Отклонено": a
re-order/partial reorder is a legitimate real-world scenario, not a bug to
guard against.» ADR-0007 п.2 отклонил блокировку намеренно — компания может
физически захотеть дозаказ тем же поставщиком (частичная поставка,
добавление позиции). **Этот принцип не пересматривается**: это ADR не о
блокировке, а о том, что между «отправлено поставщику, дозаказываем» и
«случайно нажали ещё раз на то же нерасчитанное состояние» система сейчас
не различает вообще ничего — ни блокировки (осознанно), ни предупреждения
(не рассмотрено).

ADR-0011 п.3 добавил механизм, который делает столкновение частым, а не
краевым случаем: повторный успешный расчёт откатывает `Project.status` из
`ordered` обратно в `calculated` — именно потому, что «новый расчёт ещё не
отправлен поставщикам» (см. ADR-0011 п.3). Это правильно с точки зрения
честности статуса, но кнопка «Подтвердить и создать ордера» на
`AllocationResultPage.tsx:286` остаётся видна и активна ровно в этом
состоянии, и не показывает, что по этому же проекту (тем же поставщикам)
уже существуют `draft`-ордера от прошлого расчёта, которые ещё никуда не
уходили. ADR-0011, «Последствия», зафиксировал это как риск без решения:
«Регресс `ordered → calculated` после пересчёта, в сочетании с отсутствием
защиты от повторного создания `Order` тому же поставщику (ADR-0007 п.2),
создаёт риск случайного дублирующего ордера без предупреждения на уровне
экрана — зафиксировано как связанный риск в `docs/known-issues.md`, не
устраняется в рамках этого ADR.» `docs/known-issues.md` фиксирует то же с
условием возврата: «если дублирующий ордер реально создаётся на практике
хотя бы раз — тогда видно, нужно ли предупреждение, мягкая блокировка или
что-то ещё». Условие выполнено — этот ADR закрывает пробел.

Проверено на реальных данных dev-БД перед написанием этого ADR (тот же
метод верификации, что уже применён в ADR-0011 п.6): в проекте
`8837ffb9-1145-4472-bb69-a1b17aac2606` уже есть **три** поставщика, у
каждого из которых по **два** `draft`-`Order` с идентичной
`total_amount` (725.03/725.03, 596.35/596.35, 346.30/346.30) — точный
отпечаток именно этого бага, не гипотетический сценарий. Это не «до двух»
как верхняя граница: ничто в `create_orders_for_run` не ограничивает число
повторных вызовов, поэтому проверка конфликта и её UI (п.2, п.4) обязаны
работать со **списком** прежних `draft`-ордеров на поставщика, а не с
одним — раньше в черновике этого ADR ошибочно предполагалось единственное
значение (`existing_draft_order_id`), что реальные данные сразу
опровергают.

**Различение, которое отсутствует в системе**: `Order.status == "draft"` —
внутренний черновик, ещё не покинувший систему, ничем не защищённый
физически (ничего не значит для поставщика, поставщик его не видел).
`approved`/`sent` — по духу ADR-0007 (Order как снимок, физический документ,
уже возможно ушедший поставщику) заведомо другая категория: их трогать нельзя
ни при каких условиях, это не переобсуждается здесь. Сегодняшний код не
делает этого различия вообще — `create_orders_for_run` не смотрит, есть ли
уже `Order` для этого поставщика в любом статусе, он просто создаёт новый
набор рядом.

**Не в объёме**: `approved`/`sent`-ордера никогда не удаляются и не
заменяются автоматически ни при каких условиях — ADR-0007 п.2 в этой части
остаётся как есть, этот ADR его не переоткрывает.

**Отдельный риск внутри draft**: ADR-0007 п.3 разрешает вводить
`confirmed_price` на `OrderItem` независимо от `Order.status` — сверка с
поставщиком (телефон, email, устная договорённость) может произойти раньше,
чем сотрудник формально пометит ордер отправленным. Значит `draft`-ордер не
всегда «ничем не защищённый черновик, который трудозатратно пересоздать» —
если хотя бы одна его позиция уже имеет `confirmed_price IS NOT NULL`, это
уже содержит ручной труд, который не выводится обратно из
`AllocationLine` (в отличие от `quoted_price` — производной величины,
которую `replace_drafts=true` и так пересоздаёт бесплатно). Простая замена
такого черновика удаляет данные, у которых нет источника восстановления, а
не просто повторяет предыдущий расчёт. Это отдельная ось от «draft vs
approved/sent» и требует собственного решения (п.1, п.4).

## Решение

### 1. Различение draft vs approved/sent при создании новых ордеров

При вызове создания ордеров backend перед вставкой новых строк проверяет,
есть ли для проекта уже существующие `Order` в статусе `draft` (по любому
прошлому рану, не только по текущему `run_id` — см. п.3 про гранулярность).
`approved`/`sent`-ордера в этой проверке не участвуют вообще: они не мешают
и не блокируют создание новых, ADR-0007 п.2 продолжает действовать для них
без изменений — компания может дозаказывать тому же поставщику даже если у
него уже есть отправленный `Order`, без всякого предупреждения, точно как
сейчас.

Если конфликтующих `draft`-ордеров нет — поведение не меняется, ордера
создаются сразу, как и раньше (ADR-0007 п.2).

Если есть — endpoint не создаёт ничего молча. Он возвращает информацию о
конфликте, и вызывающая сторона (фронт) должна явно сказать, что делать
дальше: заменить (удалить старые `draft` этого поставщика + их `OrderItem`,
создать новые из текущего состояния `AllocationLine`) или создать
дополнительно (оставить оба набора нетронутыми — осознанный дозаказ).
«Дополнительно» — это ровно сегодняшнее поведение (ADR-0007 п.2), не новый
режим; ADR не убирает эту возможность, только перестаёт делать её
поведением по умолчанию без спроса.

**Отклонено: блокировать создание, если есть draft-конфликт (жёсткий 409
без возможности продолжить).** Отклонено по той же причине, что и в
ADR-0007 п.2 — система не может знать, дозаказ это или ошибка, у
пользователя есть контекст, которого нет у неё. Жёсткая блокировка без пути
продолжить превратила бы легитимный сценарий в тупик. Тот же принцип
«предупреждение, не запрет», что уже применён к `below_min_order`
(ADR-0006 п.4) и к расхождению `overridden_at > ordered_at` (ADR-0007 п.2).

**Конфликт с уже подтверждёнными ценами — вторая, более строгая ступень
подтверждения, не просто более заметный текст.** Для поставщика, у
которого среди конфликтующих `draft`-`OrderItem` есть хотя бы один с
`confirmed_price IS NOT NULL`, одного клика «Заменить черновики» (п.4)
недостаточно — замена по этому конкретному поставщику требует отдельного,
специфично сформулированного согласия («да, я осознанно теряю сверенные
цены по Supplier X»), не входящего в общий клик «Заменить» по всем
затронутым поставщикам сразу. Обоснование через степень обратимости —
критерий, уже используемый в проекте (ADR-0007 п.2 отличает `draft` от
`approved`/`sent` ровно по нему: покинуло ли состояние систему): `draft`
без `confirmed_price` восстановим одним нажатием той же кнопки заново
(источник истины — `AllocationLine` — никуда не делся), `draft` с
`confirmed_price` необратим — введённое значение существует только в этой
строке, нигде больше не хранится и не выводится ни из чего. Это тот же
разрыв обратимости, который отличает `draft` от `approved`/`sent`
(п. «Не в объёме»), просто на уровень ниже: не на уровне `Order.status`,
а на уровне отдельной позиции внутри `draft`-ордера.

**Отклонено: то же единое предупреждение, только с более заметным
текстом/цветом для позиций с `confirmed_price`.** Отклонено — заметность
текста не меняет того, что один и тот же клик «Заменить» удаляет и
тривиально восстановимые, и невосстановимые данные одинаково легко;
пользователь, бегло просматривающий список из нескольких поставщиков,
может не заметить одну строку с другой формулировкой среди остальных.
Более строгая ступень (п.4) физически не даёт продолжить, не прочитав и не
подтвердив именно эту часть — тот же принцип, что уже применяется к
необратимым операциям в проекте (например, точечное подтверждение при
удалении, ADR-0009), не полагаться на то, что пользователь заметит
предупреждение сам среди прочего текста.

### 2. API-контракт

Существующий `POST /projects/{project_id}/allocations/{run_id}/orders`
получает необязательное булево поле в теле запроса:

```
POST /projects/{project_id}/allocations/{run_id}/orders
{ "replace_drafts": false }   # default
```

- `replace_drafts` отсутствует или `false` (по умолчанию), и конфликтующих
  `draft`-ордеров нет → создание проходит как сейчас, `201` со списком
  созданных `Order`.
- `replace_drafts` отсутствует или `false`, и конфликтующие `draft`-ордера
  **есть** → endpoint не создаёт ничего и не удаляет ничего, возвращает
  `409 Conflict` с телом, описывающим конфликт (поставщики, суммы старых
  draft-ордеров — см. схему в п.4), чтобы фронт мог показать модалку без
  дополнительного запроса.
- `replace_drafts: true` → в одной транзакции: для поставщиков,
  пересекающихся с текущим `supplier_summaries` рана, удалить сперва все
  `OrderItem` их существующих `draft`-`Order` (явным `DELETE`/`db.delete()`
  в коде сервисного слоя — как уже делает `delete_project` для того же
  `Order`→`OrderItem` перехода, ADR-0009 п.2, шаг 2), затем сами эти
  `Order`; **не `ON DELETE CASCADE`** — в текущей схеме такого каскада на
  FK `order_items.order_id` нет (ADR-0009, «Контекст»: «ни одна из
  связанных таблиц не имеет `ON DELETE CASCADE`… что означает `RESTRICT`
  по умолчанию в Postgres»), поэтому удаление `Order` без предварительного
  удаления его `OrderItem` упадёт на FK-ограничении. Затем выполнить
  обычную логику `create_orders_for_run`. `201` со списком новых `Order`.
- `acknowledge_conflict: true` (и `replace_drafts` не `true`), конфликт
  **есть** → добавлено 2026-08-31 как достройка этого же контракта, не
  пересмотр §1–§4: создание проходит как в случае без конфликта, ничего
  не удаляется, существующие `draft` (вместе с их `confirmed_price`)
  остаются рядом с новыми `Order`. Это и есть путь «создать
  дополнительно» из §1. Отдельное поле, а не `replace_drafts: false`,
  потому что endpoint stateless и `false` не различает «пользователя ещё
  не спросили» и «спросили, он явно хочет дозаказ» — см. «Отклонение
  реализации от принятого решения». Если переданы оба флага,
  `replace_drafts` выигрывает.
- `replace_drafts: true`, но конфликтующих draft на момент выполнения уже
  нет (например, кто-то параллельно их удалил/подтвердил) → не ошибка,
  просто создание проходит как обычно — `replace_drafts` описывает
  намерение «если есть конфликт — замени», а не требование, что конфликт
  обязан существовать.

**Отклонено: отдельный `DELETE`-endpoint для удаления старых draft-ордеров
перед созданием новых (два раздельных запроса с фронта).** Отклонено, потому
что замена обязана быть одной атомарной транзакцией: если между `DELETE` и
`POST` создание упадёт (валидация, конфликт, обрыв сети), пользователь
остаётся без единого draft-ордера по этому поставщику — хуже, чем
дублирование, которое чинит этот ADR. Одна операция с одним булевым флагом
исключает этот класс промежуточного состояния. Тот же принцип, что уже
применяется в проекте к «снимку»: операция, которая должна либо произойти
целиком, либо не произойти вовсе, не разбивается на шаги, которые клиент
обязан не забыть выполнить оба.

**Отклонено: `replace_drafts` как query-параметр вместо поля тела.**
Endpoint уже `POST` с телом (пусть сейчас пустым) по конвенции остальных
create-эндпоинтов проекта (`allocationApi`, `ordersApi`) — новое булево
поле в JSON-теле последовательно с этим, не вводит второй канал передачи
параметров для одного и того же запроса.

### 3. Гранулярность конфликта — по поставщику, не по всему проекту разом

Проверка «уже есть draft-ордера» выполняется **на пересечении поставщиков**:
конфликт есть только для тех поставщиков из текущего `supplier_summaries`
рана, у которых уже есть хотя бы один `draft`-`Order` в этом проекте.
Реалистичный кейс, который это должно покрывать: пользователь сделал
override (ADR-0006) части строк на другого поставщика между расчётами — у
поставщика A уже был draft-ордер от прошлого рана, у поставщика B (новый в
этом ране) ещё нет ничего.

`replace_drafts: true` в этом случае удаляет и пересоздаёт **только**
draft-ордера поставщиков, где было пересечение — поставщик B получает
обычное создание без затрагивания чего-либо (для него нечего заменять).
Это не «всё или ничего» на уровне проекта: список
`suppliers_with_existing_drafts` в ответе `409` (п.4) — это подмножество, не
весь проект, и `replace_drafts: true` действует ровно на это подмножество,
не удаляет draft-ордера поставщиков вне текущего рана (если по какой-то
причине такие остались — например, поставщик, который был в позапрошлом
ране, но выпал из текущего override'ом).

Обоснование выбора «по поставщику», а не «по всему проекту сразу»: кнопка
«Подтвердить и создать ордера» физически создаёт ордера отдельно на каждого
поставщика (`create_orders_for_run`, `backend/app/allocation/order_service.py:62-94`
— цикл по `supplier_summaries`) — уровень, на котором уже существует
естественная единица операции, тот же уровень, на котором сегодня возникает
и сам дубликат (два `Order` одному и тому же поставщику с одинаковой
суммой). Проверка на уровне всего проекта («есть хотя бы один draft где
угодно в проекте → блокировать всё») давала бы ложные срабатывания именно в
описанном сценарии override — пользователь, который добавил нового
поставщика B и ничего не менял у A, получил бы предупреждение о конфликте с
A, хотя для A решение уже принято раньше и не является частью текущего
действия с B.

**Отклонено: агрегированная проверка на уровне проекта («есть ли вообще
хоть один draft-ордер по проекту»).** Отклонено по причине выше — это
огрубление реального состояния (какие именно поставщики пересекаются) до
булева флага, который заставил бы пользователя каждый раз вручную
разбираться, какая часть предупреждения релевантна его текущему действию,
вместо того чтобы система сказала это явно.

### 4. UI

Модальное окно, показывается вместо немедленного создания, когда `POST`
возвращает `409` с телом конфликта (не превентивная проверка на фронте —
источник истины расчёта пересечения поставщиков должен быть один, backend,
тот же принцип, что уже применяется к деньгам, CLAUDE.md принцип 4,
распространённый здесь на структурные данные аллокации).

Тело `409`-ответа (новая Pydantic-схема, `OrderDraftConflictOut` или
аналогичное имя — детали именования подбираются на этапе реализации):

```
{
  "detail": "draft_orders_exist",
  "suppliers_with_existing_drafts": [
    { "supplier_id": "...", "supplier_name": "...",
      "existing_draft_orders": [
        { "order_id": "...", "total_amount": 725.03, "has_confirmed_prices": false },
        { "order_id": "...", "total_amount": 725.03, "has_confirmed_prices": true }
      ] },
    ...
  ]
}
```

**`existing_draft_orders` — список, не единственный объект.** Реальные
dev-данные (см. «Контекст») уже показывают поставщиков с двумя
`draft`-ордерами одновременно (последствие того же бага, до этого ADR
никак не ограниченное) — единственный `existing_draft_order_id`
физически не может описать такое состояние, схема обязана считать «сколько
угодно прежних draft на поставщика», не «максимум один». Каждая запись
списка несёт собственный `has_confirmed_prices` — сверка (ADR-0007 п.3)
могла случиться на одном из двух дублей и не случиться на другом,
агрегировать это в один флаг на поставщика значило бы потерять, какой
именно `Order` содержит невосстановимые данные.

`has_confirmed_prices` (на каждый элемент `existing_draft_orders`) —
`true`, если хотя бы один `OrderItem` этого конкретного draft-ордера имеет
`confirmed_price IS NOT NULL` (вычисляется на backend при формировании
тела `409`, тот же принцип «не хранить, что тривиально выводится», что и
`price_delta`/агрегаты «жду ответа»/«сверено» в ADR-0007 п.1/п.7 — не новая
колонка, просто ещё одно вычисляемое поле в этом конкретном ответе). Для
UI (ниже) поставщик в целом считается «с подтверждёнными ценами», если
`has_confirmed_prices: true` хотя бы у одного элемента его
`existing_draft_orders`.

Модалка показывает:
- Список затронутых поставщиков (только те, где есть пересечение — п.3);
  для каждого — все его `existing_draft_orders` с суммой каждого
  (`total_amount`), чтобы пользователь понимал масштаб того, что будет
  удалено при замене — не просто «есть конфликт», а «у Supplier X уже есть
  2 черновика на $725.03 каждый», если их несколько, а не только один.
- Для поставщика с `has_confirmed_prices: true` — отдельная явная строка
  предупреждения рядом с его записью в списке, текстом вроде «в этом
  черновике уже есть подтверждённые цены — они будут потеряны», визуально
  отличная от обычной строки конфликта (тот же язык предупреждения,
  `--color-danger-text`/`warningRow`, что уже используется для
  `below_min_order` в ADR-0006 п.4 и `>10%`-расхождения в ADR-0007 п.4).
- Общая кнопка **«Заменить черновики»** активна только для поставщиков без
  `has_confirmed_prices`; если среди отмеченных к замене есть хотя бы один
  `has_confirmed_prices: true`, эта кнопка требует дополнительного явного
  шага именно по нему — чекбокс или отдельное текстовое подтверждение рядом
  с его строкой («Да, заменить и потерять подтверждённые цены»), без
  которого общий клик «Заменить черновики» не отправляет `replace_drafts:
  true` для этого поставщика (реализация — по одному `replace_drafts`
  на весь запрос, п.2, поэтому пока не подтверждены все поставщики с
  `has_confirmed_prices`, отправка блокируется на фронте целиком; если
  пользователь хочет заменить только «безопасных» поставщиков и оставить
  проблемного как дозаказ — это уже покрывается тем, что «Создать
  дополнительно» доступно ему как отдельный путь, п.1).
- Кнопка **«Создать дополнительно»** (`replace_drafts: false`, тот же
  `POST` повторно — на этот раз без блокирующего `409`, потому что явное
  согласие уже получено; иначе пользователь не смог бы вырваться из цикла
  подтверждений) не требует второй ступени — она ничего не удаляет, старые
  `confirmed_price` остаются нетронутыми на своём ордере.
- Текст-подсказка проговаривает необратимость обеих веток явно (в духе
  уже существующего `footerHint` на `AllocationResultPage.tsx:290`,
  «Создаст по одному ордеру на каждого поставщика — необратимо»): замена
  удаляет старые draft безвозвратно, дозаказ создаёт заказ поставщику,
  который уже мог получить предыдущий.

**Отклонено: показывать предупреждение всегда (даже без конфликта), с
галочкой «не спрашивать больше».** Не в объёме и не нужно — при отсутствии
конфликта (нет draft-ордеров ни у одного поставщика текущего рана)
поведение не меняется вообще, лишний клик на пустом месте не имеет
обоснования ни в задаче, ни в спеке.

## Альтернативы

Альтернативы по каждому под-вопросу — инлайн в «Решение» (1–4), по
структуре, принятой в ADR-0006/ADR-0007/ADR-0011.

Альтернатива на уровне ADR целиком: **не спрашивать пользователя вообще,
просто всегда заменять draft-ордера тем же поставщиком автоматически при
пересчёте** (переместить логику замены в `run_allocation()`, а не в момент
создания ордеров). Отклонено — заменяло бы данные (`draft`-`Order`, который
пользователь мог уже начать печатать/готовить к отправке, см. ADR-0007 п.6:
документ для поставщика генерируется сразу при создании Order) без явного
действия пользователя, в момент, когда пользователь ещё даже не решил,
собирается ли он создавать новые ордера — пересчёт (`run_allocation`) и
создание ордеров (`create_orders_for_run`) остаются двумя разными шагами
(ADR-0011 п.2 их специально не объединяет), и эта граница не переносится.

## Последствия

- `POST /projects/{project_id}/allocations/{run_id}/orders` получает новое
  необязательное поле тела `replace_drafts: bool = false` и новый код
  ответа `409` с телом конфликта, когда `replace_drafts` не установлен в
  `true`, а конфликтующие `draft`-ордера есть.
- `create_orders_for_run()` (`backend/app/allocation/order_service.py`)
  получает шаг проверки конфликта (по пересечению поставщиков текущего
  рана и поставщиков с существующими `draft`-`Order` в проекте) перед
  вставкой, и логику удаления старых `draft`-`Order`/`OrderItem` этих
  поставщиков при `replace_drafts=True` — явным приложенческим удалением
  `OrderItem` перед `Order` (не `ON DELETE CASCADE`, которого нет в схеме,
  тот же паттерн, что `delete_project` уже использует для этого перехода,
  ADR-0009 п.2), выполняемую в той же транзакции, что и создание новых.
- Новая Pydantic-схема для тела `409` (список поставщиков с суммами
  существующих draft-ордеров и флагом `has_confirmed_prices` на каждую
  запись) — имя и точная форма подбираются в реализации, согласованно с
  `OrderOut`/`OrderItemOut` (`backend/app/api/schemas/order.py`).
- `frontend/src/routes/AllocationResultPage.tsx`: `handleCreateOrders`
  различает обычный успех, `409`-конфликт (открывает модалку с данными из
  тела ответа) и повторный вызов с `replace_drafts` по выбору пользователя.
- Новый UI-компонент модального окна конфликта — требует записи в
  `docs/ui-reference.md` (условие показа, содержимое, две кнопки, отдельная
  ступень подтверждения для поставщиков с `has_confirmed_prices`) по тому
  же правилу, что и остальные экраны проекта; сам визуал — через Claude
  Design в `docs/design/`, не вручную (правило CLAUDE.md).
- Не меняется: ADR-0007 п.2 в части `approved`/`sent`-ордеров (никогда не
  удаляются/не заменяются автоматически); статусная модель `Project.status`
  из ADR-0011 (регресс `ordered → calculated` при пересчёте остаётся как
  есть — этот ADR не отменяет его, только добавляет предупреждение в точке,
  где регресс раньше приводил к молчаливому дублированию).
- `docs/known-issues.md`: пункт «Риск дублирующего ордера после регресса
  `ordered → calculated`» закрывается этим ADR, убрать из списка отложенного
  при реализации (не раньше — до этого момента риск остаётся актуальным).
- Реализация (миграция не требуется — новых колонок в схеме БД нет; API,
  сервисный слой, фронтенд, модалка) — предмет отдельной задачи после
  вычитки этого ADR, как и с предыдущими ADR в этом проекте.

### Отклонение реализации от принятого решения (зафиксировано 2026-08-20)

**Кнопка «Создать дополнительно» (§1, §2, §4) не реализована в этой
итерации — реализация не совпадает с текстом решения выше.**

§2 утверждает: повторный `POST` с `replace_drafts: false` после показа
модалки конфликта проходит «без блокирующего `409`, потому что явное
согласие уже получено». Это оказалось неверным при живой проверке на
`#20675` (frontend-сессия, 2026-08-20): backend, как реализован (см. п.2
выше — «Реализация»), **stateless** — он не хранит и не принимает нигде
факт «пользователь уже увидел это предупреждение и явно согласился». У
эндпоинта нет входа, отличного от `replace_drafts`, чтобы отличить
«запрос ещё не спросил пользователя» от «пользователь спрошен и явно
хочет дозаказ». Оба случая на проводе неотличимы — оба сериализуются как
`{"replace_drafts": false}`. Соответственно повторный вызов с тем же
конфликтом получает тот же `409` заново, а не проходит, как
предполагало решение. Это не баг реализации в смысле "забыли строку
кода" — решение §2 в этой части описывает контракт, для выполнения
которого backend не спроектирован; между "предполагаемым" API и
"собранным" API — реальный, не гипотетический разрыв.

**Принятое в моменте решение**: кнопка «Создать дополнительно» удалена
из `OrderDraftConflictModal` (`frontend/src/components/
OrderDraftConflictModal.tsx`) в frontend-сессии, а не оставлена
фиктивно рабочей. Альтернатива — молча проглатывать повторный `409` на
фронте и вести себя так, будто дозаказ создан — отклонена: пользователь
думал бы, что второй `Order` создан, хотя на деле ничего не произошло;
это хуже честного отсутствия кнопки. Модалка сейчас предлагает только
«Отмена» и «Заменить черновики» — путь «дозаказ тому же поставщику»
(легитимный по ADR-0007 п.2) остаётся доступен исключительно **при
отсутствии конфликта** (обычный клик "Подтвердить и создать ордера",
когда draft-ордеров ещё нет) — то есть работает для первого дозаказа,
но не для дозаказа тому же поставщику, у которого уже есть draft.

**Это отклонение не переписывает §1/§2/§4 задним числом** — они
остаются как принятое решение (корректно описывают *намерение*), этот
раздел фиксирует, что *реализация* его не покрывает целиком, и почему.
Источник истины о текущем поведении UI — `docs/ui-reference.md` §3
(«Кнопки: только "Отмена" и "Заменить черновики"»), не §1/§4 этого
файла буквально.

**Статус этого отклонения на 2026-08-31: закрыто наполовину.**
Backend-разрыв, описанный выше, устранён — `POST .../orders` принимает
`acknowledge_conflict: bool = false` отдельным полем тела, и
`create_orders_for_run(..., acknowledge_conflict=True)` при конфликте
создаёт новые `Order` рядом с существующими draft, ничего не удаляя
(`201`); без флага `409` возвращается ровно как прежде. То есть §1/§2 в
части «создать дополнительно» теперь выразимы на проводе: «не спросили
ещё» — это `{}`, «спросили и пользователь хочет дозаказ» — это
`{"acknowledge_conflict": true}`. **Frontend по-прежнему не использует
это поле**: кнопка «Создать дополнительно» в `OrderDraftConflictModal`
всё ещё отсутствует, источник истины о текущем поведении UI остаётся
`docs/ui-reference.md` §3. Пока эта половина не сделана, §4 описывает
намерение, а не реализацию.

**Условие возврата — выполнено, не гипотетика**: подтверждено
пользователем 2026-08-20, что дозаказ тому же поставщику при уже
существующем draft — реальный, недавний сценарий из практики отдела
закупок, не теоретическая возможность на будущее. Full-текст follow-up
задачи (контракт нового поля, изменения в сервисном слое/фронте,
тесты) — `docs/known-issues.md`, раздел «Follow-up (не отложено —
подтверждено критично, 2026-08-20)». В отличие от остальных пунктов
`docs/known-issues.md` эта задача не откладывается на "при первом
реальном случае" — случай уже произошёл, брать в работу скоро.
