# ADR-0013: `OrderItem.received_price` и явный отказ поставщика (`declined_at`)

Статус: Принято

## Контекст

ADR-0007 формализовал сверку цены `Order` как пару `quoted_price` (что
рассчитала и отправила система) / `confirmed_price` (на чём в итоге
сошлись). Реальный процесс, описанный пользователем, устроен на одно
звено сложнее, чем эта пара: сотрудник отправляет `quoted_price`
поставщику → поставщик отвечает **своей** ценой — то, что он прислал
первым, до какого-либо торга — → сотрудник иногда торгуется → фиксируется
финальная договорённость. `confirmed_price` по смыслу — только последнее
звено ("на чём сошлись"); поля для среднего звена ("что поставщик прислал
первым") в модели нет вообще. Сейчас, если сотрудник хочет отразить и
исходный ответ поставщика, и результат торга, единственный способ —
перезаписать `confirmed_price`, потеряв исходное предложение поставщика
безвозвратно — то есть данные о том, сколько реально удалось сторговать,
физически негде хранить.

Второй, отдельный пробел: `docs/spec.md` и текущая схема `OrderItem`
(`backend/app/models/order.py:37`) не различают "поставщик ещё не
ответил" и "поставщик явно отказался/не может выполнить позицию" — оба
случая сегодня выглядят как `received_price`/`confirmed_price` оба `NULL`
(до этого ADR — просто `confirmed_price IS NULL`, п.7 ADR-0007). Тот же
класс проблемы, что уже был решён для `availability` в ADR-0005: `NULL`
там ошибочно означал "недостаточно" вместо честного "не проверялось";
здесь `NULL` рискует означать одновременно два разных факта ("ждём" и
"отказался") без способа их отличить программно. У компании реально
бывает ситуация: в плане на поставщика 30 позиций, в ответе — 28; две
недостающие нужно явно пометить, а не оставить неотличимыми от "ещё не
дошли руки сверить".

Не в объёме этого ADR (следующие задачи в очереди):
- Матрица сравнения цен по поставщикам на уровне проекта.
- Как именно declined-позиция переносится на другого поставщика
  (использует существующий override из ADR-0006, но сам триггер с экрана
  Order — отдельная задача).
- ИИ-парсинг ответа поставщика (PDF/фото) — этот ADR покрывает только
  ручной ввод текстом/числом, как и `confirmed_price` в ADR-0007 §3.

## Решение

### 1. Новое поле `OrderItem.received_price`

```python
class OrderItem(UUIDPKMixin, Base):
    ...
    quoted_price: Mapped[float] = mapped_column(Numeric(12, 2), nullable=False)
    received_price: Mapped[float | None] = mapped_column(Numeric(12, 2))
    """Цена, которую поставщик прислал первым, до торга. NULL = ответа ещё
    нет. См. ADR-0013."""
    confirmed_price: Mapped[float | None] = mapped_column(Numeric(12, 2))
    confirmed_at: Mapped[datetime | None] = mapped_column(DateTime(timezone=True))
    declined_at: Mapped[datetime | None] = mapped_column(DateTime(timezone=True))
    decline_reason: Mapped[str | None] = mapped_column(String(500))
```

`received_price` встаёт между `quoted_price` и `confirmed_price` по
семантике, не по порядку колонок в таблице (порядок колонок не имеет
значения для этой модели):

- **`quoted_price`** — что мы посчитали и отправили (ADR-0007, не
  меняется).
- **`received_price`** — что поставщик прислал **первым** в ответ, до
  каких-либо переговоров. Может быть предметом торга — это ещё не
  решение, а входные данные для решения.
- **`confirmed_price`** — на чём реально сошлись после (опционального)
  торга. Это по-прежнему "финальная договорённость", смысл поля из
  ADR-0007 не меняется ни на бит.

Оба поля `nullable`, независимо друг от друга — тот же паттерн, что
`confirmed_price` уже использует относительно `quoted_price` (ADR-0007
п.1): `NULL` = "это звено процесса ещё не произошло", не "равно нулю" и
не "равно предыдущему звену".

**`received_price` может существовать без `confirmed_price`.** Естественное
и ожидаемое промежуточное состояние: ответ получен, сотрудник ещё не
принял решение (не согласился, не начал торговаться, просто ещё не
дошли руки). Это ровно то самое "третье состояние" изначальной проблемы,
и оно не требует отдельного флага — уже описывается тем, что
`received_price IS NOT NULL AND confirmed_price IS NULL`.

**`confirmed_price` может появиться без `received_price`.** Решение:
**разрешить, не требовать `received_price` первым.** Обоснование:
реальный процесс компании не гарантирует, что каждое подтверждение
проходит через формальный "получен ответ" шаг — сотрудник может
согласиться по телефону сразу на `quoted_price` (не было расхождения,
торговаться не о чем) или получить финальную цену устно, минуя
письменный/структурированный "первый ответ". Требовать `received_price`
как обязательный предшественник означало бы либо (а) заставлять
сотрудника вводить фиктивное значение, равное `confirmed_price`, только
чтобы пройти валидацию — это врёт о процессе, который в реальности был
короче, либо (б) блокировать ввод `confirmed_price`, когда реальность
не даёт материала для среднего шага. Оба варианта хуже, чем просто
разрешить `received_price IS NULL AND confirmed_price IS NOT NULL` как
законное состояние — оно означает "подтверждено без отдельно
зафиксированного первого ответа", что и произошло на самом деле.
Backend не навязывает порядок ввода этих двух полей; PATCH (п.3)
принимает любое поле независимо.

**Отклонено: обязательный порядок (`received_price` — precondition для
`confirmed_price`, проверка на backend).** Отклонено по причине выше —
такая проверка кодифицировала бы процесс, которого нет в реальности
компании, и превратилась бы в источник трения без содержательной пользы:
ничего в данных не становится более корректным от того, что порядок
заполнения полей проверен, а сотрудник в реальном звонке с поставщиком
не обязан следовать порядку, придуманному в БД.

### 2. Явный отказ — `declined_at` / `decline_reason`

Тот же паттерн timestamp-как-признак, что `overridden_at` (ADR-0006),
`confirmed_at` (ADR-0007), `ordered_at` (ADR-0007) уже используют в этом
проекте — не изобретается заново:

- **`declined_at: DateTime | NULL`** — когда сотрудник явно пометил
  позицию как "поставщик не может выполнить/нет в наличии". `NULL` =
  не отмечено (не значит "точно доступно" — просто нет сигнала ни в
  одну сторону, симметрично тому, как `confirmed_price IS NULL` не
  означает "отклонено", а означает "не сверено").
- **`decline_reason: String | NULL`** — свободный текст, необязательное
  уточнение ("нет в наличии", "снят с производства" и т.п.). Свободный
  текст, а не enum: причины отказа не формализованы нигде в spec.md, и
  на объёме MVP (одно поле, не участвует в расчётах) закрытый список
  создал бы работу по поддержанию таксономии без выигрыша — тот же
  инстинкт, что уже применён к `Supplier.status`/`Supplier.comments`
  (`docs/data-model.md` — оба свободный текст, не enum).

**Взаимодействие с `received_price`/`confirmed_price`, если `declined_at`
установлен.** Решение для MVP: **это тот же `OrderItem`, оба набора полей
могут быть заполнены одновременно, ничего не запрещается и не
обнуляется.** Сценарий "формально отказался, но предложил заменитель по
другой цене" в этом ADR не получает отдельной сущности — заменитель
(другой материал/SKU) физически не помещается в одну строку `OrderItem`,
привязанную к конкретному `material_id`; ввод предложенного заменителя
как *новой* позиции — то же действие, что "перенос отказавшейся позиции
на другого поставщика", explicитно отложенное в "не в объёме" ниже и в
задаче. Здесь `declined_at` на конкретной строке — просто честный факт
"эта позиция у этого поставщика в этом виде не выполнима", а
`received_price` на ней (если было — например, поставщик сначала дал
цену, а потом перед подтверждением сказал "ой, этого уже нет") остаётся
как есть, потому что не противоречит факту отказа, а документирует
историю переписки. Backend не проверяет и не запрещает никакую
комбинацию `declined_at` + `received_price`/`confirmed_price` — это
осознанно оставлено человеку, по той же логике, что предупреждения (не
блокировки) уже применены к `below_min_order` (ADR-0006) и к
расхождению `overridden_at`/`ordered_at` (ADR-0007 п.2): система не
обладает контекстом переговоров, чтобы решать за сотрудника, что тут
"неправильно".

**Отклонено: `declined_at` как взаимоисключающий с
`received_price`/`confirmed_price` (проверка на backend, 400 при
конфликте).** Отклонено — реальный сценарий выше ("отказался, но
предложил замену по другой цене") прямо требует одновременного
существования обоих фактов на практике; жёсткая проверка заставила бы
сотрудника либо врать (обнулять цену, чтобы пройти валидацию), либо
заводить процесс, для которого в MVP нет модели (перенос на другой
material_id) только чтобы записать число, которое ему прямо сейчас
назвали по телефону.

### 3. Ввод — расширение существующего PATCH

`PATCH /orders/{order_id}/items/{item_id}` (ADR-0007 §3, уже существует,
`backend/app/api/order.py:102`) расширяется новыми опциональными полями,
той же single-item PATCH-семантикой, что уже применена к
`confirmed_price`:

```
PATCH /orders/{order_id}/items/{item_id}
{ "received_price": 11.80 }
{ "declined_at": "2026-08-20T14:00:00Z", "decline_reason": "нет в наличии" }
```

Каждое поле независимо: PATCH одного поля не трогает остальные (тот же
принцип, что уже применён к `confirmed_price` — явный `null` сбрасывает
парный timestamp, отсутствие поля в payload не меняет его). По
аналогии:

- `received_price` в payload (включая явный `null`) — записывается как
  есть; в отличие от `confirmed_price`, у `received_price` нет своего
  timestamp-поля (см. "Отклонено" ниже) — сверять момент получения
  явно не нужно на этом MVP, только сам факт и значение.
- `declined_at` — backend не принимает `declined_at` как timestamp от
  клиента напрямую; вместо этого payload несёт булев маркер намерения,
  и backend сам проставляет `now()` — тот же паттерн, что `confirmed_at`
  уже использует относительно `confirmed_price` (клиент не диктует
  время события, backend фиксирует момент записи). Практически: новое
  поле в `OrderItemConfirmIn` — `declined: bool | None` — `true`
  проставляет `declined_at = now()`, `false` явно сбрасывает
  `declined_at`/`decline_reason` в `NULL` (снять отметку — передумали,
  опечатались), `decline_reason` передаётся отдельным опциональным
  полем payload'а, применяется независимо от `declined`.

**UI (поведение, не разметка).** Между колонками "Отправленная цена" и
"Подтверждённая цена" появляется "Полученная цена" — та же inline-ячейка
с сохранением по `blur`/`Enter`, что уже используется для
`confirmed_price` (ADR-0007 §3), не новый визуальный паттерн. Отметка
"недоступно" — **отдельный элемент на строке (кнопка/чекбокс), не часть
формы ввода цены.** Обоснование: отказ — это не значение цены (это
факт другой природы — позиция невыполнима), у него не должно быть числа
как основного пути выражения; смешение в одну ячейку заставило бы
интерфейс различать "ввод цены" и "маркер отказа" в одном текстовом
поле, что не разделяет два разных намерения ввода так же чётко, как
физически отдельный элемент. Строка при `declined_at != null` получает
визуальную пометку (тот же словарь `--color-danger-text`/`warningRow`,
уже переиспользованный в ADR-0006 п.4 и ADR-0007 §4) независимо от
того, заполнены ли `received_price`/`confirmed_price`.

**Отклонено: `received_at: DateTime | NULL` рядом с `received_price`.**
В задаче явно спрошено только про сам факт и значение цены; ADR-0007
вводит timestamp там, где нужно мерить *момент решения* сотрудника
(`confirmed_at` — когда я согласился) — но "когда поставщик прислал
цену" не используется нигде в этом ADR (ни в расчётах, ни в UI-логике,
ни в сравнении с порогами). Добавлять поле, для которого нет
потребителя, — то же самое избыточное разрастание схемы, от которого
уже предостерегает ADR-0007 п.1 (отказ от персистентной дельты).
Если появится сценарий, где важно "сколько дней поставщик отвечал" —
отдельный ADR с этой потребностью, поле добавляется без миграции сути
уже существующих данных.

### 4. Влияние на `price_delta`

Существующий `price_delta`/`price_delta_pct` (`quoted` vs `confirmed`,
ADR-0007 §4, `backend/app/allocation/order_service.py:211`) **не
меняется** — остаётся ровно тем же расчётом с тем же порогом `>10%`.

**Дополнительный показатель `received` vs `confirmed` ("сколько
сторговали") — не добавляется в этом ADR.** Обоснование: `confirmed`
vs `quoted` уже отвечает на главный практический вопрос экрана Order —
"насколько итоговая цена разошлась с тем, что мы посчитали и заложили в
свой план" — это то число, которое имеет значение для сверки с
собственным прайсом и бюджетом проекта. "Сколько сторговали от
первого предложения поставщика" — самостоятельно интересная метрика
для *переговорной эффективности*, но она не влияет ни на один
существующий расчёт (`price_delta`, пороги предупреждений, агрегаты
Order/Project) и не была запрошена как часть текущей задачи — это то же
рассуждение, что уже отложило автоматическую связку Order↔Price в
ADR-0007 §5: вводить показатель раньше, чем видно, что он реально нужен
на практике (не просто "раз есть данные, посчитаем"), — проектирование
вслепую. `received_price` при этом уже доступен на `OrderItemOut`
(следующее поле рядом с `quoted_price`/`confirmed_price`), так что
фронтенд-код, которому в будущем понадобится вычислить `received −
confirmed` для конкретного экрана, может сделать это локально без
нового backend-поля — вычисление тривиально и не денежная операция
уровня итогов (тот же аргумент, что уже применён в ADR-0007 п.2 к
сравнению `overridden_at`/`ordered_at` на клиенте).

### 5. Declined-строки в существующих агрегатах

**Order totals (`total_amount` и т.п. на уровне `Order`) не меняются.**
`total_amount` — снимок, посчитанный один раз при создании `Order` из
`AllocationLine.line_total` (ADR-0007 §2,
`backend/app/allocation/order_service.py:182`) и не пересчитывается ни
от `confirmed_price`, ни (тем более) от нового `received_price` —
`declined_at` не меняет это поведение: `total_amount` по-прежнему
означает "план, который мы отправили поставщику", а не "то, что
реально удастся получить". Он остаётся планом до тех пор, пока не
появится отдельный, явно спроектированный шаг "пересчитать факт
закупки" — что явно отложено ниже.

Простейшее консистентное решение: **declined-позиции не исключаются ни
из `total_amount`, ни из состава `OrderItem`, факт отказа — читается
поверх плана, не убирается из него.** Обоснование, симметричное п.5
ADR-0007 ("Order — снимок, не живая ссылка"): если `declined_at`
физически вычитал бы позицию из суммы, `total_amount` перестал бы быть
снимком того, что было заказано, и стал бы гибридом "план минус то, что
сорвалось" — тот же класс проблемы, которого ADR-0007 избежал, отказавшись
пересчитывать `AllocationLine` задним числом при override после
`ordered_at`. Экран должен показывать план и статус отказа как две
раздельные вещи: сумма позиций (`total_amount`, не изменилась) и рядом —
производный (не персистентный, тот же принцип п.7 ADR-0007) счётчик
"N позиций отклонено поставщиком" на карточке Order, аналогично тому, как
уже суммируется "N позиций с расхождением >10%" (ADR-0007 §4).

**Отклонено: вычитать declined-позиции из `total_amount` или
показывать отдельный "скорректированный" итог.** Отклонено — это уже
пересечение с "не в объёме" задачи (что физически происходит с
declined-позицией дальше — перенос на другого поставщика, новый Order).
Скорректированный итог осмыслен только после того, как известно, что
случится с отклонённой позицией (заменится другим поставщиком по другой
цене? будет исключена из проекта целиком? уменьшит план без замены?) —
ни один из этих исходов не решён в этом ADR, посчитать "итог после
отказов" сейчас означало бы посчитать что-то, что не соответствует ни
одному будущему состоянию однозначно.

## Альтернативы

Альтернативы для каждого под-решения (1–5) перечислены инлайн в
"Решение" — та же структура, что уже принята в ADR-0006/ADR-0007, по
той же причине: обоснования специфичны к конкретному под-решению.

Единственная альтернатива на уровне ADR целиком: **не добавлять
`received_price` как отдельное поле, а хранить всю переписку/историю цен
как JSON-лог или отдельную таблицу `OrderItemPriceEvent` (события:
quoted → received → countered → confirmed, произвольной длины).**
Отклонено по той же причине, что ADR-0007 отклонил `OrderPriceRevision`
(журнал ревизий) в своей "Альтернативы": реальный процесс компании — один
раунд "прислали → (опционально) торгуемся → сошлись", не произвольной
длины цепочка переговоров, которую нужно воспроизводить по шагам. Три
именованных поля (`quoted`/`received`/`confirmed`) точно покрывают
описанный процесс с кратно меньшей сложностью, чем таблица событий;
вводить её сейчас — проектировать вслепую под гипотетический случай
многораундовых переговоров, которого нет в описанном процессе.

## Последствия

- Миграция Alembic: `order_items.received_price NUMERIC(12,2) NULL`,
  `order_items.declined_at TIMESTAMPTZ NULL`,
  `order_items.decline_reason VARCHAR(500) NULL`. Nullable без
  бэкафилла — семантика "не заполнено = не произошло" корректна для всех
  существующих строк.
- `OrderItemConfirmIn` (`backend/app/api/schemas/order.py`) получает
  опциональные `received_price: float | None`, `declined: bool | None`,
  `decline_reason: str | None`, независимые от существующего
  `confirmed_price`.
- `OrderItemOut` получает `received_price`, `declined_at`,
  `decline_reason` рядом с существующими `quoted_price`/
  `confirmed_price`/`confirmed_at`/`price_delta`/`price_delta_pct` —
  расчёт `price_delta` (`quoted` vs `confirmed`) не меняется (п.4).
- `set_confirmed_price` (`backend/app/allocation/order_service.py:223`)
  — переименовать/расширить под приём всех новых полей одним PATCH
  (та же single-item семантика); реализация — отдельная задача после
  вычитки этого ADR.
- `docs/data-model.md`: `OrderItem` получает `received_price`,
  `declined_at`, `decline_reason` (в дополнение к `quoted_price`/
  `confirmed_price`/`confirmed_at`, уже описанным по ADR-0007, но пока
  не отражённым в диаграмме — обновление диаграммы заодно устраняет
  этот более старый пробел).
