# ADR-0014: Замена поставщика для отклонённой позиции ордера

Статус: Принято, реализовано (2026-08-20) — backend (`GET
/materials/{material_id}/prices`, `POST
/orders/{order_id}/items/{item_id}/find-replacement`, `source_order_item_id`
на `PATCH .../lines/{line_id}`, производные поля `OrderItemOut`, миграция
`allocation_lines.overridden_via_order_item_id`) и frontend
(`OrderDetailPage.tsx`, поведение описано в `docs/ui-reference.md` §7).

## Контекст

ADR-0013 добавил `declined_at`/`decline_reason` на `OrderItem` — сотрудник
может пометить позицию как "поставщик не может выполнить", но дальше
процесс упирается в тупик: чтобы перенести материал на другого
поставщика, нужно вручную уйти с экрана Order на экран результата
аллокации проекта (`AllocationResultPage`), найти там строку с тем же
материалом, переопределить поставщика (механизм ADR-0006), вернуться на
Order, и отдельным шагом создать новый Order этому поставщику. ADR-0013
явно отложил это в "не в объёме" (п. "Не в объёме этого ADR").

Пользователь принял решения по UX заранее, до этого ADR:

- После выбора замены — остаться на странице Order, без автонавигации.
- Список кандидатов на замену показывает **всех** поставщиков с ценой на
  материал, включая тех, где `availability` `null`/недостаточно — та же
  философия видимого, не скрытого риска, что ADR-0006 §2 уже применил к
  ручному override.
- Создание нового `Order` этому переносу не входит — остаётся отдельным
  ручным шагом ("Подтвердить и создать ордера" на экране проекта).

Два существующих архитектурных факта ограничивают решение:

- `OrderItem` **не хранит** `allocation_line_id` (ADR-0007 §2) — сознательно,
  чтобы `Order` оставался снимком, не живой ссылкой на текущее состояние
  плана.
- Механизм переопределения поставщика на строке уже существует
  (`PATCH /projects/{project_id}/allocations/{run_id}/lines/{line_id}`,
  ADR-0006) — эта задача обязана переиспользовать его, не изобретать
  второй способ поменять `AllocationLine.supplier_id`.

Не в объёме этого ADR (явно перечислено в задаче):

- Полная матрица сравнения по всем материалам проекта сразу — отдельная
  будущая задача.
- Автоматическое создание нового `Order` при переносе.

## Решение

### 1. Источник кандидатов на замену — новый endpoint

```
GET /materials/{material_id}/prices
```

Возвращает активные цены (`valid_to IS NULL`) на материал по всем
поставщикам — тот же набор данных, который сейчас собирается на клиенте
в `AllocationResultPage.tsx` (`buildCheapestPriceIndex`/
`buildPricesByMaterialIndex`, построены из полного `GET /prices`), но
отфильтрованный на backend по одному материалу.

**Отклонено: переиспользовать `GET /prices` без фильтра, фильтровать на
клиенте, как уже делает `AllocationResultPage`.** Там это оправдано —
страница и так грузит весь прайс-лист для всех строк проекта разом.
Здесь контекст другой: экран Order открывает поиск замены для **одной**
declined-позиции, тянуть весь прайс-лист ради одного материала — лишняя
нагрузка без причины, и создаёт второе место, которое должно знать
формат полного `PriceOut` и уметь его группировать, вместо одного
специализированного запроса. Новый endpoint — тонкий: `SELECT` с
`WHERE material_id = :id AND valid_to IS NULL`, без нового слоя бизнес-логики.

Для каждого кандидата фронтенд показывает: имя поставщика, цену,
явный визуальный риск — переиспользуется тот же `--color-danger-text`
язык и та же логика показа, что `.availabilityRisk` на
`AllocationResultPage` (ADR-0006 §2): предупреждение показывается, когда
`availability` явно задан (не `null`) и меньше `line.quantity`
declined-позиции; `availability IS NULL` не блокирует и не помечается
как риск (симметрично ADR-0005 — "не проверялось" ≠ "недостаточно").
Текст предупреждения — тот же формат: "⚠ у поставщика доступно
{availability} {unit}, требуется {quantity}".

**Отклонено: не показывать /скрывать кандидатов без availability или с
недостаточным availability.** Явно отклонено пользователем в постановке
задачи — та же причина, что ADR-0006 §2 уже привёл для ручного
override: сотрудник может располагать контекстом (звонил поставщику),
которого нет в системе; скрытие кандидата — это решение за пользователя,
принятое неполными данными.

### 2. Какую `AllocationLine` переопределять

Триггер — кнопка "Найти замену" на declined-строке `OrderDetailPage`
(`item.declined_at != null`), не отдельная секция с ручным выбором
материала: материал уже известен из контекста строки
(`item.material_id`).

По клику backend (новый endpoint, см. п.5) ищет строку для
переопределения так:

1. Найти последний `AllocationRun` проекта — тот же запрос, что уже
   существует в `get_project()` (`backend/app/api/project.py:80-85`,
   `ORDER BY created_at DESC LIMIT 1`), не `AllocationRun`, которым был
   создан текущий `Order` (тот план мог с тех пор измениться — новый
   расчёт, новые override).
2. В строках этого run найти `AllocationLine` с
   `material_id == item.material_id`.

**Материал отсутствует в последнем `AllocationRun`** (например, позицию
удалили из BOM проекта после создания этого `Order`) — переопределять
нечего. Backend возвращает `404` с понятным сообщением ("материал
{material_name} отсутствует в текущем плане проекта — расчёт после
создания этого ордера мог измениться"), фронтенд показывает его как
инлайн-сообщение под кнопкой "Найти замену", не как `ErrorBanner`
уровня страницы (тот же принцип точечной локализации ошибки, что уже
применён к `warningBlock`/`availabilityRisk` — ошибка контекстна одной
строке, не всей странице).

**Материал уже переопределён раньше на кого-то, не совпадающего с
declined-поставщиком** (обычный сценарий — план успел измениться
независимо от этого отказа) — переопределяем ещё раз, стандартное
поведение ADR-0006 §5 п.2: `original_supplier_id`/`original_unit_price`
не перезаписываются повторным override.

Сам PATCH переопределения — существующий endpoint ADR-0006
(`PATCH .../lines/{line_id}`), новый код здесь — только поиск
`line_id` по `material_id` в последнем run и его подстановка, шаг перед
уже существующим PATCH, не новый механизм записи.

### 3. Постоянная пометка на declined-строке после переноса

После успешного override, страница Order остаётся на месте (без
навигации). Рядом с declined-строкой появляется постоянный (не
исчезающий) блок:

- Текст "→ Перенесено на {new_supplier_name}".
- Статус по этому переносу, вычисляется **на лету**, не персистентное
  поле — тот же принцип, что уже применён к `below_min_order`
  (ADR-0006 §4) и к производным "жду ответа"/"сверено" на `Order`
  (ADR-0007 §7): "есть черновик" против "ордер ещё не создан".

**Откуда берётся признак "перенесено" — почему timestamp-сравнение не
годится.** Первая версия этого раздела предлагала вычислять перенос
чисто из существующих полей: "`overridden_at` строки позже
`item.declined_at`". Это ложно-положительно: строка того же материала
может быть переопределена по совершенно другой причине в любой момент
после отметки `declined_at` — например, сотрудник вручную меняет
поставщика на `AllocationResultPage` по причине цены, никак не связанной
с этим конкретным отказом, но случайно позже него по времени. Сравнение
timestamp'ов путает "случилось после" с "случилось из-за" — у него нет
способа отличить причинно-следственную связь от совпадения по времени,
а показать "→ Перенесено на B" в ответ на отказ, когда перенос на B на
самом деле никак не связан с этим отказом, — то самое "скрытое
сообщение поверх факта", от которого явно предостерегает философия
видимого риска в остальной части этого ADR.

Решение: новое nullable-поле на `AllocationLine`:

```python
overridden_via_order_item_id: Mapped[uuid.UUID | None] = mapped_column(
    UUID(as_uuid=True), ForeignKey("order_items.id")
)
```

Проставляется **только** endpoint'ом override, вызванным из
find-replacement-флоу этого ADR (см. п.5) — обычный ручной override на
`AllocationResultPage` (ADR-0006) оставляет его `NULL`, как и было до
этого ADR. Однонаправленная связь `AllocationLine → OrderItem`, не
наоборот — **не нарушает** ADR-0007 §2: `OrderItem` по-прежнему не
хранит `allocation_line_id` и остаётся снимком, живой ссылки от Order к
плану не появляется. Появляется противоположная, более слабая связь —
"эта строка плана была востребована из этой declined-позиции" — по
аналогии с `Price.source_import_id`, на который ADR-0006 §1 уже ссылался
как на прецедент "атрибут происхождения текущего значения", не
независимая сущность со своим жизненным циклом.

При загрузке `OrderDetailPage` для каждой declined-строки backend
проверяет: тот же последний `AllocationRun` (п.2), та же строка по
`material_id`, и если `overridden_via_order_item_id == item.id` — это и
есть перенос, инициированный именно этой declined-позицией. Точный
причинный признак, не эвристика по времени. Если строка того же
материала была переопределена, но `overridden_via_order_item_id`
указывает на `NULL` или на другой `OrderItem.id` (или вообще не
установлен) — пометка "→ Перенесено" не показывается, даже если
`overridden_at > item.declined_at`: перенос был, но не из этого
конкретного отказа.

Читаем `AllocationLine.supplier_id` найденной строки как
`new_supplier_id`. Вычисляется на backend вместе с ответом
`GET /orders/{id}` (шаг 1 уже требует запроса последнего
`AllocationRun` проекта, которого `OrderDetailPage` сейчас не грузит
вообще) и отдаётся как новое производное поле `OrderItemOut`
(`replaced_by_supplier_id`/`replaced_by_supplier_name`, `null` если
переноса не было или он от другой причины).

**Что если ту же строку затем переопределят в третий раз (уже не через
find-replacement)?** `overridden_via_order_item_id` перезаписывается
обычным PATCH ADR-0006 как любое другое поле строки (в отличие от
`original_supplier_id`/`original_unit_price`, которые сознательно не
трогаются повторным override, см. ADR-0006 §1) — если новый override
пришёл не из find-replacement-флоу, поле должно стать `NULL`, чтобы не
продолжать приписывать текущее состояние строки старому отказу, из-за
которого она уже не назначена. Практически: обычный ручной PATCH
(`AllocationLineOverrideIn`, ADR-0006) всегда сбрасывает поле в `NULL`;
только вызов из-под find-replacement (п.5) передаёт его явно.

Наличие черновика новому поставщику — переиспользует ту же проверку,
что уже есть для конфликта draft-ордеров (ADR-0012,
`_conflicting_draft_orders_by_supplier` в
`backend/app/allocation/order_service.py:61-80`), примененную к одному
`new_supplier_id` вместо списка. Если находится `Order` со
`status == "draft"` этого поставщика в этом проекте — фронтенд
показывает ссылку на него; если нет — текст "ордер ещё не создан".

**Отклонено: чистое timestamp-сравнение без новой колонки (`overridden_at
> declined_at`).** Отклонено по причине, разобранной выше, — не
причинный признак, ложные срабатывания на совпадение по времени.

**Отклонено: новое поле `replaced_at` на `OrderItem` вместо FK на
`AllocationLine`.** Отклонено по той же причине, что и в первой версии
этого раздела: если план после переноса переопределят ещё раз (третий
override той же строки другой причиной), персистентная пометка на
`OrderItem` осталась бы врать про поставщика, которого уже нет в
текущем плане. `overridden_via_order_item_id` на `AllocationLine`
избегает этого — он живёт на той же строке, чьё текущее состояние и
описывает, и обнуляется вместе с изменением этого состояния (см. выше).

### 4. Судьба declined-`OrderItem`

Ничего не меняется и не удаляется. `OrderItem` остаётся историческим
снимком — ADR-0007 "снимок, не кэш": то, что этому поставщику было
отправлено, по какой цене, и что он отклонил эту позицию, — факт
прошлого, который перенос не отменяет и не переписывает.

Перенос создаёт новое состояние только в текущем плане проекта
(`AllocationLine.supplier_id` после override) — независимо от `Order`, из
которого был инициирован клик "Найти замену". Явно: `declined_at`,
`decline_reason`, `quoted_price` и все прочие поля исходного `OrderItem`
не трогаются этим ADR ни при каком исходе поиска замены (успех, 404
"материал не найден", повторный override).

### 5. Новый endpoint для самого действия

```
POST /orders/{order_id}/items/{item_id}/find-replacement
```

Тело не требуется (материал и declined-контекст уже известны из
`item_id`). Ответ — список кандидатов (п.1) с ценами, availability и
явным признаком риска; сам выбор кандидата — отдельное действие
пользователя на фронте (клик по конкретному кандидату), которое вызывает
уже существующий `PATCH .../lines/{line_id}` (ADR-0006) с `line_id`,
найденным на backend по правилам п.2, и `supplier_id` выбранного
кандидата.

Этот конкретный вызов `PATCH` — единственное место, где
`AllocationLineOverrideIn` (ADR-0006) несёт необязательное поле
`source_order_item_id`, которое backend записывает в
`AllocationLine.overridden_via_order_item_id` (п.3). Фронтенд передаёт
`item_id` declined-позиции при вызове из find-replacement-флоу; обычный
ручной override на `AllocationResultPage` этого поля не передаёт, и
backend в этом случае явно сбрасывает
`overridden_via_order_item_id = NULL` (см. п.3, "что если строку
переопределят в третий раз").

**Отклонено: один endpoint, который сразу и ищет кандидатов, и
выполняет override за один вызов (без промежуточного выбора).**
Отклонено — задача явно требует, чтобы пользователь видел список **всех**
кандидатов с рисками и выбирал сам (п.1); скрытый автовыбор "самого
дешёвого" противоречил бы прямому требованию видимости риска и не
воспроизводил бы то же поведение, что уже есть у ручного override на
`AllocationResultPage` (select, не автовыбор).

**Отклонено: `GET` вместо `POST` для поиска кандидатов.** `GET` больше
подошёл бы по идемпотентности (это чтение, не запись), но действие
завязано на конкретный `order_id`/`item_id` в пути и семантически
представляет собой шаг workflow ("найти замену для этой отклонённой
позиции"), а не универсальный запрос данных — решение не архитектурное,
можно оставить как деталь реализации; текущий выбор `POST` — чтобы
явно отличать от "просто GET цен материала" (п.1, тот endpoint
самостоятельный и переиспользуемый).

## Альтернативы

Альтернативы для каждого под-решения — инлайн в "Решение" (1–5), та же
структура, что уже принята в ADR-0006/0007/0013.

Альтернатива на уровне ADR целиком: **не вводить отдельный UI-путь на
экране Order, вместо этого просто добавить прямую ссылку "Перейти к
распределению" на declined-строке, ведущую на `AllocationResultPage` с
подсветкой нужного материала.** Отклонена явно пользователем в
постановке задачи — весь смысл в том, чтобы не покидать экран Order;
ссылка на другой экран воспроизводит именно тот тупик, который эта
задача должна устранить.

## Последствия

- Новый endpoint `GET /materials/{material_id}/prices`
  (`backend/app/api/price.py` или `backend/app/api/material.py` —
  деталь реализации) — активные цены на один материал по всем
  поставщикам.
- Новый endpoint `POST /orders/{order_id}/items/{item_id}/find-replacement`
  (`backend/app/api/order.py`) — ищет `AllocationLine` в последнем
  `AllocationRun` проекта по `material_id`, возвращает кандидатов (п.1)
  либо `404` с понятным сообщением, если материала нет в текущем плане
  (п.2).
- Миграция Alembic: новая nullable-колонка
  `allocation_lines.overridden_via_order_item_id` (FK → `order_items.id`,
  `ON DELETE SET NULL`) — без бэкафилла, все существующие строки
  получают `NULL` (п.3).
- `OrderItemOut` (`backend/app/api/schemas/order.py`) получает
  производные (не персистентные) поля для пометки переноса: как минимум
  `replaced_by_supplier_id`/`replaced_by_supplier_name` (`null`, если
  переноса не было или произошла по другой причине) — вычисляются на
  backend при `GET /orders/{id}` по правилу п.3 (сверка
  `overridden_via_order_item_id == item.id`). Точные имена полей —
  деталь реализации.
- Существующий `PATCH .../lines/{line_id}` (ADR-0006) получает новое
  необязательное поле запроса `source_order_item_id` (см. п.5) — контракт
  расширяется, не ломается: поле опционально, старые вызовы без него
  продолжают работать как раньше и явно обнуляют
  `overridden_via_order_item_id`.
- `OrderDetailPage.tsx` — новая кнопка "Найти замену" на declined-строке,
  список кандидатов (риск-язык из ADR-0006 §2), постоянный блок "→
  Перенесено на {supplier}" + статус наличия черновика (п.3). Без
  автонавигации после выбора.
- `docs/ui-reference.md` §7 — дополнить поведением "Найти замену",
  списком кандидатов, пометкой переноса, вслед за существующим описанием
  `declined_at`.
- `docs/data-model.md` — добавить `AllocationLine.overridden_via_order_item_id`
  (FK → `order_items.id`, nullable, "добавлено сверх исходной диаграммы",
  по образцу уже помеченных `overridden_at`/`original_supplier_id`/
  `ordered_at`); примечание, что `OrderItemOut` несёт производные поля о
  статусе переноса, аналогично уже отмеченным `price_delta`/
  `price_delta_pct`.
- Явно не в объёме (см. "Контекст"): полная матрица сравнения по всем
  материалам проекта сразу; автоматическое создание `Order` при переносе
  — оба остаются отдельными будущими задачами.
- Реализация (миграция, оба новых endpoint'а, расширение `PATCH
