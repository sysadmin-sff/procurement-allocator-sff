# ADR-0015: Быстрый перенос declined-позиции синхронизирует ордер

Статус: Принято, backend реализован (2026-08-20) — `POST
/orders/{order_id}/items/{item_id}/replace-and-order`
(`backend/app/api/order.py`), `replace_and_sync_order()`
(`backend/app/allocation/order_service.py`). Frontend не реализован —
`OrderDetailPage.tsx` пока вызывает старую связку `overrideLine` +
`GET /projects/{id}` (§4 не выполнен).

## Контекст

ADR-0014 добавил на `OrderDetailPage` перенос declined-позиции на другого
поставщика через "Найти замену" — клик по кандидату переопределяет
`AllocationLine.supplier_id` в текущем плане проекта. ADR-0014 сознательно
оставил создание/обновление `Order` за пределами задачи:

> Создание нового `Order` этому переносу не входит — остаётся отдельным
> ручным шагом ("Подтвердить и создать ордера" на экране проекта).

На практике (реальная проверка на проекте `#20675`, материал "36'' x 80"
Door Blank with 8" Kick Plate") это оказалось нерабочим потоком, а не
приемлемым разделением ответственности. После переноса на JM Fasteners
постоянная пометка "→ Перенесено на JM Fasteners" показывала ссылку на
уже существующий draft-ордер этого поставщика — но эта ссылка вела на
ордер, который **не содержал** перенесённую позицию: перенос менял
только план (`AllocationLine`), не `Order`/`OrderItem`. Чтобы реально
довести перенос до ордера, пользователю нужно было покинуть экран Order,
перейти на экран распределения, найти позицию там и запустить
"Подтвердить и создать ордера" на весь проект — то самое "уйти с экрана
Order, чтобы завершить перенос одной позиции", которого ADR-0014 явно
хотел избежать (см. ADR-0014 "Альтернатива на уровне ADR целиком",
отклонённая по той же причине).

Пользователь явно запросил: перенос должен одним действием менять план
**и** синхронизировать ордер нового поставщика с пересчитанными суммами,
без похода на другой экран.

Разбор в диалоге (2026-08-20) сузил запрос до конкретных решений —
зафиксированы в дизайне `docs/superpowers/specs/2026-08-20-fast-replacement-order-sync-design.md`,
этот ADR фиксирует то же решение как источник архитектурной истины
проекта.

Явно вынесено за пределы этой задачи (подтверждено пользователем):
изменение модели статусов `Order` в зависимости от заполненности
`received_price`/`confirmed_price` — отдельная, самостоятельная задача,
не связанная с переносом на другого поставщика.

## Решение

### 1. Один endpoint вместо связки из двух вызовов

```
POST /orders/{order_id}/items/{item_id}/replace-and-order
{ "supplier_id": "<выбранный кандидат>" }
```

Заменяет сегодняшнюю связку `PATCH .../lines/{line_id}` (с
`source_order_item_id`) + отдельный `GET /projects/{id}` за
`latest_allocation_run.id` на фронте (введённую этой сессией как
временное решение поверх ADR-0014, до этого разговора). Одной
транзакцией на backend:

1. Находит `line_id` — `AllocationLine` в последнем `AllocationRun`
   проекта для `item.material_id`. Переиспользует ту же логику поиска,
   что уже есть в `find_replacement_candidates()`
   (`backend/app/allocation/order_service.py`, ADR-0014 п.2) — не
   дублирует её.
2. Override `AllocationLine.supplier_id = supplier_id`,
   `overridden_via_order_item_id = item_id` — переиспользует
   существующую `override_allocation_line_supplier()`
   (`backend/app/allocation/service.py`, ADR-0006/ADR-0014 п.5) как
   есть, без изменений её контракта.
3. Ищет `Order` с `supplier_id == <выбранный кандидат>` и
   `project_id == <проект declined-позиции>` со `status == "draft"`.
   - **Есть один** → добавляет новый `OrderItem` (`material_id` —
     `item.material_id`, `quantity` — `AllocationLine.quantity` после
     override, `quoted_price` — цена выбранного кандидата из
     `find_replacement_candidates`) к этому `Order`. Существующие
     позиции этого ордера, включая их `confirmed_price`/
     `received_price`, не читаются и не изменяются.
   - **Есть несколько draft-ордеров этого поставщика в проекте**
     (известный риск ADR-0012 "Контекст" — дубли уже встречались в
     реальных данных) → `409 Conflict`, транзакция откатывается
     целиком — override плана (шаг 2) не применяется, ничего не
     создаётся и не изменяется (тот же паттерн, что уже применён к
     дублю `material_id` внутри одного ордера ниже). Сообщение
     объясняет причину явно: "У поставщика {name} уже есть {N}
     черновика ордеров по этому проекту — сначала определитесь, какой
     из них актуален, прежде чем переносить сюда позицию." Не
     пытается автоматически определить "правильный" черновик по
     эвристике (`created_at`, `id` и т.п. — `id` как UUID v4 в
     частности не хронологичен и не даёт детерминированного критерия)
     — тот же инстинкт, что уже применён к дублю материала: безопаснее
     вернуть понятную ошибку, чем угадать намерение пользователя.
     Разрешение конфликта — ручное, не в объёме этой задачи (см. §3).
   - **Нет ни одного** → создаётся новый `Order(status="draft")` с
     этой одной позицией.
   - **В целевом draft-ордере уже есть `OrderItem` с тем же
     `material_id`** → `409 Conflict`, транзакция откатывается
     целиком — ни override плана (шаг 2), ни изменение `Order` не
     применяются. Редкий случай (дубль материала в плане поставщика),
     не разрешается автоматически, требует ручного вмешательства.
4. Пересчитывает `total_amount`/`delivery_fee` **только этого одного**
   `Order` — берёт `goods_total`/`delivery_fee`/
   `free_shipping_achieved` для `supplier_id` из `supplier_summaries`
   того же `AllocationRun`, который уже используется в шаге 1. Не
   вводит отдельную формулу пересчёта доставки — переиспользует то,
   что уже посчитал солвер и что уже видно для этого поставщика на
   `AllocationResultPage`.
5. Возвращает обновлённый `OrderItemOut` declined-позиции — тот же
   набор производных полей, что и сейчас (`replaced_by_supplier_id`,
   `replaced_by_supplier_name`, `replacement_draft_order_id`,
   ADR-0014 п.3), без изменения их схемы. Единственное изменение
   поведения: `replacement_draft_order_id`, когда не `null`, теперь
   **всегда** указывает на `Order`, реально содержащий перенесённую
   позицию (раньше — на любой существующий draft этого поставщика,
   независимо от содержимого).

`404`, если материал отсутствует в последнем `AllocationRun`
(`MaterialNotInLatestRunError`, ADR-0014 п.2) — поведение не меняется,
тот же код ошибки, то же сообщение.

Существующий `PATCH .../lines/{line_id}` с `source_order_item_id`
(ADR-0014 п.5) не удаляется и не меняет контракт — остаётся
низкоуровневым примитивом override, которым продолжает пользоваться
обычный ручной override на `AllocationResultPage` (без
`source_order_item_id`) и, при желании, любой будущий вызов, которому
не нужна синхронизация с `Order`. Новый endpoint — специализированная
обёртка поверх него плюс работа с `Order`, используется только из
find-replacement-флоу `OrderDetailPage`.

**Отклонено: расширить сам `PATCH .../lines/{line_id}` синхронизацией
с `Order`.** Отклонено — этот endpoint используется и обычным ручным
override на `AllocationResultPage` (ADR-0006), где создание/изменение
`Order` было бы неожиданным побочным эффектом клика на строке
распределения, ничего общего с declined-позициями не имеющего. Новый
endpoint, специфичный для find-replacement-флоу, держит эту
синхронизацию явной и опциональной, а не встроенной в общий примитив.

### 2. Без модального подтверждения

Клик по кандидату сразу выполняет перенос и синхронизацию — без
промежуточного pop-up "подтвердите перенос".

Обоснование: операция не разрушительна — не удаляет существующие
позиции целевого draft-ордера, не трогает их `confirmed_price`/
`received_price` (шаг 3 выше). Это тот же критерий обратимости, что
уже разделяет в ADR-0012 §1 "draft без confirmed_price" (тривиально
восстановим) от "draft с confirmed_price" (требует отдельной ступени
подтверждения, потому что удаляет невосстановимые данные) — здесь
ничего не удаляется, только добавляется новая строка, поэтому даже
более лёгкий критерий ADR-0012 (простое предупреждение) не применяется:
нет данных, теряемых этой операцией, о потере которых нужно
предупреждать.

**Отклонено: pop-up подтверждения перед каждым переносом.** Отклонено
пользователем в обсуждении явно — операция безопасна, лишний клик не
имеет обоснования по той же логике, что уже применена в
ADR-0012 §4 "Отклонено: показывать предупреждение всегда".

### 3. Что не входит в эту задачу

- Автоматическое создание `approved`/`sent` ордеров — новый/обновлённый
  `Order` всегда получает `status = "draft"`, как и весь остальной flow
  создания ордеров в проекте (ADR-0007/ADR-0012).
- Изменение модели статусов `Order` в зависимости от заполненности
  `received_price`/`confirmed_price` — отдельная задача, явно отложена
  пользователем в этом же разговоре, не расширяет объём этого ADR.
- Полный пересчёт доставки/`per_order_min_amount` "с нуля" для одного
  ордера отдельной формулой — переиспользуется то, что уже посчитал
  солвер в `supplier_summaries` текущего `AllocationRun` (шаг 4 выше).
- Автоматическое разрешение конфликта "несколько draft-ордеров одного
  поставщика" — известный риск ADR-0012 "Контекст". Эта задача его не
  решает и не выбирает между дублями молча — при обнаружении такого
  конфликта endpoint возвращает `409` (шаг 3 выше), разбор остаётся
  ручным (например, вручную объединить/удалить дубли на экране
  проекта, затем повторить перенос).
- UI для показа/разрешения этого `409` пользователю (модалка со
  списком дублей, выбор нужного) — не в объёме; в первой итерации
  инлайн-сообщение под кнопкой (по аналогии с текущим `404` из
  ADR-0014 п.1) достаточно — деталь реализации.

### 4. Frontend

`frontend/src/routes/OrderDetailPage.tsx`: клик по кандидату в панели
find-replacement (введённой ADR-0014, реализованной в этой же сессии)
вызывает новый `ordersApi` метод, обёртку над
`POST .../replace-and-order`, вместо сегодняшней связки
`allocationApi.overrideLine` + `projectsApi.get` за `run_id`. После
успеха поведение не меняется: полный повторный `GET /orders/{id}`
(ADR-0014 п.6), без навигации на другой экран — тот принцип, ради
которого весь флоу существует, этим ADR не пересматривается.

Постоянный блок "→ Перенесено на {supplier}": текст ссылки на
`replacement_draft_order_id` возвращается к простому "черновик уже
создан »" (убирается оговорка "позиция пока не добавлена",
добавленная в предыдущей итерации этой же сессии как временное честное
объяснение бага, который устраняет этот ADR — после реализации эта
оговорка станет неверной: ссылка будет вести на ордер, где позиция
реально есть).

## Альтернативы

**Пересоздавать draft целиком через существующий `replace_drafts=true`
(ADR-0012), применённый только к supplier_id нового поставщика.**
Отклонено пользователем в обсуждении — `replace_drafts` удаляет и
пересоздаёт **все** существующие позиции целевого draft-ордера,
включая их `confirmed_price`, ради добавления одной строки; несоразмерный
риск потери данных для операции, которая концептуально должна быть
"добавить одну строку", не "пересобрать ордер заново".

**Модальное подтверждение перед каждым переносом.** Отклонено, см. §2.

**Дубликат материала в целевом ордере — автообъединение (обновить
`quantity`/цену существующей строки вместо ошибки).** Отклонено —
редкий случай, неочевидно ожидаемое поведение (сложить количество?
заменить цену? какая из двух цен корректна?); безопаснее вернуть `409`
и оставить ручной разбор человеку, чем угадывать намерение.

**Полный пересчёт delivery_fee/free_shipping для одного ордера
собственной формулой, без использования `supplier_summaries`
солвера.** Отклонено — solver уже является единственным источником
истины для этих величин (ADR-0002); повторная реализация той же
формулы в другом месте создала бы два места, которые должны remain in
sync, вместо переиспользования уже посчитанного результата текущего
`AllocationRun`.

## Последствия

- Новый endpoint `POST /orders/{order_id}/items/{item_id}/replace-and-order`
  (`backend/app/api/order.py`) — единая транзакция override + добавление/
  создание `OrderItem`/`Order` + пересчёт `total_amount`/`delivery_fee`
  для одного `Order`.
- Новая функция в `backend/app/allocation/order_service.py`
  (например `replace_and_sync_order()`), переиспользующая
  `find_replacement_candidates()`'s логику поиска строки и
  `override_allocation_line_supplier()` как есть — не новый механизм
  override, обёртка над существующим.
- Новая Pydantic-схема запроса (`{"supplier_id": uuid.UUID}`) и, скорее
  всего, переиспользование существующего `OrderItemOut` для ответа
  (детали именования — на этапе реализации).
- `frontend/src/api/orders.ts` — новый метод `ordersApi`, обёртка над
  `POST .../replace-and-order`.
- `frontend/src/routes/OrderDetailPage.tsx` — `ReplacementTrigger`
  переключается на новый метод вместо связки `allocationApi.overrideLine`
  + `projectsApi.get`; текст ссылки "черновик уже создан »"
  возвращается к прежней формулировке без оговорки про недобавленную
  позицию.
- `docs/ui-reference.md` §7 — обновить описание клика по кандидату:
  теперь синхронизирует `Order`, не только план.
- ADR-0014 остаётся в силе во всём, что не переопределено здесь —
  источник кандидатов (`GET /materials/{id}/prices`), состав панели
  кандидатов, риск-язык, инлайн-404, постоянная пометка "→ Перенесено"
  и её причинный признак (`overridden_via_order_item_id`) не меняются.
- Не в объёме (см. "Контекст" и §3): статусы `Order` по заполненности
  цен — отдельная будущая задача.
- Реализация (endpoint, сервисный слой, фронтенд, тесты) — предмет
  отдельного плана после этого ADR, как и с предыдущими ADR в проекте.
