# ADR-0016: Матрица сравнения цен по материалам проекта

Статус: Предложено

## Контекст

Пользователь показал реальный Excel-пример: таблица, где строки —
материалы проекта, колонки — поставщики, ячейки — цены, самая дешёвая
ячейка в каждой строке подсвечена заливкой. Это привычный сотруднику
формат анализа "у кого что лучше заказать" — визуальное сравнение всех
поставщиков по всем материалам сразу, а не по одному поставщику за раз.

Ни один существующий экран не даёт этот разрез:

- `AllocationResultPage` (`/projects/:id/allocation`) группирует **по
  поставщику** (карточка на поставщика, строки внутри неё — только
  материалы, которые ему назначены) — не видно, что было бы у других
  поставщиков по той же позиции, кроме бейджа "не самая дешёвая цена"
  на одной строке.
- `OrderDetailPage` (`/orders/:id`) — ещё уже: один конкретный `Order`
  одного поставщика, сверка `quoted`/`received`/`confirmed` (ADR-0007,
  ADR-0013).
- `GET /materials/{material_id}/prices` (ADR-0014 §1) уже отдаёт ровно
  нужный набор данных, но per-material и без UI поверх — введён как
  внутренний источник для find-replacement, не как самостоятельный
  экран.

Два архитектурных прецедента, которые это решение обязано соблюдать:

- **CLAUDE.md принцип 4** — денежные операции только на backend;
  подсветка минимума и любые суммы считаются на backend, не на клиенте.
- **Философия видимого риска** (ADR-0006 §2, ADR-0014 §1) — не скрывать
  данные с неполным `availability`, помечать риск явно, а не молчаливо
  исключать из сравнения.

Не в объёме этого ADR (явно указано в задаче): любые изменения в самом
ILP-солвере или в логике выбора поставщика — только новое отображение
уже существующих данных.

## Решение

### 1. Источник данных — два раздела на одном экране, не переключатель

Два вопроса из задачи ("у кого вообще есть материал" vs "что реально
ответили по этому проекту") получают **два раздела одной страницы**, не
переключатель между ними и не два отдельных экрана:

- **"План"** — из `Price` (`valid_to IS NULL`), по всем поставщикам
  независимо от того, отправляли ли им что-то по этому проекту.
- **"Ответы поставщиков"** — из `OrderItem` (`quoted_price`/
  `received_price`/`confirmed_price`) существующих `Order` этого
  проекта, только по поставщикам, которым что-то реально отправлено.

**Отклонено: переключатель (радиокнопка/таб "план" vs "ответы"),
скрывающий один раздел, пока не выбран.** Отклонено, потому что это два
разных момента одного и того же решения "кому заказать" — сотрудник
типично смотрит на них **вместе**: "по прайсу дешевле всех был A, но
реально ответил только B, и он подтвердил на 8% дороже плана" — вопрос,
для ответа на который нужны оба раздела в поле зрения одновременно, не
последовательный просмотр. Переключатель заставил бы держать в памяти
числа одного раздела, листая ко второму. Дополнительная причина: раздел
"Ответы поставщиков" по определению уже, чем "План" (только поставщики,
которым отправляли) — это не альтернативные проекции одних данных, а
разные по составу наборы, скрывать один из них поведением "или/или" не
соответствует их природе.

**Отклонено: два отдельных экрана/роута.** Отклонено — оба раздела
относятся к одному и тому же уровню агрегации (весь проект, все
материалы BOM, п.2) и к одной и той же задаче пользователя ("сравнить
поставщиков перед решением"); отдельные роуты добавили бы навигацию
между ними без причины, когда обе таблицы умещаются одна под другой на
одной странице (как уже сделано на `ProjectDetailPage` с несколькими
секциями — "Ордера" и "Спецификация материалов" друг под другом,
`frontend/src/routes/ProjectDetailPage.tsx:186-226`).

Если по проекту ещё не создано ни одного `Order` — раздел "Ответы
поставщиков" присутствует, но показывает пустое состояние ("Ордера ещё
не созданы — сравнение по факту появится после отправки"), не
скрывается целиком: раздел "План" полезен уже на этапе `calculated`, до
`ordered` (ADR-0011), и экран не должен требовать более позднего
статуса проекта, чтобы открыться вообще.

### 2. Уровень агрегации — весь проект, подтверждено

Одна матрица на проект: все строки `ProjectItem` (BOM), все поставщики,
у которых есть цена хотя бы на один из материалов проекта (для "Плана")
или которым отправлен хотя бы один `Order` (для "Ответов поставщиков").
Это правильный уровень — существующие экраны уже покрывают более узкие
разрезы (один поставщик — `AllocationResultPage`-карточка,
`OrderDetailPage`; один материал — `GET /materials/{id}/prices`,
ADR-0014). Матрица заполняет ровно недостающий разрез — "все × все" — и
не дублирует ни один из них.

### 3. Пустая ячейка — три разных состояния, разные обозначения

Ячейка матрицы различает три факта, ни один не путается с ценой `$0`:

- **Нет цены в справочнике** (раздел "План"): у поставщика нет активной
  `Price` на этот материал. Отображается как `—` (тире), с `title`/
  tooltip "нет цены в справочнике".
- **Не отправляли** (раздел "Ответы поставщиков"): этому поставщику не
  создан `Order` с этим материалом в этом проекте. Отображается как
  пустая ячейка без символа (не `—`) — визуально более "невидимая", чем
  "нет цены", потому что это не факт о рынке (у поставщика может быть
  прекрасная цена, её просто не спрашивали), а факт о процессе
  сотрудника. Разница в написании (`—` vs пусто) — намеренная,
  небольшая, но обе ячейки дополнительно неактивны (не hoverable, не
  выглядят как данные) — их не спутать с обозначением "не проверялось"
  у `availability` (ADR-0005), которое означает "нет данных, но не
  исключает" на другом уровне модели, не на уровне UI-ячейки.
- **Отказался** (раздел "Ответы поставщиков", `declined_at != null`,
  ADR-0013): это **не** "нет данных" — заказ был отправлен, поставщик
  ответил отказом. Отображается как текст "Отказался" (тем же
  `--color-danger-text`/`warningRow` словарём, что уже используют
  ADR-0006 §4, ADR-0007 §4, ADR-0013 §3), не как пустая ячейка и не как
  `—`. Если при этом есть `received_price` (поставщик сначала дал цену,
  потом отказался, ADR-0013 §2 явно допускает оба факта одновременно) —
  цена показывается зачёркнутой рядом с меткой "Отказался", не
  скрывается.

Ноль (`price = 0` или `confirmed_price = 0`) отображается как обычное
число `$0.00` — реальное, хоть и маловероятное на практике значение, не
переинтерпретируется в "нет данных". Это то же разделение "нет
значения" (`NULL`) vs "значение ноль", уже проведённое для
`availability` (ADR-0005) и `confirmed_price` (ADR-0007 §1) — матрица не
вводит новое правило, а показывает существующее различие визуально.

**Раздел "Ответы поставщиков", ячейка при нескольких `Order` одному
поставщику, содержащих один и тот же материал** (дозаказ, ADR-0007 §2
явно допускает несколько `Order` на поставщика за проект): нужен
точный, реализуемый критерий выбора одной строки — `OrderItem` не имеет
собственного timestamp (модель `OrderItem(UUIDPKMixin, Base)`,
`backend/app/models/order.py:37`, использует только `UUIDPKMixin` — id,
без `TimestampMixin`/`created_at`; `id` — UUID v4, нехронологичен, тот
же факт, по которому ADR-0015 §1 уже отклонил `id` как критерий выбора
между дублирующимися draft-ордерами).

Критерий: **`Order.created_at` того `Order`, где найден `OrderItem` —
берётся строка из **последнего по `Order.created_at`** `Order` этого
поставщика, содержащего материал**, без сравнения по `OrderItem`
(которого нет). Это отличается от вопроса, который ADR-0015 §1 решал
для draft-ордеров: там `created_at`/`id` были отклонены как критерий
**выбора, какой из нескольких draft-ордеров правильный получатель новой
позиции** (решение с последствиями — куда записать данные), что
ADR-0015 обоснованно передал человеку через `409`. Здесь вопрос другой
и более слабый — **чисто отображение уже существующих строк**,
последствий записи нет: если позже окажется, что выбранная по
`Order.created_at` строка не самая релевантная, ячейка просто покажет
не то число временно, до похода на `OrderDetailPage` за точной картиной
(та же степень риска, что уже принята для любого производного,
непер­систентного значения в этом проекте — п.4 ниже, `is_cheapest`).
`Order.created_at` как критерий для *этого конкретного* случая
приемлем именно потому, что ошибка здесь не имеет тех последствий,
из-за которых ADR-0015 отклонил его для записи.

**Явное ограничение, а не тихое допущение:** если у поставщика
несколько `Order`, и материал встречается в **более раннем** по
`created_at` `Order`, а не в последнем — матрица покажет строку из
последнего `Order`, даже если в нём этого материала на самом деле нет
(тогда ячейка для этого поставщика в этой строке обязана трактоваться
как "не отправляли", п.3, если ни в одном `Order` материала нет; если
он есть в нескольких `Order` одновременно — который из них "последний"
однозначно определяется по `Order.created_at`, не оценочно). Чтобы не
оставлять это неточным: правило одно и то же для всех строк — **среди
всех `Order` поставщика в проекте, содержащих `OrderItem` с этим
`material_id`, берётся `Order` с максимальным `created_at`; из него —
единственный `OrderItem` этого материала** (дубль материала внутри
одного `Order` уже исключён ADR-0015 §1 п.3, не может встретиться).
Обоснование выбора "матрица отвечает на вопрос "что сейчас актуально",
не строит историю по нескольким ордерам — история остаётся предметом
`OrderDetailPage` каждого конкретного `Order`, не этого экрана.

### 4. Подсветка минимума — по цене, независимо от availability

Раздел "План": подсвечивается ячейка с минимальной `Price.price` в
строке — **чисто по цене**, независимо от `availability`. Раздел
"Ответы поставщиков": подсвечивается ячейка с минимальной эффективной
ценой (п.3 — `confirmed`/`received`/`quoted` по приоритету) среди
неотклонённых (`declined_at IS NULL`) ответов в строке.

Обоснование — прямое продолжение уже установленной в проекте философии
видимого риска (ADR-0006 §2, ADR-0014 §1): та же логика, что уже
применена к списку кандидатов на замену ("показывать всех, включая
недостаточный availability, с явным визуальным предупреждением, не
скрывать") здесь означает "подсвечивать дешевизну как дешевизну,
показывать риск наличия отдельным, дополнительным сигналом на той же
ячейке" — не смешивать два факта в одно решение "достойна ли эта цена
подсветки". Смешивание привело бы к скрытой эвристике: подсвеченная
ячейка иногда значила бы "дешевле", иногда "дешевле и точно есть в
наличии" — пользователь не мог бы доверять подсветке одинаково в обеих
ситуациях без похода в тултип каждый раз, что обесценивает саму идею
беглого визуального сравнения (то, ради чего сотрудник просил этот
экран).

Вместо смешивания: подсвеченная (минимальная по цене) ячейка
дополнительно получает **тонкий отдельный индикатор риска**, если
`availability` явно задан и меньше `ProjectItem.quantity` этого
материала — тот же `⚠`-язык и текст, что уже использует ADR-0014 §1
("⚠ у поставщика доступно {availability} {unit}, требуется
{quantity}"), не новый визуальный паттерн. `availability IS NULL` не
помечается (симметрично ADR-0005 — "не проверялось" ≠ "недостаточно").

**Отклонено: не подсвечивать как минимум цену у поставщика с явно
недостаточным availability (подсвечивать следующую по цене
"реально доступную").** Отклонено по причине выше — превратило бы
подсветку в решение, принятое системой за пользователя, о том, что
"реально доступно", без контекста, которым система не обладает (ADR-0006
§2 explicitly формулирует этот же аргумент для ручного override).
Отдельный видимый ⚠-маркер даёт пользователю оба факта (дешевизна и
риск) без скрытия ни одного.

### 5. Текущий выбор по плану — не в MVP матрицы

Матрица **не** показывает, какого поставщика для материала сейчас
выбрал солвер/override (`AllocationLine.supplier_id`) — ни отдельной
колонкой, ни рамкой/меткой на ячейке текущего выбора.

Обоснование: это самостоятельный третий факт поверх уже двух
существующих разделов (не "какая цена лучшая", а "что уже решено"), а
матрица уже отвечает на вопрос "с кем сравнить" — вопрос "что выбрано
сейчас" уже полностью закрыт `AllocationResultPage`, который явно
показывает текущее назначение по каждой строке (селект, бейдж "изменено
вручную", ADR-0006 §3). Добавление третьего измерения в первую версию
этого экрана — то усложнение, от которого явно предостерегает сама
задача ("реши, нужно ли это для MVP, или излишне усложняет"); нет
сформулированного сценария использования ("я хочу видеть текущий выбор
именно здесь, а не на экране результата"), только гипотетическое
удобство. Тот же инстинкт, что уже отложил построчное
план↔факт-сопоставление в ADR-0008 §3 до появления практики: если после
использования матрицы окажется, что сотрудник постоянно уходит на
`AllocationResultPage` только чтобы сверить "а что выбрано", это сигнал
для отдельного, целенаправленного расширения — не для того, чтобы
гадать сейчас.

### 6. Действие из матрицы — read-only для MVP

Матрица не позволяет инициировать перенос материала на другого
поставщика напрямую из ячейки. Read-only отчётный экран; перенос
остаётся на `AllocationResultPage` (ручной override, ADR-0006) и
`OrderDetailPage` (find-replacement для отклонённых позиций, ADR-0014).

Обоснование — тот же принцип "не усложнять раньше времени", что уже
применён в ADR-0003 (не вводить статус, для которого нет данных о
частоте использования) и ADR-0008 §3 (не проектировать матчинг вслепую):
переиспользование `PATCH .../lines/{line_id}` из ячейки матрицы означало
бы решить в этом ADR ещё и вопрос UX самого действия (какая
`AllocationLine` переопределяется — тот же поиск "последний
`AllocationRun` этого проекта по `material_id`", что ADR-0014 §2 уже
решил для другого триггера, но здесь без контекста конкретной
declined-строки, из которой ясно, что и зачем меняется). Задача явно
предлагает read-only, если нет веской причины иначе — причины нет:
матрица нужна в первую очередь для **анализа перед решением** ("к кому
идти по этому материалу"), а не как ещё один путь совершить уже
существующее действие. Если на практике перенос прямо из матрицы
окажется частым запросом (сотрудник постоянно уходит с матрицы на
`AllocationResultPage` ради одного клика) — отдельный ADR, переиспользующий
существующий `PATCH`, с реальным сценарием использования как основанием.

### 7. UI и роут — новый экран, отдельный роут

Новый роут `/projects/:id/comparison`, отдельная страница (по образцу
`PurchaseRecordsPage` на `/projects/:id/purchases`), с явной ссылкой из
`ProjectDetailPage` (в `.sectionHeader`, тем же паттерном, что уже
ведёт на "Фактическая закупка »", `frontend/src/routes/
ProjectDetailPage.tsx:186-188`).

Обоснование выбора отдельного роута, а не вкладки/секции внутри
`ProjectDetailPage`:

- Матрица (все материалы × все поставщики) — по объёму данных крупная
  таблица, потенциально с прокруткой в обе стороны при большом BOM
  (`docs/known-issues.md` уже фиксирует прецедент "не оптимизировать
  раньше времени", но крупная таблица неудобна встроенной в страницу,
  где уже есть секции "Ордера" и "Спецификация материалов" —
  `ProjectDetailPage.tsx:186-226` — вставка ещё одной широкой таблицы
  между ними ухудшила бы читаемость обеих существующих секций).
- Каждый существующий экран второго уровня (`allocation`, `purchases`)
  уже отдельный роут при таком же основании ("отдельный, часто
  используемый разрез анализа проекта, не жалко отдельного URL") — не
  создаётся исключения из уже установленного паттерна навигации
  проекта.
- Отдельный URL даёт прямую ссылку/bookmark на конкретный проект +
  сравнение — полезно, раз сотрудник описывает этот экран как основной
  инструмент анализа (задача явно отмечает "часто используемый — не
  прячь его глубоко"): ссылка из `ProjectDetailPage` — не единственный
  путь входа, отдельный роут делает вход воспроизводимым (обновление
  страницы, шаринг ссылки на конкретный проект коллеге) без потери
  контекста, чего вкладка с клиентским state не гарантирует бесплатно
  (тот же класс риска, что уже подтолкнул ADR-0004 к персистентности
  автосохранения).

**Отклонено: вкладка/переключатель секций на `ProjectDetailPage`
(единый URL, скрытие остальных секций за табами).** Отклонено —
`ProjectDetailPage` сейчас построен как один прокручиваемый экран с
несколькими секциями видимыми одновременно (не табами), переход на
табы был бы отдельным, не запрошенным изменением структуры существующей
страницы ради одной новой фичи — расширение паттерна, а не следование
ему.

Размещение в навигации: ссылка "Сравнение цен »" рядом с существующей
"Фактическая закупка »" в `.sectionHeader` секции "Ордера" (или отдельным
`.sectionHeader` перед ней) — деталь реализации, не архитектурное
решение; важна доступность в 1 клик с главного экрана проекта, что уже
обеспечивается самим фактом отдельного роута со ссылкой, а не точное
место ссылки на странице.

## Альтернативы

Альтернативы для каждого под-вопроса перечислены инлайн в "Решение"
(1–7), по той же структуре, что уже принята в ADR-0006/0007/0008/0013/
0014 — обоснования специфичны к конкретному под-решению.

Альтернатива на уровне ADR целиком: **не строить отдельную матрицу,
вместо этого расширить `AllocationResultPage`, чтобы при наведении на
строку материала показывался popover со всеми ценами по нему (данные из
`GET /materials/{material_id}/prices`, уже существует, ADR-0014 §1).**
Отклонено — Excel-пример пользователя явно описывает **одновременный**
обзор всех материалов и всех поставщиков как единую таблицу для беглого
сканирования взглядом ("у кого что лучше"), не построчный
per-material lookup по требованию; popover требует по одному наведению
на материал, чтобы увидеть его строку сравнения — воспроизводит то же
неудобство ("не видно сразу всех"), которое и было исходной жалобой,
только с меньшим числом кликов, чем текущий способ (открыть
`OrderDetailPage` каждого поставщика), но не с нулевым.

## Последствия

- Новый read-only endpoint, например
  `GET /projects/{project_id}/price-comparison` — отдаёт оба раздела
  (п.1) одним ответом: `plan` (материал → список
  `{supplier_id, supplier_name, price, availability}` по всем
  поставщикам с активной ценой) и `supplier_responses` (материал →
  список `{supplier_id, supplier_name, quoted_price, received_price,
  confirmed_price, declined_at, decline_reason}`, только поставщики с
  хотя бы одним `Order`, содержащим материал; при нескольких `Order`
  одного поставщика с этим материалом — строка берётся из `Order` с
  максимальным `created_at`, точное правило см. п.3). Подсветка
  минимума (п.4) считается на
  backend и отдаётся как явный флаг на ячейке (`is_cheapest: bool`), не
  вычисляется на клиенте — CLAUDE.md принцип 4. Точная форма ответа
  (вложенная структура vs плоский список) — деталь реализации.
- Новый роут `/projects/:id/comparison`, новый компонент
  `PriceComparisonPage.tsx` (по образцу `PurchaseRecordsPage.tsx`) —
  требует дизайна в Claude Design (`docs/design/`) перед реализацией по
  правилу CLAUDE.md.
- `ProjectDetailPage.tsx` получает новую ссылку на этот роут (п.7,
  точное место — деталь реализации).
- `docs/ui-reference.md` получает новый раздел (следующий по номеру
  после §7 "Ордер поставщика — сверка цен") с поведением матрицы:
  состав ячейки в каждом из трёх состояний (п.3), правило подсветки и
  формат ⚠-предупреждения (п.4), пустое состояние раздела "Ответы
  поставщиков" при отсутствии `Order` (п.1).
- `docs/data-model.md` не меняется — этот ADR не вводит новых полей
  или таблиц, только новый способ читать существующие (`Price`,
  `OrderItem`, `ProjectItem`).
- Явно не в объёме, зафиксировано как возможные будущие расширения, не
  забытые: действие (перенос поставщика) прямо из матрицы (п.6);
  отображение текущего выбора плана в матрице (п.5); история по
  нескольким `Order` одного поставщика в одной ячейке, а не только
  последний (п.3).
- Реализация (endpoint, миграции — если понадобятся при уточнении
  формы ответа, новый экран, дизайн в Claude Design) — предмет отдельной
  задачи после вычитки этого ADR, backend и frontend раздельно, как и с
  предыдущими ADR в этом проекте.
