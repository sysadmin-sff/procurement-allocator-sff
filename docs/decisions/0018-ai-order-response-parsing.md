# ADR-0018: ИИ-распознавание ответа поставщика на Order (загрузка PDF/фото)

Статус: Предложено

## Контекст

Компания получает ответы поставщиков на запрос цен по конкретному `Order`
в разных форматах (PDF, фото счёта/переписки телефоном, текст письма).
Сейчас сотрудник вручную прогоняет документ через ChatGPT и переносит
результат построчно через существующий UI ADR-0007 §3 / ADR-0013 §3
(`PATCH /orders/{order_id}/items/{item_id}`, поля `received_price`/
`confirmed_price`/`declined`). Задача — встроить это распознавание в
систему: загрузка документа на странице `OrderDetailPage` → ИИ извлекает
позиции и цены → сопоставляет с уже известным закрытым списком `OrderItem`
этого `Order` → предпросмотр для подтверждения → запись `received_price`
(и предупреждения/предложения, см. ниже).

**Это не тот же класс задачи, что ingestion прайс-листов
(`docs/spec.md` §3).** Там — открытый набор материалов против всей БД:
любая строка прайса может оказаться совершенно новым материалом, matching
ищет среди потенциально тысяч `Material`. Здесь — закрытый набор: у
конкретного `Order` уже есть фиксированный список `OrderItem` (типично
10–30 позиций), и задача ИИ — сопоставить ответ поставщика с этим коротким
списком, не с всей базой. Это делает задачу структурно проще: меньше
контекста на вход, меньше пространства для ошибки, выше ожидаемая точность
matching при том же классе модели.

Соблюдает принцип 2 CLAUDE.md (LLM только на неструктурированном входе,
всегда с ревью человеком, ничего не пишется в боевые таблицы молча) и
принцип 4 (денежные операции только на backend).

Не в объёме этой задачи (см. постановку):
- Массовый импорт из текста письма без загрузки файла (прямая интеграция
  с почтой) — только ручная загрузка файла/фото на странице `Order`.
- Изменение ingestion pipeline прайс-листов (`docs/spec.md` §3) — другая,
  более крупная задача с открытым набором материалов.
- Связь `received_price`/`confirmed_price` ↔ `Price` в БД — уже явно
  отложено в ADR-0007 §5, этот ADR не меняет то решение.
- Полуавтоматический matching план↔факт для `PurchaseRecord` (ADR-0008
  §3, явно отложен там же) — "лишние" позиции этого ADR используют
  `PurchaseRecord` как приёмник (п.5), но не решают его собственный
  matching-вопрос.

## Решение

### 1. Модель, провайдер, расположение кода

Новый backend-модуль `backend/app/order_response_parser/` (по аналогии с
существующим разделением `backend/app/allocation/` — один модуль на один
пайплайн). Один вызов OpenAI API (аккаунт уже есть у компании) —
vision + structured outputs, реализует извлечение и matching в одном
проходе (обоснование — п.2).

**Модель для первой версии: GPT-5.6 Luna**, с явной оговоркой: выбор
предварительный, до эксплуатации подтверждается прогоном на 3–5 реальных
документов поставщиков компании (разный почерк, качество фото телефоном,
разные форматы — PDF со слоем текста, скан, фотография листа). Нельзя
гарантировать точность модели на этих форматах заранее, без реальных
образцов. Если точность на реальных документах окажется недостаточной —
следующий шаг эскалации: GPT-5.4 (полная, не mini/nano) для того же
промпта, прежде чем менять архитектуру пайплайна. **Альтернатива подешевле
для рассмотрения после проверки на реальных документах, не до неё:**
GPT-5.4 mini/nano — cost-efficient, но vision-точность на телефонных фото
и рукописных пометках ниже, рискованно фиксировать для MVP без сравнения
на реальных образцах компании. Конкретная модель — параметр конфигурации
(`OPENAI_ORDER_RESPONSE_MODEL`, env var), не хардкод в коде модуля: смена
модели по итогам проверки на реальных документах не требует правки кода.

**API-ключ.** Существующий паттерн секретов проекта (CLAUDE.md: `.env` не
трогать вручную) — ключ живёт только как backend env var
(`OPENAI_API_KEY`), читается сервером при вызове API, никогда не
передаётся на фронтенд ни в каком виде (ни в конфиге, ни в ответе
endpoint'а). Загрузка файла идёт через backend endpoint (п.7) — фронтенд
никогда не обращается к OpenAI API напрямую, что и обеспечивает
невозможность утечки ключа на клиент по построению (ключ физически не
попадает ни в один HTTP-ответ, который видит браузер).

### 2. Схема извлечения — один вызов, extraction + matching вместе

**Решение: один вызов модели, extraction и matching одновременно**, не
two-pass (сначала извлечь сырые строки отдельным вызовом, потом матчить
отдельным). Список `OrderItem` этого `Order` (`material_id`,
`canonical_name` материала, `quantity`, `quoted_price`) передаётся в
промпт как контекст вместе с документом; модель возвращает structured
output — список строк с полями:

```
{
  raw_description: string       // как написано в документе поставщика
  matched_order_item_id: uuid | null   // null = не сопоставлено ни с одной позицией заказа
  price: number
  quantity: number | null       // null = не указано в документе
  confidence: "high" | "medium" | "low"
  reasoning: string             // почему сопоставлено именно с этой позицией (или почему не сопоставлено)
}
```

**Обоснование, почему один вызов, а не two-pass.** Matching для этой
задачи не выигрывает от разделения на шаги так, как выигрывал matching
прайс-листов (`docs/spec.md` §3, где matching — отдельный шаг с
векторным поиском top-5 кандидатов из потенциально тысяч `Material`,
потому что пространство поиска большое). Здесь пространство поиска —
10–30 `OrderItem` этого заказа, помещается в один промпт целиком без
предварительной фильтрации. Модель, видящая одновременно "что написано в
документе" и "что мы заказывали", может использовать контекст обеих
сторон сразу (например, понять, что "84&quot; PREMIER SCREEN 18/14&quot;"
в документе — это тот же материал, что наша позиция "84 in. 18x14
Fiberglass Screen", хотя строки совпадают меньше чем по паре слов) —
разделение на два вызова заставило бы либо (а) первый проход сделать
"слепым" извлечением без контекста заказа, теряя именно ту информацию,
которая помогает разрешить неоднозначность, либо (б) дублировать список
`OrderItem` в оба вызова без выигрыша в точности, только с ростом
стоимости и задержки. Один вызов — меньше кода (нет промежуточного
хранения "сырых" строк между двумя запросами), меньше точек отказа,
дешевле (одна оплата за vision-обработку документа вместо двух).

**Отклонено: two-pass (extraction, затем отдельный matching-вызов).**
Рассматривался как более "чистая" декомпозиция по аналогии с
прайс-ingestion (`docs/spec.md` §3, где extraction и matching — разные
шаги). Отклонено, потому что там разделение оправдано размером
пространства поиска (нужен векторный поиск top-5 из всей БД перед тем,
как передать что-либо в LLM) — здесь этого шага физически нет, весь
список кандидатов и так помещается в контекст. Вводить два вызова без
структурной причины — сложность без выигрыша.

`confidence`/`reasoning` хранятся так же, как уже принято для
прайс-ingestion (`docs/spec.md` §3, "Важные нюансы") — тот же прецедент,
не персистентно в БД (это одноразовый проход, п.7), а в структуре ответа
endpoint'а для отображения на экране предпросмотра (п.3) и в логах
запроса (для отладки промпта), не в новой таблице.

### 3. Экран предпросмотра — три явно разделённые категории, без Claude Design

Экран не проходит через Claude Design, в отличие от правила CLAUDE.md
("новый экран — дизайн в Claude Design перед реализацией"), применённого
к предыдущим новым экранам этого домена (`OrderDetailPage` в ADR-0007,
экраны замены/матрицы сравнения в ADR-0012–0016). Обоснование: все
визуальные примитивы, из которых собран этот экран, уже установлены и
переиспользуются, ничего нового в словаре нет — inline-редактируемая
ячейка цены (ADR-0007 §3, ADR-0013 §3), ⚠-язык предупреждения
(`--color-danger-text`/`warningRow`, ADR-0006 §4, ADR-0007 §4, ADR-0013
§3), кнопка массового применения по аналогии с прайс-ревью
(`docs/spec.md` §3, "Применить"), точечное исключение строки — тот же
паттерн, что уже применяется на экранах ревью. Дизайн в Claude Design
оправдан, когда экран вводит новый визуальный язык; здесь — чистая
композиция уже принятых элементов в три блока, и весь фронтенд-слой
Order/Purchase всё равно ожидает более широкую переработку позже
(`docs/known-issues.md`), так что закладывать сейчас отдельный
Claude-Design-проход под компоновку, которая может измениться при этой
переработке, — работа, которую придётся переделывать. Реализация экрана
идёт от разметки существующих аналогичных экранов (`OrderDetailPage`,
`AllocationResultPage`) как эталона, без нового прохода через дизайн.

`POST /orders/{order_id}/parse-response` (multipart, файл PDF/изображение)
возвращает предпросмотр, **не пишет ничего в БД**. Три категории,
разделённые в UI (не единый список — три визуально разных блока/таблицы),
по аналогии с уже принятым в ADR-0007/ADR-0013 разделением "совпало
"/"предупреждение"/"нужно решение":

**(a) Совпало** — `matched_order_item_id` не `null`. Строка предпросмотра
показывает: наша позиция (`canonical_name`, `quoted_price`), предлагаемая
`received_price` из документа, в той же inline-редактируемой ячейке, что
уже используется для `received_price` (ADR-0013 §3) — сотрудник может
поправить значение прямо на экране предпросмотра до подтверждения, если
ИИ ошибся в распознавании цифры. Строки с `confidence: "low"` (и
`"medium"`, см. ниже) остаются в этой категории (не переносятся в
отдельную "неуверенную" категорию), но получают тот же визуальный
⚠-язык, что уже используется для `below_min_order`
(ADR-0006 §4) / `price_delta > 10%` (ADR-0007 §4) — предупреждение, не
сокрытие и не отдельная категория. Обоснование: низкая уверенность — это
свойство *конкретного сопоставления*, а не повод исключить строку из
"совпало"; ИИ уже сделала предположение, сотрудник видит его и решает,
доверять или поправить — то же рассуждение "предупреждение, не блокировка",
что уже применено к `below_min_order` и к расхождению `overridden_at`/
`ordered_at` (ADR-0007 п.2): система не обладает полным контекстом, чтобы
скрывать свою неуверенную догадку, но обязана явно её пометить.

**(b) Отсутствует в ответе** — `OrderItem` этого `Order`, для которого ни
одна строка документа не получила `matched_order_item_id`, равный его
`id`. **Явно только предупреждение, не автоматическая простановка
`declined_at`.** `declined_at` (ADR-0013 §2) — явный факт "поставщик
отказался", осознанно проставляемый сотрудником; отсутствие позиции в
распознанном документе — не то же самое (могли забыть упомянуть, страница
обрезана при фотографировании, позиция на второй странице, которую не
приложили). Категория (b) в UI даёт быстрый переход к существующему
элементу "Отметить как недоступно" (ADR-0013 §3) на этой строке — то есть
предлагает, но не выполняет действие. Ничего не пишется в БД для строк
этой категории при массовом подтверждении (п.4) — они не участвуют в нём
вообще, только в списке предупреждений.

**(c) Лишнее** — строка документа с `matched_order_item_id: null`
(модель не нашла соответствия ни одной нашей позиции — либо реально
внеплановая позиция, либо распознанное описание слишком отличается от
наших `canonical_name`, чтобы модель была уверена в привязке). Каждая
строка получает кнопку "Добавить" — по клику записывается как
`PurchaseRecord` (обоснование — п.5), не автоматически, требует
подтверждения по этой конкретной строке (не входит в массовое "Применить
все совпадения", п.4, потому что это не совпадение — это решение создать
новую запись).

### 4. Подтверждение — массовое, с точечными правками и исключением строк

Кнопка **"Применить все совпадения"** обрабатывает разом все строки
категории (a): для каждой — `PATCH .../items/{item_id}` с
`received_price` (через уже существующий `set_order_item_fields`,
ADR-0013 §3, без изменений в его сигнатуре — этот ADR не меняет тот
контракт, только добавляет ещё один источник вызова того же метода).
Перед нажатием сотрудник может:
- поправить `received_price` inline на любой строке (п.3a);
- снять галочку/исключить отдельную строку из массового применения (не
  отклонить материал — просто "не применять эту строку сейчас", строка
  остаётся видимой, но не отправляется в PATCH при нажатии кнопки).

Обоснование массового подтверждения, а не построчного: типичный объём
10–30 позиций на заказ (контекст задачи) делает 30 отдельных кликов
подтверждения избыточным трением — то же рассуждение, по которому
прайс-ingestion (`docs/spec.md` §3) уже даёт кнопку "Применить" на весь
набор апрувнутых строк разом, а не по одной. Точечная правка/исключение
сохраняет требование принципа 2 CLAUDE.md ("не пишется молча") — массовое
применение это не "автоматически без проверки", это "проверено и
подтверждено одним действием после того, как сотрудник просмотрел все
строки на экране предпросмотра".

Категория (b) не участвует в кнопке "Применить" (нет действия по
умолчанию — см. п.3b). Категория (c) подтверждается по одной строке
(п.3c) — не входит в общую кнопку, потому что "применить" для лишней
позиции означает решение завести новую запись, качественно другое
действие, чем заполнить уже существующее поле.

### 5. Архитектура "лишних" позиций — `PurchaseRecord`, не nullable `quoted_price`

**Решение: "лишняя" позиция (категория c) записывается как
`PurchaseRecord` (ADR-0008), не как `OrderItem` с nullable
`quoted_price`.**

Обоснование, подтверждающее выбор, а не предполагающее его:

- `OrderItem.quoted_price` — `NOT NULL` по ADR-0007 п.1 ровно потому, что
  `Order` — снимок того, что мы **отправили** поставщику (ADR-0007 §2,
  "снимок, не живая ссылка"): `quoted_price` физически не может
  существовать для позиции, которую мы не заказывали, потому что для неё
  нет числа, которое мы бы посчитали и отправили. Сделать поле nullable
  ради этого случая сохранило бы синтаксическую возможность добавить
  строку, семантика которой прямо противоречит инварианту "Order — то,
  что мы отправили" (ADR-0007 п.2): такая строка появилась бы в
  документе, который, по определению ADR-0007, представляет уже
  отправленный заказ, задним числом, для позиции, которая в этот заказ
  никогда не входила.
- `PurchaseRecord` (ADR-0008) уже спроектирован именно для этого случая —
  "купили не совсем по плану": `supplier_id` уже обязательное прямое
  поле записи (не выводится из `Order`, ADR-0008 п.1), `material_id`
  опционален (ADR-0008 п.1, ровно то же свойство, которое нужно здесь —
  "лишняя" позиция может не иметь известного `Material` вообще), а
  `raw_description` — уже обязательное свободнотекстовое поле, ровно то,
  что возвращает ИИ-извлечение (п.2) без попытки канонизации. Форма
  входных данных этого ADR (описание из документа поставщика, не
  привязанное ни к какому нашему `material_id`) — это буквально тот
  случай, для которого `PurchaseRecord.raw_description` спроектирован
  (ADR-0008 §1: "Никакой валидации против `Material`/
  `SupplierMaterialAlias` — по построению, это facts as reported").
- ADR-0008 п.1 уже явно отклонил альтернативу "поле на `OrderItem`" по
  причине, которая здесь применяется буквально: `OrderItem` привязан к
  одному `Order` с одним `supplier_id` на весь документ — "лишняя"
  позиция физически описывает то же самое несоответствие плана и факта,
  которое ADR-0008 уже решил.

Практически: кнопка "Добавить" на строке категории (c) вызывает
существующий `POST /projects/{project_id}/purchase-records` (ADR-0008
§5) с `supplier_id = Order.supplier_id` (известен из контекста —
загрузка происходит на странице конкретного `Order`, значит поставщик
уже известен, в отличие от общей формы ADR-0008, где `supplier_id`
выбирается вручную), `raw_description`, `quantity`, `unit_price = price`
из ответа ИИ, `material_id = null` (сотрудник может позже проставить
вручную на экране `/projects/:id/purchases`, как и любая другая запись
ADR-0008 — этот ADR не меняет то поведение). Этот ADR не вводит новый
endpoint для этого шага — переиспользует существующий, только источник
вызова другой (кнопка на экране предпросмотра `Order`, а не форма на
экране "Фактическая закупка").

**Отклонено: nullable `quoted_price` на `OrderItem`.** Отклонено по
причине выше — меняет уже принятый и явно защищённый (ADR-0007 п.1, п.2)
инвариант ради одного нового сценария, для которого уже существует
спроектированное решение без изменения ни одной существующей таблицы.

### 6. Ошибки и низкая уверенность

**Полный отказ распознавания** (нечитаемый документ, не тот файл,
пустой/пересвеченный скан, модель не смогла извлечь ни одной строки) —
понятная ошибка на экране (например: "Не удалось распознать документ.
Проверьте качество файла или введите цены вручную построчно."),
**не блокирует** пользователя — построчный ручной ввод через
`received_price`/`confirmed_price` (ADR-0007 §3, ADR-0013 §3) уже
существует и остаётся доступным как есть, независимо от результата этого
эндпоинта. `POST .../parse-response` в этом случае возвращает пустой или
частичный результат (например, распознал документ, но не смог сопоставить
ни одну строку) с понятным сообщением, не 500-ошибку — частичный успех
(нашли часть строк) не должен требовать повторной попытки распознать всё
целиком.

**Низкая уверенность конкретной строки** — уже покрыто в п.3a: остаётся в
категории "совпало" с визуальным предупреждением, не скрывается и не
выносится в отдельную категорию. `confidence: "low"`/`"medium"` — оба
получают ⚠-пометку (одинаковую, без разделения на два уровня
предупреждения в UI MVP — усложнение без явно запрошенного выигрыша,
`confidence` как таковой доступен в ответе endpoint'а на случай будущей
дифференциации, но экран не обязан различать "low" и "medium" визуально
по-разному в первой версии).

### 7. Хранение загруженного файла — не персистится (MVP)

Загруженный документ передаётся в OpenAI API в рамках одного вызова,
результат применяется через существующие `PATCH`/`POST` эндпоинты (п.4,
п.5), сам файл **не сохраняется** ни в БД, ни в файловом хранилище.
`POST /orders/{order_id}/parse-response` — одноразовый проход: принимает
multipart-файл, держит его только в памяти запроса на время вызова
OpenAI API, ничего не пишет на диск/в объектное хранилище.

Обоснование для MVP: сохранение самого документа (для истории "чем именно
ответил поставщик") требует файлового хранилища, которого в проекте пока
нет ни для одной другой сущности — `Order.file_ref`
(`docs/spec.md` §5) уже существует в схеме, но не используется даже для
исходящего документа заказа (ADR-0007 §6 явно оставляет его
неиспользуемым до отдельной задачи "настоящий PDF/DOCX-шаблон"). Вводить
файловое хранилище впервые ради входящего документа, когда оно ещё не
введено даже для исходящего, — расширение объёма за пределы того, что
нужно, чтобы кнопка загрузки заработала. Результат распознавания и так
попадает в БД в применимом виде — `received_price` на `OrderItem`,
`PurchaseRecord` для лишних строк — сам факт "что было в документе"
сохраняется через свои последствия (числа в БД), не как файл.

**Явно отложено на будущее, не забыто:** если аудит "чем именно ответил
поставщик" (не просто "какие числа мы из этого извлекли") окажется
реальной практической потребностью — отдельный ADR о файловом хранилище,
использующий уже существующее (пока неиспользуемое) поле
`Order.file_ref` как прецедент места для такой ссылки, либо аналогичное
новое поле. Не проектируется сейчас без подтверждённой потребности — то
же рассуждение "не проектировать вслепую", что уже применено в ADR-0007
§5 и ADR-0008 §3.

## Альтернативы

Альтернативы для каждого под-вопроса перечислены инлайн в "Решение"
(1–7), по той же структуре, что уже принята в ADR-0006/0007/0008/0013 —
обоснования специфичны к конкретному под-решению.

Единственная альтернатива на уровне ADR целиком: **не строить отдельный
ИИ-пайплайн для ответов на Order, а расширить прайс-ingestion
(`docs/spec.md` §3) так, чтобы он мог опционально принимать "документ
ответа поставщика" как ещё один тип входа.** Отклонено — прайс-ingestion
пишет в `Price` (боевую таблицу цен всех материалов), результат этого
пайплайна пишет в `received_price`/`PurchaseRecord` (данные одного
конкретного `Order`/`Project`) — разные целевые таблицы, разные
приёмники подтверждения, разное пространство matching (весь `Material`
против закрытого списка `OrderItem`, см. "Контекст"). Смешение в один
пайплайн с веткой по типу документа усложнило бы оба сценария ради
экономии одного модуля — тот же аргумент, по которому ADR-0007 §6 уже
разделил `OrderDetailPage` и `/orders/:id/print` на разные роуты ("они
обслуживают разных читателей... смешение усложнило бы оба сценария").

## Последствия

- Новый backend-модуль `backend/app/order_response_parser/` — клиент
  OpenAI API, промпт-шаблон (список `OrderItem` заказа + документ →
  structured output, п.2), без персистентной схемы под сам модуль (нет
  новой таблицы — результат применяется через существующие
  `set_order_item_fields`/`create_purchase_record`, п.4–5).
- Новый endpoint `POST /orders/{order_id}/parse-response` (multipart,
  файл PDF/изображение) — возвращает предпросмотр (три категории, п.3),
  ничего не пишет в БД сам по себе.
- Новый env var `OPENAI_API_KEY` (секрет, backend-only, не в
  `docs/`/репозитории — см. CLAUDE.md "Что не трогать без явного
  запроса") и `OPENAI_ORDER_RESPONSE_MODEL` (конфигурация модели,
  дефолт `gpt-5.6-luna`, пересматривается по итогам проверки на 3–5
  реальных документах компании перед первым релизом фичи).
- Существующие endpoints без изменений контракта: `PATCH
  /orders/{order_id}/items/{item_id}` (ADR-0007/0013) и `POST
  /projects/{project_id}/purchase-records` (ADR-0008) — этот ADR только
  добавляет вызовы из UI экрана предпросмотра, не меняет их сигнатуры.
- Новый экран/секция на `OrderDetailPage` — загрузка файла, три блока
  предпросмотра (совпало/отсутствует/лишнее), кнопка "Применить все
  совпадения" — **без прохода через Claude Design** (обоснование — §3):
  собирается из уже установленных визуальных примитивов
  (`docs/design/`, `OrderDetailPage`/`AllocationResultPage` как эталон
  разметки), не вводит новый визуальный язык.
- `docs/ui-reference.md` получает новый раздел с поведением экрана
  загрузки/предпросмотра: три категории, массовое применение с
  исключением строк, ⚠-язык для низкой уверенности, недоступность
  `declined_at` из этого потока (только предупреждение).
- `docs/glossary.md`: уточнить, что "ИИ-парсинг ответа поставщика на
  Order" (этот ADR) — отдельный пайплайн от "ИИ-парсинга прайс-листов"
  (`docs/spec.md` §3), несмотря на общего провайдера (OpenAI) и общий
  принцип "ревью перед записью" (CLAUDE.md принцип 2).
- Явно не в объёме, зафиксировано как будущее расширение, не забытое:
  хранение загруженного файла для аудита (п.7); интеграция с почтой для
  массового импорта без загрузки файла; связь `received_price` ↔ `Price`
  в БД (уже отложено в ADR-0007 §5).
- Реализация (backend-модуль, endpoint, миграции — если появятся при
  реализации, — оба фронтенд-компонента, без отдельного прохода через
  Claude Design) — предмет отдельной задачи после вычитки этого ADR,
  раздельно backend/frontend, как и было с предыдущими ADR в этом
  проекте.
