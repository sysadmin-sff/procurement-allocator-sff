# ADR-0019: ИИ-парсинг прайс-листов — извлечение и matching против всей базы материалов

Статус: Предложено

## Контекст

`docs/spec.md` §3 с самого начала проекта описывает пайплайн обновления БД
цен из PDF-прайсов поставщиков: извлечение строк → векторный поиск top-5
кандидатов среди `Material` → LLM-решение `{action: "match"|"new",
material_id?, confidence, reasoning}` → экран ревью → запись в `Price`.
Таблицы `PriceListImport`, `PriceListEntry` и `SupplierMaterialAlias`
присутствуют в модели данных с начальной миграции (`f78b06284148_initial_schema`)
и полностью соответствуют полям, описанным в spec.md §2 — но **backend
(сервисный слой, API, промпты) под этот пайплайн никогда не писался**.
Все три таблицы на проде сейчас пустые (`SupplierMaterialAlias` — совсем,
`PriceListImport`/`PriceListEntry` — не имеют кода, который бы их
заполнял). **Эта ADR — первая реализация кода поверх уже существующей
схемы**, не проектирование новой схемы с нуля; там, где ниже упоминается
запись/чтение `PriceListEntry.action` или `PriceListImport.status`,
это относится к первому появлению читающего/пишущего эти поля кода.

**Это не тот же класс задачи, что ADR-0018 (ИИ-распознавание ответа
поставщика на `Order`).** Там — закрытый список из 10–30 `OrderItem`
конкретного заказа, помещающийся целиком в один промпт вместе с
документом, поэтому extraction и matching там сделаны в одном вызове.
Здесь — открытый набор: любая строка прайса может оказаться материалом,
которого ещё нет в базе (сотни позиций, растёт), весь каталог не
помещается в контекст одного вызова вместе с документом. Поэтому здесь
matching обязан быть отдельным шагом с предварительной фильтрацией
кандидатов через векторный поиск — структурно другая задача, не
переиспользование пайплайна ADR-0018 (обоснование — п.3).

Соблюдает принцип 2 CLAUDE.md (LLM только на неструктурированном входе,
всегда с ревью человеком, ничего не пишется в боевые таблицы молча),
принцип 3 (уникальность материала — по `internal_sku`, не по строке) и
принцип 4 (денежные операции только на backend).

**Главный риск этой задачи, явно поднятый до начала проектирования:**
один и тот же реальный товар от двух поставщиков под разными названиями
не должен стать двумя `Material` — должен стать одним `Material` с двумя
`Price`. Это не побочное требование, это причина, по которой существует
`SupplierMaterialAlias` и векторный matching вообще. Решения ниже (п.2,
п.6) спроектированы с этим приоритетом, не как общий MVP-компромисс.

Не в объёме этой задачи (см. постановку):
- Автоматическое обновление уже одобренных `Price` без нового захода
  ревью ("прайс не менялся 3 месяца, считать устаревшим") — отдельная
  будущая задача.
- Мультивалютность — явно отложено, см. п.7.

## Решение

### 1. Векторная инфраструктура

**pgvector.** Новая Alembic-миграция: `CREATE EXTENSION IF NOT EXISTS vector`,
новая колонка `Material.embedding vector(1536)`, **nullable** — не у всех
строк есть эмбеддинг сразу после миграции.

**Модель эмбеддингов: `text-embedding-3-small`**, 1536 измерений,
$0.02 / 1M токенов (актуальная цена и размерность на лето 2026,
проверено, не по памяти — см. также OpenAI "New embedding models and API
updates"). Сознательно другая, более дешёвая модель, чем vision-модель
извлечения (`gpt-5.6-luna`/config, ADR-0018) — та же дисциплина выбора
"дешевейшая модель, справляющаяся с задачей", что уже применена к выбору
vision-модели в ADR-0018 п.1: эмбеддинги не требуют vision и не требуют
рассуждения, только векторное представление короткой строки. Конкретная
модель — env var (`OPENAI_EMBEDDING_MODEL`), не хардкод, по тому же
паттерну, что `OPENAI_ORDER_RESPONSE_MODEL` в ADR-0018.

**Входной текст для эмбеддинга**: `canonical_name` + сериализованные
`attributes` (буквально по формулировке spec.md §3: "embeddings по
canonical_name + attributes").

**Бэкафилл существующих ~291 материалов.** Одноразовый скрипт
`backend/app/scripts/backfill_material_embeddings.py`, того же
семейства, что уже существующие `import_real_data.py`/`seed.py`
(разовые операторские скрипты, не API endpoint) — выбирает все `Material`
с `embedding IS NULL`, вызывает embeddings API, записывает результат.
Запускается вручную один раз после того, как миграция `vector`-колонки
выкачена, покрывает и исходные ~291 из Excel-импорта, и любые материалы,
добавленные вручную через CRUD до этой ADR. Не API endpoint — это
операторская задача, не продуктовая фича, по аналогии с тем, как
`import_real_data.py`/`seed.py` уже не имеют HTTP-обёртки.

**`POST /materials` — эмбеддинг синхронно при создании, с graceful
degradation при сбое.** Чтобы база эмбеддингов не расходилась с реальным
списком материалов после первого бэкафилла, `create_material`
(`backend/app/api/material.py`) получает один дополнительный вызов
embeddings API внутри обработчика — тот же паттерн "внешний вызов внутри
существующего эндпоинта", что уже принят в ADR-0018 (загрузка файла на
`OrderDetailPage` тоже делает внешний вызов синхронно в обработчике).

**Явное решение про сбой вызова: если embeddings API недоступен/упал —
`POST /materials` НЕ падает.** Материал создаётся с `embedding = NULL`,
ошибка логируется, ответ 201 как обычно. Обоснование: `POST /materials` —
существующий ручной CRUD-эндпоинт (форма создания материала), не часть
ИИ-пайплайна этой ADR; превращать простое ручное действие в операцию,
зависящую от доступности стороннего API, было бы реальной регрессией
надёжности существующего функционала ради новой фичи — недопустимо по
тому же духу, что CLAUDE.md принцип 4 требует "backend — единственный
источник истины для денег/чисел", а не "backend может отказать в базовой
CRUD-операции из-за третьей стороны". Материалы с `embedding = NULL`
(будь то из-за сбоя здесь или до первого бэкафилла) — обнаруживаются и
закрываются повторным запуском `backfill_material_embeddings.py` (тот же
скрипт, идемпотентен: выбирает `WHERE embedding IS NULL`), не требуют
отдельного механизма. Векторный matching (п.3) при поиске top-5
кандидатов естественно исключает материалы с `embedding IS NULL` из
результатов — они просто не будут предложены как кандидат, пока не
получат эмбеддинг; это деградация полноты поиска, не ошибка.

**`PUT /materials/{id}` — re-embed при изменении текста.** Если payload
меняет `canonical_name` и/или `attributes` (поля, из которых строится
эмбеддинг, см. выше), обработчик обновления также вызывает embeddings API
заново с той же graceful degradation (сбой → `embedding` не обновляется
на новое значение, остаётся прежним, не сбрасывается в `NULL` — старый
эмбеддинг всё ещё релевантен для старого текста, если он не полностью
атомарно синхронен с новым, это лучше, чем терять его вовсе). Изменение
только `category`/`unit`/`internal_sku` не триггерит re-embed — эти поля
не входят во входной текст эмбеддинга.

### 2. `SupplierMaterialAlias` — первая реализация: когда пишется

**Пишется при одобрении пользователем `match`-строки на экране ревью,
на любом уровне confidence, не только "идеальном" совпадении.**
Обоснование: одобрение пользователем — это и есть проверка качества
(CLAUDE.md принцип 2, "ревью перед записью"); ИИ уже сделала
предположение с каким-то confidence, сотрудник его увидел и подтвердил —
с этого момента "как этот поставщик называет этот материал" является
установленным фактом для будущих импортов, независимо от того, насколько
уверенно ИИ сама пришла к этому выводу. Если запись alias ограничить
только высоким confidence, повторный импорт того же прайса с той же
формулировкой всё равно пройдёт через LLM снова для строк
среднего/низкого confidence — теряется именно та гарантия консистентности
повторных импортов, ради которой alias-таблица существует.

**Точный-match короткий путь.** Перед векторным поиском для каждой строки
прайса — проверка `(supplier_id, supplier_raw_name)` на точное строковое
совпадение в `SupplierMaterialAlias`. При совпадении: пропустить
эмбеддинг-поиск и LLM-вызов целиком, создать `PriceListEntry` сразу с
`action="match"`, `matched_material_id` из alias, `confidence=1.0`,
`reasoning="known alias"`. **Строка всё равно проходит через экран
ревью** (CLAUDE.md принцип 2 — ничего не пишется в `Price` в обход
ревью, даже при 100%-совпадении с уже известным alias) — экономия здесь
только в стоимости и задержке (не тратим LLM-вызов на то, что уже
надёжно известно), не в пропуске человеческого подтверждения.

### 3. Извлечение — отдельный шаг от matching

**Подтверждено и обосновано явно** (в отличие от ADR-0018, где extraction
+ matching — один вызов): здесь разделение обязательно, не выбор стиля.
Причина — структурная, не эстетическая: у ADR-0018 весь список кандидатов
(10–30 `OrderItem` одного `Order`) физически помещается в тот же промпт,
что и документ, поэтому объединение вызовов давало выигрыш (модель видит
обе стороны сразу, meньше вызовов). Здесь кандидатов — весь `Material`
(сотни, растёт), объединить с документом в одном промпте невозможно без
предварительной фильтрации. Поэтому:

**Шаг 1 — извлечение.** Тот же принцип vision + structured outputs, что
уже реализован в `backend/app/order_response_parser/` (ADR-0018 п.1) —
новый модуль `backend/app/price_ingestion/` по аналогии со структурой
`order_response_parser/` (`client.py`/`service.py`). Выход — список сырых
строк без попытки матчинга:

```
{
  raw_name: string
  raw_sku: string | null
  price: number
  currency: string
  availability: int | null
  min_order_qty: int | null
}
```

Модель — тот же config-driven паттерн (`OPENAI_PRICE_INGESTION_MODEL`,
дефолт равен текущей vision-модели ADR-0018, `gpt-5.6-luna`, с той же
оговоркой: подтверждается прогоном на реальных прайс-листах компании
перед эксплуатацией, эскалация на GPT-5.4 при недостаточной точности —
тот же план, что ADR-0018 п.1).

**Шаг 2 — matching, отдельный LLM-вызов на строку (или батч строк).**
Для каждой сырой строки (после проверки alias-короткого-пути, п.2):
векторный поиск top-5 `Material` по косинусному расстоянию `embedding`
(`pgvector`, оператор `<=>`), затем LLM получает сырую строку + top-5
кандидатов с их `canonical_name`/`category`/`unit`/`attributes` →
structured output `{action: "match"|"new", material_id?, confidence,
reasoning, suggested_internal_sku?}` (последнее поле — п.4). Это
буквально пайплайн spec.md §3, реализуемый впервые.

### 4. Экран ревью

Переиспользует визуальный язык, уже установленный ADR-0018 (bulk-apply с
точечным исключением строк, ⚠-язык предупреждения, inline-редактируемые
поля), не оригинальную diff-таблицу из spec.md §3 — тот же паттерн уже
стал прецедентом в этом кодовой базе после ADR-0018.

Сортировка по возрастанию confidence (низкая уверенность — наверх, как
в исходной spec.md §3). **Массовое одобрение по порогу confidence
(>95%) — НЕ в MVP.** spec.md §7 явно резервирует "автоаппрув строк прайса
с высоким confidence" как "осознанно не в MVP, заложить в архитектуру,
не переписывать потом" — эта ADR это не переопределяет. MVP-механизм:
пользователь отмечает чекбоксы (по умолчанию все включены, как в
ADR-0018 §4) и жмёт "Применить выбранные" — массовое применение
*просмотренного и подтверждённого* набора, не автоматическое применение
по порогу.

**`action="new"` — `internal_sku`.** Механического правила генерации SKU
из исходного Excel-импорта не существует (тот импорт читал `internal_sku`
готовым из исходного CSV, не вычислял). Решение: LLM-вызов шага 2
дополнительно предлагает черновой `internal_sku` (`suggested_internal_sku`
в structured output, п.3) — тем же вызовом, что принимает решение
match/new, без дополнительного запроса. На экране ревью это поле
предзаполнено предложенным значением, но **всегда редактируемо
пользователем** до одобрения — `POST /materials` уже требует
`internal_sku` как обязательную строку с уникальностью на уровне БД
(409 при конфликте), это не меняется; предложение ИИ — только черновик,
удобство, не источник истины.

**Защита от дублей внутри одного импорта — явное предупреждение, не
только визуальная группировка.** Учитывая, что предотвращение дублей —
главный риск этой задачи (см. "Контекст"), MVP-решение усилено против
изначально предложенного варианта "просто группировка": после шага 2
(до отображения экрана ревью) для всех строк с `action="new"` в рамках
одного импорта считается попарное косинусное расстояние их эмбеддингов
(эмбеддинг `raw_name` каждой `new`-строки — уже посчитан на шаге 2 для
векторного поиска кандидатов, переиспользуется, не новый вызов). Пары
ниже порога расстояния (тот же порог, что используется для отсечения
top-5 кандидатов, чтобы не вводить второй независимый порог без
обоснования) получают:
- визуальную группировку — такие `new`-строки размещаются рядом друг с
  другом в списке категории "новое" (не по алфавиту/порядку из
  документа);
- явный ⚠-бейдж на обеих строках (тот же визуальный язык, что уже
  использует `below_min_order`/расхождение цены, ADR-0006 §4/ADR-0007
  §4/ADR-0013 §3) с текстом вида "похоже на другую новую позицию ниже"
  и коротким reasoning (например, расстояние).

Ничего не блокируется — пользователь может одобрить обе как разные
материалы, если они действительно разные (например, два похожих, но не
идентичных SKU одного типа экрана) — предупреждение, не запрет, тот же
принцип "система не обладает полным контекстом, чтобы решать за
человека", что уже применён в ADR-0018 §3(a).

### 5. Запись после одобрения — одна транзакция на строку

**`action="match"`**: закрыть текущую активную `Price` для пары
(`material_id`, `supplier_id`), если была (`valid_to = сегодня`),
создать новую `Price` с `source_import_id` — тот же паттерн
версионирования, что уже реализован в `PUT /prices/{id}`
(`backend/app/api/price.py`). Upsert `SupplierMaterialAlias` (п.2) —
если запись `(supplier_id, supplier_raw_name)` уже существует
(alias-короткий-путь), не дублировать; если нет — создать.

**`action="new"`**: создать `Material` (`internal_sku` из
пользовательского ввода на экране ревью, п.4; `canonical_name` из
`raw_name` или ручной правки; эмбеддинг — синхронно, п.1, с тем же
graceful degradation при сбое) + `SupplierMaterialAlias` +
`Price` — все три в одной транзакции на одобренную строку. Откат при
сбое любого из трёх — не оставлять частично созданный `Material` без
alias/цены.

Обе ветки обновляют `PriceListEntry.action`/`confidence`/`reasoning`
(первая запись кода, читающего/пишущего эти поля — п.1 "Контекст") и, по
завершении применения всех выбранных строк импорта, `PriceListImport.status`
(`pending_review` → `approved`, либо оставить `pending_review`, если
часть строк ещё не применена — статус переходит в `approved` только
когда не осталось неприменённых `match`/`new` строк без явного решения
пользователя "не применять сейчас", по аналогии с тем, как ADR-0018 §3(b)
не проставляет действие по умолчанию за пользователя).

### 6. Валюта

`Supplier.currency` существует в схеме, нигде не используется в расчётах
(известное упрощение, зафиксированное с начала проекта). Фактические
прайс-листы поставщиков компании — все в USD, подтверждено по факту
исходного Excel-импорта (`import_real_data.py` хардкодит
`currency="USD"` при создании `Price`, без чтения значения из
исходных данных). Для MVP этой ADR: мультивалютность не решается,
явно подтверждается как отложенный вопрос — уже открытый в исходной
`docs/spec.md` §8, вопрос 3, эта ADR его не закрывает и не должна.

## Альтернативы

Альтернативы для каждого под-решения перечислены инлайн в "Решение"
(1–6), по структуре, уже принятой в ADR-0006/0007/0008/0013/0018.

Единственная альтернатива на уровне ADR целиком: **расширить пайплайн
ADR-0018 (extraction+matching одним вызовом) на этот сценарий вместо
отдельного модуля.** Отклонено по причине, уже изложенной в "Контекст" и
п.3: структурно разные задачи (закрытый список ~10-30 против открытого
каталога в сотни позиций) требуют разного числа шагов — навязывание
одного вызова сюда потребовало бы либо урезать каталог кандидатов до
входа в контекст без векторной предфильтрации (потеря точности matching
именно там, где она нужнее всего — предотвращение дублей), либо
искусственно оставить два вызова под видом одного модуля, не выигрывая
ничего по сравнению с отдельным модулем. Тот же аргумент, что ADR-0018
уже использовал для отклонения two-pass в противоположную сторону —
здесь структура задачи требует ровно противоположного решения.

## Последствия

- Новая Alembic-миграция: `CREATE EXTENSION vector`, `Material.embedding
  vector(1536)` (nullable).
- Новый backend-модуль `backend/app/price_ingestion/` (client/service, по
  аналогии с `order_response_parser/`) — извлечение (шаг 1) и matching
  (шаг 2, векторный поиск + LLM-решение) как раздельные вызовы, впервые
  реализующие пайплайн spec.md §3.
- **Первая реализация кода поверх уже существующих с начальной миграции
  таблиц** `PriceListImport`, `PriceListEntry`, `SupplierMaterialAlias` —
  схема не меняется этой ADR, меняется наличие кода, который их
  читает/пишет.
- Новый одноразовый скрипт `backend/app/scripts/backfill_material_embeddings.py`
  (не endpoint) — идемпотентный, покрывает исходные ~291 материалов и
  любые материалы с `embedding IS NULL` на момент запуска.
- Изменения в существующих `POST /materials`/`PUT /materials/{id}`
  (`backend/app/api/material.py`) — синхронный вызов embeddings API
  внутри обработчика, **с graceful degradation**: сбой API не блокирует
  и не откатывает CRUD-операцию, оставляет/сохраняет `embedding = NULL`
  (или прежнее значение при `PUT`), что подхватывается повторным
  запуском бэкафилл-скрипта. Контракт эндпоинтов (сигнатуры, коды
  ответов) не меняется.
- Новые env vars: `OPENAI_EMBEDDING_MODEL` (дефолт `text-embedding-3-small`),
  `OPENAI_PRICE_INGESTION_MODEL` (дефолт равен текущей vision-модели
  ADR-0018, подтверждается на реальных документах компании перед
  эксплуатацией, тот же процесс, что ADR-0018 п.1).
- Новый endpoint(ы) для загрузки прайса и применения ревью (полный
  список путей/схем — предмет отдельной задачи реализации, не
  фиксируется здесь детально, по аналогии с тем, как ADR-0018
  зафиксировал только `POST /orders/{order_id}/parse-response` как
  единственный новый endpoint, оставив внутренние детали реализации).
- `docs/data-model.md` — добавить `Material.embedding` в описание
  таблицы и примечание про pgvector.
- `docs/ui-reference.md` — новый раздел: экран ревью прайс-листа
  (сортировка по confidence, точечное применение без авто-порога,
  предложенный `internal_sku` для новых материалов, явное предупреждение
  о похожих `new`-строках).
- `docs/glossary.md` — уточнить, что "ИИ-парсинг прайс-листов" (эта ADR)
  и "ИИ-парсинг ответа поставщика на Order" (ADR-0018) — разные
  пайплайны с разным пространством matching, несмотря на общий принцип
  "ревью перед записью" (CLAUDE.md принцип 2) и частично общего
  провайдера.
- Явно не в объёме, зафиксировано, не забыто: автообновление устаревших
  одобренных `Price` без нового ревью; мультивалютность (п.6, уже
  отложено spec.md §8 вопрос 3).
- Реализация (миграция, backend-модуль, эндпоинты, изменения
  `material.py`, бэкафилл-скрипт, фронтенд-экран ревью) — предмет
  отдельной задачи после вычитки этой ADR, с явным прогоном на реальных
  прайс-листах компании перед первым релизом (та же дисциплина, что
  ADR-0018 применяет к своей vision-модели).
