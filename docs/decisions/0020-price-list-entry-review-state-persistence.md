# ADR-0020: Персистенция `suggested_internal_sku`/`possible_duplicate_of` на `PriceListEntry`

Статус: Принято

## Контекст

ADR-0019 §5 сознательно оставил `PriceListEntryOut.suggested_internal_sku`
и `possible_duplicate_of` непостоянными: обе величины вычисляются на этапе
матчинга (`backend/app/price_ingestion/matching.py`,
`MatchedLine.decision.suggested_internal_sku` /
`MatchedLine.possible_duplicate_of`), но `PriceListEntry` их не хранит.
ADR-0019 явно зафиксировал схему `PriceListEntry` как замороженную для той
задачи ("Do not change PriceListEntry's schema") и реализовал перенос этих
двух полей в ответ `POST /suppliers/{id}/price-lists` через транзиентный
(не персистентный) атрибут `PriceListImport._matched_lines`, который живёт
только в памяти одного запроса (`backend/app/price_ingestion/service.py`,
`create_price_list_import`). `GET /price-list-imports/{id}` использует
отдельный рендерер (`_to_import_out`, `backend/app/api/price_ingestion.py`),
который этот атрибут никогда не читает — по построению, не по недосмотру:
на объекте, перечитанном из БД заново (`db.get(PriceListImport, id)`),
транзиентного атрибута просто нет.

Найденный на практике эффект этого решения: экран ревью прайс-листа
опирается на `GET` при каждой перезагрузке страницы (обновление F5,
возврат по прямой ссылке, повторный заход после того как вкладку закрыли
не досмотрев). После первого `GET` оба поля молча теряются — черновой SKU
для новых материалов и предупреждение "похоже на другую новую позицию
ниже" (ADR-0019 §4) исчезают из интерфейса без индикации, что они вообще
существовали. Это тот же класс проблемы, что уже решался в ADR-0004: там
клиентский черновик проекта (`ProjectBuilderPage`) не переживал `F5`,
потому что ввод жил только в React state, не в БД — и решение было
"перестать держать в состоянии, которое не переживает reload, то, что
нужно для продолжения работы позже". Здесь тот же принцип, но другая
техническая причина: данные *уже* доходят до backend (`PriceListEntry`
персистентен целиком), теряются только два конкретных вычисляемых поля,
которые ADR-0019 сознательно не стал сохранять — так что здесь не "чинили
клиентское состояние", а "явно снимаем ограничение предыдущего ADR", что и
требует отдельного ADR, а не патча внутри уже принятого решения.

**Рассматривались два варианта устранения:**

**(а) Персистировать оба поля на `PriceListEntry`** — маленькая миграция,
`GET` и `POST` начинают отдавать одно и то же всегда, транзиентный
механизм `_matched_lines`/`_to_import_out_with_matches` больше не нужен.

**(б) Пересчитывать `possible_duplicate_of` на каждый `GET` заново.**
Проверено на предмет источника эмбеддинга: `Material.embedding`
(`backend/app/models/material.py`) — это эмбеддинг уже сматченных
материалов, не эмбеддинг сырой строки поставщика (`raw_name`). Эмбеддинг
для `raw_name` вычисляется в `matching.py` через `embed_text(...)` только
в момент самого матчинга и существует лишь как `MatchedLine.embedding` в
памяти этого запроса — нигде не персистируется, `PriceListEntry` не имеет
колонки под вектор вообще. Строки с `action="new"` по определению не
привязаны ни к какому `Material`, так что переиспользовать
`Material.embedding` для них нельзя даже теоретически. Следствие: вариант
(б) без миграции физически невозможен — единственные пути реализовать его
это либо (б1) повторный вызов embeddings API на `raw_name` каждой ещё не
решённой строки при каждом открытии `GET` (растущая стоимость и задержка
на число заходов на экран, не на число реальных строк прайса), либо (б2)
завести отдельную колонку-эмбеддинг на `PriceListEntry` и всё равно
персистировать — то есть тайно стать вариантом (а), но персистировать
сырой вектор вместо готового результата сравнения (дороже по месту в БД,
требует пересчёта расстояний при каждом `GET` вместо чтения готового
списка).

## Решение

**Выбран вариант (а).** Две новые nullable-колонки на `PriceListEntry`:

```python
suggested_internal_sku: Mapped[str | None] = mapped_column(String(100))
"""Черновой SKU от LLM для action="new" — см. ADR-0019 §4, ADR-0020.
NULL для action="match"/known-alias строк и для строк, где LLM не смог
предложить SKU."""

possible_duplicate_of: Mapped[list[str] | None] = mapped_column(JSON)
"""Список id (UUID как строки) других PriceListEntry этого же импорта,
которые матчинг счёл вероятным дублем — см. ADR-0019 §4, ADR-0020.
NULL/пустой список = дублей не найдено. JSON, не отдельная
many-to-many-таблица — тот же паттерн, что уже используют
Material.attributes и AllocationRun.orphaned_materials в этом проекте:
список коротко живёт с самим импортом, не участвует в join'ах или
собственных запросах, и не обязан быть нормализован ради целостности —
UUID здесь не полноценные FK-ссылки с каскадным поведением, а просто
"на что смотреть" для UI-подсказки."""
```

`suggested_internal_sku` — `String(100)`, тот же тип и длина, что
`Material.internal_sku` (`backend/app/models/material.py`) — черновик
хранит то же самое значение, которое пользователь либо примет, либо
поправит перед `POST .../apply`.

`possible_duplicate_of` — JSON-массив строк (сериализованные UUID), не
`ARRAY(UUID)`: JSON уже принятый в проекте паттерн для списков такого
рода (см. докстринг выше), и не требует диалект-специфичного типа
Postgres `ARRAY` там, где остальной проект последовательно использует
`JSON` для подобных полей.

**Запись — один раз, при создании строки.** `create_price_list_import`
(`backend/app/price_ingestion/service.py`) теперь пишет оба поля
напрямую в `PriceListEntry` при создании, из уже вычисленного
`MatchedLine`:

```python
entry = PriceListEntry(
    ...,
    suggested_internal_sku=line.decision.suggested_internal_sku,
    possible_duplicate_of=(
        [str(entries[i].id) for i in line.possible_duplicate_of]
        if line.possible_duplicate_of else None
    ),
)
```

Индексы батча (`MatchedLine.possible_duplicate_of: list[int]`) переводятся
в реальные UUID персистентных `PriceListEntry` **на этом же шаге, один
раз** — та же трансляция индекс→UUID, что раньше делал `_to_import_out_with_matches`
на каждый upload-ответ, просто теперь она происходит один раз при записи,
а не при каждом рендере. Транзиентный атрибут `_matched_lines`
(`PriceListImport._matched_lines`) и специальный рендерер
`_to_import_out_with_matches` (`backend/app/api/price_ingestion.py`)
удаляются — обе функции `_to_import_out` (единственная теперь) читают эти
два поля прямо из `PriceListEntry`, как и все остальные поля схемы.

**Ничего не пересчитывается на `PUT`/`PATCH` строки.** Оба поля пишутся
один раз, при создании импорта, и остаются неизменными до тех пор, пока
строка существует — они описывают состояние на момент ИИ-анализа, не
текущее состояние вопроса "остаются ли эти строки похожими". Если
пользователь применит одну из двух похожих строк как `action="new"`,
`possible_duplicate_of` у второй строки не обновляется и не очищается —
предупреждение по-прежнему корректно ("на момент анализа эти две строки
были похожи"), решение по нему пользователь уже принял или ещё примет,
глядя на актуальный `action` соседней записи через отдельное поле, не
через ретроактивную мутацию этого списка.

## Альтернативы

**(б) Пересчёт на каждый `GET`** — отклонено, обоснование выше: не
существует версии этого варианта дешевле или чище, чем (а), поскольку
исходный вектор для сравнения нигде не хранится и его негде взять без
либо нового вызова API, либо новой персистентной колонки под сам вектор.

**Отдельная many-to-many таблица для `possible_duplicate_of`** (например,
`PriceListEntryDuplicate(entry_id, duplicate_of_id)`) вместо JSON-колонки.
Отклонено пользователем в пользу JSON — список никогда не участвует в
собственных запросах или join'ах (это чисто UI-подсказка на экране
ревью, ADR-0019 §4), формальная реляционная целостность (FK с каскадным
удалением) не даёт здесь выигрыша, который оправдал бы лишнюю таблицу и
миграцию, и расходится с уже принятым в проекте паттерном для похожих по
природе списков (`Material.attributes`, `AllocationRun.orphaned_materials`
— оба JSON).

**Патч внутри самого ADR-0019** вместо нового ADR. Отклонено — ADR-0019
явно зафиксировал заморозку схемы `PriceListEntry` как условие своего
решения ("Global Constraints"); отменять это условие тем же документом,
который его установил, стирает историю решения. Новый ADR делает видимым
факт "предыдущее ограничение снято", а не переписывает прошлое так, будто
ограничения никогда не было.

## Последствия

- Новая Alembic-миграция: `price_list_entries.suggested_internal_sku
  VARCHAR(100) NULL`, `price_list_entries.possible_duplicate_of JSON
  NULL`. Обратной засыпки не требует — существующие (пустые на проде,
  см. ADR-0019 "Контекст") строки `PriceListEntry` получают `NULL` по
  умолчанию, это корректное состояние ("данных о предположении ИИ для этой
  строки больше нет, потому что её создал более старый код") и не
  специальный случай в логике чтения.
- `PriceListEntry` перестаёт быть "замороженной" в смысле ADR-0019 —
  зафиксировано этим ADR явно, не молчаливым дрейфом. Дальнейшие
  изменения этой таблицы вне объёма этого ADR по-прежнему требуют
  своего рассмотрения на общих основаниях, не автоматически "раз один раз
  разморозили — то можно всё".
- `backend/app/models/price_list.py` — две новые колонки на
  `PriceListEntry`.
- `backend/app/price_ingestion/service.py` — `create_price_list_import`
  пишет оба поля при создании строки; `PriceListImport._matched_lines`
  удалено целиком (больше не нужно ничего протаскивать через объект между
  созданием и рендером ответа).
- `backend/app/api/price_ingestion.py` — `_to_import_out_with_matches`
  удалена; единственный `_to_import_out` читает оба поля из
  `PriceListEntry` и используется и `POST`, и `GET` — `GET` и `POST`
  гарантированно отдают одинаковый набор полей для одной и той же строки
  с этого момента, не как отдельный факт для проверки в каждом будущем
  тесте, а как структурное свойство одного и того же кода рендера.
- `docs/known-issues.md` — запись ADR-0019 про "GET теряет
  suggested_internal_sku/possible_duplicate_of" закрывается (не
  удаляется из истории, помечается решённой этим ADR).
- `docs/data-model.md` — обе новые колонки добавляются в описание
  `PriceListEntry`.
- Тесты: `GET /price-list-imports/{id}` после `POST` должен возвращать то
  же самое значение обоих полей, что и сам `POST` — прямая проверка
  инварианта "GET и POST не расходятся", не только проверка, что поле
  где-то заполнено. Старый тест на upload-response
  (`test_upload_response_includes_suggested_sku_and_duplicate_flags`)
  остаётся в силе без изменений — он проверяет форму ответа, которая не
  меняется этим ADR, только источник данных под ней меняется с
  транзиентного атрибута на колонку.
