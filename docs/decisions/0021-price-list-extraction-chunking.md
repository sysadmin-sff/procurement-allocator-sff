# ADR-0021: Извлечение прайс-листа — разбивка документа на чанки по страницам

Статус: Предложено

## Контекст

`backend/app/price_ingestion/extraction.py` (ADR-0019 §3, шаг 1) делает
**один** вызов `client.responses.parse` на весь документ прайс-листа —
весь PDF передаётся в `input_file` целиком, модель должна извлечь все
строки одним structured-output ответом.

Реальное тестирование на 14-страничном прайс-листе одного из поставщиков
компании (~464 реальных позиций) выявило нестабильность этого подхода,
диагностированную конкретно, не как гипотеза:

- Иногда модель в reasoning решает не извлекать ничего — `lines: []`,
  `reasoning_tokens` высокий, `status="completed"` (не обрыв по лимиту
  токенов, не ошибка API — `extract_price_list_lines` в этом случае не
  бросает `PriceIngestionError`, возвращает пустой список как валидный
  результат).
- Иногда модель извлекает часть документа (наблюдалось 326 или 141 из
  ~464), формирует синтаксически валидный, корректно закрытый JSON
  (`_ExtractionResult`, схема не нарушена), но останавливается на
  середине документа — не технический обрыв (`status` всё ещё
  `"completed"`), а решение модели прекратить работу раньше, чем
  документ закончился.
- При "полном успехе" число стабильно и воспроизводимо — 464.

Смена модели (`OPENAI_PRICE_INGESTION_MODEL`: `gpt-5.6-luna` →
`gpt-5.4`) может снизить частоту таких случаев, но не устраняет причину:
один вызов на весь объём документа структурно хрупок для достаточно
большого документа независимо от того, какая модель его обрабатывает.
Выбор модели — отдельный, уже идущий вопрос тестирования, эта ADR его не
решает (см. "Не в объёме" ниже).

Эта ADR **не переоткрывает и не противоречит ADR-0019 §3** — то решение
разделило extraction (шаг 1) и matching (шаг 2) на отдельные вызовы по
структурной причине (открытый каталог кандидатов не помещается в один
промпт с документом). Эта задача меняет только внутреннее устройство
шага 1 — несколько вызовов extraction вместо одного на документ; шаг 2
(матчинг) не затрагивается, интерфейс между шагами не меняется:
`extract_price_list_lines` по-прежнему возвращает единый
`list[ExtractedPriceLine]` для всего документа, чанкинг — деталь
реализации внутри этой функции/модуля, невидимая для `matching.py`.

## Решение

### 1. Единица разбивки — фиксированное число страниц PDF на чанк

Механическая разбивка по страницам (например, 3–4 страницы на чанк),
не зависящая от содержимого документа — не попытка найти "естественные"
разделы (секции по категориям товара, повторяющиеся заголовки таблиц и
т.п.).

Обоснование: прайс-листы поставщиков — не документы с предсказуемой
структурой между разными поставщиками (разный формат, разное
форматирование таблиц, не все PDF имеют текстовый слой — часть уже
обрабатывается как скан/фото по `_SUPPORTED_CONTENT_TYPES`). Разбивка по
содержимому потребовала бы либо отдельного шага распознавания структуры
документа перед extraction (новый источник нестабильности того же рода,
который решаем), либо эвристик, специфичных под конкретного поставщика
(нарушает принцип MVP — не проектировать под один документ). Механическая
разбивка по числу страниц не требует понимания документа заранее, работает
одинаково для PDF и для будущих сканов, и — что важнее всего для причины
этой ADR — гарантированно держит объём каждого вызова маленьким
(3–4 страницы, не 14), что и является механизмом исправления: гипотеза
диагностики — модель "сдаётся" по мере роста объёма/числа reasoning-шагов
на большом документе, а не что конкретно 14 страниц является магическим
порогом.

Число страниц на чанк — конфигурируемая константа в
`price_ingestion/extraction.py` (не env var — это внутренний параметр
реализации, не операционная настройка вроде выбора модели), дефолт 3.

### 2. Объединение результатов чанков — конкатенация без дедупликации на этом этапе

Каждый чанк даёт свой `list[ExtractedPriceLine]` независимым вызовом
`extract_price_list_lines`-подобной функции на под-документ (страницы
чанка). Результат всего extraction — простая конкатенация списков всех
чанков по порядку, без попытки дедупликации внутри шага 1.

Дедупликация похожих `new`-строк уже существует в ADR-0019 §4 (попарное
косинусное расстояние эмбеддингов `raw_name` для строк с `action="new"`,
визуальная группировка + ⚠-бейдж на экране ревью) и работает на уровне
всего импорта — после шага 2 (matching), не после шага 1. Этого
достаточно и для строк, возникших из-за границы чанков: с точки зрения
ADR-0019 §4 не существует разницы между "два разных чанка случайно дали
похожие строки" и "два поставщика в одном прайсе назвали товар почти
одинаково" — оба случая покрываются одним и тем же механизмом, отдельная
логика на границе чанков не нужна.

### 3. Строка таблицы, разрезанная между чанками — перекрытие в 1 страницу

Известный риск MVP-решения: если строка таблицы физически разорвана
между двумя страницами (редко, но возможно у прайс-листов с построчной
версткой на границе страницы) и эти страницы попадают в разные чанки —
extraction на каждом чанке видит только половину строки и либо
пропускает её, либо извлекает некорректно (одна из половин).

Решение для MVP: соседние чанки перекрываются на 1 страницу — последняя
страница чанка N также включается первой страницей чанка N+1. Это
снимает разрез ровно на границе чанка (строка целиком видна хотя бы в
одном из двух чанков, обычно в обоих), ценой контролируемого дублирования
той страницы — вся страница извлекается дважды, что означает дублирование
*всех* строк на ней, не только разорванной. Дублирование ловится тем же
механизмом, что и в п.2 — ADR-0019 §4 дедупликация для `new`-строк, и
matching-шагом (ADR-0019 §3 шаг 2) для строк, распознаваемых как `match`
существующему `Material` (два предложения matching на одну и ту же
существующую позицию — пользователь на экране ревью просто одобряет одно
и снимает/не одобряет другое; ADR-0019 §4 не блокирует, только
предупреждает).

Явно фиксируется как известное ограничение MVP, не решается полным
устранением риска: если строка разорвана не на границе физической
страницы PDF, а внутри визуально одной страницы, разбитой рендерером
не так, как ожидается (маловероятно, не наблюдалось в диагностике) — вне
объёма исправления, отдельная проблема extraction на уровне одной
страницы, не относится к чанкингу.

**Уточнение по дублированию `match`-строк (проверено против кода, не
предположение).** Перекрытие в 1 страницу означает, что дубли возникают
не только среди `action="new"` строк, но и среди `action="match"` —
две строки, распознанные как совпадение с одним и тем же `material_id`
(проверено: `backend/app/price_ingestion/matching.py`,
`_flag_duplicate_new_lines` фильтрует по `action == "new"` явно, п.155
"possible_duplicate_of применяется только к action=new"; для пары
`match`/`match` на один `material_id` сейчас нет ни группировки, ни
⚠-бейджа — пользователь увидит две визуально неотличимые строки в разных
местах списка, отсортированного по confidence (ADR-0019 §4), без
объяснения, что они дублируют друг друга).

Это не редкий случай, который можно оставить как есть: перекрытие
затрагивает ровно 1 страницу на каждой из границ чанков (при 3
страницах на чанк и ~6 чанках на 14-страничный документ — 5 границ,
т.е. 5 из 14 страниц дают дублирующийся извлечённый контент, это ~35%
документа, не единичный краевой случай). Большинство строк на этих
страницах — уже существующие в базе материалы (иначе они не были бы
`match`), то есть `match`-дубли от перекрытия ожидаются чаще, чем
`new`-дубли, для которых защита уже есть. Оставлять именно более частый
случай без подсказки, а более редкий — с ней, было бы непоследовательно.

**Решение: расширить `_flag_duplicate_new_lines` (переименовать в
`_flag_duplicate_lines`) симметричной проверкой для `action="match"` —
если две строки одного batch (`match_price_list_lines`) получили
`action="match"` на один и тот же `material_id`, обе получают
`possible_duplicate_of` друг на друга**, тем же полем и тем же
визуальным языком экрана ревью (группировка + ⚠-бейдж, ADR-0019 §4),
что уже используют `new`-дубли — не новый механизм, а снятие
существующего ограничения `action == "new"` в уже существующей функции.
Условие дублирования для `match` проще, чем для `new` (точное совпадение
`material_id`, не косинусное расстояние эмбеддингов — здесь не нужно
считать похожесть, `material_id` либо совпадает, либо нет), формулировка
предупреждения на экране — не "похоже на другую новую позицию ниже", а
"совпадает с другой строкой ниже, возможно из-за наложения страниц" (или
близкая по смыслу), чтобы не путать с семантикой `new`-предупреждения.

Ничего не блокируется, тот же принцип, что и для `new`-дублей (ADR-0019
§4) — пользователь по-прежнему может одобрить обе строки (например, если
поставщик действительно указал одну позицию дважды в разных секциях
прайса не из-за чанкинга, а по своей собственной причине); предупреждение,
не запрет.

### 4. Число вызовов и стоимость

14 страниц / 3 страницы на чанк (п.1, с перекрытием 1 страница, п.3) →
приблизительно 6 чанков вместо 1 вызова (было: 1 вызов на весь документ;
станет: ~5–6 вызовов меньшего объёма каждый). Рост числа вызовов
extraction в 5–6 раз.

Подтверждено явно, не оставлено как "предполагается дешёво": в этом же
разговоре ранее была посчитана стоимость извлечения на реальном
14-страничном документе — единицы центов на документ при одном вызове.
Рост в 5–6 раз от единиц центов остаётся единицами-низкими-десятками
центов на документ — не является проблемой при частоте использования
этого пайплайна (обновление прайс-листа поставщика — не операция,
выполняемая сотнями раз в день). Токены на входе документа частично
дублируются перекрытием (п.3, +1 страница на N-1 чанков), это
закладывается в ту же оценку, не меняет порядок величины.

### 5. Отношение к ADR-0019 §3

Явно подтверждается: эта ADR не изменяет решение ADR-0019 §3 о разделении
extraction (шаг 1) и matching (шаг 2) на разные вызовы. Меняется только
внутренняя структура шага 1 — вместо одного вызова на весь документ,
несколько вызовов на чанки страниц того же документа, результаты которых
конкатенируются (п.2) в тот же формат `list[ExtractedPriceLine]`, который
шаг 1 отдавал и раньше. Шаг 2 (`matching.py`) не видит разницы между
"чанкинг был" и "чанкинга не было" — получает на входе тот же тип данных.

## Альтернативы

**Разбивка по естественным разделам документа (секции по категории
товара, повторяющиеся заголовки таблиц).** Отклонено — требует
предварительного шага распознавания структуры документа (новый источник
нестабильности того же рода, который эта ADR устраняет) и/или эвристик,
специфичных под формат конкретного поставщика; не работает одинаково для
разных поставщиков и для сканов/фото без текстового слоя. Механическая
разбивка по числу страниц (п.1) проще, надёжнее для MVP и не требует
понимания содержимого документа заранее.

**Retry того же вызова на весь документ при пустом/частичном
результате вместо разбивки на чанки.** Не рассматривалось как основное
решение — не устраняет причину (единый вызов на большой документ
структурно хрупок), только снижает вероятность конкретного неудачного
запуска ценой дополнительных вызовов без контроля над объёмом каждого
отдельного вызова модели. Может быть добавлено позже как
дополнительная защита поверх чанкинга (retry на уровне отдельного
чанка при его собственном сбое), но не заменяет разбивку — вне объёма
этой ADR.

**Дедупликация на границе чанков как отдельный шаг сразу после
extraction, до matching.** Отклонено — ADR-0019 §4 уже решает эту
задачу на уровне всего импорта после matching, любое дублирование от
перекрытия чанков (п.3) неотличимо для этого механизма от дублирования
по другим причинам (см. п.2/п.3); отдельный механизм добавил бы
сложность без дополнительной пользы.

## Последствия

- `backend/app/price_ingestion/extraction.py`: `extract_price_list_lines`
  внутренне разбивает входной PDF на чанки по страницам (константа числа
  страниц на чанк, дефолт 3, с перекрытием в 1 страницу между соседними
  чанками — п.1, п.3), делает отдельный вызов `client.responses.parse` на
  каждый чанк, конкатенирует результаты (п.2). Публичная сигнатура и
  возвращаемый тип функции не меняются — вызывающий код
  (`price_ingestion/service.py`) не требует изменений.
- Разбивка по страницам применяется только к `input_file` (PDF) —
  документы, обрабатываемые как `input_image` (одиночный скан/фото,
  `_SUPPORTED_CONTENT_TYPES`), по определению не разбиваются на страницы;
  чанкинг для этого случая не в объёме (одно изображение — уже маленький
  объём, к которому диагностированная проблема не относится).
- Рост числа вызовов extraction на документ — с 1 до ~5–6 для документа
  масштаба 14 страниц (п.4), подтверждённый рост стоимости — единицы–низкие
  десятки центов на документ, не является операционной проблемой при
  ожидаемой частоте использования пайплайна.
- Не меняет ADR-0019 §3 (разделение extraction/matching на разные
  вызовы), не меняет схему `PriceListEntry`/`PriceListImport`.
- **Меняет `matching.py`**, в отличие от первоначального намерения этой
  ADR (изменить только шаг 1): `_flag_duplicate_new_lines` расширяется до
  `_flag_duplicate_lines`, покрывая также пары `action="match"` на один
  `material_id` (см. п.3, "Уточнение по дублированию `match`-строк") —
  прямое следствие перекрытия страниц (п.3), не независимое решение.
  Экран ревью (ADR-0019 §4) получает второй вариант текста
  ⚠-предупреждения для этого случая, группировка/бейдж — тот же
  компонент, что уже используется для `new`-дублей.
- Известное ограничение MVP, зафиксировано явно: строка, разорванная не
  на границе физической страницы PDF, а внутри страницы иначе, чем
  ожидается — не покрывается перекрытием (п.3), вне объёма.
- Не в объёме этой ADR: выбор модели extraction (`gpt-5.6-luna` vs
  `gpt-5.4`) — остаётся отдельным, уже идущим тестированием; эта ADR не
  зависит от его результата и не должна пересматриваться по его итогам,
  если только тестирование не покажет, что смена модели сама по себе
  устраняет диагностированное поведение (что противоречило бы диагнозу
  "структурная хрупкость одного вызова на большой документ", см.
  "Контекст").
- Реализация (константа размера чанка, разбивка PDF на под-документы по
  страницам, цикл вызовов, конкатенация, тесты на многостраничный
  документ) — предмет отдельной задачи после вычитки этой ADR.
