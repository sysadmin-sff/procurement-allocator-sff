# ADR-0024: Аутентификация и авторизация (Google Workspace OIDC, роли admin/employee)

Статус: Предложено

## Контекст

Сейчас **ни один** endpoint в системе не защищён. Любой с сетевым доступом
может читать и писать любые данные — включая коммерческие цены поставщиков,
создавать/удалять проекты и ордера, аппрувить строки прайс-листа в боевую
таблицу `Price`. Система будет развёрнута в открытый интернет (удалённая
работа сотрудников), без VPN как защитного периметра — вся защита должна
быть полностью в приложении.

`docs/spec.md` §7 явно относит "Роли/права доступа" к сознательно
отложенному вне MVP — это решение отменяется настоящим ADR: продукт выходит
в открытый интернет, что делает авторизацию блокирующим требованием, не
future-work. `Project.created_by` (`String(255)`, см. `backend/app/models/project.py`)
существует в схеме с первой миграции, но ни один вызывающий код никогда не
заполнял его реальным значением (проверено по `grep` — единственные
использования: сериализация в ответ API и тесты, передающие `None`).

Компания использует корпоративные Google Workspace-аккаунты. Нужны две
роли — `admin` и `employee` — без per-record ACL (например, "сотрудник
видит только свои проекты" — explicitly вне объёма).

Этот ADR фиксирует полную схему аутентификации, модель пользователей, схему
сессий/CSRF и permission-матрицу для **каждого** существующего роутера, до
написания кода — тот же уровень строгости, что ADR-0002.

## Решение

### 1. Механизм аутентификации: Google OAuth 2.0 / OpenID Connect, authorization code + PKCE

Библиотека верификации: **`google-auth`** (`google.oauth2.id_token`), официальная
и поддерживаемая Google для Python по состоянию на 2026 (актуальность подтверждена
веб-поиском в рамках этой задачи, не по памяти — `verify_oauth2_token()` остаётся
рекомендуемой точкой входа). `pip`-пакет `google-auth`, добавляется в
`backend/pyproject.toml` рядом с существующими `openai`/`pgvector`.

**Точный флоу:**

1. Frontend: кнопка "Войти через Google" → переход на `GET /auth/login` (backend).
2. Backend генерирует PKCE `code_verifier` (случайные 43-128 байт, base64url) и
   `code_challenge = SHA256(code_verifier)`, а также случайный `state`.
   Сохраняет `{code_verifier, state}` в короткоживущей httpOnly cookie
   `oauth_flow` (Secure, SameSite=Lax, TTL 10 минут) — сессии пользователя
   ещё не существует, поэтому хранить их негде, кроме как у клиента,
   подписанными/зашифрованными неявно через тот факт, что cookie httpOnly и
   Secure и участвует только в обмене кода, никогда не читается как
   источник identity.
3. Backend редиректит браузер на Google authorization endpoint
   (`accounts.google.com/o/oauth2/v2/auth`) с `client_id`, `redirect_uri`
   (указывает на `/auth/callback` backend, не на frontend), `response_type=code`,
   `scope=openid email profile`, `code_challenge`, `code_challenge_method=S256`,
   `state`, и **`hd=<наш домен>`** — это UX-хинт (Google предзаполняет/фильтрует
   аккаунт), не механизм защиты: `hd` в query можно подделать/обойти, поэтому
   финальная проверка домена обязана произойти на backend после получения
   `id_token` (шаг 6), не полагаться только на этот параметр.
4. Пользователь логинится в Google (или уже залогинен), Google редиректит на
   `GET /auth/callback?code=...&state=...`.
5. Backend читает `oauth_flow` cookie, сверяет `state` из query с сохранённым
   (защита от CSRF на сам OAuth-флоу) — несовпадение или отсутствие cookie
   (истекла/подделана) → 400, редирект на страницу логина с ошибкой.
6. Backend обменивает `code` + `code_verifier` на токены напрямую с Google
   token endpoint (server-to-server, `client_secret` участвует здесь, никогда
   не на фронте). Получает `id_token`.
7. Backend верифицирует `id_token` через
   `google.oauth2.id_token.verify_oauth2_token(id_token, google_requests.Request(), audience=settings.google_client_id)`.
   Библиотека проверяет: подпись (по JWKS Google, с кэшированием), `iss`
   (`accounts.google.com`/`https://accounts.google.com`), `aud` (== наш
   `client_id`), `exp`. Исключение при любой неудаче → 401, редирект на
   логин с ошибкой "не удалось подтвердить вход".
8. **Критично, отдельно от шага 7**: backend проверяет claim `hd` из
   верифицированных claims **равен** `settings.google_workspace_domain`.
   `verify_oauth2_token` эту проверку не делает — это ответственность
   вызывающего кода. Несовпадение или отсутствие `hd` (личный Gmail-аккаунт
   не в Workspace) → переход к единому отказу (см. ниже "Единое сообщение
   об отказе"), эта проверка обязана идти раньше поиска в таблице `User`.
9. Backend ищет `User` по `google_sub` (`claims["sub"]`). Если не найден —
   fallback-поиск по `email`, но **только если у найденной записи
   `google_sub IS NULL`** (см. §2 — bootstrap-случай, когда админ завёл
   пользователя по email до его первого логина); при совпадении — заполняет
   `google_sub` этим значением (привязка на первый вход) и обновляет `email`
   на случай расхождения. Если email совпал, но `google_sub` уже заполнен
   ЧЕМ-ТО ДРУГИМ — это не тот же человек (email мог быть переиспользован
   после смены сотрудника в Workspace-admin), поиск не считается успешным.
   Не найдено ни по `sub`, ни валидным fallback по `email` → переход к
   единому отказу. **Никогда не создаётся новый `User` на этом шаге** —
   self-signup исключён полностью.
10. Если найденный `User.is_active == False` → переход к единому отказу.
11. Успех: создаётся `UserSession`, обновляется `User.last_login_at`,
    ставятся `session_id` и `csrf_token` cookies (см. §3), `oauth_flow`
    cookie удаляется, редирект на frontend (`/`).

**Единое сообщение об отказе.** Три разных по природе отказа — (8) домен
не совпал, (9) пользователь не заведён в `User`, (10) пользователь
деактивирован — обязаны вести к **одному и тому же** HTTP-статусу (`403`)
и **одному и тому же** тексту ошибки на странице логина (например: "Доступ
запрещён. Обратитесь к администратору."), без различения причины в ответе
пользователю. Если различать тексты (или статусы — например, 403 для (8)
и 404/другой код для (9)), внешний наблюдатель, перебирая email-адреса
через сам факт входа, может по разнице в ответе установить: (a) входит ли
конкретный email в домен компании (различие 8 от 9/10 раскрывает это, даже
если у наблюдателя нет пароля от этого email — сам ответ Google на шаге
до backend уже требует владения аккаунтом, но различение на backend всё
равно раскрывает лишний бит: "домен верный, но не зарегистрирован" против
"домен неверный") и (b) существует ли конкретный `User` в системе.
Оба факта — утечка информации о структуре организации и её инструментах,
не должны быть узнаваемы извне. Различение причины отказа доступно
**только** во внутреннем логе backend (для диагностики администратором),
никогда в HTTP-ответе или редиректе, видимом браузеру.

**Logout — реальная серверная инвалидация, не только очистка cookie.**
`POST /auth/logout` (доступен через `Depends(get_current_user)`, см. §4):
находит `UserSession` по `session_id` из cookie и **удаляет эту строку из
БД** (`DELETE`, не soft-flag — история сессий не нужна нигде в продукте, в
отличие от `Price`/`User`, где soft-state оправдан историей), затем
очищает `session_id` и `csrf_token` cookies в ответе (`Set-Cookie` с
истёкшим `expires`). Порядок обязателен именно такой — сперва удаление
строки в БД, потом очистка cookie у клиента: если сделать в обратном
порядке и запрос прервётся между шагами, cookie на клиенте уже нет, но
`UserSession` в БД всё ещё жива и валидна для того, кто получит доступ к
исходному значению cookie другим путём (например, из перехваченного
трафика до logout). Без удаления строки в БД скопированная/перехваченная
cookie продолжила бы аутентифицировать запросы и после того, как
легитимный пользователь нажал "Выйти" — серверная сессия, а не только
`Set-Cookie` на клиенте, обязана быть источником истины валидности.

### 2. Модель пользователей — не self-signup

```
User
  id (uuid, pk)
  google_sub (string, unique, nullable)   -- заполняется на первый логин
  email (string, unique, not null)
  name (string, nullable)                 -- из id_token claims, обновляется при логине
  role (string: "admin" | "employee", not null)
  is_active (bool, not null, default true)
  created_at (timestamp, not null)
  last_login_at (timestamp, nullable)
```

`google_sub` nullable **только** для строк, созданных админом заранее и ещё
ни разу не залогинившихся — после первого успешного логина всегда заполнено
и становится основным ключом поиска на будущее (email может меняться в
Workspace, `sub` — нет, см. контекст задачи). Уникальный индекс на
`google_sub` — частичный (`WHERE google_sub IS NOT NULL`), чтобы несколько
`NULL` не конфликтовали (SQL `UNIQUE` уже трактует `NULL` как не равный
самому себе в Postgres, отдельный `WHERE` не обязателен технически, но
делает намерение явным в миграции).

**Bootstrap первого админа**: новая переменная окружения
`BOOTSTRAP_ADMIN_EMAIL` в `Settings` (тот же паттерн, что `openai_api_key`
— `backend/app/core/config.py`). На старте приложения (в `main.py`, после
создания `app`, до приёма трафика) — если задан `BOOTSTRAP_ADMIN_EMAIL` и в
таблице `User` **нет ни одной** строки с `role="admin"`, идемпотентно
upsert: если `User` с этим `email` уже существует — выставить ему
`role="admin"`; если нет — создать новую строку `{email, role="admin",
is_active=True, google_sub=NULL}`. Условие "нет ни одного admin"
(а не "нет строки с этим email") — иначе повторный деплой с тем же env var
после того, как первый админ уже понизил себя или его роль сменили вручную,
молча вернул бы права обратно; это осознанно нежелательно, вмешательство в
`User` через уже существующий admin-CRUD (см. ниже) после bootstrap имеет
приоритет над env var.

**CRUD для управления пользователями** — новый роутер `user.py`
(`/users`), **только `admin`** (см. permission-матрицу §4):
- `GET /users` — список всех.
- `POST /users` — создать (`email`, `role`; `is_active` по умолчанию `True`,
  `google_sub` не передаётся — заполнится на первый логин этого человека).
- `PATCH /users/{id}` — изменить `role`/`is_active`.
- Нет `DELETE` — деактивация (`is_active=False`) вместо удаления, чтобы не
  терять FK-целостность с новыми audit-колонками (§6) и историю
  `last_login_at`. Тот же принцип, что `Price` никогда не удаляется, если
  закрыта (`price.py: delete_price`), — soft state, не hard delete, там где
  запись значима как история.
- Админ не может деактивировать **самого себя** через этот эндпоинт (защита
  от случайной потери доступа последним активным админом) — если это
  единственный active admin, `PATCH .../is_active=false` на себя → 409.

### 3. Сессии и CSRF

**Хранение сессии — таблица в БД**, не подписанная cookie
(`itsdangerous`). Обоснование: приложение синхронное FastAPI+SQLAlchemy без
Redis, единственный практичный способ мгновенно отозвать доступ
(деактивация сотрудника админом должна инвалидировать уже выданную сессию
на следующий же запрос, не ждать истечения TTL) — таблица, не подпись.
Масштаб (единицы-десятки сотрудников) делает лишний lookup по индексу
пренебрежимо дешёвым; вводить Redis только ради сессий на этом масштабе —
нарушение YAGNI.

```
UserSession
  id (uuid, pk)               -- само значение session_id cookie
  user_id (uuid, fk -> User, not null)
  csrf_token (string, not null)   -- случайный, генерируется при логине
  created_at (timestamp, not null)
  expires_at (timestamp, not null)
  last_seen_at (timestamp, not null)
```

- `session_id` cookie: httpOnly, Secure, `SameSite=Lax`, значение =
  `UserSession.id`. `Lax`, не `Strict` — cookie должна доезжать на
  top-level переход по внешней ссылке (например, кто-то прислал ссылку на
  проект в Slack, сотрудник уже залогинен в этом браузере — не должен
  видеть логин-страницу без причины); `Lax` всё ещё не отправляет cookie на
  cross-site subrequests/POST, что и есть реальная защита здесь, вместе с
  CSRF-токеном ниже.
- Логика истечения: sliding window — `expires_at` при каждом
  аутентифицированном запросе продлевается на константу
  `SESSION_IDLE_TTL` (предлагается 12 часов, обсуждаемо в ревью — не
  архитектурно значимо), с жёстким потолком `SESSION_ABSOLUTE_TTL`
  (предлагается 30 дней) от `created_at`, который не продлевается. Оба —
  именованные константы в коде (`app/auth/constants.py` или в `Settings`),
  не архитектурная часть этого ADR.
- **CSRF — double-submit cookie token**, отдельно от `SameSite`, так как
  прямое требование задачи — не полагаться только на `SameSite` в открытом
  интернете. Механизм:
  - `csrf_token` cookie: **не** httpOnly (frontend обязан её прочитать),
    Secure, `SameSite=Lax`, значение = `UserSession.csrf_token`.
  - На каждый `POST`/`PUT`/`PATCH`/`DELETE` frontend читает эту cookie и
    отправляет значение в заголовке `X-CSRF-Token`.
  - **Проверка безусловна и глобальна, не выборочна по эндпоинтам.**
    `get_current_user` — единственная функция, читающая `session_id` и
    резолвящая `User`/`UserSession`, и **эта же функция**, а не отдельный
    код на стороне конкретного роута, при `request.method in
    {"POST","PUT","PATCH","DELETE"}` **всегда** сверяет заголовок
    `X-CSRF-Token` с `UserSession.csrf_token` через constant-time compare
    (`secrets.compare_digest`) — несовпадение/отсутствие заголовка → 403,
    до выполнения какой-либо бизнес-логики эндпоинта. Поскольку
    `get_current_user`/`require_role` применяются router-level (§5) на
    каждом непубличном роутере, а не per-endpoint, CSRF-проверка
    автоматически покрывает 100% state-changing путей той же единой
    точкой входа, что и сама аутентификация — нет отдельного механизма,
    который можно забыть подключить на новый роут, и нет пути вызвать
    защищённый POST/PUT/PATCH/DELETE, миновав эту проверку, кроме двух
    явно публичных `/auth/login`/`/auth/callback` (у которых нет сессии
    до их завершения, поэтому CSRF-токен взять неоткуда — они защищены
    отдельно, через `state`-параметр самого OAuth-флоу, см. выше).
  - Межсайтовый атакующий не может прочитать `csrf_token` cookie другого
    origin (браузерная same-origin policy на JS-чтение cookie) и не может
    подставить корректный заголовок вслепую — это и есть защита, cookie
    здесь используется только как канал доставки токена клиенту, не как
    источник доверия сама по себе.
  - `GET`/`HEAD`/`OPTIONS` не проверяются на CSRF-токен (не state-changing,
    стандартное исключение) — та же функция `get_current_user` пропускает
    эту проверку для них, но не сам вызов аутентификации.

### 4. Авторизация — permission-матрица по всем существующим роутерам

Принцип по умолчанию: **изменение справочных данных → `admin`**;
**операционная работа с проектом → любой аутентифицированный `employee` или
`admin`**. Полный список — 9 файлов в `backend/app/api/*.py` на момент
аудита в рамках этой задачи (`health.py` исключён как публичный), плюс 2
новых:

| Роутер (файл) | Существующий префикс(ы) | Доступ | Обоснование |
|---|---|---|---|
| `health.py` | `/health` | публичный, без auth | infra-healthcheck, не бизнес-данные |
| `auth.py` *(новый)* | `/auth/login`, `/auth/callback` | публичный | сам механизм входа |
| `auth.py` *(новый)* | `/auth/me`, `/auth/logout` | `get_current_user` | нужна текущая сессия, чтобы отдать/убить её |
| `user.py` *(новый)* | `/users` | `require_role("admin")`, весь роутер | управление доступом — чисто административная функция |
| `supplier.py` | `/suppliers/**` (включая `/offices`, `/contacts`) | `require_role("admin")`, весь роутер | справочник поставщиков — реф. данные |
| `material.py` | `/materials/**` | `require_role("admin")`, весь роутер | канонический справочник материалов — реф. данные |
| `price.py` | `/prices/**` | `require_role("admin")`, весь роутер | прямая правка боевых цен в обход ревью-флоу — самое чувствительное CRUD в системе |
| `price_ingestion.py` | `/suppliers/{id}/price-lists`, `/price-list-imports/**` | `require_role("admin")`, весь роутер | загрузка прайса и **аппрув строк в `Price`** — реф. данные; см. риск ниже |
| `project.py` | `/projects/**` | `get_current_user`, весь роутер | операционная работа отдела монтажа |
| `allocation.py` | `/projects/{id}/allocate`, `/projects/{id}/allocations/**` | `get_current_user`, весь роутер | операционная работа |
| `order.py` | `/projects/{id}/orders`, `/orders/**` | `get_current_user`, весь роутер | операционная работа, включая `parse-response` (LLM-парсинг ответа поставщика — не запись в реф. данные, снимок для конкретного заказа) |
| `purchase_record.py` | `/projects/{id}/purchase-records/**` | `get_current_user`, весь роутер | операционная работа |

Итого: **6 роутеров под `require_role("admin")` целиком** (`user`,
`supplier`, `material`, `price`, `price_ingestion` + весь `/users`), **4
роутера под `get_current_user`** (`project`, `allocation`, `order`,
`purchase_record`), **1 полностью публичный** (`health`), auth.py смешанный
(два публичных пути, два — любая роль). Это покрывает 100% путей,
существующих на момент аудита — при добавлении нового роутера в будущем
CLAUDE.md/этот ADR требуют явно отнести его к одной из этих двух категорий
до мержа, не оставлять без `dependencies=[...]`.

**Явный риск, зафиксированный, не решаемый по умолчанию:** `price_ingestion.py`
объединяет upload прайса (может быть частым, рутинным действием монтажника,
получившего PDF от менеджера поставщика) и apply-в-`Price` (запись боевых
цен). Отнесение обоих под `admin` целиком — консервативный выбор по
умолчанию, соответствующий принципу "изменение справочных данных = admin";
если в реальном использовании upload окажется рутинной операцией не-админов
(например, монтажник получает прайсы, но не должен принимать решение об
аппруве) — это разделение на два разных уровня доступа внутри одного
роутера, отдельный ADR при необходимости, не молчаливое расширение
доступа задним числом.

### 5. Механизм применения — router-level dependencies, не per-endpoint

```python
# app/auth/dependencies.py
def get_current_user(request: Request, db: Session = Depends(get_db)) -> User: ...
def require_role(role: str):
    def _dependency(user: User = Depends(get_current_user)) -> User:
        if user.role != role:
            raise HTTPException(status_code=403, detail="Insufficient permissions")
        return user
    return _dependency
```

Применяется на конструкции роутера:

```python
router = APIRouter(prefix="/suppliers", dependencies=[Depends(require_role("admin"))])
```

не оборачиванием каждого `def` вручную — минимизирует риск забыть один
эндпоинт при будущем добавлении роута в уже защищённый файл. `main.py`
(`app.include_router(...)`) не меняется — защита живёт в определении
самого `APIRouter`, не в точке подключения.

**Чеклист внедрения** (соответствие §4 один-к-одному, для явной сверки при
код-ревью реализации):

- [ ] `health.py` — без изменений (публичный).
- [ ] `auth.py` (новый) — `/login`, `/callback` без dependency; `/me`,
      `/logout` — отдельный `Depends(get_current_user)` на каждом (не
      router-level, т.к. этот же файл содержит публичные пути — единственное
      сознательное исключение из "router-level everywhere").
- [ ] `user.py` (новый) — `APIRouter(dependencies=[Depends(require_role("admin"))])`.
- [ ] `supplier.py` — добавить `dependencies=[Depends(require_role("admin"))]` в `APIRouter(...)`.
- [ ] `material.py` — то же.
- [ ] `price.py` — то же.
- [ ] `price_ingestion.py` — то же (роутер сейчас без `prefix`/аргументов, добавить `dependencies=`).
- [ ] `project.py` — `dependencies=[Depends(get_current_user)]`.
- [ ] `allocation.py` — то же.
- [ ] `order.py` — то же (роутер сейчас без `prefix`, добавить `dependencies=`).
- [ ] `purchase_record.py` — то же.

### 6. Аудит — заполнить реальным `user.id` сейчас же

Дёшево, делается в рамках этой же реализации, не отдельной задачей —
объект `User` уже есть на каждом authenticated-запросе после §5, добавление
одного присвоения на существующих call site'ах не требует нового прохода
позже:

- `Project.created_by` (`String(255)`, сейчас никогда не заполняется) —
  **заменяется** на `created_by_user_id` (uuid, FK → `User`, nullable —
  nullable ради исторических строк из-до-этого-ADR, не для новых). Один и
  тот же столбец переименовывать нельзя (несовместимый тип) — миграция
  дропает старую колонку и добавляет новую. `POST /projects` перестаёт
  принимать `created_by` в payload (клиент никогда осмысленно не заполнял
  его — см. контекст) и берёт его из `Depends(get_current_user)`.
- `Order.created_by_user_id` (новая, nullable FK → `User`) — заполняется в
  `create_orders_for_run` (`app/allocation/order_service.py`) на момент
  создания.
- `PurchaseRecord.created_by_user_id` (новая, nullable FK → `User`) —
  заполняется в `create_purchase_record` (`app/purchase_records/service.py`).
- `AllocationLine.overridden_by_user_id` (новая, nullable FK → `User`,
  рядом с существующим `overridden_at`) — заполняется в
  `override_allocation_line_supplier` и `replace_and_sync_order`
  (оба пути, ведущие к ручному override строки).

Все четыре — одна Alembic-миграция вместе с `User`/`UserSession`. Ни одно
из существующих полей `nullable=False` не меняет nullability — только
добавление новых nullable-колонок плюс замена `Project.created_by`.

### 7. Frontend

- Страница `/login` — кнопка "Войти через Google", ссылка на `GET /auth/login` backend (полный редирект браузера, не fetch/XHR — OAuth-флоу не AJAX-совместим).
- **Route guard на уровне роутинга** (`App.tsx`), не в отдельных компонентах:
  обёртка вида `<RequireAuth>` вокруг текущего `<Route element={<AppLayout />}>`
  — на маунте делает `GET /auth/me`; пока не резолвится — loading state;
  401 → `<Navigate to="/login" />`; успех → рендерит текущее дерево роутов
  как есть. Один guard на всё дерево, не на каждый `<Route>` по отдельности
  — тот же принцип "не размазывать защиту по местам, которые легко забыть",
  что router-level dependencies на backend (§5).
- Header (`AppLayout.tsx`) получает блок "текущий пользователь" (имя/email
  из `/auth/me`) + кнопка "Выйти" → `POST /auth/logout` (удаляет
  `UserSession` на backend, чистит cookies) → редирект на `/login`.
- Admin-only действия (например, кнопки в `SuppliersPage`/`MaterialsPage`/
  ревью прайс-листа) скрываются/дизейблятся в UI для `role="employee"` на
  основе роли из `/auth/me`. **Явно зафиксировано: это UI-удобство, не
  граница безопасности** — реальная защита полностью на backend (§4/§5),
  тот же принцип, что CLAUDE.md уже применяет к деньгам (frontend не
  пересчитывает итоги — здесь frontend не является источником истины о
  правах).
- **`frontend/src/api/client.ts` требует правки**: ни `request`, ни
  `requestMultipart` сейчас не передают `credentials: 'include'` в
  `fetch(...)` — без этого браузер не отправляет `session_id`/`csrf_token`
  cookies на cross-origin запросы (dev: Vite dev server на другом порту,
  чем backend; prod — потенциально другой поддомен). Также добавляется
  чтение `csrf_token` cookie и простановка заголовка `X-CSRF-Token` на
  `post`/`put`/`patch`/`delete`/`postMultipart` (не на `get`). Это правка
  существующего файла в рамках реализации этого ADR, не новый модуль.

### 8. Секреты

Новые переменные в `Settings` (`backend/app/core/config.py`), тот же
паттерн, что `openai_api_key`:

```python
google_client_id: str | None = None
google_client_secret: str | None = None
"""Secret — never returned in any API response, never logged."""
google_workspace_domain: str | None = None
"""Значение claim 'hd', которому обязан равняться id_token — см. §1 п.8."""
session_signing_secret: str | None = None
"""Используется только для подписи короткоживущей oauth_flow cookie (§1 п.2)
— UserSession/csrf_token не подписываются отдельно, они opaque значения,
проверяемые через БД, не через подпись."""
bootstrap_admin_email: str | None = None
"""См. §2 — bootstrap первого admin при старте приложения."""
```

Если `google_client_id`/`google_client_secret`/`google_workspace_domain` не
заданы — `/auth/login` должен возвращать понятную 500-ошибку конфигурации
на старте (fail fast), не пытаться выполнить неполный OAuth-флоу — тот же
паттерн graceful/explicit failure, что уже есть для `openai_api_key`
(`app/order_response_parser/client.py` и др.), но здесь ошибка config
должна блокировать сам вход, а не деградировать до "ручного ввода" — входа
без Google в этой системе не существует.

### 9. HTTPS — требование к деплою, не к коду

`Secure`-флаг всех cookies (`session_id`, `csrf_token`, `oauth_flow`) не
сработает без HTTPS — браузер молча не отправит такую cookie по HTTP. Это
делает HTTPS **обязательным предусловием**, при котором вообще работает
защита сессий, а не опциональным улучшением. Ответственность — хостинг/
reverse-proxy (TLS termination перед приложением), не код FastAPI. Отдельно
фиксируется как deployment-требование, чтобы деплой без TLS не выглядел
"работающим" (Google OAuth callback технически отработает по HTTP в dev, но
cookies не будут доезжать до браузера в проде без Secure-совместимого TLS)
— вне объёма кода этого ADR, но блокирующее условие для его безопасности.

### 10. Rate limiting на `/auth/login` и `/auth/callback`

Защита от злоупотребления самим OAuth-флоу (не от подбора пароля — пароля
нет). Простейший вариант, соразмерный масштабу (не требует Redis) —
in-memory sliding window по IP на уровне ASGI middleware (например,
`slowapi` — использует `starlette`, совместим с FastAPI) с консервативным
лимитом (например, 10 запросов/минуту на IP на каждый из двух путей).
Ужесточение вне объёма этого ADR — если появятся признаки реальной
атаки/abuse, отдельная задача.

## Альтернативы

**JWT в `localStorage` вместо httpOnly cookie + сессии в БД.** Отклонено —
явно исключено в постановке задачи (уязвимо к XSS: любой инжектированный
скрипт читает `localStorage` напрямую, тогда как httpOnly cookie
недоступна JS). Также лишает возможности мгновенного revoke — JWT
самодостаточен до истечения `exp`, деактивация пользователя не имеет
эффекта, пока токен не протухнет естественным образом.

**Signed cookie (itsdangerous) вместо таблицы `UserSession`.** Рассмотрено
и отклонено — см. §3. Проще (нет БД lookup, нет схемы), но не даёт
мгновенного revoke без отдельного denylist-механизма, который свёл бы
экономию сложности к нулю. На масштабе этого приложения (единицы-десятки
сотрудников, уже синхронный SQLAlchemy) DB-lookup не создаёт измеримой
нагрузки.

**"Первый залогинившийся становится admin" вместо `BOOTSTRAP_ADMIN_EMAIL`.**
Явно отклонено в постановке задачи — это дыра: система в открытом
интернете, первый, кто пройдёт `hd`-проверку домена (то есть любой
сотрудник компании, не обязательно предполагаемый первый админ, либо кто-то,
кто успеет раньше в гонке при одновременном первом запуске), автоматически
получил бы полные права.

**Per-record ACL (например, "сотрудник видит только созданные им
проекты").** Explicitly вне объёма по прямому указанию в постановке
задачи — роли `admin`/`employee` для MVP, не per-object permissions.
Аудит-колонки из §6 закладывают для этого основу на будущее (реальный
`user_id` уже на записях), но фильтрация видимости по нему — отдельная
задача, если возникнет потребность.

**MFA сверх того, что даёт сам Google Workspace.** Вне объёма — компания
полагается на защиту самого Google-аккаунта (Workspace admin console может
принудительно требовать 2FA на своей стороне независимо от этого
приложения); дублировать MFA в приложении не добавляет защиты, только
трение.

**Password-based fallback-логин.** Вне объёма — не нужен, раз есть
единственный способ входа через Workspace; добавление пароля вводило бы
второй, более слабый путь аутентификации без причины.

## Последствия

- Новая Alembic-миграция: таблицы `User`, `UserSession`; колонки
  `Order.created_by_user_id`, `PurchaseRecord.created_by_user_id`,
  `AllocationLine.overridden_by_user_id` (все nullable FK → `User`);
  замена `Project.created_by` (String) на `Project.created_by_user_id`
  (FK → `User`, nullable).
- `docs/data-model.md` требует обновления: добавить `User`/`UserSession` в
  ER-диаграмму и таблицы полей, отразить замену `Project.created_by`.
- `docs/architecture.md` требует обновления: новый компонент "4.
  Аутентификация" (Google OIDC → `/auth/*` → `UserSession`), связь ко всем
  остальным блокам через `get_current_user`/`require_role`.
- `docs/spec.md` §7 ("Роли/права доступа" — вне MVP) должен быть явно
  отмечен как отменённый этим ADR — продукт выходит в открытый интернет, что
  делает авторизацию blocking, не deferred.
- Все существующие тесты API (`backend/tests/**/test_api.py`), обращающиеся
  к защищённым роутерам напрямую через `TestClient` без аутентификации,
  сломаются после внедрения — потребуется общая test-фикстура
  (аутентифицированный `TestClient` с валидной `UserSession`, вероятно
  `admin`-фикстура и `employee`-фикстура отдельно) в `conftest.py`. Это
  ожидаемое, не побочное следствие — тесты должны явно проверять оба:
  "правильная роль — 200", "неправильная роль — 403", "без сессии — 401",
  не только happy path.
- `frontend/src/api/client.ts` — обязательная правка (`credentials:
  'include'`, `X-CSRF-Token` заголовок), иначе ни один запрос с фронта не
  будет аутентифицирован после этого ADR, независимо от того, что backend
  уже требует сессию.
- Реализация — предмет отдельной задачи (implementation plan через
  `writing-plans`), в объём этого ADR не входит написание кода.
