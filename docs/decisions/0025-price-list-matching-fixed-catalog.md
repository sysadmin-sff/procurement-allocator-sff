# ADR-0025: Matching прайс-листа против фиксированного каталога — убрать действие "new" и векторный поиск

Статус: Предложено

## Контекст

Решение команды (зафиксировано пользователем, не переоткрывается): импорт
прайс-листа больше не предлагает создание новых материалов. Новые
материалы добавляются впредь **только вручную через `/materials`** — этот
пайплайн их больше не создаёт вообще. Задача matching сужается: проверить
входящие строки прайса **только** против уже существующего каталога
(~300 материалов на момент этой ADR), не искать среди них то, чего в базе
ещё нет.

Это меняет саму природу задачи, которую решали ADR-0019 §3 и ADR-0021/
0022/0023. ADR-0019 "Контекст" явно противопоставил эту задачу ADR-0018
(закрытый список 10-30 `OrderItem`, помещающийся в один промпт) — открытым
каталогом в сотни позиций, растущим, не помещающимся в контекст одного
вызова вместе с документом, поэтому потребовавшим отдельного шага
matching с векторной предфильтрацией top-5 кандидатов. **Эта предпосылка
была верна для открытого, растущего каталога. Теперь каталог закрыт по
построению** (расширяется только вручную, не этим пайплайном) и мал
(~300 названий) — предпосылка, обосновывавшая архитектуру ADR-0019 §3,
меняется, поэтому и решение пересматривается, тем же образом, что
ADR-0022 §1 пересмотрело обоснование ADR-0021 после смены подтверждённой
стоимости (не как отмена ошибки, а как следствие смены исходных данных).

**Явно не в объёме**: ADR-0021 (чанкинг extraction по страницам) и
дедупликация от чанк-перекрытия (ADR-0022 §2, ADR-0023) — извлечение
(шаг 1) не меняется этой задачей. `page_number`-атрибуция, конкурентность
`ThreadPoolExecutor`, retry/backoff на `RateLimitError`,
`processing_status="failed"` — всё это относится к шагу 1 (извлечение) и
инфраструктуре вызовов, а не к тому, откуда matching берёт кандидатов;
ничего из этого не пересматривается здесь. Полный отказ от возможности
расширять каталог через ИИ навсегда — тоже не в объёме; если понадобится
в будущем — отдельный новый ADR с реальным сценарием использования.

## Решение

### 1. Векторный поиск (embeddings + top-5) убирается из шага matching

**Весь список кандидатов передаётся в каждый LLM-вызов напрямую, без
предварительной векторной фильтрации.**

Оценка объёма: ~300 материалов × (`internal_sku` + `canonical_name`, без
полных `attributes`) ≈ 3-4 тыс. токенов на список кандидатов при разумном
форматировании (`- id=..., sku=..., название=...` на материал). Это
пренебрежимо мало относительно контекстного окна используемых моделей
(сотни тысяч токенов) — список кандидатов помещается в промпт вместе с
батчем сырых строк без необходимости в top-K отборе. Векторный поиск в
ADR-0019 §3 был не оптимизацией качества решения, а **вынужденной мерой
против физического ограничения контекста** ("весь `Material` не
помещается в контекст одного вызова вместе с документом" — ADR-0019
"Контекст"); при 300 названиях этого ограничения больше нет, поэтому нет
причины оставлять механизм, введённый исключительно ради его обхода.

**Атрибуты (`attributes`) — не передаются в список кандидатов**, только
`canonical_name` + `internal_sku` (+ `category`/`unit`, как и раньше, они
дёшевы и уже используются `_candidate_context` для контекста модели).
Обоснование сужения (это явный вопрос задачи, не самоочевидность): при
топ-5 кандидатах после векторного отбора `attributes` помогали модели
различить *уже похожие по эмбеддингу* варианты. При полном списке из ~300
разных названий разных категорий эта детализация не нужна для основной
работы — отличить "PVC FENCE PANEL" от "ALUMINUM RAILING" не требует
атрибутов; она может понадобиться только для действительно близких пар
(разные размеры одной линейки, как в реальных данных ADR-0023 —
`SS PING SOCKET 3/8"` vs `SS PING SOCKET 1/4"`), а полные `attributes`
всех 300 материалов утроили/учетверили бы объём промпта без
пропорциональной пользы (`canonical_name` для линейки товаров обычно уже
содержит различающий размер/вариант в самом названии, как видно из
примеров ADR-0023). Если реальный прогон (см. "Не в объёме реализации"
ниже) покажет системную путаницу именно на таких парах — включить
`attributes` обратно узкое дополнение, не пересмотр этого ADR.

**Риск спутать модель 300 одновременными названиями — рассмотрен,
принят как управляемый, не отклонён без обоснования.** Это правда
качественно другая задача для модели, чем top-5 (ADR-0019 §3) — не
"выбери наиболее похожий кандидат из короткого предфильтрованного
списка", а "найди совпадение (если есть) в среднем списке". Но:

- Список кандидатов **фиксирован и известен заранее для всего импорта**
  (не меняется построчно, в отличие от ADR-0019 §3, где топ-5 были разные
  для каждой строки) — это позволяет включить список кандидатов в промпт
  **один раз на батч**, а не дублировать на каждую строку внутри одного
  вызова, если batching строк в один вызов (не в объёме этой ADR,
  реализация вправе решить сама — см. "Не в объёме реализации") окажется
  оправданным для стоимости/скорости.
- 300 коротких строк "название + SKU" — это тот же порядок величины
  контекста, что модели такого класса (`gpt-5.6-luna`, structured
  outputs) уже надёжно обрабатывают в этом же кодовой базе для
  извлечения (ADR-0021: чанк в 3 страницы прайса, сотни строк
  извлечения за вызов) — не заявлено голословно, это тот же класс
  задачи "найти правильный элемент среди многих в контексте", что уже
  подтверждено работающим на сопоставимом объёме.
- Компенсирующая мера от путаницы — не архитектурная (не возврат
  векторного поиска), а поведенческая: confidence threshold (п.3) и
  реальный прогон перед эксплуатацией (тот же процесс, что уже применён
  ко всем LLM-компонентам этой кодовой базы, ADR-0018 §1/ADR-0019
  "Условие закрытия"/ADR-0021 "Условие закрытия") — если реальный прогон
  покажет систематическую путаницу (не единичные ошибки, а паттерн), это
  условие пересмотра для возврата к предфильтрации, а не гипотеза,
  которую нужно разрешать заранее без данных.

**Что это убирает из кода.** `find_top_candidates` (`candidates.py`) и
вызов `embed_text`/`material_embedding_input` **для сырых строк прайса**
(построчный расчёт эмбеддинга `raw_name` ради векторного поиска) больше
не нужны в `matching.py`. `Material.embedding` (колонка, миграция
ADR-0019 §1) и `backfill_material_embeddings.py` **не удаляются** —
затронуто отдельным пунктом ниже (п.6), не тем же решением, что и убор
поиска из matching.

### 2. `SupplierMaterialAlias`-короткий-путь — без изменений

`find_known_alias` (ADR-0019 §2) остаётся ровно как есть: точное
строковое совпадение `(supplier_id, supplier_raw_name)` проверяется перед
дорогим вызовом, при совпадении — `PriceListEntry` с `action="match"`,
`confidence=1.0`, `reasoning="known alias"`, дорогой вызов и экран ревью
всё равно проходятся (CLAUDE.md принцип 2). Единственное, что меняется —
природа "дорогого вызова", который alias позволяет пропустить: теперь это
matching против фиксированного списка (п.1), а не открытый поиск с
векторной предфильтрацией. Ничего в `find_known_alias` или порядке
вызовов не переписывается этой ADR.

### 3. Действие "new" убирается; confidence threshold для match vs "не найдено"

**LLM возвращает только `action: "match" | "not_found"`** (переименовать
из текущего `Literal["match", "new"]` — `"not_found"` точнее описывает
семантику "не нашёл соответствия в фиксированном списке", чем "new",
который подразумевал бы намерение создать материал, чего этот пайплайн
больше не делает). `material_id`/`confidence`/`reasoning` остаются;
`suggested_internal_sku` убирается из structured output (п.4).

**Confidence threshold — одна граница, не новая категория.** Раз
"new"/третьего варианта нет, LLM обязана классифицировать в один из двух
классов при любом confidence. Порог не решает "match или not_found" (это
уже само решение LLM) — он решает **как показать `match` на экране
ревью**:

- `confidence >= 0.7` — обычная строка `match`, без дополнительной пометки.
- `confidence < 0.7` (тот же диапазон "требует внимания", что уже
  использует order response parsing, ADR-0018 §3(a) — не новое число,
  переиспользование уже принятого в этой кодовой базе порога для того же
  класса решения "ИИ нашла соответствие, но не уверена") — строка
  `match`, но с ⚠-пометкой низкой уверенности на экране ревью, тем же
  визуальным языком, что уже применён к `below_min_order`/расхождению
  цены (ADR-0006 §4/ADR-0007 §4/ADR-0013 §3) и к low-confidence match в
  ADR-0018. **Не отдельная третья категория** — та же категория `match`,
  сортировка по возрастанию confidence (ADR-0019 §4, сохраняется) уже
  естественно поднимает эти строки наверх списка без необходимости
  отдельного раздела экрана.
- `action="not_found"` — строка не создаётся на экране ревью вообще (см.
  п.5, принятый риск), независимо от confidence этого решения. Confidence
  порог на match не применяется к not_found — not_found уже безусловно не
  показывается.

Конкретное число 0.7 — перенесено из уже принятого прецедента (ADR-0018
§3(a)), не откалибровано заново на этой задаче отдельно; если реальный
прогон (условие закрытия, как и у остальных LLM-компонентов) покажет, что
граница даёт слишком много/мало ⚠-пометок относительно факта ошибок —
корректировка числа, не пересмотр механизма.

### 4. `suggested_internal_sku` — убрать из схемы

**Решение: убрать полностью (миграция), не оставить nullable
неиспользуемым.**

Обоснование выбора между двумя вариантами задачи: поле было добавлено
ADR-0020 специально для экрана ревью действия `action="new"` — черновой
SKU, который пользователь редактирует перед `POST /materials`. Действие
"new" удаляется этой ADR **полностью** — не становится реже, не остаётся
частично, а перестаёт быть достижимым состоянием пайплайна. Поле, для
которого нет ни одного пути его заполнения (LLM больше не производит
`suggested_internal_sku`, п.3) и ни одного экрана, который бы его читал
(экран ревью показывает его только в блоке `action="new"`, которого
больше не будет) — не "пока не используется", а гарантированно мёртвое
по построению этой же задачи, не по случайности. CLAUDE.md проекта не
формулирует общего принципа про мёртвые поля напрямую, но собственная
формулировка задачи ("не усложнять расширение схемы без необходимости,
но и не оставлять по инерции то, что явно больше не нужно") резолвится
однозначно в пользу удаления именно потому, что необходимость не
"снизилась", а исчезла как класс — оставление nullable-поля было бы
оправдано, если бы существовал вероятный, хоть и не близкий, путь его
возвращения без нового ADR; здесь же явно оговорено (см. "Контекст"),
что возврат создания материалов через этот пайплайн — предмет **нового**
ADR с реальным сценарием, то есть даже при развороте решения поле
пришлось бы пересматривать заново (формат SKU, чем он предлагается),
не "просто снова начать писать в старую колонку".

Миграция: `DROP COLUMN suggested_internal_sku` на `PriceListEntry`
(колонка добавлена `ddc71f618a45_add_suggested_sku_and_possible_...`,
ADR-0020) — обратная миграция для этой одной колонки, не трогает
`possible_duplicate_of` (остаётся, используется дублированием от
чанк-перекрытия, ADR-0021 §3/ADR-0023, вне объёма этой ADR).

### 5. Строки без совпадения не показываются на экране ревью — принятый риск

**Решение пользователя, не переоткрывается**: строки с `action="not_found"`
не создаются как видимые записи на экране ревью — не как категория
"проигнорировано", а полностью отсутствуют в выводе для пользователя.

**Явно зафиксированный компромисс (см. "Последствия" ниже, раздел
рисков):** если LLM ошибочно классифицирует реальное совпадение как
`not_found` (например, из-за формулировки `raw_name`, сильно
отличающейся от `canonical_name`, либо путаницы в большом списке
кандидатов, риск которой обсуждён в п.1), пользователь **никогда не
узнает**, что эта позиция вообще присутствовала в прайсе — она не
появится ни как ошибка, ни как предупреждение, ни в каком-либо счётчике
"столько-то строк не найдено". Это тихая потеря видимости данных, не
потеря самих данных (сырые строки прайса физически не хранятся отдельно
от `PriceListEntry`, п.6 — `not_found`-строки не персистятся вообще, ни в
скрытом виде).

**Условие пересмотра**: если на практике (после реального использования
пайплайна на боевых прайсах) окажется, что реальные совпадения регулярно
теряются таким образом — не гипотетический риск, а наблюдаемая частота
— пересмотреть это решение (например, персистить `not_found`-строки
скрыто с возможностью служебного просмотра/аудита, без показа на основном
экране ревью). До этого момента — принятый риск, не открытый вопрос.

**Условие пересмотра нуждается в источнике данных, иначе оно недостижимо
на практике — структурное логирование (не БД, не экран) для калибровки.**
Как сформулировано выше, "наблюдаемая частота" ничем не производится:
без отдельного механизма единственный способ узнать, что совпадения
теряются — сотрудник случайно заметит отсутствие знакомой позиции в
прайсе, которую он не может увидеть в интерфейсе по определению этого же
решения. Это не открывает п.5 заново (строка по-прежнему не создаётся как
`PriceListEntry`, не видна пользователю, ничего в UX не меняется) — это
отдельная, более дешёвая мера: `_decide_match` **логирует** (структурный
лог-вызов, не запись в БД, не новая таблица) каждое решение
`action="not_found"`, где `confidence` находится близко к порогу 0.7
(например, `>= 0.5`, диапазон "модель колебалась, а не уверенно не нашла
совпадение") — `raw_name`, `confidence`, `reasoning` целиком (уже
содержит объяснение модели, почему не найдено). Это не persist-решение
второго рода в обход п.5 — лог не запрашиваем через API, не отображается
ни на одном экране, не связан с `PriceListEntry`/`Price`, ничем не
отличается от обычного логирования ошибок/предупреждений, которое уже
существует в этой кодовой базе для других сбоев (например, graceful
degradation эмбеддинга при сбое API, ADR-0019 §1 — "ошибка логируется").
Даёт технической команде возможность периодически просматривать логи
(вручную, не автоматизированным алертом — не в объёме) и оценивать,
насколько часто пограничные `not_found` могли быть реальными
совпадениями — то, на чём условие пересмотра выше может фактически
основываться, а не оставаться пожеланием без механизма.

**Что при этом не персистится (уточнение по объёму, вопрос, не поднятый
явно в постановке, но следующий из неё логически).** `service.py`
(`create_price_list_import`) сейчас создаёт `PriceListEntry` для каждой
строки `matched` без исключения. С этой ADR — строки с
`action="not_found"` **не создаются как `PriceListEntry` вообще**, не
только "не отдаются на экран" — раз они не видны и не редактируемы
пользователем ни в каком виде, персистентная запись без единого способа
её увидеть/применить/удалить была бы мёртвыми данными в БД без
пользы, тот же аргумент, что уже применён в п.4 к схемному полю. Не
противоречит принципу "ничего не пишется в боевые таблицы молча"
(CLAUDE.md принцип 2) — `PriceListEntry` не боевая таблица цен
(`Price`), это буферная таблица ревью, и именно её запись для
`not_found`-строк и предлагается не делать.

### 6. `Material.embedding` / `backfill_material_embeddings.py` — не удаляются, не в объёме

Векторная инфраструктура (миграция `vector`-колонки, `POST /materials`/
`PUT /materials/{id}` синхронный эмбеддинг с graceful degradation,
`backfill_material_embeddings.py`, ADR-0019 §1) **не трогается этой
ADR** — она не используется больше в matching (п.1), но:

- Убирать её было бы отдельным архитектурным решением с собственными
  последствиями (миграция `DROP COLUMN`/`DROP EXTENSION`, удаление
  скрипта, удаление кода из `material.py`) — не запрошено постановкой
  задачи и не вытекает напрямую из "упростить matching": векторная
  инфраструктура принадлежит `Material`, не `price_ingestion`.
- Она может понадобиться снова без нового структурного решения, если
  условие пересмотра п.1 (путаница модели на большом списке) наступит —
  дешевле оставить нетронутой, чем удалять и восстанавливать.

Явно вне объёма реализации этой ADR — не путать с "оставлено по инерции"
(п.4 применяет обратную логику к `suggested_internal_sku` не потому, что
"неудаление вообще плохо", а потому что там необходимость исчезла как
класс; здесь необходимость не исчезла, только текущее использование).

## Альтернативы

**Оставить векторный поиск (топ-K), просто увеличить K.** Отклонено —
не решает структурную причину задачи (векторный поиск существовал ради
физического ограничения контекста, которого больше нет), только
частично снижает его последствия (больше кандидатов в контексте) ценой
сохранения инфраструктуры (эмбеддинг каждой сырой строки прайса,
пороговая логика), не дающей пользы при закрытом малом каталоге.

**Полностью убрать `Material.embedding`/бэкафилл-инфраструктуру заодно
с векторным поиском в matching.** Отклонено (см. п.6) — отдельное
архитектурное решение с собственной ценой, не запрошено постановкой,
может понадобиться снова без нового ADR, если п.1 придётся пересмотреть.

**`suggested_internal_sku` — оставить nullable, просто не заполнять.**
Отклонено (см. п.4, полное обоснование) — поле мертво не временно, а по
построению этой же задачи; возврат к его использованию потребовал бы
нового ADR в любом случае, аргумент "дешевле не мигрировать" не
перевешивает "не оставлять по инерции то, что явно не нужно".

**Персистить `not_found`-строки скрыто (не на экране, но в БД) с самого
начала, не как условие пересмотра, а сразу.** Рассмотрено, отклонено для
MVP этой ADR — постановка задачи явно просит зафиксировать текущий выбор
("не показываются... просто отсутствуют") с условием пересмотра по
факту наблюдаемой частоты, не проектировать скрытый аудит-путь заранее
без данных о том, насколько часто это нужно.

## Не в объёме

- Batching нескольких строк в один LLM-вызов matching (упомянуто в п.1
  как возможное направление, если фиксированный список кандидатов
  делает это выгоднее, чем текущая структура "один вызов на строку") —
  не решается здесь, предмет отдельной задачи реализации/тестирования,
  если объём вызовов после этой ADR всё ещё будет проблемой
  производительности (что менее вероятно, чем при ADR-0022 — здесь нет
  ни векторного поиска, ни выросшего от чанк-перекрытия объёма, только
  сам LLM-вызов на строку).
- Число threshold 0.7 (п.3) — перенесено из ADR-0018, не откалибровано
  заново для этой конкретной задачи; калибровка — по факту реального
  прогона, как и остальные подобные числа в этой кодовой базе
  (`DUPLICATE_DISTANCE_THRESHOLD`, модель extraction).
- Реализация (изменения `matching.py`/`candidates.py`/`service.py`,
  миграция `DROP COLUMN suggested_internal_sku`, обновление
  `MatchDecision`/`PriceListEntry`-схемы и рендерера
  `_to_import_out`/фронтенда, тесты) — предмет отдельной задачи после
  вычитки этой ADR.
- Условие возврата к "new"-действию/расширению каталога через ИИ — новый
  ADR с реальным сценарием использования, не пересмотр этого решения "на
  всякий случай".

## Последствия

- `backend/app/price_ingestion/matching.py`: `_decide_match` получает
  полный список ~300 материалов (`id`/`internal_sku`/`canonical_name`/
  `category`/`unit`, без `attributes`, п.1) вместо топ-5 по векторному
  поиску; `MatchDecision.action` теряет `"new"`, приобретает
  `"not_found"`; поле `suggested_internal_sku` убирается из
  `MatchDecision`. `find_top_candidates`/векторный поиск построчных
  эмбеддингов сырых строк — убирается из пути matching (не из
  `candidates.py` полностью, если `find_known_alias` там же и остаётся —
  предмет реализации, разделить ли модуль).
- `_flag_duplicate_lines` (ADR-0019 §4/ADR-0021 §3): ветка для
  `action="new"` (попарное косинусное расстояние эмбеддингов) больше не
  имеет входных строк этого типа — удаляется или остаётся мёртвым кодом
  до чистки, предмет реализации; ветка для `action="match"` (точное
  совпадение `material_id`) остаётся без изменений.
- `service.py` (`create_price_list_import`): строки с
  `action="not_found"` не создаются как `PriceListEntry` (п.5) — цикл
  создания записей получает фильтр по действию, которого раньше не было
  (раньше создавались все строки независимо от action).
- `matching.py` (`_decide_match` или вызывающий код): новый диагностический
  лог (не БД, не новая таблица, не видим пользователю) для
  `action="not_found"` с `confidence` близко к порогу 0.7 (п.5) — даёт
  условию пересмотра п.5 фактический источник данных вместо полагания на
  случайное обнаружение пропажи позиции сотрудником.
- Alembic-миграция: `DROP COLUMN PriceListEntry.suggested_internal_sku`
  (п.4). Не трогает `possible_duplicate_of`, `processing_status`,
  `Material.embedding`.
- `Material.embedding`/`backfill_material_embeddings.py`/векторные
  вызовы в `POST /materials`/`PUT /materials/{id}` — без изменений, не в
  объёме (п.6).
- `docs/ui-reference.md` — экран ревью прайс-листа теряет категорию/блок
  "новое" (`action="new"`) целиком; ⚠-пометка низкой уверенности (п.3)
  описывается тем же языком, что уже применён к order response parsing
  (ADR-0018 §3(a)).
- `docs/known-issues.md`: наблюдение (не решение) — типичный результат
  экрана ревью сокращается с ~700 строк (весь прайс) до ожидаемо
  ~50-150 строк (только совпавшие с ~300 материалами) при том же исходном
  документе. Это резко меняет контекст записи "699 строк, применено 0 из
  134" — сам объём проблемы "нельзя физически проверить все строки"
  становится менее острым при на порядок меньшем реальном объёме экрана
  ревью. **Не чинит баг применения напрямую** — если причина того бага в
  логике apply-эндпоинта (не в объёме строк на экране), она остаётся
  отдельной, несвязанной задачей, что и зафиксировано в постановке этой
  задачи.
- Не меняет ADR-0021 (чанкинг extraction), ADR-0022 §2 (конкурентность/
  retry), ADR-0023 (page-scoped дедуп от чанк-перекрытия) — все остаются
  как есть, извлечение (шаг 1) не в объёме.
- Реализация (см. "Не в объёме") — предмет отдельной задачи после
  вычитки этой ADR.
