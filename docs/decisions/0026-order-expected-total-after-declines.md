# ADR-0026: Ожидаемая сумма ордера после отклонения позиций

Статус: Предложено

## Контекст

Реальный случай с прода (не гипотетика): ордер поставщику Lancing содержал
несколько позиций, все они были отклонены поставщиком (`OrderItem.declined_at`,
ADR-0013) и перенесены на других поставщиков через "Найти замену"
(ADR-0014/ADR-0015). Сам `Order` Lancing физически остался в системе — это
правильно, не пересматривается (см. "Не в объёме"). Но экран
`OrderDetailPage` продолжает показывать `Order.total_amount` = $148.26 и
`Order.delivery_fee` = $95.00 — снимок на момент создания ордера
(ADR-0007 §2), который больше не отражает реальность: заказывать у Lancing
по этому ордеру больше нечего, все позиции перенесены в другое место.

`Order.total_amount`/`delivery_fee` — сознательно застывший снимок "что мы
реально отправили" (ADR-0007 §2, подтверждено ADR-0013 §5: "declined-позиции
не исключаются ни из `total_amount`, ни из состава `OrderItem`"). Это решение
**не переоткрывается** этим ADR. Проблема не в том, что снимок не
обновляется — а в том, что сегодня нет **второго**, вычисляемого числа рядом
с ним, отвечающего на вопрос "а что теперь, после всех отказов и переносов".

Пользователь изначально предложил удалять `Order`, когда последняя позиция
перенесена — **отклонено**, не реализуется этим ADR. Причины:

1. `Order` — снимок факта "что реально было отправлено" (ADR-0007 §2).
   Удаление стирает историю, что именно Lancing отклонил и по какой цене —
   тот же принцип, что уже защищает declined-`OrderItem` от удаления
   (ADR-0013 §5, ADR-0014 §4: "Ничего не меняется и не удаляется").
2. Если в ордере несколько позиций и отклонена только часть — удалять весь
   `Order` нельзя. "Удалить, когда пусто" — частный случай (все позиции
   отклонены), не общее решение для частичного отказа, которого недостаточно
   для реального разброса состояний ордера.

Прецеденты, которые это решение обязано соблюдать:

- **ADR-0007 §4** — "не скрывать, показывать оба факта" уже применено к паре
  `quoted_price`/`confirmed_price`: разница не подменяет исходное значение, а
  показывается рядом.
- **ADR-0006 §4, ADR-0007 §7, ADR-0012 §4** — вычисляемые (не персистентные)
  индикаторы поверх существующих полей: `below_min_order`,
  "жду ответа"/"сверено", `has_confirmed_prices`. Тот же паттерн
  продолжается здесь, не изобретается заново.
- **ADR-0007 §2, ADR-0013 §5** — `Order`/`OrderItem` как снимок; ничего в
  этом ADR не пишет поверх `total_amount`/`delivery_fee` и не изменяет
  существующие строки `OrderItem`.

Не в объёме этого ADR (явно исключено, не путать с текущей задачей):

- Изменение `Order.status` (draft/approved/sent) в зависимости от
  отклонённых/подтверждённых позиций — отдельный, уже известный и
  сознательно отложенный вопрос (`docs/known-issues.md`, "Order.status
  никогда не меняется с draft"). Флаг "полностью отклонён" (см. Решение §2)
  — независимая вычисляемая величина, не новое значение статуса.
- Удаление `Order`, когда все позиции отклонены — отклонено выше, не
  реализуется.

## Решение

### 1. Вторая, вычисляемая сумма рядом с снимком — не вместо него

`OrderOut` получает новые производные (не персистентные) поля:

```python
class OrderOut(BaseModel):
    ...
    total_amount: float          # снимок, не меняется (ADR-0007 §2)
    delivery_fee: float          # снимок, не меняется (ADR-0007 §2)
    expected_goods_total: float  # новое, вычисляемое
    expected_delivery_fee: float # новое, вычисляемое
    expected_total: float        # новое, вычисляемое
    declined_amount: float       # новое, вычисляемое — см. ниже
```

Вычисление на backend, при чтении (`GET /orders/{id}`, тот же слой, что уже
считает `price_delta`/`price_delta_pct`, ADR-0007 §4):

```
expected_goods_total = Σ item.quoted_price * item.quantity
                        for item in order.items
                        if item.declined_at is None
declined_amount = Σ item.quoted_price * item.quantity
                   for item in order.items
                   if item.declined_at is not None
expected_delivery_fee = 0 if expected_goods_total == 0 else order.delivery_fee
expected_total = expected_goods_total + expected_delivery_fee
```

(Формула `delivery_fee` разобрана отдельно в п.4 — здесь дан итоговый вид,
чтобы схема была цельной.)

**Используется `quoted_price`, не `confirmed_price`/`received_price`.**
`total_amount`/`expected_goods_total` — оба на одной и той же денежной шкале
("план по нашему расчёту"), различаются только составом позиций (все vs
неотклонённые). Смешивать в `expected_*` значения `confirmed_price`
(другая шкала — "на чём сошлись с поставщиком", ADR-0007 §4) сделало бы пару
`total_amount`/`expected_total` уже не сопоставимой напрямую (одно число на
плановых ценах, другое — на смеси плановых и подтверждённых), а сверка
`quoted` vs `confirmed` — отдельная, уже решённая ось (ADR-0007 §4,
`price_delta`), эта задача её не трогает и не дублирует.

**Формат отображения на `OrderDetailPage`** (поведенческая логика, не
разметка — сама вёрстка через `docs/design/` по правилу CLAUDE.md):
существующая строка суммы ("Товары: $148.26 + доставка $95.00") остаётся как
подпись "Отправлено", рядом (не вместо) — вторая строка "Ожидается" с
`expected_goods_total`/`expected_delivery_fee`, показывается **только если**
`declined_amount > 0` (при отсутствии отказов `expected_total == total_amount`
— показывать тождественную пару без причины было бы шумом на каждом ордере,
а не только на тех, где есть расхождение). Пример, если все позиции
отклонены:

```
Отправлено:  Товары $148.26 + доставка $95.00 = $243.26
  из них отклонено поставщиком: $148.26
Ожидается:   Товары $0.00 + доставка $0.00 = $0.00
```

При частичном отказе (п.3):

```
Отправлено:  Товары $500.00 + доставка $50.00 = $550.00
  из них отклонено поставщиком: $120.00
Ожидается:   Товары $380.00 + доставка $50.00 = $430.00
```

Тот же принцип "не скрывать, показывать оба факта", что уже применён к
`quoted`/`confirmed` (ADR-0007 §4) — переиспользуется, не изобретается новый
визуальный язык.

**Отклонено: заменить `total_amount`/`delivery_fee` в ответе API вычисляемым
значением, оставить снимок только в БД.** Отклонено — `OrderOut` уже
единственный контракт, которым пользуется `OrderDetailPage` (и, потенциально,
`/orders/:id/print`, ADR-0007 §6, который обязан показывать **только**
`quoted_price`/снимок, никогда ожидаемую сумму задним числом). Подмена
значения в самом поле `total_amount` стёрла бы снимок для любого будущего
потребителя API, читающего это поле напрямую — тот же риск, от которого
ADR-0007 §2 защитился, отказавшись от FK `OrderItem → AllocationLine`. Новые
поля явные и аддитивные, старые не меняют смысл.

**Отклонено: считать `expected_*` на клиенте из уже отданных
`OrderItemOut`.** Отклонено по CLAUDE.md принципу 4 ("все денежные и
количественные операции — только на backend") — это прямая арифметика над
ценами и количеством, тот же класс операции, что `price_delta` (ADR-0007 §4)
уже явно вынесла на backend по той же причине, а не оставила клиенту как
"просто сумма из списка, который и так есть".

### 2. Признак "ордер полностью отклонён"

Новое вычисляемое (не персистентное) поле `OrderOut.fully_declined: bool` —
`true`, если `len(order.items) > 0` и **все** `OrderItem` этого `Order` имеют
`declined_at is not None`. Пустой `Order` (`items == []`) — `false`, не
`true`: у ордера без позиций нет фактического отказа, это отдельное (сейчас
не встречающееся при нормальном создании через `create_orders_for_run`,
ADR-0007 §2) состояние, которое не следует путать с "все позиции отклонены".

Тот же паттерн timestamp-производного вычисления, что `below_min_order`
(ADR-0006 §4), "жду ответа"/"сверено" (ADR-0007 §7) и `has_confirmed_prices`
(ADR-0012 §4) — не новая колонка, вычисляется при чтении, риск рассинхрона
отсутствует по построению (та же причина, по которой ADR-0007 §1 отклонил
персистентную `price_delta`).

**Список ордеров проекта (`ProjectDetailPage`).** Показывать видимую пометку
"Полностью отклонён" рядом с таким `Order` в списке — да. Обоснование:
сегодня список ордеров проекта не даёт никакого сигнала о том, что конкретный
`draft`/`sent`-ордер по факту пуст по содержанию (все позиции сорваны) —
пользователь узнаёт об этом, только открыв ордер и просмотрев все строки.
Та же логика видимости, что уже применена к `below_min_order` (ADR-0006 §4:
"предупреждение, не запрет, но обязано быть видно") и к списку
`existing_draft_orders` с их суммами в модалке конфликта (ADR-0012 §4) —
пользователь не должен идти внутрь сущности, чтобы узнать факт, который
система уже вычислила. Формат — тот же визуальный язык
`--color-danger-text`/бейдж, что уже переиспользован во всех предыдущих ADR
этого проекта, не новый паттерн.

**Draft-conflict guard (ADR-0012).** Полностью отклонённый `draft`-ордер
**не должен** считаться конфликтующим при следующей проверке
`_conflicting_draft_orders_by_supplier` (`create_orders_for_run`,
ADR-0012 §1/§3) — то есть при повторном создании ордеров тому же поставщику
(например, Lancing снова понадобился по этому же проекту позже) не должен
показывать модалку "у поставщика уже есть черновик" применительно к этому
конкретному, полностью отклонённому черновику.

Обоснование: весь смысл guard'а ADR-0012 — предупредить, что повторное
создание рискует **задублировать реально актуальный** черновик или **стереть
невосстановимые данные** (`has_confirmed_prices`, тот же ADR §1: "необратимо
— введённое значение существует только в этой строке"). Полностью
отклонённый `draft` не несёт ни одной живой позиции ("заказывать у Lancing по
этому ордеру больше нечего" — дословно формулировка задачи) — предупреждать о
конфликте с ним означало бы защищать пользователя от столкновения с
документом, который уже не описывает никакое реальное намерение закупки.

**Уточнение о `has_confirmed_prices`, чтобы не расходиться молча с
ADR-0012.** Признак "полностью отклонён" **не отменяет** и не заменяет
`has_confirmed_prices` (ADR-0012 §4) — оба вычисляются независимо и
**оба** учитываются при построении списка конфликтующих ордеров:

- `fully_declined = true` **и** `has_confirmed_prices = false` — этот
  конкретный `existing_draft_orders`-элемент исключается из проверки
  конфликта целиком (см. ниже, конкретика реализации): не попадает ни в
  список `409`-конфликта, ни в подсчёт "у поставщика X уже есть N
  черновиков".
- `fully_declined = true` **и** `has_confirmed_prices = true`
  (например, позиция была отклонена **после** того, как на неё уже ввели
  `confirmed_price`, до отказа — ADR-0013 §2 явно разрешает одновременное
  существование `declined_at` и `confirmed_price`/`received_price` на одной
  строке: "ничего не запрещается и не обнуляется") — **не исключается** из
  проверки. Причина: `has_confirmed_prices` сигнализирует о невосстановимых
  данных, введённых человеком вручную; факт, что позиция впоследствии
  отклонена, не отменяет того, что кто-то уже потратил время на сверку этой
  цены — стирание такого черновика без строгого подтверждения (вторая
  ступень ADR-0012 §1) остаётся оправданным независимо от `declined_at`.
  Иными словами: "полностью отклонён" ослабляет guard только там, где ничего
  ценного не может быть потеряно; там, где guard защищает конкретно
  ручной труд сверки — он продолжает защищать.

Практически: изменение в `_conflicting_draft_orders_by_supplier`
(`backend/app/allocation/order_service.py`) — при сборе
`existing_draft_orders` для поставщика пропускать `Order`, если
`fully_declined(order) and not has_confirmed_prices(order)`; если после
фильтрации у поставщика не осталось ни одного элемента —
поставщик не попадает в `suppliers_with_existing_drafts` вообще (как если бы
конфликтующих `draft` для него не было, симметрично тому, как карточка
поставщика без строк убирается из `SupplierAllocationSummaryOut` целиком,
ADR-0006 §4 п.5 — та же идиома "пустое после фильтра не показывается как
пустая запись, а не показывается вовсе").

**Отклонено: делать `fully_declined` условием для мягкого
пропуска guard'а без учёта `has_confirmed_prices`.** Отклонено — привело бы
к молчаливой потере сверенных цен ровно в сценарии, который ADR-0012 §1
специально выделил как требующий более строгого подтверждения; "отклонена
позиция" и "потеряны деньги ручного труда" — независимые факты, смешивать их
в одно условие значило бы тайно ослабить существующую защиту там, где она не
теряла силу.

**Тот же фильтр НЕ применяется к поиску целевого черновика в
`replace_and_sync_order` (ADR-0015 §1, шаг 3).** Явное решение, не
умолчание, не побочный вывод из логики фильтра выше — это разные проверки
над структурно похожими данными, и расхождение между ними должно быть
зафиксировано, а не обнаружено случайно при реализации:

- **`_conflicting_draft_orders_by_supplier` (ADR-0012)** отвечает на вопрос
  "стоит ли предупредить перед массовым созданием набора новых `Order` по
  всему `run`", запускается один раз при клике "Подтвердить и создать
  ордера". Полностью отклонённый без `confirmed_price` `draft` там
  действительно нечего защищать — п.2 выше.
- **Поиск черновика в `replace_and_sync_order` (ADR-0015 §1.3)** отвечает
  на другой вопрос: "куда физически положить одну конкретную позицию,
  которую пользователь только что перенёс на этого поставщика" —
  единственная альтернатива операции найти существующий `draft` этого
  поставщика в проекте — создать **второй** `draft` этому же поставщику в
  этом же проекте рядом с уже существующим, пустым по содержанию.

Если бы поиск в ADR-0015 §1.3 игнорировал полностью отклонённый `draft` (как
будто его нет), результат — создание нового `Order` рядом со старым: два
`draft`-`Order` одного поставщика в одном проекте, один пустой
(все позиции `declined_at != null`), другой свежий с одной перенесённой
позицией. Это ровно та же форма дублирования (§"Контекст" ADR-0012: "три
поставщика, у каждого по два `draft`-`Order` с идентичной `total_amount`"),
которую ADR-0012 создан устранять — просто вместо предупреждения перед
массовым создание оно возникло бы молча, в обход guard'а, через другой
эндпоинт. Расширение проверки ADR-0012, применённое к ADR-0015 непоследовательно
(закрывает дыру в одном месте, открывает её в соседнем), было бы хуже, чем не
трогать ADR-0015 вовсе.

**Решение: полностью отклонённый `draft` в ADR-0015 §1.3 продолжает
считаться "единственным найденным" и получает новую позицию — оживает.**
Не игнорируется. Пустой (по факту содержания) `draft` без единой активной
строки — не то же самое, что "черновика не существует"; строка `Order`
физически есть, привязана к этому `(project_id, supplier_id)`, и наличие
второго `draft` того же поставщика в том же проекте — именно то состояние,
от появления которого ADR-0012 защищает в принципе, независимо от того, что
конкретно вызвало создание второго ордера. Добавление новой позиции в
существующий (пусть и полностью отклонённый) `draft` — не "оживление" в
смысле подмены истории: `declined_at`/`decline_reason`/`quoted_price` уже
существующих (отклонённых) строк этого `Order` не трогаются (ADR-0015 §1.3:
"Существующие позиции этого ордера... не читаются и не изменяются"), просто
рядом появляется новая, неотклонённая строка — тот же `Order`, что уже был,
с более полным содержанием. `expected_total`/`fully_declined` (п.1–2 этого
ADR) для него на следующий `GET` пересчитаются автоматически и корректно
покажут `fully_declined = false`, раз в нём снова есть неотклонённая
позиция — никакого отдельного кода для "разожления" не требуется, это
прямое следствие того, что оба поля вычисляются на чтении, не хранятся.

### 3. Частично отклонённый ордер

Формулы п.1 (`expected_goods_total`, `declined_amount`, `expected_delivery_fee`,
`expected_total`) не завязаны на "все или ничего" — они суммируют по
подмножеству `declined_at is None`/`is not None` независимо от того, сколько
позиций в каждом подмножестве. `fully_declined` (п.2) — единственное поле,
которое требует "все", и это осознанно: он отвечает на другой, более узкий
вопрос ("нечего больше заказывать по этому ордеру целиком"), не на "есть ли
вообще отказы".

Экран показывает "частично отклонён" неявно — через одновременное появление
блока "Ожидается" (п.1, показывается при `declined_amount > 0`) и **отсутствие**
пометки "Полностью отклонён" (п.2, `fully_declined = false`). Отдельного
третьего вычисляемого поля/статуса "partially_declined" не вводится — оно
было бы чистым отрицанием уже доступной информации
(`declined_amount > 0 and not fully_declined`), тот же инстинкт, что уже
отклонил персистентную `below_min_order`-подобную дельту без причины
(ADR-0007 §1: не хранить то, что тривиально выводится).

### 4. Доставка (`delivery_fee`) в ожидаемой сумме

**Решение: `expected_delivery_fee = 0`, только если `expected_goods_total ==
0` (все позиции ордера отклонены); иначе `expected_delivery_fee =
order.delivery_fee` без изменений (снимок).**

Обоснование через две отдельные причины:

- **Когда все позиции отклонены** — платить за доставку действительно нечего
  (дословно сформулировано в задаче: "заказывать у Lancing по этому ордеру
  больше нечего"). `delivery_fee` в исходном снимке отражал решение солвера
  привезти именно эти товары этим поставщиком (ADR-0002); если товаров
  больше нет, `flat_fee` за пустую доставку — не реалистичное ожидание, оно
  вводило бы пользователя в заблуждение о том, сколько денег реально
  потребуется в будущем по этому конкретному документу.
- **Когда отклонена только часть** — `delivery_fee` **не пересчитывается**
  как функция нового `expected_goods_total` относительно
  `free_shipping_threshold`/`per_order_min_amount` поставщика (в отличие от
  того, как ADR-0006 §4 пересчитывает `delivery_fee` при **живом** override
  строки в `AllocationLine`). Причина различия: `AllocationLine`-пересчёт
  (ADR-0006 §4) работает над **актуальным планом закупки**, где такой
  пересчёт напрямую управляет тем, что реально будет отправлено в следующий
  `Order`; `expected_delivery_fee` здесь — производная витрина поверх уже
  отправленного, зафиксированного документа (`Order`, снимок ADR-0007 §2),
  не альтернативный план. Полный пересчёт `free_shipping_achieved` по
  формуле доставки поставщика для частично отклонённого набора товаров
  создал бы третье, независимо вычисляемое число ("что было бы, если бы мы
  сегодня отправили только неотклонённые позиции этому же поставщику") —
  которое **не является** фактом об уже существующем `Order` (у него нет
  такого гипотетического заказа, есть только фактически отправленный), а
  было бы прогнозом для документа, которого не существует. Это тот же
  инстинкт, что уже дважды отклонил "проектировать вслепую" в этом проекте
  (ADR-0007 §5 про автосвязку Order↔Price, ADR-0013 §4 про
  received-vs-confirmed показатель): нет запрошенной потребности в такой
  гипотетической переоценке доставки для частичного случая, и вводить её
  сейчас — считать то, что не соответствует ни одному реальному состоянию
  однозначно, дословно то же рассуждение, что ADR-0013 §5 уже применила к
  отказу от "скорректированного total_amount".

Итог: доставка в `expected_*` — бинарна (снимок либо ноль), не
пересчитываемая величина, за одним явным исключением ("всё отклонено, значит
доставки не будет вообще").

**Отклонено: полный пересчёт `expected_delivery_fee` по формуле
поставщика (`free_shipping_threshold`/`per_order_min_amount`) для любой
степени отказа, не только 100%.** Отклонено по причине выше — превращает
производную витрину факта в гипотетический перерасчёт несуществующего
документа, качественно другая (и не запрошенная) задача.

**Отклонено: оставить `expected_delivery_fee = order.delivery_fee` всегда,
даже при 100% отказе.** Отклонено — прямо противоречит формулировке задачи
("платить за доставку $0 реально нечего") и духу "не скрывать реальность"
(п.1) — было бы формально консистентно со снимком, но вводило бы
пользователя в заблуждение именно в том случае, который стал поводом для
этого ADR.

## Альтернативы

Альтернативы для каждого под-решения — инлайн в "Решение" (1–4), та же
структура, что принята в ADR-0006/0007/0012/0013/0014.

Альтернатива на уровне ADR целиком (уже отклонена пользователем до начала
работы, см. "Контекст"): **удалять `Order`, когда последняя позиция
перенесена**. Отклонено по обеим причинам, разобранным в "Контекст" —
противоречит принципу "снимок, не кэш" (ADR-0007 §2) и не обобщается на
частичный отказ.

## Последствия

- `OrderOut` (`backend/app/api/schemas/order.py`) получает новые
  вычисляемые поля: `expected_goods_total`, `expected_delivery_fee`,
  `expected_total`, `declined_amount`, `fully_declined`. Ни одно не
  персистентно, ни одно не меняет существующие поля (`total_amount`,
  `delivery_fee` остаются снимком, ADR-0007 §2 не переоткрывается).
- Расчёт — в том же слое, что уже считает `price_delta`/`price_delta_pct`
  (`backend/app/allocation/order_service.py`, рядом с существующей функцией
  построения `OrderItemOut`/`OrderOut` при `GET /orders/{id}`), не новая
  таблица и не новая миграция Alembic.
- `_conflicting_draft_orders_by_supplier`
  (`backend/app/allocation/order_service.py`, ADR-0012 §1/§3) получает
  дополнительный фильтр: `draft`-`Order` пропускается при сборе конфликта,
  если `fully_declined(order) and not has_confirmed_prices(order)` — иначе
  логика ADR-0012 (список, суммы, `has_confirmed_prices` на каждый элемент,
  вторая ступень подтверждения) не меняется.
- **Явное следствие фильтра выше**: поскольку `replace_drafts=true`
  (ADR-0012 §2) удаляет ровно тот набор `Order`/`OrderItem`, который вернула
  `_conflicting_draft_orders_by_supplier`, полностью отклонённые без
  `confirmed_price` черновики **никогда не участвуют в удалении через
  `replace_drafts`** — они просто не появляются в списке кандидатов на
  замену (`suppliers_with_existing_drafts`, ADR-0012 §4) и остаются в системе
  нетронутыми при любом исходе модалки конфликта (замена/дозаказ/отмена).
  Это не отдельное решение, а прямое следствие того, что `replace_drafts`
  оперирует над результатом того же фильтра, а не сканирует `draft`-ордера
  заново собственным запросом — фиксируется здесь явно, а не оставляется как
  побочный вывод, который нужно каждый раз выводить заново из логики фильтра.
- **Тот же фильтр не применяется к поиску целевого черновика в
  `replace_and_sync_order` (ADR-0015 §1, шаг 3)** — см. "Решение" §2,
  отдельный явный подраздел. Полностью отклонённый `draft` там по-прежнему
  находится как "единственный существующий" и получает новую позицию
  (оживает), не игнорируется — иначе перенос через "Найти замену" начал бы
  молча создавать второй `draft`-`Order` того же поставщика в обход
  guard'а ADR-0012, а не потому что это два похожих, но разных по смыслу
  запроса (см. обоснование в тексте решения).
- `OrderDetailPage.tsx`: вторая строка "Ожидается", показывается только при
  `declined_amount > 0` — формат из п.1, обёртка/разметка через
  `docs/design/` (правило CLAUDE.md, не редактируется руками).
- `ProjectDetailPage.tsx`: список ордеров проекта получает бейдж/пометку
  "Полностью отклонён" для ордеров с `fully_declined = true` — визуальный
  язык уже установлен предыдущими ADR, конкретная разметка — через Claude
  Design.
- `docs/ui-reference.md`: раздел про `OrderDetailPage` (введён ADR-0007,
  дополнен ADR-0013/ADR-0014) получает описание блока "Ожидается" и условия
  его показа; раздел про `ProjectDetailPage` — описание пометки "Полностью
  отклонён" в списке ордеров.
- `docs/data-model.md`: примечание, что `OrderOut` несёт производные поля
  `expected_*`/`declined_amount`/`fully_declined`, аналогично уже отмеченным
  `price_delta`/`price_delta_pct`/`has_confirmed_prices` — сама схема БД
  `Order`/`OrderItem` не меняется, миграция не требуется.
- Явно не в объёме (см. "Контекст"): изменение `Order.status`
  (draft/approved/sent) — остаётся отдельной, уже зафиксированной в
  `docs/known-issues.md` задачей; удаление `Order` при полном отказе —
  отклонено, не реализуется.
- Реализация (расчёт на backend, фильтр в guard'е ADR-0012, оба экрана
  фронтенда) — предмет отдельной задачи после вычитки этого ADR, как и с
  предыдущими ADR в проекте.
