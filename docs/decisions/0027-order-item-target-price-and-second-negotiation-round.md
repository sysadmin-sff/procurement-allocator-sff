# ADR-0027: `OrderItem.target_price` и второй раунд ИИ-парсинга (заполнение `confirmed_price`)

Статус: Предложено

## Контекст

ADR-0007/ADR-0013 формализовали сверку цены `Order` как тройку
`quoted_price` (что отправили) / `received_price` (первый ответ поставщика,
до торга) / `confirmed_price` (финальная договорённость). ADR-0018 добавил
ИИ-парсинг документа-ответа поставщика, который сейчас заполняет **только**
`received_price` через кнопку "Применить все совпадения".

Реальный созвон с руководством и сотрудником отдела закупок вскрыл, что
между `received_price` и `confirmed_price` в реальном процессе есть ещё одно
звено, не отражённое в модели:

1. Отправили запрос — `quoted_price`.
2. Получили ответ — `received_price` (ADR-0013).
3. Цена не устроила — сотрудник вписывает **свою** целевую цену и отправляет
   её поставщику повторно, торгуясь.
4. Получили **второй** ответ поставщика (после торга) — эта цена и есть
   финальная договорённость, `confirmed_price`.

Два отдельных пробела отсюда:

- Негде хранить целевую цену (шаг 3) — намерение сотрудника, не факт от
  поставщика. Без поля она нигде не фиксируется между вводом и получением
  ответа на неё, теряется, если сотрудник не помнит, на чём торговался.
- ИИ-парсинг ответа (ADR-0018) умеет распознавать документ и предлагать
  цены, но жёстко привязан к `received_price` как единственной цели записи
  — нет способа прогнать тот же пайплайн второй раз, целясь в
  `confirmed_price`, без ручного построчного ввода (ADR-0007 §3), который
  ADR-0018 как раз и должен был избавить сотрудника делать вручную для
  10–30 позиций.

Явно подтверждено пользователем как часть контекста задачи: это **ровно
один** дополнительный шаг (target → второй ответ), не общий механизм на N
раундов. ADR-0013 уже отклонила безграничный журнал переговоров
(`OrderItemPriceEvent`) как избыточный для реального процесса компании
("Альтернативы" ADR-0013) — тот вывод не пересматривается здесь, он
подтверждён практикой: нужен один дополнительный шаг, не журнал.

Дополнительно найденный смежный дефект — попутно исправляется здесь, не
отдельным ADR, потому что второй раунд переговоров делает его практически
значимым (см. п.5 ниже). `buildOrderText`
(`frontend/src/routes/OrderDetailPage.tsx:301–338`, функция, строящая текст
"Список материалов" для копирования и отправки поставщику) не фильтрует
`OrderItem` по `declined_at` — отклонённые поставщиком позиции сейчас
попадают в копируемый текст наравне со всеми остальными, по `quoted_price`.
При одном раунде копирования (текст обычно копируется один раз, до того как
получены отказы) это было почти незаметно. С введением второго раунда тот
же текст реалистично копируется повторно уже после того, как часть позиций
отклонена в первом раунде — тогда в исходящем сообщении поставщику будут
ошибочно перечислены позиции, которые он сам же отклонил.

Не в объёме этого ADR (см. постановку задачи):
- Безграничный журнал/история раундов переговоров — прямо отклонено выше.
- Автоматическая связь `confirmed_price` ↔ `Price` в БД — уже отдельно
  отложена в ADR-0007 §5, не переоткрывается.
- Изменения в самом ИИ-пайплайне распознавания (`order_response_parser`,
  ADR-0018 §1–2) — второй раунд переиспользует тот же `parse-response`
  endpoint без изменений в извлечении/матчинге, меняется только то, во что
  фронтенд применяет результат.

## Решение

### 1. Новое поле `OrderItem.target_price`

```python
class OrderItem(UUIDPKMixin, Base):
    ...
    quoted_price: Mapped[float] = mapped_column(Numeric(12, 2), nullable=False)
    received_price: Mapped[float | None] = mapped_column(Numeric(12, 2))
    target_price: Mapped[float | None] = mapped_column(Numeric(12, 2))
    """Цена, на которую сотрудник хочет сторговаться — намерение с нашей
    стороны, не факт от поставщика. NULL = торг не предлагался. См. ADR-0027."""
    confirmed_price: Mapped[float | None] = mapped_column(Numeric(12, 2))
    confirmed_at: Mapped[datetime | None] = mapped_column(DateTime(timezone=True))
    declined_at: Mapped[datetime | None] = mapped_column(DateTime(timezone=True))
    decline_reason: Mapped[str | None] = mapped_column(String(500))
```

`target_price` встаёт между `received_price` и `confirmed_price` по
семантике процесса (шаг 3 из "Контекст"), тем же паттерном, что уже
применён ко всей тройке `quoted`/`received`/`confirmed` (ADR-0007 п.1,
ADR-0013 п.1): `NULL` = "это звено ещё не произошло", не 0 и не копия
соседнего поля. Независимое, необязательное поле — тот же принцип "backend
не навязывает порядок ввода" (ADR-0013 п.1): `target_price` может
существовать без `received_price` (сотрудник заранее знает, что цена
завышена, и сразу называет свою, даже не дожидаясь формального первого
ответа) и `confirmed_price` может появиться без `target_price` (согласились
сразу на `received_price`, торговаться не о чем — тот же случай, что
ADR-0013 п.1 уже разрешила для `confirmed_price` без `received_price`).

**Ввод — та же inline-редактируемая ячейка**, что уже используется для
`confirmed_price` (ADR-0007 §3): сохранение по `blur`/`Enter`, `PATCH`
одного поля через уже существующий endpoint (см. п.3 ниже — расширение, не
новый endpoint).

**Расположение колонки на `OrderDetailPage`.** Текущий порядок колонок:
Отправленная цена → Полученная цена → Подтверждённая цена → Расхождение.
`target_price` встаёт между "Полученная цена" и "Подтверждённая цена" —
Отправленная → Полученная → **Целевая (наша)** → Подтверждённая →
Расхождение. Это порядок колонок, совпадающий с порядком шагов процесса
(quoted → received → target → confirmed) — тот же принцип, что уже
неявно соблюдён существующим порядком трёх колонок. Заголовок колонки:
"Целевая цена" — короче и однозначнее в контексте уже подписанных
"Отправленная"/"Полученная"/"Подтверждённая" (все — прилагательное +
подразумеваемое "цена"), не "Цена для торга" (длиннее, не сохраняет
параллелизм заголовков).

**Отклонено: располагать `target_price` как модальное/выезжающее поле
рядом с кнопкой "Торговаться", а не постоянную колонку.** Отклонено —
таблица `OrderDetailPage` уже построена как построчная сверка всех
известных цен разом (ADR-0007 §3, ADR-0013 §3: "сверка — по определению
построчный процесс"), скрытие `target_price` за дополнительным действием
противоречило бы этому установленному паттерну без причины — цена не
настолько редко используемая, чтобы прятать её за кликом (в отличие,
например, от `decline_reason`, который скрыт за состоянием "отклонено",
потому что осмысленен только в этом состоянии; `target_price` осмыслен
на любой строке, где идёт торг).

### 2. Второй раунд ИИ-парсинга — отдельный, независимый блок загрузки

**Решение: второй, независимый блок загрузки под существующим "Распознавание
ответа поставщика" — не переключатель режима в одном компоненте.**

На `OrderDetailPage` под существующей секцией `ParseResponseSection`
(которая пишет в `received_price`, ADR-0018 §3–4, без изменений) появляется
второй, отдельно озаглавленный блок — "Распознавание финального ответа
(после торга)" — с собственной кнопкой загрузки файла и собственной кнопкой
"Применить все совпадения". Оба блока видны одновременно, независимо друг
от друга; какой из них использовать — решает сотрудник по факту (загружает
в первый блок первый ответ, во второй — второй, после торга).

**Backend не меняется.** `POST /orders/{order_id}/parse-response` (ADR-0018
§1–2) остаётся ровно тем же endpoint'ом — извлечение и matching (закрытый
список `OrderItem` этого заказа, structured output с
`matched_order_item_id`/`price`/`confidence`/`reasoning`) не знают и не
обязаны знать, какой раунд переговоров прислали на вход: это чисто
фронтенд-решение, в какое поле маппится результат. Второй блок вызывает тот
же endpoint, тот же клиентский метод `ordersApi.parseResponse`; различие —
только в том, что при нажатии "Применить все совпадения" из второго блока
`PATCH .../items/{item_id}` уходит с `confirmed_price`, а не
`received_price` (единственная точка изменения — вызов
`handleApplyAllMatched`, параметризованный целевым полем).

**Обоснование выбора (отдельный блок, не переключатель в одном
компоненте).** Рассматривался вариант единого `ParseResponseSection` с
переключателем "Первый ответ" / "После торга" над формой загрузки,
определяющим целевое поле результата. Отклонён в пользу двух отдельных
блоков по прямому запросу пользователя (см. постановку задачи): два
всегда видимых, отдельно озаглавленных блока проще для сотрудника, который
в реальности может держать оба документа открытыми и сверяться с обоими
одновременно (что показал первый ответ, что — второй) — переключатель
скрывал бы один из результатов, требуя переключения туда-обратно, чтобы
свериться с обоими. Компонентно это означает параметризацию существующего
`ParseResponseSection` полем `targetField: "received_price" |
"confirmed_price"` (и заголовком блока, кнопкой "Применить") и рендер двух
его экземпляров — не дублирование логики, тот же компонент с двумя
конфигурациями.

### 3. Визуальный индикатор — расширение существующего `price_delta`, не новый показатель

**Решение: расширить существующий механизм `price_delta` (ADR-0007 §4),
добавив параллельный расчёт `received_price` vs `quoted_price` тем же
визуальным языком и тем же порогом `>10%` — не изобретать новый
показатель.**

Явно запрошено на созвоне: подсветка, подорожала/подешевела **полученная**
цена относительно **базы** (`quoted_price`, что мы посчитали и отправили),
не только относительно `confirmed_price`, как уже считает существующий
`price_delta`. ADR-0013 п.4 уже рассматривала близкий вопрос ("received vs
confirmed — сколько сторговали") и отложила его как не запрошенный на тот
момент и не влияющий ни на один расчёт; этот ADR отвечает на другой,
дословно запрошенный сейчас вопрос ("received vs quoted — на сколько
ответ поставщика разошёлся с нашим планом") и вводит его явно, потому что
теперь запрошен.

`OrderItemOut` получает вторую пару вычисляемых полей:

```
received_price_delta: float | None
received_price_delta_pct: float | None
```

Тот же расчёт, что `price_delta`/`price_delta_pct` (ADR-0007 §4,
`order_service.price_delta()`), но с `received_price` вместо
`confirmed_price` в роли сравниваемого значения; `quoted_price` — база в
обоих случаях, не меняется. `NULL` при `received_price IS NULL` — та же
логика "нет базы для сравнения, не 0" (ADR-0007 п.1). Backend переиспользует
существующую функцию `price_delta(quoted_price, received_price)` — она уже
принимает `confirmed_price: float | None` вторым параметром обобщённо
(не завязана на имя поля), второй вызов с `received_price` требует только
второй строки в API-слое, не новой функции.

**`target_price` — без собственного индикатора расхождения.**
`target_price` — наше намерение, не цена, полученная от кого-то внешнего;
сравнивать "что мы хотим" с "что мы отправили" не несёт того же смысла,
что сравнение двух *фактов* (`quoted`/`received`/`confirmed` — все три:
что мы посчитали, что нам ответили, на чём сошлись). Показатель расхождения
отвечает на вопрос "насколько результат разошёлся с планом"; `target_price`
сам по себе не результат, а промежуточный ввод — вводить для него дельту
означало бы визуально уравнять "мы предложили X" с "нам подтвердили X",
что смешивает намерение с фактом на экране, специально спроектированном
эту грань различать (ADR-0013 "Контекст": весь ADR-0013 — про то, чтобы
не терять различие между "что предложено" и "что случилось").

**Одна и та же строка получает подсветку по обоим показателям
независимо** — если строка одновременно `|received_price_delta_pct| >
10%` (расхождение первого ответа) и `|price_delta_pct| > 10%` (расхождение
финальной цены, редкий, но возможный случай — например, торговались, но
всё равно не дотянули до `quoted_price`), обе колонки подсвечиваются
раздельно; агрегированный счётчик на карточке Order ("N позиций с
расхождением >10%", ADR-0007 §4) считает только по `price_delta` (сверка
уже отправленного/подтверждённого), как и раньше — `received_price_delta`
не добавляется в этот агрегат, потому что это внутренний рабочий сигнал по
ещё не финализированной цене, не итоговый статус позиции; в отличие от
`price_delta`, который отвечает на вопрос про уже принятое решение.

**Отклонено: отдельный, самостоятельный визуальный паттерн для
`received_price_delta`.** Прямо исключено постановкой задачи ("не
изобретай новый визуальный паттерн — переиспользуй уже установленный") —
расширение существующего механизма, тот же `--color-danger-text`-язык,
тот же порог `10%`, тот же расчёт функцией, тот же формат отображения
(`+$X (+Y%)`), что и колонка "Расхождение" для `confirmed_price`.

### 4. Порядок применения — второй раунд не трогает `received_price`

Подтверждено явно: загрузка второго документа (ответ на `target_price`) **не
перезаписывает** `received_price`. Оба поля (`received_price` из первого
раунда, `target_price` — введённая вручную цена-предложение,
`confirmed_price` из второго раунда) остаются видны одновременно на одной
строке — ничего не подменяется. Обеспечивается по построению, без
дополнительной логики:

- Второй блок парсинга (п.2) вызывает `PATCH .../items/{item_id}` с
  `confirmed_price`, никогда не с `received_price` — `set_order_item_fields`
  (ADR-0013 п.3) уже принимает оба поля независимо (`_UNSET`-сентинел на
  каждом), PATCH одного не трогает другой, тот же механизм, что уже
  гарантирует независимость `received_price`/`declined_at`/
  `decline_reason` друг от друга.
- Единственный способ стереть `received_price` — явный `PATCH {
  "received_price": null }` (снять значение, как и сейчас, ADR-0013 п.3,
  "снять подтверждение — опечатался, хочет отменить"), второй раунд
  парсинга никогда не формирует такой payload.

`target_price` при этом тоже не трогается вторым раундом парсинга (тот же
`_UNSET`-принцип: PATCH с `confirmed_price` не задевает `target_price`) —
сотрудник видит на строке одновременно, что он предложил (`target_price`) и
на чём в итоге сошлись (`confirmed_price`), может сравнить визуально без
дополнительного расчёта (разница между двумя видимыми числами на экране —
не денежная операция уровня агрегатов, тот же аргумент, что уже применён к
сравнению `overridden_at`/`ordered_at` на клиенте, ADR-0007 п.2).

### 5. `buildOrderText` исключает отклонённые позиции

**Решение: `buildOrderText` (`frontend/src/routes/OrderDetailPage.tsx:301–338`)
полностью исключает `OrderItem` с `declined_at IS NOT NULL` из копируемого
текста — не включает их с пометкой "отклонено", а не перечисляет вовсе.**
Применяется независимо от того, какая цена используется в тексте
(`quoted_price` сейчас; если позже текст расширится и на `target_price` —
исключение действует так же).

**Обоснование — исключать, а не помечать.** `buildOrderText` строит внешний
документ, адресованный поставщику (копия для письма/сообщения), не
внутренний рабочий экран. Позиция, отклонённая этим же поставщиком, — это
факт, уже известный ему от него самого; сообщать поставщику в исходящем ему
тексте "вот эта позиция отклонена" — избыточно и странно (это его собственный
ответ, не наша констатация). Внутри `OrderDetailPage` (таблица, не текст для
копирования) отклонённые позиции по-прежнему видны с пометкой — там аудитория
другая (сотрудник, которому нужно видеть полную картину, ADR-0013 §3), этот
пункт не меняет поведение таблицы. Разграничение по аудитории — тот же
принцип, что уже развёл `OrderDetailPage` и `/orders/:id/print` на разные
компоненты в ADR-0007 §6 ("они обслуживают разных читателей... смешение
усложнило бы оба сценария").

**Реализация — фильтр списка строк на клиенте, но итоговые суммы берутся
готовыми с backend, не пересчитываются.** Две отдельные правки, разной
природы:

- Построчный список: `buildOrderText` получает список позиций, уже
  отфильтрованный по `item.declined_at == null`, вместо прямой итерации по
  `order.items` — `order.items.filter(...)` перед `.forEach`. Это не
  денежная арифметика (принцип 4 CLAUDE.md её не касается) — это выбор,
  какие строки показывать, того же рода, что уже делает `sortedItems` на
  этой странице (декларативная фильтрация/сортировка представления, не
  вычисление суммы).
- Итоговые строки текста (`Goods total`/`Grand total`) — используют
  **уже существующие** `order.expected_goods_total` и
  `order.expected_delivery_fee` (ADR-0026, приходят в том же `GET
  /orders/{id}`, на котором и так построен весь `OrderDetailPage`), не
  `order.total_amount`/`order.delivery_fee` (снимок при отправке, ADR-0007
  §2, который не учитывает отказы) и не пересчёт из отфильтрованного
  списка на клиенте. `expected_goods_total`/`expected_delivery_fee` уже
  вычислены backend'ом (`order_service.order_expected_totals`) ровно как
  "план минус отклонённые позиции" — та же величина, что нужна здесь,
  посчитанная один раз, а не заново другой формулой на клиенте.

Это устраняет любое отступление от принципа 4: единственная сумма,
появляющаяся в скопированном тексте, — число, которое backend уже отдал,
не число, вычисленное во второй раз фронтендом. Побочный эффект,
достойный явной фиксации: скопированный текст и блок "Ожидается" на самой
странице (ADR-0026, `order.expected_total`) теперь неизбежно показывают
одно и то же число — оба читают одно и то же поле ответа, вместо двух
независимых расчётов одной и той же величины, которые могли бы разойтись
(например, если бы клиентская формула суммирования когда-нибудь
разошлась с серверной — тот самый класс риска, из-за которого ADR-0007
п.1 изначально отказалась хранить `price_delta` как персистентную
колонку, посчитанную в двух местах).

**Отклонено: помечать строку как "Отклонено поставщиком — не включено" вместо
полного исключения.** Отклонено по причине выше (сообщать поставщику его же
отказ его собственными словами избыточно); также помеченная, но
присутствующая строка усложняет и без того плоский построчный формат текста
(нумерация "1. 2. 3." либо продолжает считать отклонённые позиции, путая
нумерацию, либо требует отдельной логики пропуска номера — усложнение ради
информации, которая не нужна получателю текста).

## Альтернативы

Альтернативы для каждого под-решения (1–5) перечислены инлайн в "Решение"
— та же структура, что уже принята в ADR-0006/0007/0013/0018.

Единственная альтернатива на уровне ADR целиком: **не вводить `target_price`
как поле схемы, полагаться на то, что сотрудник помнит/держит цену для
торга вне системы (в переписке с поставщиком) и вводит сразу
`confirmed_price` после того, как сошлись.** Отклонено — прямо противоречит
описанному пользователем реальному процессу, где `target_price` — не
формальность, а конкретное число, которое сотрудник вписывает и отправляет
поставщику; без поля оно нигде не фиксируется в системе между вводом и
получением ответа, теряется для истории конкретной сделки (в отличие от
`confirmed_price`, которое всё равно будет введено по итогу) и не может
быть визуально сопоставлено с итоговым `confirmed_price` на экране (см. п.4
— именно эта сверка "что просили / что получили" — часть явного запроса
пользователя).

## Последствия

- Миграция Alembic: `order_items.target_price NUMERIC(12,2) NULL`. Nullable
  без бэкафилла — семантика "не заполнено = торг не предлагался" корректна
  для всех существующих строк (тот же прецедент, что миграции ADR-0013).
- `OrderItemConfirmIn` (`backend/app/api/schemas/order.py`) получает
  опциональное `target_price: float | None`, той же независимой семантикой,
  что остальные поля этого PATCH (омиссия — не трогать, явный `null` —
  сбросить).
- `set_order_item_fields` (`backend/app/allocation/order_service.py`)
  получает параметр `target_price` тем же `_UNSET`-паттерном, что уже
  применён к `confirmed_price`/`received_price`/`declined`/`decline_reason`
  — без нового timestamp-поля (`target_price` не получает собственный
  `*_at`, по аналогии с `received_price`, которому ADR-0013 п.3 явно
  отказала в `received_at` за отсутствием потребителя; та же причина
  применяется здесь — ничто в этом ADR не использует "когда предложена
  целевая цена").
- `OrderItemOut` получает `target_price`, `received_price_delta`,
  `received_price_delta_pct` рядом с существующими полями. Расчёт
  `price_delta`/`price_delta_pct` (`quoted` vs `confirmed`) не меняется.
- `order_service.price_delta()` вызывается второй раз в API-слое с
  `received_price` вместо `confirmed_price` — сама функция не меняется
  (уже принимает второй параметр обобщённо).
- Backend `order_response_parser`/`POST .../parse-response` (ADR-0018) —
  без изменений контракта. Меняется только фронтенд: `ParseResponseSection`
  параметризуется полем `targetField`, рендерится дважды — "Распознавание
  ответа поставщика" (пишет `received_price`, как сейчас) и "Распознавание
  финального ответа (после торга)" (пишет `confirmed_price`, новое).
- `OrderDetailPage.tsx`: новая колонка "Целевая цена" между "Полученная
  цена" и "Подтверждённая цена" (та же inline-редактируемая ячейка), новая
  колонка/индикатор расхождения `received_price` vs `quoted_price` рядом с
  существующей колонкой "Расхождение" (или второй под-колонкой в ней —
  решается на этапе реализации/дизайна), второй `ParseResponseSection`-блок
  под первым.
- `docs/data-model.md`: `OrderItem` получает `target_price` (в дополнение к
  уже описанным по ADR-0007/0013 полям).
- `docs/ui-reference.md`: раздел про `OrderDetailPage` дополняется
  расположением колонки "Целевая цена", поведением второго блока
  распознавания, и правилом отображения `received_price_delta` тем же
  визуальным языком, что и `price_delta`; а также правилом п.5 —
  скопированный текст заказа никогда не содержит отклонённые позиции.
- `buildOrderText` (`frontend/src/routes/OrderDetailPage.tsx:301–338`)
  фильтрует `order.items` по `declined_at == null` перед построением
  построчного списка, а `Goods total`/`Grand total` в тексте берёт из
  `order.expected_goods_total`/`order.expected_delivery_fee` (ADR-0026,
  уже приходят в `OrderOut`) вместо `order.total_amount`/`delivery_fee` и
  вместо пересчёта на клиенте (см. п.5) — правка существующего бага,
  попутная этому ADR, не отдельная задача.
- Реализация (миграция, схемы, PATCH-расширение, фронтенд — колонка, второй
  блок парсинга, фильтр в `buildOrderText`) — отдельная задача после вычитки
  этого ADR, как и было с предыдущими ADR в этом проекте.
