# ADR-0028: Строгая группировка поставщика по категории материала (Doors, Gutter, Profil, Mesh, Roof panels)

Статус: Принято — реализовано в `backend/app/allocation/` (`solver.py`:
`STRICT_CATEGORIES`, `diff[C][m]` + штраф; `types.py`: `MaterialInput.category`;
`service.py`: `algorithm_version = "adr-0028-v1"`, `AllocationRun.split_categories`).

**Корректировка §1 при реализации.** Буквальный псевдокод §1
(`model.add(x[(m*, s)] == x[(m, s)])` и `model.add(x[(m*, s)] == 0)` для
асимметричных пар) — это **hard**-ограничения, добавляемые безусловно, не
через `diff`. Это прямо противоречит гарантии §3 ("категорийное ограничение
не может самостоятельно сделать модель infeasible... `diff[C][m]` — обычная
бинарная переменная без принудительного `= 0`") и ключевому тесту из
"Последствия" (ни один поставщик не покрывает всю категорию → `OPTIMAL`/
`FEASIBLE`, не `INFEASIBLE`) — воспроизведено buildом именно такого сценария
(mesh1 только у s1, mesh2 только у s2, ни одного общего поставщика): буквальная
hard-линковка §1 даёт `INFEASIBLE`. Реализовано без hard-равенства — только
неравенства `diff[C][m] >= x[m*][s] − x[m][s]` / `>= x[m][s] − x[m*][s]` (с
отсутствующей переменной как константой 0, как и предписывает §2), то есть
асимметричная ветка §1 ("опорному материалу тоже запрещён этот `s`") реализована
как часть штрафа в целевой функции, а не как жёсткий запрет. Штраф при этом
всё равно ощутимо тянет решение к единому поставщику при разумном ценовом
разрыве — см. тесты `test_strict_category_asymmetric_pair_*` в
`backend/tests/allocation/test_solver.py`.

## Контекст

Созвон с руководством и сотрудником отдела закупок (2026-09-04) зафиксировал
требование: материалы **пяти** категорий — `Doors`, `Gutter`, `Profil`,
`Mesh`, `Roof panels` — должны в рамках **одного проекта** закупаться у
**одного и того же поставщика**, все вместе. Причина дословно с созвона:
это визуально заметные на объекте категории (двери, жёлоба, профили,
экраны, кровельные панели), и разные поставщики дают неуловимо разные
оттенки одного номинального цвета — риск видимого рассогласования цвета на
готовой конструкции. Три другие категории — `Connectors`, `Screws`,
`Caulk` — не группируются: они не на лицевой части конструкции, и (тоже с
созвона) реальный каталог покрывает их у каждого отдельного поставщика
менее полно, чем крупные видимые категории — строгая группировка именно
здесь резко повысила бы частоту `infeasible`, не принеся визуальной пользы.

ADR-0002 формализует ILP-модель с переменными `x[m][s]` (материал → один
поставщик, Ограничение 1: `Σ_s x[m][s] = 1`), `y[s]` (поставщик
задействован), `free[s]`/big-M для консолидации доставки. Это ЯДРО системы:
любое изменение постановки задачи здесь имеет тот же вес, что сам ADR-0002,
и разбирается тем же уровнем строгости.

### Проверка `Material.category` на реальных данных (не предположение)

`Material.category` — `String(100), nullable=True`, свободный текст (не
enum, не FK), заполняется при импорте (`backend/app/scripts/
import_real_data.py:159`, читает `MaterialRow.category` из
`xlsx_price_matrix.parse_price_matrix`). Значение приходит из колонки
`Group` реального прайс-листа поставщиков
(`backend/data/import/materials_price_matrix.xlsx`), с forward-fill внутри
файла (см. `xlsx_price_matrix.py:9-15,179-181`).

Запущен фактический парсер (`parse_price_matrix`) поверх реального файла,
не сделано предположение по имени столбца или по названиям категорий:

```
'Caulk' 2
'Connectors' 49
'Doors' 26
'Gutter' 29
'Mesh' 57
'Profil' 68
'Roof panels' 34
'Screws' 29
total materials: 294
dividers skipped: 7
```

Результат: **ровно восемь категорий**, дословно совпадающих с обоими
списками из задачи (5 строгих + 3 нестрогих), без расхождений в
регистре/написании, без категорий вне этого набора восьми. Также
подтверждено через `CATEGORY_SKU_PREFIX` (`xlsx_price_matrix.py:57-66`) —
словарь префиксов SKU уже содержит ровно эти 8 ключей, что было решено
раньше и независимо от этого ADR (при проектировании SKU-схемы импорта).
`FALLBACK_SKU_PREFIX = "MISC"` существует в коде на случай будущей девятой
категории в файле поставщика, но по факту сейчас не используется ни одним
материалом — если/когда появится, категория `None`/новая должна попасть в
нестрогую группу по умолчанию (см. "Ограничения" раздел, правило для
`category IS NULL` или неизвестного значения) до отдельного решения, что
с ней делать, а не молча в строгую.

Список категорий (`STRICT_CATEGORIES` = `{Doors, Gutter, Profil, Mesh, Roof
panels}`) в реализации — константа в коде (`backend/app/allocation/
service.py` или `preprocess.py`, конкретное место — деталь реализации), не
колонка в БД и не поле `Supplier`/`Material` — симметрично тому, как
`_SOLVED_STATUSES` в `service.py:28` уже захардкожен как список статусов
солвера. Расширение/изменение набора строгих категорий — вне объёма этого
ADR (см. задачу), но если понадобится, это правка константы + новый ADR
только если сам механизм группировки при этом меняется, иначе — обычный
код-ревью без нового ADR.

### Эмпирическая проверка охвата каталога — критично для решения по п.2 ниже

Прежде чем решать hard vs soft (см. следующий раздел), фактически посчитано
покрытие реального каталога поставщиками для каждой строгой категории
(`data/import/materials_price_matrix.xlsx`, через `parse_price_matrix` +
факт наличия строки `Price` в `result.prices`):

```
Всего поставщиков с ценами в файле: 7 (Aluminum Distributors Int LLC,
American Metals Supply, Classic Metals, EMS, Florida Sales & Marketing,
JM Fasteners, Lancing)

Категория      | материалов | поставщиков хотя бы с 1 ценой | поставщиков,
               |            | в категории                    | покрывающих
               |            |                                 | ВЕСЬ каталог
               |            |                                 | категории
Doors          | 26         | 7                               | 0
Gutter         | 29         | 7                               | 0
Profil         | 68         | 6                               | 0
Mesh           | 57         | 7                               | 0
Roof panels    | 34         | 4                               | 0
```

**Ни один поставщик не покрывает весь каталог ни одной строгой категории.**
Дополнительно, распределение количества поставщиков на *отдельный*
материал внутри категории:

```
Категория    | ср. поставщиков/материал | материалов без цены ни у кого
Doors        | 2.73                     | 6 из 26
Gutter       | 3.79                     | 2 из 29
Profil       | 3.99                     | 1 из 68
Mesh         | 2.39                     | 5 из 57
Roof panels  | 0.24                     | 29 из 34
```

`Roof panels` — крайний случай: 29 из 34 материалов категории уже сегодня
не имеют цены ни у одного поставщика (независимо от этого ADR — это
существующий пробел каталога, попадающий в `orphaned_materials` уже сейчас
для любого проекта, включающего такой материал). Строгая группировка не
создаёт эту проблему, но означает, что для `Roof panels` в реальности
почти всегда участвует ≤1 поставщик с ценой на конкретный материал —
категория уже структурно близка к "один вариант или ничего".

Оценка практического риска инфизибельности — не полный каталог категории
разом попадает в один проект (проект заказывает подмножество BOM, обычно
2–6 позиций категории на объект, не все 26–68 сразу), поэтому имеет
значение пересечение поставщиков именно по *выбранному подмножеству*, не
по полному списку. Смоделировано Монте-Карло (500 случайных подмножеств
размером 2–5 материалов на категорию, только из материалов, где хотя бы
один поставщик есть — то есть исключая уже-`orphaned`-по-факту случаи, не
относящиеся к этому ADR):

```
Категория     | покупаемых материалов | доля случайных 2–5-позиционных
               |                       | наборов без общего поставщика
Doors          | 20                    | 23%
Gutter         | 27                    | 7%
Profil         | 67                    | 21%
Mesh           | 52                    | 60%
Roof panels    | 5                     | 87%
```

Это не хвостовые случаи — при жёстком ограничении **типичный** проект,
включающий несколько материалов `Mesh` или `Roof panels`, имеет
значительный шанс (60–87% в симуляции) не собрать ни одного поставщика,
покрывающего весь выбранный набор. Для `Doors`/`Profil` риск ниже, но не
пренебрежим (~20%), для `Gutter` — умеренный (7%).

**Методология симуляции — важное ограничение оценки.** Код (запущен
интерактивно, воспроизводится с тем же файлом каталога):

```python
suppliers_by_desc = defaultdict(set)
for p in result.prices:                       # result = parse_price_matrix(...)
    suppliers_by_desc[p.description].add(p.supplier_name)

for cat in STRICT:
    descs = [d for d in mats_by_cat[cat] if suppliers_by_desc.get(d)]
    for _ in range(trials):                    # trials = 500
        k = random.randint(2, min(5, len(descs)))
        sample = random.sample(descs, k)
        common = set.intersection(*(suppliers_by_desc[d] for d in sample))
        if not common:
            infeasible += 1
```

`suppliers_by_desc[d]` строится только из `ParsedWorkbook.prices`
(`PriceCell(description, supplier_name, price)`) — поставщик засчитан
как "покрывающий" материал исключительно по факту наличия ценовой ячейки
в прайс-листе. `PriceCell` не несёт поля `availability` вообще —
симуляция проверяет допустимость пары `(m, s)` только по существованию
цены (ADR-0002 Ограничение 2, часть "нет цены"), **не** по
`available[m][s] >= qty[m]` (та же часть Ограничения 2, "недостаточно
наличия"). Иными словами, симуляция моделирует допустимость пары так, как
если бы `availability` было проигнорировано целиком, а не так, как
реально ведёт себя `preprocess.split_orphaned_materials`/`solver.py`
(где `availability = NULL` тоже трактуется как "доступно" по ADR-0005, но
явно указанное недостаточное `availability` по-прежнему исключает пару).

На **сегодняшних** реальных данных это не занижает результат: по ADR-0005
все 769 строк `Price.availability`, импортированных из реального прайса,
— `NULL`, что и в реальном солвере, и в этой симуляции трактуется
одинаково ("доступно", пара не исключается). Совпадение оценки с реальным
поведением солвера сейчас не случайно, но и не структурно гарантировано:
это верно только пока `availability` остаётся `NULL` у всех цен. ADR-0005
явно оставляет "postfactum-корректировку" и обновление `availability`
после ответа поставщика на ордер вне объёма, но не исключает, что
`availability` начнёт заполняться реальными числами в будущем (например,
после интеграции с ответом на ордер) — с этого момента часть пар `(m, s)`,
засчитанных здесь как "общий поставщик есть", может перестать быть
допустимой из-за нехватки, что может только **сокращать** пересечение
поставщиков по подмножеству, никогда не расширять его.

**Практический вывод: приведённые проценты (23% / 7% / 21% / 60% / 87%) —
консервативная (оптимистичная) нижняя граница реального риска
infeasible при гипотетическом hard-ограничении, не верхняя.** Настоящая
частота при жёстком ограничении может быть выше, если/когда
`availability` начнёт отражать реальные остатки. Это не меняет выбор в
п.2 (soft вместо hard) — при soft-ограничении данные `availability`
вообще не создают риска infeasible тем же путём (см. п.3), так что более
высокая настоящая частота конфликтов по availability только усиливает, а
не ослабляет обоснование выбора soft. Если бы вместо soft рассматривалось
hard-ограничение, эту границу следовало бы считать поводом для
дополнительной осторожности, а не финальной цифрой.

## Решение

### 1. Формализация ограничения в CP-SAT

**[Исправлено при реализации — см. блок "Статус" вверху документа.]** Ниже —
исходный текст раздела с заменой hard-равенства на использованный на практике
soft-механизм: там, где исходная формулировка писала `model.add(x[m*][s] ==
x[m][s])` / `model.add(x[m*][s] == 0)` как ограничение, реально добавляемое в
модель, в реализации вместо этого добавляются только неравенства
`diff[C][m] >= ...` (см. §2), без какого-либо `model.add(... == ...)` над
`x`. Причина — буквальные hard-равенства делают всю подсекцию противоречащей
§2/§3 (soft-режим, гарантия "не может стать infeasible") и ключевому тесту
"ни один поставщик не покрывает всю категорию → OPTIMAL/FEASIBLE, не
INFEASIBLE": сценарий "материал A есть только у поставщика 1, материал B той
же категории есть только у поставщика 2" при буквальном `model.add(x[m*][s]
== 0)` даёт `INFEASIBLE`, что и было воспроизведено тестом при реализации.

Выбор: **прямая линковка `x[m1][s] == x[m2][s]` для всех пар материалов
одной строгой категории внутри проекта**, без явной переменной `y[C][s]`
— **эта формула сама по себе не реализована как hard-ограничение**; вместо
`model.add(x[m1][s] == x[m2][s])` в коде — только `diff[C][m]` и его
неравенства (§2), которые математически поощряют, но не требуют этого
равенства. Обоснование выбора именно этой формы выражения зависимости (через
диагональ пар материал–поставщик одной категории), а не `y[C][s]` +
`x[m][s] == y[C][s]`, остаётся в силе независимо от hard/soft:

- Переменная `y[C][s]` добавляет `|C ∩ M_solvable| × |S|` новых бинарных
  переменных и `2 × |C ∩ M_solvable| × |S|` новых ограничений (равенство в
  обе стороны для каждой пары материал–поставщик внутри категории), не
  давая ничего, что нельзя выразить проще: `y[C][s]` в этой задаче
  используется только внутри самой категории, не входит ни в целевую
  функцию, ни в другие ограничения (в отличие от `y[s]` из ADR-0002,
  которая используется в Ограничении 3, Ограничении 4 и линеаризации
  доставки — там `y[s]` оправдана, потому что несёт нагрузку в нескольких
  местах модели). Вводить переменную ради ограничения, которое она сама же
  и описывает, — лишний слой косвенности без выигрыша.
- Прямая линковка для категории `C` с материалами `{m_1, ..., m_k}` в
  проекте выражается через `k − 1` **пар неравенств** per категория per
  проект (не равенств — см. корректировку в начале раздела): для каждого
  `i = 2..k` и каждого допустимого `s` (там, где хотя бы одна из двух
  переменных существует в модели — см. ниже про частичные пары),
  `diff_i[s] >= x[m_1][s] − x[m_i][s]` и `diff_i[s] >= x[m_i][s] − x[m_1][s]`
  (это и есть `diff[C][m]` из §2 — раздел §1 фиксирует только *какую пару
  материал–поставщик линковать*, сама механика неравенств формализована
  в §2, чтобы не дублировать формулу дважды). Поскольку `Σ_s x[m][s] = 1`
  (Ограничение 1) уже гарантирует, что ровно один `x[m][s] = 1` на материал,
  `diff_i[s] = 0` для всех `s` эквивалентно "оба материала назначены одному
  и тому же поставщику" — то есть штраф `category_split_penalty × Σ diff`
  (§2) поощряет именно это состояние, не требует его. Линковка — не
  привязана к цепочке `m_1`, можно линковать через любой опорный материал
  категории (например, первый по сортировке `material_id` внутри категории
  — транзитивность делает выбор опорного элемента произвольным и не
  влияющим на решение).
- **Асимметрия допустимых пар требует явной обработки.** Если материал
  `m_i` строгой категории не имеет допустимой пары `(m_i, s)` у конкретного
  `s` (нет цены или `availability < qty`), а материал `m_1` той же
  категории у этого `s` — имеет, переменной `x[(m_i, s)]` в модели попросту
  нет (ADR-0002, Ограничение 2 — недопустимые пары исключаются из модели,
  не запрещаются равенством нулю). В этом случае неравенство
  `diff_i[s] >= x[m_1][s] − x[m_i][s]` не может быть написано буквально —
  переменной справа не существует; отсутствующая переменная трактуется как
  константа `0` в этой позиции (см. §2), то есть неравенство сводится к
  `diff_i[s] >= x[m_1][s]`. Это **не** запрещает `m_1` назначаться этому
  `s` — лишь гарантирует, что такое назначение засчитывается как разброс
  категории (`diff_i[s] = 1`) и штрафуется в целевой функции наравне с
  любым другим разбросом. Иными словами, бизнес-намерение "весь набор — одному
  поставщику" здесь реализовано мягко: поставщик, не закрывающий один
  материал категории, не исключается автоматически из рассмотрения для
  остальных материалов категории, а лишь становится финансово менее
  привлекательным для них через штраф — окончательный выбор солвер делает
  по сумме цены, доставки и штрафа, не по жёсткому запрету.
- `y[C][s]`-подход дал бы аналогичную механику (штраф/неравенства через
  дополнительный слой переменных вместо прямых пар `diff_i[s]`), не проще,
  просто по-другому написана та же зависимость. Асимметричный случай
  (отсутствующая пара) моделируется в обоих подходах одинаково — отсутствие
  переменной трактуется как константа `0` в соответствующей формуле, без
  введения фиктивной переменной специально под это.

Формально для проекта с материалами `M`, строгой категорией `C` и
`M_C = M ∩ C ∩ M_solvable` (материалы категории `C`, дошедшие до модели
после стандартной предобработки orphaned-материалов ADR-0002):

```
Если |M_C| ≤ 1: линковка не добавляется (нечего линковать — один
материал категории или её отсутствие в проекте тривиально удовлетворяет
"все материалы категории у одного поставщика", штраф не может возникнуть).

Иначе, выбрать произвольный опорный материал m* ∈ M_C (например,
min по material_id — детерминированный выбор, не влияет на результат
благодаря симметрии неравенств и Ограничения 1):

для каждого m ∈ M_C \ {m*} завести diff[C][m] ∈ {0, 1}, и для каждого
s ∈ S_project (все поставщики, имеющие хотя бы одну цену на любой материал
этого проекта):
    если (m*, s) ∈ x и (m, s) ∈ x:
        model.add(diff[C][m] >= x[(m*, s)] - x[(m, s)])
        model.add(diff[C][m] >= x[(m, s)] - x[(m*, s)])
    иначе если (m*, s) ∈ x и (m, s) ∉ x:
        model.add(diff[C][m] >= x[(m*, s)])  -- отсутствующая x[(m, s)]
                                               трактуется как константа 0
    иначе если (m*, s) ∉ x и (m, s) ∈ x:
        model.add(diff[C][m] >= x[(m, s)])   -- симметрично, x[(m*, s)] = 0
    иначе (обе не существуют): ничего не добавлять — вклад в diff[C][m]
        по этому s равен 0 константой, обоим и так запрещено назначение
        этому s самим построением модели.
```

**Никакого `model.add(... == ...)` над переменными `x` здесь нет** —
единственные ограничения, которые линковка строгой категории добавляет в
модель, это неравенства `diff[C][m] >= ...` выше. Это принципиально: если бы
вместо неравенств стояло `model.add(x[(m*, s)] == 0)` (как в исходной,
неисправленной редакции этого раздела — см. блок "Статус"), назначение
`x[(m*, s)] = 1` стало бы структурно невозможным для солвера, и в сценарии,
где `m*` имеет цену только у `s`, вся модель ушла бы в `INFEASIBLE`
(нарушив Ограничение 1 — `Σ_s x[m*][s] = 1` не из чего удовлетворить). Именно
это и означает "мягко" в §2/§3: солвер физически волен оставить `diff[C][m]
= 1` (разброс), заплатив штраф, а не обязан искать другое назначение под
угрозой infeasibility.

Реализация проще выразить кодом напрямую (перебор существующих ключей
словаря `x`), чем явной таблицей случаев — три ветки выше эквивалентны
"добавить неравенство относительно того, что существует, трактуя
отсутствующее как 0", без дополнительной семантики.

### 2. Жёсткое ограничение или мягкое — **выбрано мягкое: штраф в целевой функции**

Формулировка с созвона ("должно быть у одного поставщика") звучит как
требование, но эмпирическая проверка каталога (раздел "Контекст" выше)
показывает, что жёсткое ограничение на реальных данных резко увеличивает
риск `infeasible`: симуляция даёт 60% для `Mesh` и 87% для `Roof panels`
на случайных 2–5-позиционных наборах, при том что ни один поставщик не
закрывает полный каталог ни одной строгой категории. Это не крайний
случай — это типичное поведение при текущем составе каталога и текущем
числе поставщиков (7).

**Решение: мягкое ограничение — штраф за разброс поставщиков внутри
строгой категории проекта, не запрет.** Обоснование:

- Жёсткое ограничение превратило бы "визуальная согласованность —
  желательное свойство результата" в "система массово отказывается
  считать закупку" для категорий, где реальный каталог этого не
  выдерживает (`Mesh`, `Roof panels` — и в меньшей степени `Doors`,
  `Profil`). Компания в самом начале использования реальных прайсов уже
  один раз наступила на похожую проблему (ADR-0005 — `availability = NULL`
  трактовалось как "недостаточно" и заблокировало *весь* первый реальный
  проект). Повторение того же класса ошибки — "формально корректное чтение
  правила ломает систему на реальных данных" — с новым ограничением
  вместо старого было бы неоправданным риском, тем более что задача прямо
  просит оценить именно этот риск перед выбором.
- У штрафа при этом остаётся тот же практический эффект в подавляющем
  большинстве случаев: если хотя бы один поставщик закрывает всю
  выбранную подгруппу категории *и* остаётся конкурентным по цене+доставке
  — солвер его и выберет, штраф просто делает это математически выгодным,
  а не потому что альтернатива запрещена. Разница проявляется только в
  том явном меньшинстве случаев, где категория физически не собирается у
  одного поставщика (или собирается по неприемлемо завышенной цене) —
  тогда жёсткое ограничение вернуло бы `infeasible` без альтернативы,
  а мягкое — рабочий (разбитый) результат с явным предупреждением на
  экране (см. п.3 ниже, симметрично философии override ADR-0006:
  "предупреждение, не блокировка").
- Возражение "а что если бизнес действительно имел в виду hard-constraint,
  ценовая экономия неважна против визуального брака" — учтено выбором
  **величины штрафа**, не выбором hard/soft как такового: штраф
  калибруется достаточно высоким, чтобы солвер предпочитал единого
  поставщика категории почти всегда, когда цена не расходится драматически
  (см. формулу и масштаб ниже), сохраняя при этом solvability как
  структурное свойство модели.

#### Формула штрафа

Обозначим `split_count[C]` для строгой категории `C` в проекте — число
**дополнительных** поставщиков сверх одного, обслуживающих материалы этой
категории в проекте (0, если все материалы `C` попали к одному поставщику
или категория отсутствует/представлена одним материалом; иначе
`(число различных s среди назначенных M_C) − 1`).

Прямое выражение `split_count[C]` через `x[m][s]` в ILP требует счётной
переменной "число различных поставщиков среди набора" — не тривиально в
CP-SAT напрямую (это по сути считать `|{s : ∃m ∈ M_C, x[m][s]=1}|`).
Вместо этого штраф выражается через **попарное несовпадение** назначений
внутри категории — эквивалентно по цели (наказывать разброс), линейно по
построению, не требует вспомогательной "count distinct" конструкции:

```
Для каждой строгой категории C с |M_C| ≥ 2 в проекте, выбрать тот же
опорный материал m* ∈ M_C, что и в п.1. Для каждого m ∈ M_C \ {m*} и
каждого s, где определены обе переменные x[(m*, s)] и x[(m, s)]:

    mismatch[C][m] = 1 - x[(m*, s_m)] * x[(m, s_m)]  -- где s_m конкретный
    назначенный поставщик m — но это нелинейно (произведение переменных).

Линейный эквивалент через вспомогательную бинарную diff[C][m]:

    diff[C][m] ∈ {0, 1}
    для каждого s (где определена хотя бы одна из двух переменных):
        diff[C][m] >= x[(m*, s)] - x[(m, s)]   (или 0, если одна из
                                                 переменных не существует —
                                                 тогда несуществующая
                                                 трактуется как константа 0
                                                 в правой/левой части)
        diff[C][m] >= x[(m, s)] - x[(m*, s)]
    -- то есть diff[C][m] = 1, если m* и m назначены разным поставщикам
    (в терминах индикаторных переменных: diff = |x[m*] - x[m]| в смысле
    "вектор назначения различается хотя бы по одной координате s", что при
    Σ_s x[m][s] = 1 корректно эквивалентно "разные поставщики").
```

Целевая функция ADR-0002 расширяется дополнительным линейным слагаемым:

```
min  Σ_m Σ_s x[m][s] × price[m][s] × qty[m]      (как в ADR-0002)
   + Σ_s flat_fee[s] × z[s]                       (как в ADR-0002)
   + Σ_C∈STRICT  category_split_penalty × Σ_{m ∈ M_C \ {m*_C}} diff[C][m]
```

**Масштаб штрафа `category_split_penalty`.** Требование — штраф должен
быть достаточно велик, чтобы разбиение категории между поставщиками
происходило только тогда, когда альтернатива (единый поставщик) стоит
заметно дороже, но не настолько велик, чтобы фактически имитировать
hard-constraint (в этом случае разница между "мягкое" и "жёсткое" исчезла
бы, и весь смысл выбора soft — сохранить solvability — терялся бы при
любой сколько-нибудь значимой ценовой разнице).

Предлагается калибровать `category_split_penalty` относительно
характерного масштаба самой задачи, не как абсолютную константу: например,
`category_split_penalty = k × avg(flat_fee[s] по всем поставщикам
проекта)`, с `k` в диапазоне 3–5 — то есть разбить категорию по цене
эквивалентно "не сэкономленной доставке в 3–5 раз больше типичной ставки
доставки". Обоснование именно доставки как единицы масштаба: доставка —
уже существующая в модели величина того же порядка, что и "стоимость
неоптимальности одного решения" (десятки–низкие сотни долларов на
поставщика по `flat_fee`), в отличие от `price[m][s] × qty[m]`, который
варьируется на порядки в зависимости от материала и легко даёт штраф,
либо тривиально доминирующий над всей ценовой частью целевой функции
(эффективно hard-constraint), либо пренебрежимо малый (штраф без эффекта)
— обе крайности одинаково нежелательны здесь.

Точное значение `k` — предмет калибровки на реальных прогонах после
первой реализации (сравнить, для какой доли реальных проектов штраф
реально меняет решение против simple-minimum-cost без штрафа), не
фиксируется здесь как финальное число — но факт "штраф выражен через
`flat_fee`, а не через абсолютную сумму в долларах и не через долю от
`price`" фиксируется как архитектурное решение этого ADR, чтобы штраф
масштабировался вместе с ценами каталога, а не требовал ручной
перекалибровки при добавлении новых поставщиков с другим порядком цен.

**Если после реализации и наблюдения на реальных прогонах выяснится, что
штраф систематически недостаточен** (пользователи регулярно видят
разбитые категории там, где ожидали единого поставщика) **или
систематически избыточен** (эффективно блокирует любую экономию) — это
повод для калибровки константы `k`, не для пересмотра самого механизма
(soft-constraint через линейный штраф) — если не подтвердится опытным
путём, что бизнесу нужен именно hard-запрет, тогда это будет новый ADR,
меняющий фундаментальный выбор этого документа, с реальными данными по
частоте конфликтов за плечами (тот же паттерн "отложено до реальных
данных", что уже применён в ADR-0003 к атрибуции min-order-инфизибельности).

### 3. Infeasible из-за категорийного ограничения — атрибуция не нужна (при выбранном soft-подходе вопрос снимается почти полностью)

При soft-реализации (п.2) категорийное ограничение **не может** самостоятельно
сделать модель infeasible: `diff[C][m]` — обычная бинарная переменная без
принудительного `= 0`, штраф в целевой функции никогда не создаёт
противоречия ограничений (в отличие от Ограничения 4 ADR-0002/ADR-0003,
которое действительно может конфликтовать с Ограничением 1). Модель может
остаться infeasible по тем же причинам, что и до этого ADR (orphaned
materials, конфликт `per_order_min_amount`) — категорийная группировка
такой причиной больше не является.

Это отвечает на вопрос из задачи практически: **дополнительная атрибуция
"проблема в категории Doors" не нужна**, потому что новый класс
infeasible-случаев, который стоило бы атрибутировать, при выбранном
решении не создаётся. Существующий общий `status: "infeasible"` без
атрибуции причины (ADR-0003) продолжает покрывать все случаи как раньше;
ADR-0003 "Не в объёме" (атрибуция min-order-конфликта) по-прежнему не
переоткрывается этим документом, как и указано в задаче.

Если бы вместо этого было выбрано hard-ограничение (отклонённая в п.2
альтернатива) — атрибуция была бы явно необходима, и веским аргументом
против hard-варианта был бы именно риск повторить нерешённую сложность
ADR-0003 (эвристика "убрать материал и пересчитать" не гарантированно
сходится за один шаг для min-order; для категорийного конфликта она
качественно так же сложна — "какой из k материалов категории убрать,
чтобы разрешить конфликт" не имеет единственного естественного ответа).
Выбор soft устраняет этот вопрос архитектурно, а не оставляет его
отложенным, как в ADR-0003, — это дополнительный (не единственный, но
значимый) аргумент в пользу soft-решения из п.2.

### 4. Взаимодействие с override (ADR-0006) — разрешено с предупреждением, не блокируется

Override отдельной строки `AllocationLine` внутри строгой категории —
**разрешён**, с новым явным предупреждением на затронутых строках, по той
же философии, что уже применена в ADR-0006 к `below_min_order`:
"система не обладает полным контекстом, чтобы решать за человека" —
сотрудник отдела закупок может знать то, чего нет в модели (например, что
цветовое рассогласование в этом конкретном случае не критично, потому что
материал скрыт, или что нужно сохранить прежнего поставщика по
внедоговорной причине).

**Отклонено: блокировать override, если он разбивает строгую категорию.**
Отклонено по той же причине, что ADR-0006 уже отклонил блокировку override
по недостаточному availability (Ограничение 2 ADR-0002) — там прямая
цитата обоснования переносится сюда без изменений по существу: жёсткая
блокировка вернула бы пользователя к обходу через прямое изменение данных
в БД, что хуже явного предупреждения, и противоречила бы уже
установленному в проекте принципу для этой границы (override как
исключение из автоматики, а не второй солвер с собственными жёсткими
правилами).

Механизм обнаружения для UI: при рендере строк `AllocationLine` строгой
категории клиент (или backend в ответе — как и `below_min_order`, деньги/
статусные поля должны считаться на backend по CLAUDE.md принципу 4, но сам
факт "разные поставщики внутри одной строгой категории проекта" не
денежный расчёт, а сравнение UUID) вычисляет: для каждой строгой категории
`C`, присутствующей в проекте, — есть ли более одного различного
`supplier_id` среди строк с `material.category == C`. Если да — на **каждой**
такой строке (не только на той, что стала override) показывается
предупреждение: `"Категория {C} разбита между {N} поставщиками:
{список коротких имён}"`, в стиле, аналогичном `belowMinOrderNotice`
(ADR-0006 п.4: отдельная текстовая строка, не бейдж внутри уже плотного
хедера) — конкретное CSS-размещение (карточка поставщика vs. строка
материала) решается на этапе UI-реализации по аналогии с существующими
паттернами `docs/ui-reference.md`, не фиксируется здесь как архитектурное
решение (в отличие от ADR-0006 п.4, где именно *отсутствие числового
контекста* в альтернативах было конкретной причиной архитектурного
выбора — здесь такой конфликт компоновки не установлен, поэтому решение
оставляется реализации).

Важное отличие от `below_min_order` (ADR-0006): `below_min_order` — свойство
одного поставщика (числовой порог, пересчитываемый локально), а разбитая
категория — свойство *набора строк* нескольких материалов, потенциально
разных поставщиков одновременно. Предупреждение поэтому не может жить
только в `SupplierAllocationSummaryOut` одного поставщика — нужен признак
на уровне `AllocationLine` (или отдельное поле уровня `AllocationRun`,
например `split_categories: list[str]` — категории, фактически оказавшиеся
разбитыми в текущем состоянии строк после всех override). Второе (уровень
`AllocationRun`) предпочтительно: вычисляется один раз при каждом
изменении состояния строк (после `run_allocation` и после каждого
`override_allocation_line_supplier`), не требует дублирования признака на
каждой строке категории, и симметрично тому, как `orphaned_materials`
уже живёт на уровне `AllocationRun`, а не размазано по строкам.

### 5. Влияние на целевую функцию и консолидацию доставки — подтверждено явно

Целевая функция ADR-0002 **не заменяется**, только расширяется одним
дополнительным слагаемым (штраф за разброс категории, см. формулу в п.2):

```
min  [цена, как в ADR-0002]
   + [доставка z[s] × flat_fee[s], как в ADR-0002]
   + [новое: Σ_C category_split_penalty × Σ_m diff[C][m]]
```

Первые два слагаемых и вся их внутренняя механика (big-M linking для
`free[s]`, линеаризация `z[s] = y[s] × (1 − free[s])`, Ограничения 1–4)
остаются буквально без изменений — ADR-0002 не переоткрывается и не
переформулируется, этот ADR **добавляет новый слой ограничений и
слагаемое штрафа поверх** уже существующей модели, не трогая её
структуру. Консолидация доставки (несколько материалов у одного
поставщика → возможен `free[s] = 1`) продолжает действовать в точности
как раньше: новое ограничение из п.1 при этом даже может *усиливать*
естественную консолидацию — раз материалы строгой категории теперь чаще
оказываются у одного поставщика не только благодаря цене, но и благодаря
штрафу, это увеличивает шанс совместно перейти порог бесплатной доставки
у этого поставщика, что уже учитывается существующей механикой `free[s]`
без каких-либо изменений в ней.

Единственное новое взаимодействие, которое стоит явно отметить: штраф за
разброс категории и стоимость доставки теперь **оба** подталкивают решение
к консолидации у одного поставщика, но по независимым причинам (визуальная
согласованность vs. экономия на flat fee) — они складываются аддитивно в
целевой функции, не конфликтуют и не требуют относительной приоритизации
между собой, потому что оба — это просто отдельные слагаемые одной суммы,
которую солвер минимизирует целиком.

## Альтернативы

**Жёсткое ограничение (`y[C][s]` или прямая линковка без штрафа, с полным
запретом разброса)** — рассмотрено и отклонено в п.2 на основании
эмпирической проверки каталога: 0 поставщиков закрывают полный каталог
любой строгой категории, симулированный риск infeasible на реалистичных
подмножествах BOM — 60–87% для `Mesh`/`Roof panels`, ~20% для
`Doors`/`Profil`. Технически проще (не требует калибровки штрафа), но
класс риска "формально верное правило ломает систему на реальных данных"
уже случался в проекте (ADR-0005) и прямо предвиден в самой формулировке
задачи для разбора.

**`y[C][s]` с явной переменной вместо прямой линковки `x[m1][s] ==
x[m2][s]`** — рассмотрено в п.1, отклонено как менее эффективная запись
той же семантики без дополнительной пользы (переменная не используется
больше нигде в модели, в отличие от `y[s]`).

**Штраф как множитель к цене (`price × category_split_multiplier`)
вместо аддитивной константы через `flat_fee`.** Не выбрано — мультипликативный
штраф на цену масштабируется вместе с размером заказа, что означает: для
большого дорогого проекта разброс категории наказывается сильнее в
абсолютных долларах, чем для маленького — нет причины считать, что
визуальная проблема (несовпадение оттенка) серьёзнее пропорционально
бюджету проекта. Аддитивный штраф через `flat_fee` даёт постоянную "цену
разброса" независимо от масштаба заказа, что ближе к природе самой
проблемы (визуальный дефект — бинарное свойство объекта, не
пропорциональное его стоимости).

**Атрибуция причины infeasible для категорийного конфликта (Option A по
аналогии с ADR-0003)** — рассмотрено в п.3, отклонено как ненужное при
выбранном soft-решении (проблема не создаёт новый infeasible-путь). Если
бы был выбран hard-constraint, эта альтернатива стала бы обязательной
частью решения, а не отдельным вопросом — сохранено здесь как явная
развилка, зависящая от решения по п.2, а не забыто.

**Блокировка override внутри разбитой категории** — рассмотрено в п.4,
отклонено по прецеденту ADR-0006 (жёсткая блокировка override по
availability уже отклонена по тому же классу обоснования).

## Не в объёме

- Изменение набора строгих/нестрогих категорий (создание новых, слияние,
  переименование `Doors`/`Gutter`/`Profil`/`Mesh`/`Roof panels`/
  `Connectors`/`Screws`/`Caulk`) — работа только с уже существующими в
  данных категориями, зафиксированными в разделе "Проверка `Material.category`
  на реальных данных" выше.
- Автоматическая атрибуция причины infeasible для существующего
  min-order-конфликта (ADR-0003, "Не в объёме" того документа) —
  не переоткрывается.
- Точное численное значение коэффициента `k` в `category_split_penalty =
  k × avg(flat_fee)` — предмет калибровки после первой реализации на
  реальных прогонах, не фиксируется как финальное решение здесь (см. п.2).
- Конкретная UI-разметка предупреждения о разбитой категории (расположение,
  CSS-класс) — решается на этапе реализации по аналогии с
  `docs/ui-reference.md`, не проектируется здесь в деталях, в отличие от
  `below_min_order` в ADR-0006 п.4, где конкретная компоновка была
  архитектурно обоснована необходимостью показать число.
- Что делать с материалом, у которого `category IS NULL` или значение вне
  восьми известных (сейчас такого нет в реальных данных, см. проверку выше)
  — если появится, по умолчанию трактуется как нестрогая категория (не
  участвует в группировке ни по каким переменным этого ADR), но это должно
  быть явно решено (не молча) при первом реальном появлении такого случая,
  аналогично тому, как ADR-0003 указывает условие возврата к отложенному
  вопросу.

## Последствия

- `backend/app/allocation/solver.py` — новый набор ограничений (п.1) и
  дополнительное слагаемое в целевой функции (п.2), константа
  `STRICT_CATEGORIES` и `category_split_penalty` (или функция её расчёта
  от `flat_fee`) добавляются в модуль allocation (`solver.py` или
  `service.py` — конкретное место решается на реализации).
- `AllocationInput`/`MaterialInput` (`backend/app/allocation/types.py`) —
  `MaterialInput` должен нести `category` (сейчас только `material_id`,
  `quantity`) — солвер сегодня не знает категорию материала вообще, это
  меняет данные, которые `service.py` передаёт в `solve_allocation`.
- `algorithm_version` (`backend/app/allocation/service.py:19`, сейчас
  `"adr-0005-v1"`) должен быть забампан — это прямо тот случай, который
  ADR-0002 "Последствия" предвидел явно: "если модель ограничений
  изменится... это будет новый ADR и новая версия алгоритма, а не
  молчаливое изменение".
- `AllocationRun` — новое поле `split_categories: list[str]` (см. п.4) для
  атрибуции разбитых категорий после override, аналогично
  `orphaned_materials`/`supplier_summaries` (JSON-поле, не отдельная
  таблица — та же логика, что уже применена ADR-0002 к
  `orphaned_materials`: чисто информационно для UI, не участвует в
  дальнейших расчётах). Пересчитывается и в `run_allocation` (сразу после
  солвера), и в `override_allocation_line_supplier` (после каждого PATCH),
  симметрично тому, как уже пересчитываются `supplier_summaries` в
  ADR-0006 п.4.
- `docs/ui-reference.md` — новый раздел: предупреждение о разбитой строгой
  категории (текст, условие показа, на каких строках) по аналогии с уже
  описанным `below_min_order`.
- `docs/architecture.md`/`docs/data-model.md` — отметить новое поле
  `AllocationRun.split_categories`, по образцу того, как уже отмечены
  `status`/`orphaned_materials` (ADR-0002/ADR-0003).
- Тесты (обязательны по CLAUDE.md для ILP allocation engine edge cases):
  - `backend/tests/allocation/test_solver.py` — новые кейсы: (a) все
    материалы строгой категории у одного поставщика при прочих равных —
    не должно быть неожиданного разброса; (b) один поставщик дешевле на
    один материал категории, но дороже в сумме по всей категории — солвер
    должен предпочесть единого поставщика при разумном штрафе, дать разброс
    только при достаточно большой ценовой разнице (параметризовать штрафом);
    (c) ни один поставщик не покрывает всю категорию проекта — soft-режим
    должен вернуть `OPTIMAL`/`FEASIBLE` с разбросом и непустым
    `split_categories`, не `INFEASIBLE`; (d) нестрогая категория
    (`Connectors`/`Screws`/`Caulk`) с материалами у разных поставщиков — не
    должна давать предупреждение/штраф вообще, поведение идентично коду до
    этого ADR.
  - `backend/tests/allocation/test_service.py` — `split_categories`
    появляется на `AllocationRun` после `run_allocation` и корректно
    пересчитывается после `override_allocation_line_supplier`
    (`test_override.py` — новый кейс: override строки категории `Doors` на
    другого поставщика при исходно едином поставщике → `split_categories ==
    ["Doors"]`, предупреждение появляется на всех строках `Doors` этого
    проекта, не только на переопределённой).
  - Тест на константу `STRICT_CATEGORIES` буквально ловящий регресс, если
    список категорий в коде разойдётся со значениями в реальном каталоге
    (например, snapshot-тест над `xlsx_price_matrix.CATEGORY_SKU_PREFIX`
    keys ⊇ `STRICT_CATEGORIES` — эти два списка сейчас совпадают не
    случайно, но ничто в коде их не связывает явно; тест фиксирует
    инвариант, а не полагается на совпадение).
- Реализация (сам код ограничений/штрафа в `solver.py`, миграция для
  `split_categories`, UI-предупреждение) — предмет отдельной задачи после
  вычитки этого ADR, как и для ADR-0002/ADR-0006.
