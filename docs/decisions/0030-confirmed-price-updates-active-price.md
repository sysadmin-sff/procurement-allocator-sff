# ADR-0030: `confirmed_price` предлагает обновить активную `Price` — узкое исключение из admin-only (ADR-0024 §4)

Статус: Предложено

## Контекст

ADR-0007 §5 явно отложила связку "расхождение `confirmed_price` ↔ `Price`"
до появления данных о том, как реально происходят расхождения — не
проектировать вслепую. Реальный созвон с руководством и сотрудником отдела
закупок (контекст задачи) вскрыл ровно тот сценарий, которого не хватало для
проектирования: систематическое устаревание цены в БД ("прошёл месяц, он мне
вообще ничего не отправил") — не единичные опечатки, а рутинный дрейф между
тем, что зафиксировано в `Price`, и тем, что реально согласовано с
поставщиком по факту заказа. Это ADR **снимает** отсрочку ADR-0007 §5,
реализует именно то, что тогда было явно намечено как решение по умолчанию
для будущего ADR ("окно подтверждения"), не пересматривает саму отсрочку
задним числом.

Второй прецедент, который это решение обязано соблюдать без исключений —
ADR-0024 §4: `price.py` (`/prices/**`) целиком `require_role("admin")`,
обоснование — "прямая правка боевых цен в обход ревью-флоу — самое
чувствительное CRUD в системе". Это правило **не переоткрывается**. Задача
явно поставлена как узкое, обоснованное исключение — не общее ослабление
admin-only для `Price`.

Что уже есть в схеме и коде, что этот ADR обязан переиспользовать, не
изобретать заново:

- **`OrderItem.confirmed_price`/`confirmed_at`** (ADR-0007 §1) — финальная
  договорённая цена, отдельно от `received_price` (ADR-0013, первый ответ
  поставщика до торга) и `target_price` (ADR-0027, наше намерение на торг).
  Только `confirmed_price` относится к этому ADR — см. п.1.
- **`set_order_item_fields`** (`backend/app/allocation/order_service.py:588`)
  — единственная точка записи полей `OrderItem`, `_UNSET`-паттерн,
  вызывается и из ручного PATCH (ADR-0007 §3), и из второго раунда
  ИИ-парсинга (ADR-0027 §2, тот же `handleApplyAllMatched`, параметризованный
  целевым полем). Оба источника `confirmed_price` проходят через эту одну
  функцию — см. п.2 про то, почему это важно для единой точки обнаружения
  расхождения.
- **Версионирование `Price`** (`backend/app/api/price.py:83`,
  `update_price`) — закрывает текущую активную строку
  (`valid_to = today()`), создаёт новую с `valid_from` = сегодня. `Price`
  неизменяем по докстрингу модели: обновление всегда версия, никогда
  `UPDATE` на месте.
- **Аудит-колонки `created_by_user_id`** на `Order`/`PurchaseRecord`,
  `overridden_by_user_id` на `AllocationLine` (ADR-0024 §6) — прецедент
  "кто инициировал операцию с деньгами", см. п.6.

Не в объёме (см. постановку задачи):
- Изменение permission-модели `/prices/*` в целом — роутер `price.py`
  остаётся `require_role("admin")` без изменений, ни один endpoint этого
  роутера не получает новый доступ.
- Автоматическое (без подтверждения) обновление `Price` — вся суть фичи в
  явном подтверждении, не в автоматизме; отклонено явно, не по умолчанию.
- Обновление `Price` из `received_price`/`target_price` — торг ещё не
  закончен, обновлять боевую цену на основании непроторгованного значения
  преждевременно (см. п.1).

## Решение

### 1. Триггер — только `confirmed_price`, не `received_price`/`target_price`

Окно подтверждения появляется **исключительно** при записи
`OrderItem.confirmed_price`, отличной от текущей активной `Price` для пары
(`material_id`, `order.supplier_id`). `received_price` (ADR-0013) и
`target_price` (ADR-0027) не участвуют в этом механизме вообще — ни как
триггер, ни как значение, которое может попасть в `Price`.

**Обоснование, явно завязанное на семантику полей (ADR-0013 п.1, ADR-0027
п.1), не произвольный выбор.** `received_price` — то, что поставщик прислал
**первым**, до какого-либо торга; предмет входных данных для решения, не
само решение. `target_price` — наше собственное намерение, ещё не факт от
поставщика вообще. Обновлять боевую цену на основании любого из двух
означало бы записывать в `Price` цену, которая либо ещё будет
пересматриваться в разговоре с поставщиком, либо не исходит от поставщика
вовсе. `confirmed_price` — единственное поле тройки, означающее "на чём
реально сошлись" (ADR-0013 "Контекст", п.1) — это ровно тот факт, который
`Price` призвана отражать: действующая, согласованная цена материала у
поставщика.

### 2. Обнаружение расхождения — три случая, точка обнаружения

Сравнение выполняется в `set_order_item_fields` сразу после записи
`confirmed_price` (единственная точка входа для всех источников — ручной
PATCH ADR-0007 §3 и второй раунд ИИ-парсинга ADR-0027 §2 уже проходят через
неё, см. "Контекст"), не в API-слое отдельно для каждого источника — иначе
пришлось бы дублировать проверку в двух местах и рисковать тем, что один из
источников впоследствии её обойдёт.

Запрос активной цены — тот же `_active_price_query`-паттерн, что уже
использует `price.py` (`material_id`, `supplier_id = order.supplier_id`,
`valid_to IS NULL`).

**Возвращаемый тип — `PriceDivergence`, dataclass в `order_service.py`,
не кортеж и не поле, довешенное на `OrderItem`.**

```python
@dataclass(frozen=True)
class PriceDivergence:
    """Результат сравнения новозаписанного confirmed_price с активной Price
    для (material_id, order.supplier_id) — см. ADR-0030 п.1/п.2. Возвращается
    set_order_item_fields только когда confirmed_price был среди переданных
    полей (_UNSET иначе не входит в сравнение) и попадает в случай (а) или
    (в); случай (б) (совпадение) и вызовы без confirmed_price в payload дают
    None, не PriceDivergence с action=None — отсутствие расхождения не
    нуждается в форме "результата", это и есть отсутствие результата."""

    action: Literal["update", "create"]
    """"update" — случай (а), активная Price есть и отличается.
    "create" — случай (в), активной Price для этой пары нет вообще."""
    order_item_id: uuid.UUID
    material_id: uuid.UUID
    supplier_id: uuid.UUID
    current_price: float | None
    """Цена активной Price на момент сравнения. None при action="create"
    (нет активной записи, сравнивать не с чем) — не 0, та же логика
    "нет базы для сравнения" (ADR-0007 п.1), что уже применена к
    price_delta."""
    confirmed_price: float
    """Значение, только что записанное в OrderItem.confirmed_price —
    предлагаемая новая цена Price. Не Optional: PriceDivergence не
    создаётся, если confirmed_price не был передан или был явно очищен
    (None) этим PATCH — очистка confirmed_price не может ничего
    "предложить" обновить."""
```

`set_order_item_fields` меняет сигнатуру возврата с `OrderItem` на
`tuple[OrderItem, PriceDivergence | None]` — второй элемент кортежа
результата самой функции (не кортеж вместо dataclass, см. заголовок этого
подпункта: кортеж здесь — только внешняя обвязка "два независимых
результата одного вызова", сам объект расхождения остаётся типизированным
dataclass, а не безымянным набором полей). Оба существующих вызывающих
(`patch_order_item`, batch-цикл ADR-0027 §2) обновляются под новую сигнатуру
как часть реализации этого ADR — оба уже проходят через эту функцию (см.
"Контекст"), это единственные два call site'а в кодовой базе на момент
написания.

- **(а) Активная цена есть, отличается от `confirmed_price`.** Предложить
  обновление — основной случай, ради которого это ADR существует.
- **(б) Активная цена есть, совпадает с `confirmed_price`.** Ничего не
  происходит, никакого предложения. Совпадение — не расхождение, попап
  здесь был бы шумом без содержания: цена в базе уже верна.
- **(в) Активной цены нет вообще для этой пары (`material_id`,
  `supplier_id`) — новое сочетание материал+поставщик.** **Предложить
  СОЗДАТЬ**, тем же экраном подтверждения, что и обновление (п.4), без
  отдельного UI-пути.

  Обоснование решения (в): отсутствие активной цены для пары, по которой
  сотрудник только что получил и подтвердил реальную цену от поставщика, —
  не менее ценный сигнал, чем расхождение с устаревшей ценой — это ровно та
  же проблема "постепенного устаревания/отсутствия данных", которую фича
  призвана решать (созвон: "прошёл месяц, он мне вообще ничего не
  отправил" — крайний случай этого же явления — цена не просто устарела,
  её вовсе нет для этой связки). Практический источник случая (в): `Order`
  может содержать позицию, которую переопределили на другого поставщика
  через find-replacement (ADR-0014/ADR-0015) — цена этого поставщика на
  момент подбора кандидата бралась из уже существующей активной `Price`
  (`find_replacement_candidates` фильтрует именно по `valid_to IS NULL`,
  `order_service.py:214-219`), поэтому случай (в) на практике реже
  относится к find-replacement и чаще — к материалам, добавленным в план
  вручную без предварительного прайса этого поставщика, либо к историческим
  Order, где `Price` была удалена (`DELETE /prices/{id}` допускает удаление
  только незакрытых записей, `price.py:135`, но не защищает от того, что
  единственная активная запись для пары была удалена по ошибке ранее). В
  обоих случаях предложение "создать" не хуже предложения "обновить" —
  семантически то же самое действие (записать новую активную `Price`),
  различается только тем, есть ли что закрывать (п.5).

### 3. Порог расхождения — любое численное отличие, без порога

**Решение: триггерит любое отличие `confirmed_price` от активной `Price`,
без минимального порога.** Не тот же `>10%`, что уже применён к
`price_delta` (ADR-0007 §4) для визуальной подсветки на `OrderDetailPage`, и
не заимствуется оттуда по аналогии.

**Обоснование, почему не тот же порог, а не умолчание.** `price_delta`
(ADR-0007 §4) отвечает на другой вопрос в другом контексте: "насколько
подтверждённая цена разошлась с тем, что *мы* заранее посчитали и
отправили" — сигнал внимания на экране, который сотрудник и так листает
построчно, где допустимо отфильтровать мелкий шум (округления, локальные
корректировки — обоснование ADR-0007 §4 явно называет эту причину для
выбора именно 10%, не более низкого числа). Здесь вопрос другой: "устарела
ли цена в справочнике *относительно факта, только что подтверждённого
поставщиком*" — у справочной цены нет "естественного шума" того же рода,
который оправдывал бы игнорирование мелких отличий: если поставщик только
что подтвердил $12.47, а в базе лежит $12.50, это те же самые 24 цента
устаревания, что и любые более крупные — только более медленно
накопившиеся. Цель фичи, явно сформулированная в контексте (борьба именно с
постепенным устареванием, не только с резкими скачками), означает, что
именно мелкие, накапливающиеся расхождения — целевой случай, а не шум,
который нужно отфильтровать. Порог `>10%` здесь работал бы против
собственной цели фичи: устаревание на 3-5% за счёт постепенного роста цен
поставщика месяц за месяцем осталось бы систематически невидимым для этого
конкретного механизма, хотя именно к нему и апеллирует созвон.

**Не вводится компромиссный собственный порог (например, `>0.5%` или
"тот же 10%, но другая константа") — граница ровно "любое отличие
(`!=`), исключая точное совпадение"**, потому что любой ненулевой порог
здесь произвольно определял бы "сколько устаревания достаточно, чтобы
беспокоиться", не имея под собой той же логики, что оправдывала 10% для
`price_delta` (частота ложных срабатываний от округлений на конкретном
заказе) — для сравнения с боевым справочником такой логики попросту нет:
любое отличие уже означает, что запись в `Price` не соответствует
последнему подтверждённому факту.

### 4. Batch-сценарий — единый экран пакетного подтверждения

**Критично, отдельный флоу от построчного PATCH.** "Применить все
совпадения" второго раунда ИИ-парсинга (ADR-0027 §2) вызывает
`set_order_item_fields` последовательно для 10-30 позиций через
`handleApplyAllMatched`. Триггерить попап на каждую отличающуюся позицию
внутри этого цикла — 10-30 модалок подряд, неприемлемо (прямо исключено
постановкой задачи).

**Решение: разделение обнаружения и подтверждения на два прохода.**

1. **Обнаружение остаётся в `set_order_item_fields`** (п.2) — та же
   единая точка, оба источника (ручной PATCH, batch-применение) проходят
   через неё одинаково. Функция **не показывает** попап сама — она
   возвращает признак расхождения (или его отсутствия) как часть
   результата операции, не решает, как это отображать. Это ответственность
   вызывающего кода (API-слоя/фронтенда), потому что "что показать" зависит
   от того, единичный это вызов или часть batch — то же разделение
   ответственности, что уже применено к `price_delta`/`received_price_delta`
   (вычисляются на backend, отображаются по-разному в разных местах
   фронтенда, ADR-0027 §3).

2. **Единичный PATCH** (ручное построчное редактирование,
   `OrderDetailPage`, ADR-0007 §3): если результат несёт признак
   расхождения (случай а или в из п.2) — один попап на эту одну позицию,
   сразу после сохранения. Симметрично существующему UX построчного
   редактирования (inline-ячейка, сохранение по `blur`/`Enter`) — попап
   появляется как естественное продолжение того же действия, не отдельный
   визит на другой экран.

3. **Batch-применение** (`handleApplyAllMatched` с `targetField:
   "confirmed_price"`, ADR-0027 §2): цикл записи по всем позициям
   выполняется как сейчас (без изменений в порядке/механике самого
   applied-цикла), но **вместо** немедленного попапа на каждой итерации —
   накопление списка расхождений (case а/в) по ходу цикла. После того как
   весь batch применён (все `confirmed_price` уже записаны на `OrderItem`
   — см. п.7, почему это не блокирует ввод), фронтенд показывает **один**
   экран пакетного подтверждения:

   - Список всех позиций этого конкретного batch-применения, где
     обнаружено расхождение (случай а) или отсутствие активной цены
     (случай в) — не всех позиций batch, только этих.
   - На каждой строке: материал, поставщик, текущая активная `Price.price`
     (или "нет активной цены" для случая в), новое `confirmed_price`,
     чекбокс.
   - **Чекбоксы по умолчанию не отмечены.** Обоснование: batch-применение
     уже совершает одно "довериться результату целиком" действие (ADR-0018
     §4 — "проверено и подтверждено одним действием после того, как
     сотрудник просмотрел все строки" — то же рассуждение уже применялось к
     самому применению `confirmed_price`). Второе, отдельное по природе
     решение — обновить боевой справочник цен, используемый *всеми
     будущими* allocation-расчётами по *всем* проектам, не только этим
     заказом — не должно наследовать тот же "довериться по умолчанию"
     режим: последствия ошибки здесь шире одного `Order` (неверная `Price`
     искажает будущие ILP-расчёты для любого проекта, где встретится эта
     пара материал/поставщик), поэтому явное включение каждой строки, а не
     явное исключение, — более безопасный default. Симметрично тому, как
     категория (c) "лишнее" в ADR-0018 §4 не входит в общую кнопку
     "Применить" именно потому, что это "качественно другое действие" —
     здесь то же качественное отличие (запись в справочник, не в сам
     `Order`) оправдывает более консервативный default чекбокса, чем
     "предзаполнено включённым".
   - Одна кнопка **"Обновить выбранные цены в базе"** — по нажатию
     вызывает п.5 (переиспользование `update_price`/создание, по случаю
     а/в) для каждой отмеченной строки. Отклонение всех чекбоксов и закрытие
     экрана без нажатия кнопки — валидный путь, ничего не обновляется в
     `Price`, `confirmed_price` на `OrderItem` уже сохранён на шаге 1 этого
     пункта, не откатывается (см. п.7).

   **Контракт: `POST /orders/{order_id}/confirm-price-updates`.** Роутер
   `order.py`, тот же `get_current_user` (не новая admin-точка — см. п.1),
   тот же файл, что и `patch_order_item`, — не отдельный роутер, потому что
   область действия та же (позиции одного `Order`) и не пересекает границу
   `/prices/**`.

   ```python
   class PriceUpdateSelectionIn(BaseModel):
       """Одна строка выбора на экране пакетного подтверждения — см.
       ADR-0030 п.4. order_item_id должен присутствовать среди
       PriceDivergence, возвращённых этим Order за текущую сессию
       фронтенда (batch-применение confirmed_price, п.4.3) — сервер не
       принимает произвольный order_item_id, не участвовавший в
       обнаруженном расхождении, см. валидацию ниже."""

       order_item_id: uuid.UUID
       apply: bool

   class ConfirmPriceUpdatesIn(BaseModel):
       """Body for POST /orders/{order_id}/confirm-price-updates. Список
       всех строк, показанных на экране пакетного подтверждения (и
       отмеченных, и неотмеченных) — не только apply=True. Сервер
       обрабатывает только apply=True; остальные включены в payload для
       симметрии с тем, что видел пользователь, но не обязательны
       (frontend может прислать только apply=True строки — оба варианта
       валидны, сервер не проверяет полноту множества)."""

       selections: list[PriceUpdateSelectionIn]

   class PriceUpdateResultOut(BaseModel):
       """Результат одной обработанной строки — и успешной, и
       отклонённой (apply=False), чтобы фронтенд мог отрисовать полный
       итог без повторного GET Order."""

       order_item_id: uuid.UUID
       applied: bool
       """False для строк с apply=False во входном payload — не ошибка,
       осознанный пропуск."""
       price_id: uuid.UUID | None = None
       """id новой версии Price — заполнено только когда applied=True."""
       action: Literal["update", "create"] | None = None
       """Эхо PriceDivergence.action для этой строки — None когда
       applied=False."""
       error: str | None = None
       """Заполнено, если order_item_id не найден в этом Order, или не
       входит в множество известных серверу PriceDivergence для этого
       Order (см. валидацию ниже) — applied остаётся False, остальные
       строки запроса обрабатываются независимо (частичный успех
       допустим и ожидаем, не all-or-nothing транзакция на весь список,
       см. обоснование ниже)."""

   class ConfirmPriceUpdatesOut(BaseModel):
       results: list[PriceUpdateResultOut]
   ```

   **Ответ — `200` с `ConfirmPriceUpdatesOut`, не `204`.** Обоснование:
   фронтенд batch-экрана должен показать итог по каждой выбранной строке
   (обновлено/создано, с каким `price_id`) без отдельного `GET
   /orders/{id}` — та же логика, что уже определяет форму ответа
   `PATCH .../items/{item_id}` (возвращает `OrderItemOut` целиком, не
   `204`) и `POST .../orders` (возвращает список созданных `Order`, не
   просто статус) — эндпоинты этого роутера последовательно возвращают
   результат операции, не пустой успех, чтобы фронтенду не приходилось
   рефетчить состояние отдельным запросом сразу после мутации.

   **Валидация: сервер не доверяет `current_price` от клиента, только
   `order_item_id`.** Обработка каждой строки заново вызывает ту же
   проверку, что и обнаружение (п.2) — берёт текущее
   `OrderItem.confirmed_price` и текущую активную `Price` на момент
   обработки запроса (не значения, которые фронтенд показал на экране
   несколько секунд/минут назад), затем вызывает `version_price`
   (переиспользуя её, п.5) только если расхождение всё ещё существует.
   Если `OrderItem.confirmed_price` не задан (снят другим PATCH между
   обнаружением и подтверждением) или активная `Price` уже совпадает
   (кто-то другой её обновил за это время) — строка возвращается с
   `applied=False`, `error="stale: confirmed_price changed or price
   already matches"`, не применяется вслепую к устаревшим числам с
   экрана. Эта проверка — не гипотетическая защита "на всякий случай": на
   масштабе единиц-десятков сотрудников (ADR-0024 §3 уже фиксирует этот же
   масштаб) конкурентная правка того же `OrderItem` между открытием
   batch-экрана и нажатием кнопки — редкий, но реальный случай (два
   сотрудника сверяют один Order), и `version_price` не идемпотентна
   (повторный вызов с тем же значением создал бы шумную закрытую версию с
   нулевой дельтой) — без этой проверки повторное нажатие кнопки после
   частичного сбоя сети создавало бы дублирующиеся версии `Price`.

   **Обработка списка — независимая по строкам, не одна транзакция на
   весь batch.** Каждая строка коммитится (через `version_price`)
   отдельно; ошибка на одной строке (`error`, выше) не откатывает и не
   блокирует уже применённые до неё — симметрично тому, как batch-цикл
   ADR-0018 §4 уже обрабатывает "Применить все совпадения" построчно, не
   одной атомарной транзакцией на весь список.

   Ручной построчный ввод (единичный `OrderItem`, inline-редактирование,
   п.4.2 выше) остаётся отдельным, более простым путём — единичный попап на
   одну позицию, без списка/чекбоксов, симметрично тому, как это уже
   работает для остальных полей `OrderItem`.

### 5. Механизм записи — переиспользование `update_price`, не дублирование

**Экспортируемая сервисная функция `price.py` вызывается напрямую, не
дублируется.** `update_price` (`backend/app/api/price.py:83`) сейчас —
FastAPI route-handler, принимает `PriceUpdate` (Pydantic-схема с
HTTP-семантикой) и работает с `price_id` конкретной закрываемой записи.
Чтобы вызываться из другого места (не `/prices/{id}` роута) без дублирования
логики версионирования, выделяется внутренняя функция
`version_price(db: Session, *, material_id, supplier_id, price, ...) ->
Price`, куда переносится тело текущего `update_price` (поиск активной
записи по (`material_id`, `supplier_id`) вместо `price_id` напрямую — те же
шаги: найти активную запись, если есть — закрыть (`valid_to = today()`),
создать новую с `valid_from = today()`, наследуя `currency`/`availability`/
`min_order_qty`/`source_import_id` от закрываемой строки, если не переданы
явно; если активной записи нет (случай в, п.2) — создать без закрытия
предыдущей). `update_price`-route становится тонкой обёрткой над
`version_price`, принимающей `price_id`, резолвящей его в
(`material_id`, `supplier_id`) и делегирующей — **тот же поведенческий
контракт**, HTTP-путь `/prices/{id}` не меняется ни в сигнатуре, ни в
ответах.

`order_service.py` (или новый модуль `app/allocation/price_sync.py`, рядом
с `order_service.py`, по аналогии с тем, как `order_response_parser`
получил отдельный модуль, ADR-0018 §1, когда логика структурно не
принадлежит существующему файлу — здесь же логика прямо расширяет
`set_order_item_fields`/batch-флоу `order_service.py`, поэтому остаётся в
нём, а не выносится) импортирует `version_price` из `price.py` и вызывает
её при подтверждении из п.4 — **никакого нового кода, открывающего
активную запись/закрывающего её/создающего новую** вне `price.py`.

**Явно подтверждено: переиспользование существующей сервисной функции, не
дублирование её логики.** Дублирование было бы риском рассинхрона того же
класса, что уже отклонён в ADR-0007 п.1 (персистентная дельта) и ADR-0018
§4 (два вызова vs один) — если версионирование понадобится изменить позже
(например, добавить поле в цепочку наследования при закрытии), придётся
помнить о двух местах.

### 6. Аудит — `Price` получает `created_by_user_id`/`source_order_item_id`

**Решение: да, добавить обе колонки, в объёме этого ADR, не откладывать.**

```python
class Price(UUIDPKMixin, Base):
    ...
    created_by_user_id: Mapped[uuid.UUID | None] = mapped_column(
        UUID(as_uuid=True), ForeignKey("users.id")
    )
    """Кто создал эту версию записи. NULL для версий, созданных через
    admin-only /prices (аноним по этому полю, не обязателен там — см.
    ниже), не NULL для версий, созданных через узкое исключение ADR-0030.
    """
    source_order_item_id: Mapped[uuid.UUID | None] = mapped_column(
        UUID(as_uuid=True), ForeignKey("order_items.id")
    )
    """OrderItem, чей confirmed_price породил эту версию — только для
    версий, созданных через ADR-0030. NULL для всех версий, созданных
    вручную через /prices (нет исходного OrderItem — прямая правка
    справочника)."""
```

**Обоснование, почему сейчас, не отложено, по аналогии с ADR-0024 §6.**
ADR-0024 §6 ввела `created_by_user_id` на `Order`/`PurchaseRecord`,
`overridden_by_user_id` на `AllocationLine` по одному и тому же принципу:
"дёшево, делается в рамках этой же реализации... объект `User` уже есть на
каждом authenticated-запросе... не требует нового прохода позже". Тот же
аргумент применяется здесь буквально, с усилением: это ADR **впервые**
позволяет роли `employee` писать в `Price` — до этого момента 100% строк
`Price` создавались исключительно через `admin`-only `price.py` (прямой ввод
или аппрув прайс-ingestion). Если не добавить атрибуцию сейчас, первая же
запись, созданная через это узкое исключение, окажется неотличима от любой
записи, созданной обычным admin-флоу — что прямо противоречит характеру
исключения, объявленному в п.7/preamble этого ADR ("привязано к конкретной,
уже согласованной сделке, которую ведёт этот сотрудник, не произвольное
редактирование справочника"): без `source_order_item_id`, доказывающего эту
привязку, утверждение "это узкое, а не произвольное действие" ничем не
подкреплено в самих данных — это ровно тот случай, где аудит-колонка не
удобство, а часть самого обоснования безопасности решения.

**`created_by_user_id`/`source_order_item_id` не заполняются для версий,
созданных через `/prices/{id}` (admin-флоу).** `update_price`-route
(HTTP-обёртка после рефакторинга п.5) не передаёт эти параметры в
`version_price` — остаются `NULL`. Это осознанно, не "негде взять
`current_user`": `price.py` уже имеет `current_user` через
`require_role("admin")` dependency, технической преграды заполнить их и там
нет. Решение — не заполнять, потому что это ADR **не расширяет** объём
аудита для существующего admin-флоу (не в объёме, явно отмечено в
"Контекст"); отдельная задача, если понадобится атрибуция и для
admin-правок справочника — то же рассуждение "не проектировать вслепую",
уже несколько раз применённое в этой цепочке ADR.

**Не в объёме этого ADR: атрибуция для строк `Price`, созданных
прайс-ingestion (`price_list_imports`).** У них уже есть
`source_import_id` (существующее поле) — другой, ранее решённый вопрос
происхождения, не расширяется и не пересматривается здесь.

### 7. Отказ подтверждать не блокирует ввод `confirmed_price`

**Явно подтверждено: `OrderItem.confirmed_price` сохраняется успешно
независимо от решения по попапу/batch-экрану.** `set_order_item_fields`
(п.2) выполняет запись `confirmed_price` полностью, коммитит, и только
**после** этого (или как часть того же ответа, без отдельного commit —
см. ниже) сообщает о расхождении вызывающему коду. Показ попапа/batch-экрана
и решение пользователя по нему — целиком после точки, где ввод цены заказа
уже необратимо сохранён; отклонение предложения (закрыть попап без
подтверждения, снять все чекбоксы в batch-экране) не откатывает и не
блокирует уже записанный `confirmed_price`.

**Обоснование, почему это не гейт.** Прямо указано в постановке задачи и
следует из архитектурной роли `confirmed_price` в этой системе ADR: он —
факт о конкретной сделке (что реально подтвердил поставщик по этому
заказу), тогда как обновление `Price` — отдельное, необязательное действие
над *другой* сущностью (справочник, используемый другими проектами).
Блокировка первого до решения по второму означала бы, что ввод данных о
своём собственном заказе зависит от готовности сотрудника в моменте принять
решение об изменении общего справочника — смешение двух разных по весу
решений в одну атомарную операцию, тогда как задача явно требует их
разделить ("попап — это дополнительное предложение, не гейт на сам ввод
цены заказа").

## Альтернативы

Альтернативы для каждого под-вопроса (1–7) перечислены инлайн в "Решение" —
та же структура, что уже принята в ADR-0006/0007/0013/0018/0027, по той же
причине: обоснования специфичны к конкретному под-решению.

Единственная альтернатива на уровне ADR целиком, отклонённая полностью:
**расширить общий доступ `employee` к `/prices/**` (снять
`require_role("admin")` с роутера целиком или добавить `PATCH
/prices/{id}` под ролью `employee`).** Отклонено — прямо исключено
постановкой задачи и противоречит явному обоснованию ADR-0024 §4
("прямая правка боевых цен в обход ревью-флоу — самое чувствительное CRUD в
системе"): это ADR намеренно не даёт `employee` возможности зайти на
`PricesPage` и отредактировать произвольную запись — узкая write-точка
внутри `order.py` (п.5) работает только от конкретного, уже введённого,
уже согласованного `confirmed_price` на уже существующем `OrderItem`
конкретного заказа, которым этот сотрудник и так управляет по
ADR-0024 §4 (`order.py` — `get_current_user`, любая роль). Нет пути вызвать
запись в `Price` из этого механизма без предварительно существующего
`OrderItem.confirmed_price` — это структурное ограничение, не
процедурное (нет отдельного endpoint'а `POST/PATCH /prices` под
`employee`, который можно было бы вызвать напрямую, минуя `Order`).

## Последствия

- Миграция Alembic: `prices.created_by_user_id UUID NULL` (FK → `users`),
  `prices.source_order_item_id UUID NULL` (FK → `order_items`). Nullable без
  бэкафилла — все существующие строки созданы до этого ADR через admin-флоу,
  `NULL` корректен для них (симметрично прецеденту ADR-0024 §6 для
  `Order.created_by_user_id`).
- `backend/app/api/price.py`: `update_price`-route рефакторится в тонкую
  обёртку над новой `version_price(db, *, material_id, supplier_id, price,
  currency=None, availability=None, min_order_qty=None, source_import_id=None,
  created_by_user_id=None, source_order_item_id=None) -> Price` —
  переносится вся логика поиска активной записи/закрытия/создания. Публичный
  контракт `PUT /prices/{id}` не меняется.
- Новая логика в `backend/app/allocation/order_service.py`:
  `set_order_item_fields` меняет тип возврата на
  `tuple[OrderItem, PriceDivergence | None]` (dataclass `PriceDivergence`,
  п.2) — оба существующих вызывающих (`patch_order_item`, batch-цикл
  ADR-0027 §2) обновляются под новую сигнатуру.
- Новый endpoint `POST /orders/{order_id}/confirm-price-updates` (п.4.3) —
  `ConfirmPriceUpdatesIn`/`ConfirmPriceUpdatesOut` в
  `backend/app/api/schemas/order.py`, `200` с построчным результатом
  (`applied`, `price_id`, `action`, опционально `error` при stale-строке),
  не `204`. Построчная обработка, не атомарная транзакция на весь список;
  сервер перепроверяет расхождение на момент обработки, не доверяет
  `current_price`, показанному фронтендом ранее.
- `backend/app/api/order.py`: `patch_order_item` получает
  `current_user: User = Depends(get_current_user)` (сейчас отсутствует в
  сигнатуре, несмотря на router-level dependency) — нужен для передачи
  `created_by_user_id` в `version_price`.
- `docs/data-model.md`: `Price` получает `created_by_user_id`,
  `source_order_item_id` (в дополнение к существующим полям).
- `docs/ui-reference.md`: новый раздел — единичный попап подтверждения
  (случаи а/в, п.2/п.4.2) и экран пакетного подтверждения после
  batch-применения confirmed_price (п.4.3), включая правило дефолтных
  невыбранных чекбоксов.
- Реализация (миграция, рефакторинг `price.py`, новая логика в
  `order_service.py`, endpoint(ы), фронтенд — попап и batch-экран) —
  предмет отдельной задачи после вычитки этого ADR, как и было с
  предыдущими ADR в этом проекте.
