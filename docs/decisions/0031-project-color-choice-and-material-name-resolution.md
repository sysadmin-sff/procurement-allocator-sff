# ADR-0031: `Project.color_choice` и разрешение цвета в названии материала для supplier-facing документов

Статус: Предложено

## Контекст

Часть реального каталога (`backend/data/import/materials_price_matrix.xlsx`,
294 материала) содержит **два** цвета в одной строке `canonical_name` —
поставщик продаёт материал в любом из цветов по одной цене, но конкретный
заказ должен называть поставщику ровно один цвет, не оба сразу. Сегодня
`canonical_name` копируется как есть (`import_real_data.py:158`) во все
supplier-facing документы (`buildOrderText`, ADR-0027 §5) — двусмысленное
название реально уходит поставщику.

Пользователь подтвердил: один цвет выбирается **на весь проект целиком**
(все материалы проекта — один и тот же цвет) — та же логика визуальной
согласованности, что уже привела к строгой группировке поставщика по
категории в ADR-0028 (там — чтобы разные поставщики не давали неуловимо
разные оттенки одного цвета; здесь — чтобы в принципе не оказалось смеси
двух номинально разных цветов на одном объекте). Разная гибкость цвета
внутри одного проекта — не нужна, пользователь явно отклонил.

### Проверка на реальных данных (Шаг 0 — выполнена до черновика этого ADR)

Запущен фактический парсер (`xlsx_price_matrix.parse_price_matrix`) поверх
реального файла, результат показан пользователю до написания этого раздела,
не предположен:

**Найденные паттерны написания цвета — не единый формат:**

| Паттерн | Кол-во | Категории | Пример |
|---|---|---|---|
| `(White/Bronze)` — два цвета в скобках через `/` | 127 | Doors, Gutter, Profil, Connectors | `Super Gutter End Cap 5" (White/Bronze)` |
| `(White)` / `(Bronze)` — один цвет в скобках | 35 | Gutter, Profil, Roof panels | `E-Fascia x 24’ (White)` |
| `Bronze/White` — два цвета **без скобок**, посреди строки | 22 | Screws | `12 x 3/4" Bronze/White Stainless steel` |
| `.024`, `with holes`, `5 Rib`, номера деталей — скобки, но НЕ цвет | 35 уникальных групп | разное | `3" Panel WITHOUT Fan Beam (.024)...` |

Значимое расхождение с предположением задачи: формат **не всегда**
`(Color1/Color2)`. 22 материала категории `Screws` содержат ту же пару
цветов как обычные слова без скобок, вплетённые в середину названия перед
словом-материалом (`Stainless steel`/`Galvanized` — это финиш крепежа,
ортогонален цвету, не второе измерение выбора). Регэксп только по скобкам
пропустил бы весь `Screws`. Три и более цвета, сокращения (`wht/brz`) —
не встретились ни разу; единственное сокращение в данных (`SCRW-006`,
`"10 X 3/4 TEK WHT CERAMIC"`) — это один цвет, не пара, не тот случай.

**Итого материалов с двумя цветами: 127 + 22 = 149 из 294 (~51%)** —
почти половина каталога, значительно больше "нескольких особых случаев".

**Цена — подтверждено, не предположение: одна цена независимо от цвета.**
Дубликатов `description` в каталоге — 0 (проверено программно по всем 294
строкам). Базовое имя (текст с вырезанным цветом) двухцветных материалов не
пересекается ни с одним базовым именем однoцветных — 0 пересечений, то есть
нет скрытой пары строк "White отдельно / Bronze отдельно" для того же
физического товара нигде в файле. Каждый двухцветный материал — ровно одна
строка xlsx → один `Material` → один набор `Price` по поставщикам (пример:
`Door Blank with 8” Kick Plate (White/Bronze)` — EMS $66.00, Lancing $49.71,
JM Fasteners $49.50 и т.д., одно число на поставщика). Раздельной цены по
цвету в реальных данных нет — условие задачи "если Шаг 0 неожиданно это
найдёт, остановиться" не сработало, ADR продолжен.

### Существующие прецеденты, которые это решение продолжает

- **ADR-0028** — та же бизнес-мотивация (визуальная согласованность на
  объекте), на уровень ниже: там — один поставщик на категорию, здесь — один
  цвет на проект. Не пересекаются механически (разные оси), но одна и та же
  причина с того же созвона с руководством.
- **ADR-0027 §5** — `buildOrderText` уже определена как место, требующее
  правки в этом релизе (там — фильтрация отклонённых позиций; здесь —
  разрешение цвета). Задача явно называет её местом, требующим разрешения
  цвета.
- **ADR-0007 §6** — `/orders/:id/print`, второй явно supplier-facing
  документ. **Проверено явно: этот роут пока не реализован** — грепом по
  `frontend/src/` не найдено ни компонента, ни маршрута `print` — ADR-0007
  описывает его в разделе "Решение", но "Последствия" ADR-0007 фиксируют
  экран как ещё не существующий, и по факту с тех пор он не появился.
  Это не снимает вопрос, а меняет его форму: `resolve_material_name`
  проектируется здесь так, чтобы использоваться этим экраном **с момента
  его первой реализации**, а не патчиться отдельным ADR после факта.

## Решение

### 1. Структурное представление цветов на `Material` — `color_options`

**Новое поле `Material.color_options: list[str] | None` (JSON), заполняется
один раз при импорте, не парсится на лету в каждом потребителе.**

```python
class Material(UUIDPKMixin, Base):
    ...
    canonical_name: Mapped[str] = mapped_column(String(255), nullable=False)
    color_options: Mapped[list[str] | None] = mapped_column(JSON, nullable=True)
    """Цвета, доступные для этого материала без изменения цены — извлечены
    из canonical_name при импорте, не пересчитываются на чтении. NULL или
    пустой список = материал не имеет цветового выбора (нейтрален к цвету,
    либо цвет уже зафиксирован как часть названия неотделимо). Список из
    ровно одного элемента отличается от NULL семантически (см. п.4) даже
    если для текущего каталога не встречается на практике. См. ADR-0031."""
```

**`canonical_name` не переименовывается и не меняется** — остаётся полным
названием с обоими цветами для внутренних экранов, как и требует задача:
сотрудник видит `"Super Gutter End Cap 5" (White/Bronze)"` и по контексту
выбранного цвета проекта понимает, какой из двух имеется в виду. Ничего в
`OrderDetailPage`/`AllocationResultPage`/матрице сравнения цен не меняется
(см. п.5, пункт "не требуют").

**Формат значения** — список нормализованных строк с заглавной буквы, в
том порядке, в котором цвета встречаются в `canonical_name`: `["White",
"Bronze"]`, не `{"White", "Bronze"}` (JSON-массив, не множество — порядок
несёт смысл для UI, если понадобится показать список цветов, например, при
выборе цвета на экране проекта, см. п.2). Значения — из фиксированного
словаря известных цветов (`WHITE`, `BRONZE` — единственные два, встреченные
в реальных данных; словарь расширяется при появлении нового цвета в
будущем прайсе, не строится динамически из произвольного текста, чтобы
опечатка вида `Bronz` не создала третий "цвет" молча).

**Заполнение для существующих ~294 материалов — одноразовый скрипт,
ручная проверка перед применением.** Тот же принцип, что уже применён к
другим одноразовым скриптам проекта (`import_real_data.py` сам — ручной
запуск с dry-run выводом перед записью, см. его существующий `--dry-run`).
Новый скрипт `backend/app/scripts/backfill_color_options.py`:

1. Проходит все существующие `Material.canonical_name` через два
   регэкспа, оба найденных в Шаге 0 (не один):
   - Скобочный: `\(([A-Za-z]+(?:/[A-Za-z]+)+)\)` → если найдено и каждый
     токен после split по `/` — известное слово из словаря цветов, это
     `color_options` (`["White", "Bronze"]`), а также запоминается, что
     скобочный текст целиком — это то, что должно быть заменено при
     разрешении (см. п.4).
   - Голый (без скобок): скан на пару `Bronze/White` или `White/Bronze`
     как отдельный токен (границы слова) в любом месте строки, вне
     скобок — покрывает `Screws` (22 случая из Шага 0).
   - Однoцветные скобки (`(White)`, `(Bronze)`) — **не** дают
     `color_options` (это не выбор, это уже зафиксированный цвет; список
     из одного элемента здесь не нужен, см. отличие поля от того,
     "содержит ли строка слово-цвет вообще" в примечании ниже).
2. Выводит dry-run отчёт: для каждого найденного материала — `internal_sku`,
   `canonical_name`, извлечённый `color_options`, и какой из двух
   регэкспов сработал. Отдельно — список материалов, где скобки/слова похожи
   на цвет, но не распознаны уверенно (например, содержат цветовое слово
   вместе с чем-то ещё в той же скобке — в реальных данных Шага 0 такого не
   встретилось, но скрипт должен явно вывести "не смог разобрать", не
   угадывать и не молча пропускать).
3. Ничего не пишет в БД до явного повторного запуска с `--apply` после
   того, как человек просмотрел dry-run отчёт — тот же паттерн, что уже
   установлен `import_real_data.py --dry-run`.

**Примечание про однoцветные материалы.** Материал `E-Fascia x 24’
(White)` — это НЕ материал без цвета: у него есть цвет ("White"), просто
без выбора (единственный вариант). `color_options = None` для него
корректно означает "нет *выбора* цвета", не "нет цвета вообще" — различие
не имеет практических последствий в этом ADR (п.4 всё равно возвращает
`canonical_name` как есть для любого материала без множественного
выбора), но фиксируется явно, чтобы будущий читатель поля не удивился,
увидев `color_options IS NULL` у материала, название которого содержит
слово-цвет.

**Отклонено: парсить `canonical_name` на цвет в каждом месте, где нужно
supplier-facing имя.** Прямо отклонено постановкой задачи и логикой этого
ADR — дублирование regex-логики в `buildOrderText`,
`buildTargetPriceOrderText` и будущем `/orders/:id/print` создаёт три
места, которые должны согласованно знать про оба формата (скобочный и
голый) и не разойтись при будущем изменении формата каталога. Один разбор
при импорте + одна функция чтения (п.4) устраняют этот риск структурно.

### 2. `Project.color_choice` — новое nullable-поле, устанавливается на экране проекта, редактируется до генерации ордеров

```python
class Project(UUIDPKMixin, TimestampMixin, Base):
    ...
    color_choice: Mapped[str | None] = mapped_column(String(20), nullable=True)
    """Единый цвет на весь проект для материалов с color_options. NULL =
    цвет ещё не выбран. Значение — один из известных цветов словаря
    (см. п.1), не свободный текст (тот же принцип, что category — но там
    свобода текста была осознанным выбором под конкретный источник
    данных; здесь источник — фиксированный выбор пользователя из
    известного набора, свободный текст добавил бы риск опечатки,
    непроверяемой на бэкенде). См. ADR-0031."""
```

**Где и когда устанавливается — редактируется в любой момент на экране
проекта до генерации ордеров, не поле формы создания.** Обоснование, не
оставлено "на реализацию":

- Создание проекта (`POST /projects`) сегодня — минимальная форма
  (`title`, состав BOM собирается отдельным шагом конструктора). Требовать
  цвет уже на этом шаге означало бы либо задавать вопрос до того, как
  пользователь вообще увидел, есть ли в его BOM материалы с выбором цвета
  (пользователь может добавить материалы с `color_options` только позже,
  в процессе подбора), либо задавать его вслепую всем проектам, включая
  те, где ни один материал не содержит цветового выбора (например, проект
  только из `Screws`-крепежа без выбора цвета, или, наоборот, только из
  однoцветных материалов) — бессмысленный обязательный вопрос для доли
  проектов.
- Редактируемость **в любой момент до генерации ордеров** (не блокируется
  после первого выбора) — симметрично тому, как `AllocationLine.override`
  (ADR-0006) и `OrderItem.target_price` (ADR-0027 п.1) уже разрешают
  правку значения в любой момент жизненного цикла до того, как оно
  зафиксировано снимком: `color_choice` фиксируется как часть Order только
  в момент генерации ордер-документа (тот же принцип "снимок, не кэш",
  ADR-0007 п.2 — но здесь снимок неявный, потому что `resolve_material_name`
  вызывается один раз при генерации текста/документа, не хранится отдельным
  полем на `OrderItem`, см. п.4 почему это не нужно).
- Расположение в UI — секция параметров проекта на `ProjectDetailPage`
  (уже существующий экран, где живут `title`/`status`), не отдельный
  экран и не шаг мастера — простой `<select>` из известных цветов словаря,
  та же категория изменения, что и переименование проекта.

**Отклонено: устанавливать `color_choice` обязательным полем при
создании.** Отклонено по причине выше — преждевременный вопрос, не
имеющий ответа на момент, когда он был бы задан, для доли проектов вообще
не имеющий смысла.

**Отклонено: цвет как часть каждого `ProjectItem` (материал), а не
`Project` целиком.** Явно отклонено пользователем в постановке задачи —
не проектируется даже как гибкость на будущее (задача прямо просит не
проектировать эту гибкость).

### 3. Материал с двумя цветами в BOM без выбранного `color_choice` — блокировать генерацию

**Решение: блокировать генерацию supplier-facing документа (текст ордера,
печатный документ), если в BOM проекта есть хотя бы один материал с
непустым `color_options`, а `Project.color_choice` не выбран. Не
предупреждение с пропуском.**

Обоснование выбора блокировки, не предупреждения — вопрос из задачи прямо
просил не оставлять "решается по умолчанию":

- Цель фичи — исключить именно тот случай, когда двусмысленное название
  реально уходит поставщику. Предупреждение с возможностью продолжить
  оставляет ровно эту дыру открытой: сотрудник может кликнуть "продолжить"
  не глядя (тот же паттерн спешки, из-за которого фича вообще появилась —
  проблема не гипотетическая, а такая, которая уже происходит сегодня,
  потому что раньше в системе не было механизма её поймать), и
  сгенерированный текст уйдёт поставщику с `(White/Bronze)` внутри — то
  есть система создала бы видимость решения проблемы, не решая её.
- Это отличается от паттерна "предупреждение, не блокировка", уже
  установленного в ADR-0006 (override при недостаточном availability) и
  ADR-0028 п.4 (override внутри разбитой категории) — там обоснование
  предупреждения explicitly было "система не обладает полным контекстом,
  чтобы решать за человека": сотрудник может знать то, чего нет в модели
  (внедоговорные причины, скрытая деталь). Здесь другая форма вопроса:
  "какой цвет выбрать" — это не решение, которое уже принято человеком и
  которое система не должна оспаривать, а решение, которое **ещё не
  принято вообще** (`color_choice IS NULL` в буквальном смысле означает
  "выбор не сделан", не "выбор сделан, но система с ним не согласна").
  Блокировка здесь не отменяет решение пользователя — она просит его
  сделать выбор, которого пока физически не существует. Прецедент
  "предупреждение, не блокировка" неприменим по этой причине, а не
  проигнорирован.
- Стоимость ложного срабатывания низкая: выбор цвета — один `<select>` на
  экране проекта (п.2), не многошаговая форма; блокировка не создаёт
  тяжёлого препятствия, в отличие от гипотетического hard-constraint в
  ADR-0028, где блокировка (infeasible) означала полный отказ системы
  посчитать закупку без обходного пути.

**Механизм:** backend-эндпоинт генерации (создание `Order`,
ADR-0007 §2 `POST /projects/{project_id}/allocations/{run_id}/orders`)
проверяет перед созданием: для всех `Material` строк, вошедших в план
(`AllocationLine`/`ProjectItem`), есть ли хотя бы один с непустым
`color_options`; если да и `Project.color_choice IS NULL` — эндпоинт
возвращает ошибку (4xx, конкретный код/сообщение — деталь реализации), не
создаёт `Order`. Фронтенд показывает это как явное состояние на
`AllocationResultPage` **до** нажатия кнопки создания ордеров (не только
как реакцию на упавший запрос) — кнопка "Подтвердить и создать ордера"
неактивна с подсказкой "Выберите цвет проекта, чтобы продолжить" при
обнаружении непустого пересечения BOM с материалами, имеющими
`color_options`, аналогично тому, как эта же кнопка уже условно
недоступна по другим причинам на этом экране.

То же правило применяется к любой будущей генерации `/orders/:id/print`
(ADR-0007 §6) — если документ генерируется в тот же момент, что и Order
(ADR-0007 §6: "Генерация документа происходит сразу при создании Order"),
проверка уже выполнена на этапе создания Order, второй отдельной проверки
не требуется; если в будущем печать станет возможной независимо
(перегенерация без пересоздания Order), та же проверка переносится и туда
— фиксируется здесь как требование к любой точке генерации, не только к
одной сегодняшней.

**Отклонено: предупреждение с возможностью продолжить.** Отклонено по
причине выше — прямо противоречит цели фичи ("не отправлять поставщику
двусмысленное название"), рассмотрено как вариант по умолчанию и явно
отвергнуто, не пропущено.

### 4. `resolve_material_name` — единая функция разрешения

```python
def resolve_material_name(material: Material, color: str | None) -> str:
    """Возвращает supplier-facing название материала с разрешённым цветом.

    - material.color_options пусто/None -> возвращает material.canonical_name
      как есть (материал без выбора цвета, либо одноцветный, либо
      нейтральный к цвету).
    - material.color_options непусто, color is None -> возвращает
      canonical_name как есть, НЕ вызывающая сторона решает, можно ли
      вообще дойти до этой точки (см. ниже "вызывающий контракт").
    - material.color_options непусто, color задан и присутствует в
      color_options -> возвращает canonical_name с цветовым фрагментом,
      заменённым на выбранный цвет (единственный, без второго варианта и
      без скобок вокруг него, если исходный формат был скобочным —
      "(White/Bronze)" -> "(White)"; если исходный формат был голым —
      "Bronze/White" -> "White", сохраняя падеж/порядок остального текста
      без изменений).
    - color задан, но отсутствует в color_options материала -> возвращает
      canonical_name как есть (несоответствие цвета материалу — по
      построению не должно происходить, раз color_choice ограничен тем же
      словарём, но функция не должна упасть или придумать цвет, которого
      нет; деталь реализации — логировать это как аномалию).
    """
```

**Вызывающий контракт: `resolve_material_name` не решает, блокировать ли
генерацию — это ответственность вызывающей стороны (п.3).** Функция —
чистое разрешение имени по уже известным входным данным, не место для
бизнес-правила "запретить, если цвет не выбран". Причина разделения:
`resolve_material_name` полезна и в контексте, где блокировка уже прошла
(генерация уже разрешена, потому что `color_choice` есть) — там она просто
трансформирует строку; смешивание проверки внутрь функции заставило бы
каждого вызывающего перехватывать исключение или специальное возвращаемое
значение вместо простого чтения результата.

**Реализация замены цветового фрагмента — не regex на лету в
`resolve_material_name`, а хранимая позиция или повторное применение того
же разбора, что и backfill.** Простейший корректный вариант: хранить сам
цветовой фрагмент как он выглядит в `canonical_name` (например,
дополнительно `Material.color_fragment: str | None` — точная подстрока,
которую нужно заменить, будь то `"(White/Bronze)"` или `"Bronze/White"`) —
тогда `resolve_material_name` делает один `str.replace(color_fragment,
new_fragment)`, без повторного regex-разбора на каждый вызов. Это второе
поле, не альтернатива `color_options`: `color_options` — что доступно
(семантика для UI/бизнес-логики), `color_fragment` — как это записано
буквально в этой конкретной строке (техническая деталь для замены).
Оба заполняются одним и тем же backfill-скриптом (п.1) за один проход.

**Все места, требующие supplier-facing название, вызывают эту одну
функцию** — см. полный список в п.5, ни одно не реализует собственный
парсинг цвета.

### 5. Места, где нужно разрешённое имя — полный список

- **`buildOrderText`** (`frontend/src/routes/OrderDetailPage.tsx:406`,
  ADR-0027 §5) — да, точно, как и указано в задаче. Строит текст для
  копирования поставщику по `quoted_price`.
- **`buildTargetPriceOrderText`** (`frontend/src/routes/OrderDetailPage.tsx:467`)
  — **дополнительно найдено при чтении кода, не было в списке задачи**:
  вторая функция того же назначения (текст "с целевыми ценами" для второго
  раунда торга, ADR-0027 §2), тоже использует `material?.canonical_name`
  напрямую (строка 485) для того же supplier-facing текста. Пропустить её
  означало бы решить проблему только для одной из двух копируемых версий
  документа поставщику — оставшаяся дыра были бы такой же реальной, как и
  до этого ADR. Обе функции вызывают `resolve_material_name`.
- **`/orders/:id/print`** (ADR-0007 §6) — да, вероятно, подтверждено явно:
  это формальный документ поставщику, тот же класс, что `buildOrderText`.
  Проверено (см. "Контекст" выше): роут ещё не реализован сейчас — решение
  распространяется на его первую реализацию, не на правку существующего
  кода. Функция генерации этого документа (когда будет написана) обязана
  вызывать `resolve_material_name`, а не собственный вывод `canonical_name`.
- **Внутренние экраны — подтверждено явно: НЕ требуют разрешения,
  показывают `canonical_name` как есть.** Проверено по каждому месту
  использования `canonical_name` в текущем фронтенде:
  - `OrderDetailPage.tsx` (табличные ячейки, строки 530/692/894/1007/1070,
    модалка `PriceDivergenceModal` через `materialName` на строке 225) —
    внутренний экран сверки, сотрудник видит полное название, зная из
    контекста, какой цвет выбран для проекта (тот же аргумент, что уже
    обосновал видимость `canonical_name` без изменений в "Решение" п.1).
  - `AllocationResultPage.tsx` (строки 268/455) — внутренний экран
    результата аллокации, тот же аргумент.
  - `PriceComparisonPage.tsx` (матрица сравнения цен, строки 198/282) —
    внутренний экран сравнения цен по материалам/поставщикам, не документ
    для поставщика; тот же аргумент.
  - `ProjectDetailPage.tsx`, `ProjectBuilderPage.tsx`,
    `project-builder/MaterialCombobox.tsx`, `MaterialsPage.tsx`,
    `materials/MaterialForm.tsx`, `price-list-import/PriceListImportReviewPage.tsx`
    — все внутренние экраны построения/справочника/ревью, ни один не
    формирует документ, уходящий во внешний адрес; `canonical_name`
    остаётся без изменений во всех.

## Альтернативы

**Парсить `canonical_name` на цвет в каждом supplier-facing месте отдельно
(regex inline в `buildOrderText`, `buildTargetPriceOrderText`,
`/orders/:id/print`).** Отклонено в п.1/п.4 — три копии логики, которые
должны синхронно знать про оба найденных на Шаге 0 формата (скобочный и
голый); любое будущее изменение формата каталога (новый поставщик, новый
цвет) требовало бы находить и чинить все три места одновременно, точно тот
риск рассинхрона, который уже мотивировал единые функции в других ADR
проекта (например, `price_delta()`, ADR-0007 п.1, переиспользуемая, а не
задублированная для `received_price_delta` в ADR-0027 §3).

**Предупреждение вместо блокировки при отсутствующем `color_choice`.**
Рассмотрено и отклонено в п.3 как вариант по умолчанию — прямо
противоречит цели фичи (см. обоснование в п.3), в отличие от прецедентов
ADR-0006/ADR-0028 п.4, где предупреждение было оправдано тем, что человек
уже принял решение, которое система не вправе оспаривать; здесь решение
ещё не существует вообще.

**`color_choice` как обязательное поле при создании проекта.** Отклонено
в п.2 — преждевременный вопрос: на момент создания проекта состав BOM (и,
следовательно, наличие материалов с выбором цвета) может быть ещё не
определён; для проектов без материалов с `color_options` вопрос не имеет
смысла вообще.

**Цвет на уровне `ProjectItem`, а не `Project`.** Явно отклонено
пользователем в постановке задачи, не рассматривается как гибкость на
будущее.

**Хранить только `color_options` без `color_fragment`, парсить позицию
цвета в `canonical_name` заново при каждом вызове `resolve_material_name`.**
Отклонено в п.4 — тот же класс риска, что и первая отклонённая
альтернатива, только перенесённый внутрь одной функции вместо трёх:
`resolve_material_name` пришлось бы заново решать "скобочный или голый
формат" при каждом вызове, вместо использования уже посчитанного один раз
при импорте результата. Дополнительное поле `color_fragment` — небольшая
цена (одна колонка) за то, чтобы разбор происходил один раз, а не на
каждый рендер/генерацию документа.

## Не в объёме

- Разная цена по цвету — проверено на Шаге 0, не существует в реальных
  данных; если появится в будущем прайсе, это отдельный вопрос (вероятно,
  разделение на два `Material` с разными `internal_sku`, что уже
  поддерживается моделью без изменений), не решается здесь.
- Разные цвета для разных материалов одного проекта — пользователь
  подтвердил, не проектируется, `color_choice` строго один на `Project`.
- Расширение словаря известных цветов сверх `White`/`Bronze` — тривиально
  (новая запись в словаре), не требует структурных изменений схемы, но
  само добавление нового цвета в реальный каталог — будущее событие, не
  проектируется заранее.
- Что происходит с уже созданными `Order`/сгенерированными документами при
  последующем изменении `color_choice` проекта (после того, как заказ уже
  ушёл поставщику с одним цветом, а пользователь потом меняет
  `color_choice`) — генерация использует `color_choice` на момент
  генерации (неявный снимок через разовый вызов `resolve_material_name`,
  см. п.2); ретроактивное перегенерирование уже отправленных документов
  не проектируется здесь, аналогично тому, как ADR-0007 п.2 не
  перегенерирует Order при изменении `AllocationLine` после его создания.
- Полный редизайн `MaterialForm`/`MaterialsPage` для ручного управления
  `color_options`/`color_fragment` при создании/редактировании материала
  вручную (не через импорт) — не запрошено; поля заполняются backfill-ом
  для существующих 294 материалов, будущий импорт новых материалов
  должен использовать тот же парсинг (расширение `import_real_data.py`/
  `xlsx_price_matrix.py` этой логикой — деталь реализации, не отдельное
  архитектурное решение).

  `materials.color_fragment VARCHAR(50) NULL`; `projects.color_choice

  материалов происходит отдельным одноразовым скриптом (п.1), не в теле

  dry-run по умолчанию, `--apply` для записи, отчёт для ручной проверки

  `color_fragment`.
