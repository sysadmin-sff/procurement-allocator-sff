# ADR-0032: Шаблоны проектов (ProjectTemplate)

Статус: Принято — backend реализован (`backend/app/api/template.py`,
`backend/app/models/project_template.py`, миграция `5e49cad05696`).
Frontend (экран управления шаблонами, выбор шаблона в
`ProjectBuilderPage.tsx`) — отдельная задача, ещё не реализована.

## Контекст

С реального созвона с руководством: сотрудники отдела монтажа регулярно
создают проекты с почти одинаковым набором материалов (например,
"стандартная дверь", "стандартный патио") и каждый раз набирают этот
список руками через `MaterialCombobox` в конструкторе проекта
(`frontend/src/routes/ProjectBuilderPage.tsx`). Нужен способ администратору
заранее задать несколько именованных шаблонов, чтобы сотрудник мог быстро
подставить нужный набор материалов вместо повторного ручного набора.

Уточнение от пользователя сузило исходную идею до конкретной формы:

- Несколько именованных шаблонов на выбор, не один универсальный список.
- Позиции шаблона не хранят количество — при применении все добавляются с
  `quantity=1`, сотрудник правит количество вручную после применения.
- Применение — только в момент создания проекта, опционально (есть явный
  вариант "без шаблона"). Один шаблон на один акт создания, без накопления
  нескольких шаблонов разом.
- Применение к уже существующему проекту — вне объёма.

Текущий флоу создания проекта (`ProjectBuilderPage.tsx`) не имеет отдельного
модального "создать проект" действия — проект создаётся **лениво**, на
первый автосейв (первое изменение title или первой заполненной строки, см.
`ensureProjectCreated`, ADR-0004). До этого момента `POST /projects` вообще
не вызывается. Выбор шаблона обязан вписаться в эту модель, а не
предполагать отдельный explicit submit-экран, которого сейчас не
существует.

## Решение

### 1. Модель данных

```
ProjectTemplate
  id (uuid, pk)
  name (string, not null, unique)
  created_at (timestamp, not null)

ProjectTemplateItem
  id (uuid, pk)
  template_id (uuid, fk -> ProjectTemplate, not null)
  material_id (uuid, fk -> Material, not null)
  -- нет quantity
```

**`quantity` в `ProjectTemplateItem` не нужен, решение явное, не по
умолчанию.** Единственное допустимое значение — константа `1` (задача
прямо это формулирует: "все позиции добавляются с количеством 1"). Хранимое
поле, которое во всех строках всегда равно одной и той же константе, не
несёт информации — оно только создаёт риск (кто-то однажды передаст другое
значение через API/миграцию данных, и это будет молча воспринято как
осмысленное отличие, которого на самом деле нет) без какой-либо выгоды.
Если в будущем понадобится шаблон с зафиксированным количеством на позицию
— это самостоятельное расширение требований, а не то, что решается сейчас;
поле добавляется тогда, когда реально появится причина хранить значение,
отличное от implicit "1".

Уникальность `(template_id, material_id)` — партийный индекс на
`ProjectTemplateItem`, чтобы один материал не попал в шаблон дважды
(симметрично тому, что `internal_sku` уникален на `Material`, принцип 3
CLAUDE.md — не дублировать одну и ту же сущность в рамках одной связи).

**Почему `unique` на `ProjectTemplate.name`.** Пользователь при выборе
шаблона ориентируется на имя ("стандартная дверь" vs "стандартный патио") —
два шаблона с одинаковым именем создают неоднозначность в UI выбора без
компенсирующей выгоды. `PriceListImport`/`Order` и другие сущности системы
не имеют аналогичного "выбор по имени" UX, поэтому это не общий паттерн
проекта, а свойство именно этой сущности.

Миграция — одна Alembic-ревизия, две новые таблицы. Не трогает существующие
таблицы `Project`/`ProjectItem`/`Material`.

### 2. Admin-only CRUD

Новый роутер `template.py` (`/project-templates`), по образцу
`material.py` (`backend/app/api/material.py`) — `require_role("admin")` на
уровне `APIRouter(...)`, не на отдельных эндпоинтах (ADR-0024 §5, тот же
принцип "не размазывать защиту по местам, которые легко забыть").

Подтверждено явно: это тот же уровень доступа, что Suppliers/Materials/
Prices (ADR-0024 §4) — шаблон — справочные данные ("изменение справочных
данных → admin"), не операционная работа с конкретным проектом. Сотрудник
(`employee`) не создаёт и не редактирует шаблоны, только выбирает готовый
при создании проекта (см. §3 — этот выбор происходит через `project.py`,
роутер которого уже `get_current_user`, не `admin`).

Эндпоинты:

- `GET /project-templates` — список всех, с вложенными items
  (`material_id` + денормализованные поля материала для отображения в UI
  выбора, аналогично тому, как `ProjectWithItemsOut` уже вкладывает
  `ProjectItemOut`).
- `POST /project-templates` — создать (`name`), пустой список items.
- `PATCH /project-templates/{id}` — переименовать (`name`).
- `DELETE /project-templates/{id}` — удалить шаблон целиком (каскадом
  удаляет его `ProjectTemplateItem`, см. §4 про направление каскада внутри
  самого шаблона — это не тот же вопрос, что каскад от `Material`).
- `POST /project-templates/{id}/items` — добавить материал в шаблон
  (`material_id`).
- `DELETE /project-templates/{id}/items/{item_id}` — убрать материал из
  шаблона.

Нет `PUT`/`PATCH` на `ProjectTemplateItem` — нет поля, которое можно было
бы менять (нет `quantity`, см. §1); "изменить позицию" всегда выражается
как удалить + добавить другой материал.

### 3. Применение шаблона при создании проекта — опционально

Экран создания проекта получает выбор шаблона, включая явный вариант "без
шаблона" (текущее поведение — пустой проект). Один выбранный шаблон на
один акт создания, без накопления нескольких разом — соответствует прямому
ограничению задачи, не в объёме этой ADR.

**Механизм в текущей модели ленивого создания.** Раз `POST /projects`
сейчас вызывается неявно из `ensureProjectCreated` при первом автосейве, а
не из явной формы создания, выбор шаблона логично довесить в тело того же
запроса, не создавать отдельный экран/шаг:

```
POST /projects
{
  "title": "...",
  "template_id": "<uuid> | null"
}
```

Backend: `create_project` (`app/api/project.py`) — если `template_id`
передан и найден, после создания `Project` в той же транзакции создаёт
`ProjectItem(project_id=project.id, material_id=item.material_id,
quantity=1)` для каждого `ProjectTemplateItem` шаблона. `template_id`
не найден → `404`, ничего не создаётся (как и текущий `get_material`/
`get_project` паттерн 404 в этом файле). `template_id=null`/отсутствует —
поведение не меняется, пустой проект, как сейчас.

**Фронтенд-следствие.** `ProjectBuilderPage.tsx` сейчас создаёт проект
только на первое изменение title/строки — значит, выбор шаблона должен
происходить **до** первого такого изменения и попасть в тот самый первый
`ensureProjectCreated`/`projectsApi.create` вызов, не в отдельный
последующий запрос. Практически: экран получает выбор шаблона как часть
самого начального состояния страницы (например, компактный selector над
полем "Название проекта" на пустом, ещё не сохранённом проекте), значение
которого прокидывается в `ensureProjectCreated` → `projectsApi.create`.
После того как проект создан (`projectIdRef.current` заполнен),
selector скрывается/дизейблится — повторное применение к уже существующему
проекту не в объёме (см. "Не в объёме" ниже), и текущая функция
`ensureProjectCreated` вызывается многократно за жизнь черновика (на
каждый новый filled row) — принятие `template_id` должно быть учтено
только в первом вызове, вариант это не решить архитектурно значимо сейчас
здесь фиксируется как деталь реализации, не архитектурное решение.

Именно применение к строкам, добавленным сразу после выбора шаблона —
обычные `ProjectItem`, дальше ведут себя как строки в `rows`, добавленные
руками (материал/количество редактируются, строка удаляется тем же
`removeRow`) — фронтенд не отличает их происхождение (см. §5).

### 4. Удаление материала, на который ссылается шаблон — мягкая связь, `ON DELETE CASCADE`

`ProjectTemplateItem.material_id` — `ForeignKey("materials.id",
ondelete="CASCADE")`. Удаление материала автоматически убирает
соответствующие строки `ProjectTemplateItem` (сам `ProjectTemplate`
остаётся, просто с одной позицией меньше), не блокирует `delete_material`
как `IntegrityError`.

**Обоснование, явно, за и против.**

За мягкую связь (принятое решение):
- Шаблон — это UX-удобство подстановки, не исторический/денежный документ.
  В отличие от `Price` (боевая цена, влияет на расчёт закупки прошлых
  периодов) и `ProjectItem` (состав реального проекта, на основе которого
  уже мог быть посчитан `AllocationRun`/создан `Order` — удалить материал
  из-под него означало бы тихо искажать историю уже свершившегося
  расчёта/заказа), `ProjectTemplateItem` не фиксирует ничего, что уже
  произошло — это просто "текущий рекомендуемый набор для быстрого старта".
  Материал, который перестал существовать в каталоге, не должен быть
  причиной, по которой админ не может его удалить, если шаблон, в котором
  он значится, никому не мешает — блокировка здесь была бы чисто
  бюрократическим препятствием без содержательной причины.
- Симметрично уже описанному в `docs/known-issues.md`: `delete_material`/
  `delete_supplier` сегодня блокируют удаление даже когда остались только
  исторические/неактивные связанные записи ("нет пути 'депрецировать',
  только 'нельзя удалить, пока есть любая связанная запись'") — это
  зафиксировано как известное ограничение, не желаемое поведение. Не стоит
  сознательно копировать это ограничение на новую сущность, у которой нет
  того же исторического веса, который изначально мотивировал жёсткую
  блокировку у `Price`/`ProjectItem`.

Против (рассмотрено, не выбрано):
- Мягкий каскад означает, что шаблон может тихо "похудеть" без уведомления
  админа, который его завёл — если материал удалили, а админ не помнит,
  что он входил в "стандартную дверь", шаблон применится с одной позицией
  меньше без явного предупреждения в UI CRUD-экрана шаблонов. Это реальная
  потеря видимости, но её стоимость ограничена (админ, работающий с
  экраном шаблонов, увидит текущий состав при следующем открытии — не
  скрытая порча данных, а просто отсутствие retroactive-уведомления о
  событии в прошлом) и не сопоставима по цене с блокировкой удаления
  материала из-за одной строки в списке для быстрого подбора.

Итог: мягкое поведение оправдано разницей в природе связи (шаблон — не
история), решение принято явно, а не как побочный эффект отсутствия
внимания к вопросу.

### 5. ProjectItem, добавленные из шаблона — не отличаются от добавленных вручную

Подтверждено явно: после применения шаблона на новом проекте это обычные
строки `ProjectItem` — сотрудник свободно редактирует количество, меняет
материал строки, удаляет строку, добавляет новые. Никакой
"заблокированности" или связи с шаблоном на уровне поведения. Полностью
соответствует принципу, что шаблон — это удобство первичного набора, не
постоянное ограничение состава проекта.

**`ProjectItem.source_template_id` (nullable FK → `ProjectTemplate`, для
статистики "какие шаблоны реально используются") — сознательно отложено,
не реализуется в этой задаче.** Решение явное, не молчаливое упущение:

- Не нужно ни для одной функции текущего объёма задачи (§1-4 выше не
  зависят от знания происхождения строки) — добавление колонки сейчас было
  бы преждевременной подготовкой под гипотетическую будущую аналитику, а
  не тем, что решает текущую задачу (YAGNI).
  `ON DELETE SET NULL` понадобился бы при удалении шаблона, чтобы не
  сломать существующие `ProjectItem`, — дополнительная сложность миграции
  без потребителя её значения сегодня.
- Условие возврата к вопросу: если/когда появится реальный запрос
  "показать, какие шаблоны реально ускоряют работу" (например, обсуждение
  с руководством о том, стоит ли заводить больше шаблонов, или какие
  недоиспользуются) — тогда это отдельная небольшая задача (одна nullable
  колонка + одна строка в `create_project`, не архитектурное изменение,
  вероятно не требует нового ADR, если не меняет ничего из решённого
  здесь). До этого момента фиксируется здесь как известный, осознанно не
  реализуемый сейчас вопрос — не переоткрывать это обсуждение при следующей
  сессии, если не появится новый повод (тот же принцип, по которому
  `docs/known-issues.md` фиксирует уже рассмотренные-и-отложенные пункты).

## Альтернативы

**Один универсальный список материалов на все проекты, без множественных
именованных шаблонов.** Отклонено — явно противоречит уточнению
пользователя ("не один универсальный список… возможны несколько именованных
шаблонов на выбор").

**`quantity` на `ProjectTemplateItem`, всегда равное 1 по default.**
Рассмотрено и отклонено — см. §1. Хранение константы без вариативности не
даёт информации, только риск немого рассинхрона в будущем, если кто-то
интерпретирует поле как значимое.

**Жёсткая блокировка удаления материала при наличии `ProjectTemplateItem`
(тот же принцип, что `Price`/`ProjectItem`).** Рассмотрено, отклонено в
пользу `ON DELETE CASCADE` — см. §4 полный разбор "за и против".

**`ProjectItem.source_template_id` реализуется сразу.** Рассмотрено,
отложено — см. §5. Не отклонено навсегда, явно отложено с зафиксированным
условием возврата.

**Применение шаблона к уже существующему проекту (кнопка "применить
шаблон" на экране редактирования, не только при создании).** Вне объёма —
прямое ограничение постановки задачи ("задача явно про момент создания").
Если понадобится позже — вероятно тот же backend-эндпоинт `POST
/projects/{id}/apply-template` с той же семантикой добавления
`ProjectItem(quantity=1)` для каждой позиции шаблона, но это отдельное
решение (например: что происходит при пересечении с уже существующими
позициями того же материала — накопить количество или создать вторую
строку? — вопрос, который не возникает в объёме "применение только на
пустом новом проекте", поэтому сознательно не решается здесь).

**Накопление нескольких шаблонов на одном акте создания.** Вне объёма —
прямое ограничение постановки задачи. Данные модели (§1) этому не мешают
технически (ничего не предполагает "ровно один" на уровне схемы), но API
контракт §3 (`template_id: <uuid> | null`, единственное значение, не
список) отражает именно этот явный предел объёма — расширение до списка
было бы отдельным решением API-контракта, не автоматическим следствием
модели данных.

## Последствия

- Новая Alembic-миграция: таблицы `ProjectTemplate`, `ProjectTemplateItem`
  (последняя — с `ON DELETE CASCADE` на оба FK: `template_id` и
  `material_id`).
- Новый роутер `backend/app/api/template.py`, `require_role("admin")` на
  уровне `APIRouter`. Регистрация в `app/main.py` рядом с существующими
  `include_router` вызовами.
- `POST /projects` (`app/api/project.py`) — новое опциональное поле
  `template_id` в `ProjectCreate`, логика подстановки позиций шаблона в
  той же транзакции создания проекта.
- `docs/data-model.md` — добавить `ProjectTemplate`/`ProjectTemplateItem`
  в ER-диаграмму, отметить `ON DELETE CASCADE` от `Material`.
- `docs/architecture.md` — новый компонент "Шаблоны проектов" (admin CRUD
  → `ProjectTemplate` → опциональный вход в `create_project`).
- Frontend: новый admin-экран управления шаблонами (по аналогии с
  `MaterialsPage`/`SuppliersPage`), плюс правка `ProjectBuilderPage.tsx` —
  выбор шаблона на пустом, ещё не созданном проекте, до первого
  `ensureProjectCreated`.
- Тесты (backend, обязательны по аналогии с существующим покрытием
  material/supplier CRUD): admin-only 403 для `employee`/без сессии на
  `/project-templates/**`; `create_project` с валидным `template_id`
  создаёт правильные `ProjectItem` с `quantity=1`; с несуществующим
  `template_id` → 404, ничего не создано; удаление материала, входящего в
  шаблон, не блокируется и убирает позицию из шаблона (не удаляет сам
  `ProjectTemplate`).
- Реализация (backend/frontend раздельно) — предмет отдельной задачи, вне
  объёма этой ADR.
