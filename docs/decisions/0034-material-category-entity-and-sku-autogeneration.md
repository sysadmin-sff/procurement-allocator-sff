# ADR-0034: Category как управляемая сущность, автогенерация internal_sku, requires_single_supplier вместо STRICT_CATEGORIES

Статус: Предложено

## Контекст

Сейчас при создании материала (`backend/app/api/material.py:create_material`,
`MaterialCreate` в `backend/app/api/schemas/material.py`) администратор
вводит `internal_sku` руками и `category` — свободный текст
(`Material.category: String(100), nullable=True`, `backend/app/models/material.py:21`).
Два независимых риска этого состояния:

1. **Дубли/опечатки `internal_sku` и `category`.** Ничто не мешает второму
   администратору ввести `category="doors"` или `"Door"` вместо `"Doors"` —
   такая строка молча не попадёт ни в `STRICT_CATEGORIES`
   (`backend/app/allocation/solver.py:27`), ни в `CATEGORY_SKU_PREFIX`
   (`backend/app/scripts/xlsx_price_matrix.py:59-68`), без ошибки или
   предупреждения где-либо в системе — просто иначе посчитается солвер для
   этого материала (нестрогая группировка вместо строгой), и это не будет
   замечено, пока кто-то не сравнит цветовую согласованность на объекте.
2. **`STRICT_CATEGORIES` — хардкод-константа кода** (ADR-0028), изменение
   набора строгих категорий требует деплоя, что прямо противоречит цели
   этой задачи ("управляемый через БД флаг").

Пользователь подтвердил объём: `Category` — новая сущность с полями `id`,
`name` (unique), `sku_prefix` (unique), `requires_single_supplier: bool`,
`created_at`; `Material.category_id` — FK; `internal_sku` генерируется из
`sku_prefix`, не вводится вручную; удаление категории с материалами —
блокируется явной ошибкой.

**Ровно 294 материала, 8 существующих строковых значений `category`** —
подтверждено в ADR-0028 фактическим запуском `parse_price_matrix` над
реальным файлом (не предположение): `Doors` (26), `Gutter` (29), `Profil`
(68), `Mesh` (57), `Roof panels` (34, из них 29 без цены ни у одного
поставщика — известный, не связанный с этой задачей пробел каталога),
`Connectors` (49), `Screws` (29), `Caulk` (2). `STRICT_CATEGORIES` =
`{Doors, Gutter, Profil, Mesh, Roof panels}` — ровно те пять, для которых
`requires_single_supplier=True` после миграции; `Connectors`/`Screws`/`Caulk`
получают `requires_single_supplier=False`.

Это ЯДРО системы: солвер (`backend/app/allocation/solver.py`) читает
`STRICT_CATEGORIES` как источник истины для soft-ограничения ADR-0028.
Любая ошибка в переносе этого набора в БД **молча меняет поведение
allocation engine для всего каталога** — тот же уровень риска и та же
строгость регрессионного тестирования, что уже применены при самом
введении `STRICT_CATEGORIES` (ADR-0028).

**Второй, не названный в задаче call site того же хардкода — найден при
подготовке этого ADR.** `backend/app/allocation/service.py:208-229`,
`_compute_split_categories` — вычисляет `AllocationRun.split_categories`
(ADR-0028 §4) через собственную проверку `if category not in
STRICT_CATEGORIES` (строка 222), импортируя ту же константу
(`service.py:1` — `from app.allocation.solver import STRICT_CATEGORIES,
...`, подтверждено grep). Задача явно называет только `solver.py`, но
`_compute_split_categories` — второй потребитель той же константы: если
рефакторинг заменит источник истины в `solver.py`, но не в `service.py`,
рассинхрон снова станет молчаливым (например, при добавлении новой
категории с `requires_single_supplier=True` через новый admin-экран —
`solver.py` начнёт группировать материалы этой категории, но `service.py`
не будет отражать это в `split_categories`, то есть предупреждение на
UI не появится для реально разбитой строгой категории). Оба call site
обязаны читать одно и то же поле одним и тем же способом — это часть
объёма рефакторинга п.3, не отдельная задача.

**Исчерпывающий grep по всей кодовой базе (не только
`backend/app/allocation/`) — найдены ещё два места, ни одно из которых
не названо в задаче.** По прямому запросу перед финализацией выполнен
`grep -rn "\.category\b" backend/app --include=*.py | grep -v test` —
полный список непустой (не только `allocation/`):

```
backend/app/allocation/service.py:102   (сборка MaterialInput — уже учтено выше)
backend/app/allocation/service.py:210,215 (_compute_split_categories — уже учтено выше)
backend/app/allocation/solver.py:93     (STRICT_CATEGORIES — предмет самого рефакторинга §3)
backend/app/allocation/types.py:18      (докстринг поля MaterialInput.category)
backend/app/api/material.py:42          (create_material — payload.category, предмет §1/§5)
backend/app/api/template.py:34          (_to_out — item.material.category)
backend/app/price_ingestion/matching.py:111 (_candidate_context — LLM-промпт)
backend/app/scripts/import_real_data.py:169,236 (разовый исторический импорт)
```

**Третье место — `backend/app/price_ingestion/matching.py:108-114`,
`_candidate_context`.** Строит текстовый контекст кандидатов-материалов
для LLM-промпта матчинга строки прайс-листа (ADR-0019 §1, "матчинг
названий материалов" — CLAUDE.md принцип 2, ровно тот случай, где вход
неструктурированный и допустим LLM): `f"категория={m.category!r}, ..."`
— читает `Material.category` напрямую как строку внутри f-строки,
подставляемой в `_PROMPT_TEMPLATE` (строка 125, `{candidates_context}`).
После замены `Material.category` (String) на `category_id` (FK) это
выражение либо сломается (`AttributeError`, если колонка `category`
физически исчезает — миграция дропает её, см. п.2 шаг 4), либо (если бы
`category` осталось relationship-полем с тем же именем, как решено в
п.1) вывело бы `repr()` ORM-объекта `Category` (что-то вроде
`<app.models.category.Category object at 0x...>`) вместо
человекочитаемого имени — оба исхода портят промпт, которым LLM реально
пользуется для решения "это тот же материал или нет" (ADR-0025 —
matching работает по фиксированному каталогу, категория в контексте
кандидата — часть того, чем LLM отличает, например, одноимённые, но
разнокатегорийные материалы). Это не косметическая правка — если её
пропустить, регресс проявится не сразу и не как ошибка, а как тихая
деградация качества матчинга (LLM видит мусор вместо категории и получает
меньше сигнала, чем раньше), обнаруживаемая только на реальном прогоне
импорта прайса, что прямо тот класс риска, который эта секция ADR
призвана исключить перечислением, а не полаганием на то, что "выяснится
само" при ручном тестировании.

**Четвёртое место — `backend/app/api/template.py:34` /
`backend/app/api/schemas/template.py:28`.** `_to_out`
(`ProjectTemplateOut` сериализация, ADR-0032 §2) читает
`item.material.category` и кладёт в `ProjectTemplateItemOut.category:
str | None` — тот же паттерн денормализации отображаемого имени, что уже
есть в `MaterialOut` (`backend/app/api/schemas/material.py:33`). Оба
поля объявлены как `str | None` в Pydantic-схемах — после замены
`Material.category` на relationship это либо ломает сериализацию (Pydantic
`from_attributes=True` попытается присвоить ORM-объект `Category` полю,
типизированному `str | None`, и упадёт валидацией), либо молча
сериализует не то, что ожидает фронтенд, если тип поля не поправить
одновременно с моделью. И `MaterialOut.category`, и
`ProjectTemplateItemOut.category` должны быть переименованы в
`category_name: str` (не `str | None` — после этой задачи `category_id`
обязателен, см. п.1, значит имя категории у существующего материала
всегда есть) и читать `material.category.name` (relationship), не
`material.category` напрямую. Это правка **двух** Pydantic-схем и **двух**
функций сериализации (`material.py` — неявно, через `from_attributes`;
`template.py:_to_out` — явно, ручная сборка) в рамках объёма §3, не
последующая доработка, обнаруженная после того, как фронтенд сломается.

**Пятое место, значимо более серьёзное и найденное не самим grep, а
только когда его результат подвергся сомнению при реализации —
`backend/app/price_ingestion/apply.py:_apply_new` (ADR-0019 §5),
второй, отдельный от `create_material`, путь создания `Material`.**
`grep -rn "\.category\b"` (и любой его вариант, ищущий обращение к
атрибуту `category`) по построению не может найти код, который создаёт
`Material` **вообще без категории** — там просто нет токена `.category`
для совпадения. Именно так пропущен `_apply_new`: он строит
`Material(internal_sku=..., canonical_name=..., unit="unit",
attributes={})` без единого упоминания категории — не потому что
категория ему не нужна, а потому что этот путь исторически (ADR-0019, до
самой идеи `Category` как сущности) никогда её не имел, и поэтому не
совпал ни с одним `grep`-паттерном, построенным вокруг существующего
употребления `.category`.

Путь реальный, не отмерший: `_apply_new` — backend-сторона действия
`action="new"` в `POST /price-list-imports/{id}/entries/{id}/apply`
(ADR-0019 §5), вызываемого из `PriceListImportReviewPage.tsx` — когда
строка прайс-листа не сопоставлена ни с одним материалом (`not_found`),
экран ревью показывает поля ручного ввода `internal_sku` и
`canonical_name`, и кнопка "Применить" вызывает именно этот путь. Найден
только когда `_apply_new` был выполнен вручную для проверки уже после
того, как этот ADR считался готовым к реализации, и упал на `NOT NULL`
ограничении `materials.category_id` — то есть после того, как объём
задачи здесь уже считался закрытым по результатам "исчерпывающего" grep.

Второе следствие того же пробела: `_apply_new` принимает `internal_sku`
как свободный текст от рецензента (`ApplyEntryIn.internal_sku`) —
ровно та же проблема ручного ввода SKU, которую пп.4/7 устраняют для
`create_material`, здесь остаётся нетронутой, если её не устранить тем
же способом. Оба следствия (отсутствие категории и ручной SKU) устраняет
новый п.7 ниже — второй путь создания материала обязан подчиняться тому
же принципу, что и основной: категория выбирается, `internal_sku`
генерируется сервером через ту же атомарную функцию, не вводится вручную.

**Урок для будущих аналогичных проверок, зафиксированный явно, не только
как исправленный пробел.** "Исчерпывающий grep" по обращению к полю,
которое заменяется/вводится, находит только код, уже знающий об этом
поле — он не находит код, который создаёт ту же сущность в обход поля
вообще (пустым/дефолтным значением, отсутствующим параметром/аргументом
конструктора). Для проверки полноты объёма задачи, вводящей обязательное
поле на существующей сущности, правильный дополнительный запрос — не
только `grep .category`, а также `grep -rn "Material("
backend/app` (все конструкторы сущности целиком, вне зависимости от
того, что они сейчас передают), с ручной проверкой каждого найденного
места на использование нового обязательного поля. Именно смена самого
паттерна поиска (не повтор старого grep) на "все конструкторы
`Material`" и нашла `apply.py` как единственное не учтённое выше место.

## Решение

### 1. Модель данных `Category`

```
Category
  id (uuid, pk)
  name (string, not null, unique)
  sku_prefix (string(10), not null, unique)      -- неизменяемо после создания, см. п.5
  requires_single_supplier (bool, not null, default false)
  next_sku_number (integer, not null, default 1)  -- см. п.4
  created_at (timestamp, not null)

Material
  category_id (uuid, fk -> Category, not null)   -- заменяет category (String)
```

**`Material.category` (String) полностью заменяется на `category_id` (FK),
старая колонка удаляется, не сохраняется параллельно.** Рассмотрены обе
альтернативы:

- *Оставить `category: String` для отображения/обратной совместимости,
  рядом с `category_id: FK`.* Отклонено — прямо противоречит принципу 3
  CLAUDE.md ("уникальность материала — по `internal_sku`… связь
  переиспользования — отдельная таблица, не колонка"), применённому здесь
  по аналогии: две колонки, одна из которых производна от другой
  (`category` как денормализованный снимок `category_id -> Category.name`),
  создают тот же класс риска рассинхрона, который принцип 3 уже запрещает
  для `SupplierMaterialAlias`. Конкретный сценарий поломки: админ
  переименовывает `Category.name` через новый admin-экран (п.5) — если
  `Material.category` не пересчитывается по всем материалам этой категории
  синхронно, любой код, читающий `Material.category` напрямую
  (сериализация, будущий отчёт), покажет устаревшее имя, пока не найдётся
  причина искать именно `category_id`. Ничего не выигрывается взамен: имя
  категории доступно всегда через `relationship` за одну JOIN, тот же
  паттерн, что уже применён в `template.py:_to_out`
  (`item.material.canonical_name` через `joinedload`).
- **Выбрано: полная замена на `category_id: FK`, отображаемое имя —
  через `relationship` (`Material.category` становится relationship-полем
  на `Category`, не колонкой).** Единственный источник истины для имени —
  `Category.name`; сериализация (`MaterialOut`) отдаёт вложенный объект
  или `category_name: str` вычисляемым полем поверх `relationship`, не
  хранимой колонкой. Все существующие потребители `Material.category` как
  строки (`solver.py`, `service.py`, `template.py:_to_out`,
  `MaterialOut`/`MaterialCreate`/`MaterialUpdate`,
  `xlsx_price_matrix.py`/`import_real_data.py` — импорт из прайса) должны
  быть найдены и обновлены на `category_id`/`category.name` — это часть
  объёма реализации, не последующая доработка (см. "Последствия").

**`Category.next_sku_number` — часть модели данных Category, не отдельная
таблица-счётчик.** Обоснование в п.4 (атомарность в той же транзакции
создания материала), но сама колонка фиксируется здесь как часть схемы.

### 2. Backfill существующих 294 материалов — dry-run/--apply, по образцу `backfill_color_options.py`

Новый скрипт `backend/app/scripts/backfill_material_categories.py`,
тот же паттерн, что `backfill_color_options.py` (`backend/app/scripts/
backfill_color_options.py`): функция `run_backfill(db, apply)` возвращает
структурированный отчёт, `print_report` печатает его человекочитаемо,
`--apply` обязателен для реальной записи, dry-run по умолчанию.

**Отличие от `backfill_color_options.py` по критичности — явно
отмечено, не скрыто общим паттерном.** `backfill_color_options` заполняет
новое информационное поле (`color_options`), ошибка в нём —
косметический баг отображения цвета. Здесь backfill **определяет
`requires_single_supplier` для каждой из 8 категорий**, то есть напрямую
управляет поведением ILP-солвера для всего каталога сразу после
`--apply` — это тот же уровень последствия, что сам переход ADR-0028 от
отсутствия группировки к `STRICT_CATEGORIES`. Отчёт dry-run обязан
явно печатать **сопоставление имя-категории → `requires_single_supplier`
→ количество материалов**, чтобы админ мог свериться с ожидаемым списком
(`{Doors, Gutter, Profil, Mesh, Roof panels} -> True`, остальные три ->
`False`) визуально перед `--apply`, а не полагаться на то, что скрипт
"наверное" сделал правильный маппинг.

**Шаги backfill:**

1. Создать 8 строк `Category` — `name` = каждое из 8 существующих
   значений `Material.category` (различные строки, найденные `SELECT
   DISTINCT category FROM materials`, не хардкод-список в самом скрипте —
   иначе скрипт сам стал бы вторым местом с тем же риском рассинхрона,
   который эта задача устраняет). `sku_prefix` = значение из
   `CATEGORY_SKU_PREFIX` (`xlsx_price_matrix.py:59-68`) для этого имени
   (переиспользуется, как и просит задача) — **явная ошибка (не
   молчаливый fallback на `MISC`/произвольный префикс), если
   `SELECT DISTINCT category` вернёт значение, которого нет в
   `CATEGORY_SKU_PREFIX`** (сегодня такого нет — ADR-0028 подтвердил
   точное совпадение множеств, но backfill не должен молча полагаться на
   то, что это по-прежнему верно на момент своего запуска, если между
   ADR-0028 и этой задачей кто-то создал материал с девятой строкой
   `category` через API в обход импорта). `requires_single_supplier` =
   `True` для имени в `{Doors, Gutter, Profil, Mesh, Roof panels}`
   (константа **внутри backfill-скрипта**, не в `solver.py` — после этой
   задачи `solver.py` больше не содержит список имён категорий вообще, см.
   п.3), `False` иначе. `next_sku_number` = `(текущий MAX numeric suffix
   среди internal_sku этого префикса) + 1` — вычисляется из уже
   существующих `internal_sku` вида `{prefix}-{NNN}` (формат
   `_next_sku` в `xlsx_price_matrix.py:116-119`), не от `1`, иначе первый
   новый материал этой категории после backfill получил бы SKU,
   дублирующий уже существующий.
2. Для каждого материала — `UPDATE materials SET category_id = <id
   соответствующей Category> WHERE category = <старое строковое
   значение>`.
3. **Верификация перед выводом успеха**: после backfill количество
   материалов с `category_id IS NULL` должно быть равно количеству
   материалов, у которых `category IS NULL` было **до** backfill (то
   есть backfill не оставляет ни одного материала с непустым старым
   `category`, но без нового `category_id` — молчаливая потеря связи).
   Если это не так — скрипт обязан завершиться ошибкой и **не**
   продолжать (в dry-run — просто напечатать несоответствие; в `--apply`
   — откатить транзакцию, не коммитить частичный результат).
4. Миграция дропает старую колонку `Material.category` (String) — **в той
   же Alembic-миграции, что вводит `category_id`, но backfill (шаг 2) —
   отдельный скрипт, запускаемый вручную между `alembic upgrade` "добавить
   category_id nullable" и следующей ревизией "сделать category_id
   not null + дропнуть category"**. Это стандартный two-phase паттерн для
   backfill с последующим `NOT NULL` (тот же принцип, что `alembic upgrade
   head` в CLAUDE.md подразумевает пошаговую миграцию, не единственный
   big-bang шаг) — конкретное разбиение на ревизии фиксируется здесь как
   архитектурное требование (не молчать про промежуточное состояние
   `category_id nullable`), точные номера ревизий — деталь реализации.

**Обязательная ручная проверка перед `--apply` на реальных данных** (по
прямому требованию задачи "критично проверить вручную перед --apply") —
описывается в самом выводе dry-run-отчёта (текстовая инструкция в
`print_report`, не отдельный документ): свериться, что все 5 категорий
из `STRICT_CATEGORIES` (см. текущее значение в `solver.py` **до**
удаления константы этим ADR) получили `requires_single_supplier=True` в
отчёте, остальные 3 — `False`, и что нет неожиданной 9-й категории.

### 3. Рефакторинг `solver.py` и `service.py` — оба call site, не только `solver.py`

**`MaterialInput.category: str | None` (`backend/app/allocation/types.py:14-20`)
заменяется на `MaterialInput.requires_single_supplier: bool` и
`MaterialInput.category_name: str | None`.** Обоснование раздельных полей,
не одного:

- `requires_single_supplier` — единственное, что нужно солверу для
  логики группировки (текущая проверка `if cat in STRICT_CATEGORIES` →
  `if material.requires_single_supplier`), но солверу всё ещё нужен
  идентификатор категории **как ключ группировки** (несколько разных
  строгих категорий в одном проекте линкуются раздельно —
  `materials_by_category` в `solver.py:94-98` группирует именно по
  значению категории, не только по булеву флагу: два материала из
  `Doors` и `Mesh` оба `requires_single_supplier=True`, но не должны
  линковаться друг с другом). Ключ группировки — `category_id` (уникален,
  стабилен при переименовании — см. п.5), не `category_name`
  (переименование не должно требовать инвалидации in-flight allocation
  run). `category_name` остаётся только для `split_categories` (нужно имя
  для текста предупреждения на UI, не только факт разброса), передаётся
  отдельно, солвер сам не использует его для логики группировки — только
  прокидывает как часть данных, которые видит.

  Итоговая правка типа: `MaterialInput.category_id: str | None`,
  `MaterialInput.requires_single_supplier: bool = False`,
  `MaterialInput.category_name: str | None = None` (используется только
  для отображения/`split_categories`, не для группировки).
- `solver.py`: `STRICT_CATEGORIES` (модульная константа, строка 27)
  **удаляется полностью**. `materials_by_category` (строки 93-98) строится
  как `if m.requires_single_supplier: materials_by_category.setdefault(
  m.category_id, []).append(m.material_id)` — группировка по
  `category_id`, не по членству в множестве имён. Остальная механика §1/§2
  ADR-0028 (`diff[C][m]`, опорный материал, штраф) **не меняется** —
  рефакторинг затрагивает только источник признака "эта категория
  строгая" и ключ группировки, не саму ILP-формулировку. `CATEGORY_SPLIT_PENALTY_K`
  не трогается этой задачей.
- `service.py:_compute_split_categories` (строки 208-229) — второй call
  site, найденный при подготовке ADR (см. "Контекст"). Запрос строки
  214-217 (`select(Material.category, AllocationLine.supplier_id).join(...)`)
  переписывается на `select(Category.name, Category.requires_single_supplier,
  AllocationLine.supplier_id).join(Material, ...).join(Category, ...)`
  (или эквивалентно — джойн через `Material.category_id`), проверка строки
  222 (`if category not in STRICT_CATEGORIES`) заменяется на `if not
  requires_single_supplier: continue`. **Оба call site читают один и тот
  же `Category.requires_single_supplier` одним и тем же способом (через
  JOIN на `Category`, не через дублирующую константу в `service.py`)** —
  это явное условие приёмки рефакторинга, не подразумеваемое следствие.
- `service.py` — там, где сейчас строится `MaterialInput(...,
  category=material.category)` (место, где `AllocationInput.materials`
  собирается из `Material` перед вызовом `solve_allocation`) — передаёт
  `category_id=str(material.category_id)`,
  `requires_single_supplier=material.category.requires_single_supplier`,
  `category_name=material.category.name`.
- **`backend/app/price_ingestion/matching.py:_candidate_context`** (третье
  место, см. "Контекст") — `f"категория={m.category!r}"` заменяется на
  `f"категория={m.category.name!r}"`. Единственная правка в этом файле в
  рамках этой задачи — сама логика матчинга (промпт, дедупликация,
  ADR-0019/0022/0023/0025) не переоткрывается, меняется только то, откуда
  берётся строка имени категории внутри уже существующей f-строки.
  Регрессионный тест: существующие тесты `price_ingestion/test_matching.py`
  (если строят `Material` через фабрику/фикстуру с `category` как
  строкой) должны быть поправлены на создание `Category` + `category_id`
  и проверять, что `_candidate_context` по-прежнему выводит
  человекочитаемое имя категории в промпте, не `repr()` ORM-объекта.
- **`backend/app/api/template.py:_to_out` и
  `backend/app/api/schemas/template.py:ProjectTemplateItemOut`** (четвёртое
  место, см. "Контекст") — `category: str | None` переименовывается в
  `category_name: str`, читает `item.material.category.name`, не
  `item.material.category`. Симметрично для
  `backend/app/api/schemas/material.py:MaterialOut.category` →
  `category_name: str`, `create_material`/`update_material` в
  `material.py` читают `payload.category_id`, не `payload.category`.
- `algorithm_version` (`service.py`, сейчас `"adr-0028-v1"`, см. ADR-0028
  "Последствия") — **не бампается этим ADR**, если регрессионные тесты
  п.3.1 ниже подтверждают буквально идентичное поведение солвера для всех
  8 категорий. ADR-0002 "Последствия" (процитировано в ADR-0028)
  требует новую версию алгоритма только когда "модель ограничений
  изменится" — здесь ILP-формулировка (переменные, ограничения, целевая
  функция) остаётся математически тождественной, меняется только откуда
  берётся булев признак "эта категория строгая" (константа кода → колонка
  БД). Если регрессионные тесты (п.3.1) обнаружат хотя бы одно расхождение
  в решении для существующих 8 категорий — это сигнал, что рефакторинг
  случайно изменил модель, а не повод бампать версию задним числом;
  расхождение должно быть исправлено до мержа, не задокументировано как
  ожидаемое изменение.

#### 3.1. Обязательное регрессионное тестирование — точная формулировка

**Требование дословно из задачи: "не 'похоже на то же самое', а
воспроизведённые тесты ADR-0028 прогнанные заново на новой структуре
данных".** Конкретно:

- Каждый существующий тест в `backend/tests/allocation/test_solver.py`,
  использующий `MaterialInput(..., category="Doors"/"Mesh"/"Connectors"/...)`
  (перечислены в ADR-0028 "Последствия": `test_strict_category_all_materials_at_one_supplier_stays_together`,
  `test_strict_category_prefers_single_supplier_at_moderate_price_difference`,
  `test_strict_category_splits_when_price_difference_is_large_enough`,
  `test_strict_category_no_single_supplier_covers_whole_category_stays_feasible`,
  тест на нестрогую категорию (`Connectors`), `test_strict_category_asymmetric_pair_mechanism_registers_mismatch_via_penalty`,
  `test_strict_category_asymmetric_pair_still_penalized_at_moderate_gap` —
  9 тестов по grep, включая `test_strict_categories_constant_matches_spec`
  и `test_strict_categories_are_a_subset_of_real_catalog_categories`,
  которые перестают существовать в прежней форме, см. ниже) должен быть
  **переписан на новую сигнатуру** (`requires_single_supplier=True/False`,
  `category_id="doors-cat-id"` вместо `category="Doors"`) с **тем же
  ожидаемым результатом** (тот же `status`, те же назначения `x[m][s]`,
  тот же факт наличия/отсутствия штрафа) — не новый тест "похожего"
  поведения, а тот же тест-сценарий на новом API солвера. Ревью этого ADR
  — сверять построчно, что ни один сценарий не выпал и не изменил
  ожидаемый результат при переписывании.
- `test_strict_categories_constant_matches_spec` и
  `test_strict_categories_are_a_subset_of_real_catalog_categories`
  (`test_solver.py:525-536`) **теряют смысл буквально** — после этого
  ADR в `solver.py` нет константы `STRICT_CATEGORIES`, которую можно было
  бы сверить со спецификацией/каталогом. Заменяются тестом на **backfill-скрипт**
  (не на `solver.py`): `test_backfill_maps_exactly_five_categories_to_requires_single_supplier_true`
  — тот же инвариант (ровно `{Doors, Gutter, Profil, Mesh, Roof panels}`
  → `True`), но проверяемый там, где теперь реально живёт это решение
  (dry-run отчёт backfill-скрипта над фикстурой из 8 категорий), не в
  `test_solver.py` (солвер после рефакторинга не знает имён категорий
  вообще, только `category_id`+`bool`, поэтому проверять соответствие
  имени и флага в тестах солвера стало бы проверкой чужой ответственности).
- **Новый тест на `service.py`**: `test_compute_split_categories_matches_solver_requires_single_supplier`
  — категория с `requires_single_supplier=True` и материалами у разных
  поставщиков (после override, по аналогии с существующим тестом
  `test_override.py`, ADR-0028 "Последствия") даёт непустой
  `split_categories`; категория с `requires_single_supplier=False` в той
  же ситуации — не даёт. Это прямая проверка того, что оба call site
  (п.3) остались синхронны после рефакторинга — регрессия, которую задача
  не называла явно, но которую нашёл этот ADR (см. "Контекст").
- Тест на пустой `Category.requires_single_supplier` (новая категория,
  созданная через admin-экран п.5 с `requires_single_supplier=False` по
  умолчанию schema) — материалы такой категории ведут себя как сегодняшние
  `Connectors`/`Screws`/`Caulk`, без штрафа/группировки — не новый
  сценарий по существу, но явно фиксирует, что default `False` (не
  `True`) — осознанный выбор: новая категория без явного решения
  администратора не должна тихо начать наказывать разброс поставщика,
  пока кто-то сознательно не включит `requires_single_supplier`.

### 4. Автогенерация `internal_sku` — атомарный инкремент в транзакции создания материала

**Проблема гонки состояний**, названная в задаче: голый `MAX(internal_sku
существующих этого префикса) + 1` без блокировки — два одновременных
`POST /materials` с одинаковой `category_id` оба читают один и тот же
`MAX`, оба вычисляют один и тот же следующий номер, оба коммитят разные
материалы с одинаковым `internal_sku` → нарушение `UNIQUE` на
`internal_sku`, но **после** того, как один из двух запросов уже успешно
закоммитился, а другой упал по `IntegrityError` уже подготовив материал
под неверным ожидаемым SKU — не структурная защита, а обнаружение
постфактум одной из двух гонок (та, что коммитится второй).

**Решение — `Category.next_sku_number`, инкрементируемый атомарно через
`UPDATE ... SET next_sku_number = next_sku_number + 1 ... RETURNING
next_sku_number` в той же транзакции, что `INSERT` материала**:

```python
# app/api/material.py: create_material, внутри одной транзакции с INSERT Material
result = db.execute(
    update(Category)
    .where(Category.id == payload.category_id)
    .values(next_sku_number=Category.next_sku_number + 1)
    .returning(Category.next_sku_number, Category.sku_prefix)
)
new_number, prefix = result.one()
assigned_sku = f"{prefix}-{new_number - 1:03d}"  # -1: занятый номер — старое значение
material = Material(internal_sku=assigned_sku, category_id=payload.category_id, ...)
db.add(material)
db.commit()
```

Почему это безопасно при параллельном создании двумя администраторами:
`UPDATE ... SET x = x + 1` в PostgreSQL (движок БД проекта — подтверждено
по `postgres`-специфичным конструкциям в существующей кодовой базе,
например частичный уникальный индекс в ADR-0024 §2, `pgvector` в
`Material.embedding`) **атомарен на уровне строки** — второй конкурентный
`UPDATE` той же строки `Category` блокируется первым до его `COMMIT`
(row-level lock, стандартное поведение `UPDATE` в MVCC Postgres), то есть
два одновременных запроса на одну категорию физически не могут прочитать
одно и то же значение `next_sku_number` — один обязан подождать
завершения транзакции другого. Не требует `SELECT ... FOR UPDATE`
отдельной строкой — сам `UPDATE ... RETURNING` уже совмещает чтение
текущего значения и захват блокировки одной атомарной операцией, что
проще и меньше кода, чем явный `SELECT FOR UPDATE` + отдельный `UPDATE`.

**Конкретный числовой пример, обязательный тест — не только пустая
категория.** После backfill реального каталога категория `Doors` содержит
26 материалов с `internal_sku` от `DOOR-001` до `DOOR-026`
(`sku_counters` в `xlsx_price_matrix._next_sku`, подтверждено ADR-0028
подсчётом "Doors — 26"), и `Category.next_sku_number` для неё после
backfill обязан быть выставлен в `27` (`MAX numeric suffix + 1`, см. п.2
шаг 1 — не `1` и не `26`). Тест
`test_create_material_after_backfill_continues_existing_sku_sequence`
(в `backend/tests/api/test_material.py` или
`backend/tests/scripts/test_backfill_material_categories.py`, по месту,
где удобнее собрать фикстуру): fixture воспроизводит `Category(name="Doors",
sku_prefix="DOOR", next_sku_number=27)` и 26 существующих `Material` с
`internal_sku="DOOR-001"`..`"DOOR-026"` (не обязательно 26 реальных строк
— достаточно самого счётчика в правильном состоянии и хотя бы одной
существующей строки с `DOOR-026`, чтобы тест проверял именно
"продолжение последовательности", а не пустую инициализацию) — затем
`POST /materials` с этой категорией **обязан** вернуть материал с
`internal_sku == "DOOR-027"` ровно, не `"DOOR-026"` (переиспользование
последнего занятого номера — реальная гонка, которую призвана
предотвратить эта задача) и не `"DOOR-028"` (пропуск номера, ошибка off-
by-one в `new_number - 1` из примера кода выше). Это прямая проверка
формулы на конкретном числе, отдельная от общих тестов "категория без
материалов начинает с 1" и "два параллельных запроса не коллизируют" —
ни один из них по отдельности не поймал бы off-by-one в вычислении
`assigned_sku` относительно уже занятого диапазона.

**Что если `db.commit()` материала откажет после успешного `UPDATE
Category`** (например, конкурентная гонка на что-то другое, не
`internal_sku` — маловероятно, но не невозможно)? Оба `UPDATE Category`
и `INSERT Material` — одна и та же транзакция SQLAlchemy `Session`
(`db.add(material); db.commit()` уже так делает во всех существующих
`create_*` в этом файле) — откат `commit()` откатывает и инкремент
счётчика, то есть **не** остаётся "дыр" в последовательности номеров при
неудачном создании (не критично по существу — дыры в SKU-нумерации не
нарушают уникальность или бизнес-логику, просто эстетическая
непрерывность, — но откат транзакции целиком даёт эту непрерывность
бесплатно, без дополнительного кода).

**Что происходит с `internal_sku` при смене `category_id` существующего
материала (не создание, а `PATCH /materials/{id}`)?** Не в объёме этой
задачи — задача формулирует автогенерацию только для создания. Если
`MaterialUpdate` позволит менять `category_id` (текущий эндпоинт `PATCH
/materials/{id}` — общий `setattr` по всем переданным полям, технически
ничего не мешает передать `category_id` в теле), `internal_sku` **не
пересчитывается** (нет причины — SKU, единожды выданный, идентифицирует
материал независимо от того, в какую категорию его позже переклассифицировали;
пересчёт задним числом сломал бы уже напечатанные ордер-документы,
ссылающиеся на старый SKU). Фиксируется здесь явно, чтобы не оставлять
открытым вопросом при реализации: `PATCH` может сменить `category_id`
материала (переклассификация без выдачи нового SKU), но не может задать
или изменить `internal_sku` через тело запроса вообще — `internal_sku`
исключается из `MaterialUpdate` полностью (сейчас присутствует, см.
`backend/app/api/schemas/material.py:20`), так как ручной ввод SKU
устраняется этой задачей и для создания, и для последующего изменения —
несогласованно было бы запретить его при создании, но разрешить при
редактировании тем же полем.

### 5. Admin-only CRUD для `Category` — новый роутер `category.py`

По образцу `template.py` (`backend/app/api/template.py`) —
`require_role("admin")` на уровне `APIRouter(...)`, тот же паттерн, что
уже подтверждён дважды (`material.py`, `template.py`) со ссылкой на
ADR-0024 §5 ("не размазывать защиту по местам, которые легко забыть").

```
GET    /categories                  -- список всех
POST   /categories                  -- создать (name, sku_prefix, requires_single_supplier)
PATCH  /categories/{id}             -- переименовать (name) и/или переключить requires_single_supplier
DELETE /categories/{id}             -- удалить, блокируется если есть материалы (см. п.6)
```

**`sku_prefix` неизменяем после создания — явное решение, устраняет
производный вопрос.** `PATCH /categories/{id}` принимает только `name` и
`requires_single_supplier` в теле (схема `CategoryUpdate` не содержит
поля `sku_prefix` вообще, не просто "игнорируется, если передано" — та
же семантика, что `ProjectTemplateItem` не имеет `PATCH`, потому что
менять нечего, ADR-0032 §2). Обоснование: `internal_sku` уже выданных
материалов (`{prefix}-{NNN}`) содержит префикс как часть значения — если
бы `sku_prefix` можно было сменить, все ранее выданные SKU этой категории
стали бы иметь префикс, не соответствующий актуальному имени/префиксу
категории (например, категория "Doors" сначала имела `sku_prefix=DOOR`,
затем администратор сменил на `DOORX` — материалы `DOOR-001..026`
остаются с "устаревшим" префиксом навсегда, новые получают `DOORX-NNN`).
Задача прямо предлагает сделать `sku_prefix` неизменяемым именно чтобы
этот вопрос не возникал — принято без альтернативы, вопрос "что делать
с уже выданными SKU при смене префикса" не рассматривается дальше,
потому что предпосылка (префикс можно сменить) отклонена на уровне API
контракта, а не решается отдельной политикой миграции данных.

**Переименование `name`** (в отличие от `sku_prefix`) не влияет на уже
выданные `internal_sku` (SKU не содержит `name`, только `sku_prefix`) и
не влияет на связь `Material.category_id` (FK на `id`, не на `name`) —
переименование категории мгновенно отражается везде, где имя читается
через `relationship`, без миграции данных. Единственное явное следствие
переименования — уже упомянутое в п.1: любой код, кэширующий имя
категории отдельно от `category_id` (сериализация с записью строки
в другую таблицу, если такая появится в будущем), окажется устаревшим;
на сегодня таких мест не существует за пределами `Material.category`
(String), который эта задача удаляет.

**`requires_single_supplier` переключается тем же `PATCH`** — обычное
поле, без специальной защиты сверх admin-only самого роутера. Эффект
переключения — солвер начинает/перестаёт группировать материалы этой
категории со **следующего** запуска allocation (не ретроактивно —
`AllocationRun` уже посчитанных запусков не пересчитывается сама по себе,
то же поведение, что любое другое изменение справочных данных после
факта: `Price`, `Supplier.flat_fee_cents` и т.д. уже не пересчитывают
прошлые `AllocationRun` задним числом нигде в системе, симметрично).

**`POST /categories` — validation `name`/`sku_prefix` unique** — стандартный
паттерн `IntegrityError` → `409`, как везде в `material.py`/`template.py`
(`"Category with this name/sku_prefix already exists"`).

### 6. Удаление категории с материалами — блокировка, 409, явная ошибка

**Отличие от ADR-0032 §4 (шаблоны, `ON DELETE CASCADE`) — зафиксировано
явно, не оставлено на "по аналогии".** ADR-0032 §4 выбрал мягкий каскад
для `ProjectTemplateItem.material_id`, потому что связь "материал входит
в шаблон" — чисто UX-удобство подстановки, не влияющее на прошлые расчёты
(прямая цитата обоснования ADR-0032: "шаблон — не история"). Связь
`Material.category_id -> Category` — **другой природы**:

- `Category.requires_single_supplier` — не описательный атрибут для
  отображения, а **вход в ILP-модель солвера** (п.3). Материал без
  `category_id` был бы материалом, для которого солвер не может решить,
  участвует ли он в строгой группировке — не "отсутствие лишней метки",
  а потеря информации, напрямую влияющей на корректность allocation
  engine (тот же довод, по которому эта задача вообще существует —
  сравнить с тем, как сейчас `category: String, nullable=True`, и ADR-0028
  явно резервирует случай `category IS NULL` как открытый вопрос "не в
  объёме", а не решённое поведение по умолчанию).
- `internal_sku` уже выданных материалов ссылается на `sku_prefix`
  удалённой категории — `CASCADE`-удаление категории оставило бы
  материалы с "осиротевшим" SKU-неймспейсом (никто не мешает следующей
  созданной категории случайно переиспользовать тот же `sku_prefix`
  позже, если он не зарезервирован удалённой строкой — риск коллизии SKU
  двух разных, никогда не пересекавшихся во времени категорий).
- Материал без категории вообще не вписывается в модель данных этой
  задачи (`category_id` — `not null` FK, см. п.1) — `ON DELETE SET NULL`
  здесь невозможен без противоречия собственной схеме этого же ADR
  (сделать `category_id` nullable специально ради этого каскада означало
  бы вернуть половину проблемы, которую задача устраняет — "материал без
  определённой категории").

**Решение: `DELETE /categories/{id}` возвращает `409` с явным сообщением
(`"Category is referenced by N material(s), cannot delete"` — по образцу
уже существующего `delete_material`/`delete_supplier`, `material.py:126-130`),
если существует хотя бы один `Material.category_id == id`.** Не
`IntegrityError` от БД как единственный источник ошибки (хотя FK без
`ON DELETE CASCADE`/`SET NULL` и так физически откажет на уровне БД) —
явная предварительная проверка `COUNT` перед `db.delete`, чтобы сообщение
об ошибке было содержательным (число материалов), а не обобщённым текстом
перехваченного `IntegrityError`, как это уже сделано в некоторых, но не
всех существующих `delete_*`: `delete_material` (`material.py:118-131`)
перехватывает `IntegrityError` без предварительной проверки количества —
для `Category` выбирается более информативный вариант (сначала `COUNT`,
явное сообщение с числом), потому что ошибка здесь блокирует более
значимое действие (нельзя удалить категорию, которая нужна десяткам
материалов сразу) и админу полезнее видеть масштаб, чем при удалении
одного материала, блокированного одной строкой цены.

**Нет пути "мягко" удалить категорию, к которой привязан хотя бы один
материал.** Единственный способ освободить категорию для удаления —
явно переклассифицировать (`PATCH /materials/{id}`, смена `category_id`)
все материалы на другую категорию сначала — не автоматизируется этой
задачей (массовое перемещение материалов между категориями — отдельная
операция, не описанная в объёме).

### 7. Второй путь создания материала (`_apply_new`, price-list ревью) — тот же принцип, не отдельная задача

Найден при подготовке этого дополнения (см. "Контекст", пятое место) —
`backend/app/price_ingestion/apply.py:_apply_new`, вызываемый из
`POST /price-list-imports/{id}/entries/{id}/apply` с `action="new"`,
управляемый экраном `PriceListImportReviewPage.tsx` (кнопка "Применить"
на строке прайс-листа, не сопоставленной ни с одним материалом). Это
**реальный, второй, независимый от `create_material` путь создания
`Material`** — расширение объёма этого ADR, не отдельная задача: если
`create_material` требует `category_id` и генерирует `internal_sku`
сервером, а `_apply_new` продолжает создавать материалы без категории и
с произвольным SKU от рецензента, задача решена только наполовину — тот
же класс риска дубля/опечатки, который весь этот ADR устраняет для
одного пути создания, останется открытым для другого.

**Атомарная генерация SKU выносится в отдельную переиспользуемую
функцию, не дублируется копипастой между `create_material` и
`_apply_new`** — тот же принцип "одна функция, не две копии", что уже
применён в проекте к `calculate_tax`/`calculate_tax_dollars`
(`backend/app/allocation/tax.py`), `resolve_material_name`
(`backend/app/services/material_naming.py`), `version_price`
(`backend/app/api/price.py`, переиспользуется другими API-модулями).
Новая функция — `generate_next_sku(db: Session, category_id: uuid.UUID)
-> str` в `backend/app/services/material_sku.py` (новый модуль в
`app/services/`, где уже живёт `material_naming.py` — та же роль:
доменная функция, используемая и API-слоем, и price-ingestion
пайплайном, без взаимного импорта между `api/material.py` и
`price_ingestion/apply.py`). Реализует ровно ту же атомарную формулу, что
и п.4 (`UPDATE Category SET next_sku_number = next_sku_number + 1
WHERE id = :category_id RETURNING next_sku_number, sku_prefix`,
`assigned_sku = f"{prefix}-{new_number - 1:03d}"`), без дублирования
кода — `create_material` (п.4) и `_apply_new` оба вызывают эту функцию,
ни один не содержит собственной копии формулы. Если `category_id` не
существует — функция поднимает то же `HTTPException(404, "Category not
found")`, что и текущая реализация в `create_material` (единое поведение
для обоих вызывающих, не два разных сообщения об одной и той же ошибке).

**`ApplyEntryIn.internal_sku: str` заменяется на `category_id:
UUID`** — тот же переход, что `MaterialCreate.category: str` →
`category_id: UUID` в п.7 (нумерация подпунктов основного текста; исходно
единственный п.7 этого документа — автогенерация SKU для
`create_material` — считается частью настоящего п.7 целиком, отдельно не
переименовывается). `ApplyEntryIn` для `action="new"` становится:
`internal_sku` полностью убирается из схемы (та же семантика "422 при
попытке передать", что выбор для `MaterialCreate`/`MaterialUpdate`, —
решение единое для обоих путей, не разное для основного и для
price-list-ревью), `category_id: UUID` становится обязательным при
`action="new"` (та же валидация через `model_validator`, что уже
проверяет `material_id`/`internal_sku`+`canonical_name` для
`match`/`new` сегодня). `_apply_new()` вызывает `generate_next_sku(db,
category_id)` вместо приёма SKU параметром — сигнатура функции меняется
с `_apply_new(db, entry, supplier_id, internal_sku, canonical_name)` на
`_apply_new(db, entry, supplier_id, category_id, canonical_name)`.

**Frontend (`PriceListImportReviewPage.tsx`) — отдельным пунктом,
не обязательно в этой же сессии реализации, но зафиксировано здесь как
часть объёма, не отложено как отдельная задача**: поле `newSku`
убирается полностью, вместо него — выбор категории (тот же
компонент/источник данных, что и на основной форме создания материала
`create_material`, когда та появится на фронтенде), поле `newName`
(`canonical_name`) остаётся единственным текстовым вводом.

**Тесты (обязательны, тем же порядком строгости, что и вся остальная
регрессия этого ADR)**: `action="new"` с валидным `category_id` создаёт
материал с корректно сгенерированным SKU (тот же принцип точного
числового теста, что п.4 — `DOOR-027`, не "какой-то SKU"); попытка
передать `internal_sku` в теле `POST .../apply` — `422` (то же явное
решение, что для `POST /materials`, не два разных подхода к одному и
тому же вопросу "что если клиент всё равно прислал SKU"); `action="new"`
без `category_id` — `422` от `model_validator` (та же форма ошибки, что
уже существует для `match` без `material_id`); regression-тест на
`generate_next_sku` как общую функцию — вызов из обоих мест
(`create_material`, `_apply_new`) на одной и той же категории в одной
"сессии" сценария не создаёт коллизию SKU (прямое продолжение теста на
параллельное создание из п.4, теперь через два разных вызывающих пути,
не только два конкурентных запроса к одному эндпоинту).

## Альтернативы

**Хранить `category: String` рядом с `category_id: FK` для обратной
совместимости отображения.** Рассмотрено и отклонено в п.1 — тот же
класс риска денормализованного дубликата, который принцип 3 CLAUDE.md
уже запрещает для похожей ситуации (`SupplierMaterialAlias`).

**`y[C][s]`-подобная переменная вместо `category_id` как ключа группировки
в `materials_by_category`.** Не рассматривалось заново — эта задача не
трогает саму ILP-формулировку ADR-0028 §1 (прямая линковка через опорный
материал, обоснованная там же), только источник булева признака и ключ
словаря группировки.

**`sku_prefix` изменяемым, с ретроактивным решением "что делать со старыми
SKU".** Отклонено по прямому предложению задачи — см. п.5: неизменяемость
устраняет сам вопрос, а не откладывает его решение.

**`ON DELETE CASCADE`/`SET NULL` для `Material.category_id` при удалении
`Category`, по аналогии с ADR-0032 §4.** Рассмотрено и явно отклонено в
п.6 — природа связи разная (входные данные солвера и SKU-неймспейс
против UX-удобства шаблона), аналогия с ADR-0032 не переносится
механически.

**`MAX(internal_sku) + 1` с `SELECT ... FOR UPDATE` на последнем материале
категории вместо счётчика на самой `Category`.** Рассмотрено, отклонено —
требует блокировки строки `Material` (какой из нескольких десятков строк
категории — не единственный кандидат, сложнее выразить, чем блокировка
единственной строки `Category`), и не работает для только что созданной
категории без единого материала (нет строки, которую можно было бы
заблокировать `SELECT FOR UPDATE` — `Category.next_sku_number` с
default `1` тривиально покрывает пустую категорию без специального
случая).

## Не в объёме

- Изменение набора существующих 8 категорий (см. "Контекст") — задача
  переносит существующие значения в БД, не меняет их состав. Новые
  категории могут появиться через admin-экран п.5 в будущем, но что
  происходит при импорте нового прайс-листа с незнакомым значением
  `Group`-колонки (`xlsx_price_matrix.py`) — отдельный вопрос, не
  проектируется здесь (прямое ограничение объёма из постановки задачи).
- Массовая переклассификация материалов между категориями (bulk-`PATCH`) —
  не нужна для освобождения категории перед удалением в этой задаче,
  но не реализуется как отдельная UI-операция.
- Пересчёт уже существующих `AllocationRun` при изменении
  `requires_single_supplier` задним числом — не происходит нигде в
  системе для аналогичных изменений справочных данных, не вводится
  специально для этого поля.
- Поведение импорта прайс-листа (`import_real_data.py`/
  `price_ingestion`) при встрече со значением категории, отсутствующим в
  таблице `Category`, — существующий импорт-скрипт работает с реальным
  файлом один раз (историческое разовое действие), новые прайс-листы
  поступают через `price_ingestion.py` (LLM-парсинг + ревью, ADR-0018/
  ADR-0019), который сегодня не создаёт `Material` автоматически без
  ревью — вопрос "что если матчинг предлагает материал с неизвестной
  категорией" не в объёме, симметрично общему "Не в объёме" выше.

    материалами → `409` с числом материалов в сообщении; `DELETE` пустой
    категории → `204`.
  - `backend/tests/api/test_material.py` (существующий, правится) —
    `internal_sku` больше не принимается в `POST /materials` (проверка,
    что переданное значение игнорируется или отклоняется — решить на
    реализации: `MaterialCreate` без поля `internal_sku` делает лишний
    ключ в JSON либо молча отброшенным Pydantic, либо `422` при
    `model_config` с запретом лишних полей — выбор строгости `422` vs
    игнорирования — деталь реализации, не архитектурное решение);
    параллельное создание двух материалов одной категории (два потока/
    сессии БД в тесте) даёт два разных `internal_sku` без коллизии —
    прямая проверка требования п.4 "безопасно при параллельном создании";
    отдельно — `test_create_material_after_backfill_continues_existing_sku_sequence`
    (п.4): категория `Doors` с `next_sku_number=27` после backfill даёт
    ровно `DOOR-027` на следующем создании, не `DOOR-026`/`DOOR-028`.
  - `backend/tests/price_ingestion/test_matching.py` (существующий,
    правится) — `_candidate_context` выводит `Category.name` в промпте
    для материала с `category_id`, не `repr()` ORM-объекта (см. "Контекст",
    третье найденное место).
  - `backend/tests/api/test_template.py` (существующий, правится) —
    `ProjectTemplateItemOut.category_name` (переименовано из `category`)
    отражает `material.category.name` (см. "Контекст", четвёртое найденное
    место).
- Новый модуль `backend/app/services/material_sku.py` —
  `generate_next_sku(db, category_id) -> str`, единственная реализация
  атомарной формулы п.4/п.7 (`UPDATE ... RETURNING`), вызывается и из
  `create_material`, и из `_apply_new` — ни одна копия формулы не
  дублируется (п.7).
- `backend/app/price_ingestion/apply.py:_apply_new` — принимает
  `category_id` вместо `internal_sku`, вызывает `generate_next_sku` (см.
  "Контекст", пятое найденное место, и п.7). `ApplyEntryIn`
  (`backend/app/api/schemas/price_ingestion.py`) — `internal_sku: str`
  заменяется на `category_id: uuid.UUID`, обязательное при `action="new"`.
- `frontend/src/routes/price-list-import/PriceListImportReviewPage.tsx` —
  поле `newSku` убирается, добавляется выбор категории, `newName`
  остаётся единственным текстовым вводом (п.7; сам фронтенд-код — вне
  объёма backend-реализации этой сессии, зафиксирован здесь как часть
  задачи, не отдельная).
- Тесты на второй путь создания (п.7): `action="new"` с валидным
  `category_id` создаёт материал с точным ожидаемым SKU (тот же принцип,
  что `test_create_material_after_backfill_continues_existing_sku_sequence`);
