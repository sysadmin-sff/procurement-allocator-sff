# ADR-0035: Синхронизация каталога из файла против непустой БД — новый скрипт, не `import_real_data.py`

Статус: Предложено

## Зависимость — блокирует реализацию, не блокирует черновик ADR

**Этот ADR проектируется в предположении, что ADR-0034 (`Category` как
сущность, `Category.next_sku_number`, `generate_next_sku()` в
`backend/app/services/material_sku.py`) уже реализован.** На момент
написания ADR-0034 реализован на ветке `adr-0034-category-entity-sku-autogen`
(backend и frontend, коммиты вплоть до `05afa18`), но **не смержен в
`main`**. Реализация настоящего ADR (скрипт `sync_catalog_from_file.py`,
п.3) не начинается, пока ADR-0034 не смержен — новый скрипт создаёт
материалы исключительно через `generate_next_sku(db, category_id)`
(ADR-0034 §7), не проектирует параллельный механизм генерации SKU и не
дублирует его формулу. Если по какой-то причине ADR-0034 будет
пересмотрен до мержа, этот ADR подлежит пересмотру вместе с ним в части
п.3.

## Контекст

`backend/app/scripts/import_real_data.py` — единственный существующий
путь загрузки каталога компании из xlsx-файла (`xlsx_price_matrix.py`,
wide-matrix формат: `Group`/`Description`/`Quantity` + колонка на
поставщика). Он **полностью очищает** БД (`TRUNCATE ... CASCADE` по
`TABLES_IN_DELETE_ORDER`, включая `projects`/`orders`/`allocation_runs`)
перед повторной загрузкой — операция, задуманная для одноразового
первого наполнения пустой dev/прод БД, не для повторного применения.

БД компании больше не пуста: в ней есть реальные `Project`, `Order`,
`AllocationRun`, ссылающиеся на существующие `Material`/`Supplier`/
`Price` по FK. Получен новый, актуализированный файл каталога того же
формата (обновлённые цены части позиций, новый восьмой поставщик "A&S",
несколько потенциально новых материалов — ~301 против текущих 294) —
`import_real_data.py` для его применения категорически не подходит:
`TRUNCATE CASCADE` таблиц из `TABLES_IN_DELETE_ORDER` уничтожил бы
`projects`/`orders`/`allocation_lines` без возможности восстановления
(перечислены в `TABLES_IN_DELETE_ORDER` как "дети" каскада именно
потому, что физически ссылаются на `materials`/`suppliers`/`prices`,
которые скрипт обязан пересоздать).

**Это не разовая проблема одного файла — это постоянное свойство
дальнейшей жизни системы.** Компания будет получать актуализированные
прайс-файлы того же формата периодически (созвон/контекст задачи: тот
же источник, что уже присылал `materials_price_matrix.xlsx`), и после
первого реального использования системы (первые `Project`/`Order`)
`import_real_data.py` не может использоваться ни для одного из них —
нужен постоянный, отдельный путь применения новых файлов к уже
работающей БД, не разовый скрипт под конкретный файл этой задачи.

Реальные факты о конкретном новом файле (ориентир для проектирования и
тестовых фикстур, не единственный поддерживаемый сценарий — скрипт
проектируется общим для любого файла того же формата):

- 8 категорий совпадают с уже существующими — новой категории не
  обнаружено в этом конкретном файле.
- ~301 материал против текущих 294 — почти совпадает, вероятно
  несколько новых позиций.
- Новый, восьмой поставщик "A&S", отсутствовавший в
  `SUPPLIER_NAMES` (`import_real_data.py`).
- Формат файла идентичен уже поддерживаемому `xlsx_price_matrix.py`
  (wide-matrix: `Group`/`Description`/`Quantity` + колонки поставщиков).

**Что этот ADR обязан переиспользовать, не изобретать заново** (прямое
условие задачи):

- `xlsx_price_matrix.parse_price_matrix()` — чтение и разбор
  wide-matrix xlsx в `ParsedWorkbook` (материалы + цены), не
  переписывается.
- `app/api/price.py:version_price()` — версионирование `Price`
  (закрыть активную, открыть новую с наследованием
  `currency`/`availability`/`min_order_qty`), уже вынесена в
  переиспользуемую функцию ADR-0030 §5, уже используется вне
  `price.py` (`order_service.py`, ADR-0030 §5) — этот ADR становится
  третьим вызывающим тем же способом.
- `app/services/material_sku.py:generate_next_sku()` — атомарная
  генерация `internal_sku` для новых материалов (ADR-0034 §4/§7), см.
  "Зависимость" выше.
- Паттерн dry-run/`--apply` + структурированный отчёт, уже
  установленный `backfill_color_options.py`/
  `backfill_material_categories.py`: функция `run_*(db, ..., apply) ->
  Report` (dataclass), отдельная `print_report(report)`, `--apply`
  обязателен для записи.

**Явно НЕ переиспользуется/НЕ трогается**:

- `import_real_data.py` — остаётся без изменений, для случая пустой
  БД (первое наполнение dev-окружения или полный сброс по явному
  запросу администратора). Не вызывается этим ADR, не переиспользует
  его код (кроме уже общей зависимости от `xlsx_price_matrix.py`,
  которая была общей и раньше).
- `PriceListImport`/`PriceListEntry`/`SupplierMaterialAlias`/ИИ-пайплайн
  (ADR-0019/0025) — тот путь предназначен для **единичного PDF-документа
  одного поставщика** с неструктурированным вход-текстом, где нужен
  LLM-парсинг и matching. Здесь вход — **весь каталог сразу**, тот же
  детерминированный, машиночитаемый wide-matrix формат, уже разобранный
  `xlsx_price_matrix.py` без каких-либо элементов неструктурированного
  текста, не требующий LLM ни для извлечения, ни для матчинга (см. п.1
  про то, почему matching здесь — точное совпадение, не LLM-решение).
  Разные входы (весь прайс общей структуры vs один документ одного
  поставщика с произвольной вёрсткой), разная природа matching
  (точное строковое совпадение против уже принятого решения ADR-0025 —
  фиксированный каталог, а не открытый список кандидатов через
  embeddings) — не тот же механизм, не переиспользуется механически, как
  прямо и было указано в постановке задачи.

## Решение

### 1. Matching строки файла с существующим `Material` — точное совпадение по `canonical_name`, без порога/AI

**Единственный стабильный признак сопоставления — `canonical_name`
(нормализованная строка описания), не `internal_sku`.** `internal_sku`
генерируется системой (ADR-0034), не приходит из файла — файл не может
содержать значение, которое можно было бы сравнить с уже выданным SKU.
`canonical_name` — единственное поле, которое одновременно (а) есть в
файле (колонка `Description`) и (б) есть на существующем `Material`
(`xlsx_price_matrix.MaterialRow.description` → `Material.canonical_name`
при первом импорте, без трансформации).

**Сопоставление — точное строковое совпадение после нормализации
(`strip()` + схлопывание внутренних пробельных последовательностей),
без нечёткого/similarity-порога и без LLM-матчинга.** Тот же принцип,
что уже дважды применён в этой кодовой базе к похожей проблеме
("сливать потенциально разные материалы автоматически без ревью
человека" — ADR-0019 п.2/ADR-0025 п.1 отклонили это для менее
структурированного входа, PDF-прайса одного поставщика с произвольными
формулировками): если это оправдано отклонить там, где вход
действительно неоднозначен, тем более оправдано здесь, где вход —
тот же самый детерминированный wide-matrix формат, из которого
каталог изначально и был создан (`import_real_data.py`) — если
`canonical_name` в новом файле не совпадает побайтово с уже
существующим, это **не задача для эвристики "похоже, наверное то же
самое"**, а сигнал, что либо название реально изменилось (тогда это
не тот же материал по умолчанию, пока человек не решит иначе), либо
это опечатка составителя файла (тоже требует внимания человека, не
тихого слияния).

**Нормализация — только whitespace, не casefold/punctuation-strip.**
Более агрессивная нормализация (например, приведение регистра) увеличила
бы количество ложных совпадений (два реально разных материала,
отличающихся, например, только числом в названии, регистронезависимо
совпасть не могут — риск здесь не в этом; риск в обратную сторону:
слишком агрессивная нормализация могла бы склеить строки, которые
человек, заполнявший файл, различал намеренно). Whitespace-нормализация
выбрана как минимально необходимая (устраняет только очевидно
случайный шум типа двойного пробела/лишнего таба при копировании в
Excel), не решение "давай угадаем получше" — тот же дух, что ADR-0025
п.1 применило к решению не добавлять `attributes` в контекст LLM без
доказанной необходимости.

**Список "не сопоставлено" — явный, не тихий пропуск и не тихое
создание дубля.** Любая строка файла, для которой нормализованный
`canonical_name` не совпал ни с одним `Material.canonical_name`
(нормализованным тем же способом) в БД, **не создаётся автоматически
как новый материал** (это отдельная ветка, п.3, требующая явного
резолва категории) и **не пропускается молча** — попадает в раздел
отчёта `unmatched_price_rows` (материал+все цены строки), требующий
ручного разбора администратором (либо это опечатка существующего
названия — тогда правка в БД руками, либо реально новый материал —
тогда ручной запуск создания через `POST /materials`/экран ревью п.7
ADR-0034, а не через этот скрипт).

### 2. Реконсиляция цен — три случая на пару (material, supplier)

Для каждой пары (`material_id`, `supplier_id`), где `material_id`
разрешён через сопоставление п.1 (совпавшие строки) или создан как
новый материал (п.3) — сравнение значения ячейки файла с текущей
активной `Price` (`valid_to IS NULL`) для этой пары:

**(а) Значение в файле есть, отличается от текущей активной цены.**
`version_price(db, material_id=..., supplier_id=..., price=<новое
значение>, source_import_id=None)` — закрывает старую (`valid_to =
сегодня`), создаёт новую (`valid_from = сегодня`), наследуя
`currency`/`availability`/`min_order_qty` от закрываемой строки (уже
встроенное поведение `version_price`, не переопределяется этим ADR).
Прямое переиспользование ADR-0030 §5, третий вызывающий после
`update_price`-route и `order_service.py` batch-подтверждения.

**(б) Значения в файле нет (пустая ячейка), активная `Price` для
этой пары СЕЙЧАС существует.**

**Решение: закрыть активную цену (`valid_to = сегодня`), не создавая
новую взамен.** Пустая ячейка в актуализированном полном
прайс-каталоге поставщика интерпретируется как "поставщик больше не
предлагает эту позицию по этому прайсу" — то есть то же действие, что
уже существует для этой ситуации в системе (`DELETE /prices/{id}`,
`price.py:198`, ограничен только незакрытыми записями, тот же эффект
здесь достигается версионированием, не прямым удалением, чтобы не
терять историю).

Обоснование выбора между двумя интерпретациями (сравнение цены ошибки в
обе стороны, как явно требует постановка задачи):

- *Не трогать* (интерпретация "в этом конкретном экспорте просто не
  указано") ошибается в сторону **сохранения устаревшей видимости
  предложения**: allocation engine продолжит считать эту пару
  material+supplier доступной по последней известной цене, хотя
  поставщик её больше не предлагает по актуальному прайсу — ILP-солвер
  может выбрать этого поставщика для этого материала, ордер будет
  сформирован, и только на этапе реального размещения заказа
  обнаружится, что позиции у поставщика больше нет. Это прямое
  нарушение цели самой задачи каталога (актуальные данные для
  оптимального распределения закупки) и самое дорогое по последствиям
  из двух ошибок — узнаётся поздно, после того как решение уже принято
  и, возможно, заказ отправлен.
- *Закрыть* ошибается в сторону **ложного скрытия реально доступной
  позиции**, если пустая ячейка на самом деле — артефакт составления
  конкретного файла (например, сотрудник поставщика забыл заполнить
  строку, зная, что цена не менялась), а не факт ухода с позиции. Цена
  этой ошибки ниже и дешевле для обнаружения: закрытая `Price`
  немедленно видна как "нет активной цены" на любом экране, где она
  ожидалась (создание проекта, экран цен поставщика) — администратор
  или сотрудник закупок, работающий с этим материалом, заметит
  отсутствие цены в ближайшее естественное взаимодействие с системой
  (не позже, чем при следующей попытке включить этот материал в BOM у
  этого поставщика), и восстановление тривиально (`POST /prices` или
  следующий цикл синхронизации, если позиция вернётся в файл). Не
  требует специального аудита или отчёта, чтобы быть замеченным —
  сама структура системы (allocation просто не предложит поставщика
  без активной цены) делает эту ошибку самокорректирующейся при
  следующем использовании, в отличие от противоположной ошибки,
  которая обнаруживается только постфактум.

**Каждое такое закрытие — обязательная строка dry-run отчёта** (раздел
"будут закрыты", материал/поставщик/текущая цена), не агрегированное
число — администратор должен иметь возможность проверить весь список
перед `--apply`, в том числе на случай, если пустых ячеек оказалось
неожиданно много (сигнал, что новый файл структурно отличается от
ожидаемого — не тот же прайс, а, например, частичный экспорт одного
поставщика, ошибочно принятый за полный каталог; п.7 покрывает эту
защиту явно).

**(в) Значение в файле есть, активной `Price` для этой пары нет
вообще.** `version_price(...)` без предварительного закрытия (уже
встроенная ветка функции — "если активной записи нет, создаёт
напрямую") — тот же случай (в), что уже определён ADR-0030 §2 для
единичного подтверждения `confirmed_price`, переиспользуется здесь
без изменений семантики.

**Явно НЕ входит в эту реконсиляцию**: пары (material, supplier), где
материал не сопоставлен (п.1, `unmatched`) — для них реконсиляция цен
не выполняется, весь ряд файла идёт в список ручного разбора целиком,
не частично.

### 2.1. `category_id`/`unit` совпавшего материала — не трогаются этим путём

**Явный пробел, требующий отдельного решения: файл несёт свою
собственную `Group`-колонку (категория) и `Quantity`-производный
`unit` для каждой строки, в том числе для строк, совпавших по п.1 с
уже существующим `Material`.** Реконсиляция п.2 касается только
`Price` — она ничего не говорит о том, что делать, если, например,
`Group` файла для совпавшей строки читается как `"Doors"`, а
`Material.category_id` в БД уже указывает на категорию `"Gutter"` (не
гипотетический сценарий: реальная причина расхождения — не обязательно
ошибка составителя, материал мог быть намеренно переклассифицирован
администратором через `PATCH /materials/{id}` после первого импорта, и
файл поставщика при этом не знает о такой переклассификации вообще).
Такое расхождение нельзя оставить решаться подразумеваемо — `Category`
после ADR-0034 не описательный атрибут, а прямой вход в
ILP-модель солвера (`requires_single_supplier`, ADR-0028/0034 §3):
молчаливая перезапись `category_id` этим скриптом изменила бы
поведение allocation engine для всего каталога как побочный эффект
операции, задуманной как "обновить цены", — тот же класс риска,
который ADR-0034 назвала главной причиной своего существования
("никто не мешает… это просто иначе посчитается солвер для этого
материала, и это не будет замечено").

**Решение: этот путь синхронизирует ТОЛЬКО `Price` для уже
существующих (совпавших по п.1) материалов. `category_id` и `unit`
совпавшего `Material` не читаются из файла и не изменяются скриптом
ни при каком расхождении — независимо от того, совпадает `Group`/
`Quantity` файла с текущим значением в БД или нет.** Переклассификация
материала (`category_id`) или исправление единицы измерения (`unit`)
— отдельное, осознанное действие администратора через существующие
пути (`PATCH /materials/{id}`, ADR-0034 §5 — `PATCH /categories/{id}`
для самой категории), не побочный эффект синхронизации прайса.

Обоснование, тем же уровнем строгости, что и остальные решения этого
документа:

- **Асимметрия последствий ошибки.** Ошибочно закрытая/обновлённая
  `Price` (п.2) — по конструкции самого `Price` обратима без потери
  истории (новая версия, старая остаётся закрытой строкой, не
  удаляется) и локальна по эффекту (одна пара material+supplier).
  Ошибочно перезаписанный `category_id` — по конструкции ADR-0034
  необратим без явного administrative-действия (нет версионирования
  категории материала, только текущее значение) и **глобален по
  эффекту** (немедленно меняет группировку этого материала в каждом
  будущем allocation-расчёте любого проекта, где он встретится, до
  тех пор пока кто-то не заметит и не исправит вручную). Второе явно
  не должно происходить как незапрошенный побочный эффект первого.
- **Файл — не источник истины для классификации, только для цены.**
  Задача этого ADR (см. "Контекст") — обновление цен и добавление
  новых позиций каталога, о котором явно попросили; она не
  формулирует переклассификацию существующих материалов как цель
  синхронизации. `Group`-колонка файла используется этим ADR только
  один раз — для резолва категории **новых** материалов (п.3, где нет
  существующего `category_id`, который можно было бы случайно
  перезаписать); для уже существующего материала этот же источник
  становится ненадёжным индикатором намерения: расхождение "файл
  говорит одно, БД — другое" не отличимо программно от "поставщик
  для этой строки использует другую внутреннюю группировку в своём
  экспорте, не совпадающую с нашей `Category`" — ничего в самом файле
  не удостоверяет, что расхождение вообще означает намерение сменить
  категорию в нашей системе.
- **Молчаливое решение здесь недопустимо, но и молчаливое сравнение
  без действия — тоже не то же самое, что "не заметить".** Расхождение
  всё равно не должно теряться незамеченным (иначе реальная
  переклассификация, которую администратор всё-таки хотел бы сделать,
  осталась бы невидимой в этом же прогоне) — но реагировать
  предупреждением, а не автоматическим применением.

**Расхождение отражается в отчёте информационно, без действия.** Новый
раздел `category_or_unit_mismatches: list[CategoryMismatchRow]` —
материал (`internal_sku`/`canonical_name`) / текущий `category_id`
(имя категории) / `Group` из файла / текущий `unit` / `Quantity`-
производный `unit` из файла, для каждой совпавшей по п.1 строки, где
`Group` файла (сопоставленный с `Category.name` тем же способом, что
п.3) не совпадает с `Material.category_id`, и/или `unit` файла не
совпадает с `Material.unit`. Не блокирует применение остальных
разделов отчёта (`price_updates`/`price_closures`/`price_creations`
для этой же строки применяются как обычно) — расхождение
категории/unit не делает саму цену этой строки недостоверной, это
независимые друг от друга решения.

### 3. Новые материалы — через `generate_next_sku`, зависимость от ADR-0034

Строка файла без совпадения по `canonical_name` (п.1) создаётся как
`Material` только когда её `Group`-колонка (категория) разрешается в
одну из существующих 8 строк `Category` — тем же способом, что уже
разрешает `import_real_data.py`/`xlsx_price_matrix.CATEGORY_SKU_PREFIX`
имя категории в префикс, но здесь резолв идёт в `Category.id` через
`SELECT ... WHERE name = ...`, не через хардкод-словарь (после
ADR-0034 источник истины для категорий — таблица `Category`, не
константа кода).

```python
category = db.scalar(select(Category).where(Category.name == row.category))
if category is None:
    report.unresolved_category_rows.append(row)  # см. ниже, не пропуск
    continue
sku = generate_next_sku(db, category.id)  # ADR-0034 §4/§7
material = Material(internal_sku=sku, canonical_name=row.description,
                     category_id=category.id, unit=row.unit, attributes={})
```

**Незнакомая (9-я) категория — явная ошибка строки, не тихое
пропускание и не попытка создать категорию на лету.** Тот же вопрос,
что ADR-0034 прямо вынесла в "Не в объёме" ("что происходит при
импорте нового прайс-листа с незнакомым значением `Group`-колонки"),
здесь не переоткрывается — если файл содержит значение категории, не
совпадающее ни с одной строкой `Category.name`, соответствующая строка
файла попадает в раздел отчёта `unresolved_category_rows` (материал +
название незнакомой категории), скрипт не создаёт материал и не
предлагает "ближайшую похожую" категорию. В конкретном известном файле
такого не случится (8 категорий совпадают, см. "Контекст"), но скрипт
не должен полагаться на это как на инвариант, который не будет
нарушен в будущем файле — тот же принцип защитной проверки, что
`backfill_material_categories.py` уже применяет к аналогичному
несовпадению (ADR-0034 п.2 шаг 1: "явная ошибка, если `SELECT DISTINCT
category` вернёт значение, которого нет в `CATEGORY_SKU_PREFIX`").

Цена для новой связки (новый материал, поставщик из файла) создаётся
тем же путём (в) п.2, в той же транзакции, что и создание материала —
не оставляет материал без цены, если это единственный источник данных
о нём.

### 4. Материалы в БД, не найденные в файле — не трогаются

Материал, для которого ни одна строка файла не совпала по
`canonical_name` (обратное направление п.1 — не "файл не нашёл
совпадения в БД", а "БД содержит материал, отсутствующий в файле"),
**не изменяется, не деактивируется, не помечается никаким флагом**.
Обоснование: материал мог не попасть в конкретный прайс-каталог по
причинам, не связанным с его актуальностью для системы (поставщик
временно не включил позицию в этот экспорт, материал закупается у
поставщика, не входящего в анализируемый файл), и на него могут
ссылаться существующие `Order`/`ProjectItem`/`AllocationLine` — прямое
условие задачи ("никогда не удалять/деактивировать материал, на
который могут ссылаться реальные записи").

Список таких материалов включается в отчёт как информационный раздел
`not_in_file` (только материал, без действия) — не для принятия
решения скриптом, а чтобы администратор мог одним взглядом увидеть
масштаб расхождения (например, если "не встретилось в файле" оказалось
неожиданно много материалов — сигнал проверить, тот ли это файл/тот же
ли объём каталога, прежде чем полагаться на результат синхронизации).

**Явно не путать с п.2(б).** П.2(б) — материал сопоставлен (есть в
файле), но конкретная ячейка (material, supplier) пуста → цена этой
пары закрывается. П.4 — материала целиком нет ни в одной строке файла
→ ничего не закрывается ни для одной цены этого материала ни у одного
поставщика (все существующие активные `Price` этого материала
остаются как есть, независимо от поставщика).

### 5. Новый поставщик в файле — создаётся с той же заглушкой `delivery_policy`

Поставщик, чьё имя в заголовке колонки файла (после сопоставления
через тот же `SUPPLIER_COLUMN_HEADERS`-паттерн, что уже использует
`xlsx_price_matrix.py`) не совпадает ни с одним существующим
`Supplier.name` в БД — создаётся новой строкой `Supplier` с тем же
`DEFAULT_DELIVERY_POLICY`, что использует `import_real_data.py` при
первом наполнении (`flat_fee=0.0`, `free_shipping_threshold=null`,
`per_order_min_amount=0.0`, `lead_time_days=0` — заглушка, не реальные
условия доставки).

**Явная строка в отчёте**, отдельная от обычной сводки — новый
поставщик создан с placeholder-условиями доставки, администратору
нужно заполнить реальные значения через `PATCH /suppliers/{id}` до
того, как allocation-расчёты, учитывающие доставку этого поставщика,
станут осмысленными (то же предупреждение, что уже печатает
`import_real_data.print_summary`, дословно применимо и здесь — не
новая формулировка, тот же текст/тот же смысл, переиспользуется).

Сопоставление имени колонки файла с известным поставщиком — точное
совпадение через существующий `SUPPLIER_COLUMN_HEADERS`-словарь
(`xlsx_price_matrix.py`); заголовок, отсутствующий в этом словаре,
попадает в `unmapped_supplier_headers` (уже существующее поле
`ParsedWorkbook`) и не создаёт нового поставщика автоматически по
непредусмотренному заголовку — **требует ручного добавления записи в
`SUPPLIER_COLUMN_HEADERS`** (та же механика, что уже действует для
`import_real_data.py` сегодня: новый заголовок колонки без
сопоставления не создаёт поставщика молча, попадает в
`unmapped_supplier_headers` отчёта). "A&S" должен быть добавлен в
`SUPPLIER_COLUMN_HEADERS` как часть реализации этой синхронизации
(конкретный заголовок колонки для A&S в реальном файле — деталь
реализации, не архитектурное решение этого ADR).

### 6. Аудит происхождения обновлённых `Price` — простое логирование, без новой таблицы

**Решение: не вводить новую сущность-журнал.** Рассмотрена и отклонена
идея отдельной лёгкой таблицы (`CatalogSyncRun` или аналог
`source_import_id`) — для этого детерминированного, редко
запускаемого (несколько раз в год, не поток документов, в отличие от
`PriceListImport`) операторского скрипта полноценная queryable-история
в БД непропорциональна ценности: `PriceListImport` (ADR-0019)
оправдана как сущность именно потому, что обслуживает **регулярный,
многократный, пользовательский** UI-флоу (сотрудник загружает
прайс-документ через экран, видит список прошлых загрузок,
ревьюит построчно) — ничего из этого не относится к скрипту,
запускаемому администратором из командной строки против всего
каталога сразу.

Вместо этого:

- **Dry-run/`--apply` отчёт** (п.7) — полный, структурированный,
  печатается в stdout при каждом запуске (тот же паттерн, что
  `backfill_color_options.py`/`backfill_material_categories.py`).
- **Обязательная запись в `docs/known-issues.md`** после каждого
  реального (`--apply`) запуска в проде — дата, имя файла, сводные
  числа (обновлено/создано/закрыто/не сопоставлено), тем же
  человекочитаемым, ручным способом, каким уже задокументирован
  инцидент восстановления категорий (`4812ad5`, "document category
  recovery incident honestly in known-issues.md") — не автоматизация,
  осознанная договорённость на будущее, часть процедуры запуска
  скрипта, описанной в его собственном докстринге.
- `Price.created_by_user_id`/`source_order_item_id` (ADR-0030 §6) —
  **не заполняются** этим путём (остаются `NULL`), тот же смысл, что
  и для admin-флоу `/prices/{id}`: `created_by_user_id` требует
  живого `User` из authenticated HTTP-запроса, скрипт запускается из
  командной строки без такого контекста, и вводить синтетического
  "системного" пользователя ради заполнения этого поля — отдельное
  решение, не запрошенное этой задачей и не имеющее прецедента в
  кодовой базе (`import_real_data.py` тоже не заполняет эти поля,
  хотя технически мог бы).
- `Price.source_import_id` (ADR-0019, FK на `PriceListImport`) — не
  заполняется (остаётся `NULL`), потому что обновления этим скриптом
  не порождены `PriceListImport`-записью (этот путь её не создаёт, см.
  "Контекст" — явно не переиспользуется). Не вводится новое значение
  толкования этого поля ради частичного покрытия одним скриптом того,
  что поле исторически означает "пришло из ИИ-пайплайна одного
  документа".

**Если в будущем окажется, что даже этого недостаточно** (например,
понадобится программный откат конкретного батча синхронизации) — это
основание для отдельного нового ADR с реальным сценарием, не решается
здесь заранее без данных о частоте такой потребности (та же
дисциплина "не проектировать вслепую", что уже применена ADR-0030
в отношении отложенной с ADR-0007 §5 связки `confirmed_price`↔`Price`).

### 7. Dry-run / `--apply` — обязательный, детальный отчёт

Новый скрипт `backend/app/scripts/sync_catalog_from_file.py`,
структура по образцу `backfill_color_options.py`/
`backfill_material_categories.py`:

```python
def run_sync(db: Session, path: Path, apply: bool) -> SyncReport: ...
def print_report(report: SyncReport) -> None: ...
```

**Использование:**

```
python -m app.scripts.sync_catalog_from_file <path>            # dry-run
python -m app.scripts.sync_catalog_from_file <path> --apply     # запись
```

**`SyncReport` — разделы, каждый со своим детальным списком, ничего не
скрыто в агрегированном числе:**

- `price_updates: list[PriceUpdateRow]` — материал / поставщик / старая
  цена → новая цена (п.2а).
- `price_closures: list[PriceClosureRow]` — материал / поставщик /
  закрываемая цена, без замены (п.2б).
- `price_creations: list[PriceCreationRow]` — материал / поставщик /
  новая цена, для пар без предшествующей активной записи (п.2в,
  включая цены для только что созданных материалов из `new_materials`).
- `new_materials: list[NewMaterialRow]` — категория / сгенерированный
  (в dry-run — **предсказанный**, см. ниже) `internal_sku` /
  `canonical_name` (п.3).
- `new_suppliers: list[str]` — имена, с явной пометкой про заглушку
  `delivery_policy` (п.5).
- `unmatched_price_rows: list[UnmatchedRow]` — строки файла без
  совпадения по `canonical_name` (п.1).
- `unresolved_category_rows: list[UnresolvedCategoryRow]` — строки с
  категорией, не найденной среди существующих `Category` (п.3).
- `category_or_unit_mismatches: list[CategoryMismatchRow]` — совпавшие
  материалы, где `Group`/`Quantity`-производный `unit` файла расходится
  с текущим `category_id`/`unit` в БД (п.2.1) — информационно, без
  действия, цена этой же строки при этом применяется как обычно.
- `not_in_file: list[str]` — `internal_sku`/`canonical_name`
  материалов БД, отсутствующих в файле (п.4, информационно, без
  действия).
- `unmapped_supplier_headers: list[str]` — из `ParsedWorkbook`
  (переиспользуется как есть, п.5).

**Dry-run не пишет в БД вообще** (тот же принцип, что и у всех
предыдущих backfill-скриптов) — включая генерацию `internal_sku`:
`generate_next_sku` физически инкрементирует
`Category.next_sku_number` атомарным `UPDATE` (ADR-0034 п.4), поэтому
dry-run **не вызывает** её напрямую — вместо этого предсказывает SKU
чтением текущего `Category.next_sku_number` без инкремента
(`f"{category.sku_prefix}-{category.next_sku_number:03d}"`) и явно
помечает эти значения в отчёте как "предварительно, может измениться
при `--apply`, если другой процесс создаст материал этой категории
между dry-run и `--apply`" — та же осторожность, что уже применена
`generate_next_sku`'s docstring к параллельному созданию через API
(ADR-0034 п.4), здесь применяется к разнесённому во времени
dry-run/`--apply` двум отдельным запускам того же скрипта.

**Верификация перед выводом успеха при `--apply`** (по образцу
`backfill_material_categories.py` п.3 ADR-0034) — после применения:
количество созданных `Price`+обновлённых `Price` (закрытых/открытых)
соответствует сумме `price_updates`+`price_closures`+`price_creations`
из отчёта того же запуска; при несоответствии — `--apply` завершается
ошибкой, транзакция откатывается целиком (одна транзакция на весь
`--apply` запуск, не построчный commit — в отличие от batch-эндпоинта
ADR-0030 п.4.3, где независимость строк оправдана конкурентным доступом
нескольких сотрудников; здесь единственный оператор запускает скрипт
разово, частичное применение при сбое создало бы неопределённое
промежуточное состояние каталога без явного способа понять, что уже
применилось, а что нет).

**Признанный tradeoff: row-level локи `Category` удерживаются на всю
длительность `--apply`, не освобождаются между шагами.** Одна
транзакция на весь запуск (обоснование выше) означает, что каждый вызов
`generate_next_sku` (п.3) — а их может быть до нескольких десятков,
по одному на каждый новый материал файла — берёт row-level lock на
свою строку `Category` через `UPDATE ... RETURNING` и **удерживает его
до конца всей транзакции скрипта**, не до конца своего отдельного вызова
(стандартная семантика блокировок Postgres внутри одной транзакции — лок
снимается только на `COMMIT`/`ROLLBACK`, не раньше). Практический
эффект: пока `--apply` этого скрипта выполняется (весь прогон, не
только момент создания конкретного материала), любой конкурентный
`POST /materials`/`_apply_new` (ADR-0034 §4/§7) с той же `category_id`,
что затронута синхронизацией, заблокируется до завершения скрипта, а не
только на время одного `UPDATE`.

Явно принято как приемлемый риск, не как незамеченное следствие
архитектуры: скрипт запускается редко (несколько раз в год, см. п.6) и
единолично (один администратор, не конкурентный UI-флоу), сам прогон
для ~300 строк — секунды, не часы, а обычное использование системы
(создание материалов через `POST /materials`/`_apply_new`) — тоже
редкое событие относительно частоты обычных операций (allocation,
работа с заказами), не затрагиваемых этим локом вообще (блокируется
только `UPDATE` той же строки `Category`, не чтение/использование уже
существующих материалов этой категории). Если в будущем частота того
и другого вырастет настолько, что совпадение по времени станет
реальной проблемой (не гипотетической) — смягчение (например, отдельная
транзакция на группу "новые материалы" с коротким удержанием лока,
отдельно от транзакции на цены) — предмет пересмотра при реальном
инциденте, не проектируется здесь заранее без данных.

**Обязательная ручная проверка перед `--apply` на реальных данных** —
инструкция в самом выводе dry-run-отчёта (по тому же принципу, что
ADR-0034 п.2): свериться, что число `price_closures` соответствует
ожиданиям (не аномально большое — сигнал не того файла/неполного
экспорта), что `unresolved_category_rows` и `unmatched_price_rows`
пусты или разобраны вручную перед продолжением, что список
`new_suppliers` ожидаем.

## Альтернативы

**Расширить `import_real_data.py` флагом `--merge`/`--no-wipe` вместо
отдельного скрипта.** Отклонено — `import_real_data.py` спроектирован
вокруг предположения "БД пуста после `TRUNCATE`" на каждом шаге
(`create_suppliers`/`create_materials` не проверяют существование,
всегда `INSERT`); ветвление всей функции на "wipe-режим"/"merge-режим"
внутри одного файла усложнило бы уже существующий, редко меняющийся
скрипт ради функциональности с принципиально другой семантикой
(реконсиляция против существующего состояния, не чистое наполнение) —
дешевле и понятнее как отдельный модуль, переиспользующий только
`xlsx_price_matrix.parse_price_matrix()`, не структуру самого
`import_real_data.py`.

**Fuzzy/similarity-matching названий вместо точного совпадения (п.1).**
Отклонено прямым требованием задачи, тем же обоснованием, что уже дважды
применено в этой кодовой базе к похожей проблеме (ADR-0019 п.2 —
alias только по точному совпадению; ADR-0025 п.1 — отказ от
векторного поиска в пользу полного списка кандидатов с LLM-решением,
но здесь даже LLM не привлекается: формат детерминированный,
машиночитаемый, эвристика "похоже, но не совпадает" добавляла бы риск
тихого слияния разных материалов без пропорциональной пользы).

**Не трогать активную цену при пустой ячейке (альтернатива п.2б).**
Рассмотрено и отклонено — см. полное обоснование в п.2б: ошибка "не
заметили реальный уход поставщика с позиции" дороже и обнаруживается
позже, чем ошибка "ложно закрыли реально доступную позицию", которая
самокорректируется при следующем естественном использовании системы.

**Новая сущность-журнал (`CatalogSyncRun`) вместо текстового
логирования (п.6).** Рассмотрено, отклонено для этого ADR — редкий,
операторский, недостаточно частый сценарий для отдельной queryable
БД-сущности; пересмотр возможен отдельным ADR при реальной
потребности (например, программный откат батча), не решается заранее.

**Построчный commit при `--apply`, как в batch-эндпоинте ADR-0030
п.4.3, вместо одной транзакции на весь запуск.** Отклонено — там
независимость строк оправдана конкурентным доступом нескольких
пользователей к одному экрану; здесь единственный оператор запускает
скрипт разово против всего каталога, частичный сбой без отката
оставил бы БД в состоянии, которое сложнее диагностировать
("применилось всё, кроме случайной строки где-то в середине"), чем
однозначный откат целиком с возможностью перезапустить скрипт заново.

## Не в объёме

- Изменение `import_real_data.py` — остаётся без изменений, для
  случая пустой БД (см. "Контекст").
- Нечёткое/AI-сопоставление материалов при синхронизации — явно
  отклонено п.1, тот же принцип, что ADR-0019/ADR-0025 уже применили к
  смежной задаче.
- Поведение при появлении 9-й, незнакомой категории — тот же вопрос,
  что ADR-0034 явно вынесла за рамки ("Не в объёме"), не переоткрывается
  здесь; текущее решение — явная ошибка строки в отчёте (п.3), не
  автосоздание категории.
- Массовое обновление `delivery_policy` новых поставщиков автоматически
  из каких-либо реальных данных — не в объёме, администратор заполняет
  вручную после `--apply` (п.5), как и при первом импорте.
- Программный откат конкретного батча синхронизации после `--apply` —
  не в объёме (п.6); при потребности — отдельный ADR.
- UI/экран для запуска этой синхронизации — операторский CLI-скрипт,
  не продуктовая фича с экраном; отдельная задача, если понадобится
  дать доступ к синхронизации не через терминал администратора.

## Последствия

- Новый скрипт `backend/app/scripts/sync_catalog_from_file.py` —
  `run_sync(db, path, apply) -> SyncReport`, `print_report(report)`,
  CLI с `--apply`, по образцу существующих backfill-скриптов.
  Переиспользует `xlsx_price_matrix.parse_price_matrix()`,
  `price.py:version_price()`, `services/material_sku.py:
  generate_next_sku()` (зависимость от ADR-0034, см. "Зависимость").
  Не изменяет и не вызывает `import_real_data.py`.
- `xlsx_price_matrix.SUPPLIER_COLUMN_HEADERS` — требует добавления
  записи для заголовка колонки "A&S" (и любого будущего нового
  поставщика) как часть обычного цикла использования скрипта, не
  автоматизируется (п.5) — тот же процесс, что уже действует для
  `import_real_data.py` сегодня.
- `docs/known-issues.md` — процедурное требование: каждый реальный
  (`--apply`) запуск скрипта в проде документируется вручную (дата,
  файл, сводка) — часть докстринга скрипта, не отдельный механизм
  (п.6).
- Тесты (новый файл `backend/tests/scripts/test_sync_catalog_from_file.py`,
  по аналогии с `test_backfill_material_categories.py`):
  - Точное совпадение `canonical_name` matched → корректная ветка
    п.2(а/б/в) в зависимости от состояния активной `Price`.
  - Whitespace-нормализация матчит строки, отличающиеся только
    пробелами; casing-различие (например, `"Door Handle"` vs
    `"DOOR HANDLE"`) **не** матчит (осознанно, не баг — п.1).
  - Пустая ячейка при существующей активной `Price` закрывает её без
    создания новой (п.2б) — регрессия ключевого решения этого ADR,
    явный тест, не подразумеваемое поведение.
  - Совпавший материал с расходящимся `Group`/`Quantity` в файле
    (например, `Group="Doors"` в файле против `category_id`,
    указывающего на `"Gutter"` в БД, и/или другой `unit`) — после
    `--apply` `Material.category_id` и `Material.unit` **не изменились**
    относительно значений до запуска, только `Price` этой пары
    обновилась как обычно (п.2а/б/в); строка присутствует в
    `category_or_unit_mismatches` отчёта (п.2.1) — прямая регрессия
    ключевого решения "этот путь синхронизирует только цену", не
    подразумеваемое поведение.
  - Новый материал: категория резолвится по имени → `generate_next_sku`
    вызван, `Price` создана в той же транзакции; незнакомая категория →
    `unresolved_category_rows`, материал не создан.
  - Новый поставщик → создан с `DEFAULT_DELIVERY_POLICY`-эквивалентом,
    присутствует в `new_suppliers` отчёта.
  - Материал в БД, отсутствующий в файле → не изменяется, ни одна его
    `Price` не закрывается, присутствует в `not_in_file`.
  - Dry-run не пишет в БД (никакой из разделов отчёта не приводит к
    `db.commit()` при `apply=False`), включая непроведённый инкремент
    `Category.next_sku_number`.
  - Верификация после `--apply`: искусственно испорченный случай
    (несовпадение подсчёта) откатывает всю транзакцию — тест на
    defensive-проверку, не только happy path (по аналогии с ADR-0034
    п.2 шаг 3).
- `docs/architecture.md`/`docs/data-model.md` — не меняются
  (никакая новая сущность/колонка не вводится этим ADR).
- Реализация (сам скрипт, тесты) — предмет отдельной задачи после
  вычитки этого ADR, **не начинается до мержа ADR-0034 в `main`** (см.
  "Зависимость").
