# ADR-0036: Очистка ведущего "1 " в Material.unit (регресс "180 1 sq ft")

Статус: Принято

## Контекст

На проде в строках вида "количество + единица измерения" (AllocationResultPage,
OrderDetailPage, PurchaseRecordsPage, ProjectDetailPage) отображалась лишняя
"1": "180 1 sq ft" вместо "180 sq ft", "1 1 pcs" вместо "1 pcs".

Расследование (см. систематический debugging в истории чата) показало, что
фронтенд рендерит `{quantity} {material.unit}` корректно — баг не в отображении,
а в самих данных: `Material.unit` для большинства материалов реально хранит
"1 sq ft", "1 pcs" и т.п., а не чистую единицу измерения.

Источник: `backend/app/scripts/xlsx_price_matrix.py`, функция `_clean_unit()`.
Колонка "Quantity" в исходном xlsx-прайсе (`materials_price_matrix.xlsx`,
ADR-0035) — это не чистая единица измерения, а склеенное поле "количество в
упаковке + единица" ("1 pcs", "1 box/100 pcs", "5 box"). `_clean_unit()`
исторически сохраняла эту строку как есть, без разбора. Проверено на реальном
файле: 288 из 301 строки имеют такую форму, из них подавляющее большинство —
ведущая "1" (198 "1 pcs", 52 "1 roll", 28 "1 box/100 pcs", 7 "1 sq ft", 3 "1 ft").

Это не регресс в смысле "кто-то откатил прошлый фикс" — `_clean_unit()` вела
себя так с момента появления xlsx-формата (заменил старый materials.csv,
где `unit` был чистым, см. docstring модуля). Симптом воспринимался как
регрессия, потому что баг того же вида ("лишнее число рядом с текстом")
уже чинился в этом проекте раньше в других местах — но в этом конкретном
случае корень новый: испорченные данные, а не испорченный рендер.

## Решение

1. `_clean_unit()` вырезает ведущий счётчик упаковки, только когда он равен
   `1` (regex `^1\s+(.+)$`) — "1 sq ft" → "sq ft", "1 pcs" → "pcs". Счётчик
   `1` не несёт информации (любой материал по умолчанию мыслится как "1 своей
   единицы"), поэтому его можно отбросить безопасно.
2. Счётчик, отличный от 1 (например "5 box"), **не трогается** — это реальная
   информация о размере упаковки (5 штук в коробке), а не мусор. Нет надёжного
   правила, что показывать в таком случае вместо исходной строки, не потеряв
   данные, которые продавец туда осознанно положил (см. существующий
   комментарий `_clean_unit` и ADR-0035 §2.1 про те же ограничения).
3. Это исправляет только: (а) новые материалы, создаваемые
   `sync_catalog_from_file.py`/`import_real_data.py` при следующем импорте;
   (б) отчёт `category_or_unit_mismatches` для уже существующих материалов —
   после фикса `file_unit` в отчёте будет чистым ("sq ft"), и любое
   расхождение с уже испорченным `Material.unit` в БД станет видно при
   следующем dry-run синхронизации.
4. Уже испорченные значения `Material.unit` в БД (материалы, заведённые ДО
   этого фикса) не переписываются автоматически — ADR-0035 §2.1 запрещает
   `sync_catalog_from_file.py` менять `unit`/`category_id` совпавших
   материалов без участия человека. Для них — отдельный ручной backfill:
   `backend/app/scripts/backfill_unit_pack_count.py`, dry-run по умолчанию,
   печатает список кандидатов на исправление и требует `--apply` (см. сам
   скрипт и его тесты).

## Альтернативы

- **Хранить количество в упаковке отдельным полем** (`Material.pack_quantity`)
  вместо того чтобы отбрасывать его. Отклонено для этого фикса: это схема-
  изменение с миграцией и потенциальным влиянием на ILP allocation engine
  (принцип 1 CLAUDE.md — детерминированный солвер, количество/единица —
  вход для него), то есть непропорционально большой blast radius для бага
  отображения. Может быть сделано отдельным ADR, если бизнесу понадобится
  сама величина упаковки (не только чистая единица) где-то в расчётах.
- **Просто откатить регресс** — неприменимо, так как это не регрессия кода,
  а изначально неверная обработка данных при вводе нового формата прайса.

## Последствия

- `Material.unit`, создаваемый через xlsx-импорт, отныне не должен содержать
  ведущую "1 " — это гарантия на будущее, не переиспользовать пройденный путь
  без пропуска через `_clean_unit()`.
- Пример "5 box" (и любой другой count ≠ 1) намеренно остаётся как есть в
  `unit` — при показе на фронтенде это даст "10 5 box" для quantity=10. Это
  ожидаемо согласно этому ADR, не повторно заводить как баг без нового
  решения о том, как правильно показывать составную упаковку.
- Любое дальнейшее изменение семантики `Material.unit` (например, разбиение
  на pack_quantity/unit) требует нового ADR, не тихого патча `_clean_unit()`.
- В текущем реальном каталоге случай "счётчик отличен от 1" не встречается
  вообще: все 288 испорченных строк — это ведущая "1" (198 "1 pcs" + 52
  "1 roll" + 28 "1 box/100 pcs" + 7 "1 sq ft" + 3 "1 ft" = 288). Пример
  "5 box" выше описывает архитектурный принцип на будущее (на случай, если
  такая строка появится в файле), а не реально существующий сегодня случай.
