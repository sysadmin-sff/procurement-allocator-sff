# ADR-0037: Удаление одного ордера — standalone endpoint, консолидация дублированной логики

Статус: Предложено

## Контекст

Реальный запрос с созвона: кнопка удаления одного конкретного `Order`, "в
пару кликов" — сотрудник отдела закупок создал draft-ордер по ошибке (не тот
поставщик, дубликат после сбоя, тестовый прогон) и должен иметь возможность
убрать его, не удаляя весь проект.

Сейчас трёхшаговый танец удаления одного `Order` (обнулить
`Price.source_order_item_id` → удалить его `OrderItem` → удалить сам `Order`)
продублирован в двух местах:

- `_delete_orders()` (`backend/app/allocation/order_service.py:492-517`) —
  вызывается из `create_orders_for_run()` при `replace_drafts=True`
  (ADR-0012 §2).
- `delete_project()` (`backend/app/api/project.py:211-273`), шаги
  236-254 — тот же трёхшаговый танец инлайн, не через `_delete_orders()`.

Обе копии обязаны делать одно и то же по одной и той же причине:
`order_items.order_id` не имеет `ON DELETE CASCADE` (ADR-0009 «Контекст»,
подтверждено ADR-0012 §2: "в текущей схеме такого каскада… нет… удаление
`Order` без предварительного удаления его `OrderItem` упадёт на
FK-ограничении"), а `Price.source_order_item_id` (ADR-0030 §6) — ссылка на
`order_items.id` без `ondelete` на уровне FK, поэтому обнуляется вручную в
коде перед удалением `OrderItem`. Для сравнения:
`AllocationLine.overridden_via_order_item_id` — тоже FK на `order_items.id`
(ADR-0014) — уже объявлен как `ondelete="SET NULL"` прямо в миграции
(`backend/alembic/versions/a1b2c3d4e5f6_add_overridden_via_order_item_id.py:28-35`)
и в модели (`backend/app/models/allocation.py:93-94`); `Price` — единственная
из двух ссылок на `order_items`, которая всё ещё решает эту задачу вручную в
Python, а не декларативно.

Прямого `DELETE /orders/{id}` эндпоинта сейчас не существует. `order.py`
защищён `router = APIRouter(dependencies=[Depends(get_current_user)])`
(`backend/app/api/order.py:61`) — любая роль, не admin-only (ADR-0024 §4,
таблица: `order.py` → "операционная работа, включая... не запись в реф.
данные").

`Order.status` на практике никогда не отличается от `"draft"` — подтверждено
на реальных данных (предыдущая сессия), не только чтением кода: ни один
эндпоинт/сервисный метод нигде не присваивает `"approved"`/`"sent"`
(`docs/known-issues.md`, раздел про `Order.status`). Условие возврата к этому
факту — то же, что уже зафиксировано для того known-issue и для ADR-0011:
"появление реального workflow «отправить ордер поставщику» (ручная кнопка
или интеграция), тогда видно, какая именно статусная модель нужна".

**ADR-0012 §2 отклонил отдельный `DELETE`-эндпоинт — не тот же вопрос.**
Дословно: "Отдельный `DELETE`-endpoint для удаления старых draft-ордеров
**перед созданием новых** (два раздельных запроса с фронта)... Отклонено,
потому что замена обязана быть одной атомарной транзакцией: если между
`DELETE` и `POST` создание упадёт... пользователь остаётся без единого
draft-ордера по этому поставщику". Это возражение — про атомарность
DELETE-затем-POST *replace*-сценария (ADR-0012 §2, `replace_drafts=true`), не
про удаление без последующего создания. Standalone-удаление, которое этот
ADR вводит, не участвует ни в какой замене — оно не оставляет систему без
альтернативы взамен удалённого, оно просто убирает ошибочный/лишний ордер.
Этот вопрос не переоткрывается здесь.

## Решение

### 1. Консолидация дублированной логики в `order_service.py`

Общая функция:

```python
def delete_order(db: Session, order: Order) -> None:
    """Delete one Order: null out any Price.source_order_item_id pointing
    at its OrderItem rows (ADR-0030 §6 audit back-reference only — the
    Price row and its created_by_user_id survive), delete the OrderItem
    rows, then the Order itself. Does not commit — caller controls the
    transaction. See ADR-0037."""
    _delete_orders(db, [order])
```

Переиспользует существующую `_delete_orders(db, orders: list[Order])`, не
переписывает её — сигнатура списком уже нужна `create_orders_for_run` (может
удалять draft-ордера нескольких поставщиков разом при `replace_drafts=True`),
`delete_order` — тонкая обёртка для случая "ровно один `Order`", той же
формы, что уже применяется в проекте (`update_price` как обёртка над
`version_price`, ADR-0030 §5).

**Три вызывающих места после консолидации:**
1. `create_orders_for_run()` при `replace_drafts=True` — заменяет прямой
   вызов `_delete_orders(db, conflicting_orders)` на тот же вызов
   (сигнатура не меняется, это уже список).
2. `delete_project()` (`backend/app/api/project.py:236-254`) — инлайн-код
   удаляется, заменяется вызовом `_delete_orders(db, orders)` (тот же список
   всех `Order` проекта, что сейчас собирается вручную в переменной
   `order_ids`/`item_ids`).
3. Новый standalone endpoint (§3) — `delete_order(db, order)` на одном
   `Order`.

**Явно подтверждено: не меняет наблюдаемое поведение двух существующих
мест.** Это чистое устранение дублирования, не поведенческое изменение:
- `create_orders_for_run`/`replace_drafts=True` — тот же SQL (те же три
  запроса: `UPDATE prices SET source_order_item_id = NULL...`, `DELETE FROM
  order_items...`, `DELETE FROM orders...`), тот же порядок, та же
  транзакция (вызывающий код по-прежнему коммитит сам, `_delete_orders` не
  коммитит и не коммитила раньше).
- `delete_project` — идентично: `_delete_orders` получает тот же список
  `Order`, что сейчас строит `delete_project` вручную по
  `Order.project_id == project_id`, выполняет те же три шага в том же
  порядке, `delete_project` продолжает сама коммитить в конце (после
  `PurchaseRecord`/`AllocationRun`/`AllocationLine`/`ProjectItem`/`Project`
  — `delete_order`/`_delete_orders` не знают о них и не должны).
- Ни один тест на `_delete_orders`-поведение (существующие тесты в
  `backend/tests/allocation/test_order_draft_conflict.py` и
  `backend/tests/allocation/test_project_deletion.py`, см. «Контекст»
  задачи) не должен потребовать изменений — они проверяют результат
  (что удалено, что осталось, `source_order_item_id == None`), не то, какая
  функция физически выполнила SQL.

**Отклонено: сделать `delete_project` вызывающей стороной `delete_order` в
цикле (по одному вызову на `Order`) вместо `_delete_orders(db, orders)`
списком.** Отклонено — превратило бы один batched `DELETE ... WHERE id IN
(...)` в N отдельных `DELETE` по одному ордеру, без причины (ни
корректность, ни консолидация этого не требуют — список уже общий
интерфейс, `delete_order` лишь частный случай списка из одного элемента).

### 2. FK-согласованность — `Price.source_order_item_id`: оставить ручное обнуление в коде, не переходить на `ondelete="SET NULL"`

**Решение: не добавлять `ondelete="SET NULL"` на FK
`prices.source_order_item_id → order_items.id`. Оставить явное обнуление в
`_delete_orders`/`delete_order`.**

Это осознанный выбор, не "то же самое, что уже было" по умолчанию —
рассмотрены оба варианта:

**За декларативный `ondelete="SET NULL"` (тот же паттерн, что
`overridden_via_order_item_id`):** убрал бы необходимость ручного обнуления
в консолидированной функции, переложил бы гарантию на уровень БД —
защищённее от будущего кода, который удалит `OrderItem`/`Order` в обход
`delete_order` и забудет про `Price.source_order_item_id` (ADR-0030 §6
явно называет этот столбец частью *обоснования безопасности* узкого
admin-исключения, не просто аудитом для удобства — молчаливое рассинхрон
здесь дороже обычного).

**Почему всё-таки нет, в этой задаче:** после консолидации (§1) во всей
кодовой базе останется **ровно одна** функция, физически выполняющая
`DELETE FROM order_items`/`DELETE FROM orders` — `_delete_orders`. Риск
"кто-то удалит `OrderItem` в обход обнуления" — тот самый риск, который §1
уже устраняет структурно (единая точка, не обход по построению, в отличие
от ситуации до этого ADR, когда было два места и она могла реально
разойтись). `ondelete="SET NULL"` добавил бы Alembic-миграцию и изменение
модели (`backend/app/models/price.py:45-47`) ради гарантии, которая после
консолидации уже обеспечена на уровне единственной функции в Python —
не обходимый через `db.delete()`/raw SQL путь физически не существует
нигде в кодовой базе на data-write слое проекта (весь доступ к БД — через
SQLAlchemy ORM/Core в сервисном слое, ADR-0002, не raw SQL по обходным
путям). Разница с `overridden_via_order_item_id` (ADR-0014) не в
принципе, а в истории: та колонка добавлена *одновременно* с
FK-декларацией в одной миграции — не было предшествующего ручного кода,
который нужно было бы согласовывать. Здесь ручное обнуление уже
существует, работает, покрыто тестами (`test_order_draft_conflict.py`,
`test_project_deletion.py`) — переход на `ondelete="SET NULL"` не меняет
наблюдаемый результат (оба пути дают `source_order_item_id = NULL` после
удаления `OrderItem`), только переносит место, где это происходит, без
устранения дополнительного риска сверх того, что уже даёт консолидация.

Дополнительный, более узкий довод: декларативный `ondelete="SET NULL"`
сработал бы и для гипотетических будущих путей удаления `OrderItem`, не
идущих через `delete_order` — но таких путей в кодовой базе сейчас нет
(единственные два места удаления `OrderItem` — оба уже консолидируются
этим ADR в §1), а вводить защиту от кода, который ещё не написан и не
запланирован, — то же нарушение YAGNI, которое CLAUDE.md уже требует
избегать ("не проектировать вслепую" — язык, уже использованный в
ADR-0007 §5/ADR-0030 «Контекст» для того же типа решения).

**Условие возврата к этому вопросу**: если в кодовой базе появится второе
место, удаляющее `OrderItem`/`Order` в обход `delete_order`/`_delete_orders`
(до ре-открытия этого решения — маловероятно, поскольку `delete_order`
становится единственной точкой входа, но не исключено architecturally),
тогда риск рассинхрона возвращается и декларативный `ondelete="SET NULL"`
становится оправданным — тот же тип условия, что уже применяется в проекте
(например, ADR-0033 §2 — расширение guard, если появится новый источник
записи).

**Отклонено: гибрид — добавить `ondelete="SET NULL"` и всё равно оставить
явное обнуление в коде "на всякий случай".** Отклонено — двойная защита
одного и того же факта без дополнительной гарантии (если код обнуляет явно
до удаления, декларативный `ondelete` никогда не сработает на практике;
единственный сценарий, где он бы сработал, — обход кода, который и так
устраняется §1) добавляет только шум в модели/миграции без выигрыша.

### 3. Ограничение на draft-only

`DELETE /orders/{order_id}` работает только для `order.status == "draft"`;
для любого другого статуса — `409 Conflict`.

Тот же guard, что уже есть в `delete_project` (`ProjectHasSentOrdersError`,
блокирует удаление проекта целиком, если хоть один его `Order` не draft) —
не новый принцип, применение уже принятого правила на уровне одного
`Order` вместо всего проекта. Обоснование то же, что в ADR-0007 §2/ADR-0009:
`approved`/`sent`-ордер — снимок физического документа, который мог уже
уйти поставщику; удаление такого не может быть операцией "в пару кликов" на
уровне одного ордера точно так же, как оно не может быть частью удаления
проекта.

Учитывая, что на практике **все** реальные ордера сейчас `draft`
(подтверждено на реальных данных, «Контекст») — это ограничение не
искусственно сужает функциональность прямо сейчас: сегодня оно не запрещает
ни одного реального use case, которого пользователь мог бы захотеть. Оно
фиксирует границу на будущее, когда появится реальный статус, отличный от
`draft`.

**Условие возврата**: то же, что уже зафиксировано для `Order.status` в
`docs/known-issues.md` и ADR-0011 — "появление реального workflow «отправить
ордер поставщику» (ручная кнопка или интеграция), тогда видно, какая именно
статусная модель нужна". Пока этого шага нет, guard `status == "draft"`
здесь (как и в `delete_project`) не проверяем на практике ни в каком другом
состоянии, кроме `draft` — тот же непроверяемый на реальных данных статус,
что уже отмечен как известное ограничение. Этот ADR не пытается решить
workflow "отправлено поставщику"/переход статуса — вне объёма, тот же вопрос
уже отложен ADR-0011, не переоткрывается здесь.

**Реализация guard**: переиспользует форму `OrderNotDraftError`
(`backend/app/allocation/order_service.py:76-82`, введена ADR-0033 §2 для
`add_raw_order_item` — "the composition of a non-draft Order is closed") —
тот же exception класс, тот же смысл ("мутация non-draft Order закрыта"),
удаление — ещё один вид мутации non-draft `Order`, которая должна быть
закрыта по той же причине. Не вводится отдельный exception специально для
удаления.

```python
def delete_order_by_id(db: Session, order_id: uuid.UUID) -> Order:
    """Look up the Order, raise OrderNotFoundError if missing, raise
    OrderNotDraftError if status != "draft", otherwise delete_order() it
    and commit. Returns the deleted Order's data is not meaningful after
    commit — callers use this for its side effect plus the 404/409 mapping
    at the API layer. See ADR-0037 §3."""
```

(точное имя/сигнатура — деталь реализации; ключевое — переиспользование
`OrderNotFoundError`/`OrderNotDraftError`, уже существующих в
`order_service.py`, не новых классов).

Endpoint:

```python
@router.delete("/{order_id}", status_code=204)
def delete_order_endpoint(order_id: uuid.UUID, db: Session = Depends(get_db)) -> None:
    ...
    except OrderNotFoundError: raise HTTPException(404, ...)
    except OrderNotDraftError: raise HTTPException(409, "Ордер уже не в статусе черновика — удаление недоступно.")
```

Формулировка сообщения 409 — по аналогии с уже существующим текстом
`delete_project_endpoint` ("У проекта есть отправленные поставщику ордера —
удаление недоступно.", `backend/app/api/project.py:286`), тот же тон и
уровень детализации.

### 4. Подтверждение перед удалением (frontend)

Модальное подтверждение, не многошаговая форма — "в пару кликов" означает
один клик на кнопку удаления + один клик на подтверждение в модалке, не
больше.

- Кнопка удаления — на экране деталей ордера (`OrderDetailPage` или
  эквивалент), рядом с прочими действиями над конкретным `Order`.
- По клику — модалка: "Удалить ордер? Это необратимо." Без дополнительных
  чекбоксов/текстового ввода — операция затрагивает ровно один `Order`,
  который пользователь уже открыл и видит целиком (в отличие от
  `OrderDraftConflictModal`, ADR-0012 §4, где несколько поставщиков и
  необходимость различить, у кого есть `confirmed_price` — здесь один
  ордер, одно решение).
- Если у удаляемого ордера есть хотя бы один `OrderItem` с
  `confirmed_price IS NOT NULL` или `received_price IS NOT NULL` (реальные
  цены, введённые сотрудником вручную, не восстановимые ни из чего — тот же
  критерий необратимости, что ADR-0012 §1 уже использует для
  `has_confirmed_prices`) — модалка добавляет ту же по духу, но не блокирующую
  строку предупреждения, что ADR-0012 §4 уже показывает для конфликта:
  "В этом ордере есть подтверждённые цены — они будут потеряны безвозвратно."
  Не отдельная ступень подтверждения (в отличие от ADR-0012 §1, где
  многошаговая защита оправдана потому, что общий клик "Заменить" мог
  незаметно задеть *несколько* поставщиков сразу в одном действии) — здесь
  пользователь и так смотрит ровно на один ордер, который сам открыл,
  дополнительная ступень не добавляет защиты, которой уже не даёт сам факт
  того, что это единственный, осознанно выбранный объект действия.
- Кнопки модалки: "Отмена" / "Удалить". По "Удалить" — `DELETE
  /orders/{order_id}`, `204` → закрыть модалку, уйти со страницы ордера
  (список ордеров проекта, откуда пришли, или `ProjectDetailPage`).
  `409` (гонка: статус изменился между открытием страницы и кликом) —
  закрыть модалку, показать тот же текст, что вернул backend, не выполнять
  удаление молча.

Требует записи в `docs/ui-reference.md` (условие показа кнопки удаления,
условие дополнительной строки предупреждения, текст модалки) — по тому же
правилу, что и остальные экраны (CLAUDE.md).

### 5. Права доступа

`DELETE /orders/{order_id}` — на роутере `order.py`, уже защищённом
`router = APIRouter(dependencies=[Depends(get_current_user)])`
(`backend/app/api/order.py:61`). Новый endpoint не получает собственный
`dependencies=`/`require_role` — наследует router-level защиту, как и все
остальные эндпоинты этого файла.

**Явно подтверждено**: удаление ордера остаётся на том же уровне доступа,
что и вся остальная работа с ордерами (`get_current_user`, любая роль) — не
admin-only. Обоснование то же, что ADR-0024 §4 уже даёт для `order.py`
целиком: "операционная работа отдела монтажа... включая... не запись в
реф. данные". Удаление одного своего draft-ордера — операционное действие
сотрудника над собственной рабочей записью того же рода, что создание
ордера (`POST .../orders`) или правка позиции (`PATCH .../items/{id}`),
не изменение справочных данных (`Supplier`/`Material`/`Price` через
admin-only роутеры, ADR-0024 §4 таблица) — граница admin/employee в этом
проекте проведена по типу данных (справочник vs операционная запись), не
по разрушительности отдельного действия, и удаление одного ордера не
пересекает эту границу.

Не в объёме: изменение permission-модели `order.py` в целом (весь роутер
остаётся `get_current_user`) — не переоткрывается здесь.

## Альтернативы

Альтернативы к каждому под-решению — инлайн в «Решение» (§1–§5), та же

## Последствия

- Новая функция `delete_order(db, order)` в
  `backend/app/allocation/order_service.py` — тонкая обёртка над
  существующей `_delete_orders`, без изменения её тела.
- `create_orders_for_run()` — без изменения поведения, вызов
  `_delete_orders` остаётся (или обновляется на `delete_order` в цикле по
  одному, если реализация решит явно перечислить по одному — деталь
  реализации, не меняющая результат; список остаётся основным путём, §1).
- `backend/app/api/project.py`: `delete_project()` заменяет инлайн-код
  строк 236-254 на вызов `_delete_orders(db, orders)` — то же поведение,
  меньше кода.
- Новый endpoint `DELETE /orders/{order_id}` в `backend/app/api/order.py`,
  `204` на успех, `404` если не найден, `409` если `status != "draft"`.
  Использует существующие `OrderNotFoundError`/`OrderNotDraftError`, не
  вводит новые классы исключений.
- Миграция БД: **не требуется**. `Price.source_order_item_id` остаётся без
  `ondelete` на уровне FK — §2 явно решает не менять схему.
- Новый UI: кнопка удаления на экране деталей ордера + модалка
  подтверждения (с условной строкой предупреждения при наличии
  `confirmed_price`/`received_price`) — требует записи в
  `docs/ui-reference.md`.
- Не меняется: permission-модель `order.py` (остаётся `get_current_user`,
  любая роль); статусная модель `Order.status`/workflow "отправлено
  поставщику" (ADR-0011, отложено); поведение `_delete_orders` как такового
  (только откуда её вызывают).
- Тесты — новые: `DELETE /orders/{id}` для draft (успех, `source_order_item_id`
  обнуляется, `OrderItem`/`Order` удалены), для non-draft (`409`, ничего не
  удалено), для несуществующего id (`404`); тест, что `delete_project` и
  `create_orders_for_run`/`replace_drafts` продолжают проходить без
  изменений (регрессия консолидации §1 — те же ассерты, что уже есть в
  `test_order_draft_conflict.py`/`test_project_deletion.py`, не должны
  потребовать правок).
- Реализация (backend: `delete_order`, endpoint, тесты; frontend: кнопка,
  модалка, `docs/ui-reference.md`) — предмет отдельной задачи после
  вычитки этого ADR, backend и frontend раздельно, как обычно в этом
  проекте.
