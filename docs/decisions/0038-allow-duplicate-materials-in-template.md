# ADR-0038: Разрешить повтор материала в шаблоне проекта — снятие уникальности (template_id, material_id)

Статус: Принято — частично отменяет ADR-0032 §1.

## Контекст

ADR-0032 §1 ввёл уникальный индекс `(template_id, material_id)` на
`ProjectTemplateItem` явно: "чтобы один материал не попал в шаблон дважды",
по аналогии с принципом 3 CLAUDE.md (не дублировать сущность в рамках одной
связи).

На практике это привело к плохому UX без компенсирующей пользы:

- Администратор, добавляя материал в `TemplateItemsPanel`, который уже есть
  в шаблоне, получает `409` от backend (`add_template_item`,
  `backend/app/api/template.py`, ловит `IntegrityError` от уникального
  индекса) — добавление молча не происходит.
- Хуже того, фронтенд показывает **неверное** сообщение об ошибке:
  `ProjectTemplatesPage.tsx` использует один общий `ErrorBanner` с
  `conflictMessage="Шаблон с таким названием уже существует."` для *любого*
  409 на странице шаблонов (create/rename/addItem/removeItem одинаково) —
  так что попытка добавить дубликат материала показывает пользователю текст
  про конфликт **имени шаблона**, что не имеет отношения к происходящему и
  вводит в заблуждение.
- Прямой пользовательский запрос: не блокировать повторное добавление того
  же материала, а подсвечивать обе строки как дубль, чтобы решение
  "оставить оба или убрать один" осталось за человеком (визуальный паттерн
  подсветки дублей уже реализован в `TemplateItemsPanel.tsx`, см. commit
  "Group TemplateItemsPanel by category, highlight duplicate materials" —
  но он был **мёртвым кодом** для новых добавлений, поскольку backend уже
  не давал создать вторую строку с тем же `material_id`).

Довод ADR-0032 §1 ("не дублировать сущность в рамках одной связи",
принцип 3 CLAUDE.md) в реальности не подходит для этого случая:
принцип 3 — про идентичность материала (`internal_sku`, не строковое имя),
не про то, сколько раз позиция может встретиться в шаблоне. У шаблона нет
`quantity` (ADR-0032 §1) — единственный способ выразить "нужно два разных
комплекта одного и того же материала в базовом наборе" (например, два
одинаковых замка на входную и заднюю дверь одного проекта, которые сотрудник
хочет видеть как два отдельных пункта, а не мысленно домножать после
применения шаблона) — это именно повторная строка. Блокировка не защищает от
реальной ошибки, а мешает легитимному сценарию.

## Решение

Снять уникальный индекс `uq_project_template_item` — `ProjectTemplateItem`
больше не гарантирует уникальность `(template_id, material_id)` на уровне
БД. Материал может входить в один шаблон более одного раза, каждое
добавление — обычная новая строка.

### 1. Backend

- `backend/app/models/project_template.py`: убрать
  `__table_args__ = (UniqueConstraint("template_id", "material_id", ...),)`
  у `ProjectTemplateItem`.
- Новая Alembic-миграция: `DROP CONSTRAINT uq_project_template_item` (down —
  восстановить индекс; если к моменту отката в БД уже накопились
  дубликаты, откат состояния данных не в объёме этой ADR — так же, как
  любая другая ADR-миграция не решает произвольное состояние данных на
  момент отката).
- `backend/app/api/template.py`, `add_template_item`: убрать
  `try/except IntegrityError` вокруг `db.commit()`, введённый специально
  для этого индекса (409 "Material already in this template" был *для*
  этого ограничения — без ограничения ловить нечего; обычная вставка).
  Проверка "материал существует" (`404`) остаётся.
- `create_project` (`app/api/project.py`, ADR-0032 §3) — **без изменений**.
  Уже создаёт по одному `ProjectItem(quantity=1)` на каждый
  `ProjectTemplateItem` независимо; шаблон с двумя строками одного
  `material_id` даёт две строки `ProjectItem` — то же самое поведение,
  что и раньше для *разных* материалов, никакой специальной логики
  слияния не добавляется (см. "Альтернативы").

### 2. Frontend — TemplateItemsPanel

Уже реализованная подсветка дублей (группировка по категории + подсчёт
`material_id` + класс `duplicateRow` + бейдж "дубль", коммит
"Group TemplateItemsPanel by category, highlight duplicate materials")
становится действующей логикой без изменений в самом компоненте —
добавление дубликата теперь реально доходит до backend и возвращает
шаблон с двумя строками, что и должно было подсвечиваться с самого начала.

### 3. Frontend — исправление ErrorBanner на странице шаблонов (сопутствующий баг)

Отдельная, но связанная проблема: `ProjectTemplatesPage.tsx` передаёt
`conflictMessage="Шаблон с таким названием уже существует."` в единственный
`<ErrorBanner>`, общий для всех действий страницы (`handleCreate`,
`handleRename`, `handleAddItem`, `handleRemoveItem`, `handleDelete`). Любой
409 показывает этот текст, даже когда причина другая. Это баг независимо от
текущей ADR (проявится для любого будущего 409 на этих действиях), но
именно он маскировал реальную причину блокировки, обсуждаемой здесь —
чинится в рамках той же задачи.

Исправление: `conflictMessage` применяется только к 409 от
`handleCreate`/`handleRename` — по действию, вызвавшему ошибку, а не
безусловно для любого 409 на странице. Минимальный способ: хранить в
состоянии не просто `unknown`, а пару "какое действие/какая ошибка"
(например, `{ action: 'create' | 'rename' | 'addItem' | 'removeItem' | 'delete'; error: unknown }`),
и передавать `conflictMessage` в `<ErrorBanner>` только когда
`action === 'create' || action === 'rename'`. Для остальных действий
`ErrorBanner` показывает `error.detail` как есть (уже корректно
человекочитаемый текст с backend, например "Material not found").

`TemplateForm.tsx` не меняется — по-прежнему полагается на баннер
родителя (см. комментарий в `handleSubmit`), меняется только то, какое
сообщение этот баннер показывает в зависимости от источника ошибки.

## Альтернативы

**Слияние дублей в `quantity` при применении шаблона к проекту (ADR-0032
§3).** Рассмотрено, отклонено. `ProjectTemplateItem` намеренно не хранит
`quantity` (ADR-0032 §1) — если бы дубликаты должны были схлопываться в
большее количество, это было бы неявным способом всё-таки выразить
количество через число повторяющихся строк, что прямо противоречит
явному решению ADR-0032 §1 не хранить/не подразумевать `quantity`
отличным от 1. Также вводит вопрос "а что если хотят три или больше",
не имеющий отношения к текущему запросу (просто разрешить дубликат и
подсветить). Каждая строка шаблона — независимая позиция, как и было
решено; повторное применение просто даёт больше независимых позиций.

**Разрешить дубликаты только в UI (не трогать backend/БД), подделывая
подсветку на клиенте без реальной второй строки.** Отклонено — сервер
остаётся источником правды по принципу 4 CLAUDE.md ("все денежные и
количественные операции — только на backend"); фронтенд не может создать
несуществующую на backend позицию шаблона, любая подсветка без реальных
данных с сервера — фикция, которая разойдётся при обновлении страницы.

**Оставить уникальный индекс, но добавить отдельную, более точную
формулировку 409 ("Материал уже в этом шаблоне") вместо снятия
блокировки.** Рассмотрено — решило бы только баг с неверным текстом
ошибки, но не выполнило бы явный запрос пользователя ("не блокировать
добавление, только подсвечивать"). Отклонено как не отвечающее
поставленной задаче, а не как технически неверное — если бы требование
было только "почини текст ошибки", это было бы верным маленьким фиксом
без ADR.

## Последствия

- Изменяет ADR-0032 §1 в части "уникальность `(template_id, material_id)`
  — партийный индекс… чтобы один материал не попал в шаблон дважды".
  Остальные решения ADR-0032 (§2-5) не затронуты.
- Новая Alembic-миграция (drop constraint).
- `backend/app/models/project_template.py`,
  `backend/app/api/template.py` — код правится.
- `frontend/src/routes/ProjectTemplatesPage.tsx` — состояние ошибки
  становится action-aware; `conflictMessage` больше не безусловный.
- `docs/data-model.md:368-369` — заменить утверждение "Уникальный индекс
  `(template_id, material_id)` — один материал не может входить в шаблон
  дважды" на описание нового поведения, со ссылкой на эту ADR.
- Тесты (обязательны):
  - backend: `tests/template/test_api.py::test_add_same_material_twice_returns_409_not_duplicate`
    прямо утверждает старое поведение (второй `POST` → `409`, в БД остаётся
    одна строка) — заменяется тестом на новое поведение (`201`, две строки).
    Не оставлять старый тест рядом с новым — они взаимоисключающие
    утверждения об одном и том же эндпоинте.
  - backend: новый тест в `tests/project/test_api.py` — `create_project` с
    шаблоном, содержащим дублирующийся `material_id`, создаёт два
    `ProjectItem` по `quantity=1`.
  - frontend: `TemplateItemsPanel` — добавление уже присутствующего
    материала не блокируется (реальный ответ API с двумя строками), обе
    строки подсвечены как дубль; `ProjectTemplatesPage` — 409 от
    `addItem`/`removeItem` показывает `error.detail`, не текст про имя
    шаблона; 409 от `create`/`rename` по-прежнему показывает текст про имя
    шаблона.
