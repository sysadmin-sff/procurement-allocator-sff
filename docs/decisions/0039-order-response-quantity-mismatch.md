# ADR-0039: Сравнение quantity из ответа поставщика с OrderItem.quantity

Статус: Предложено

## Контекст

`backend/app/order_response_parser/` (ADR-0018) классифицирует строки распознанного
ответа поставщика на `matched`/`missing`/`extra` по единственному критерию —
наличию `matched_order_item_id` (`service.py::parse_order_response`, строки 85-89):

```python
matched_ids = {line.matched_order_item_id for line in extracted if line.matched_order_item_id}
matched_lines = [line for line in extracted if line.matched_order_item_id is not None]
extra_lines = [line for line in extracted if line.matched_order_item_id is None]
missing_items = [item for item in order.items if item.id not in matched_ids]
```

`ExtractedLine` (`client.py`, строки 22-28) уже извлекает `quantity: int | None` —
LLM-модель видит и распознаёт количество из документа поставщика (промпт,
`client.py:83`: `"quantity: количество, если указано в документе; null, если не
указано"`). Это значение доходит до фронтенда нетронутым — `MatchedLineOut.quantity`
(`backend/app/api/schemas/order_response_parser.py:21`) присутствует в ответе API
(`backend/app/api/order.py:443`). Но нигде на пути от извлечения до отображения оно
не сравнивается с `OrderItem.quantity` (`backend/app/models/order.py:62`, `NOT NULL`,
наш план закупки). `ParseResponseSection`/`MatchedLineRow` на фронтенде
(`OrderDetailPage.tsx:1385-1435`) не читает `line.quantity` вообще — таблица
"Совпало" (строки 1281-1312) не имеет колонки под количество.

Модель, что важно, уже **видит** наш план количества в том же промпте —
`_order_items_context` (`service.py:38-49`) передаёт `quantity: item.quantity` в
контекст, `client.py` включает его в текст (`f"кол-во={item['quantity']}"`) — то
есть теоретически модель могла бы сама заметить расхождение, но структурно нигде
не извлекается отдельное поле сравнения ни в `ExtractedLine`, ни после ответа модели.

**Реальный инцидент**: поставщик прислал позицию с `quantity=4`, в нашем ордере было
`quantity=2` (`OrderItem.quantity`). Позиция матчилась по `matched_order_item_id`
(правильно, тот же материал), поэтому классифицировалась как обычный `matched` — расхождение
в 2× по количеству прошло без единой подсветки, вошло бы в PATCH при "Применить все
совпадения" (`OrderDetailPage.tsx:1146-1185`) без единого сигнала пользователю.

## Решение

### 1. Не новая категория — поле поверх `matched`, по прямой аналогии с `received_price`

Категория (`matched`/`missing`/`extra`) в этом пайплайне отвечает на вопрос
"удалось ли распознавателю сопоставить строку документа с позицией нашего плана"
— это вопрос **идентичности** (какой материал), решаемый исключительно
`matched_order_item_id`. Расхождение по количеству — вопрос о **свойстве уже
установленного соответствия**, ортогональный самому матчингу: строка либо
сопоставлена, либо нет, независимо от того, совпадает ли количество внутри
сопоставленной пары. Ровно то же рассуждение уже применено к цене в ADR-0013/
ADR-0027 — `received_price`/`received_price_delta` не породили категорию
"расхождение по цене", а стали nullable-полями на той же строке `OrderItem`
(`backend/app/models/order.py`, строки 72, 76) и вычисляемой парой в
`OrderItemOut` (`schemas/order.py:56-59`, через переиспользуемую
`price_delta()`, `order_service.py:757-766`, обобщённую по значению, не
привязанную к конкретному имени поля).

Копируем этот паттерн буквально:

- `OrderItem.received_quantity: int | None` — новая nullable-колонка,
  количество из ответа поставщика для уже сматченной позиции. `NULL` — либо
  строка ещё не разобрана, либо LLM не распознала количество в документе
  (`ExtractedLine.quantity is None`) — не 0, ровно тот же принцип, что
  `received_price IS NULL` (ADR-0007 §1/§4, переиспользован ADR-0013).
- `quantity_delta: int | None` на `OrderItemOut` — вычисляемое,
  `received_quantity - quantity`, `None` при `received_quantity IS NULL`.
  Не персистится, как `price_delta`/`received_price_delta`.

### 2. Где проставляется

`order_response_parser` остаётся read-only (докстринг `service.py:1-6` — не
меняем этот инвариант). `received_quantity` заполняется тем же путём, что и
`received_price`/`confirmed_price` — явный PATCH после того, как пользователь
подтвердил совпадения (`handleApplyAllMatched`, `OrderDetailPage.tsx:1146-1185`,
сейчас пишет только `[targetField]: price`; расширяется до `{ [targetField]:
price, received_quantity: line.quantity }`, но **только** когда `targetField ===
'received_price'`; при `targetField === 'confirmed_price'` (второй раунд, после
торга по `target_price`, ADR-0027 §2) PATCH пишет только `confirmed_price`,
`received_quantity` не переписывается повторно).

**Важное уточнение, не продуманное в первой версии этой ADR**: `ParseResponseSection`
(`OrderDetailPage.tsx:1066`) — один и тот же компонент, рендерится дважды с разным
`targetField` (строки 345 и 353), каждый раз со своим собственным `result` (свой
файл, свой вызов `parseResponse`). `MatchedLineRow` внутри него **не
параметризуется по `targetField`** ни сегодня, ни в этой ADR — значит колонка
"Кол-во" и подсветка расхождения (§5) рендерятся одинаково в обоих раундах,
независимо от того, какой из них пишет в БД. Если поставщик во втором раунде
(отвечая на `target_price`) заодно меняет количество — например, исправляет
ошибку, которую сам заметил после первого ответа, — это ровно случай (б) из
двух возможных, не (а): значение **не теряется молча**. Пользователь видит
расхождение визуально в тот же момент, что и в первом раунде (та же колонка,
та же подсветка, тот же `line.quantity` из вновь загруженного файла), может
среагировать вручную — поправить `OrderItem.quantity` до отправки, открыть
replacement-flow (ADR-0014/0015) или просто заметить и учесть при финальной
проверке ордера. Персистится (пишется в `received_quantity`) при этом только
значение из первого раунда — это осознанное, а не случайное ограничение,
обоснование см. ниже.

**Почему безопасно персистить только первый раунд.** `received_quantity` — это
факт "что подтвердил поставщик в ответ на наш исходный запрос", той же природы,
что `received_price` (ADR-0013) — оба поля физически введены как парность к
`quoted_price`/`quantity` **плана**, не как журнал всех раундов переписки.
Второй раунд в этой кодовой базе (ADR-0027 §2) уже устроен так, что пишет
только `confirmed_price` — не заводит `confirmed_quantity`, не расширяет
`OrderItem` вторым слоем сравнения для количества, потому что сам процесс
второго раунда специфичен для цены (реакция на `target_price`, наш встречный
торг) — количество там не было предметом переговоров ни до, ни после этой ADR.
Добавлять `confirmed_quantity` ради этого случая означало бы вводить третье
поле сравнения (`quantity` / `received_quantity` / `confirmed_quantity`) под
сценарий, для которого нет прецедента ни в одном существующем ADR и нет
прямого аналога `confirmed_price` (у `confirmed_price` есть явная причина
существовать отдельно — фиксация окончательной цены сделки для расчётов;
у количества после первого раунда такой отдельной причины нет, план
(`OrderItem.quantity`) либо меняется вручную пользователем, либо не меняется).

`set_order_item_fields` (`order_service.py:949-959`) получает новый keyword-параметр
`received_quantity: int | None = _UNSET`, с тем же `_UNSET`-сентинелом (строка 769),
без специальной логики — просто ещё одно независимо-опциональное поле PATCH,
тот же механизм, что уже несёт пять таких полей.

### 3. Не блокирует — UI-подсветка без гарда на backend

Backend **не отклоняет и не блокирует** PATCH/подтверждение при
`received_quantity != quantity`. Это решение по прямой аналогии с ADR-0013 §2
(дословно: "Backend не проверяет и не запрещает никакую комбинацию `declined_at`
+ `received_price`/`confirmed_price`") и с паттерном "Отказался" в
price-comparison (ADR-0016 §3) — оба случая расхождения между планом и фактом
от поставщика в этой кодовой базе разрешены как *видимые, не блокирующие*
сигналы, оставляющие решение человеку.

Гварды в духе `DraftOrderConflictError` (ADR-0012) — не подходящий прецедент.
Тот класс гвардов блокирует **создание новых сущностей** (повторные draft-ордера
поставщику), где ошибка необратима и дорога (дублирующиеся ордера в БД). Здесь
речь о PATCH одного поля на уже существующем `OrderItem` — пользователь всегда
может исправить/перепроверить значение до отправки ордера, отменить конкретную
строку (`declined`) или оставить как есть осознанно. Реальные причины
расхождения по количеству у поставщика (частичная поставка, апсейл по своей
инициативе, опечатка с любой из двух сторон) требуют **разных** реакций
человека — ни одна не выводится автоматически из самого факта расхождения,
значит жёсткий блок был бы неверен чаще, чем полезен.

Взвешивание "что хуже" (по аналогии со структурой ADR-0028 — не абстрактно,
а через два симметричных сценария отказа):

- **Тихо принять** (текущее поведение, без этой ADR) — расхождение проходит
  незамеченным, ордер отправляется/подтверждается с неверным количеством в
  плане закупки. Уже случилось на практике (инцидент выше) — стоимость этого
  сценария подтверждена, не гипотетична.
- **Жёстко заблокировать** (нельзя подтвердить/применить, пока пользователь
  не разрешит конфликт явно) — стоимость: каждая легитимная частичная поставка
  или согласованный апсейл превращается в дополнительный обязательный шаг
  разрешения, даже когда расхождение уже замечено и осознанно принято
  человеком в момент клика "Применить". Непоследовательно с тем, как уже
  решён тот же вопрос для цены (ADR-0013/0016) — два свойства одной и той же
  сматченной строки (цена, количество) вели бы себя по разным правилам без
  видимой причины.
- **Видимая, не блокирующая подсветка** (это решение) — стоимость близка к
  нулю (одна колонка, один визуальный сигнал), выгода — тот же инцидент
  перестаёт быть тихим: пользователь видит расхождение в тот момент, когда
  решает, применять строку или нет, до PATCH, а не после.

Средний вариант (подсветка) доминирует над обоими крайними при одинаковой
структуре компромисса, что уже была принята для цены — целесообразно
единообразие, а не повторное открытие того же вопроса с другим ответом.

### 4. Пересечение с missing/extra

Не конфликтует по построению: `received_quantity`/`quantity_delta` — поля
исключительно на `matched`-строках (только там существует пара
`OrderItem.quantity` + строка ответа, которую можно сравнить). `missing`-позиции
(`MissingItemOut`, `schemas/order_response_parser.py:33`) уже несут `quantity`
плана — им сравнивать не с чем, ответа от поставщика по ним нет. `extra`-строки
(`ExtraLineOut`, строка 39) не привязаны ни к одному `OrderItem` — `quantity` там
уже используется как seed для *новой* позиции (`ExtraLineRow`,
`OrderDetailPage.tsx:1487`), это не тот же случай и не меняется этой ADR.

### 5. UI

`MatchedLineRow` (`OrderDetailPage.tsx:1385-1435`) получает колонку "Кол-во"
(рядом с существующими "Наша позиция"/цена-колонками, `1286-1290`), показывающую
`line.quantity` рядом с `orderItem.quantity` (план). При `line.quantity != null &&
line.quantity !== orderItem.quantity` — построчная подсветка тем же локальным
словарём, что уже использует эта страница для аналогичных сигналов на той же
таблице: класс по образцу `.discrepantRow`/`.declinedRow`
(`OrderDetail.module.css:143-151`, построчная подсветка `var(--color-danger-tint)`/
`var(--color-danger-text)` при значимом расхождении), не `badgeWarning`
(тот класс из `CrudScreen.module.css:307` не используется на этой странице —
`OrderDetailPage` держит собственный локальный словарь классов вместо общего
`badge`). Новый класс `.quantityMismatchRow` — по образцу существующего
`.discrepantRow` (не переиспользует его буквально, т.к. `.discrepantRow`
завязан на порог `SIGNIFICANT_PRICE_DELTA_PCT`, а расхождение по количеству —
бинарное: `received_quantity === quantity` или нет, без процентного порога,
любое расхождение в штуках значимо для закупки).

Значение показывается как есть (`4` при плане `2`), не как дельта — в отличие
от `PriceDelta` (`OrderDetailPage.tsx:787-808`), где показывается именно
разница. Количество — не денежная величина, абсолютное число само по себе
достаточно информативно (пользователь и так видит план рядом), а знак дельты
(+2/-2) не добавляет ясности, которую не даёт уже само сопоставление двух чисел
в соседних колонках.

## Альтернативы

**Отдельная четвёртая категория `quantity_mismatch`.** Отклонено — потребовала
бы дублировать всю структуру `matched`-обработки (чекбокс включения, reasoning,
подтверждение цены) внутри новой категории или расщеплять один UI-блок на два
почти идентичных, ради различия, которое уже адекватно выражается одним
дополнительным полем на существующей строке. Также ломает уже устоявшийся в
этом пайплайне принцип "категория = matching identity" (см. §1) без причины,
специфичной для quantity, которой нет для price.

**LLM сам сравнивает и явно возвращает флаг расхождения** (например,
`ExtractedLine.quantity_matches: bool`), вместо вычисления на backend после
извлечения. Отклонено — расхождение `received_quantity != OrderItem.quantity`
детерминированно вычислимо из уже извлечённого числа; перекладывать
арифметическое сравнение на LLM добавляет источник нестабильности
(галлюцинация булева поля) туда, где backend может посчитать точно и
воспроизводимо. Согласуется с принципом 2 CLAUDE.md — LLM только там, где вход
неструктурирован; сравнение двух уже структурированных чисел таковым не
является.

**Жёсткая блокировка подтверждения при расхождении** (в духе `DraftOrderConflictError`).
Рассмотрено и отклонено — обоснование в §3 выше. Как и ADR-0012 §1 сам
явно отклонил "жёсткий 409 без возможности продолжить" для конфликта черновиков,
здесь по той же логике отклоняется полный блок: пользователь должен сохранить
возможность осознанно принять расхождение одним действием, а не быть
вынужден проходить дополнительный шаг подтверждения для уже понятного ему случая.

**Полагаться на то, что модель уже видит план количества в промпте, и просто
понадеяться, что она откажется матчить строку с сильно другим количеством.**
Отклонено — именно это уже происходит сегодня и именно это привело к
инциденту: модель матчит по совпадению материала (описание/цена/контекст), не
обязана и не должна сама решать, является ли расхождение по количеству
ошибкой распознавания или легитимным фактом (частичная поставка) — это
решение принадлежит человеку, а не модели (принцип 2 CLAUDE.md: результат ИИ
всегда заканчивается экраном ревью, не тихим решением).

## Последствия

- Новая Alembic-миграция: `order_items.received_quantity INTEGER NULL`.
- `backend/app/models/order.py` — новое nullable-поле `received_quantity` на
  `OrderItem`, по образцу `received_price` (строка 72).
- `backend/app/api/schemas/order.py` (`OrderItemOut`) — новые поля
  `received_quantity: int | None = None`, `quantity_delta: int | None = None`.
- `backend/app/allocation/order_service.py`:
  - `set_order_item_fields` — новый параметр `received_quantity: int | None = _UNSET`.
  - `_to_order_item_out` (`backend/app/api/order.py:71-110`) — вычисление
    `quantity_delta` (простое вычитание, не требует новой функции по образцу
    `price_delta()`, т.к. нет процентной составляющей и не нужен `None`-guard
    сверх обычного `is None`).
- `frontend/src/api/types.ts` — `OrderItem`/`OrderItemOut`-тип получает
  `received_quantity`, `quantity_delta`.
- `frontend/src/routes/OrderDetailPage.tsx`:
  - `handleApplyAllMatched` — PATCH расширяется полем `received_quantity`
    (только для `received_price`-варианта секции, не для `confirmed_price`-варианта
    второго раунда торга).
  - `MatchedLineRow` — новая колонка "Кол-во", условная подсветка строки.
- `frontend/src/routes/OrderDetail.module.css` — новый класс
  `.quantityMismatchRow` по образцу `.discrepantRow`/`.declinedRow`.
- `docs/data-model.md` — добавить `received_quantity` в описание `OrderItem`,
  со ссылкой на эту ADR (по аналогии с тем, как там уже описан `received_price`
  со ссылкой на ADR-0013).
- Не меняет: категоризацию `matched`/`missing`/`extra` (§1 этой ADR явно
  сохраняет её как есть), read-only инвариант `order_response_parser`
  (докстринг `service.py:1-6`), поведение `ExtraLineRow`/`MissingItemMarkUnavailable`.
- Тесты (обязательны):
  - backend: `set_order_item_fields` — `received_quantity` PATCH-ится
    независимо от остальных полей (по образцу существующих тестов на
    `received_price`); `_to_order_item_out`/`quantity_delta` — `None` при
    `received_quantity IS NULL`, корректная разница иначе, отсутствие влияния
    на `price_delta`/`received_price_delta`.
  - backend: `parse_order_response` — категоризация `matched`/`missing`/`extra`
    не меняется при наличии/отсутствии совпадения количества внутри `matched`
    (регрессионный тест на §4 — расхождение по quantity не переводит строку в
    `missing`/`extra`).
  - frontend: `MatchedLineRow` — подсветка появляется только при
    `line.quantity != null && line.quantity !== orderItem.quantity`, отсутствует
    при `line.quantity == null` (модель не распознала количество в документе)
    и при точном совпадении.
  - frontend: `ParseResponseSection` с `targetField="confirmed_price"` —
    подсветка и колонка "Кол-во" в `MatchedLineRow` отображаются точно так же,
    как в `targetField="received_price"` варианте (не зависят от `targetField`);
    `handleApplyAllMatched` для этого варианта отправляет PATCH **без**
    `received_quantity` (только `{ confirmed_price: price }`) — явный
    регрессионный тест на разделение "видно в обоих раундах, персистится
    только в первом", описанное в §2.
