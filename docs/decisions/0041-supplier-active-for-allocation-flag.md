# ADR-0041: Явный флаг "поставщик участвует в расчёте распределения"

Статус: Предложено

## Контекст

Сегодня нет административного способа временно исключить поставщика из
ILP-расчёта распределения (ADR-0002), кроме одного: закрыть вручную все его
активные `Price` (`valid_to = now()`). Это буквально то, что было сделано
по SSH на проде для A&S — сработало, но это ручная, неаудируемая операция
без UI, полагающаяся на прямой доступ к БД.

**Как сегодня формируется список кандидатов-поставщиков для ILP.**
`run_allocation` (`backend/app/allocation/service.py:118-135`) не читает
`Supplier` для решения "участвует ли он" — участие выводится косвенно:

```python
prices = db.scalars(
    select(Price).where(Price.material_id.in_(material_ids), Price.valid_to.is_(None))
).all()
...
supplier_ids = {p.supplier_id for p in prices}          # строка 134
suppliers = db.scalars(select(Supplier).where(Supplier.id.in_(supplier_ids))).all()
```

Поставщик без единой активной цены на нужные материалы просто не попадает
в `supplier_ids` → не попадает в `AllocationInput.suppliers`. `Supplier` как
сущность сегодня не имеет `is_active`/`enabled` — есть только
`status: str | None` (ADR-0010), заявленно свободный текст.

**Что фиксирует ADR-0010 про `status` — проверено по тексту, не по памяти.**
ADR-0010 п.1 прямо говорит: *"`status` — свободный текст, не enum. В
реальных данных видно только 2 разных значения, но это не гарантирует
закрытый список: формулировки... — это заметки о состоянии отношений с
поставщиком, а не фиксированные категории."* Модель (`backend/app/models/
supplier.py:32-33`) повторяет это в докстринге: `"""Свободный текст
("Активные закупки" и т.п.), не enum — см. ADR-0010."""`. Это подтверждает
предположение из задачи: `status` задуман как человеко-читаемая заметка для
карточки поставщика (ADR-0010 п.4, секция "Основная информация"), не как
поле, которое код расчёта когда-либо должен парсить. Ничего в ADR-0010 не
говорит и не подразумевает обратного.

**Прецедент в этой же кодовой базе.** `User.is_active` (`backend/app/
models/user.py:26`, `Boolean, nullable=False, default=True`) — ровно тот же
паттерн "отключить без удаления": используется как gate-проверка в
`auth/service.py:36` (`if not user.is_active: ...` при логине) и управляется
через `UserUpdate.is_active` в админ-экране пользователей
(`backend/app/api/user.py`). Прямая аналогия по форме (bool-флаг, default
`True`, отдельное поле, не совмещённое со свободнотекстовым полем).

## Решение

### 1. Где живёт флаг: `Supplier.is_active_for_allocation: bool`, default `True`

Новое поле на `Supplier`, отдельное от `status`:

```python
is_active_for_allocation: Mapped[bool] = mapped_column(
    Boolean, nullable=False, default=True, server_default=sa.true()
)
"""Административный флаг участия в ILP-расчёте (ADR-0041). Не то же самое,
что отсутствие активных Price — см. ADR-0041 п.2 про различие причин."""
```

**Почему не переиспользовать `status`.** Три независимые причины, не одна:

- **Фактическая, по ADR-0010**: `status` прямо задокументирован как
  свободный текст ("заметки о состоянии отношений"), не закрытый список
  значений. Превратить его в машинно-читаемый флаг означало бы либо (а)
  парсить произвольные формулировки по подстрокам — хрупко, сломается на
  следующей же новой формулировке, которую кто-то впишет в карточку
  поставщика, либо (б) задним числом навязать `status` enum-семантику,
  которую ADR-0010 явно отверг, что требует нового ADR, переопределяющего
  0010, а не тихой перегрузки поля.
- **Семантическая**: `status` — это заметка *для человека* на карточке
  поставщика (секция "Основная информация", ADR-0010 п.4), которую видит и
  правит кто угодно с доступом к форме поставщика. Флаг участия в расчёте —
  *управляющий* параметр, который явно должен быть отдельным полем с
  понятным именем, читаемым кодом расчёта напрямую, без риска, что
  случайная правка текстовой заметки ("уменьшили закупки из-за цен")
  незаметно исключит поставщика из ILP или наоборот.
- **По прецеденту кодовой базы**: `User.is_active` уже устанавливает
  паттерн "административный bool-флаг участия, отдельный от любых
  описательных текстовых полей" — последовательно использовать то же имя
  и форму для аналогичной задачи у `Supplier`, а не изобретать второй
  способ решать ту же проблему.

Название `is_active_for_allocation`, не просто `is_active` — на `Supplier`
уже есть `status` (свободный текст про отношения с поставщиком в целом), и
голое `is_active` рядом с ним читалось бы как ещё один синоним `status`.
Явный суффикс `_for_allocation` фиксирует, что это узкоспециализированный
флаг ровно одного потребителя (ILP-солвер), не общий переключатель
"поставщик активен как сущность вообще" (та же дисциплина именования, что
уже применена к `is_active_for_allocation`-подобным узким полям в проекте,
например `Material.requires_single_supplier` на `Category`, а не общий
`mode`).

### 2. Где фильтруется: после сборки `supplier_ids` по ценам, не до

Правка — в `run_allocation` (`backend/app/allocation/service.py`), сразу
после строки 134 (`supplier_ids = {p.supplier_id for p in prices}`), перед
запросом `Supplier`:

```python
prices = db.scalars(
    select(Price).where(Price.material_id.in_(material_ids), Price.valid_to.is_(None))
).all()
...
supplier_ids = {p.supplier_id for p in prices}
suppliers = db.scalars(
    select(Supplier).where(
        Supplier.id.in_(supplier_ids),
        Supplier.is_active_for_allocation.is_(True),
    )
).all()
active_supplier_ids = {s.id for s in suppliers}
price_inputs = [p for p in price_inputs if uuid.UUID(p.supplier_id) in active_supplier_ids]
```

**Почему после, не до.** Фильтрация по `Price.valid_to.is_(None)` (строка
119) и фильтрация по `Supplier.is_active_for_allocation` — запросы к разным
таблицам с разной селективностью; текущий код уже устроен как "сначала
цены → вывести поставщиков из цен" (строки 118-135), а не "сначала
поставщики → цены под них". Вставлять флаг раньше этого порядка означало бы
либо отдельный ранний запрос к `Supplier` без пользы (все равно нужно
пересечение с `supplier_ids` из цен), либо инвертировать порядок всей
функции без архитектурной необходимости. Фильтрация сразу после строки 134
— минимальная правка на один конкретный шаг, не рефакторинг.

**`price_inputs` после фильтра `suppliers` тоже нужно подрезать.** Иначе
`AllocationInput.prices` продолжит содержать `PriceInput` для
деактивированного поставщика, которого нет в `AllocationInput.suppliers` —
несогласованный вход для солвера (ADR-0002 предполагает, что каждая цена в
`prices` ссылается на поставщика, присутствующего в `suppliers`; сегодня
это верно автоматически, потому что `supplier_ids` строится из тех же
`prices` без промежуточной фильтрации — с новым флагом это перестаёт быть
автоматическим и должно стать явным шагом).

**Две разные причины отсутствия поставщика — разводятся явно.** "Нет
активной цены на нужные материалы" и "отключён флагом
`is_active_for_allocation`" — из текущего кода солвера неразличимы (оба
дают "поставщика нет в `AllocationInput.suppliers`"), но семантически это
разное: первое — следствие состояния прайса (могло бы исчезнуть само по
себе, если появится новая цена), второе — намеренное административное
решение. В объём этого ADR входит только backend-фильтрация (см. выше);
причина по которой конкретный поставщик не попал в список кандидатов для
*одного конкретного расчёта* сегодня нигде не выводится пользователю (ни
для "нет цены", ни для "отключён флагом") — UI-объяснение "почему
поставщика нет в списке" в объём **не входит**, это самостоятельное
расширение `docs/ui-reference.md` (экран результата allocation), которое
можно сделать отдельной задачей позже, когда будет понятно, что оно реально
востребовано (тот же принцип "не проектировать вслепую", что уже применён в
ADR-0010 к `comments`). Здесь фиксируется только то, что два пути
семантически различны и не должны молча смешиваться в одном булевом
"поставщика нет" без потери информации о причине — достаточно, чтобы код
фильтрации был явным (два отдельных условия в запросе/коде, не одно общее
"куда-то делся"), а не чтобы UI уже показывал разницу.

### 3. Существующие `Order`/`AllocationLine` — флаг не ретроактивен

Деактивация поставщика (`is_active_for_allocation = False`) влияет только
на **будущие** вызовы `run_allocation`. Не трогает:

- Существующие `AllocationLine`, уже ссылающиеся на этого поставщика
  (`supplier_id` на строке — ссылка на факт прошлого расчёта, не на
  "текущего валидного кандидата").
- Существующие `Order`, созданные на основе прошлых `AllocationRun`.
- Ручной override поставщика на существующей `AllocationLine`
  (`override_allocation_line_supplier`, ADR-0006) — этот путь сегодня не
  фильтрует кандидатов через `run_allocation`; вопрос, должен ли
  деактивированный поставщик быть недоступен как **новая** цель ручного
  override на уже существующем расчёте, в объём этого ADR не входит
  (отдельный вопрос UX ручного override, не автоматического ILP-подбора) и
  явно откладывается, а не решается по умолчанию.

Это симметрично двум уже принятым в проекте прецедентам:

- Закрытие `Price.valid_to` уже работает так же — закрытая цена не
  меняет/не скрывает прошлые `AllocationLine`/`Order`, которые
  зафиксировали цену на момент расчёта (`unit_price`/`line_total` на
  `AllocationLine` — снимок, не вычисляемое значение).
- Soft-удаление шаблона/категории (ADR-0032 §4, ADR-0038) — конфигурация,
  меняющая будущее поведение, не переписывающая прошлое состояние.

Никакой каскадной правки `Order`/`AllocationLine` при изменении флага не
требуется — ни в модели, ни в миграции, ни в сервисном коде.

### 4. UI — чекбокс на уже существующей карточке `/suppliers/:id`

Экран уже существует: `/suppliers` (`SuppliersPage.tsx`, обзорный список) +
`/suppliers/:id` (`SupplierDetailPage.tsx`, карточка с секциями, введена
ADR-0010 п.4). Это **не** новый CRUD-экран — масштаб задачи не меняется на
"завести admin-экран с нуля", только на расширение уже существующей формы.

- **Список `/suppliers`**: добавить колонку/индикатор активности участия в
  расчёте (например, доп. колонка "Участвует в расчёте" рядом с "Статус",
  или бейдж в существующей колонке "Статус" — конкретная разметка решается
  на этапе реализации по `docs/design/`, не здесь) — чтобы деактивированный
  поставщик был виден сразу в обзоре, не только при открытии карточки.
- **Карточка `/suppliers/:id`**, секция "Основная информация" (та же
  секция, где уже редактируются `status`/`payment_terms`/пр., ADR-0010
  п.4): добавить чекбокс "Участвует в расчёте распределения", сохраняется
  вместе с остальной формой (тот же `PATCH`-паттерн, что уже описан в
  ADR-0010 для этой секции).
- **Уровень доступа** — `admin`, тот же, что весь `/suppliers/*` роутер
  сегодня: `backend/app/api/supplier.py:34` — `APIRouter(prefix=
  "/suppliers", dependencies=[Depends(require_role("admin"))])` уже
  применяется ко всем операциям над поставщиком на уровне роутера (тот же
  принцип ADR-0024 §5 — "не размазывать защиту", уже использованный для
  этого же роутера). Новое поле просто входит в существующий `PATCH
  /suppliers/{id}`, никакого нового эндпоинта или отдельной проверки роли
  не требуется. Фронтенд — тот же паттерн `disabled={!isAdmin}`, что уже
  используется в `SuppliersPage.tsx` (UI-подсказка, не граница
  безопасности — граница на backend).

### 5. Миграция — non-nullable колонка с `server_default`

```python
op.add_column(
    "suppliers",
    sa.Column(
        "is_active_for_allocation",
        sa.Boolean(),
        nullable=False,
        server_default=sa.true(),
    ),
)
```

**`server_default`, не только application-level default.** Три причины:

- Таблица `suppliers` сегодня непустая (8 строк) — `nullable=False` без
  `server_default` на уже существующих строках потребовал бы отдельного
  `UPDATE`-шага внутри той же миграции (SQLite/Postgres: `ALTER TABLE ...
  ADD COLUMN ... NOT NULL` без default на непустой таблице либо падает,
  либо требует явного значения). `server_default=sa.true()` решает это за
  один шаг — ровно так же, как уже сделано для `Category.
  requires_single_supplier` (`backend/alembic/versions/
  a54edb312c7c_...py:28` — `Boolean(), nullable=False, server_default=
  sa.false()`), прямой прецедент того же класса миграции в этом же
  проекте.
- `server_default` защищает и пути, которые создают `Supplier` в обход
  Python-слоя приложения (прямые `INSERT` при ручных операциях на проде —
  ровно тот класс операций, которым в этой задаче уже один раз
  воспользовались для A&S). Application-level default (`default=True` в
  `mapped_column` без `server_default`) не покрывает такие пути.
- После применения миграции `default=True` на уровне `mapped_column`
  остаётся — не как замена `server_default`, а как явное намерение в коде
  модели (та же двойная запись, что уже принята для `requires_single_
  supplier`: `Boolean, nullable=False, default=False` в модели +
  `server_default=sa.false()` в миграции).

### 6. Обратная совместимость с ручным отключением A&S — вернуть цены, переключить флагом

Рекомендация: после выката флага — открыть обратно вручную закрытые цены
A&S (`valid_to = NULL`) и выставить `A&S.is_active_for_allocation = False`
через новый UI.

**Обоснование.** Если оставить как есть (цены закрыты руками + флаг
`True` по умолчанию, то есть фактически не используется для A&S), система
окажется в состоянии, где один и тот же результат ("A&S не участвует в
расчёте") объясняется одним механизмом (закрытые цены), а не тем, который
вводит этот ADR. Это не ломает корректность расчёта (оба пути дают
одинаковый эффект — п.2 выше), но создаёт ровно ту путаницу, которую сам
ADR призван устранить: следующий человек, открывший карточку A&S, увидит
`is_active_for_allocation = True` (значение по умолчанию) и не поймёт, почему поставщик
всё равно отсутствует в allocation — придётся отдельно идти смотреть
`Price.valid_to` по всем материалам A&S, то есть возвращаться к тому же
непрозрачному ручному расследованию, которое этот ADR должен был закрыть.
Возврат цен + переключение флагом делает состояние A&S
самообъясняющимся через тот же UI, что и любой другой будущий случай
деактивации — нет двух параллельных, взаимно непрозрачных способов
достичь одного эффекта на одном и том же поставщике.

Не блокирующее условие для выката самого ADR/функционала — это операционный
шаг после реализации, не часть миграции или кода.

## Альтернативы

**Переиспользовать `status: str | None` как машинный флаг (через парсинг
или превращение в enum).** Отклонено — см. п.1: прямо противоречит
зафиксированному в ADR-0010 назначению поля (человеко-читаемая заметка,
явно не enum), совмещало бы в одном поле два разных потребителя (человек,
читающий заметку vs код расчёта) с риском, что правка одного молча ломает
другого.

**Фильтровать до сборки `supplier_ids` (отдельный ранний запрос по
`Supplier.is_active_for_allocation`, пересекать с ценами).** Рассмотрено,
отклонено — см. п.2. Не даёт функциональной разницы (то же множество
поставщиков на выходе), но требует либо лишнего запроса, либо инверсии
уже существующего порядка построения `run_allocation` без архитектурной
необходимости.

**Жёстко блокировать создание новых `Price` для деактивированного
поставщика на уровне API прайс-ревью.** Рассмотрено, отклонено — выходит
за рамки задачи ("флаг — про участие в расчёте", не "про возможность вести
цены") и создаёт дополнительную связанность между модулем прайс-ревью и
модулем allocation, которой сегодня нет. Деактивированный поставщик может
продолжать иметь актуальные цены в БД (например, временная приостановка
закупок без желания терять историю цен) — это отдельное, оправданное
состояние, не баг.

**Каскадно скрывать/помечать существующие `AllocationLine`/`Order`
деактивированного поставщика.** Отклонено — см. п.3, прямо противоречит
уже принятому в проекте принципу "прошлые расчёты — снимок на момент
расчёта, не производное текущего состояния справочника".

**Не возвращать цены A&S, оставить как есть (цены закрыты + флаг
неиспользуемый).** Рассмотрено при выборе рекомендации п.6, отклонено в
пользу единообразия — см. обоснование там.

## Последствия

- Новая колонка `suppliers.is_active_for_allocation` (`BOOLEAN NOT NULL
  DEFAULT true`, `server_default=sa.true()`), одна Alembic-ревизия. Не
  трогает существующие колонки `suppliers`, не трогает `Price`/
  `AllocationLine`/`Order`.
- `backend/app/models/supplier.py` — новое поле `is_active_for_allocation:
  Mapped[bool]`.
- `backend/app/allocation/service.py` — правка `run_allocation` сразу
  после текущей строки 134: фильтр `Supplier.is_active_for_allocation.is_(
  True)` при запросе `suppliers`, плюс подрезка `price_inputs` до
  активных поставщиков (см. п.2).
- `backend/app/api/schemas/supplier.py` (`SupplierOut`/`SupplierUpdate` или
  их текущие аналоги) — новое поле, доступное через существующий `PATCH
  /suppliers/{id}` (роутер уже `admin`-only, новых эндпоинтов не требуется).
- Frontend: `SuppliersPage.tsx` — индикатор в списке;
  `SupplierDetailPage.tsx`, секция "Основная информация" — чекбокс,
  сохраняется тем же `PATCH`, что и остальные поля секции (по образцу
  формы, описанной в ADR-0010 п.4). Не новый экран.
- `docs/data-model.md` — новое поле на `Supplier` в ER-диаграмме/описании.
- `docs/ui-reference.md` — новый пункт в поведении карточки `/suppliers/
  :id`: чекбокс "Участвует в расчёте распределения", admin-only.
- Тесты (обязательны, ADR-0002/CLAUDE.md "Тесты"): `run_allocation` не
  включает поставщика с `is_active_for_allocation=False` даже при наличии
  активной цены; поставщик с флагом `True`, но без активных цен,
  по-прежнему отсутствует (существующее поведение не меняется); смена
  флага не изменяет существующие `AllocationLine`/`Order` уже завершённых
  расчётов; `PATCH /suppliers/{id}` с `is_active_for_allocation` — 403 для
  `employee`/без сессии (тот же паттерн проверки, что у прочих admin-only
  полей роутера).
- Явно вне объёма, зафиксировано как возможное будущее расширение:
  UI-объяснение "почему конкретный поставщик не попал в кандидаты для
  этого расчёта" (различение "нет цены" vs "отключён флагом" на экране
  результата allocation, не только в коде фильтрации); доступность
  деактивированного поставщика как цели **ручного** override
  (`override_allocation_line_supplier`, ADR-0006) на уже существующей
  `AllocationLine`.
- Операционный шаг после реализации (не часть кода/миграции): вернуть
  активные цены A&S (`valid_to = NULL`) и переключить его
  `is_active_for_allocation = False` через новый UI — см. п.6.
- Реализация (миграция, backend-фильтр, схемы, frontend) — предмет
  отдельной задачи после ревью этого ADR.
