# ADR-0042: Фиксированный порядок отображения категорий

Статус: Предложено

## Контекст

`Category` (ADR-0034) сегодня не имеет поля порядка — только `id`, `name`,
`sku_prefix`, `requires_single_supplier`, `next_sku_number`, `created_at`.
Категорий в системе 8: Doors, Gutter, Caulk, Profil, Roof panels, Mesh,
Connectors, Screws. Они были созданы один раз бэкфилл-скриптом из
`SELECT DISTINCT category FROM materials` — порядок их появления в БД
недетерминирован и не несёт смысла.

Порядок, в котором категории видны пользователю, сегодня складывается из
нескольких независимых и несогласованных источников:

- `GET /categories` (`backend/app/api/category.py:17`) — сортирует по
  `Category.name`, т.е. алфавитно. От этого наследуют `CategoriesPage.tsx`
  (CRUD-список) и `useCategories()` (селекты в `MaterialForm.tsx`,
  `PriceListImportReviewPage.tsx`).
- `frontend/src/lib/groupByCategory.ts:18-37` — общий хелпер группировки
  строк (шаблонов, BOM) по `category_name`. Сортировка — **first-appearance
  order** во входном массиве items, категория без имени — всегда последней.
  Используется в `TemplateItemsPanel.tsx:56` и `ProjectBuilderPage.tsx:144`.
- `frontend/src/routes/ProjectDetailPage.tsx:297,400-428` — независимо
  продублированная копия той же first-appearance-логики
  (`groupItemsByCategory`), не импортирует общий хелпер.
- `PriceComparisonPage.tsx` (ADR-0016) и `AllocationResultPage.tsx` категории
  не группируют вовсе (первая — плоская матрица материал×поставщик, вторая
  группирует по поставщику; `category_name` там используется только как ключ
  для предупреждений о split-категориях).

Ни ADR-0034, ни ADR-0016 порядок отображения категорий не специфицируют —
он нигде не был осознанным решением, а просто выпал из порядка ввода данных.
Это даёт разный порядок групп в разных экранах одного и того же приложения
(first-appearance зависит от того, в каком порядке пользователь вводил
строки) и не соответствует тому, как монтажники физически думают о категориях
(двери → водосток → герметик → профиль → кровельные панели → сетка →
крепёж → саморезы — порядок, утверждённый отделом монтажа).

Нужен единый, стабильный порядок, применяемый согласованно везде, где
категории участвуют в группировке или отображении списком.

## Решение

### 1. Где хранится порядок

Добавляем колонку `Category.display_order: int`, `NOT NULL`, **без
уникального constraint на уровне БД**. Совпадение двух значений — не
ожидаемая, но переживаемая ситуация (не «баг данных» в смысле падения
запроса): любая сортировка по `display_order` везде в коде задаётся как
`ORDER BY display_order, name` — `name` служит детерминированным
тай-брейкером. Причина не делать `UNIQUE`: это админский инструмент
расстановки порядка, а не идентификатор; при ручной правке через будущий UI
(см. п.6) временное совпадение значений в процессе перетаскивания — обычное
промежуточное состояние, и не стоит держать в БД constraint, из-за которого
любая транзакция перестановки требует doubleshuffle (временного значения вне
диапазона) только чтобы не упасть на intermediate constraint violation.

Дефолт для новых категорий, создаваемых позже через `POST /categories`:
**`MAX(display_order) + 1` по всем существующим категориям** (0, если
категорий ещё нет), вычисляется на backend в момент создания. Явное
значение через API не принимается (см. п.6 — управление порядком вне объёма
для UI); поле `display_order` отсутствует в `CategoryCreate`/`CategoryUpdate`
схемах. Это гарантирует, что новая категория всегда встаёт в конец видимого
списка, не нарушая уже расставленный порядок остальных 8.

### 2. Миграция и бэкфилл

Одна Alembic-миграция:

1. `ALTER TABLE categories ADD COLUMN display_order INTEGER`.
2. Data-миграция (в теле той же миграции, через `op.get_bind()`) — проставляет
   `display_order` по точному совпадению `name`:

   | name | display_order |
   |---|---|
   | Doors | 0 |
   | Gutter | 1 |
   | Caulk | 2 |
   | Profil | 3 |
   | Roof panels | 4 |
   | Mesh | 5 |
   | Connectors | 6 |
   | Screws | 7 |

3. После простановки — `ALTER COLUMN display_order SET NOT NULL`.

Бэкфилл сверяет набор имён в БД с этим списком **строго**, регистр и пробелы
не нормализуются:

- Если в БД есть категория с `name`, отсутствующим в списке выше (опечатка,
  лишний пробел, другой регистр, категория, заведённая уже после написания
  этого ADR) — миграция **падает** (`raise RuntimeError` с текстом,
  перечисляющим точные несовпавшие `name`), а не проставляет `NULL`/`0` и не
  пропускает молча. `NOT NULL` на шаге 3 всё равно бы это поймал, но упасть
  нужно раньше — с понятным сообщением, а не с голой ошибкой constraint.
- Если в списке выше есть имя, отсутствующее в БД (категория ещё не
  заведена/переименована) — это не ошибка миграции: `display_order` для
  несуществующей строки просто не на что проставлять. Строка лога
  (`WARNING`) об этом достаточна.

Даунгрейд — `DROP COLUMN display_order`.

### 3. Где менять сортировку на `display_order`

`groupByCategory.ts` и `groupItemsByCategory` (в `ProjectDetailPage.tsx`)
получают на вход items с `category_name: string`, не объект `Category` —
`display_order` туда не долетает без изменений. Два варианта: (а) прокинуть
`display_order` в каждую схему, где сегодня есть `category_name`
(`MaterialOut`, `ProjectTemplateItemOut`, и т.д. — расширять при каждом новом
использовании), или (б) держать на фронте справочник `name → display_order`
и сортировать по нему в самих хелперах.

**Выбираем (б).** `useCategories()` уже существует, уже дергает
`GET /categories` и уже расшарен как «единый источник списка категорий»
(см. докстринг хука, п.2/3 его исходной задачи). Вариант (а) требует трогать
каждую DTO, где сегодня есть `category_name` (как минимум `MaterialOut`,
`ProjectTemplateItemOut`, и любую будущую), размножая одно и то же число по
всем ответам API, где уже есть более естественное место — единый список
категорий. Вариант (б) меняет сортировку в одном месте (`GET /categories`) и
у потребителей хелперов группировки, не трогая ни одной из схем, что уже
содержат `category_name`.

Конкретные изменения:

- **`GET /categories`** (`category.py:17`): `ORDER BY display_order, name`
  вместо `ORDER BY name`. Это автоматически даёт правильный порядок в
  `CategoriesPage.tsx` и во всех `<select>`, использующих `useCategories()`
  (см. п.5).
- **`groupByCategory.ts`**: сигнатура меняется на приём справочника
  `categoryOrder: Map<string, number>` (или `Record<string, number>`)
  вторым параметром. Группировка по `category_name` остаётся как есть
  (items внутри группы группируются как раньше), но итоговый порядок
  **групп** строится сортировкой по `categoryOrder.get(category) ?? Infinity`
  вместо first-appearance; категория, отсутствующая в справочнике (в теории
  недостижимо при консистентных данных, но на всякий случай — например,
  рассинхрон кэша `useCategories()` с БД) — в конец, перед «Без категории»,
  которая остаётся жёстко последней. Оба существующих вызывающих места
  (`TemplateItemsPanel.tsx:56`, `ProjectBuilderPage.tsx:144`) уже имеют
  доступ к `useCategories()` или должны его получить (оба — компоненты
  верхнего уровня страницы, добавление хука тривиально) и передают
  построенный из него `Map<name, display_order>`.
- **`ProjectDetailPage.tsx`**: см. п.4 — либо переводится на общий хелпер
  (тогда правка совпадает с предыдущим пунктом), либо получает симметричную
  правку сортировки на месте, если решим не консолидировать сейчас.
- **`PriceComparisonPage.tsx`, `AllocationResultPage.tsx`**: изменений не
  требуют — они не группируют по категории сегодня, и этот ADR не добавляет
  такую группировку (вне объёма).

### 4. Консолидация `ProjectDetailPage.tsx`

**Рекомендация: консолидировать в рамках этого же ADR**, не выносить отдельной
задачей. Обоснование: `groupItemsByCategory` в `ProjectDetailPage.tsx` —
копия той же first-appearance-логики с той же дырой (нет учёта
`display_order`), которую мы и так обязаны исправить, чтобы `ProjectDetailPage`
не остался единственным экраном со старым, рассинхронизированным порядком.
Исправлять копию на месте (дублируя новую логику сортировки по
`display_order` ещё и туда) — тот же объём работы, что и удалить копию и
заменить на вызов общего хелпера с тем же справочником. Откладывать
консолидацию значило бы намеренно оставить временное окно, где один экран
использует общую логику с фиксом, а другой — независимую копию без фикса,
до следующей сессии. Разница в объёме работы между «исправить дубликат» и
«удалить дубликат и вызвать общий хелпер» — несколько строк; риск
рассинхронизации в будущем (кто-то поправит `groupByCategory.ts` и забудет
про копию) — реальный и уже материализовавшийся один раз (это и есть текущая
причина дублирования). Хелпер уже параметризован через generic `<T extends
CategorizedItem>`, `ProjectItem`+`Material`-комбинация должна быть адаптирована
к `CategorizedItem` (`{ material_id, category_name }`) перед вызовом — это
уже делает сегодняшняя `groupItemsByCategory` неявно, так что адаптация не
добавляет нового объёма.

### 5. `CategoriesPage.tsx` (CRUD-список)

Сортируется по `display_order` — автоматически, без изменений на фронте,
как только `GET /categories` отдаёт данные в этом порядке (п.3). Явное
решение: **не оставлять алфавитный порядок на CRUD-экране**, даже как
опцию — рассинхрон «в CRUD один порядок, в группировке материалов другой»
прямо то, что этот ADR должен устранить, и он бы воспроизвёлся на первом же
экране, если тут сделать исключение.

### 6. Управление порядком через UI (вне объёма)

**Вне объёма этого ADR.** `display_order` после бэкфилла управляется только
прямой операцией в БД (или разовым скриптом по аналогии с
`backfill_material_categories.py`) — `CategoriesPage.tsx` не получает в
рамках этой задачи ни drag-and-drop, ни поле для ручного ввода номера.
Причина вынести отдельно: это самостоятельный кусок работы (UI для
reordering, валидация, вероятно — batch-эндпоint `PATCH /categories/reorder`
вместо точечных `PATCH` на каждую категорию, чтобы не по одной пересчитывать
уникальность/тай-брейки) с отдельной UX-поверхностью, не нужной для того,
чтобы зафиксировать уже утверждённый порядок 8 существующих категорий. Если
до появления UI понадобится завести категорию №9 не в конец списка, а
где-то в середине — это делается прямым `UPDATE` в БД, так же, как сегодня
управляются другие поля без UI (например, `requires_single_supplier`
выставляется бэкфилл-скриптом, не через `CategoriesPage.tsx`).

## Альтернативы

- **Захардкодить порядок в frontend-константе** (массив имён категорий,
  `indexOf()` вместо `display_order` из БД). Отклонено: порядок — это
  бизнес-данные отдела монтажа, а не деталь UI; хардкод в коде фронтенда
  означает, что смена порядка требует деплоя фронтенда, а не правки в БД, и
  создаёт риск рассинхрона, если этот же порядок понадобится backend'у
  (например, для сортировки в будущем экспорте ордер-документов).
- **Уникальный `display_order`** с `UNIQUE constraint`. Отклонено — см. п.1:
  избыточная жёсткость для админского поля порядка, усложняет будущий UI
  reordering без выгоды, потому что везде используется `ORDER BY
  display_order, name`, что и так даёт детерминированный результат при
  коллизии.
- **Прокидывать `display_order` в каждую DTO с `category_name`** (вариант
  (а) из п.3). Отклонено в пользу справочника на фронте — см. обоснование
  там.
- **Ничего не трогать в `ProjectDetailPage.tsx` в рамках этого ADR**
  (оставить дублирующую копию, поправив её отдельно). Отклонено — см. п.4.

## Последствия

- `Category.display_order` — новое обязательное поле; любой будущий код,
  создающий категорию напрямую (минуя `POST /categories`, например,
  в тестовых фикстурах или скриптах), обязан его проставлять — `NOT NULL`
  без server-side дефолта на уровне БД (дефолт — только в application-слое
  эндпоинта создания, см. п.1).
- `groupByCategory()` меняет сигнатуру (новый обязательный параметр) —
  ломающее изменение для обоих вызывающих мест; оба должны быть поправлены
  в этом же PR, иначе TypeScript не даст собрать проект.
- `ProjectDetailPage.tsx` теряет собственную `groupItemsByCategory` —
  переиспользует общий хелпер.
- Порядок 8 категорий становится управляемым только через БД/скрипт до
  появления отдельного UI-таска (п.6) — это сознательное ограничение,
  задокументированное здесь, не забытое упущение.
- Любое последующее решение дать `CategoriesPage.tsx` drag-and-drop
  reordering — отдельный ADR не обязателен (не архитектурное решение, а
  фича существующего экрана), но должно явно сослаться на этот ADR при
  реализации batch-эндпоинта для смены порядка.
