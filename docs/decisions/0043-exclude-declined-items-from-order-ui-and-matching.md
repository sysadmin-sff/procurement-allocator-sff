# ADR-0043: Исключить declined+перенесённые позиции из общего списка ордера и из matching-контекста ответа поставщика

Статус: Принято

## Контекст

Позиция ордера может быть отклонена и перенесена другому поставщику
(`OrderItem.declined_at IS NOT NULL`, связь переноса — `overridden_via_order_item_id`,
ADR-0013 §3, ADR-0014). Сегодня такая позиция участвует на равных с активными
в двух местах, не предусматривавших для неё отдельной обработки:

1. **OrderDetailPage.tsx** — `sortedItems` ([OrderDetailPage.tsx:283-285](../../frontend/src/routes/OrderDetailPage.tsx#L283-L285))
   берёт полный `order.items` и только сортирует так, что declined-строки уходят
   вниз списка. Рендерится именно `sortedItems`
   ([OrderDetailPage.tsx:393](../../frontend/src/routes/OrderDetailPage.tsx#L393)) —
   ничего не фильтруется. Отличие от активных строк — только CSS-класс
   `declinedRow` и текстовая метка «→ Перенесено на …» внутри самой строки
   (`styles.replacedNotice`, ~строка 1001-1007). Строка остаётся в общем списке.

2. **order_response_parser/service.py** (ADR-0018 §3) — `_order_items_context()`
   ([service.py:38-49](../../backend/app/order_response_parser/service.py#L38-L49))
   строит контекст для LLM из всего `order.items` без фильтра по `declined_at`.
   `missing_items` ([service.py:89](../../backend/app/order_response_parser/service.py#L89))
   строится тем же образом: `[item for item in order.items if item.id not in matched_ids]`.

Следствие — путаница при разборе ответа нового (принявшего перенос) поставщика:
declined-позиция либо попадает в категорию `missing` (хотя её отсутствие в ответе
этого поставщика ожидаемо — мы сами её отклонили и перенесли, он её и не должен
был прислать), либо, если поставщик по инерции упомянул её в тексте ответа,
LLM может ошибочно сматчить с ней extracted-строку (`matched_order_item_id`
указывает на declined item), что тоже неверно — эта позиция больше не относится
к его заказу.

Перенос позиции и её история (`overridden_via_order_item_id`, ADR-0014) при этом
уже работают правильно и не меняются этим ADR — проблема только в видимости
в UI и в участии в matching-контексте разбора ответа.

## Решение

### 1. UI ордера (OrderDetailPage.tsx)

- Из основного списка (`sortedItems` / таблица в OrderDetailPage.tsx:390-393)
  по умолчанию исключаются строки с `declined_at != null`.
- Они выносятся в отдельную сворачиваемую секцию «Перенесённые позиции» под
  основным списком, свёрнутую по умолчанию.
- Секция переиспользует существующий паттерн `collapsedCategories` /
  `toggleCategory()` ([OrderDetailPage.tsx:1113-1114](../../frontend/src/routes/OrderDetailPage.tsx#L1113-L1114)),
  которым уже пользуются секции matched/missing/extra блока разбора ответа
  поставщика — тот же визуальный компонент (шеврон + заголовок с count +
  сворачиваемое тело), новый ключ в `collapsedCategories` (например `declined`).
- Содержимое секции при раскрытии — те же строки `OrderItemRow`, что и сейчас
  (включая `declinedRow`-подсветку и `replacedNotice` с «→ Перенесено на …»),
  просто отрендеренные не в основной таблице, а внутри новой секции.
- Из БД ничего не удаляется и не архивируется — меняется только то, что видно
  в основном списке по умолчанию. Строка остаётся доступной через раскрытие
  секции в любой момент.

### 2. order_response_parser/service.py

- `_order_items_context()` перестаёт включать позиции с `declined_at != null`
  в контекст, передаваемый LLM как кандидатов для матчинга.
- `missing_items` строится по тому же отфильтрованному множеству (позиции
  с `declined_at != null` не могут попасть в `missing`), а не по полному
  `order.items`, как сейчас на строке ~89.
- Обоснование: раз позиция сознательно отклонена и перенесена другому
  поставщику, её отсутствие в ответе **этого** поставщика — ожидаемое
  состояние, а не недостача. Она не должна быть ни кандидатом на matched,
  ни поводом для записи в missing.
- Категоризация matched/missing/extra для всех **не-declined** позиций не
  меняется — фильтр применяется только к позициям с `declined_at != null`,
  для остальных `_order_items_context()` и построение `missing_items`
  работают как сегодня.

### 3. Поведение при "поставщик по инерции упомянул declined-позицию"

Если после исключения declined-позиций из `_order_items_context()` поставщик
всё равно упоминает такую позицию в присланном ответе (например, по старому
контексту/памяти), извлечённая LLM строка не найдёт для себя кандидата в
(уже отфильтрованном) `order_items` и, соответственно, не получит
`matched_order_item_id` — она попадёт в категорию `extra`. Это ожидаемое и
корректное поведение, а не побочный эффект: `extra` уже сегодня не создаёт
позицию в ордере автоматически и требует явного решения пользователя на
экране разбора ответа (ADR-0033). Никакой новой логики для этого случая не
требуется — он закрывается существующей обработкой `extra`.

### 4. `overridden_via_order_item_id` (ADR-0014)

Это решение не меняет сам FK, механизм переноса или его историю. Правки
затрагивают только (а) видимость declined-позиции по умолчанию в UI и
(б) её участие в matching-контексте `order_response_parser`. Факт переноса,
ссылка на позицию-получателя и вся история остаются как есть.

## Альтернативы

- **Помечать declined-позиции в UI визуально ярче, но оставить в общем списке
  без сворачивания.** Отклонено: не решает исходную путаницу — задача именно
  в том, чтобы основной список ордера по умолчанию показывал только активные
  позиции, а не в том, чтобы улучшить их подсветку.
- **Полностью удалять declined-позиции из `order.items` в API-ответе для
  разобранных/старых ордеров.** Отклонено: ломает историю ордера и
  `overridden_via_order_item_id`-связь, которая должна оставаться видимой при
  необходимости (через сворачиваемую секцию), а не только в БД.
- **Фильтровать declined-позиции в `order_response_parser` только для
  `missing_items`, но продолжать передавать их в LLM-контекст как кандидатов
  для matched.** Отклонено: не устраняет сценарий ошибочного матчинга (LLM
  всё ещё может сопоставить с ней упомянутую поставщиком строку) — нужно
  убирать позицию из обоих мест, где она участвует как активный кандидат.

## Последствия

- Основной список ордера в OrderDetailPage.tsx по умолчанию показывает только
  активные (не-declined) позиции; declined+перенесённые доступны по запросу
  через сворачиваемую секцию «Перенесённые позиции» — БД не меняется.
- `order_response_parser` больше не предлагает LLM declined-позиции как
  кандидатов для матчинга и не включает их в `missing`. Для этого добавляется
  явный фильтр по `declined_at` в `_order_items_context()` и при построении
  `missing_items`.
- Требуется регрессионный тест, подтверждающий, что фильтр по `declined_at`
  не меняет категоризацию matched/missing/extra ни для одной не-declined
  позиции — только declined-позиции перестают попадать в matched/missing.
- Требуется тест (или явная проверка в существующих тестах разбора ответа) на
  сценарий "поставщик упомянул declined-позицию" → строка уходит в `extra`,
  а не создаёт и не обновляет никакой `OrderItem` автоматически.
- Любое дальнейшее изменение видимости declined-позиций в UI ордера или их
  участия в matching-контексте `order_response_parser` требует нового ADR —
  это решение фиксирует текущую границу (видимость по умолчанию +
  matching-контекст), а не расширяет её дальше.

## Amendment 1 (2026-10-01): разделить declined-позиции на "неперенесённые" и "перенесённые" в UI

Исходное решение (раздел 1) отправляло в свёрнутую секцию «Перенесённые
позиции» любую строку с `declined_at != null`, независимо от того, был ли
перенос уже подтверждён (`replaced_by_supplier_id != null` /
`overridden_via_order_item_id`, ADR-0014) или ещё нет.

Это было ошибкой для одного случая: позиция, которую сотрудник отклонил
(`declined_at != null`), но ещё **не перенёс** другому поставщику
(`replaced_by_supplier_id == null`), — это не архивная запись, а активная
незавершённая задача. Кнопка «Найти замену» для такой строки — следующее
действие, которое сотрудник должен предпринять почти сразу после отказа, а
не что-то, что он открывает по необходимости раз в месяц, глядя в историю.
Прятать её за раскрытием свёрнутой секции добавляет трение именно в тот
момент рабочего процесса, где скорость важнее всего.

Пересмотренное решение — **три группы** вместо двух в OrderDetailPage.tsx:

1. **`activeItems`** — `declined_at == null`. Основной список, без изменений.
2. **`unreplacedDeclines`** — `declined_at != null && replaced_by_supplier_id == null`.
   Остаётся видимой **сразу**, отдельным блоком под основным списком (не в
   свёрнутой секции) — с тем же активным CTA «Найти замену», что сегодня есть
   у любой declined-строки без переноса.
3. **`replacedItems`** — `replaced_by_supplier_id != null`. Только эта группа
   уходит в сворачиваемую секцию «Перенесённые позиции» — здесь перенос уже
   состоялся, переход завершён, это действительно архивная информация
   (`overridden_via_order_item_id` уже указывает на позицию-получателя).

Backend (`order_response_parser/service.py`) этим amendment'ом **не
затрагивается** — критерий исключения из matching-контекста остаётся
`declined_at != null` целиком, для обеих подгрупп. Обоснование раздела 2
исходного ADR не завязано на то, перенесена ли позиция другому поставщику
физически (`replaced_by_supplier_id`) — оно завязано на то, что мы сами
отклонили её у **этого** поставщика, и его ответ по ней не ожидается в любом
случае, независимо от того, нашли ли уже замену. Неперенесённая declined-
позиция так же не должна предлагаться LLM как кандидат и так же не должна
попадать в `missing`, как и уже перенесённая — здесь различия между двумя
подгруппами нет.
