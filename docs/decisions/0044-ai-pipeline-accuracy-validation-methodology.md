# ADR-0044: Методология валидации точности AI-пайплайнов (order-response + price-ingestion)

Статус: Принято

## Контекст

Два пайплайна в проекте используют LLM на неструктурированном входе —
`order_response_parser` (ADR-0018) и `price_ingestion` (ADR-0019) — оба
настроены на `gpt-5.6-sol` (`backend/app/core/config.py`,
`openai_order_response_model`/`openai_price_ingestion_model`), и оба
остаются **непроверенными на реальных документах** с момента смены модели
2026-09-23 (`docs/known-issues.md`, разделы "Точность GPT-5.6 Sol не
проверена..." и "ADR-0019 price-list ingestion — точность модели не
проверена"). Единственная проверка точности, проведённая до сих пор
(ADR-0025, линейка крепежа/дверей/коннекторов/mesh) была ручным
одноразовым экспериментом с промптом matching, не воспроизводимой
методологией — у неё нет ни скрипта, ни CSV, ни фиксированного набора
метрик, результат живёт только как текст в `known-issues.md`.

Эта ADR фиксирует методологию, а не разовую проверку — решение сделать
её ADR, а не просто dev-tool без документа (по аналогии с тем, как ADR-0018
п.6/ADR-0023 задокументировали пайплайны, которые к ним относятся): результат
будет использоваться повторно (при каждой смене модели/промпта в будущем),
и на формат CSV/метрик будут ссылаться последующие проверки — то есть это
архитектурное решение о том, как вообще устроено доверие к AI-пайплайнам
в системе, не разовый скрипт.

У двух пайплайнов принципиально разная доступность ground truth:

- **order-response** (ADR-0018) пишет результат через существующий ручной
  путь подтверждения (`OrderItem.received_quantity`/`confirmed_price`,
  ADR-0013/ADR-0039) — для уже подтверждённых `Order` в прод-БД существует
  факт "что на самом деле ответил поставщик", независимый от модели.
  Исходный документ ответа поставщика при этом **не хранится физически**:
  `Order.file_ref` — только имя файла (строка), сам файл читается в память
  и выбрасывается без сохранения (`backend/app/api/order.py`, докстринг
  `parse_order_response_endpoint`, явно со ссылкой на ADR-0018 §7; тот же
  паттерн у `PriceListImport.file_ref`,
  `backend/app/price_ingestion/service.py:53-54`). Автоматической пары
  "подтверждённый `Order` в БД + исходный документ" в системе не существует
  — её придётся строить вручную, см. "Решение" п.2.
- **price-ingestion** (ADR-0019) не имеет аналогичного независимого ground
  truth вообще: `PriceListEntry` после ревью — это уже решение человека,
  принятое *на основе* вывода модели (экран ревью), не независимый факт,
  существовавший до него. Для неподтверждённых ответов поставщиков (ещё не
  дошли до `received_quantity`/`confirmed_price`) та же проблема.

Без доступа к прод-БД напрямую (нет пароля к Postgres) Claude Code не может
сам прогнать ни один из двух скриптов этой ADR — они написаны для ручного
запуска пользователем через `docker compose exec backend ...`, тот же
механизм, каким пользователь уже выполнял прошлые прод-операции
(`docs/known-issues.md`, разбор инцидента ADR-0034).

## Решение

### 1. Разная стратегия ground truth на пайплайн, общая инфраструктура скоринга/отчёта

```
backend/app/scripts/validation/
  __init__.py
  scoring.py                    — сравнение/метрики, без сети и без БД
  csv_report.py                 — построение CSV-строк + markdown-отчёта
  validate_order_response.py    — пайплайн 1, ground truth из прод-БД
  validate_price_ingestion.py   — пайплайн 2, двойной заход sol/luna
```

`scoring.py`/`csv_report.py` не зависят ни от OpenAI, ни от `Session` —
чистые функции над уже полученными данными, поэтому покрываются лёгкими
юнит-тестами на синтетических фикстурах (`backend/tests/scripts/
validation/`), без мока сети/БД.

### 2. Order-response: явный mapping-файл, никакого угадывания по содержимому

Пользователь собирает 3-5 исторических документов ответов поставщиков
(сохранённых у себя локально/в почте — не через систему) и сам составляет
простой явный файл, например:

```json
[
  {"filename": "supplier_response_1.pdf", "order_id": "8837ffb9-..."},
  {"filename": "supplier_response_2.pdf", "order_id": "..."}
]
```

Скрипт **не пытается угадать**, какой документ относится к какому `Order`
(ни по имени файла, ни по содержимому, ни по дате) — это осознанное
решение: автоматическое сопоставление было бы эвристикой над данными, у
которых нет независимого подтверждения (ровно тот же класс риска, что уже
описан в "ИНЦИДЕНТ 2026-09-16" в `known-issues.md` про домысливание вместо
явного факта), а у пользователя эта информация уже есть точно, потому что
он сам получал эти документы.

CLI: `validate_order_response.py --mapping mapping.json --documents-dir
./docs/ --out ./report/`. Для каждой записи:

- Загружается `Order` + его `OrderItem` (исключая `declined_at IS NOT
  NULL`, тот же фильтр, что `parse_order_response` уже применяет —
  ADR-0043).
- Запись без ни одного `OrderItem` с `received_quantity IS NOT NULL OR
  confirmed_price IS NOT NULL` пропускается с предупреждением в stderr —
  не каждый подтверждённый `Order` обязательно имеет построчное
  подтверждение на каждой позиции.
- Документ прогоняется через `parse_order_response_document`
  (`backend/app/order_response_parser/client.py`) с текущим
  `settings.openai_order_response_model` — **один** проход, не
  sol/luna-пара: ground truth уже существует независимо от модели, двойной
  заход здесь не нужен (сравнение "сошлись ли модели" ничего не добавляет
  к сравнению "совпала ли модель с фактом").

**Инвариант read-only, в коде и в комментарии рядом (по аналогии с прошлыми
прод-операциями):**

```python
# READ-ONLY: этот скрипт только читает прод-БД (db.get/db.scalars через
# parse_order_response). session.commit() не вызывается нигде в этом
# файле — если его когда-либо добавят, это осознанная поломка инварианта
# данного скрипта, см. ADR-0044.
```

Вызов самой модели (OpenAI) может идти откуда угодно (прод- или
dev-контейнер) — он не завязан на то, откуда читается БД; `DATABASE_URL`/
`SessionLocal` уже настроены в контейнере, отдельный пароль к Postgres не
нужен.

### 3. Классификация соответствия — три исхода, не бинарный match rate

По прямому требованию: бинарный "нашли/не нашли" прячет самый опасный
случай — тот же класс ошибки, что уже был зафиксирован как реальный
инцидент в ADR-0039 (поставщик присылает `quantity=4` вместо `2`, строка
матчится по `matched_order_item_id` правильно, расхождение проходит молча).
В терминах этой валидации опасен не только расхождение по количеству
внутри правильного match — опасен **сам факт**, что matching может быть
неправильным (привязан к другому `OrderItem`), а результат всё равно
выглядит как обычный `matched`.

Для каждого `OrderItem` с известным ground truth (`received_quantity`/
`confirmed_price` не `NULL`) результат классифицируется в одну из трёх
категорий:

1. **correct_match** — модель привязала строку документа ровно к этому
   `OrderItem` (`matched_order_item_id == item.id`).
2. **missing** — ни одна извлечённая строка не сослалась на этот
   `OrderItem` (та же логика, что `missing_items` в `service.py`, здесь
   применённая отдельно к каждой позиции с ground truth, а не ко всему
   `Order`), **и** не нашлось численного доказательства кражи (см. ниже) —
   безопасный default.
3. **mismatched** — другая извлечённая строка документа (привязанная к
   другому `OrderItem` того же `Order`) на самом деле описывает именно эту
   позицию. Это тот самый тихий класс ошибки из ADR-0039 — засчитывается и
   показывается отдельной строкой в отчёте, не сворачивается в общий
   "match rate %".

**Алгоритм различения `missing` vs `mismatched` — явно, не подразумевается
кодом.** У нас нет построчного ground truth вида "эта строка документа =
вот этот `OrderItem`" — есть только агрегированный факт по позиции
(`received_quantity`/`confirmed_price`). Различать два случая по
содержимому/тексту строки означало бы ровно ту эвристику, которую
"Альтернативы" ниже отвергают для сопоставления документ↔`Order` — поэтому
единственный источник доказательства здесь **числовой**, не текстовый.

Для позиции `X` с ground truth, у которой нет строки с
`matched_order_item_id == X.id` (кандидат на `missing`), скрипт
дополнительно проверяет все остальные позиции `Y` того же `Order` (тоже с
ground truth), и для каждой извлечённой строки `L`, у которой
`L.matched_order_item_id == Y.id`:

- Если `L.price`/`L.quantity` **точно совпадают** с ground truth позиции
  `X` (не `Y`) **и не совпадают** с ground truth самой `Y` — это позитивное
  численное доказательство, что `L` на самом деле описывает `X`, а не `Y`
  (цена/количество `X` "утекли" в строку, которую модель привязала к `Y`).
  `X` классифицируется как `mismatched`.
- Если такой строки `L` не нашлось вообще, либо найденное совпадение
  неоднозначно (например, `price`/`quantity` `X` и `Y` случайно совпадают
  между собой, так что `L` одинаково хорошо "доказывает" обе), либо `L`
  совпадает с `Y` настолько же, насколько с `X` — результат `missing`, не
  `mismatched`. **`missing` — default при любой неопределённости;
  `mismatched` требует позитивного численного доказательства, а не
  предположения.**
- Сравнение численное и точное (`Decimal`/`int`, та же точность, что §4),
  не по тексту `raw_description`.

Это делается на уровне всего `Order` (нужен полный список позиций с ground
truth и полный список извлечённых строк одновременно), не на уровне одной
позиции в изоляции — функция `score_order_response_item` получает готовый
набор "эта позиция доказанно mismatched" извне, а вычисляет этот набор
отдельная функция уровня `Order` (`detect_mismatched_items` в
`scoring.py`).

**Уточнение по самой позиции `Y` ("похититель"):** `Y` при этом остаётся
`correct_match` для самой себя — у неё есть строка с
`matched_order_item_id == Y.id` (та самая `L`), а категория `correct_match`
— это исключительно вопрос идентичности (есть ли хоть одна строка,
указывающая на этот `OrderItem`), независимо от того, кому реально
принадлежат её числа (см. п.1 выше). Несовпадение всплывает не в
категории `Y`, а в её `price_match`/`quantity_match` (оба `False`, т.к.
числа `L` принадлежат `X`, не `Y`) — то есть для `Y` ошибка видна как
"правильно сматчено по идентичности, но с неверными значениями", для `X`
— как `mismatched`. Это два разных, оба корректных сигнала об одной и той
же реальной ошибке модели, не противоречие.

`correct_match`/`missing`/`mismatched` считаются и показываются как три
отдельных числа (доли от общего числа позиций с ground truth), не
агрегируются в один процент.

### 4. Price accuracy / quantity accuracy — только среди correct_match, точное сравнение

Среди позиций, попавших в `correct_match`:

- **price accuracy** — доля строк, где `extracted_line.price ==
  OrderItem.confirmed_price` (или `received_price`, если `confirmed_price`
  не задан — то же предпочтение, что уже имплицитно принято
  ADR-0013/ADR-0027 для "окончательной" цены) **точно**, без допуска на
  округление: `Numeric(12, 3)` в БД уже хранит точное decimal-значение, не
  float с погрешностью, сравнение через `Decimal`, не `abs(a - b) <
  epsilon`.
- **quantity accuracy** — доля строк, где `extracted_line.quantity ==
  OrderItem.received_quantity` точно (целые числа, допуска не требуется по
  построению).

Позиции из `missing`/`mismatched` не участвуют в знаменателе этих двух
метрик — для них нет корректно сопоставленной пары "извлечённое значение
↔ план", сравнивать нечего.

### 5. Price-ingestion и неподтверждённые order-response документы: двойной заход sol/luna

Для документов без независимого ground truth (прайс-листы; черновые,
ещё не подтверждённые ответы поставщиков) — прогон через обе модели,
конфиг уже позволяет переключать (`settings.openai_price_ingestion_model`/
`openai_order_response_model` — обычные поля `Settings`, читаются в момент
вызова, см. `backend/app/price_ingestion/extraction.py`/`matching.py`).
Обе модели запускаются **в одном запуске скрипта**, не в двух отдельных
прогонах: `settings.openai_price_ingestion_model` временно
переключается на `"gpt-5.6-sol"`, затем на `"gpt-5.6-luna"` вокруг каждого
вызова пайплайна и восстанавливается в исходное значение после — это
даёт один CSV на документ с обоими результатами рядом, вместо того чтобы
пользователю вручную сравнивать два отдельных прогона.

Построчное сравнение (по позиции в документе + `raw_name`/`page_number`,
аналогично тому, как `dedup.py` уже сопоставляет строки одного документа
между собой, ADR-0023):

- Совпали (одинаковый `action`/`material_id` или одинаковый
  `matched_order_item_id`, в зависимости от пайплайна) → `needs_manual_
  review = False`, отдельная ручная проверка не нужна.
- Разошлись → `needs_manual_review = True`, попадает в тот же CSV, но в
  выборку для ручной разметки (меньший объём, чем весь документ).

В отчёте — доля строк с `needs_manual_review = True` показывается
**отдельно** от итоговых цифр точности, как явная мера "сколько
автоматизация реально сэкономила" (сколько строк не потребовало ручного
внимания), а не часть самой оценки точности.

**Явная оговорка, обязательная в отчёте и в `known-issues.md` при записи
результата:** согласие между sol и luna **не является доказательством
правильности** — обе модели могут совпасть в одной и той же ошибке
(например, обе одинаково неверно интерпретируют искажённый OCR-текст, ровно
тот случай, что уже наблюдался при эксперименте с промптом matching,
ADR-0025 — "Super Screen" линейка, обе модели потенциально подвержены
одному и тому же сбою распознавания формата). Итоговая точность, когда
применяется ручная сверка только по расхождениям, **формально измеряется
только на подмножестве**: (строки с расхождением, вручную размеченные) ∪
(строки, для которых существует независимое БД-подтверждение — только в
order-response пайплайне, см. §2-4) — **не на 100% строк документа**. Эта
граница должна быть написана прямым текстом в отчёте и в записи
`known-issues.md`, не представлена как полная валидация всего документа.

### 6. Общий CSV-формат и markdown-отчёт

Один CSV на прогон (по документу или по всему набору документов — формат
общий для обоих скриптов через `csv_report.py`), колонки: `document`,
`line_identifier` (raw_name/raw_description), `category`
(`correct_match`/`missing`/`mismatched` для order-response;
`agree`/`needs_manual_review` для price-ingestion), значения из каждой
модели/источника ground truth, `manual_label` (пусто, заполняется
пользователем для строк с `needs_manual_review`).

Markdown-отчёт (`csv_report.py`) — таблица трёх метрик для
order-response (`correct_match` / `missing` / `mismatched`, отдельно
price accuracy / quantity accuracy на подмножестве `correct_match`), для
price-ingestion — доля `needs_manual_review` отдельно от точности на
размеченном подмножестве, плюс явный абзац-оговорка из §5.

После прогона — результат добавляется в `docs/known-issues.md` (новая
запись или замена существующей "точность не проверена" записи по каждому
ADR-0018/ADR-0019), не держится только в CSV на диске.

### 7. Нет UI для ручной сверки — вне объёма

Ручная разметка строк с `needs_manual_review`/без ground truth — через
прямое редактирование CSV (столбец `manual_label`), не через отдельный
экран приложения. Экран ревью для этого — отдельная задача, не входит в
объём этой ADR.

## Альтернативы

**Автоматическое сопоставление документа ↔ `Order` по содержимому/дате
вместо явного mapping-файла.** Отклонено пользователем явно — риск
совпадает с уже описанным в "ИНЦИДЕНТ 2026-09-16" классом проблемы:
эвристика поверх данных, для которых у пользователя уже есть точный факт,
не добавляет надёжности, только создаёт шанс тихой ошибки сопоставления
внутри самого инструмента валидации.

**Сохранять файл ответа поставщика при получении (новая колонка/storage),
чтобы ground truth собирался проспективно и автоматически.** Рассмотрено,
отклонено для этой задачи — требует отдельного архитектурного решения
(меняет инвариант ADR-0018 §7 "файл не персистится"), и набор 3-5 кейсов
нужен сейчас, а не после того, как накопятся новые подтверждённые заказы.
Не исключает возможность отдельной будущей ADR, если захочется
автоматизировать сбор ground truth на постоянной основе.

**Единый общий скрипт `validate.py --pipeline order-response|price-
ingestion`, вместо двух отдельных файлов.** Отклонено — ground truth
стратегия принципиально разная (БД-факт против двойного LLM-прогона),
CLI-аргументы разные (`--mapping` против `--supplier-id`), общий
диспетчер добавил бы ветвление без упрощения; общая логика уже выделена
в `scoring.py`/`csv_report.py`, повторного кода между двумя файлами
избежать и так.

**Третья, "средняя" категория между `missing` и `mismatched` — например,
"matched, но с низкой confidence".** Отклонено — `confidence`
(`ExtractedLine.confidence`) уже является отдельным полем модели,
показывается пользователю независимо; подмешивать его в саму
классификацию verification-результата смешало бы "что сказала модель о
своей уверенности" с "оказалась ли она права по факту" — две разные оси,
каждая из которых интересна отдельно (можно отдельно посчитать точность
в разрезе по confidence, не меняя сами три категории).

**Различать `missing`/`mismatched` по текстовому сходству
(`raw_description` извлечённой строки против `canonical_name`
"украденного" `OrderItem`), а не по численному совпадению цены/
количества.** Отклонено на ревью перед принятием этой ADR — текстовое
сходство — ровно та же эвристика по содержимому, которую этот документ
уже отверг для сопоставления документ↔`Order` ("Автоматическое
сопоставление..." выше): она не даёт позитивного доказательства, только
вероятностную догадку, и внесла бы в сам инструмент валидации точности
тот же класс неопределённости, который инструмент должен измерять у
проверяемых пайплайнов. Численное совпадение price/quantity — то же
структурированное сравнение, что уже используется в §4 для accuracy, не
новый механизм.

## Последствия

- Новые файлы: `backend/app/scripts/validation/__init__.py`,
  `scoring.py`, `csv_report.py`, `validate_order_response.py`,
  `validate_price_ingestion.py`.
- Новые тесты: `backend/tests/scripts/validation/test_scoring.py`,
  `test_detect_mismatched.py` (алгоритм §3 — позитивное численное
  доказательство кражи, `missing` как safe default при любой
  неоднозначности), `test_csv_report.py`, `test_validate_order_response.py`
  (включая сквозной тест обнаружения mismatch через реальную тестовую БД,
  не через вручную подставленный набор), `test_validate_price_ingestion.py`
  — логика сравнения/CSV/детекции без сети, DB-тесты против обычной
  тестовой БД (как остальной backend-сьют). Интеграционный прогон с
  реальным OpenAI/прод-БД не автоматизируется и не покрывается CI —
  выполняется пользователем вручную по мере необходимости (при смене
  модели/промпта).
- Не меняет код самих пайплайнов (`order_response_parser`,
  `price_ingestion`) — валидация работает поверх существующих публичных
  функций (`parse_order_response_document`, `match_price_list_lines`),
  не требует новых точек расширения в них.
- `docs/known-issues.md` — результат каждого прогона фиксируется там
  (замена/дополнение существующих записей "точность не проверена" для
  ADR-0018/ADR-0019), с явной оговоркой §5 там, где применим двойной
  sol/luna заход.
- Условие для будущего пересмотра: если понадобится регулярный
  (не ручной, по запросу) прогон валидации — например, перед каждым
  релизом смены модели — тогда стоит вернуться к вопросу проспективного
  сохранения документов (см. "Альтернативы" выше) как отдельной ADR, а не
  продолжать расширять ручной mapping-файл.
