# ADR-0045: Минимальное количество заказа (MOQ) на связке поставщик+материал

Статус: Принято

## Контекст

Для связки "поставщик + материал" нужно учитывать минимальное количество к
заказу (MOQ — реальные упаковки/кратность, не только крепёж). Расчёт
аллокации должен его соблюдать; интерфейс — мягко предупреждать, когда
есть расхождение. Пользователь решил:

- MOQ живёт на связке поставщик+материал, не на материале и не на
  поставщике целиком.
- В solver это жёсткое ограничение: для пары (материал, поставщик) — либо
  ноль, либо не меньше MOQ.
- Если реальная потребность меньше MOQ, это не делает пару недопустимой:
  заказываем `max(потребность, MOQ)` у неё (или у другого поставщика, если
  так дешевле с учётом излишка), излишек явно виден на экране, не скрыт.

Факты о текущем поведении (проверено чтением кода, не пересказ).

### Поле уже существует, solver его не читает

`Price.min_order_qty` (`backend/app/models/price.py:31`) — nullable int,
без CHECK — присутствует с ADR-0019 (парсер прайсов уже извлекает его,
`backend/app/price_ingestion/extraction.py:143,162`), есть в
`PriceCreate`/`PriceUpdate`/`PriceOut`
(`backend/app/api/schemas/price.py:21,41,61`) и на `PriceListEntry`
(`backend/app/models/price_list.py:51`). Но `PriceInput`
(`backend/app/allocation/types.py:41-46`) не содержит этого поля вообще —
оно физически не долетает до solver. Ни один тест в
`backend/tests/allocation/` не касается MOQ-vs-allocated-qty;
`conftest.py:231` ставит `min_order_qty=1` как нейтральный дефолт фикстуры,
не варьируя его. `docs/spec.md:168` явно держит "минимальная сумма заказа /
кратность упаковки" как открытый вопрос к бизнесу — этот ADR закрывает
только половину (MOQ), не кратность (покупку только пачками по N — см.
§Последствия, этот вопрос остаётся открытым). ADR-0036 (§Альтернативы)
сознательно отложил похожую идею (`Material.pack_quantity`) "до отдельного
ADR", отметив blast radius на ILP — это и есть тот ADR.

### Формулировка потребности в solver — one-hot на материал, количество константа

`solver.py:66-69`: `model.add(sum(candidates) == 1)` на материал — весь
объём материала уходит ровно одному выбранному поставщику. Частичные/
split-поставки одного материала между несколькими поставщиками вне MVP
(`docs/spec.md:158`). `qty = {m.material_id: m.quantity for m in
data.materials}` (`solver.py:39`) — обычный Python-словарь констант,
вычисленный один раз до построения модели, не переменная CP-SAT.

Отсюда прямое следствие для MOQ, которое первая версия этого ADR сделала
неверно: раз `qty[m_id]` — не переменная, а константа на входе в модель,
**"заказываемое количество для пары" тоже можно сделать константой**,
не переменной — достаточно предрасчитать `order_qty[(m,s)] =
max(material.quantity, price.min_order_qty or 0)` до вызова `solve_allocation`,
отдельно для каждой допустимой пары. One-hot-ограничение (`solver.py:66-69`)
не меняется вообще — оно всё ещё "ровно один `x[m][s]=1` на материал";
просто стоимостные и объёмные величины, которые умножаются на выбранный
`x[m][s]`, теперь могут отличаться по парам одного материала, когда у них
разный MOQ. Никакой новой переменной или big-M-линковки не требуется —
первая версия ADR ошибочно заключила, что раз solver one-hot, то
"излишек" структурно невозможен; это неверно: невозможен переменный
**сплит** (несколько поставщиков на один материал), но не переменная
величина внутри уже выбранной константой пары.

### Существующие переменные и ограничения, затронутые пересчётом количества

- `x[(m,s)]` — допустимая пара выбрана (`solver.py:60-64`).
- `y[s]` — поставщик задействован (`solver.py:116`, `x <= y[s]` в
  `solver.py:119-120`).
- `diff[(cat,m)]` — ADR-0028 мягкий штраф за разброс строгой категории
  (`solver.py:92-113`) — завязан только на `x`, не на количество; не
  затрагивается напрямую.
- `order_total[s] = Σ x[m][s] * price[m][s] * qty[m]` (`solver.py:122-134`)
  — **здесь `qty[m_id]` входит как множитель**; при MOQ он должен стать
  `order_qty[(m,s)]`, зависящим от пары, не только от материала —
  см. §Решение/Solver. Через `order_total` это каскадом затрагивает:
  - Ограничение 4, `order_total[s] >= min_amount * y[s]`
    (`solver.py:137-140`, `per_order_min_amount`) — должно считаться от
    суммы с учётом MOQ-излишка, иначе долларовый минимум заказа будет
    недооценён для поставщика, которому фактически отгружают больше.
  - Порог бесплатной доставки `free[s]`/`z[s]` (`solver.py:143-168`) —
    та же причина: `order_total[s]` используется в сравнении с
    `threshold`.
  - Целевая функция `model.minimize(...)` (`solver.py:185`) — минимизирует
    `price_terms`, которые сегодня `x[(m,s)] * price[(m,s)] * qty[m_id]`
    (`solver.py:174`) — должно считать реальную стоимость закупки, то есть
    с учётом MOQ-излишка, иначе solver будет недооценивать дорогих
    поставщиков с большим MOQ и может выбрать их, хотя по факту с
    излишком они дороже.
- `AllocationLineResult.quantity = qty[m_id]` (`solver.py:204`,
  `types.py:65-70`) — сегодня одно и то же число что "нужно" и "заказано".
  После этого ADR это два разных числа для пары с действующим MOQ выше
  потребности — см. §Решение/Модель данных про `AllocationLine`/
  `OrderItem`.
- **`max_order_total[s_id]` и big-M линеаризация `free[s]`/`z[s]`
  (`solver.py:124-168`) — отдельный риск, не учтённый во второй версии
  ADR.** `max_order_total[s_id] = sum(price[(m_id,s_id)] * qty[m_id] for
  m_id in material_ids if (m_id, s_id) in x)` (`solver.py:132-134`) —
  верхняя граница возможной суммы заказа у поставщика, посчитанная **от
  `qty[m_id]` (потребности)**, не от `order_qty`. Эта граница используется
  как `big_m = threshold + max_order_total[s_id]`
  (`solver.py:158`) в двух неравенствах линеаризации:
  `order_total[s] >= threshold - big_m * (1 - free_var)` и
  `order_total[s] <= threshold - epsilon_cents + big_m * free_var`
  (`solver.py:159-160`). Big-M обязан быть **строго больше** любого
  достижимого значения `order_total[s]`, иначе неравенства перестают
  корректно линеаризовать условие — без явной ошибки, модель просто
  может выдать математически допустимое, но содержательно неверное
  значение `free_var` (пропустить или ложно засчитать бесплатную
  доставку) в конкретных пограничных случаях суммы. Если `order_total[s]`
  считается от `order_qty` (с MOQ-излишком, см. §Решение/Solver), а
  `max_order_total[s_id]` — от `qty[m_id]` (без излишка), то при
  достаточно большом MOQ `order_total[s]` может **превысить** текущий
  `max_order_total[s_id]`, нарушая предположение big-M. Это главный
  технический риск этого ADR — исправление: `max_order_total[s_id]`
  должен считаться от `order_qty[(m_id, s_id)]`, той же величины, что и
  сам `order_total[s]`, не от `qty[m_id]`.

`_CENTS_PER_UNIT = 100` (`service.py:44`) используется только на границе
Decimal-доллары↔целые центы (цена, доставка, пороги); количества (`qty`,
`availability`, `min_order_qty`) — обычные целые без масштабирования,
предрасчёт `max(qty, moq)` этой границы не касается.

Активный фильтр поставщиков (ADR-0041) — `Supplier.is_active_for_allocation`,
фильтруется в `service.py:132-142`, с обязательной повторной фильтрацией
`price_inputs` после фильтрации `Supplier` (сам ADR-0041 явно требует этот
повторный шаг — автоматически он не происходит).

`split_orphaned_materials` (`preprocess.py:14-45`) сравнивает
`price.availability` с `material.quantity` (`preprocess.py:27-29`) —
**потребностью**, не тем, что реально закажут. После этого ADR availability
должно сравниваться с `order_qty[(m,s)]` (заказываемым количеством,
`>= потребности`), иначе возможна ситуация "у поставщика по данным
availability его хватит на потребность 37, но реально закажут 100 при его
MOQ=100, а в наличии только 50" — молчаливо прошло бы мимо текущей
проверки. Это не было учтено в первой версии ADR.

### Нет сегодня никакой обработки MOQ при аллокации

Подтверждено: `PriceInput` не содержит `min_order_qty`; solver его не
видит; `backend/tests/allocation/` не содержит ни одного теста на эту
тему. Существующий долларовый аналог (Ограничение 4) уже имеет
нерешённую проблему атрибуции при инфизибельности, сознательно отложенную
ADR-0003 до "первого реального случая" (`docs/known-issues.md:365-384`).
После этого ADR Ограничение 4 не может стать infeasible *из-за* MOQ само
по себе (MOQ не убирает допустимые пары — см. §Решение/Solver), так что
новый источник инфизибельности не создаётся.

## Решение

### Модель данных

Поле **не переименовывается**. `Price.min_order_qty` остаётся как есть —
имя уже используется в схеме извлечения LLM-парсера
(`extraction.py`), в API-контракте, во фронтенде, в тестах и сидах; его
переименование не даёт никакой функциональной выгоды (семантика поля не
меняется этим ADR — оно и раньше должно было означать именно минимум
заказа, просто никогда не было подключено к расчёту) и создаёт ненужный
риск ровно в тот момент, когда точность той же самой схемы экстракции
измеряется отдельной методологией (ADR-0044) — рассинхронизация имени
поля между этим ADR и методологией валидации добавила бы путаницу без
пользы. Семантика поля (что именно оно означает, как трактуется `NULL`,
как используется в расчёте) описывается в `docs/data-model.md` при этом
ADR — это корректный путь прояснить смысл существующего поля без
изменения схемы.

Новое поле **на `AllocationLine`**: `needed_quantity: int | None`.
`quantity` остаётся как сегодня — реально заказываемое количество
(`max(потребность, MOQ)`), совпадающее с тем, что идёт в стоимость и в
`OrderItem.quantity`. `needed_quantity` — снимок исходной потребности
(`MaterialInput.quantity` на момент расчёта), **NULL, когда он равен
`quantity`** (MOQ не действовал или вообще не был задан) — по тому же
принципу "NULL = нет особого случая, не 0", который уже используется для
`received_price`/`received_quantity` (ADR-0013/0039). Хранится только при
расхождении, чтобы не раздувать обычный путь лишним дублирующим числом,
совпадающим с `quantity` в подавляющем большинстве строк.

Аналогично **на `OrderItem`**: `needed_quantity: int | None`, тот же
принцип, заполняется при создании `OrderItem` из `AllocationLine`
(`order_service.py:456,663`: `needed_quantity=line.needed_quantity`, без
преобразований) — нужен на `OrderItem` отдельно от `AllocationLine`,
потому что это разные таблицы с разным временем жизни (`OrderItem`
переживает ордер, `AllocationLine` — конкретный прогон аллокации),
ровно как `received_quantity` ADR-0039 заведено на `OrderItem`, а не
только на `AllocationLine`. Используется при сравнении с ответом
поставщика (ADR-0039 `received_quantity`) — пользователь должен видеть,
что план "заказано 100" расходится с "нужно 37" по причине MOQ, не
путая это с расхождением из ответа поставщика.

Оба новых поля — не только на ORM-моделях, но и в API-контракте:
`needed_quantity: int | None = None` добавляется в `AllocationLineOut`
(`api/schemas/allocation.py:16-33`) и в `OrderItemOut`
(`api/schemas/order.py:36-83`), чтобы быть видимым фронтенду, который
читает именно эти Pydantic-схемы, а не ORM-модели напрямую. Без этого
добавления поле существовало бы в БД, но не доходило бы до UI — тот же
класс дефекта, что уже был у самого `min_order_qty` до этого ADR
(§Контекст).

Наследование `Price.min_order_qty` при создании новой версии цены:
продолжает идти через `version_price()` ровно как сегодня — caller
передаёт `None` → наследуется от закрываемой строки. **Единственное
исправление**: путь `apply.py` (`_apply_match`/`_apply_new`, PDF-импорт)
сегодня не наследует это поле вообще, обходя `version_price()`.
Принимается как исправление в рамках этого ADR (подтверждено
пользователем): если `entry.min_order_qty is None`, `_apply_match`
явно берёт `active_price.min_order_qty` закрываемой строки (симметрично
уже работающей логике `version_price`), вместо текущего безусловного
`min_order_qty=entry.min_order_qty`. `_apply_new` не меняется — там
действительно нет prior row. **Следствие, которое нужно задокументировать
в коде и в `docs/data-model.md`:** после этого исправления `Price.
min_order_qty` можно обнулить обратно в `NULL` только вручную через
`PriceForm` (явно передав пустое значение в `PUT /prices/{id}`) —
PDF-реимпорт больше не может сделать это неявно, даже если текущий прайс
поставщика перестал упоминать MOQ.

### Solver

Расчёт MOQ выполняется **до** вызова `solve_allocation`, в
`service.py`, при сборке `price_inputs` (аналогично тому, как там же
сегодня считается `_to_cents`). Для каждой `Price`-строки:

```python
order_qty = max(material.quantity, price.min_order_qty or 0)
```

Это не переменная решения — такая же константа, как сегодняшний
`qty[m_id]`, просто теперь по паре `(материал, поставщик)`, а не только по
материалу. `PriceInput` получает новое поле `order_qty: int` (не
`None` — всегда вычислено заранее, минимум равен `material.quantity`,
если MOQ не задан или ниже потребности). `solver.py` везде, где сегодня
умножает на `qty[m_id]` в контексте конкретной пары `(m, s)`, заменяет
его на `order_qty[(m_id, s_id)]`:

- `order_total[s]` (`solver.py:122-134`) — сумма берёт
  `order_qty[(m_id, s_id)]`, не `qty[m_id]`, для каждого слагаемого.
  Это автоматически протаскивает MOQ-излишек в Ограничение 4
  (`per_order_min_amount`) и в сравнение с `free_shipping_threshold` —
  никаких отдельных правок этих ограничений не требуется, они уже
  выражены через `order_total[s]`.
- **`max_order_total[s_id]` (`solver.py:132-134`) — обязательно тоже
  через `order_qty`, не через `qty[m_id]`.** Это верхняя граница
  (big-M) для линеаризации `free[s]`/`z[s]` (`solver.py:143-168`,
  подробности риска — см. §Контекст выше). Если её не поправить
  симметрично с `order_total[s]`, она станет заниженной при большом
  MOQ и может сломать линеаризацию порога бесплатной доставки без
  видимой ошибки: `max_order_total[s_id] = sum(price[(m_id,s_id)] *
  order_qty[(m_id,s_id)] for m_id in material_ids if (m_id, s_id) in
  x)`.
- `price_terms` в целевой функции (`solver.py:174`) — то же самое:
  `x[(m_id,s_id)] * price[(m_id,s_id)] * order_qty[(m_id,s_id)]`. Это и
  есть честная экономика, которую просил пользователь: поставщик с
  дешёвой ценой за штуку, но большим MOQ, теперь явно конкурирует по
  **реальной стоимости закупки** (цена × фактически заказываемое
  количество), а не по цене за штуку × потребность — дорогой по факту
  вариант перестаёт казаться оптимальным solver'у.
- Ограничение 1 (`solver.py:66-69`, one-hot `sum(candidates) == 1`) —
  **не меняется**: это ограничение про то, что материал достаётся ровно
  одному поставщику, не про величину количества. MOQ не делает пару
  недопустимой (в отличие от первой версии этого ADR) — пара остаётся в
  модели всегда, когда есть активная цена и достаточный `availability`
  **относительно `order_qty`**, не относительно исходной потребности:
  фильтр `solver.py:50-51` (`availability < qty[m]`) заменяется на
  `availability < order_qty[(m,s)]` — см. ниже про `split_orphaned_materials`.
- `AllocationLineResult` (`types.py:65-71`) получает новое поле
  `needed_quantity: int`; `quantity` становится `order_qty[(m,s)]`
  выбранной пары, `needed_quantity` — исходный `qty[m_id]`. Сервис
  (`service.py:209-219`) сохраняет оба в новую колонку
  `AllocationLine.needed_quantity`, но **только когда они отличаются**
  (иначе `NULL`, см. §Модель данных).

**`split_orphaned_materials` (`preprocess.py:14-45`)**: сравнение
`price.availability is None or price.availability >= material.quantity`
(`preprocess.py:27-29`) меняется на сравнение с `order_qty` для этой
конкретной пары, не с исходной потребностью — чтобы не допустить ровно
тот сценарий, который пропустила первая версия ADR: поставщик с MOQ=100
и availability=50 не должен считаться "достаточным" для потребности 37,
потому что реально закажут 100, а в наличии только 50. Это требует
передать в `split_orphaned_materials` не просто `PriceInput`, а уже
посчитанный `order_qty` по каждой паре (сигнатура функции меняется:
принимает словарь `order_qty` или `PriceInput` уже с новым полем —
выбор конкретной сигнатуры оставлен реализации, не архитектурное
решение).

Совместимость:
- **`requires_single_supplier`/категории (ADR-0028/0034)**: `diff[(cat,m)]`
  завязан только на `x`, не на количество — не взаимодействует.
- **Активный фильтр поставщиков (ADR-0041)**: порядок не меняется —
  `is_active_for_allocation`, затем `availability` (теперь относительно
  `order_qty`), без новых шагов.
- **Неразрешимость**: MOQ не создаёт нового случая INFEASIBLE, который
  не существовал бы и без него — единственный способ, которым MOQ влияет
  на допустимость пары, это через `availability`-проверку
  (недостаточно физического стока на реально заказываемое количество),
  а это тот же механизм, что ADR-0002 уже имеет для обычной нехватки
  стока. Случай "единственный поставщик, и MOQ больше бюджета/потребности"
  — сам MOQ никогда не делает пару недопустимой по цене/бюджету (солвер
  всегда может выбрать её, просто заплатив за `order_qty`); если результат
  "слишком дорого" — это вопрос бизнес-решения продолжать ли закупку, не
  технической инфизибельности, и явно виден через цену и
  предупреждение (§Предупреждения п.5), а не прячется под INFEASIBLE.

### Инвентаризация потребителей `quantity` — что означает "нужно" и что означает "заказываем" после этого ADR

До этого ADR `AllocationLine.quantity`/`OrderItem.quantity` означали
только "нужно" (потребность). После него — "заказываем" (может быть
выше потребности из-за MOQ), а "нужно" переносится в
`needed_quantity`. Полный список мест, где эти поля читаются
(grep по `\.quantity\b` в `backend/app`), с явным решением по каждому:

- `solver.py:39` (`qty = {m.material_id: m.quantity ...}`) — читает
  `MaterialInput.quantity`, то есть **потребность проекта**, не
  `AllocationLine`/`OrderItem`. Не меняется — это и есть вход "нужно",
  от которого считается `order_qty`.
- `service.py:109` (`MaterialInput(quantity=item.quantity, ...)`) —
  читает `ProjectItem.quantity`, потребность. Не меняется, та же причина.
- `service.py:215` (`AllocationLine(quantity=line.quantity, ...)`) —
  запись результата solver'а. После ADR `line.quantity` из
  `AllocationLineResult` — уже `order_qty` выбранной пары, то есть
  **заказываем**. Корректно без изменений — просто значение, которое
  сюда приходит, теперь другое по смыслу.
- `service.py:350` (`override_allocation_line_supplier`,
  `line.line_total = float(new_price.price) * line.quantity`) —
  **заказываем**, но сегодня `line.quantity` при override не
  пересчитывается вообще (баг относительно нового смысла поля,
  уже отмеченный в §Контекст/Прецедент override) — исправляется
  в рамках этого ADR, см. §Предупреждения п.3.
- `order_service.py:456,663` (`OrderItem(quantity=line.quantity, ...)`)
  — перенос из `AllocationLine` в `OrderItem` при создании ордера.
  **Заказываем** — корректно без изменений, `AllocationLine.quantity`
  уже содержит нужное значение к этому моменту.
- `order_service.py:737,740` (`order_expected_totals`,
  `float(item.quoted_price) * item.quantity`) — считает
  `expected_goods_total`/`declined_amount` от **заказываем** —
  корректно без изменений: `quoted_price` — цена, зафиксированная на
  момент создания ордера именно за `order_qty` штук (ADR-0007 п.1), не
  за потребность, поэтому умножение на `quantity` (заказываем) и раньше,
  и сейчас — единственно верная пара множителей.
- `preprocess.py:28,39` (`split_orphaned_materials`) — читает
  `material.quantity` (`MaterialInput`, потребность), не
  `AllocationLine`. Корректируется на сравнение с `order_qty` отдельно,
  см. §Решение/Solver — другой механизм, не про это поле.
- `api/order.py:77` (`quantity_delta = item.received_quantity -
  item.quantity`, ADR-0039) — сравнивает ответ поставщика с
  **заказываем**, не с потребностью. Корректно без изменений и после
  этого ADR: `received_quantity` — то, что подтвердил поставщик в ответ
  на наш `quoted_price`/`quantity` (уже пост-MOQ), сравнение "сошлось ли
  то, что мы заказали, с тем, что он прислал" не должно знать о MOQ
  вообще — это ортогональный вопрос (см. ADR-0039 §1, `quantity_delta` —
  свойство уже установленного соответствия, не идентичности).
- `api/order.py:87,449,462,471`, `api/project.py:159,184`,
  `api/purchase_record.py:55,109`, `purchase_records/service.py:58,85,150`,
  `order_response_parser/service.py:48`,
  `scripts/validation/scoring.py:93,134`,
  `scripts/validation/validate_order_response.py:102` — все читают
  либо `ProjectItem.quantity` (потребность, не меняется), либо
  `OrderItem.quantity`/`received_quantity` уже после создания ордера
  (**заказываем** / ответ поставщика на заказанное, не меняются по той
  же логике, что `api/order.py:77` выше), либо `PurchaseRecord.quantity`
  (фактическая закупка по факту — отдельная сущность, не затрагивается
  этим ADR вообще, её `quantity` — это факт, не планирование).

**`find_replacement_candidates`/`override_allocation_line_supplier`
(ADR-0014, "найти замену")** — отдельный случай, требующий исправления,
не только констатации. Сегодня `order_service.py:280-290` строит
`availability_risk = price.availability is not None and
price.availability < line.quantity` для **каждого кандидата-замены**,
сравнивая availability кандидата с `line.quantity` **исходной** строки.
После этого ADR `line.quantity` — заказываем у **текущего** (заменяемого)
поставщика, что не обязано совпадать с тем, что было бы заказано у
**кандидата** — у кандидата может быть свой, другой MOQ. Исправление:
для каждого кандидата считать его собственный
`candidate_order_qty = max(line.needed_quantity or line.quantity,
candidate_price.min_order_qty or 0)` (используя `needed_quantity`, если
оно задано, иначе `line.quantity` как потребность — см. ниже про
`needed_quantity is None`), и `availability_risk` сравнивать с этой
величиной, не с `line.quantity` заменяемого поставщика. При выборе
кандидата (PATCH на `line_id`, который вызывает
`override_allocation_line_supplier`) пересчёт `quantity`/`line_total`
(§Предупреждения п.3) применяется одинаково и для обычного override, и
для override из find-replacement-флоу — это уже один и тот же вызов
функции (`source_order_item_id` — не влияет на формулу пересчёта
количества, только на `overridden_via_order_item_id`, `service.py:352`).

### Излишек

Явно отражается, а не скрывается:

- `AllocationLine.needed_quantity` (NULL, если нет расхождения) против
  `AllocationLine.quantity` (всегда фактически заказываемое) — разница
  видна прямым вычитанием там, где это нужно показать.
- `OrderItem.needed_quantity` — то же, перенесённое в ордер, остаётся
  видимым после того, как `AllocationRun`, породивший его, уже неактуален.
- В итогах (`SupplierSummary`/`service.py`) `goods_total_cents` и
  `order_total[s]` уже включают излишек, потому что считаются от
  `order_qty`, не от потребности — сумма, которую видит пользователь,
  всегда соответствует тому, что реально будет куплено и оплачено.

### Предупреждения

Мягкие, не блокирующие — везде, где показана/редактируется цена или
результат аллокации:

1. **Ручная правка `Price.min_order_qty` в `PriceForm`**: без нового
   предупреждения на этом экране — тут просто задают число.
2. **Экран ревью PDF-импорта**: предупреждение "MOQ не был указан в этом
   прайсе, но у активной цены стоит N" — только когда
   `entry.min_order_qty is None` и `entry.current_active_min_order_qty is
   not None` (симметрично паттерну `current_active_price` из ADR-0040 —
   требует добавить `current_active_min_order_qty` в
   `PriceListEntryOut` тем же способом). Предупреждает про то, что теперь
   (после исправления в `apply.py`) значение не потеряется, но реальная
   причина отсутствия в текущей выгрузке стоит проверить вручную.
3. **Ручной override строки аллокации** (`override_allocation_line_supplier`,
   `service.py:305+`): сегодня при смене поставщика пересчитываются
   только `unit_price`/`line_total` (`service.py:348-350`), количество
   не трогается. После этого ADR override **обязан пересчитать и
   количество**: `line.quantity = max(line.needed_quantity or
   line.quantity, new_price.min_order_qty or 0)`, и `line_total` —
   от нового количества. Если новое количество отличается от
   `needed_quantity` (или от исходной потребности, если
   `needed_quantity` было `NULL` до этого override) — `needed_quantity`
   проставляется/обновляется соответственно. Это главное предупреждение
   из набора: именно оно показывает пользователю "вы переключили на
   этого поставщика — теперь заказываем 100 вместо 37 из-за его MOQ".
   Поле на возврате override, например `moq_adjusted: bool` (аналог
   `below_min_order`, пересчитывается с нуля в
   `_recompute_supplier_summary`) — не блокирует действие.
4. **`OrderItem` ниже MOQ** (устаревшая формулировка из первой версии ADR
   — теперь переформулирована): если `OrderItem.needed_quantity is not
   None` (то есть заказанное количество больше того, что реально
   требовалось, из-за MOQ) — предупреждение на `OrderDetailPage`, тем же
   визуальным языком, что уже использует `AvailabilityWarning` на
   `PriceComparisonPage.tsx`: "заказано {quantity} вместо {needed_quantity}
   из-за минимального количества заказа у поставщика".
5. **"Заказано больше потребности из-за MOQ" — главное предупреждение,
   не отменяется** (в первой версии ADR было ошибочно снято как
   неприменимое): появляется везде, где `needed_quantity is not None` —
   на `AllocationResultPage` (по строке) и на `OrderDetailPage` (по
   позиции ордера). **Только на внутренних экранах.** `needed_quantity`
   — внутренняя информация о нашей потребности, не предназначена для
   поставщика: в тексте ордера, который уходит поставщику
   (`buildOrderText`/`buildTargetPriceOrderText`,
   `OrderDetailPage.tsx:667-714,731+`), он видит и обязан видеть только
   итоговое количество к поставке (`item.quantity` — "заказываем"), не
   нашу внутреннюю потребность и не объяснение, почему она ниже. Это
   коммерческая/проектная информация, которая не имеет отношения к
   исполнению его заказа. Подтверждено чтением `buildOrderText`
   (`OrderDetailPage.tsx:687-699`): уже сегодня читает только
   `item.quantity`, `item.quoted_price` и `material.unit` — не трогает
   и не обязано трогать `needed_quantity`; этот ADR должен сохранить
   это свойство явным регрессионным тестом (см. §Тесты), а не просто
   полагаться на то, что никто туда это поле не добавит случайно.
6. **`PriceComparisonPage`**: рядом с кандидатом-поставщиком, у которого
   `required_quantity < candidate.min_order_qty`, — пояснение, что выбор
   этого поставщика означает закупку `max(required_quantity,
   candidate.min_order_qty)`, с показанной итоговой стоимостью на этом
   объёме (не на объёме потребности) — чтобы сравнение цен между
   кандидатами было честным на этом экране точно так же, как в solver.

### UI настроек MOQ

Без изменений расположения — поле `min_order_qty` редактируется там же,
где сегодня (`PriceForm.tsx`). Массовая правка (для крепежа, где много
позиций у одного поставщика с одинаковым MOQ) — **не входит в объём этого
ADR**. Предлагаемый, но не реализуемый здесь вариант на будущее: массовое
применение одного MOQ к набору выбранных `Price`-строк одного поставщика
через существующий `MaterialPricesPanel.tsx` (чекбоксы + одно действие),
отдельным ADR при запросе.

### Права

Без изменений: MOQ редактируется через тот же `PUT /prices/{id}`/
`POST /prices`, защищённые `require_role("admin")` на уровне роутера
(`price.py:13`).

## Альтернативы

- **MOQ на `Material`** (а не на связке). Отклонено пользователем до
  начала этого ADR: разные поставщики продают один материал разными
  упаковками — MOQ на материале не отражает реальность для части
  поставщиков.
- **MOQ на `Supplier` целиком** (минимум на весь заказ). Отклонено: это
  другая, уже существующая сущность — `per_order_min_amount`
  (Ограничение 4, долларовый минимум заказа у поставщика). Смешение
  этих понятий в одно поле было бы потерей информации.
- **Жёсткое исключение пары, если потребность ниже MOQ** (версия этого
  ADR, отклонённая ревью пользователя). Отклонено: ломает основной
  случай использования (крепёж) — часть позиций просто перестанет
  считаться вместо того, чтобы честно показать, что их придётся купить с
  избытком или найти другого поставщика. Также технически ошибочно
  выводило "излишек невозможен" из факта one-hot-ограничения, что не
  следует одно из другого (см. §Контекст).
- **Мягкий штраф в целевой функции вместо жёсткого ограничения на сам
  факт MOQ**. Не применимо в выбранной формулировке: MOQ больше не
  ограничение, которое может быть нарушено (оно всегда выполняется
  через `max(qty, moq)`), значит штрафовать нечего — "жёсткость", о
  которой просил пользователь, реализована через саму формулу количества,
  не через ограничение модели.
- **Только предупреждение, без учёта в стоимости solver**. Отклонено:
  тогда solver продолжил бы считать по цене за штуку × потребность,
  игнорируя реальную стоимость закупки — ровно та ошибка, которую
  пользователь указал как главную проблему первой версии.
- **Переименование `min_order_qty` в `moq`/`unit_moq`** (версия этого
  ADR, отклонённая ревью пользователя). Отклонено: не даёт
  функциональной выгоды, создаёт риск одновременно с измерением точности
  той же схемы экстракции в ADR-0044. Семантика описывается в
  `docs/data-model.md`, не в имени колонки.
- **Новое отдельное поле на `Price` для количества-к-заказу вместо
  вычисления на лету**. Отклонено: `order_qty`/`needed_quantity` — не
  атрибут цены, это результат сравнения цены (её MOQ) с конкретной
  потребностью конкретного материала в конкретном проекте — у одной
  `Price`-строки нет единого "количества к заказу" вне контекста проекта,
  поэтому это поле считается при аллокации, не хранится на `Price`.

  выбранного поставщика → `AllocationLine.quantity == 100`,
  `needed_quantity == 37`, `line_total` считается от 100, не от 37.
- `test_moq_cost_computed_from_order_qty_not_demand` — прямая проверка
  того, что `price_terms`/итоговая стоимость в целевой функции считаются
  от `max(qty, moq)`, не от `qty` — регрессия именно против ошибки первой
  версии ADR.
- `test_moq_expensive_but_no_moq_supplier_beats_cheap_high_moq_supplier`
  — два поставщика: дешёвый за штуку с большим MOQ (излишек делает его
  дороже по факту) и дороже за штуку без MOQ (ближе к потребности) —
  solver выбирает того, кто дешевле по итоговой сумме с учётом MOQ, даже
  если его цена за штуку выше.
- `test_moq_availability_checked_against_order_qty_not_demand` —
  availability=50, MOQ=100, потребность=37 → пара недопустима (50 < 100),
  хотя по потребности (37) availability казалось бы достаточным; материал
  уходит другому поставщику или в orphaned, если такого нет.
- `test_moq_all_suppliers_insufficient_availability_material_orphaned` —
  ни у одного поставщика материала `availability >= order_qty` → материал
  в `orphaned_materials`, прогон остаётся `OPTIMAL`/`FEASIBLE` для
  остальных материалов.
- `test_moq_surplus_included_in_per_order_min_amount` — Ограничение 4
  (`per_order_min_amount`) считается от `order_total`, включающего
  MOQ-излишек — поставщик, который без учёта излишка не набирал бы
  минимум заказа, с учётом излишка может его набрать (или наоборот —
  не тестируется отдельно, но проверяется, что сумма именно с излишком).
- `test_moq_surplus_included_in_free_shipping_threshold_and_tax` —
  порог бесплатной доставки и расчёт налога (ADR-0029) учитывают

- `test_moq_much_larger_than_demand_does_not_break_free_shipping_bigm`

## План выкатки

Без флага включения — порядок строго последовательный, потому что
изменение затрагивает данные, которые никто ранее не проверял, и
должно быть включено только после того, как эти данные подтверждены,
не "параллельно с деплоем":

1. `alembic current`/`alembic heads` — подтвердить единственный head
   перед началом (на момент написания: `c7f2a91b4e0d`).
2. **Аудит значений на проде (можно и нужно начать уже сейчас, не ждать
   остального ADR).** Read-only скрипт `backend/app/scripts/
   audit_min_order_qty.py` — рядом с остальными прод-скриптами
   (`sync_catalog_from_file.py`, `import_real_data.py`), не в
   `app/scripts/validation/` (та папка принадлежит методологии точности
   ADR-0044, это другая задача — оценка точности LLM-экстракции в
   целом, не разовый аудит одного поля перед включением). Не пишет в
   БД; выгружает распределение всех ненулевых `Price.min_order_qty` по
   поставщикам (поставщик, материал, значение, дата последнего
   обновления цены, признак вероятного происхождения из PDF-импорта по
   `source_import_id`). Запускается через `docker compose exec backend
   python -m app.scripts.audit_min_order_qty` на проде. Результат —
   пользователю на просмотр. Готовится также (но не исполняется без
   отдельного подтверждения) `backend/app/scripts/clear_min_order_qty.py`
   — обнуление конкретных строк по явному списку `Price.id`, внутри
   транзакции, с проверочным `SELECT` до и после, по умолчанию dry-run
   (пишет только с флагом `--confirm`) — он нужен, если часть значений
   окажется мусором (парсер принял за MOQ что-то другое), но его
   исполнение требует отдельного explicit go/no-go, не входит в этот
   ADR как предрешённое действие.
3. **Подтверждение или обнуление** — пользователь просматривает выгрузку
   из п.2 и решает по каждому подозрительному значению: оставить как
   реальный MOQ или обнулить через `clear_min_order_qty.py --confirm`
   (с его собственным подтверждением на запуск). Значения `> 1` не
   считаются подтверждёнными по умолчанию — пока явно не одобрены.

   **Статус на 2026-10-14: аудит выполнен (на копии прода в Docker, не
   на самом проде — read-only, см. ниже), решение по значениям
   отложено.** 21 строка с ненулевым `min_order_qty`: 12 у JM Fasteners
   (все `min_order_qty=100`) и 9 у Aluminum Distributors Int LLC, все
   из PDF-импорта (диапазон значений 250–10000). Решение по каждому
   значению (оставить как реальный MOQ или обнулить) **отложено до
   решения по кратности упаковки** (`docs/spec.md:168`, открытый вопрос
   — см. §Контекст и §Последствия) — часть audited-значений (особенно
   кратные 100/1000/4000/10000 у Aluminum Distributors) правдоподобно
   являются количеством в упаковке или порогом цены за коробку, а не
   буквальным MOQ, и смешивать эти два решения преждевременно. **Деплой
   backend-кода пп.6-11 на прод заблокирован до этого решения** — это
   не снятие блокировки п.11 ниже, а дополнительное условие к ней,
   специфичное для текущего состояния данных. Реализация кода и его
   проверка (включая тесты из §Тесты и ручной прогон сравнения "до/после"
   из пп.4-5/12) **допускаются на dev и на локальной read-only копии
   прода** — сама реализация ADR-0045 не зависит от решения по
   значениям, зависит только её включение на реальных прод-данных.
4. **Снимок "до".** `run_allocation` сам по себе не read-only — он
   создаёт новую строку `AllocationRun` и новые `AllocationLine` в БД
   при каждом вызове (`service.py:194-220`), так что "просто прогнать
   его ещё раз на проде" само является побочно-действующей операцией,
   а не нейтральным снимком. Вместо повторного запуска аллокации
   пишется отдельный read-only скрипт (рядом с `sync_catalog_from_file.py`,
   не пишет в БД), который экспортирует **уже существующий** последний
   `AllocationRun` выбранного проекта в JSON — построчно: `material_id`,
   `supplier_id`, `quantity`, `unit_price`, `line_total`, плюс
   `supplier_summaries`/`total_cents`. Снимок "до" — это выгрузка
   текущего (уже посчитанного до этого ADR) прогона, не новый расчёт.
5. **Снимок "после" и сравнение** — симметричный read-only скрипт
   экспортирует новый `AllocationRun`, появившийся после первого
   пост-деплойного вызова `run_allocation` на том же проекте (этот
   вызов — обычное использование системы пользователем, не специальная
   операция снимка; система в любом случае должна продолжать считать
   аллокации). Третий скрипт сравнивает два JSON-снимка построчно по
   `(material_id, supplier_id)` и печатает только отличия (не весь
   дифф) — именно по этому отчёту проверяется требование "любое
   расхождение объясняется конкретным MOQ" (см. п.12). **Снимок "до" и
   первый пост-деплойный прогон делаются близко по времени, без правок
   цен, проектов и BOM между ними** — иначе сравнение (п.12) не может
   отличить эффект MOQ от эффекта обычного изменения входных данных
   между двумя прогонами, и вывод "расхождение объясняется MOQ" станет
   недостоверным.
6. Миграции: `AllocationLine.needed_quantity INTEGER NULL`,
   `OrderItem.needed_quantity INTEGER NULL`. Без backfill — новые
   прогоны заполняют по необходимости, старые строки остаются `NULL`.
7. Backend: `price_inputs`/`order_qty` в `service.py`, правки `solver.py`
   (`order_total`, `max_order_total`/big-M, `price_terms`,
   `AllocationLineResult.needed_quantity`), правка
   `split_orphaned_materials` на сравнение с `order_qty`,
   `needed_quantity` в `AllocationLineOut`/`OrderItemOut` (API-схемы,
   см. §Тесты) — тесты из §Тесты (allocation/solver слой) до написания
   логики (TDD).
8. Backend: исправление наследования MOQ в `apply.py` + тесты.
9. Backend: пересчёт `quantity`/`line_total`/`needed_quantity` в
   `override_allocation_line_supplier`, включая путь
   find-replacement (candidate-specific `order_qty`, см.
   §Решение/Инвентаризация) + тесты.
10. Backend: `current_active_min_order_qty` в `PriceListEntryOut`
    (симметрично ADR-0040).
11. **Деплой backend-кода пп. 6-10 только после пп. 2-5 завершены** —
    то есть только когда данные подтверждены/обнулены и снимок "до"
    (JSON-выгрузка существующего прогона) сохранён. Это единственный
    момент, когда расчёт MOQ физически начинает влиять на прод-аллокацию
    (нет отдельного флага — сам факт деплоя этого кода включает
    механизм, поэтому все предыдущие шаги обязаны предшествовать именно
    этому деплою, не быть "параллельными" ему).
12. **Сравнение "после"** — после деплоя п.11 и первого обычного
    пост-деплойного прогона `run_allocation` на том же проекте,
    скрипт-сравнение из п.5 прогоняется на двух JSON-выгрузках. Любое
    расхождение должно объясняться конкретным MOQ конкретной пары

    указывать на `Price.min_order_qty`, который был уже в БД на момент

    объяснения — сигнал регрессии, не ожидаемый эффект этого ADR, и
    блокирует продолжение до выяснения причины (см. §Откат). **Этот

13. Frontend: предупреждения на экранах (§Предупреждения), отдельными

## Откат

Если сравнение "после" (п.12) показывает расхождение, которое **не**
объясняется конкретным `Price.min_order_qty` — это регрессия, и нужно
вернуть предыдущий образ backend (откат деплоя до версии, предшествующей
п.11). Это обычный откат деплоя, не специальная процедура:

- Новые колонки `AllocationLine.needed_quantity`/
  `OrderItem.needed_quantity` nullable и не читаются старым кодом — их
  можно **оставить** в БД при откате backend-образа (предыдущий код их
  просто не видит и не трогает) либо откатить миграцией
  (`alembic downgrade`), если решено откатиться до состояния БД целиком.
  Оба варианта безопасны именно потому, что поля nullable и ничего,
  кроме нового кода, их не читает.
- `AllocationRun`/`AllocationLine` строки, уже посчитанные новым кодом
  (с учётом MOQ) до обнаружения проблемы, **не удаляются и не
  помечаются особым образом** — это обычные записи аллокации, как любой
  другой прогон; откат касается только того, какой код исполняется
  дальше, не истории уже сделанных расчётов. Если конкретный прогон
  оказался основан на ошибочно интерпретированном MOQ (мусорное
  значение, которое проскочило аудит), это тот же случай, что и любая
  другая ошибка в цене/наличии — исправляется повторным запуском
  аллокации после исправления данных, а не специальной очисткой истории.
- Исправления в `apply.py` (наследование MOQ при PDF-импорте) и новая
  колонка `current_active_min_order_qty` в `PriceListEntryOut` не
  зависят от включения MOQ в солвер — откат солверной части (п.7) не
  обязан откатывать эти две правки, если именно они не являются
  причиной регрессии.

## Последствия

- `Price.min_order_qty` не переименовывается; его семантика
  документируется в `docs/data-model.md`.
- Новые nullable-колонки `AllocationLine.needed_quantity`,
  `OrderItem.needed_quantity` — различают "нужно" и "закажем", по
  прецеденту ADR-0039 (`received_quantity`).
- Solver считает стоимость, `order_total`, порог бесплатной доставки и
  сравнение `availability` от `max(qty, moq)`, не от исходной
  потребности — это меняет фактический результат оптимизации (не только
  добавляет новое ограничение) там, где у материала есть поставщик с
  MOQ. Требует полного прогона `backend/tests/allocation/` на регрессию,
  не только новых тестов.
- `override_allocation_line_supplier` перестаёт оставлять `quantity`
  неизменным при смене поставщика — поведение, которое раньше было верно
  всегда (потребность не завязана на выбранного поставщика), становится
  верным только когда у нового поставщика нет MOQ выше потребности. Это
  затрагивает оба пути, которые вызывают эту функцию — обычный ручной
  override и find-replacement (ADR-0014) — `availability_risk` в
  `find_replacement_candidates` также пересчитывается от MOQ каждого
  конкретного кандидата, не от количества заменяемой строки.
- `max_order_total[s_id]` (big-M граница линеаризации бесплатной
  доставки) обязана считаться от той же величины (`order_qty`), что и
  `order_total[s]` — иначе большой MOQ может молча сломать эту
  линеаризацию без видимой ошибки. Это самый высокий технический риск
  реализации этого ADR, явно протестированный отдельным тестом
  (`test_moq_much_larger_than_demand_does_not_break_free_shipping_bigm`).
- MOQ не создаёт новых случаев `INFEASIBLE` — максимум переводит материал
  в `orphaned_materials` тем же механизмом, что уже используется для
  обычной нехватки `availability`.
- `needed_quantity` — строго внутреннее поле: видно на
  `AllocationResultPage`/`OrderDetailPage`, никогда не попадает в
  исходящий поставщику текст ордера (`buildOrderText`/
  `buildTargetPriceOrderText`).
- Единица измерения `Price.min_order_qty` принимается равной единице
  измерения `Price`/`ProjectItem.quantity` для той же пары (материал,
  поставщик) — это допущение, не проверяемое кодом (нет отдельного
  поля "единица MOQ"), фиксируется явно в `docs/data-model.md`. Если
  окажется, что парсер иногда извлекает MOQ в другой единице (например,
  "мин. заказ: 1 паллета" при единице материала "шт."), это неверно
  интерпретируется как число штук — отдельный риск, не решаемый этим
  ADR, частично покрываемый обязательным аудитом перед включением
  (§План выкатки п.2) и ручным подтверждением подозрительных значений.
- Данные, извлечённые парсером прайсов с ADR-0019, но до сих пор никогда
  не влиявшие на расчёт, начинают влиять на прод — обязательная ручная
  проверка распределения значений перед включением (§План выкатки п.2).
- Кратность упаковки (отдельно от минимума) остаётся открытым вопросом
  `docs/spec.md:168` — не закрывается этим ADR.
- Исправление дефекта наследования MOQ в `apply.py` — после него
  `Price.min_order_qty` можно обнулить только вручную через `PriceForm`,
  не через повторный импорт прайса без указанного MOQ в строке.
