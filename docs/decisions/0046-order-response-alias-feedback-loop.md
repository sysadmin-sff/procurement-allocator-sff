# ADR-0046: Alias-память и ручная связь "Лишнее"/"Отсутствует" для order-response matching

Статус: Принято

## Контекст

Реальный прогон ADR-0044 (2026-10-19, `docs/known-issues.md`, запись к
"ADR-0018 — точность GPT-5.6 Sol не проверена", уже сохранён) на 3
документах/52 позициях дал `correct_match` 80.8% / `missing` 19.2% /
`mismatched` 0%.

Повод завести эту ADR — наблюдение сотрудника на экране ревью одного
заказа AMS того же проекта: в "Отсутствует в ответе" — `Rain Carrying
Accessories (3 x 4 A Elbow) (White/Bronze)`, в "Лишнее" — `S-25-00-00070
3X4 A ELBOW BRONZE`, одна и та же физическая позиция. Модель прочитала
документ верно (SKU и название совпадают с текстом PDF один в один) — она
не смогла **сопоставить** раздельно написанное название поставщика с
канонической формулировкой материала в заказе.

**Важная оговорка.** Этот конкретный заказ AMS — не `70017a8a-...` из
прогона ADR-0044 (тот заказ не содержал этой пары вообще; см. разбивку
причин `missing` ниже). Пример-мотиватор служит качественной
иллюстрацией класса ошибки, но количественная проверка (разбивка 10
`missing` прогона 2026-10-19) показала: **из 10 исходных `missing` — 0
относится к этому классу**. Все 10 — позиции, которых физически нет в
соответствующем документе ответа. **Эта классификация получена сверкой
текста PDF ассистентом в рамках подготовки ADR, не подтверждена
пользователем отдельно — до подтверждения пользователем это утверждение
считается предварительным,** не окончательным фактом (в отличие от
схемы БД/кода, подтверждённых прямым запросом к реальной БД и grep):

| OrderItem (canonical_name) | Документ | Есть ли в PDF текст про этот товар | Класс |
|---|---|---|---|
| `36'' x 80" Door Blank with 8" Kick Plate` | FS | Нет | отсутствует в документе |
| `Adjustable Z-Bar x 17'` | FS | Нет | отсутствует в документе |
| `Hinges (White/Bronze)` | FS | Нет | отсутствует в документе |
| `Eliminator Door Hardware Kit (White/Bronze)` | FS | Нет | отсутствует в документе |
| `Bugsweep 36"` | FS | Нет | отсутствует в документе |
| `Solar Seal Bronze` | FS | Нет | отсутствует в документе |
| `Touch Up Paint (White/Bronze)` | FS | Нет | отсутствует в документе |
| `2" x 8" SMB x 30' (White/Bronze)` | AMS | Нет | отсутствует в документе |
| `14 x 2" Bronze/White Stainless steel` | AMS | Нет | отсутствует в документе |
| `14 x 3" Bronze/White Stainless steel` | AMS | Нет | отсутствует в документе |

Этот класс ошибки (SKU/сокращение vs каноническое имя) реален и будет
наблюдаться на других заказах/поставщиках — но прогон 2026-10-19 не даёт
числовой оценки его частоты, и нет оснований ожидать, что он объясняет
заметную долю текущего `missing_rate`. Решение ниже выбрано исходя из
минимального объёма изменений и минимального влияния на БД, а не из
предположения о большом измеримом эффекте.

**Побочно обнаруженный факт — разброс между повторными прогонами.**
Повторный прогон тех же 3 документов в тот же день (другой вызов
`gpt-5.6-sol`, без изменений кода) дал другое количество `missing` для
одного документа (AD: 0 → 2 дополнительных) при сохранении всех 10
исходных `missing` как есть. OpenAI-вызов недетерминирован между
прогонами одного документа — это нужно учитывать при любой будущей оценке
эффекта (раздел "Метрика успеха" ниже).

### Асимметрия с price-ingestion и схема `SupplierMaterialAlias`

У пайплайна price-list ingestion (ADR-0019) есть рабочий механизм именно
для этого класса задачи: `SupplierMaterialAlias` читается перед
LLM-вызовом как exact-match short-circuit (`find_known_alias`,
`backend/app/price_ingestion/candidates.py:27-37`, текст приведён
буквально ниже) и пишется при каждом подтверждении сотрудником строки
ревью (`_upsert_alias`, `backend/app/price_ingestion/apply.py:36-51`). У
order-response пайплайна (ADR-0018) этого нет: grep по
`backend/app/order_response_parser/` на `SupplierMaterialAlias` — ноль
совпадений.

```python
# backend/app/price_ingestion/candidates.py:27-37
def find_known_alias(
    db: Session, supplier_id: uuid.UUID, raw_name: str
) -> SupplierMaterialAlias | None:
    """Exact-match short-circuit before any embedding/LLM call — see
    ADR-0019 §2. Scoped to (supplier_id, supplier_raw_name)."""
    return db.scalar(
        select(SupplierMaterialAlias).where(
            SupplierMaterialAlias.supplier_id == supplier_id,
            SupplierMaterialAlias.supplier_raw_name == raw_name,
        )
    )
```

Никакой нормализации текста нет — точное `==` на сырой `raw_name`,
регистрозависимо, чувствительно к пробелам. Существующее поведение, не
вводится этой ADR.

**Схема `SupplierMaterialAlias` сегодня** (`backend/app/models/
supplier_material_alias.py:15-28`, подтверждено `\d
supplier_material_aliases` на реальной БД):

```
id                 uuid         PK
supplier_id        uuid         NOT NULL, FK suppliers.id ON DELETE CASCADE
material_id        uuid         NOT NULL, FK materials.id ON DELETE CASCADE
supplier_sku       varchar(100) nullable
supplier_raw_name  varchar(255) NOT NULL
```

Индексы: PK на `id` и обычный (не уникальный) btree на
`(supplier_id, material_id)`. Нет уникального ограничения ни на
`(supplier_id, supplier_raw_name)`, ни на `(supplier_id, material_id)` —
таблица физически уже сегодня допускает, что один и тот же
`(supplier_id, raw_name)` указывает на разные `material_id`. Нет полей
происхождения записи.

**Схема извлечённой строки модели** (`ExtractedLine`,
`backend/app/order_response_parser/client.py:22-28`, буквально):

```python
class ExtractedLine(BaseModel):
    raw_description: str
    matched_order_item_id: uuid.UUID | None
    price: float
    quantity: int | None
    confidence: str
    reasoning: str
```

Отдельного поля `sku` нет — SKU, если есть, находится внутри
`raw_description` целиком (пример: `"S-25-00-00070 3X4 A ELBOW BRONZE 3X4
A ELBOW BRONZE"` — текст задвоен моделью, причина задвоения не
исследована в этой ADR).

**Роли.** Весь роутер `order.py` объявлен как
`APIRouter(dependencies=[Depends(get_current_user)])`
(`backend/app/api/order.py:63`) — единая зависимость на уровне роутера,
без `require_role` на отдельных эндпоинтах PATCH/parse-response внутри
него. `User.role` — `'admin' | 'employee'`
(`backend/app/models/user.py:25`, докстринг буквально). То есть **и
`admin`, и `employee` уже сегодня могут читать parse-response, менять
`received_price`/`confirmed_price`/`declined_at` через `PATCH
.../items/{item_id}` и создавать `PurchaseRecord`** — вся секция ответа
заказа не ограничена ролью `admin`. Это другой прецедент, чем
`/prices`/`/suppliers` (`require_role("admin")` на уровне роутера) —
первая версия этой ADR ошибочно скопировала права `/prices` без проверки
факта.

## Решение

Минимальный объём: пост-матч в коде (без изменения промпта, без
промпт-подсказки, без автоматического извлечения SKU), один новый
эндпоинт записи, одна правка price-ingestion (фильтр по `origin`), одна
миграция с тремя nullable/default-колонками без новых индексов.

### 1. Пост-матч в `service.py`

Выполняется **после** `parse_order_response_document`, **до** разбиения
на `matched_lines`/`missing_items`/`extra_lines` в `parse_order_response`
(`backend/app/order_response_parser/service.py:56-101`).

**Алгоритм** (для каждой строки `line` из `extracted`, где
`line.matched_order_item_id is None`):

1. Если у `line` уже есть `matched_order_item_id` — пост-матч эту строку
   не трогает вообще (условие `is None` выше уже это гарантирует, но
   явно: **никогда не перезаписывается непустой match модели**, ни при
   каком условии ниже).
2. Загружается весь набор `SupplierMaterialAlias` для
   `order.supplier_id`, `origin='order_response'` — **одним запросом**
   на весь вызов `parse_order_response` (не на каждую строку), без новых
   индексов: фильтрация по `supplier_id` уже покрыта существующим
   `ix_supplier_material_aliases_supplier_material`
   (`(supplier_id, material_id)` — supplier_id ведущий столбец составного
   индекса, used as a prefix). Дальнейшее сравнение текста — в Python, не
   в SQL.
3. Сравнение `line.raw_description` с `alias.supplier_raw_name` **без
   учёта регистра, с схлопыванием пробелов**:
   `" ".join(line.raw_description.split()).casefold() == " ".join(
   alias.supplier_raw_name.split()).casefold()`. Это единственная
   нормализация, которую вводит эта ADR — применяется только в Python на
   уже загруженном в память наборе алиасов этого поставщика, не меняет
   `find_known_alias`/SQL-сравнение price-ingestion.
4. Если совпадение найдено — берётся `alias.material_id`. Среди
   не-declined (`declined_at IS NULL`) `OrderItem` этого заказа ищутся
   все с `material_id == alias.material_id`, **исключая**:
   - все `order_item_id`, уже присутствующие как `matched_order_item_id`
     у **любой** строки `extracted` этого вызова (не только у самой
     строки `line`) — то есть позиция, которую модель сопоставила
     **другой** строке того же документа, не считается кандидатом для
     пост-матча этой строки, даже если сама `line` её не получила;
   - все `order_item_id`, уже присвоенные пост-матчем **более ранним**
     строкам в рамках этого же прохода (накопленное множество, растущее
     по мере обработки `extra`-строк одна за другой) — чтобы два разных
     extra-текста с одним и тем же alias не получили один и тот же
     `OrderItem` дважды.
   Оба исключения вместе гарантируют: к моменту проверки кандидатов для
   строки `line`, "уже занятые" `order_item_id` — это объединение (a)
   всех `matched_order_item_id` из исходного ответа модели и (b) всех
   `order_item_id`, присвоенных пост-матчем ранее в этом же проходе.
5. **Ровно одна** такая позиция → `line.matched_order_item_id`
   присваивается её `id`. **Ноль или больше одной** → не угадывается,
   `line` остаётся как есть (`matched_order_item_id is None`,
   по-прежнему попадёт в `extra_lines`).
6. При присвоении: `line.confidence` **не меняется**, остаётся тем
   значением, которое вернула модель для этой строки — берётся как есть,
   значение может быть любым из `"high"`/`"medium"`/`"low"` (модель
   присваивает `confidence` по собственной оценке, не только по факту
   "сопоставлено/не сопоставлено" — см. промпт `client.py:84-86`:
   confidence запрашивается даже для `matched_order_item_id = null`
   строк, "насколько ты уверен, что это действительно новая позиция").
   `line.reasoning` дополняется текстом (не заменяется, не перезаписывает
   исходное объяснение модели полностью): `f"[сопоставлено по
   сохранённому alias поставщика] {line.reasoning}"`. Это и есть пометка
   источника — других технических полей не вводится (`ExtractedLine` не
   расширяется новым структурным полем в этой ADR, минимальный объём).

**Почему `confidence` не меняется — буквально, где он читается сегодня.**
Для order-response (не путать с отдельным порогами `>90%`/`70–90%`/`<70%`
из `docs/ui-reference.md:8-12,650-692` — та секция про другой экран,
price-list review, не про этот эндпоинт) единственное использование —
`frontend/src/routes/OrderDetailPage.tsx:40`:
```ts
const LOW_CONFIDENCE_LEVELS = new Set(['low', 'medium']);
```
и строка 1545:
```ts
const lowConfidence = LOW_CONFIDENCE_LEVELS.has(line.confidence);
```
— используется только для визуальной подсветки `styles.
parseLowConfidenceRow` (строка 1554) и текста "⚠ низкая уверенность
распознавания" под названием позиции (`docs/ui-reference.md:379-383`).
**Не используется** нигде для фильтрации массового применения: кнопка
"Применить все совпадения" (`docs/ui-reference.md:384-391`) применяет все
строки с включённым чекбоксом независимо от `confidence` — чекбокс
включён по умолчанию для всех строк блока "Совпало", порог confidence не
участвует в этом решении нигде в коде order-response (подтверждено
отсутствием любого фильтра по `confidence` в `OrderDetailPage.tsx` вокруг
кода "Применить все совпадения"). То есть единственный эффект смены
`confidence` на `"high"` был бы — **скрыть** предупреждающую подсветку от
сотрудника, не изменить, что происходит при нажатии кнопки.

Решение — **не менять `confidence`**: пост-матч даёт гарантию другого
рода (точное текстовое совпадение + единственный кандидат — детерминизм
кода), не "высокую уверенность LLM в этом конкретном вызове", и выдавать
одно за другое было бы нечестной подменой перед сотрудником. Оставляя
`confidence` как есть, пост-матчённая строка **может** сохранить
подсветку "низкая уверенность" (если модель вернула `"low"`/`"medium"`
для соответствующей несматченной строки — заранее неизвестно, какое
значение вернёт конкретный вызов) — это нормально и ожидаемо:
подсветка говорит "в этом конкретном распознавании могла быть ошибка",
что остаётся верным даже после того, как код нашёл для неё совпадение по
памяти; текстовая пометка в `reasoning` — отдельный, самостоятельный
сигнал "как это было сопоставлено", не заменяющий и не требующий
изменения `confidence`.

**Downstream на уровне кода `service.py` — идентичен пути модели, но
API-схема получает новый флаг, и фронтенд обязан вести себя иначе для
строк пост-матча.** После присвоения `matched_order_item_id` в пункте 5,
строка попадает в `matched_lines` через тот же существующий фильтр
`backend/app/order_response_parser/service.py:93` (`[line for line in
extracted if line.matched_order_item_id is not None]`) — на уровне
`ExtractedLine`/`service.py` код не различает, откуда взялось
`matched_order_item_id`, присвоение происходит **до** этого фильтра на
том же объекте. Но `parse_order_response` (сигнатура строк 56-62) обязана
отдельно отслеживать, какие `order_item_id` присвоены пост-матчем (то же
накопленное множество, что используется в пункте 4 алгоритма для
исключения уже занятых позиций, — переиспользуется как источник этого
флага, не вычисляется второй раз) и передать это множество до точки,
где строится ответ API.

**`MatchedLineOut.matched_by_alias: bool`** — новое поле в схеме ответа
(`backend/app/api/schemas/order_response_parser.py`, рядом с
существующими `order_item_id`/`raw_description`/`price`/`quantity`/
`confidence`/`reasoning`). **Только в API-схеме** — `ExtractedLine`
(`client.py:22-28`) не меняется, колонка в БД не добавляется (в этом
объёме ADR не персистит сам факт разового пост-матча, только логирует
агрегат, см. "Метрика успеха"). `True` для строк, чей
`matched_order_item_id` присвоен пунктом 5 алгоритма пост-матча; `False`
для строк, у которых `matched_order_item_id` пришёл от модели в исходном
ответе `parse_order_response_document`.

**Применение цены/количества по-прежнему не автоматизируется** — пост-
матч меняет только `matched_order_item_id`/`reasoning` на `ExtractedLine`
(не `confidence`, см. обоснование выше); `received_price`/
`confirmed_price` на `OrderItem` остаются `NULL`, пока сотрудник сам не
подтвердит.

**Фронтенд — обязательное отличие в поведении, не только подписи.**
Причина: чекбокс массового применения в блоке "Совпало" сегодня включён
по умолчанию для всех строк независимо от `confidence`
(`frontend/src/routes/OrderDetailPage.tsx` — подтверждено выше, у
кнопки "Применить все совпадения" нет фильтра по `confidence` или любому
другому полю строки). Если строку, сматченную по alias, подать на экран
неотличимо от строки, сматченной моделью, ошибочный alias (например,
созданный по кнопке "Связать" с опечаткой или неверно подтверждённой
парой) автоматически получил бы цену **чужого** материала одним нажатием
"Применить все совпадения" — тем же кликом, каким сотрудник применяет
десятки нормальных совпадений, не глядя на каждую строку отдельно.
Поэтому: строки с `matched_by_alias: true` в блоке "Совпало" —
- **чекбокс массового применения по умолчанию НЕ отмечен** (в отличие от
  всех остальных строк блока, где чекбокс включён по умолчанию) —
  сотрудник должен явно отметить её, чтобы она попала в следующее
  нажатие "Применить все совпадения"; как и для остальных строк, он может
  это сделать, после явного решения, не автоматически;
- подписаны текстом **"по сохранённой связи"** рядом с названием позиции
  (аналогично тому, как сегодня `confidence` `"low"`/`"medium"` подписаны
  "⚠ низкая уверенность распознавания", `docs/ui-reference.md:379-383`,
  но это отдельная, не взаимоисключающая подпись — строка может иметь обе
  одновременно, если `confidence` от модели также низкий).

### 2. Эндпоинт `POST /orders/{order_id}/response-aliases` + кнопка "Связать"

**Бэкенд и фронтенд — отдельными сессиями** (явно разносится на две
отдельные задачи реализации после принятия этой ADR, не один PR).

**Эндпоинт.** Тело `{supplier_raw_name: str, supplier_sku: str | null,
material_id: uuid}`. Доступ — `Depends(get_current_user)`, тот же уровень,
что остальной `order.py` (см. "Роли" выше — не `require_role("admin")`,
это было ошибкой первой версии).

Сервер:
- 404, если `order_id` не найден; 404, если `material_id` не найден;
- конфликт: `(supplier_id, supplier_raw_name, origin='order_response')`
  уже существует с другим `material_id` → 409, тело включает существующую
  запись (`material_id`, `canonical_name`, `created_at`) и требует
  явного `force: true` для перезаписи (обновление `material_id` на
  существующей строке, не вставка дубля);
- без конфликта: точная тройка `(supplier_id, material_id,
  supplier_raw_name, origin='order_response')` уже существует — no-op,
  200; иначе — создаёт новую строку с `origin='order_response'`,
  `created_by_user_id=current_user.id`, `created_at=now()`.
- Сравнение `supplier_raw_name` для определения конфликта/идемпотентности
  — точное (`==`, как `_upsert_alias` сегодня), не нормализованное: это
  осознанная асимметрия с пост-матчем (п.1), который сравнивает с
  нормализацией при **чтении**. Запись остаётся точной, чтобы не
  потребовалось менять `_upsert_alias`/schema уникальности в
  price-ingestion заодно — минимальный объём.

**Кнопка "Связать".** В блоке "Лишнее" — кнопка рядом с существующей
"Добавить". Предложение пары показывается только когда **ровно один**
кандидат из блока "Отсутствует в ответе" (только с `material_id is not
None`) даёт точное числовое совпадение (`Decimal`, без допуска) по цене,
и дополнительно по количеству если `quantity` extra-строки не `null`.
Ноль или больше одного — предложения нет, выбор вручную. Рядом с
предложением — текст основания ("совпадает цена: $62.10"). Под кнопкой —
текст: **"Связь сохранится для следующих документов этого поставщика"**
— явно сообщает сотруднику, что это не разовое действие на этом
документе. Никакого автоподтверждения.

### 3. Миграция

```sql
-- upgrade
ALTER TABLE supplier_material_aliases
  ADD COLUMN origin varchar(20) NOT NULL DEFAULT 'price_import',
  ADD COLUMN created_by_user_id uuid NULL REFERENCES users(id) ON DELETE SET NULL,
  ADD COLUMN created_at timestamptz NULL;

-- downgrade
ALTER TABLE supplier_material_aliases
  DROP COLUMN origin,
  DROP COLUMN created_by_user_id,
  DROP COLUMN created_at;
```

Три колонки, как решено: `origin` NOT NULL с константным дефолтом
(литерал `'price_import'`, не функция/подзапрос); `created_by_user_id`
nullable, `ON DELETE SET NULL`; `created_at` **nullable** — у всех
существующих строк остаётся `NULL` (не backfill на `now()`), потому что
их фактическое время создания не записано нигде и подставлять дату
миграции вместо него было бы придуманным фактом, не настоящим — тот же
принцип, что CLAUDE.md/эта кодовая база уже применяет к другим полям
("NULL = не значит 0/придуманное значение", см. докстринги `OrderItem.
received_quantity`/`confirmed_price` в `models/order.py`).

**Перепишет ли `ALTER TABLE` таблицу — проверяется прямым сравнением
`relfilenode` до и после, не косвенно через `EXPLAIN`.** С Postgres 11
`ADD COLUMN` с **константным** `DEFAULT` (ровно наш случай —
`'price_import'` — литерал, не volatile-выражение) не требует полного
переписывания таблицы: значение по умолчанию хранится в системном
каталоге (`pg_attribute.atthasmissing`/`attmissingval`) и материализуется
лениво при чтении старых строк. Переписывание таблицы физически меняет её
файл на диске — Postgres выделяет новый `relfilenode` для новой версии
файла; если `relfilenode` не изменился, переписывания не было —
это прямая проверка факта, не косвенный вывод из плана выполнения
запроса (`EXPLAIN` мог не показать разницу даже при переписывании,
если новый файл физически компактнее).

**Шаг 0 — обязательная проверка версии PostgreSQL на проде перед
применением.** Поведение lazy-default для `ADD COLUMN` гарантировано
только с версии 11 (на локальной копии подтверждено `PostgreSQL 17.11`,
`server_version_num=170011` — выше требуемого минимума, но прод может
отличаться по версии от локальной копии, это не проверено в рамках этой
ADR):
```sql
SELECT current_setting('server_version_num')::int >= 110000 AS supports_lazy_default;
```
Если на проде версия ниже 11 — `ADD COLUMN ... DEFAULT 'price_import'`
перепишет таблицу целиком под блокировкой `ACCESS EXCLUSIVE` на время
всего сканирования, не только метаданных; в этом случае перед применением
миграции на проде нужен отдельный план (например, добавление колонки без
`DEFAULT`, затем `UPDATE` батчами, затем `SET DEFAULT` — вне объёма этой
ADR, применяется только если шаг 0 покажет версию < 11).

**Команда проверки на локальной копии прод-БД** (не на проде):
```sql
SELECT relfilenode AS before_relfilenode
FROM pg_class WHERE relname = 'supplier_material_aliases';
-- запомнить before_relfilenode, затем:
BEGIN;
ALTER TABLE supplier_material_aliases
  ADD COLUMN origin varchar(20) NOT NULL DEFAULT 'price_import',
  ADD COLUMN created_by_user_id uuid NULL REFERENCES users(id) ON DELETE SET NULL,
  ADD COLUMN created_at timestamptz NULL;
SELECT relfilenode AS after_relfilenode
FROM pg_class WHERE relname = 'supplier_material_aliases';
ROLLBACK;
```
`before_relfilenode == after_relfilenode` (сравнить два полученных
числа вручную — `ROLLBACK` отменяет сам `ALTER`, но `relfilenode`,
считанный **внутри** транзакции до отката, уже показывает, выделялся ли
новый файл в момент выполнения `ALTER`) — переписывания не было. Если
числа отличаются — таблица была переписана, несмотря на ожидание,
и перед выкаткой на прод нужно отдельно оценить время операции на
реальном объёме данных прода (в рамках этой ADR объём прод-таблицы не
измерялся).

### 4. Правка price-ingestion — единственная

`find_known_alias` (`backend/app/price_ingestion/candidates.py:27-37`)
добавляет третье условие в `where`: `SupplierMaterialAlias.origin ==
"price_import"`. `_upsert_alias` (`backend/app/price_ingestion/
apply.py:36-51`) при создании новой строки передаёт
`origin="price_import"` явно (не полагается на DEFAULT колонки — тот же
принцип, что ADR изначально требовала, но здесь выражен проще: без `DROP
DEFAULT` отдельным шагом, поскольку в этом минимальном объёме не
вводится третий source, которому дефолт мог бы помешать — если он
появится в будущем, тогда и рассматривается `DROP DEFAULT`).

Это единственное изменение в `price_ingestion/`. Ничего больше в этом
модуле не меняется.

### 5. Права — буквально

- `POST /orders/{order_id}/response-aliases` — `Depends(get_current_user)`,
  без `require_role`. Обоснование — см. "Роли" в разделе "Контекст":
  вся секция ответа заказа (`order.py`, весь роутер) уже сегодня доступна
  и `admin`, и `employee`; создание alias из этой же секции не вводит
  более узкое ограничение, чем остальные действия на этом экране.
- `DELETE /suppliers/{supplier_id}/aliases/{alias_id}` — `Depends(
  require_role("admin"))`. Обоснование — удаление alias влияет на
  будущие документы **любого** сотрудника и (из-за общей таблицы,
  несмотря на изоляцию `origin`) требует более широкого обзора
  последствий, чем создание одной связи из одного документа; тот же
  уровень, что `/suppliers`/`/prices` сегодня для операций над общими
  справочниками.
- 404, если `alias_id` не существует **или** принадлежит другому
  `supplier_id`, чем указан в пути — не 403/400, тот же принцип, что
  "Order not found"/"Order item not found" по всему `order.py` (не
  раскрывать существование чужого ресурса).

### 6. Восстановление после ошибочной связи

Два штатных пути и один аварийный:

1. **Перезапись** — повторный вызов `POST /orders/{order_id}/response-
   aliases` с тем же `supplier_raw_name` и правильным `material_id` даёт
   409 (конфликт с существующей записью), сотрудник подтверждает через
   `force: true` — обновляет `material_id` на существующей строке (п.2
   выше). Исправляет направление связи без удаления истории.
2. **Удаление** — `DELETE /suppliers/{supplier_id}/aliases/{alias_id}`,
   доступно только `admin` (см. "Права" выше). Полностью убирает
   ошибочную связь; следующий документ этого поставщика снова пройдёт
   без пост-матча на этот текст, как до создания alias.
3. **Аварийный путь — прямой SQL**, когда нужно массово просмотреть или
   удалить несколько ошибочных записей сразу (не через API по одной) —
   например, если один и тот же неверный `material_id` был по ошибке
   привязан несколько раз разными сотрудниками до того, как ошибка
   замечена. Рецепт документируется в `docs/known-issues.md` (не
   исполняется этой ADR, не автоматизируется):
   ```sql
   -- Просмотр всех order-response-алиасов конкретного пользователя
   -- (например, при разборе жалобы "я создал что-то не то")
   SELECT id, supplier_id, material_id, supplier_sku, supplier_raw_name,
          created_at
   FROM supplier_material_aliases
   WHERE origin = 'order_response' AND created_by_user_id = :user_id
   ORDER BY created_at DESC NULLS LAST;

   -- Удаление одной конкретной ошибочной записи по id — в транзакции,
   -- со сверкой перед коммитом (origin в условии WHERE — не полагаться
   -- на то, что id уже точно принадлежит order-response-записи):
   BEGIN;
   DELETE FROM supplier_material_aliases
   WHERE id = :alias_id AND origin = 'order_response'
   RETURNING id, supplier_id, supplier_raw_name;
   -- Сверить напечатанную строку (id/supplier_id/supplier_raw_name)
   -- с тем, что ожидалось удалить. Совпало -> COMMIT; не совпало или
   -- ничего не вернулось (0 строк — значит id не было, или он
   -- принадлежит другому origin) -> ROLLBACK.
   COMMIT; -- или ROLLBACK;

   -- Удаление ВСЕХ order-response-алиасов конкретного поставщика —
   -- крайняя мера, используется только когда точечные id неизвестны
   -- и восстановление по одной записи нецелесообразно. Сначала узнать
   -- объём, затем удалить в той же транзакции со сверкой числа:
   SELECT count(*) FROM supplier_material_aliases
   WHERE origin = 'order_response' AND supplier_id = :supplier_id;
   -- Записать полученное число, затем:
   BEGIN;
   DELETE FROM supplier_material_aliases
   WHERE origin = 'order_response' AND supplier_id = :supplier_id
   RETURNING id, supplier_raw_name;
   -- Сверить количество напечатанных строк с числом из предыдущего
   -- SELECT. Совпало -> COMMIT; не совпало (кто-то создал/удалил
   -- записи между SELECT и DELETE) -> ROLLBACK и повторить сначала.
   COMMIT; -- или ROLLBACK;
   ```
   **Важная граница этого рецепта.** `RETURNING` в обеих формах — не
   декоративный шаг: он даёт то, что фактически было удалено, печатается
   до `COMMIT`, и именно его сверяют глазами перед тем, как коммитить —
   без него `DELETE` подтверждался бы вслепую. Условие `origin =
   'order_response'` присутствует в обеих формах всегда, включая удаление
   по точному `id`: если `id` по ошибке указывает на запись с
   `origin='price_import'` (созданную price-ingestion), `DELETE` с этим
   условием не затронет её — вернёт 0 строк в `RETURNING`, что сразу видно
   перед `COMMIT` и означает `ROLLBACK`, не тихую порчу чужой записи.
   Эндпоинт `DELETE /suppliers/{supplier_id}/aliases/{alias_id}` этой же
   проблемы не имеет — он не фильтрует по `origin` вообще (удаляет
   `alias_id` любого происхождения для указанного `supplier_id`), и это
   осознанно: `admin`, явно удаляющий конкретный `alias_id` через API, уже
   видел его `origin` на экране перед удалением (отложенный экран
   управления, см. "Отложенные части"), так что эта же граница существует
   и там, но смягчена тем, что UI показывает `origin` перед действием,
   чего прямой SQL-рецепт не делает сам по себе.

## Альтернативы

**Подсказка в промпте вместо/вместе с пост-матчем.** Рассмотрено,
**отложено** (см. "Отложенные части" ниже) — не минимальный объём:
требует правки `_PROMPT_TEMPLATE`/`_order_items_context`, нового лимита
размера, нового формата разделителей, и отдельного замера эффекта,
который сложнее изолировать от эффекта пост-матча. Пост-матч один уже
закрывает ровно тот случай, который стал поводом ADR (строка извлечена
верно, не привязана моделью) — детерминированно и без изменения
LLM-вызова вообще.

**Нормализация текста и в `find_known_alias`/`_upsert_alias`
(price-ingestion), не только в пост-матче.** Отклонено для этой ADR —
меняло бы существующее поведение price-ingestion без отдельного
измерения эффекта на тот пайплайн (там точное совпадение, возможно,
осознанно строгое — не исследовано здесь); минимальный объём для этой
ADR означает не трогать price-ingestion сверх фильтра `origin`.

**Автоматическое применение связи без подтверждения человеком.**
Отклонено — даже единственное числовое совпадение не доказывает
идентичность товара; решение остаётся за сотрудником (не изменилось
между версиями ADR).

**Глобальный (не по поставщику) ключ alias.** Отклонено пользователем
явно в обсуждении перед этой ADR.

**`require_role("admin")` на `POST /orders/{order_id}/response-aliases`
(как в первой версии этой ADR).** Отклонено после проверки факта — весь
`order.py` сегодня открыт для `employee`, ограничивать именно эту кнопку
было бы случайным расхождением с остальной секцией ответа заказа, не
обоснованным разницей в риске (риск ошибочного alias ограничен
изоляцией `origin` — см. п.4 — и всегда обратим через `DELETE`).

**Пропустить `origin` вовсе, полагаясь только на то, что order-response
не читает таблицу сегодня.** Отклонено — без `origin`-фильтра в
`find_known_alias` первая же запись из кнопки "Связать" немедленно начала
бы влиять на price-ingestion того же поставщика (общая таблица, общий
`(supplier_id, material_id)`-индекс), создавая риск неверной цены через
`_apply_match`. `origin` — минимальный способ это предотвратить без
разделения на две таблицы.

## Отложенные части (не в этом объёме)

Вынесены из предыдущей версии этой ADR целиком, не удалены — остаются
кандидатом для отдельной будущей ADR/фазы, если пост-матч (минимальный
объём выше) не даст достаточного эффекта на практике.

### Подсказка aliases в промпте

Добавление в `_order_items_context`/`_PROMPT_TEMPLATE`
(`client.py:60-101`) явного блока со списком известных алиасов этого
поставщика (`origin='order_response'`, `material_id` среди позиций
текущего заказа, лимит 50, `ORDER BY created_at DESC`), обёрнутого
разделителями `---НАЧАЛО/КОНЕЦ СПРАВОЧНЫХ ДАННЫХ---` как цитируемые
данные, не инструкция — чтобы модель могла сопоставлять по смыслу близкие,
но не идентичные варианты написания той же позиции (что точный пост-матч
не поймает). Требует: лимита размера, формата разделителей, отдельного
замера эффекта изолированно от пост-матча (иначе нельзя разделить вклад
двух механизмов), и решения по тому, как фильтровать `material_id`
текущего заказа без дополнительных индексов.

### Правка текста промпта (классы эквивалентности)

Явные примеры в `_PROMPT_TEMPLATE` (SKU-код не означает другой товар;
сокращения единиц измерения; скобки с цветом/материалом) — мотивировано
наблюдением со скриншота, но не подтверждено количественно прогоном
2026-10-19 (0 из 10 `missing` к этому классу). Требует отдельного
прогона `validate_order_response.py` до/после, отдельно от эффекта
alias-механизмов.

### Экран управления алиасами

Просмотр/массовое редактирование/фильтрация алиасов за пределами
точечного `POST`/`DELETE` этой ADR. `source_order_id` (аудит "из какого
документа взялась связь") тоже отложен — без него `DELETE` всё ещё
работает (по `alias_id`), просто отчётность "почему эта связь появилась"
менее подробна; добавляется вместе с экраном управления, если он
понадобится.

### Уникальные ограничения на уровне схемы

`(supplier_id, supplier_raw_name, origin)` как уникальный индекс — не
вводится; конфликт обрабатывается на уровне API (409+`force`) в этом
объёме. Условие пересмотра — если конфликты станут частыми на практике.

### Объединение origin-источников

Если alias подтверждён и в price-ingestion, и в order-response для одного
и того же `(supplier_id, raw_name)` — не считается более достоверным,
не объединяется; каждый источник работает только в своём пайплайне (п.4).
Отдельный вопрос для будущего пересмотра.

## Тесты, обязательные к покрытию

**Пост-матч (`service.py`):**
- Текст `extra`-строки нормализованным сравнением совпадает с ровно одним
  alias этого поставщика, `material_id` которого соответствует ровно
  одной не-declined и ещё не сопоставленной позиции заказа → строка
  переносится в `matched`, `confidence` остаётся неизменным (тем
  значением, что вернула модель для этой строки — тест фиксирует
  конкретное фикстурное значение до и после, проверяя равенство, не
  "high"), `reasoning` дополнен пометкой источника, `matched_by_alias:
  true` в ответе API.
- То же, но `material_id` алиаса соответствует **нескольким**
  не-сопоставленным позициям заказа (например, два `OrderItem` одного
  материала в одном заказе) → пост-матч не угадывает, строка остаётся в
  `extra`.
- То же, но ни одна позиция заказа не имеет такого `material_id` → не
  угадывает, остаётся в `extra`.
- Строка уже имеет `matched_order_item_id` от модели (не `None`) → пост-
  матч её не трогает, даже если есть подходящий alias (тест явно
  проверяет, что значение, присвоенное моделью, не перезаписывается).
- Позиция, подходящая по `material_id` для `line`, уже сматчена моделью
  **другой** строкой этого же документа (`matched_order_item_id` этой
  позиции указывает на другую строку `extracted`) → не считается
  кандидатом для `line`, `line` остаётся в `extra` (не угадывает вторую
  позицию взамен).
- Два разных `extra`-текста обоих совпадают (по нормализованному
  сравнению) с одним и тем же alias → только первый по порядку обработки
  получает match на соответствующий `OrderItem`, второй не находит
  свободного кандидата (позиция уже в исключённом множестве) и остаётся
  в `extra` — явный тест на то, что alias не применяется дважды к одному
  `OrderItem`.
- Alias другого поставщика с тем же текстом `raw_description` → не
  применяется (изоляция по `supplier_id`).
- Alias с `origin='price_import'` (созданный price-ingestion) → не
  применяется пост-матчем order-response (изоляция по `origin`).
- `OrderItem`, подходящий по `material_id`, но с `declined_at IS NOT
  NULL` → не считается кандидатом, не применяется.
- Регистр/пробелы: `raw_description="S-25-00-00070  3x4 a elbow bronze"`
  (другой регистр, двойной пробел) совпадает с сохранённым alias
  `"S-25-00-00070 3X4 A ELBOW BRONZE"` — нормализация работает в обе
  стороны.

**Price-ingestion изоляция:**
- Alias с `origin='order_response'` не возвращается `find_known_alias`
  (которая теперь фильтрует на `origin='price_import'`) — явный тест
  "alias из order-response не влияет на price-ingestion matching того же
  поставщика и того же текста".
- `_upsert_alias` при создании новой строки проставляет
  `origin='price_import'` явно.

**Эндпоинт `POST /orders/{order_id}/response-aliases`:**
- 404 — `order_id` не найден; 404 — `material_id` не найден.
- Конфликт `(supplier_id, raw_name, origin='order_response')` → другой
  `material_id`, без `force` — 409 с телом, содержащим существующую
  запись; с `force: true` — перезапись существующей строки (не дубль).
- Точная тройка уже существует — no-op, 200, не создаёт вторую строку.
- **Созданная строка всегда имеет `origin='order_response'`** — явный
  тест, читающий созданную запись из БД после вызова эндпоинта и
  проверяющий значение колонки напрямую (не косвенно через поведение
  matching), в том числе при `force: true`-перезаписи (перезаписанная
  строка не меняет `origin` на что-то иное).

**`DELETE /suppliers/{supplier_id}/aliases/{alias_id}`:**
- `alias_id`, принадлежащий другому `supplier_id`, чем в пути — 404.
- Успешное удаление — 204 (или принятый в проекте код для DELETE, см.
  прецедент `DELETE /orders/{order_id}` → 204 в `order.py:195`).

**Миграция (up/down):**
- `alembic upgrade head` применяет три новые колонки без ошибок на БД с
  уже существующими строками `supplier_material_aliases` (не пустая
  таблица — тест прогоняется поверх фикстуры с хотя бы одной
  price-ingestion-записью, созданной до миграции).
- Существующие строки после `upgrade` получают `origin='price_import'`
  (дефолт), `created_at IS NULL`, `created_by_user_id IS NULL`.
- `alembic downgrade -1` откатывает три колонки без ошибок; последующий
  `alembic upgrade head` снова применяется чисто (миграция идемпотентна
  в цикле up→down→up на тестовой БД).

**Фронтенд (отдельная сессия, но тест-требование фиксируется здесь,
в объёме ADR):**
- Предложение пары при **единственном** числовом кандидате (цена, и
  количество если применимо) — кнопка "Связать" показывает
  предзаполненную пару с текстом основания, без необходимости сотруднику
  искать вручную.
- Предложения нет при **нескольких** кандидатах с совпадающими числами —
  форма открывается с пустым выбором, сотрудник ищет среди полного списка
  "Отсутствует в ответе".
- Предложения нет при **нуле** кандидатов — то же самое, пустой выбор.

**Бэкенд — `matched_by_alias`:**
- Строка, привязанная пунктом 5 алгоритма пост-матча, выходит в ответе
  `POST /orders/{order_id}/parse-response` с `matched_by_alias: true` —
  явный тест, читающий это поле в JSON-ответе эндпоинта, не внутреннее
  состояние `service.py`.
- Строка, привязанная моделью в исходном ответе (не тронутая пост-матчем)
  — `matched_by_alias: false`, даже если для её `material_id` существует
  подходящий alias (случай "модель и так справилась, alias был бы
  избыточен" — не должен ложно подниматься как "это сработал alias").

**Фронтенд — `matched_by_alias`:**
- Строка блока "Совпало" с `matched_by_alias: true` — чекбокс массового
  применения **не отмечен** по умолчанию при отрисовке экрана (в отличие
  от остальных строк того же блока, где он отмечен по умолчанию) — явный
  тест, проверяющий начальное состояние чекбокса конкретно для этой
  строки, не общее поведение блока.
- Такая строка подписана текстом "по сохранённой связи".
- Нажатие "Применить все совпадения" без ручной отметки этого чекбокса
  **не включает** эту строку в отправляемый `PATCH`-цикл — явный тест на
  то, что строка пропускается, если сотрудник её не отметил вручную.

## Метрика успеха — без прогона на документах

Полный повторный прогон `validate_order_response.py` на новой выборке
**не входит в минимальный объём** этой ADR (он требовал бы новых
документов и был бы подвержен тому же разбросу между прогонами, что уже
обнаружен в "Контексте" — 10→12 `missing` без изменений кода на той же
выборке). Вместо этого:

- **Три числа в логах бэкенда** при каждом вызове `parse_order_response`,
  одна структурная запись на документ:
  - `aliases_loaded` — сколько `SupplierMaterialAlias` с
    `origin='order_response'` загружено для `order.supplier_id` (шаг 2
    алгоритма пост-матча) — ноль означает "у этого поставщика ещё нет ни
    одной сохранённой связи", отличимо от "связи есть, но не сработали";
  - `extra_lines_before` — число строк с `matched_order_item_id is None`
    **до** применения пост-матча (т.е. то, что вернула модель как
    "лишнее" изначально);
  - `post_match_hits` — число строк, перенесённых из `extra` в `matched`
    пунктом 5 алгоритма (0, если ни одной).
  Три числа вместе дают интерпретируемую картину: `aliases_loaded=0` →
  пост-матчу не на чем сработать (ожидаемо, если ещё не создавалось
  alias для этого поставщика); `aliases_loaded>0, post_match_hits=0` →
  алиасы есть, но ни один не совпал с текстом этого документа (стоит
  посмотреть, почему — другая формулировка, другой SKU); `post_match_hits
  / extra_lines_before` — доля "лишнего", которую пост-матч закрыл на
  этом конкретном документе. Не персистится в БД в этом объёме — только
  структурный лог, чтобы не добавлять новую таблицу/колонку сверх уже
  решённых трёх полей миграции.
- **Ручная проверка на следующих реальных ответах AMS** — после того, как
  хотя бы один alias создан через кнопку "Связать" на документе AMS,
  следующий полученный от AMS документ ответа проверяется сотрудником
  визуально: появилась ли в блоке "Совпало" строка с пометкой "[сопоставлено
  по сохранённому alias поставщика]" там, где раньше была бы пара
  "Лишнее"/"Отсутствует". Это качественная, не статистическая проверка —
  достаточна для минимального объёма, где количественный прогон отложен.

## Порядок выкатки

**После деплоя ADR-0045, отдельным деплоем.** Текущая alembic-голова на
момент написания этой ADR — `50786ee4d5ed` ("add needed_quantity to
allocation_line and order_item", миграция ADR-0045) — подтверждено
`alembic heads`. Миграция этой ADR (п.3) создаётся с `down_revision =
"50786ee4d5ed"`, то есть **поверх** головы ADR-0045, не параллельно ей.

**Если ADR-0045 ещё не выкачена на момент, когда пишется миграция этой
ADR** (т.е. её revision физически существует в `alembic/versions/`
локально, но ещё не применена на проде) — цепочка всё равно линейна,
потому что `down_revision` ссылается на файл по его revision id, не на
"применённое на проде состояние"; alembic разрешает граф миграций по
файлам в репозитории, не по тому, что уже накачено на конкретной БД.
Единственный практический риск — если кто-то попытается накатить эту
ADR-0046 раньше ADR-0045 на одной БД: `alembic upgrade head` в этом
случае сам применит обе по порядку (ADR-0045, затем ADR-0046), потому что
голова (`head`) — это конец всей цепочки, и `upgrade head` всегда
проходит от текущей версии БД до конца, не позволяя пропустить
промежуточную ревизию. Запутать цепочку можно только если создать вторую
ветку миграций с тем же `down_revision` (две миграции одновременно
ссылаются на `50786ee4d5ed`) — тогда `alembic heads` покажет два head и
потребует явного merge; чтобы это не произошло, автор миграции этой ADR
обязан проверить `alembic heads` непосредственно перед тем, как писать
`down_revision =`, и использовать актуальный на тот момент head, а не
число, зафиксированное в этом тексте (оно могло устареть к моменту
реализации, если между написанием этой ADR и её кодированием добавятся
другие миграции).

## Что не проверено

- Действительно ли сотрудники заметят и воспользуются неотмеченным по
  умолчанию чекбоксом/подписью "по сохранённой связи" на практике, а не
  машинально отметят его тоже перед массовым применением, сведя на нет
  защитный эффект — это поведенческое предположение, не проверяемое до
  реального использования интерфейса; UX-формулировку подписи стоит
  пересмотреть, если в ручной проверке (см. "Метрика успеха") окажется,
  что сотрудники отмечают такие строки не глядя.
- Частота класса "SKU+сокращение vs каноническое имя" на репрезентативной
  выборке — прогон 2026-10-19 дал 0 примеров среди 10 `missing`;
  пример-мотиватор взят с другого, неизмеренного заказа. Минимальный
  объём этой ADR сознательно не делает ставку на то, что пост-матч даст
  измеримо лучший `missing_rate` — успех измеряется логом `post_match_
  hits` и ручной проверкой, не процентом.
- Частота конфликта `(supplier_id, raw_name, origin='order_response')` →
  два разных `material_id` (409-путь) в реальной практике.
- Поведение на документах поставщиков вне тех 3, что уже видела эта ADR.
- **Миграция проверена вручную (цикл upgrade→downgrade→upgrade,
  `relfilenode` до/после `ALTER` на локальной копии прод-БД,
  `alembic heads` после — ровно один head), но автоматического теста
  (pytest-уровня, прогоняемого в CI) нет.** Причина: сама тестовая
  инфраструктура этого проекта на общей dev-БД (`localhost:5432`)
  нестабильна между прогонами (найдено при ревью этой ADR, см.
  `docs/known-issues.md` — накопленные строки от предыдущих прогонов
  дают разное число падений от запуска к запуску), а миграционный тест
  по своей природе требует менять схему самой этой БД — на нестабильной
  общей среде такой тест либо сам стал бы ещё одним источником
  нестабильности для остальных тестов, либо потребовал бы отдельной
  изолированной БД в CI, которой сейчас нет (см. ту же запись в
  known-issues.md про полную alembic-цепочку, которая не воспроизводится
  с нуля). Ручная проверка остаётся единственным текущим способом
  подтвердить эту конкретную миграцию; условие для будущего пересмотра —
  если/когда появится изолированная CI-БД, перенести эту проверку туда
  как автоматический тест.
- Надёжность пост-матча на вариантах текста, которые нормализация этой
  ADR (casefold + схлопывание пробелов) не покрывает — например, другой
  порядок слов или другая пунктуация (`"3x4 A Elbow"` vs `"3X4-A-ELBOW"`)
  не совпадут; такие случаи остаются на будущую подсказку в промпте
  (отложенную часть), не на этот минимальный объём.
- UI для 409/force — текст и поведение диалога не детализированы здесь
  (реализуется фронтенд-сессией отдельно от бэкенда, п.2), только
  контракт ответа сервера (409 + тело с существующей записью).
- Влияние `created_at IS NULL` у старых строк на любую будущую сортировку
  "по давности" (`ORDER BY created_at`) — в этом объёме такой сортировки
  нигде не вводится (отложенная подсказка в промпте, где она была бы
  нужна, не входит в текущий объём), поэтому `NULL`-значения не создают
  проблему прямо сейчас, но станут вопросом, если отложенная часть
  "подсказка в промпте" будет реализована позже.
