# ADR-0047: Солвер переходит с целых центов на миллиценты — точность на мелком крепеже

Статус: Предложено

## Контекст

Обнаружено при ревью ADR-0046 (2026-10-20), не связано с ней — отдельный
баг в `app/allocation/`. `Price.price` хранится как `Numeric(12, 3)`
(`backend/app/models/price.py:28`) — три знака после запятой, нужные для
мелкого крепежа (цена может быть $0.019/шт). Солвер переводит всё в целые
центы **до** умножения на количество:

```python
# backend/app/allocation/service.py:44,90-91
_CENTS_PER_UNIT = 100

def _to_cents(amount) -> int:
    return round(float(amount) * _CENTS_PER_UNIT)

# backend/app/allocation/service.py:126
unit_price_cents=_to_cents(price.price),
```

```python
# backend/app/allocation/solver.py:225,233-234
unit_price = price[(m_id, s_id)]
quantity = order_qty[(m_id, s_id)]
...
unit_price_cents=unit_price,
line_total_cents=unit_price * quantity,
```

**Подтверждено на реальных прод-данных (2026-10-21, снимок активных
цен).** Из 729 активных цен 23 несут третий знак после запятой (нулевого
округления до центов среди них нет — ни одна цена не теряет весь смысл,
округляясь в 0). Разбивка по типу материала:

- **12 из 23** — крепёж, диапазон $0.019–$0.335/шт. Ошибка округления
  единичной цены — **5–9%** от истинного значения.
- **11 из 23** — профили/рулоны, $17–$260. Ошибка округления —
  пренебрежимо мала в относительном выражении.

**Реальный случай ложной ничьей, зафиксированный на проде**: материал
`Anchor 1/4x3" Bronze/White Galvanized`, два поставщика — `JM Fasteners`
($0.019/шт) и `Florida Sales & Marketing` ($0.022/шт). Это два разных
значения — реальная разница между ними **16%**. После `_to_cents`
(`round(0.019 * 100) = 2`, `round(0.022 * 100) = 2`) оба становятся
`unit_price_cents = 2` — солвер видит их как **одинаковую** цену и теряет
единственный реальный сигнал о том, что один поставщик дешевле другого на
этом материале. Это не гипотетический пример — конкретная пара
поставщик/материал, существующая в проде на момент этого ADR.

**Асимметрия внутри самого `service.py`.** Округление происходит не
единообразно — есть два разных порядка:

- `service.py:126` — округляется **цена за единицу**, до умножения на
  количество (путь, где обнаружен баг).
- `service.py:280` (`_rebuild_supplier_summary`, override-путь) —
  `goods_total_cents = sum(_to_cents(line.line_total) for line in lines)`
  — округляется уже **сумма по строке** (`AllocationLine.line_total`,
  которая сама `Numeric(12,3)`, посчитана как `unit_price × quantity` на
  момент создания строки, `order_service.py` — точное значение уже
  умножено). Этот путь не теряет точность тем же образом, потому что
  умножение произошло раньше округления, не после.

**Остальные места, где `_to_cents`/`_from_cents` используются** (полный
список, подтверждено):
- `service.py:150,154,156` — `supplier.delivery_policy` (`flat_fee`,
  `free_shipping_threshold`, `per_order_min_amount`) — JSON-поля, не
  `Numeric`-колонки БД, округляются в центы как константы солвера.
- `service.py:175-180` — обратная конвертация `_from_cents` для
  `supplier_summaries` на выходе, плюс вызов `calculate_tax` инлайн.
- `service.py:220-221` — `_from_cents` на `AllocationLine.unit_price`/
  `line_total` при записи в БД.
- `service.py:284,290,293` — тот же `_to_cents` на `delivery_policy`
  внутри `_rebuild_supplier_summary`.

**`calculate_tax`** (`backend/app/allocation/tax.py:19-25`) явно
зафиксирован в центах — и в сигнатуре, и в докстринге, и в ADR-0029:
```python
def calculate_tax(goods_subtotal_cents: int) -> int:
    """7% of the goods subtotal, rounded to the nearest cent — see ADR-0029
    §3. ..."""
    return round(goods_subtotal_cents * TAX_RATE)
```
`calculate_tax_dollars` (строки 28-32) — тонкая обёртка, сама делает
`* 100`/`/ 100`.

**ADR-0029 явно коммитится к "центам", не к абстрактной "целочисленной
единице".** Цитата из ADR-0029 (докстринг `tax.py`, со ссылкой на
ADR-0002): "Работает в центах (int), не в float/Decimal долларах.
Симметрично solver.py/service.py (_to_cents/_from_cents... "деньги —
целые центы на границе солвера, чтобы избежать ошибок плавающей
точки")". Это значит переход на другую единицу требует отдельной ADR,
явно дополняющей/заменяющей этот пункт ADR-0029 — не тихой правки кода
под старым текстом. **ADR-0002 сам по себе** (исходная ILP-постановка,
`docs/decisions/0002-supplier-allocation-algorithm.md`) **не фиксирует
единицу как "центы" в собственном тексте** — работает символически с
`price[m][s]` как вещественной величиной; формулировка "целые центы"
принадлежит коду/докстрингам ADR-0029, не самому ADR-0002. Значит эта
ADR не переоткрывает саму ILP-постановку (переменные, ограничения,
целевую функцию ADR-0002) — только единицу измерения денег на границе
солвера, которую зафиксировал ADR-0029.

**Вторая, более глубокая точка усечения — за пределами солвера.**
`AllocationLine.unit_price`/`line_total`/`original_unit_price` — уже
`Numeric(12, 3)` (`backend/app/models/allocation.py:73-74,89`), то есть
**не требуют миграции** для хранения более точного значения — они уже
физически способны. Но `Order.total_amount`/`delivery_fee`/`tax_amount`
— `Numeric(12, 2)` (`backend/app/models/order.py:29-31`), и
`create_orders_for_run` (`order_service.py:654`) пишет туда
`sum(float(line.line_total) for line in lines)` — если `line_total`
станет точнее (3 знака вместо округлённых до цента 2), сумма всё равно
молча обрежется до 2 знаков на границе `Order`, повторно теряя ту же
точность, которую этот ADR должен вернуть, просто на один шаг дальше по
цепочке.

## Решение

### 1. Внутренняя единица солвера — миллиценты (1/1000 доллара), не центы

`_CENTS_PER_UNIT = 100` → `_MILLICENTS_PER_UNIT = 1000`. Выбор
миллицентов, не произвольно более мелкой единицы — потому что это
**точно** совпадает с шагом `Price.price` (`Numeric(12,3)`, минимальный
шаг 0.001 доллара = 1 миллицент): любая цена, какой бы она ни была в
БД в пределах объявленной точности, конвертируется в миллиценты и
обратно без потери ни одного значащего разряда. Выбор более мелкой
единицы (например, микроцентов) не добавил бы точности (в БД больше трёх
знаков после запятой физически нет) и увеличил бы коэффициенты
CP-SAT-модели без пользы.

`_to_millicents`/`_from_millicents` заменяют `_to_cents`/`_from_cents`
во всех перечисленных выше точках `service.py` (126, 150/154/156,
175-180, 220-221, 280, 284/290/293) — везде, где раньше был `* 100`,
становится `* 1000`; везде, где было `/ 100`, становится `/ 1000`.
Переименование функций и константы обязательно (не оставлять имя
`_to_cents` над кодом, который считает в миллицентах — вводящее в
заблуждение имя хуже, чем лишний diff при переименовании).

### 2. CP-SAT — коэффициенты, не архитектура модели

Подтверждено (research перед этой ADR): `solve_allocation` использует
OR-Tools CP-SAT (`ortools.sat.python.cp_model`,
`backend/app/allocation/solver.py:10,65,209`), переменные — 64-битные
целые. Увеличение коэффициентов в 10 раз (объектная функция —
`solver.py:141`, `order_total` — там же, big-M свободной доставки —
строки 161-176, `category_split_penalty` — строка 204) остаётся на много
порядков ниже практического предела домена переменных CP-SAT на
реальных объёмах закупки (единицы-десятки тысяч долларов). Переполнения
не ожидается. Время решения определяется в первую очередь структурой
задачи (число переменных/ограничений), не масштабом коэффициентов в этом
диапазоне — замедления не ожидается, но должно быть подтверждено
реальным прогоном солвера на существующих интеграционных тестах перед
принятием (не только юнит-тестами на искусственно малых данных).

**Переименования внутри `solver.py`, без изменения логики:**
- `epsilon_cents = 1` (строка 161) → `epsilon_millicents = 1` — остаётся
  "наименьшая единица для строгого неравенства big-M", концептуально не
  меняется, меняется только то, что это за единица; `threshold`/
  `max_order_total`/`big_m`, участвующие в том же блоке (строки 174-176),
  должны быть явно сверены на согласованность единиц при реализации — не
  только переименованы, а проверено, что весь блок работает в одной и
  той же шкале.
- `category_split_penalty = round(CATEGORY_SPLIT_PENALTY_K *
  avg_flat_fee_cents)` (строка 204) — переменная `avg_flat_fee_cents`
  тоже станет миллицентовой; сам коэффициент `CATEGORY_SPLIT_PENALTY_K`
  (ADR-0028 §2, значение 4) не требует пересмотра — он масштабирует
  штраф относительно `flat_fee`, которая масштабируется вместе с
  остальной моделью, соотношение сохраняется.

### 3. `calculate_tax` — контракт меняется, по согласованию с ADR-0029

`calculate_tax(goods_subtotal_cents: int) -> int` →
`calculate_tax(goods_subtotal_millicents: int) -> int`, та же формула
(`round(goods_subtotal_millicents * TAX_RATE)`), только единица входа
и выхода. `calculate_tax_dollars` обновляет свою `* 100`/`/ 100` на
`* 1000`/`/ 1000`. **Это явно дополняет ADR-0029**, не отменяет её
по существу (TAX_RATE, место применения — на уже просуммированный
subtotal, не на каждую строку отдельно — всё остаётся в силе); меняется
только единица измерения параметра, зафиксированная в ADR-0029 буквально
как "центы". ADR-0029 не переписывается задним числом — этот ADR
фиксирует, что её формулировка "работает в центах" заменяется на "работает
в миллицентах" начиная с этой ADR, сохраняя остальной текст ADR-0029 в
силе.

### 4. `Order.total_amount`/`delivery_fee`/`tax_amount` — миграция на `Numeric(12,3)`

Без этого шага пункты 1-3 не имеют практического эффекта для
пользователя: возвращённая солвером более точная сумма по строке
(`AllocationLine.line_total`, уже `Numeric(12,3)`, точность не терялась
бы) всё равно обрежется до цента на границе `Order`
(`create_orders_for_run`, `order_service.py:654`,
`total_amount=sum(float(line.line_total) for line in lines)`, пишется в
`Numeric(12,2)`-колонку). Миграция расширяет `Order.total_amount`,
`Order.delivery_fee`, `Order.tax_amount` до `Numeric(12,3)` — тот же
паттерн, что миграция `c7f2a91b4e0d` уже применила к `Price.price`/
`OrderItem`-полям (упомянута в контексте ADR-0046 и подтверждена в коде).
Обратная совместимость: расширение точности `Numeric` не теряет
существующие данные (значения с 2 знаками остаются валидными значениями
с точностью до 3 знаков, третий знак — ноль).

### 5. Обязательный regression-тест — реальный прод-пример

В `backend/tests/allocation/test_solver.py` добавляется тест,
буквально воспроизводящий найденный на проде случай — не абстрактные
числа, а эту конкретную пару:

```python
def test_distinguishes_suppliers_with_sub_cent_price_difference():
    """Real prod case (2026-10-21 snapshot): JM Fasteners $0.019/pc vs
    Florida Sales & Marketing $0.022/pc for the same material (Anchor
    1/4x3" Bronze/White Galvanized) — a real 16% difference that
    _to_cents (round to whole cents) collapsed into a false tie
    (both rounded to $0.02), making the solver treat them as equally
    priced. With millicent precision, the solver must pick the
    genuinely cheaper supplier (JM Fasteners), not split arbitrarily
    or ignore the real price signal."""
    materials = [MaterialInput(material_id="anchor", quantity=1000)]
    suppliers = [
        SupplierInput(supplier_id="jm_fasteners", flat_fee_cents=0,
                       free_shipping_threshold_cents=None),
        SupplierInput(supplier_id="florida_sales", flat_fee_cents=0,
                       free_shipping_threshold_cents=None),
    ]
    prices = [
        PriceInput(material_id="anchor", supplier_id="jm_fasteners",
                   unit_price_millicents=19, availability=10_000, min_order_qty=1),
        PriceInput(material_id="anchor", supplier_id="florida_sales",
                   unit_price_millicents=22, availability=10_000, min_order_qty=1),
    ]

    result = solve_allocation(AllocationInput(materials=materials, suppliers=suppliers, prices=prices))

    assert result.status in ("OPTIMAL", "FEASIBLE")
    line = next(l for l in result.lines if l.material_id == "anchor")
    assert line.supplier_id == "jm_fasteners"  # genuinely cheaper, must not tie
```

Точные имена полей (`unit_price_millicents` и т.п.) зависят от итогового
переименования в реализации — здесь приведён контракт теста, не готовый
к копированию код (поля/дата-классы солвера на момент написания этой ADR
называются `*_cents`, переименовываются по п.1-2 решения).

## Альтернативы

**Decimal вместо целочисленных миллицентов.** Отклонено — не
рассматривалось всерьёз в этой ADR: CP-SAT требует целочисленных
коэффициентов модели, `Decimal` неприменим внутри самого решателя
независимо от того, какая точность нужна бизнесу. Вопрос этой ADR —
только в том, какая целочисленная единица выбрана, не в отказе от
целых чисел вовсе.

**Более мелкая единица, чем миллиценты (например, микроценты,
1/1,000,000 доллара).** Отклонено — `Price.price` ограничена
`Numeric(12,3)` на уровне схемы БД, точнее 0.001 доллара цена физически
не может быть сохранена сегодня. Более мелкая внутренняя единица солвера
не добавила бы точности (конвертация `Decimal(12,3) → ещё более мелкая
единица` не создаёт новую информацию), только увеличила бы коэффициенты
модели без необходимости.

**Оставить центы, компенсировать округление в момент сравнения цен (не
внутри солвера).** Рассмотрено, отклонено — проблема не в сравнении, а
в том, что сама информация о разнице теряется до того, как солвер её
увидит (`_to_cents` вызывается один раз на входе, до построения модели);
"компенсация при сравнении" потребовала бы либо держать исходные
нецелые цены параллельно с целочисленными (дублирование источника
истины, риск рассинхрона), либо пересчитывать модель иначе для каждого
сравнения — сложнее и менее надёжно, чем просто увеличить точность самой
целочисленной единицы один раз у источника.

## Последствия

**Миграция**: `Order.total_amount`/`delivery_fee`/`tax_amount`
`Numeric(12,2)` → `Numeric(12,3)`. Прямая расширяющая миграция, без
backfill (существующие значения валидны как есть, третий знак — 0).
Откат — сужение обратно до `(12,2)`, с риском обрезания любых новых
значений с ненулевым третьим знаком, записанных после выката этой ADR —
стандартный компромисс downgrade для расширяющей миграции.

**Код**: переименование `_CENTS_PER_UNIT`/`_to_cents`/`_from_cents` →
`_MILLICENTS_PER_UNIT`/`_to_millicents`/`_from_millicents` в
`service.py` (все перечисленные выше вызовы); переименование
`unit_price_cents`/`line_total_cents`/`goods_total_cents`/
`flat_fee_cents`/`free_shipping_threshold_cents`/
`per_order_min_amount_cents`/`epsilon_cents`/`avg_flat_fee_cents` в
дата-классах `solver.py` (`PriceInput`/`SupplierInput`/
`AllocationLineResult`/внутренние переменные) на эквиваленты с
`_millicents`; `calculate_tax`/`calculate_tax_dollars` в `tax.py`.

**Тесты, блок-радиус (подтверждено research перед этой ADR)**:
- `backend/tests/allocation/test_solver.py` — ~180 мест с литералами
  `*_cents=`/`*_cents ==` требуют домножения на 10 **и** переименования
  полей (простой find/replace значений недостаточен, если переименованы
  и сами поля дата-классов).
- `backend/tests/allocation/test_tax.py` — ~4 литеральных assertion
  (`calculate_tax(10_000) == 700` и подобные) требуют домножения на 10.
- `backend/tests/allocation/test_service.py` — assertions выражены в
  долларах (`float(lines[0].unit_price) == 5.00`), не в сырых центах —
  не требуют изменений, т.к. конвертация туда-обратно остаётся
  прозрачной на границе дата-класса/БД.
- `test_preprocess.py` — не работает с деньгами (availability/qty),
  не затронут.
- Новый тест из п.5 решения (прод-пример) — обязателен к зелёному
  прохождению перед принятием этой ADR.

**Не меняется**: сама ILP-постановка (переменные, ограничения, целевая
функция ADR-0002) — только единица измерения денежных коэффициентов.
`Price.price`/`AllocationLine.unit_price`/`line_total`/
`original_unit_price`/`OrderItem`-денежные поля — уже `Numeric(12,3)`,
миграция не требуется.

**Что не проверено:**
- Реальное время решения солвера на существующих интеграционных тестах
  с новыми коэффициентами ×10 — агент-ресёрч оценил риск как
  пренебрежимый по структуре задачи, но это не было измерено прогоном,
  только архитектурной оценкой; должно быть подтверждено до принятия
  (см. "Решение" п.2).
- Полнота списка мест, где `Order.total_amount` или производные от него
  суммы дальше используются (например, в allocation-UI, отчётах) —
  найдена сама точка усечения в `order_service.py:654`, но не
  прослежено, есть ли downstream-код, который уже полагается на
  округление `Order.total_amount` до цента (например, сравнение с
  `OrderItem`-суммами) и может неожиданно начать показывать расхождение
  в третьем знаке после этой ADR.
- Частота других пар "ложная ничья из-за округления" среди 729 активных
  цен прода, кроме найденной пары `Anchor 1/4x3"` — снимок дал количество
  позиций с третьим знаком (23) и диапазон ошибки по категориям, но не
  полный перебор всех пар поставщик/материал на предмет совпадения после
  округления; возможны другие необнаруженные случаи с тем же эффектом.
- Поведение `category_split_penalty`/эпсилон-блока big-M при реальном
  масштабировании — переименование описано, но фактическая проверка (что
  результат модели с категорийным сплитом не меняется при переходе на
  миллиценты, помимо самого исправления точности цены) не выполнена.

## Порядок выкатки

Реализация не начинается до явного ОК пользователя на этот ADR. Деплой —
не раньше завершения выкатки ADR-0045 (условие, заданное пользователем
для всей текущей серии изменений, относится и к этой ADR, т.к. она
меняет тот же allocation-модуль, где ADR-0045 добавила MOQ-логику).
