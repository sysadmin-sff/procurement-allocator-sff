# ADR-0048: Выбор действия по каждому поставщику в конфликте draft-ордеров

Статус: Принято (варианты выбора и поведение «Заменить» согласованы с
пользователем 2026-11-02)

## Контекст

ADR-0012 ввёл модалку конфликта draft-ордеров: при `POST
/projects/{project_id}/allocations/{run_id}/orders`, если у поставщиков
текущего рана уже есть `draft`-`Order` в проекте, backend отвечает `409`, и
сотрудник выбирает **одно действие на всех поставщиков сразу**:
`replace_drafts: true` («Заменить черновики») или `acknowledge_conflict:
true` («Создать дополнительно»).

Реальный сценарий из практики (2026-11-02, скриншот пользователя):
сотрудник пересчитывает закупку, чтобы проверить, сколько будет стоить то
же самое, если часть позиций перенести (override, ADR-0006) от одного
поставщика к другому, и хочет получить ордера **для сравнения** рядом со
старыми. «Создать дополнительно» в этом случае дублирует и тех
поставщиков, у которых в пересчёте ничего не изменилось: на скриншоте у
American Metals Supply уже два одинаковых черновика по $3,125.12. «Заменить
черновики» стирает старые ордера, с которыми и нужно сравнивать. Нужного
действия («у этого поставщика заменить, у этого создать дополнительно, этому
вообще не создавать новый») всё-или-ничего контракт ADR-0012 выразить не
может.

ADR-0012 §3 уже считает конфликт по каждому поставщику отдельно, и тело
`409` уже содержит список поставщиков. Не хватает только способа передать
решение для каждого поставщика.

## Решение

### 1. API: поле `supplier_actions`

Тело `POST .../orders` получает необязательное поле:

```
supplier_actions: dict[supplier_id, "replace" | "add" | "skip"] | null = null
```

- `"replace"` — удалить **все** конфликтующие draft-ордера этого
  поставщика (ровно те, что попали в тело `409`, то же множество, что
  удаляет `replace_drafts` сегодня, включая фильтр полностью отклонённых
  черновиков без подтверждённых цен, ADR-0026) и создать новый ордер из
  рана. Выбор отдельных черновиков внутри поставщика не предусмотрен —
  согласовано с пользователем; дубли этим путём и чистятся.
- `"add"` — создать новый ордер рядом со старыми, ничего не удаляя (то же,
  что `acknowledge_conflict` для этого поставщика).
- `"skip"` — **не создавать** новый ордер этому поставщику; его старые
  черновики не трогаются, `AllocationLine.ordered_at` строк этого
  поставщика в ране не проставляется (они не ушли ни в какой `Order`).

Правила сервера (stateless, как и в ADR-0012):

- Поставщики рана **без** конфликта создаются как обычно, независимо от
  `supplier_actions`. Запись в `supplier_actions` для поставщика, у которого
  на момент запроса конфликта нет (например, его черновик удалили между
  `409` и повторным запросом), игнорируется — поставщик создаётся обычным
  путём. Дубля это не создаёт: дубля без существующего черновика нет.
- Если у **хотя бы одного** конфликтующего на момент запроса поставщика нет
  записи в `supplier_actions` (конфликт появился между `409` и повторным
  запросом) — снова `409` с актуальным телом, ничего не создаётся и не
  удаляется. Сервер не угадывает действие за пользователя.
- `supplier_actions` вместе с `replace_drafts: true` или
  `acknowledge_conflict: true` — `422`: два способа сказать одно и то же в
  одном запросе, без правила приоритета.
- Старые поля `replace_drafts`/`acknowledge_conflict` остаются как есть
  (эквивалент «replace всем» / «add всем»), обратная совместимость.
- Все удаления и создания — одна транзакция, как сейчас.
- Если в итоге не создано ни одного ордера (все поставщики рана в
  конфликте и все `"skip"`) — `201` с пустым списком, `Project.status` не
  меняется (существующее условие `if orders:`).

### 2. UI: модалка конфликта

`OrderDraftConflictModal` вместо двух общих кнопок «Создать
дополнительно» / «Заменить черновики» показывает у каждого поставщика три
варианта (радиокнопки): «Заменить» / «Создать дополнительно» / «Не
создавать». Одна кнопка «Создать ордера» отправляет `supplier_actions`.

- Предвыбора нет: кнопка неактивна, пока у каждого поставщика не выбран
  вариант. Ни один из трёх не является безопасным умолчанием для всех
  случаев («Создать дополнительно» как раз и производит дубли из
  «Контекста»).
- Чекбокс подтверждения потери подтверждённых цен (ADR-0012 §4) требуется
  только если «Заменить» выбрано хотя бы у одного поставщика с
  `has_confirmed_prices`; предупреждение у такого поставщика показывается
  как раньше.
- Подсказка внизу: замена удаляет старые черновики выбранных поставщиков
  безвозвратно.
- После успеха — как сейчас (переход на экран проекта), в том числе при
  пустом списке созданных ордеров.

## Альтернативы

- **Галочка «заменить» у поставщика (снята = создать дополнительно).**
  Проще, но не убирает дубли поставщиков без изменений — основную боль из
  «Контекста». Отклонено пользователем.
- **Галочки у каждого черновика (что удалить), новые ордера — всем.**
  Гибче для чистки дублей, но не позволяет не создавать новый ордер, и
  модалка сложнее. Отклонено пользователем.
- **Отдельный эндпоинт** вместо поля в существующем — дублировал бы всю
  логику `create_orders_for_run` (цвет, ран, транзакция) ради одного
  параметра. Отклонено.

## Последствия

- `CreateOrdersIn` получает `supplier_actions`; `create_orders_for_run()`
  — параметр `supplier_actions` и ветку обработки по поставщику
  (`backend/app/allocation/order_service.py`).
- `frontend/src/components/OrderDraftConflictModal.tsx` — радиокнопки по
  поставщикам вместо общих кнопок; `AllocationResultPage.tsx`/
  `ordersApi.createForRun` — передача `supplier_actions`.
- `docs/ui-reference.md` §3 (модалка конфликта) переписывается под новое
  поведение.
- Миграции нет.
- Визуал модалки собран из существующих стилей вручную, не через Claude
  Design — `docs/design/` не обновлялся.
- Не меняется: правила ADR-0012 о том, что считается конфликтом
  (`approved`/`sent` никогда не конфликтуют и не удаляются), фильтр
  ADR-0026, проверка цвета проекта (ADR-0031) до любого удаления.
