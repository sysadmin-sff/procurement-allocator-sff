# ADR-0049: Порядок материалов внутри категории — по `internal_sku`

Статус: Принято (правило согласовано с пользователем 2026-11-02)

## Контекст

ADR-0042 зафиксировал порядок **категорий** (`Category.display_order`), но
не порядок материалов внутри категории. Его не задаёт ни одна таблица:
у `ProjectItem`, `ProjectTemplateItem`, `AllocationLine`, `OrderItem` нет
поля позиции, связи и запросы идут без `ORDER BY`. Внутри категории
материалы показываются в том порядке, в каком Postgres вернул строки, —
обычно порядок вставки, но строка, у которой меняли количество, может
уехать в конец. Каждый экран читает свой запрос, поэтому порядок ещё и
различается между конструктором, спецификацией, расчётом и ордером.

Сотрудники сверяют проект со своей сводной BOM-таблицей. На примере
Profil (2026-11-02) порядок в таблице совпал с нумерацией SKU каталога
(`PROF-002…PROF-059`: Open Back → Patio 2x2 → 2x3 → SMB 2"x6" → 7" → 10" →
Square Tube), а двери уже выглядят правильно по той же нумерации
(`DOOR-001…`). Пользователь подтвердил правило «по SKU, от меньшего к
большему» для всех категорий.

## Решение

Внутри категории материалы упорядочиваются по `Material.internal_sku`,
сравнение с числовой частью (`localeCompare(..., { numeric: true })`, так
что `X-99` < `X-100`, даже если номера когда-нибудь перестанут быть
трёхзначными). Категории — по-прежнему по `display_order` (ADR-0042),
"Без категории" и позиции без материала из каталога (lightweight
`OrderItem`, ADR-0033) — в конце, между собой в исходном порядке.

Правило одно, в `frontend/src/lib/groupByCategory.ts`, и применяется на
всех экранах, где выводится список материалов: конструктор проекта,
спецификация на экране проекта, панель шаблона, карточки поставщиков на
экране расчёта, таблица ордера и тексты для копирования поставщику.
Это порядок отображения, не данные: в БД ничего не пишется, миграции нет.
SKU экраны берут из уже загруженного каталога материалов
(`materialsApi.list`); панель шаблона каталог не загружает, поэтому
`ProjectTemplateItemOut` получает поле `internal_sku` (единственное
изменение backend).

Если порядок в какой-то категории должен отличаться от текущих номеров
SKU (например, Spline в Mesh сейчас `MESH-001…005` и идут перед сеткой, а
`.290`/`.285` — после `.325`), это решается перенумерацией SKU в каталоге,
не кодом.

## Альтернативы

- **Поле «порядок» у материала в каталоге** — гибче, но нужны миграция и
  UI для перестановки; при нынешней нумерации SKU избыточно. Можно ввести
  позже, если перенумерации SKU окажется недостаточно.
- **Порядок заполнения проекта (поле позиции у `ProjectItem`)** — зависит
  от того, как сотрудник заполнял, и требует протаскивать позицию через
  расчёт и ордер. Отклонено.
- **Сортировка на backend** в каждом эндпоинте — тот же результат, но
  конструктору всё равно нужна сортировка на фронте для строк, которые
  сотрудник добавляет на лету; два места для одного правила. Отклонено.

## Последствия

- Строка в конструкторе после выбора материала и сохранения встаёт на своё
  место по SKU внутри категории (раньше — в конец категории).
- Нумерация «№» в спецификации и в текстах для поставщика следует новому
  порядку.
- `docs/ui-reference.md` — правило добавлено к описанию группировки.
