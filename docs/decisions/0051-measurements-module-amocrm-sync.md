# ADR-0051: Модуль «Замеры» — read-only синхронизация с amoCRM и доступ по отдельному гранту

Статус: Предложено к утверждению

## Контекст

Нужно хранить и обновлять данные о замерах из amoCRM, чтобы отдельным ADR
построить дашборд. Источник — amoCRM API v4, только чтение.

Данные в amo (проверено пробными запросами 2026-11-09):

- С 2026-11-09 замеры ведутся задачами типов «Замер» (`4410970`) и
  «Доп. Замер» (`4410974`). На дату ADR задач этих типов нет.
- До перехода замерами были задачи «Встреча» (`2`) у замерщиков. Всего
  «Встреч» на сделках 1633: Nazar (`9861902`) — 1423 на 1327 сделках,
  Matt Measurement (`14156562`) — 67 на 64 сделках, все остальные
  ответственные — 143 на 124 сделках. Массового перевода старых задач в новые
  типы не будет, а на переходный период замеры ещё могут выставляться как
  «Встречи».
- Поле сделки Site Visit Result (`784029`) вводится вместе с переходом. За
  60 дней до ADR были только три тестовых события на сделке `25341615`,
  последнее — очистка.

Ограничения кода:

1. У пользователя одна роль, `admin` или `employee`. `require_role` сравнивает
   её точно.
2. `project`, `allocation`, `order`, `purchase_record` защищены только
   `get_current_user`, то есть любой ролью. Новое значение `User.role` получило
   бы эти роутеры и запись в `Price` по исключению ADR-0030.
3. `UserCreate`, `UserUpdate`, `UserRole` и `<select>` в `UsersPage` знают
   ровно два значения.
4. Uvicorn работает одним процессом, через него же идут импорты прайсов на
   13+ минут. Фоновой инфраструктуры нет.
5. `backend/.env` попадает и в контейнер `postgres`.
6. `RequireAuth` при любой ошибке `/auth/me` уводит на `/login`.
7. `User.is_active` проверяется только при входе.

Отдельная проблема: поле Site Visit Result одно на сделку, а замеров на ней
может быть несколько. Среди исторических «Встреч» на 137 из 1454 сделок (9,4%)
их больше одной.

## Решение

### 1. Изоляция

Пакет `backend/app/measurements/` содержит роутер, модели, клиент amo,
синхронизацию, атрибуцию и скрипты. Логику закупок он не импортирует. Роутер:
`/measurements` на backend, `/api/measurements` снаружи. Страница frontend:
`/measurements`. Таблицы с префиксом `measurements_`.

Точечные правки существующих файлов при реализации:

| Файл | Правка |
|---|---|
| `backend/app/main.py` | Условное подключение роутера с импортом внутри условия |
| `backend/app/models/__init__.py` | Импорт моделей, иначе `alembic --autogenerate` предложит удалить таблицы модуля |
| `docker-compose.yml` | Новый сервис под профилем |
| `.gitignore` | Строка для `backend/.env.measurements` |
| `frontend/src/App.tsx`, `AppLayout.tsx`, индекс маршрутов | Маршрут и пункт меню |

`require_role`, `get_current_user`, `/auth/me`, `MeOut`, `RequireAuth`,
`UserCreate`/`UserUpdate` и таблица `users` не меняются.

**Миграция.** Одна ревизия от `ea480577269c`: только `create_table`,
`create_index` и вставка начального маппинга в таблицу модуля, с полным
`downgrade`. Перечисления хранятся как `String` с `CHECK`, поэтому проблема
`ALTER TYPE ... ADD VALUE` не возникает. Единственное касание `users` — FK из
новой таблицы: краткая блокировка `SHARE ROW EXCLUSIVE` при создании, данные
не меняются.

**Отдельный процесс.** Контейнер `measurements-worker` собирается из образа
backend, команда `python -m app.measurements.worker`, профиль Compose
`measurements`, `restart: unless-stopped`. Основные сервисы от него не зависят.
Обычный цикл с `sleep`, новых зависимостей нет.

- Свой engine: `pool_size=2`, `max_overflow=0`, `statement_timeout`,
  `lock_timeout`, короткие транзакции.
- Единственность экземпляра и исключение параллельного бэкфилла — через
  `pg_try_advisory_lock`.

**Флаги**, оба по умолчанию `false`:

- `MEASUREMENTS_ENABLED`: при `false` все пути отдают 404, код модуля не
  загружается. Меняется пересозданием `backend`, это несколько секунд простоя.
- `MEASUREMENTS_SYNC_ENABLED`: опрос amo. Меняется без затрагивания `backend`.

### 2. Доступ

Логическая роль `measurements_viewer` реализована как **грант, а не значение
`User.role`**. Таблица `measurements_user_access`: `user_id` (PK, FK на
`users`, `ON DELETE CASCADE`), `granted_by_user_id`, `granted_at`.

Зависимость `require_measurements_access` в пакете модуля строится на
`get_current_user` и подключается на уровне всего `APIRouter`. Доступ есть,
если `is_active = true` и пользователь `admin` либо имеет грант. Этот ADR
**расширяет ADR-0024 §4 третьей категорией доступа**.

- `admin` получает доступ автоматически: он управляет доступами и мог бы выдать
  грант себе.
- В v1 грант выдаётся только `admin` и существующим пользователям закупок.
  Пользователям «только замеры» доступ не выдаётся (см. «Последствия»).
- Без гранта 403, без сессии 401.
- Frontend: компонент меню запрашивает `GET /measurements/access` (200 —
  показать, 403, 404 или ошибка — скрыть). Это UI-удобство, не граница
  безопасности.
- Выдача: `python -m app.measurements.scripts.grant_access --email …
  [--revoke] [--apply]`, по умолчанию dry-run. Экран в админке — позже.
- `result_text` хранится, но API модуля в v1 его не отдаёт.

### 3. Модель данных

ID из amo служат натуральными ключами `BigInteger` вместо `UUIDPKMixin`: upsert
идёт именно по ним. Жёстких FK между таблицами синхронизации нет, данные
приходят не по порядку. Upsert не откатывает строку назад
(`excluded.amo_updated_at >= amo_updated_at`).

| Таблица | Содержимое |
|---|---|
| `measurements_leads` | `lead_id` PK, `pipeline_id`, `status_id`, `site_visit_enum_id`, `closed_at`, `price` (`Numeric(12,3)`), `amo_updated_at`, `deleted_at`, `synced_at` |
| `measurements_visits` | `task_id` PK, `lead_id`, `task_type_id`, `kind` (`primary`/`additional`/`legacy`), `responsible_amo_user_id`, `scheduled_at` (начало замера, `complete_till`), `duration`, `is_all_day`, `is_completed`, `completed_at` (nullable, из `task_completed`), `result_text` (nullable), `amo_updated_at`, `deleted_at`, `deleted_reason` (`deleted`/`retyped`, nullable), `synced_at` |
| `measurements_amo_events` | `event_id` PK (`String(64)`), `event_type`, `entity_type`, `entity_id`, `lead_id` (nullable), `occurred_at`, `amo_user_id`, `value_before`/`value_after` (JSONB), `ingested_at`. Только `INSERT ... ON CONFLICT DO NOTHING` |
| `measurements_field_values` | `enum_id` PK, `label`, `sort`, `visit_occurred` (nullable), `outcome_type` (nullable), `is_active` |
| `measurements_result_attributions` | `id` PK, `event_id` (nullable, unique), `lead_id`, `task_id` (nullable), `rule`, `deadline_source` (`history`/`current`/null), `is_effective`, `rule_version`, `computed_at`. Производная таблица, полностью пересчитывается |
| `measurements_sync_state` | `stream` PK, `watermark_at`, `last_attempt_at`, `last_success_at`, `last_status`, `last_http_status`, `consecutive_failures`, `heartbeat_at`, `counters` (JSONB) |
| `measurements_user_access` | см. §2 |
| `measurements_amo_users` | `amo_user_id` PK, `name`, `is_active`, `synced_at`. Обновляется раз в час из `GET /api/v4/users` |
| `measurements_pipeline_statuses` | (`pipeline_id`, `status_id`) PK, `pipeline_name`, `status_name`, `sort`, `is_archived`, `synced_at`. Обновляется раз в час из `GET /api/v4/leads/pipelines`. Составной ключ обязателен: статусы `142`/`143` есть в каждой воронке |

`text` задачи не хранится: в нём детали клиента и инструкции по въезду.
`is_all_day = true`, только если срок приходится на 23:59 по New York и
`duration = 0`. `is_all_day` на расчёт привязки не влияет.

**Вид замера** определяется только по `task_type_id` и правилу legacy:

| `kind` | Условие |
|---|---|
| `primary` | `task_type_id = 4410970` |
| `additional` | `task_type_id = 4410974` |
| `legacy` | `task_type_id = 2`, ответственный входит в карту замерщиков из конфига (сейчас Nazar `9861902` и Matt Measurement `14156562`), и переходный период не закрыт: `legacy_meetings_until` не задан, **либо** `complete_till < legacy_meetings_until`, **либо** `created_at < legacy_meetings_until` |

Пока `legacy_meetings_until` не задан, все «Встречи» Nazar и Matt, включая
созданные после `cutover_at`, временно считаются замерами. Их число попадает в
счётчик `transition_meetings_counted` (созданы не раньше `cutover_at`), чтобы
было видно, когда переходный период можно закрывать. «Встречи» других
ответственных замерами не считаются.

Закрытие переходного периода — установка `legacy_meetings_until`. Условие
`created_at` сохраняет встречи, назначенные до этой даты на более поздний срок.
«Встреча» замерщика, созданная и назначенная после закрытия периода, не
считается замером и попадает в счётчик `post_cutover_meeting_ignored`.

Классификация пересчитывается на ночной сверке, поэтому изменение
`legacy_meetings_until` применяется к истории без миграции. Legacy-задача,
которая перестала подходить под условие (например, сменился ответственный),
получает `deleted_reason='retyped'`.

`kind` не определяет, применяется ли Site Visit Result: это решает срок замера
(см. правила привязки). Legacy-замеры со сроком до `cutover_at` получают исход
только по воронке и статусу сделки (правила — в ADR метрик). Legacy-замеры со
сроком не раньше `cutover_at`, то есть «Встречи» замерщиков переходного
периода, получают результат по Site Visit Result, как и новые типы.

**Маппинг** задан только по `enum_id`, `label` хранится для отображения и
обновляется синхронизацией:

| `enum_id` | Значение | `visit_occurred` | `outcome_type` |
|---|---|---|---|
| `627963` | Closed, Not Sold On-Site | true | `not_sold` |
| `627965` | Visit Completed (передан в продажу) | true | `completed` |
| `627967` | Sold On-Site | true | `sold` |
| `627969` | Declined Before Visit | false | `declined` |

Новый `enum_id` добавляется с `NULL`-маппингом. Синхронизация не перезаписывает
маппинг.

**Конфиг** (`MeasurementsSettings`, значения нужны только воркеру):

| Параметр | Значение |
|---|---|
| `field_id` | `784029` |
| `task_type_id` Замер / Доп. Замер / legacy | `4410970` / `4410974` / `2` |
| Карта замерщиков: аккаунт amo → человек, один к одному | `9861902` → Nazar, `14156562` → Matt Measurement |
| `pipeline_id` воронки замеров / продаж | `8740486` (Measurements) / `8740490` (Продажа) |
| `cutover_at` (переход и введение поля) | 2026-11-09, начало дня, `America/New_York` |
| `legacy_meetings_until` | Не задан, переходный период открыт |
| Таймзона | `America/New_York` |
| Исключённые `lead_id` | Пусто. Сделка `25341615` реальная, её тестовые события закончились очисткой |

Строки с исключёнными `lead_id` отбрасываются при приёме. `pipeline_id` не
ограничивает синхронизацию: замер определяется задачей, а сделка может быть в
любой воронке.

Карта замерщиков живёт только в конфиге. Новый аккаунт добавляется одной
записью, без миграции: `measurements_visits` хранит
`responsible_amo_user_id`, а человек определяется по карте. Классификация
применяет новую запись к истории на ближайшей ночной сверке.

**Правила привязки результата.** Детерминированная функция от всей истории
сделки, без LLM. Применяются к любому замеру без `deleted_at`, у которого
текущий `scheduled_at` не раньше `cutover_at`, независимо от `kind`, включая
«Встречи» замерщиков переходного периода. Это множество называется «подходящие
замеры», и слово «замер» в таблице ниже означает именно их. События идут по
`(occurred_at, event_id)`, дни считаются в `America/New_York`.

Срок замера на момент события: значение последнего `task_deadline_changed` до
события, иначе `value_before` первого изменения после него
(`deadline_source='history'`). Если изменений срока нет, берётся текущий
`scheduled_at` (`deadline_source='current'`).

| Правило | Условие | Результат |
|---|---|---|
| `cleared` | Пустой `value_after` при непустом `value_before` | Снимает результат с замера, у которого он был действующим |
| `same_or_past` | `visit_occurred=true` | Последний замер со сроком не позже дня события. Если в этот день их несколько: последний со сроком не позже времени события, иначе самый ранний за день |
| `early_entry` | `visit_occurred=true`, прошлых замеров нет | Ближайший будущий замер |
| `upcoming` | `visit_occurred=false` | Ближайший замер со сроком не раньше события и без состоявшегося результата |
| `late_decline` | `visit_occurred=false`, будущих нет | Последний прошедший замер |
| `snapshot_fallback` | Событий поля по сделке нет, в снимке значение есть | Последний замер, без `event_id` |
| `unmapped` | Маппинг `NULL` | Не привязывается, счётчик |
| `no_visit` | Подходящих замеров нет, в том числе если у сделки только замеры со сроком до `cutover_at` | Не привязывается, счётчик |

Действующим считается последнее привязанное событие на замере. При перезаписи
журнал не меняется, прежнее значение остаётся в истории. Пересчёт идёт по всей
сделке при любом её изменении, в одной транзакции. Если события есть, но
последнее расходится со снимком, увеличивается счётчик `drift`, значение не
подставляется.

| Сценарий | Итог |
|---|---|
| Замер 10.03 + `Visit Completed`, Доп. Замер 20.03 + `Sold On-Site` | У каждого свой результат |
| Замер 10.03, значение исправлено 12.03, Доп. Замера нет | Новое значение действует на том же замере |
| Замер 10.03, Доп. Замер 20.03, исправление 22.03 | Уходит на Доп. Замер. Ограничение принимается и видно по счётчикам |
| Замер перенесён с 10.03 на 15.03, `Declined Before Visit` от 09.03 | Привязка к той же задаче |
| Задача удалена или сменила тип | Сделка пересчитывается |
| «Встреча» замерщика со сроком не раньше `cutover_at`, поле заполнено | Получает результат по общим правилам, `kind` остаётся `legacy` |
| Legacy-замер со сроком до `cutover_at`, поле заполнено | Результат не привязывается, исход только по статусу сделки |

### 4. Синхронизация

Модуль выполняет только GET. Опрос раз в 5 минут, ночная сверка. Везде
`limit=250`, ответ 204 означает пустой результат. Свой ограничитель: 5 запросов
в секунду.

| Поток | Запрос | Что сохраняется |
|---|---|---|
| Задачи новых типов | `/tasks`: `filter[task_type][]` по двум типам + `filter[updated_at][from]` | Строки с `entity_type != 'leads'` отбрасываются у нас |
| Legacy | То же для типа `2`, действует и после `cutover_at` | Только подходящие под правило `legacy` |
| Поле | `/events`: `filter[type]=custom_field_784029_value_changed` | Все. Неизвестная сделка становится известной |
| Статусы | `filter[type]=lead_status_changed` | Только известные сделки |
| События задач | `task_deadline_changed`, `task_deleted`, `task_completed`, по запросу на тип | Только известные задачи |
| Смена типа | `task_type_changed` | Известная задача или вход в типы замера |
| Сделки | `/leads` пачками по 50, `filter[id][]` | Снимок |
| Справочники (раз в час) | `/leads/custom_fields`, `/users`, `/leads/pipelines` | Upsert |

Окно: перекрытие 2 минуты, идемпотентный upsert, watermark сдвигается только
после успеха всего окна.

**Хранение `lead_status_changed`.** Только по известным сделкам. Сделка,
впервые попавшая в модуль, получает всю свою историю через
`filter[entity]=lead`, поэтому хранение по всему аккаунту не добавляет данных и
наполняло бы таблицу сделками вне модуля.

**Догрузка истории при первом появлении:** для сделки
`filter[entity]=lead&filter[entity_id][]`, для задачи
`filter[entity]=task&filter[entity_id][]`. По одной сущности на запрос,
сохраняются только типы из таблицы выше.

**Смена типа.** На событие `task_type_changed` задача перечитывается через
`GET /tasks/{id}`:

- вышла из типов замера: `deleted_reason='retyped'`, сделка пересчитывается;
- стала замером: upsert и догрузка истории событий;
- вернулась в тип замера: запись восстанавливается.

**Статусы и ошибки.** 429 — экспоненциальная пауза с учётом `Retry-After`.
401/403 — статус `auth_failed` и остановка цикла опроса с редкими проверками.

**Бэкфилл:** `python -m app.measurements.scripts.backfill`, dry-run по
умолчанию, `--apply` для записи, держит тот же advisory lock. Берёт всю
доступную историю (подтверждено минимум 730 дней) для legacy и всё с
`cutover_at` для новых типов. Объём малый (1490 legacy-задач), дополнительные
окна не нужны. Печатает счётчики: задачи по `kind`, сделки, события по типам,
`unmapped`, `no_visit`, `drift`, `transition_meetings_counted`,
`post_cutover_meeting_ignored`.

**Ночная сверка** (03:30 New York): полный список типов `4410970`, `4410974`,
`2` сравнивается с локальным. Отсутствующая задача перечитывается по id: другой
тип — `retyped`, задача не существует — `deleted`, сверка не путает эти случаи.
Сделки проверяются по id. Если на удаление попадает больше 5% строк, сверка
прерывается и ничего не пишет. Здесь же пересчитываются `kind` и счётчики
`transition_meetings_counted`, `post_cutover_meeting_ignored`.

**Вебхук не используется.** Фаза 2 при необходимости: только сигнал «перечитай
сделку», payload не является источником данных.

### 5. Секреты

Для модуля выпускается отдельная приватная интеграция amo со своим долгоживущим
токеном, не общая с n8n и rc2amocrm: независимые лимит, ротация и отзыв. Срок
токена максимальный при выпуске, дата истечения фиксируется в
`docs/DEPLOYMENT.md`.

- `MEASUREMENTS_AMO_ACCESS_TOKEN` типа `SecretStr` лежит только в
  `backend/.env.measurements` на сервере и подключается только к
  `measurements-worker`.
- Файл добавляется в `.gitignore` до создания, проверка — `git check-ignore`.
- Токен передаётся только в заголовке. Логгер `httpx` поднят до WARNING. В
  `measurements_sync_state` пишутся только код статуса и класс ошибки.
- Ротация: заменить значение и выполнить
  `docker compose --profile measurements up -d --force-recreate measurements-worker`.
- При истечении или отзыве модуль показывает дату последней синхронизации,
  основное приложение не затронуто.

### 6. Вне рамок

Определения метрик и SQL, UI дашборда, вебхук, разделение доступа к закупкам.

## Альтернативы

| Вариант | Причина отказа |
|---|---|
| Значение `measurements_viewer` в `User.role` | Открывает операционные роутеры и запись в `Price`, исключает совмещение ролей |
| Массив или таблица ролей вместо `User.role` | Нужно менять `require_role` и все проверки ролей |
| Поле в `/auth/me` | Сбой модуля мог бы разлогинить всех |
| Планировщик внутри uvicorn | Дублируется при `--workers N`, делит процесс с ILP и импортами |
| `BackgroundTasks` FastAPI | Привязаны к запросу |
| Host cron | Запуск контейнера каждые 5 минут, наложения, нет heartbeat |
| Celery/RQ + Redis | Новая инфраструктура ради одной задачи |
| Привязка результата к последнему замеру | Теряет результат первичного замера, искажается при переносах |
| Вебхук как основной механизм | Нет гарантий доставки, публичный эндпоинт |
| Хранение `lead_status_changed` по всему аккаунту | Догрузка по сделке даёт те же данные |

## Последствия

- Появляется третья категория доступа к роутерам (дополнение к ADR-0024 §4).
- **Условие, блокирующее расширение доступа:** пользователям «только замеры»
  (лид-менеджеры, замерщики и другие) грант не выдаётся до отдельного ADR,
  который заменит `get_current_user` на `require_any_role("admin", "employee")`
  на роутерах `project`, `allocation`, `order`, `purchase_record`. Скрипт выдачи
  показывает `users.role` пользователя и напоминает об этом условии в dry-run.
- **Обнаруженный дефект основного приложения:** `User.is_active` проверяется
  только при входе (`app/auth/service.py:36`), поэтому деактивированный
  пользователь сохраняет доступ к закупкам до истечения сессии. Исправляется
  отдельным фиксом в `get_current_user` вне этого ADR. Будущая задача: ссылка
  будет добавлена при её заведении. Собственная проверка `is_active` в
  `require_measurements_access` защищает только этот модуль.
- Пока `legacy_meetings_until` не задан, временные «Встречи» замерщиков
  учитываются как замеры. Со сроком не раньше `cutover_at` они получают
  результат по Site Visit Result.
- Операционно добавляются контейнер, отдельная интеграция amo и файл секрета.
  Нужно обновить `docs/DEPLOYMENT.md`, `architecture.md`, `data-model.md`,
  `glossary.md`.
- Экран требует макета в Claude Design и раздела в `docs/ui-reference.md` до
  frontend-сессии.
- Нельзя без нового ADR: писать в amoCRM, использовать payload вебхука как
  данные, задавать маппинг исходов в коде, применять Site Visit Result к
  замерам со сроком до `cutover_at`.

## План отката

| Уровень | Действие | Влияние |
|---|---|---|
| 1 | `MEASUREMENTS_SYNC_ENABLED=false` или остановка контейнера | Данные замеров перестают обновляться |
| 2 | `MEASUREMENTS_ENABLED=false`, пересоздать `backend` | Короткий простой, API и пункт меню исчезают |
| 3 | После 1–2: выгрузить гранты, `alembic downgrade ea480577269c` | Данные модуля удаляются, восстанавливаются бэкфиллом |
| 4 | `git revert` правок | Закупки не затронуты |

## План выката

0. **Отдельная сессия разбора базовой линии** до backend-сессии модуля:
   классификация «окружение / реальный баг» с дословным выводом для 12 failed и
   2 errors pytest, 9 ошибок ruff и 1 ошибки vitest. Инфраструктура
   миграционных тестов должна работать до backend-сессии, иначе критерий
   `upgrade`/`downgrade`/`upgrade` непроверяем.
1. Миграция при выключенных флагах.
2. Выкат кода, проверка `docker compose config` на сервере.
3. Бэкфилл dry-run, сверка с amo, затем `--apply`.
4. Включение воркера.
5. Выдача грантов.
6. Включение API.

## Критерии приёмки

1. Базовая линия 2026-11-09 зафиксирована (pytest: 12 failed, 2 errors,
   851 passed; ruff: 9 ошибок; vitest: 608 passed, 1 необработанная ошибка;
   lint и build проходят) и разобрана на шаге 0 плана выката. После реализации
   нет новых падений, существующие тесты не менялись.
2. При выключенном флаге в OpenAPI нет путей `/measurements`, а поведение
   существующих эндпоинтов и страниц не меняется.
3. Тест обходит `app.routes` и проверяет защиту каждого маршрута
   `/measurements`: без сессии 401, `employee` без гранта 403, с грантом 200,
   `admin` 200, деактивированный пользователь с живой сессией 403.
4. Значения `users.role` и права существующих пользователей после миграции не
   меняются.
5. Миграция проходит `upgrade`, `downgrade`, `upgrade`, `alembic check` без
   расхождений.
6. Ответ API не содержит `result_text`.
7. Тесты привязки покрывают все правила и сценарии §3, `deadline_source`,
   классификацию `legacy` до и после закрытия переходного периода, границу
   применения поля по `cutover_at` (переходная «Встреча» с заполненным полем
   получает результат, legacy-замер со сроком до `cutover_at` не получает),
   счётчики `transition_meetings_counted` и `post_cutover_meeting_ignored`,
   повторный пересчёт даёт тот же результат.
8. Тесты клиента на моках: 204, 429, 401, пагинация, повторная доставка
   событий, смена типа в обе стороны, различение `deleted`/`retyped`,
   предохранитель сверки.
9. При недоступном amo и неверном токене основное приложение работает, статус
   модуля отражает сбой.
10. Два одновременных запуска воркера или воркер с бэкфиллом не работают
    параллельно.
11. Токена нет в git, логах, БД и в `docker inspect` контейнеров `backend` и
    `postgres`.
12. Счётчики dry-run сверены с amo, включая чтение сделок пачками по 50.
