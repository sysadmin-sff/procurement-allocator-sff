# ADR-0053: Метрики замеров v1 — определения, исход legacy-замера, API

Статус: Принято (2026-11-10). Октябрьские цифры (критерий приёмки 3) приняты
владельцем.

## Контекст

ADR-0051 §6 отложил определения метрик на отдельный ADR. Модуль хранит замеры
(`measurements_visits`), события сделок и задач (`measurements_amo_events`) и
привязку Site Visit Result (`measurements_result_attributions`). Эндпоинтов
метрик нет.

Данные dev-БД на 2026-11-10 (агрегаты, read-only запросы):

- 1498 активных замеров: legacy 1489 (до `cutover_at` 1484, после 5),
  primary 9, additional 0. Удалённых и retyped нет, all-day нет, ответственных
  вне карты замерщиков нет.
- 18 групп «сделка + день NY + замерщик» с двумя задачами. В каждой оба замера
  выполнены, у 15 совпадает и время.
- Site Visit Result на реальных замерах не заполняется: 3 атрибуции, все от
  тестовых событий.
- 15 из 17 выходов из Measurements в Квалификацию/142 возвращаются в
  Measurements за ≤2 с (автоматика amo). Один выход возвращается через 3,4 дня,
  один — никогда.
- Исход legacy-замеров до `cutover_at` по правилам §3, по группам (1466):
  produced 1185, closed 43, not_held 67, no_data 171 (окно 81, сделка не была
  в Measurements 90).

Ограничения:

1. `measurer_map`, `cutover_at` и id воронок есть только в конфиге воркера.
   Правило деплоя (DEPLOYMENT.md, ADR-0051 §5) пропускает в `backend` только
   `MEASUREMENTS_ENABLED`, поэтому переопределения конфига до backend не
   доходят.
2. Все расчёты — на backend (CLAUDE.md, принцип 4).
3. Структурный тест маршрутов (`tests/measurements/test_access.py`) ожидает
   200 на голый GET каждого маршрута `/measurements` от пользователя с грантом.
4. Пересчёт производных данных идёт не в транзакции записи, а потоком
   `attribution` в конце цикла опроса (`sync.py:516-527`, отбор сделок —
   `_changed_lead_ids`, `sync.py:481-495`), ночной сверкой
   (`reconcile.py:204-205`) и бэкфиллом (`backfill.py:270`).
5. `alembic --autogenerate` без построчного ревью запрещён
   (`docs/known-issues.md`).

## Решение

### 1. Базовое множество и общие правила

- **Замер в метриках** — строка `measurements_visits` с `deleted_at IS NULL`,
  у которой есть строка в `measurements_visit_outcomes` (§3). Удалённые и
  retyped задачи, сделки из `excluded_lead_ids` и удалённые сделки
  (`measurements_leads.deleted_at`) строк не дают и не считаются нигде.
- **День замера** — дата текущего `scheduled_at` в `America/New_York` через
  `AT TIME ZONE`, а не фиксированное смещение. Переход на летнее и зимнее время
  учитывается сам: неделя 26.10–01.11.2026 (169 часов) считается за 7 дней.
- **Перенос** учитывается только по текущему `scheduled_at`: замер целиком
  переезжает в новую неделю или месяц. История переносов на метрики v1 не
  влияет.
- **Около полуночи** решает дата NY, а не UTC: 31.10 23:30 EDT
  (01.11 03:30 UTC) относится к 31.10.
- **All-day** (срок 23:59 NY, `duration = 0`) относится к своему дню и
  считается как обычный замер.
- **Неделя** — понедельник–воскресенье, **месяц** — календарный, по дате NY.
- **Замерщик** — `measurer_key` из `measurer_map` по
  `responsible_amo_user_id`; материализуется воркером (§3). Задача без ключа
  (ответственный не из карты, возможно только у primary и additional) входит в
  итог компании и в группу `measurer_key = null`.
- **Набор правил результата** определяется сроком, а не `kind`, в
  согласии с ADR-0051 §3:
  `scheduled_at >= cutover_at` — по Site Visit Result (`site_visit`), иначе —
  по воронке (`funnel`). Переходная «Встреча» после `cutover_at` идёт по
  `site_visit`, в разбивке остаётся `legacy`. Перенос замера через
  `cutover_at` меняет набор при пересчёте.
- **Группа дублей** — замеры с одинаковыми `lead_id`, днём NY и
  `measurer_key` (`NULL` — тоже ключ), независимо от времени:
  - основной — первый по (`scheduled_at`, `task_id`), остальные —
    `is_duplicate`;
  - метрики M1–M4 считают группу одним замером;
  - исход группы — исход основного; группа выполнена, если выполнен любой её
    замер; `kind` — по основному;
  - замеры разных замерщиков в один день на одной сделке — разные группы.

### 2. Метрики

Каждая метрика считается по замерщику, по компании и за весь диапазон.
Единица счёта — группа (§1).

| № | Метрика | Определение |
|---|---|---|
| M1 | Проведённые | Группа выполнена и: `funnel` — исход ≠ `not_held`; `site_visit` — действующий результат ≠ `declined` (результата нет — входит, видно в M6). Разбивка `primary`/`additional`/`legacy` |
| M2 | Запланированные | Группа не выполнена, исход ≠ `not_held`/`declined`. `upcoming`: `scheduled_at >= now()`; `overdue`: `scheduled_at < now()` |
| M3 | Замерные дни | Различные даты NY с ≥1 группой из M1. У компании — различные даты по всем замерщикам, не сумма |
| M4 | На замерный день | M1 / M3; при M3 = 0 — `null` |
| M5 | Среднее в неделю | M1 / (D / 7). D — длина периода в днях. У периода, содержащего сегодняшний день NY, D — дни от начала периода по сегодня включительно; у будущих периодов D = 0 и значение `null` |
| M6 | Качество данных | `without_site_visit_result {completed, not_completed}` — прошедшие группы `site_visit` без действующего результата; `no_outcome` — **выполненные** прошедшие группы `funnel` с `no_data` (невыполненные уже учтены в `overdue`); `duplicates` — число замеров с `is_duplicate` по дню замера |

- Отношения считаются на backend в `Decimal`, 2 знака, `ROUND_HALF_UP`; в
  ответе — строки.
- `is_partial = true` только у периода, содержащего сегодняшний день NY. У
  итога за диапазон — если такой период в нём есть.
- Выполненный замер с будущим `scheduled_at` входит в M1 своего дня (сейчас
  таких 0).

### 3. Исход legacy-замера и хранение

**Выход из Measurements** — событие `lead_status_changed`, у которого
`value_before.pipeline_id = 8740486`, и при этом неверно, что одновременно
`value_after.pipeline_id = 8740486` и `value_after.status_id ∉ {142, 143}`.
Переходы между стадиями Measurements, включая удалённую `77511290`, выходом не
являются.

**Прозрачный выход** — выход в `8740374/142`, после которого (по
`(occurred_at, event_id)`) в тот же день NY есть вход в `8740486` из другой
воронки. Он не является исходом, поиск выхода продолжается. Прочие выходы в
Квалификацию с возвратом в тот же день прозрачными не считаются: задержки у них
от 1 с до нескольких часов (v2).

**Окно** — от дня замера до ближайшего более позднего дня, в который на сделке
есть замер любого `kind`; этот день не включается. Замеры одного дня делят
окно. У последнего дня сделки верхней границы нет.

**Исход** — первый непрозрачный выход в окне по `(occurred_at, event_id)`,
сравнение по дню NY:

- `produced` — `142` в Measurements или переход в Продажу `8740490`;
- `closed` — `143` в Measurements;
- `not_held` — переход в Квалификацию `8740374`, любая стадия;
- `no_data` — выхода в окне нет (`no_data_reason = window`) или сделка не была
  в Measurements (`never_in_measurements`);
- выход в другую воронку — `no_data` (`window`) и счётчик `other_exit`
  (сейчас 0).

Исход вычисляется только для `funnel`. В M1 не входит только `not_held`.

**Хранение — материализация** в новой производной таблице
`measurements_visit_outcomes`:

- Исход и группы считает чистая функция в `app/measurements/outcomes.py` по

**Обязательная часть реализации:**

1. Срабатывание предохранителя сверки (`reconcile.py:155-166`): перед
   `ReconcileAborted` пересчитать все сделки, а не только
   переклассифицированные. Пересчёт работает только с нашей БД, а
   предохранитель защищает от удалений, выведенных из ответов amo. Иначе смена
   `measurer_map`, `cutover_at`, маппинга `field_values` или `rule_version` не
   применится до первой успешной сверки.
2. `recompute_lead` для сделки из `excluded_lead_ids` или с `deleted_at`
   удаляет её производные строки (атрибуции и исходы) и новых не пишет. Сейчас
   ни один путь не убирает строки сделки, исключённой после приёма.
3. Скрипт `python -m app.measurements.scripts.recompute`: dry-run по
   умолчанию, `--apply`, тот же advisory lock, все сделки. Нужен для первичного
   заполнения и для смены `rule_version` при `MEASUREMENTS_SYNC_ENABLED=false`,
   когда воркер не пересчитывает ничего (`worker.py:156-159`).
4. Ответ метрик и `/measurements/status` отдают `outcomes_stale` — число строк
   с `rule_version` меньше текущего.

Производные строки отстают от записи замера на часть цикла (поток
`attribution` идёт последним в том же цикле). `is_completed` читается из
`measurements_visits` напрямую.

**Таймзона** — константа модуля `America/New_York`. Её читают воркер
(`sync.py:240`, `backfill.py:226`, `attribution_store.py:114`, `worker.py:262`)
и backend. `MeasurementsSettings.timezone` удаляется (ADR-0051, «Изменение
2026-11-10 (ADR-0053)»).

### 4. Где считаются метрики

SQL через SQLAlchemy Core в `backend/app/measurements/metrics.py` по
`measurements_visit_outcomes` с соединением на `measurements_visits`
(`is_completed`, `scheduled_at`, `kind`). Отношения досчитываются в Python в
`Decimal`. Представлений БД нет. Индексов на `measurements_visits` v1 не
добавляет: 1,5 тыс. строк.

### 5. API

Новые маршруты — в существующем роутере модуля с
`require_measurements_access` на уровне `APIRouter`, поэтому их покрывает
существующий структурный тест маршрутов. У всех параметров есть значения по
умолчанию.

`GET /measurements/metrics`

| Параметр | По умолчанию | Правило |
|---|---|---|
| `from` | первое число текущего месяца NY | `week` — сдвиг назад до понедельника; `month` — до 1-го числа |
| `to` | сегодня NY | `week` — сдвиг вперёд до воскресенья; `month` — до последнего дня месяца |
| `group_by` | `month` | `week` \| `month`, иначе 422 |
| `measurer` | все | неизвестный ключ — 200 с нулями |

Запрос с `from > to` или с запрошенным диапазоном больше 366 дней (до
выравнивания) — 422. Ответ возвращает и запрошенные, и фактические границы.

```json
{
  "timezone": "America/New_York",
  "requested": {"from": "2026-10-01", "to": "2026-10-31"},
  "from": "2026-09-28", "to": "2026-11-01", "group_by": "week",
  "data_as_of": "<max last_success_at>",
  "outcomes_stale": 0,
  "periods": [
    {"period_start": "2026-09-28", "period_end": "2026-10-04", "days": 7,
     "is_partial": false,
     "company": {"<metrics>": "..."},
     "measurers": [{"measurer_key": "Nazar", "<metrics>": "..."},
                   {"measurer_key": null, "<metrics>": "..."}]}
  ],
  "total": {"days": 35, "is_partial": false, "company": {}, "measurers": []}
}
```

`<metrics>`: `conducted {total, primary, additional, legacy}`,
`planned {upcoming, overdue}`, `visit_days`, `per_visit_day`,
`per_week_avg`, `data_quality {without_site_visit_result {completed,
not_completed}, no_outcome, duplicates}`. Только агрегаты.

`GET /measurements/metrics/visits` — детализация. Параметры `from`, `to`
(без выравнивания), `measurer`, `kind`, `limit` (по умолчанию 200, максимум
1000). Поля: `task_id`, `lead_id`, `local_date`, `measurer_key`, `kind`,
`result_source`, `outcome`, `is_completed`, `is_duplicate`. Без названий
сделок, `result_text` и `price`.

## Альтернативы

| Вариант | Причина отказа |
|---|---|
| Исход «на лету» в SQL запроса | ~235 мс на dev — по скорости допустимо, но backend не знает конфиг воркера (id воронок, `cutover_at`, `measurer_map`). Логика дублировалась бы в SQL рядом с Python-атрибуцией; нет `rule_version` и события-источника |
| Исход в колонках `measurements_visits` | Смешивает строку синхронизации из amo с производными данными; upsert и пересчёт писали бы одну строку |
| `measurer_key` из конфига на backend | Переопределение карты до backend не доходит, метрики разошлись бы с классификацией воркера |
| Представления БД | Каждая правка формулы — миграция; усугубляет известный дрейф моделей; параметры периода всё равно в коде |
| Окно «до дня следующего замера» буквально | У замеров одного дня окно первого пустое: на dev 16 замеров меняли исход |
| Сравнение выхода по моменту | Терялись 304 замера с выходом в тот же день, но раньше часа срока |
| Считать дубли отдельными замерами | 18 лишних замеров в истории, 15 — с тем же временем |
| Прозрачность любого выхода с возвратом в тот же день | Возвраты из прочих стадий Квалификации растянуты до часов и похожи на ручные; без данных о причинах — v2 |
| `no_outcome` включает невыполненные | Двойной учёт с `overdue` |
| Пересчёт в транзакции записи | Меняет устройство цикла опроса; поток `attribution` того же цикла даёт задержку в секунды |
| Знаменатель M5 — полная длина текущего периода | Среднее в начале месяца занижено в разы |

## Уточнения реализации (2026-11-11)

Приняты на ревью этапов 0–4 и имеют приоритет над текстом выше.

- **Id Квалификации в конфиге.** `MeasurementsSettings.pipeline_qualification_id`
  (по умолчанию `8740374`) рядом с `pipeline_measurements_id` и
  `pipeline_sales_id` (ограничение 1).
- **`never_in_measurements`.** Сделка не была в Measurements, если ни одно её
  событие `lead_status_changed` не касается воронки `8740486` ни в
  `value_before`, ни в `value_after`, и снимок сделки
  (`measurements_leads.pipeline_id`) не в `8740486`. В остальных случаях `no_data`
  без выхода в окне — `window`.
- **Исход группы дублей (уточнение §1).** Для `funnel` исход группы — исход
  основного замера: окно у замеров одного дня общее. Для `site_visit` исход
  группы — действующий результат любого замера группы; если результатов
  несколько, берётся результат с наиболее поздним событием атрибуции по
  (`occurred_at`, `event_id`). Результат из снимка (`snapshot_fallback`, без
  события) уступает любому событию. Причина: при нескольких замерах в день
  события правило `same_or_past` отдаёт результат последнему замеру, и при
  исходе «по основному» результат дубля терялся, а «Declined Before Visit»
  засчитывался бы проведённым. Колонки исхода в `measurements_visit_outcomes`
  у всех замеров группы — исход группы. `rule_version` исходов — `2`.
- **`other_exit`.** Колонки нет. Число групп с выходом в другую воронку
  печатается только в выводе скрипта `recompute`.
- **`outcomes_stale`.** В `/measurements/status` — поле верхнего уровня ответа,
  рядом с `counts`.

## Изменение 2026-11-11 (Deal Number)

Решение владельца после просмотра экрана «Замеры»: в детализации нужен номер
сделки из поля amo **Deal Number** — по нему сделку ищут в работе удобнее, чем
по `lead_id`.

- **Хранение.** Новая колонка `measurements_leads.deal_number` (`String(64)`,
  nullable) — снимок поля, как `site_visit_enum_id`. Пишется тем же upsert
  сделки (`sync._upsert_lead`) в опросе, бэкфилле и ночной сверке; пустое
  значение и отсутствие поля — `NULL`. Ранее загруженные сделки получают номер
  на ближайшей ночной сверке (она перечитывает все известные сделки) или при
  повторном бэкфилле. Новая ревизия поверх `a83d51c07e94`.
- **Конфиг воркера.** `MeasurementsSettings.deal_number_field_id` — id поля в
  amo, рядом с `field_id` (Site Visit Result). Пока `None`, поле не читается и
  колонка остаётся `NULL`.
- **API (§5).** `GET /measurements/metrics/visits` отдаёт `deal_number`
  (`str | null`) — номер берётся из `measurements_leads` по `lead_id`. Это
  идентификатор сделки, как `lead_id`, а не данные клиента: запрет §5 на
  названия сделок, `result_text` и `price` не меняется. **Допущение,
  требует подтверждения владельца:** в Deal Number нет имени, адреса или
  телефона клиента. Если есть — поле убирается из ответа.
- **Метрики не меняются**: номер только отображается в детализации.
