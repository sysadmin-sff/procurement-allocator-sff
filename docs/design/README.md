# Handoff: Закупки Screen Factory — импорт прайсов, проект, расчёт закупки

## Overview
Три экрана внутреннего инструмента закупок подрядчика по монтажу screen enclosures (Флорида):

1. **Импорт прайс-листа (ревью)** — оператор проверяет строки, распознанные из PDF прайса поставщика, сопоставляет их с материалами в базе, одобряет/отклоняет, применяет одобренные цены.
2. **Создание проекта** — быстрый клавиатурный ввод спецификации материалов проекта (материал + количество).
3. **Результат расчёта закупки** — алгоритм разложил спецификацию по поставщикам с учётом цен, наличия и порогов бесплатной доставки; оператор видит обоснование выбора, может вручную переназначить поставщика строки, обязан закрыть дефицит, затем создаёт ордера.

Сквозная логика: **прайсы (1) → спецификация проекта (2) → план закупки и ордера (3)**.

## About the Design Files
Файлы в `design/` — это **дизайн-референсы, сделанные в HTML**. Это прототипы, показывающие целевой внешний вид и поведение, **а не production-код для копирования**. Задача: **воспроизвести эти экраны в целевой кодовой базе** (React/Vue/Svelte/native — что используется в проекте), опираясь на её существующие паттерны, компоненты и библиотеки. Если кодовой базы ещё нет — выбрать подходящий стек и реализовать экраны в нём.

Технические особенности прототипов, которые НЕ надо переносить:
- Разметка — шаблоны в собственном мини-формате (`<x-dc>`, `<sc-for>`, `<sc-if>`, `{{ hole }}`) плюс класс логики. `support.js` — рантайм прототипа, в продукт не нужен.
- Все стили — инлайновые (ограничение среды прототипирования). В продукте используйте нормальные компоненты/стили/токены.
- Данные (`CATALOG`, `DATA`, `ITEMS`, `SUP`) — моки, демонстрирующие форму данных и краевые случаи. Реальные данные приходят из API.

Как читать файл: шаблон между `<x-dc>` и `</x-dc>` — это разметка (`<sc-for list="{{ rows }}">` = `rows.map(...)`, `<sc-if value="{{ x }}">` = условный рендер); класс `Component` внизу — состояние и вычисления, `renderVals()` возвращает всё, что подставляется в шаблон.

## Fidelity
**High-fidelity.** Финальные цвета, типографика, отступы, состояния и интерактив. UI воспроизводить пиксельно точно, средствами существующей библиотеки компонентов. Копирайт (все русские тексты, лейблы, тултипы, пустые состояния) — финальный, брать дословно.

### Поведение
- Строки отсортированы по возрастанию уверенности (**сначала самые сомнительные**).

- Счётчик «одобрено» = строки с действием `approve` **или** `new`; прогресс-бар и активность primary-кнопки зависят от него.
- Клик по кнопке материала или по `⤢` делает строку активной в PDF-панели.
- `Применить одобренные` → состояние «всё обработано» (в продукте: отправка на бэкенд + журнал изменений).

### State
`view: 'review'|'empty'|'done'` (в продукте — роутинг/данные, не переключатель), `rows[{id, raw, sku, page, conf, material, price, prev, stock, lead, action: null|'approve'|'reject'|'new', selected}]`, `activeId`, `pickerId`, `query`.

### Data / API
Строка импорта: `raw` (сырой текст из PDF), `sku`, `page`, `conf` 0…1 (скор матчинга), `material` (ссылка на материал базы или null), `price`, `prev` (текущая цена в базе или null), `stock`, `lead`. Нужны: список строк импорта с пагинацией, поиск по каталогу материалов, создание материала из строки, bulk-применение решений.

### Алгоритм и поведение (важно повторить в бэкенде)
- **Назначение поставщика**: по умолчанию `base` (консолидированный план). Стратегия `lowest_unit` (проп) — минимальная цена среди поставщиков, у которых достаточно наличия.
- **Доступность**: поставщик может быть выбран для позиции только если `available >= qty`.
- **Группировка**: позиции группируются по назначенному поставщику; группы сортируются по убыванию суммы товаров.
- **Доставка**: `sub >= supplier.free ? 0 : supplier.ship`. Итог = товары + доставка.
- **Обоснование строки**: если есть более дешёвый доступный поставщик — считается «дороже на (Δцены × qty)» и пересчитывается полный итог плана при переносе позиции к нему; если полный итог вырос — объясняем экономией на консолидации доставки, если упал — прямо говорим о возможной экономии.
- **Ручное переопределение** поставщика строки мгновенно пересчитывает группы, доставку и итог; помечает строку и группу бейджем «вручную»; сбрасывает подтверждение.
- **Отклонение от алгоритма**: сравнение текущего итога с итогом базового плана; показывается при разнице > $0.005, кнопка сбрасывает все переопределения.
- **Дефицит**: `open` → `split` (позиция разбивается на две частичные строки: 3 рул. по $231.00 у Phifer + 2 рул. по $238.00 у Gulf Coast) или `excluded` (позиция уходит из плана). Ордера можно создать только из `excluded` (в реальном продукте — из любого состояния, где дефицита нет).
- **`⌘↵` / `Ctrl+Enter`** — подтвердить создание ордеров (работает только когда не заблокировано).

### State
`overrides: {itemId: supplierId}`, `shortage: 'open'|'split'|'excluded'`, `confirmed: boolean`. Пропы: `strategy: 'consolidated'|'lowest_unit'`, `showAltPrice: boolean`.

### Data / API
Поставщик: `{id, name, short, ship, free, meta}`. Позиция: `{id, name, spec, unit, qty, base, offers: {supplierId: {price, available}}}`. Нужны: расчёт плана (сервер), пересчёт при переопределении, создание ордеров, CSV-экспорт.
