## Массовое применение строк ревью прайс-листа не применяет часть выбранных (подтверждено критично, требует обсуждения)

Обнаружено при первом реальном использовании экрана ревью после
ADR-0019/0021/0022/0023, на импорте 699 строк.

**Наблюдаемая последовательность:**
1. Пользователь выбрал строки, нажал "Применить выбранные".
2. После первого нажатия часть строк осталась неприменённой — на
   экране показано "699 строк · выбрано к применению: 134".
3. Пользователь нажал "Применить выбранные" повторно.
4. Результат: "Применено 0 из 134" — ни одна из 134 выбранных строк не
   применилась на этот раз.
5. Как минимум одна строка из этих 134 (confidence 68%, "14 X 2 (5/16)
   TPK (100-PK 1000-BX)", $18.87) показывает статус действия
   "ПРОПУЩЕНО" — неясно, это отражение реального решения пользователя
   (строка была явно пропущена ранее) или ошибочная маркировка
   результата неудачного apply-вызова как "пропущено" вместо явной
   ошибки.

**Не выяснено (требует диагностики, не диагностировано на месте по
явному решению пользователя — сначала обсуждение, не дальнейшая ручная
отладка):**
- Падают ли сами `POST .../entries/{entry_id}/apply` вызовы (сетевая
  ошибка, 422/500) и это тихо интерпretируется фронтом как "пропущено",
  или reactive-состояние чекбоксов на экране рассинхронизировалось
  между двумя нажатиями (например, второе "Применить" сработало по
  устаrevшему списку "выбранных", не совпadающему с тем, что реально
  видно на экране).
- Является ли проблема специфичной для большого объёма (699 строк) —
  например, цикл вызовов apply прерывается частично на середине без
  явного сообщения об ошибке, или частота проявления не зависит от
  объёма.
- Связь с недавней доработкой параллелизации/дедупликации (ADR-0021-
  0023) — эти изменения трогали backend price_ingestion, но не
  затрагивали сам apply-эндпоинт (ADR-0019 §5) впрямую; требует
  проверки, не предположения.

**Статус:** пользователь прекратил дальнейшее использование этого
экрана до обсуждения с командой (см. также отдельный открытый вопрос —
пересмотр самого UX-подхода: возможно, нужно разделить "обновление цен
по уже известному каталогу" и "поиск новых позиций" на два разных,
более узких сценария вместо одного экрана на весь прайс-лист сразу,
чтобы не требовать ревью сотен строк за раз).

**Условие возврата:** после обсуждения с командой — если решено
продолжать в текущем виде экрана, эта проблема блокирует использование
и должна быть продиагностирована первой (воспроизвести на файле поменьше,
проверить сетевые ответы apply-вызовов в браузере, проверить
согласованность фронтенд-состояния между двумя последовательными
нажатиями "Применить выбранные").
