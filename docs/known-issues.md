# Known issues / отложено

## Гигиена тестовых данных на общей dev-БД (2026-09-16, обнаружено при финальной проверке перед мержем ADR-0034)

Backend test suite гоняется против **живой, общей dev PostgreSQL БД**
(`SessionLocal()` напрямую), не изолированной тестовой БД. Два независимых
пробела в очистке, найденные при полном прогоне `pytest` перед мержем
ветки `adr-0034-category-entity-sku-autogen` в `main`:

**1. `tests/auth/conftest.py`/`bootstrap_admin` — тесты падают, если на БД
уже есть реальный admin.** `bootstrap_admin` (`app/auth/service.py:111`)
возвращается рано, если `role == "admin"` уже существует хоть один —
корректное поведение для прода, но тесты `tests/auth/test_service.py`/
`tests/scripts/test_bootstrap_admin.py`/
`test_self_deactivation_of_last_active_admin_returns_409` предполагают
пустую БД без единого admin. Как только на dev-БД появился настоящий
постоянный admin (`sysadmin@screen-factory-florida.com`) — эти 5 тестов
падают systematically, не из-за регрессии кода.

**Дополнительно, причина найдена и исправлена в этой же сессии (см. §3
ниже) — не "причина не найдена", как было написано здесь изначально.**
Полный прогон suite создавал ~111 тестовых `User`-строк
(`employee-order1@...`, `confirm-price-user1@...` и т.д.), которые
оставались в БД после прогона, хотя все тесты проходили (`passed`, не
`failed`) — то есть `finally`-блок teardown реально выполнялся до конца,
но не удалял пользователей. Причина — опечатка в распаковке кортежа
`db_session` в `tests/allocation/conftest.py:110` (`make_user`), из-за
которой переменная `user_ids` внутри `make_user` указывала не на тот
список, что реальный `user_ids` в teardown, — созданные пользователи
накапливались в чужом списке (`category_ids`), реальный `user_ids`
оставался пустым, `if user_ids:` в teardown не срабатывал никогда.
Подробности и разбор всего класса этой проблемы — §3 ниже. Исправлено
там же.

**2. Найдено и очищено в этой сессии: 13 "Test Project" деревьев,
накопленных за несколько более ранних прогонов того же дня (метки времени
01:39–13:41), включая связанные `purchase_records`, `orders`/`order_items`,
`allocation_runs`/`allocation_lines`, 5 материалов `TEST-SKU-*` и 5
категорий `Test Category *`.** Все явно синтетические (совпадают с
дефолтными именами тестовых фикстур, ни одно не пересекается с двумя
реальными проектами `20675`/`#4665`) — проверено и удалено вручную,
пошагово, в правильном FK-порядке, с явным подтверждением пользователя
перед каждым удалением. **Найден реальный пробел в самом коде очистки**:
`tests/allocation/conftest.py`, `db_session` teardown (строки 46-80) не
обрабатывает `purchase_records.project_id` вообще — если тест этого файла
когда-либо создаёт `PurchaseRecord`, привязанный к тестовому `Project`, и
доходит до teardown, `DELETE FROM projects` упадёт `ForeignKeyViolation`
(`purchase_records_project_id_fkey`), teardown прервётся до
`session.commit()`, и все накопленные к этому моменту строки (проект,
ордера, allocation run, материалы) останутся в БД без отката — то же
следствие, что и пробел №1 выше, другой недостающий FK. **Не исправлено в
коде этой сессией** (сама очистка данных на БД была сделана, добавление
`purchase_records` в teardown-цепочку — нет) — исправление тривиально
(добавить `session.query(PurchaseRecord).filter_by(project_id=project_id)
.delete(...)` перед `session.query(Project)...delete(...)`), но не входило
в объём финальной проверки ADR-0034, оставлено как открытый пункт.

**3. Найдена и исправлена в этой сессии: хрупкая звёздочная распаковка
кортежа `db_session` в нескольких `conftest.py` — один реально сломанный
случай (см. §1 выше), остальные пять хрупких по конструкции, но
случайно корректных на сегодняшней форме кортежа.** Каждый `db_session`
в проекте (14 независимо продублированных фикстур с одинаковым именем,
не общий хелпер) — обычный Python-кортеж `(session, project_ids,
material_ids, ...)`, не именованная структура. Несколько `make_user`/
`make_material` в разных файлах распаковывали его через `session, *_rest,
user_ids = db_session` (или симметрично `session, material_ids, *_rest =
db_session`) вместо явного перечисления всех позиций по именам —
компактнее писать, но `*_rest` привязывает последнюю/первую переменную
к последнему/первому элементу **фактического** кортежа, не к
семантически предназначенной позиции. Если в каком-то файле кортеж
`db_session` длиннее, чем `user_ids` как его предпоследний/непоследний
элемент (ровно так и произошло в `tests/allocation/conftest.py`, где
после `user_ids` при реализации ADR-0034 добавился `category_ids`) —
`*_rest` тихо поглощает лишний элемент, а именованная переменная
получает не то значение, без любой ошибки на этапе выполнения
(`TypeError`/`ValueError` здесь в принципе не возникает — распаковка
переменной длины валидна синтаксически при любом достаточном количестве
элементов).

**Grep по всему `tests/` на паттерн `*_rest`/аналогичную звёздочную
распаковку `= db_session` (кроме безопасной формы `session, *_ =
db_session`, которая просто отбрасывает остаток и не может присвоить не
туда) — нашёл 6 вхождений в 5 файлах:**

```
tests/allocation/conftest.py:110           make_user   — РЕАЛЬНО СЛОМАН (см. §1)
tests/order_response_parser/conftest.py:76 make_user   — хрупкий, пока корректный
tests/price/conftest.py:70                 make_user   — хрупкий, пока корректный
tests/purchase_record/conftest.py:113      make_user   — хрупкий, пока корректный
tests/template/conftest.py:86              make_user   — хрупкий, пока корректный
tests/template/conftest.py:156             make_material — хрупкий, пока корректный
```

Для каждого из 5 "хрупких, пока корректных" случаев фактическая форма
кортежа `db_session` в соответствующем `conftest.py` сегодня такая, что
`user_ids`/`material_ids` действительно является последним/первым
элементом — то есть распаковка сейчас даёт верный результат, но перестанет
быть верной, если кто-то (как уже случилось в `allocation/conftest.py`)
добавит новый трекинг-список рядом с `user_ids` в будущем — тот же класс
ошибки повторится молча, без предупреждения на этапе код-ревью, если не
знать про этот прецедент.

**Исправлено — все 6 переписаны на явную позиционную распаковку по
именам, без `*`:**

```python
# было (allocation/conftest.py:110, реально сломано):
session, *_rest, user_ids = db_session

# стало:
session, _project_ids, _material_ids, _supplier_ids, user_ids, _category_ids = db_session
```

Симметрично для остальных 4 файлов и второго вхождения в
`template/conftest.py`. Полный тест-сьют прогнан заново после правки —
см. результат под этой записью/в истории коммитов.

**Не сделано в этой сессии, осознанно отложено: структурный рефакторинг
`db_session` из голого кортежа в именованную структуру (`dataclass`/
`NamedTuple` с полями `session`, `project_ids`, `material_ids`, ...),
который сделал бы весь класс этой ошибки структурно невозможным** (любая
опечатка в имени поля дала бы `AttributeError` сразу, а не тихую
подмену значения). Причина отложить: 14 независимо продублированных
`db_session`-фикстур, и почти каждая функция в соответствующих
`test_*.py`/`conftest.py` файлах распаковывает `db_session` хотя бы раз
(включая безопасную форму `session, *_ = db_session`, которую тоже
пришлось бы переписать на `.session`, если убирать кортеж полностью) —
это рефакторинг в духе "переписать сотни строк почти во всех тестовых
файлах backend", с реальным риском внести новую ошибку в конце уже
длинной сессии, ради устранения класса проблемы, у которой сейчас
подтверждён ровно один живой случай (уже исправленный) и пять
потенциальных (тоже уже исправленных точечно). **Условие возврата**:
если тот же класс ошибки (пропущенное поле при расширении кортежа
`db_session`) проявится снова в новом месте — это будет второй
независимый сигнал за короткое время, тогда стоит вернуться и сделать
структурный рефакторинг, а не чинить по одному вхождению.

## ИНЦИДЕНТ (2026-09-16): живой alembic-тест уничтожил Category/Material.category_id на dev-БД во время реализации ADR-0034

**Не "восстановлено успешно" — восстановлено эвристикой без независимого
подтверждения на уровне отдельных материалов.** Читай это целиком, не
только заголовок, прежде чем полагаться на текущие `categories`/
`materials.category_id` как на факт.

### Что произошло

Во время реализации ADR-0034 (сессия `d9847b2b-b4d4-4f61-a7f3-bb73aabe2cde`,
2026-09-15 21:11 UTC — 2026-09-16 08:35 UTC, коммит `a73ae95`) полный
прогон backend test suite вызвал `backend/tests/allocation/
test_order_item_migration.py` в его тогдашнем виде — этот файл гонял
**настоящий** `alembic.command.downgrade("-1")` / `command.upgrade("head")`
(ADR-0033, тест на guard понижения `a7c3e9f21b04`) напротив **общей dev-БД**,
не изолированной тестовой. Тест был написан и безопасен, когда
`a7c3e9f21b04` была последней миграцией: `"-1"` от `head` понижал ровно её.
После того как в этой же сессии сверху добавились две миграции ADR-0034
(`a54edb312c7c` — добавление `categories`/`category_id` nullable,
`2d4335886fd3` — `category_id NOT NULL` + `DROP COLUMN materials.category`),
`"-1"` от нового `head` стал понижать **чужую, более новую миграцию**, не ту,
на которую тест был рассчитан — и переход вниз/вверх прошёл через
двухфазную миграцию ADR-0034, чей `downgrade()` **документированно
лоссовый** (восстанавливает форму колонки `materials.category`, но не её
исходные строковые значения — то же решение, что и `1d82548b7a2c` для
`created_by`). Итог: все 294 материала получили `category = NULL` на живой
БД, строки `categories` были удалены целиком (id/`created_at` потеряны).
Полный пошаговый разбор — в git-истории коммита `a73ae95` (сообщение
коммита) и в scrollback сессии `d9847b2b...` (~строки 1368-1620).

### Как было восстановлено — эвристика, не побайтовое восстановление

`internal_sku` каждого материала (`{sku_prefix}-{NNN}`, например `DOOR-014`)
пережил инцидент нетронутым — колонка `category` (String) была уничтожена,
но `internal_sku` не участвовал в откате миграции ADR-0034. Восстановление:
для каждого материала `category_id` выведен **заново из префикса
`internal_sku`** через тот же словарь `CATEGORY_SKU_PREFIX`
(`xlsx_price_matrix.py`), что и сам backfill-скрипт — не восстановлен из
резервной копии исходной строки `category`, потому что такой копии не
существовало на момент инцидента (см. ниже про dry-run отчёт).

**Ключевое допущение, на котором стоит вся реконструкция: SKU-префикс
материала однозначно соответствует его категории (1:1), и так было
всегда.** Подтверждено по построению для исходного xlsx-импорта (294
материала, 8 категорий, ADR-0028/ADR-0034 контекст). Не подтверждено (и не
могло быть, из-за самого инцидента) для любого материала, который к
моменту инцидента мог быть вручную переклассифицирован в категорию, не
совпадающую с префиксом его исторического SKU — на момент инцидента такой
функциональности (переклассификация `category_id` без смены `internal_sku`,
ADR-0034 п.4) в реальном UI ещё не существовало, поэтому такого случая,
предположительно, не было. **Это предположение, не проверенный факт.**

совпадение доказывает только отсутствие арифметической ошибки при

оригинальным dry-run и текущим восстановленным состоянием не существует

агрегаты по 8 категориям (таблица выше), которые совпадают с текущим
состоянием БД (проверено повторно в этой сессии — см. ниже), но это
подтверждает только совпадение **сумм**, не то, что каждый конкретный

категорию A, и сумма по категории всё равно сошлась бы. Дальнейшая
косвенная реконструкция (пытаться домыслить построчное сравнение оттуда,
где его нет) не предпринята по прямому указанию не выдавать отсутствие
данных за подтверждение.

`ыфва` — ноль совпадений. `git log --all -S"ыфва"` и `git log --all
-S"CONN-309"` по всей истории репозитория — ноль коммитов, где-либо
добавляющих или удаляющих эту строку. Файлов `*.log` в репозитории нет.
**Вывод: строка не происходит ни из одного закоммиченного seed/импорт-
скрипта — она была создана напрямую через API (`POST /materials`) на живой
dev-БД, до этой сессии, кем-то, кто вручную ввёл `category` на русской
раскладке, не переключив её, и/или тестовые данные с плейсхолдером
"Новый материал".** Кем именно и когда — не установлено: в системе нет
audit-лога изменений `Material`, а `Material` не имеет `created_at`/
`created_by` (в отличие от некоторых других таблиц, см. `1d82548b7a2c`).
Это не абстрактный мусор по построению — именно так выглядела бы ручная
проверка сотрудником через реальный админ-интерфейс, но подтвердить это
как факт (а не как правдоподобное предположение) невозможно с
имеющимися данными.

### п.4 — остаточный риск, не устранённый этой записью

- **Данные, потерянные безвозвратно**: оригинальные UUID и `created_at`
  всех 8 строк `categories` (новые строки после восстановления имеют новые
  `id`/`created_at`, не совпадающие с теми, что существовали между
  `--apply` backfill-скрипта и инцидентом). Любой внешний код/отчёт,
  когда-либо сославшийся на старый `category_id` по значению UUID
  (не через FK на живую строку) — рассинхронизирован без возможности
  исправить.
- **Допущение, на котором держится восстановление `category_id` для 294
  материалов**: SKU-префикс материала однозначно и неизменно определяет
  его категорию (1:1). Подтверждено по построению исходного импорта;
  не проверено (и не может быть проверено задним числом) для гипотетической
  ручной переклассификации до инцидента — такой функциональности в UI не
  существовало на момент инцидента, поэтому вероятность низкая, но это
  предположение, не факт.
- **Для скольких материалов допущение подтверждено независимо**: **ноль**
  из 294 в строгом смысле построчного сравнения — см. п.1 выше. Совпадение
  агрегатов по 8 категориям (полное) — единственное, что есть, и оно не
  является независимым построчным подтверждением.
- **`CONN-309` реклассифицирован мной (сессией) вручную до инцидента, не
  восстановлен после него** — то есть на момент SKU-префиксной
  реконструкции его `category` уже была принудительно выставлена в
  `'Connectors'`, а не в исходное нечитаемое значение. Реконструкция для
  этого материала опирается на ручную правку, сделанную той же сессией,
  а не на восстановление исходных данных — на практике безопасно (SKU
  `CONN-309` и так соответствует Connectors), но это отдельный факт от
  "SKU-префикс восстановил все 294 материала одинаковым методом".
- Условие закрытия этой записи как разрешённой (не только
  задокументированной): либо (a) появление способа независимо
  верифицировать `category_id` хотя бы части из 294 материалов не через
  `internal_sku` (например, если найдётся внешняя копия каталога — экспорт,
  бэкап, скриншот админки — сделанная до инцидента), либо (b) явное решение
  пользователя принять текущее состояние как достаточно надёжное без
  дальнейшей проверки.

## Сознательно отложено (архитектурное решение принято, реализация — нет)

- **Атрибуция материала/поставщика при min-order-инфизибельности** (ADR-0003).
  ADR-0003 фиксирует `AllocationRun.status = "infeasible"` как сигнал "расчёт
  невыполним" (например, единственный поставщик материала не набирает
  `per_order_min_amount` в изоляции — Ограничение 4 из ADR-0002 конфликтует
  с Ограничением 1). Но ADR-0003 сознательно не пытается определить, *какой
  именно* материал/поставщик виноват, и не пересчитывает модель над
  оставшимися материалами (в отличие от того, как `preprocess.
  split_orphaned_materials` уже делает это для обычной недоступности).
  Причина отложить: атрибуция для `per_order_min_amount` — свойство
  подмножества материалов у одного поставщика, а не одной пары
  `(material, supplier)` — эвристика "убрать один материал и пересчитать"
  может не сойтись за один шаг, нужен bucket-по-поставщику fallback.
  Проектировать её сейчас, на синтетических тестовых данных, без единого
  реального прайса из Excel-импорта (`docs/spec.md §3`) — гадание вслепую о
  том, насколько частая и в какой форме это реальная проблема.
  **Условие возврата**: первый реальный (не тестовый) случай
  min-order-инфизибельности после того, как в системе появятся настоящие
  прайсы поставщиков — тогда видно форму проблемы, а не додумывать её.

### ADR-0025 — качество matching на плотных товарных линейках (измерено, не закрыто)

Измерено на реальном документе (`Price 20.08.25.pdf`, поставщик Florida
Sales & Marketing) на линейке крепежа "14 X 3" (10 вариантов на страницах
11-12, различающихся диаметром/типом головки/покрытием, при пустых
`Material.attributes={}` в каталоге для всех кандидатов этой линейки —
`SCRW-010..SCRW-015`) — точность против ручной разметки (человек решил,
какая из 10 строк прайса должна матчиться на какой `internal_sku`, если
вообще должна):

- **Базовый промпт (`matching.py` как есть)**: 6/10 (60%). Все 4 ошибки —
  ложный `match` (модель выбрала "ближайший по смыслу" кандидат вместо
  `not_found`, когда различающий признак сырой строки — диаметр/тип
  головки/покрытие — не подтверждён текстом ни в одном названии
  кандидата). Confidence ошибок разбросан по обе стороны от порога 0.7
  (0.68/0.78/0.84/0.86) — ⚠-пометка низкой уверенности (ADR-0025 §3)
  ловит только 1 из 4.
- **Экспериментальный более строгий промпт** (тестовый скрипт, НЕ внесён
  в `matching.py` — явное правило "если различающий признак не
  подтверждён текстом ни в одном кандидате, возвращай not_found, не
  выбирай ближайший по сходству"): 8/10 (80%). 3 из 4 исходных ошибок
  исправились (confidence вырос до 0.97-0.98), но правило **сработало
  слишком буквально** и превратило единственный истинно положительный
  случай линейки (`<SS-304> 14 X 3 TPK...` → `SCRW-014`, "SS-304"
  семантически означает "Stainless steel" в названии материала, но
  дословно этот текст в кандидате отсутствует) в новую ошибку —
  `not_found` вместо верного `match`.

**Почему это не техническая деталь, а вопрос типа ошибки.** По ADR-0025
§5 `not_found`-строки не персистируются и не видны на экране ревью вообще
(принятый риск) — это самый тихий тип отказа в системе. Строгий промпт
обменивает 3 ложных `match` (видны на экране, могут быть отклонены
пользователем) на 1 новую тихую потерю `not_found` — чистое сокращение
числа ошибок (4→3 на этой выборке), но не однозначное улучшение по
серьёзности последствий одной ошибки.

**Условие продолжения выполнено (2026-08-27): проверены 3 дополнительные
линейки других категорий, вывод — эффект строгого промпта разнонаправлен,
универсального улучшения нет.** Тот же метод (ручная разметка + прогон
обоих промптов на реальных строках того же документа, тот же реальный
291-материал каталог) применён к трём линейкам вне категории Screws:

- **SCREEN DOOR + KP (Doors, 11 строк)**: базовый 9/11 (82%), строгий
  7/11 (64%) — **строгий промпт хуже**. Строгое правило сломало 4
  истинных `match`, где различающий признак (высота/ширина/толщина
  kick-plate) физически присутствовал у кандидата, но в другом текстовом
  формате (`"40x80"` в строке прайса vs `40" x 80"` в названии
  материала) — модель restrictively потребовала дословного совпадения
  вместо распознавания того же числа в другой нотации. При этом строгий
  промпт корректно поймал оба реальных OCR-артефакта в выборке (`<10 X
  96>`, `<12 X 96>` — искажённые размеры без реального кандидата),
  где базовый промпт ложно смэтчил.
- **GUSSET PLATE (Connectors, 6 строк)**: базовый 6/6 (100%), строгий
  5/6 (83%) — **строгий промпт хуже**. Базовый промпт без всякой
  инструкции корректно связал `1/8"`=`.125` и `3/16"`≈`.187` (разные
  нотации одной толщины); строгое правило сломало один из двух таких
  случаев (`1/8" 12"x10'` → должен быть `CONN-020`, стал `not_found`).
- **SUPER SCREEN плотность (Mesh, 6 строк)**: базовый 1/6 (17%), строгий
  6/6 (100%) — **строгий промпт значительно лучше**. Здесь расхождение
  было не нотацией, а искажённым OCR-текстом (`"1/1/14"`/`"1/1/20"`
  вместо `"16/14"`/`"17/20"`) — базовый промпт 5 раз из 6 домыслил
  "похоже на 16/14", строгий корректно отказался при отсутствии
  дословного текстового совпадения.

**Итог по 3 новым линейкам (23 строки): базовый 16/23 (70%), строгий
18/23 (78%)** — усреднённое число маскирует, что улучшение полностью
обеспечено одной линейкой (Mesh), а на двух других строгий промпт хуже
базового. Модель в базовом промпте уже неявно (без всякой инструкции)
умеет отличать "то же значение в другой записи" (`1/8"`↔`.125`,
`40x80`↔`40"x80"`) от "вероятно испорченный текст" (`1/1/14`↔`16/14`) —
не всегда точно (крепёж дал 60%), но эта грань явно присутствует в
поведении модели. Формулировка "признак не подтверждён текстом дословно"
рушит именно эту грань: она не различает переформатирование числа от
искажения текста, обе трактует одинаково строго.

**Вывод: ни один вариант промпта не готов заменить текущий в
`matching.py`.** Проблема на крепеже (ADR-0025, выше) не была случайной
удачей строгого промпта — но и не общий паттерн "строгий промпт всегда
лучше". Правка требует различать два разных случая расхождения
(нотация/формат числа — можно сопоставлять; искажение/отсутствие текста
— нельзя), а не единое правило "нет дословного совпадения → not_found".
Не в объёме этой диагностики — предмет отдельной задачи, если будет
решено взяться за улучшение промпта matching.

**Закрыто ADR-0020 (2026-08-26):** `PriceListEntryOut.suggested_internal_sku`/
`possible_duplicate_of` изначально заполнялись только в ответе на загрузку
(вычислялись в памяти на этапе извлечения, не персистились в
`PriceListEntry`) — `GET /price-list-imports/{id}` после обновления
страницы посреди ревью терял оба поля молча, тот же класс проблемы, что уже
решался в ADR-0004 для клиентского черновика проекта. ADR-0020 снял
заморозку схемы `PriceListEntry` из ADR-0019 и добавил две nullable-колонки
(`suggested_internal_sku VARCHAR(100)`, `possible_duplicate_of JSON`) —
`GET` и `POST` теперь гарантированно отдают одно и то же для одной и той же
строки, оба через единственный рендерер `_to_import_out`
(`backend/app/api/price_ingestion.py`).

Условие закрытия точности модели остаётся открытым: пользователь
предоставит реальные прайс-листы для проверки.

## ADR-0021 — чанкинг extraction по страницам: известные MVP-ограничения

Реализовано: `extract_price_list_lines` (`backend/app/price_ingestion/
extraction.py`) разбивает входной PDF на чанки по `DEFAULT_PAGES_PER_CHUNK`
(3 страницы) с перекрытием в 1 страницу между соседними чанками, отдельный
вызов `client.responses.parse` на каждый чанк, конкатенация без дедупликации
на этом шаге. `input_image` (одиночный скан/фото) не чанкуется — не в
объёме ADR-0021. Дубли `action="match"` на один `material_id` от
перекрытия чанков теперь тоже флагаются (`_flag_duplicate_lines` в
`matching.py`, расширение `_flag_duplicate_new_lines` из ADR-0019 §4) —
ADR-0021 явно допускал оставить это как принятое ограничение, но
симметричная проверка оказалась дешёвой (точное совпадение `material_id`,
без косинусного расстояния), поэтому сделана сразу, не отложена.

Оставлено как принятое MVP-ограничение (ADR-0021, явно зафиксировано в
самой ADR, не переоткрывается здесь):
- Строка, разорванная не на границе физической страницы PDF, а внутри
  страницы иначе, чем ожидается рендерером — не покрывается перекрытием в
  1 страницу, вне объёма.
- Retry на уровне отдельного чанка при его собственном сбое (пустой/частичный
  результат конкретного чанка) — не реализован, ADR-0021 упоминает его как
  возможное будущее дополнение поверх чанкинга, не входит в эту задачу.

Условие закрытия основного вопроса ADR-0021 (нестабильность extraction на
больших документах): 5-10 прогонов реального 14-страничного документа
(~464 позиций) с `gpt-5.6-luna` — см. результаты прогона, приложенные к
задаче реализации.

## ADR-0022 §1 (ранняя дедупликация от чанк-перекрытия) — ЗАКРЫТО ADR-0023 (2026-08-26)

`EARLY_DEDUP_ENABLED = True` снова (`backend/app/price_ingestion/matching.py`).
Механизм переписан: кандидатные пары сужены до строк с общей физической
страницы (перекрытие между соседними чанками — `ExtractedPriceLine.page_number`,
ADR-0023), сигнал дублирования — только точное совпадение `raw_name` после
нормализации пробелов/регистра, без порога по косинусному расстоянию
(проверено на реальном документе: даже внутри overlap-only пар настоящие
дубли и разные позиции одной товарной линейки перемешаны без разделяющей
границы — второй уровень проверки признан неприменимым, не просто
неоткалиброванным, см. ADR-0023).

Финальный прогон на реальном документе (`Price 20.08.25.pdf`, 702 строки):
120 строк (17%) унаследовали решение представителя — **все 120 пар
проверены (не выборка): точное совпадение текста и совпадение
`page_number`, ноль ошибок**. Полный текст диагностики, включая пример
раздела — в ADR-0023.

**Открытый вопрос, не закрытый этой задачей — время полного прохода
(экстракция + matching) 13.8 мин, медленнее оценки ADR-0022 (~7-8 мин).**
Причины: доля дедуплицированных строк ниже предполагавшейся (17% вместо
~35% — ожидаемо, эта ADR отказалась от более широкого, но недостоверного
сигнала ради корректности) и наблюдаемое время LLM-вызова matching выше
оценки ADR-0022. Не блокирует включение флага (условием было корректность
механизма, не скорость) — производительность matching вне объёма
ADR-0023, отдельный вопрос для будущей задачи, если 13.8 мин окажется
неприемлемым для UX.

## ADR-0022 §1 (ранняя дедупликация от чанк-перекрытия) — было ОТКЛЮЧЕНО, аварийная запись (закрыто выше)

**Статус: `EARLY_DEDUP_ENABLED = False`** (`backend/app/price_ingestion/
matching.py`) — временная аварийная мера, не откат ADR-0022 целиком.
Параллелизация и retry/backoff (ADR-0022 §2) остаются включёнными без
изменений; отключена только "строка-последователь наследует decision
представителя вместо своего дорогого вызова" (ADR-0022 §1).

**Причина отключения.** Полный прогон на реальном 14-страничном документе
(`Price 20.08.25.pdf`, поставщик Florida Sales & Marketing, 697 строк
после extraction) с последующим анализом всех 479 пар
представитель→последователь показал: `DUPLICATE_DISTANCE_THRESHOLD=0.15`
(унаследован из `candidates.py`, уже помечен там как непроверенное
предположение) даёт **массовые ложные срабатывания**, не калибровочную
неточность:

- Гистограмма расстояний по всем 479 парам — почти равномерное
  распределение по всему диапазону 0.00–0.15, без чёткой границы между
  "настоящими дублями" и "разными товарами". Один заметный пик у
  0.00-0.01 (64 пары, вероятно реальные чанк-дубли), но и второй пик
  у самой границы 0.14-0.15 (33 пары).
- Ручная проверка 10 случайных пар глазами: **0 из 10** — это одна и та
  же позиция прайса. Примеры: `MUSHROOM END CAP (BRZ/WHT)` признана
  дублем `14 X 2 (1/4-TEK) (100-PK 1000-BX)` (заглушка и упаковка
  саморезов, расстояние ровно 0.0); `FLAT WASHERS 1/4" ZINC` → `1.8"x1.4"
  SNAP POST` (шайбы и стойка); `ROLL FORM GUTTER` → `POOL CABLE TIE`
  (жёлоб и стяжка для бассейна).
- Отдельные строки-"магниты": например `HIGH SPEED DRILL BIT 5/16 X 4`
  и `2 X 4 SMB ->18,20,21,22,24,26,28,30'` каждая ложно притянула по
  21 не связанному товару как "последователей" — похоже на структурную
  проблему greedy-группировки (`dedup.py`, `group_duplicate_lines`):
  строка сравнивается только с уже назначенными представителями по
  порядку, и если один представитель попадает в неспецифичную область
  векторного пространства эмбеддинга, он подряд поглощает всё, что
  проходит порог относительно именно себя.
- Итог по объёму: из 697 строк 479 (69%) стали бы последователями,
  унаследовав чужое matching-решение (action/material_id/SKU) вместо
  собственного — при том что ADR-0022 оценивал ожидаемую долю дублей от
  чанк-перекрытия в ~35% (236 из ~700).

**Что сделано.** `EARLY_DEDUP_ENABLED = False` в `matching.py` — при
выключенном флаге каждая строка снова является собственным
представителем (`representative_of = list(range(len(lines)))`),
alias/векторный-поиск/LLM выполняются для всех строк независимо, как до
ADR-0022 §1. Реализация группировки (`dedup.py`) не удалена — пригодится
после исправления самого механизма. Тесты, специфичные для наследования
(`TestEarlyDedup`, `TestEarlyDedupInteractsWithRetryFailure` в
`test_matching_concurrency.py`), помечены `pytest.mark.skip` с явной
причиной, не удалены. **(Обновление ADR-0023: оба класса переписаны под
новую сигнатуру группировки — страница + точное совпадение текста — и
раскомментированы; `test_matching_early_dedup_disabled.py`, существовавший
только чтобы фиксировать выключенное состояние, удалён.)**

**Цена возврата**: время matching возвращается к до-ADR-0022 масштабу
(последовательный по объёму дорогих вызовов, хоть и всё ещё с пулом
потоков конкурентности 6 из ADR-0022 §2 — не полный откат к
однопоточному циклу). На реальном документе это означает время matching
ближе к оценке "20+ минут" из ADR-0022 "Контекст" для полного объёма
~700 строк без дедупликации объёма, а не подтверждённые в этой же задаче
~4 минуты с дедупликацией.

**Условие возврата `EARLY_DEDUP_ENABLED = True`**: см.
`docs/decisions/0023-price-list-overlap-scoped-dedup.md` — предложенный
путь: сузить пространство кандидатов до строк с общей страницы
перекрытия соседних чанков (не сравнивать весь документ со всем
документом) и внутри этого суженного набора приоритизировать точное
совпадение `raw_name` как основной сигнал, косинусное расстояние — как
вторичный, с заново откалиброванным (более строгим) порогом. Подтверждено
на реальных данных того же документа: сужение до "соседние чанки целиком"
даёт лишь ~3.7× сокращение (недостаточно — нужна атрибуция по странице,
не по чанку), но точное текстовое совпадение внутри suженного набора дало
136 пар с расстоянием ~0 — все похожи на настоящие дубли, тогда как
оставшиеся 689 пар "ниже порога, но не точное совпадение" при ручной
проверке оказались разными позициями одной товарной линейки (не дублями).
Реализация — предмет отдельной задачи после вычитки ADR-0023.

## `resolveMaterialName` дублирована между backend и frontend (ADR-0031)

`frontend/src/lib/colors.ts` (`resolveMaterialName`) — независимый
TypeScript-порт `backend/app/services/material_naming.py`
(`resolve_material_name`), не вызов backend через сеть. Осознанный
компромисс, зафиксированный в ADR-0031 п.4 "Отклонено": поход на backend
только за текстом ради отображения/копирования — на каждый рендер
`OrderDetailPage` или при простом наборе цвета — избыточен для чистой
строковой трансформации над уже загруженными на клиенте
`Material.color_options`/`color_fragment`.

**Риск**: если backend когда-либо изменит формат разбора цвета (новый
цвет сверх `White`/`Bronze`, новый паттерн написания в `canonical_name`,
правку самого алгоритма замены фрагмента) — `colors.ts` не обновится
синхронно сам по себе, и подтверждённое поставщику название разойдётся
с тем, что видно на внутренних экранах/что посчитал бы backend.

**Защита**: `frontend/src/lib/colorResolution.crossvalidation.test.ts` —
построчное сравнение `resolveMaterialName` (TS) и `resolve_material_name`
(Python) на всех 147 материалах реального каталога с `color_options`
(`materials_price_matrix.xlsx`), для обоих известных цветов каждый (294
сравнения). Тест падает, если хоть один результат разойдётся. Referenced-
данные (`frontend/src/lib/__fixtures__/colorResolutionRealCatalog.json`)
сгенерированы backend'ом заранее
(`backend/app/scripts/generate_color_resolution_fixture.py`) и закоммичены,
не пересчитываются на каждый прогон теста — так тест ловит именно
рассинхрон реализаций, а не просто повторяет один и тот же расчёт дважды.
Проверено вручную (2026-09-09): намеренная порча `colors.ts`
(отключение скобочного паттерна) валит 254 из 295 кейсов теста — сигнал
действительно срабатывает, не только существует на бумаге.

**Не устраняет дублирование, только защищает от тихого рассинхрона.**
Если backend изменит `parse_color`/`resolve_material_name` (новый цвет,
новый паттерн) — нужно вручную: (1) обновить `KNOWN_COLORS` и логику в
`colors.ts` синхронно, (2) перезапустить
`generate_color_resolution_fixture.py` и закоммитить обновлённую
фикстуру. Тест сигнализирует о необходимости первого шага, но не
выполняет ни один из них сам.

## Установка pgvector на Windows-машине разработки (ADR-0019)

`pip install pgvector` ставит только Python/SQLAlchemy-адаптер — он ничего
не знает про сам PostgreSQL и не устанавливает расширение `vector` на
сервере БД. Без него `CREATE EXTENSION IF NOT EXISTS vector` (миграция
`f1a6780bb7da_add_material_embedding_column.py`) падает с
`FeatureNotSupported: расширение "vector" отсутствует`.

Для PostgreSQL, установленного через официальный EDB-инсталлятор на
Windows, **Stack Builder не содержит pgvector** (проверено на PG17,
Stack Builder 4.2.2 — только PostGIS, pgAgent, pgBouncer в разделах
Add-ons/Spatial Extensions). Расширение пришлось собирать из исходников:

1. Установить **Visual Studio** (или отдельно **Build Tools for Visual
   Studio**) с компонентом **Desktop development with C++** — проверяется/
   ставится через Visual Studio Installer → выбрать установку → "Изменить"
   → вкладка Workloads.
2. Склонировать исходники pgvector (любой актуальный релиз, совместимый с
   версией PostgreSQL — здесь использовался тег для PG17):
   ```
   git clone https://github.com/pgvector/pgvector.git
   ```
3. Открыть **x64 Native Tools Command Prompt for VS** (не обычный
   cmd/PowerShell — там не настроены `nmake`/`cl` в PATH; ищется в Пуске
   как отдельный ярлык) **от имени администратора** — сборка сама не
   требует прав администратора, но `nmake install` копирует файлы в
   `Program Files`, куда без повышения прав нет доступа на запись.
4. В этом окне:
   ```
   set "PGROOT=C:\Program Files\PostgreSQL\17"
   cd /d <путь-к-склонированному-pgvector>
   nmake /F Makefile.win
   nmake /F Makefile.win install
   ```
   Это компилирует `vector.dll` и копирует `vector.control`,
   `vector--*.sql` в `%PGROOT%\share\extension\`, заголовки — в
   `%PGROOT%\include\server\extension\vector\`.
5. Перезапустить службу PostgreSQL, чтобы она подхватила новое
   расширение (обязательный шаг — без него `CREATE EXTENSION` всё ещё не
   находит `vector.control`, даже если файлы уже на месте):
   ```
   net stop postgresql-x64-17
   net start postgresql-x64-17
   ```
   (тоже из-под администратора; либо через `services.msc` → перезапуск
   службы `postgresql-x64-17`).
6. Проверка готовности (можно от обычного пользователя):
   ```
   psql -U postgres -h localhost -c "SELECT * FROM pg_available_extensions WHERE name = 'vector';"
   ```
   Должна вернуться строка `('vector', '0.8.6', ...)` — тогда
   `alembic upgrade head` пройдёт.

Ни один из этих шагов Claude Code не может выполнить сам: `git worktree`/
Bash-сессии в этой среде не имеют прав администратора Windows и не могут
писать в `Program Files` или перезапускать системные службы — сборка и
установка требуют участия человека за клавиатурой каждый раз на новой
машине (новый dev-ноутбук, CI-раннер без готового образа с pgvector и т.п.).
точности пайплайна.
