# Спецификация: procurement-allocator

Инструмент формирования закупочных ордеров для отдела монтажа Screen Factory Florida.

## 1. Цель и контекст

Отдел монтажа получает чертежи → формирует спецификацию материалов (BOM) → должен закупить материалы у оптимального поставщика с учётом цены, наличия и **стоимости доставки**. Сейчас это делается вручную по Excel-базе. Инструмент должен:

1. Держать актуальную БД цен поставщиков, обновляемую из PDF-прайсов через ИИ-распознавание с человеческим ревью.
2. Позволять создавать проект, вносить список материалов и количества.
3. Автоматически считать, у какого поставщика (или комбинации поставщиков) выгоднее всего закупить всё, **включая доставку**, а не только цену за единицу.
4. Генерировать финальный документ-ордер по каждому поставщику после проверки пользователем.

---

## 2. Модель данных (ядро)

```
Supplier
  id, name, contacts, currency,
  delivery_policy: { flat_fee, free_shipping_threshold, per_order_min_amount, lead_time_days }

Material (канонический справочник)
  id, internal_sku (наш уникальный артикул), canonical_name, category, unit (шт/м/кг...),
  attributes (диаметр, материал, класс и т.д. — для будущего фасетного поиска)

SupplierMaterialAlias  -- связь "как поставщик называет этот материал"
  supplier_id, material_id, supplier_sku, supplier_raw_name

PriceListImport  -- одна загрузка PDF
  id, supplier_id, file_ref, uploaded_at, status(pending_review/approved/rejected), parsed_by_ai_at

PriceListEntry  -- предложенные ИИ строки на ревью (до аппрува)
  import_id, supplier_raw_name, supplier_sku, matched_material_id (nullable — новый материал?),
  confidence, price, currency, stock_qty/availability, min_order_qty, action(update/new/ignore)

Price  -- актуальная цена (после апрува попадает сюда, с историей)
  material_id, supplier_id, price, currency, valid_from, availability, min_order_qty, source_import_id

Project
  id, title, created_by, status

ProjectItem
  project_id, material_id, quantity

AllocationRun  -- результат расчёта "кто что везёт"
  project_id, created_at, algorithm_version

AllocationLine
  allocation_run_id, material_id, supplier_id, quantity, unit_price, line_total

Order  -- финальный ордер поставщику (после апрува пользователем)
  project_id, supplier_id, status(draft/approved/sent), total_amount, delivery_fee, file_ref
OrderItem
  order_id, material_id, quantity, unit_price
```

Ключевой момент: **уникальность материала — по `internal_sku`**, а не по названию. `SupplierMaterialAlias` — таблица-мост, которая решает проблему "один и тот же компонент называется по-разному у разных поставщиков".

## 3. Блок 1 — Обновление БД цен из PDF

### Поток
1. Пользователь загружает PDF прайс-листа конкретного поставщика.
2. Экстракция: сначала детерминированный парсинг таблиц (текстовый слой PDF), для сканов/сложных layout — распознавание через LLM с vision. Разные поставщики = разные форматы, поэтому парсер должен быть промпт-based, не хардкод-based.
3. **Matching-шаг**: для каждой строки из прайса ИИ решает — это существующий `Material` (новое название/цена от этого поставщика) или новая позиция.
   - Через векторный поиск (embeddings по `canonical_name` + `attributes`) строятся top-5 кандидатов из нашей БД.
   - LLM получает сырую строку + top-5 кандидатов + их атрибуты → structured output: `{action: "match"|"new", material_id?, confidence, reasoning}`.
4. Результат падает в `PriceListEntry` со статусом `pending_review`, не сразу в `Price`.
5. **UI ревью**: таблица diff — "было / стало", фильтр по confidence (низкая уверенность — наверх). Подтвердить match / перепривязать вручную / создать новый материал / отклонить строку.
6. По кнопке "Применить" — апрувнутые строки пишутся в `Price` с версионированием (старая цена закрывается по `valid_from/valid_to`, не удаляется).

### Важные нюансы
- Хранить `confidence` и `reasoning` от ИИ — для UX и для дообучения промпта.
- Валюта и единицы измерения — явно показывать в ревью (одна и та же позиция может продаваться "за метр" у одного и "за упаковку 10 шт" у другого).

## 4. Блок 2 — Создание проекта и подбор поставщика

### 4.1 Создание проекта
- Название проекта.
- Таблица: материал (searchable dropdown по `canonical_name`/`internal_sku`) + количество.
- Кнопка "Рассчитать закупку" → запускает `AllocationRun`.

### 4.2 Логика подбора (ядро продукта)

Наивный подход — "для каждого материала взять поставщика с минимальной ценой" — не работает, не учитывает доставку. Правильная постановка:

> Минимизировать: `Σ(цена_позиции × количество)` + `Σ(стоимость доставки по каждому задействованному поставщику)`
> при условии: каждая позиция назначена ровно одному поставщику, у которого есть в наличии нужное количество.

Это задача выбора поставщиков с фиксированными издержками (supplier selection / facility location-подобная задача). Решается точным методом через **ILP-солвер** (Integer Linear Programming) — не нужен ИИ.

**Формализация:**
- `x[m][s] = 1`, если материал `m` закупается у поставщика `s`.
- `y[s] = 1`, если поставщик `s` используется в заказе (тогда платим за его доставку).
- Ограничения:
  - `Σ_s x[m][s] = 1` для каждого материала.
  - `x[m][s] = 0`, если у `s` нет материала `m` в наличии в нужном количестве.
  - `x[m][s] ≤ y[s]`.
  - Опционально: `Σ_m (x[m][s] × price × qty) ≥ min_order_amount[s] × y[s]`.
- Стоимость доставки `delivery_cost[s]`: плоская ставка, либо бесплатна при сумме заказа ≥ `free_shipping_threshold` (кусочно-линейная функция — потребуется доп. бинарная переменная).
- Целевая функция: `min Σ x[m][s]×price[m][s]×qty[m] + Σ y[s]×delivery_cost[s]`.

**Реализация:** Python + OR-Tools (CP-SAT) или PuLP. На масштабе MVP (десятки материалов, единицы-десятки поставщиков) решение — миллисекунды, точный оптимум.

**Что показываем пользователю после расчёта:**
- Сводная таблица "материал → выбранный поставщик → цена → сумма".
- Разбивка по поставщикам: сумма товаров + доставка + итого.
- Явная подсветка случаев, где алгоритм пожертвовал минимальной ценой позиции ради консолидации доставки, с объяснением экономии.
- Возможность вручную переопределить назначение по любой строке.

### 4.3 Edge cases
- Материал недоступен ни у одного поставщика в нужном количестве → явный warning.
- Материал доступен только частично → предложить split, либо показать дефицит.
- Несколько валют у разных поставщиков → единый курс на момент расчёта, хранить курс в `AllocationRun` для воспроизводимости.
- Устаревшие цены (прайс не обновлялся N дней) → помечать в UI.

## 5. Блок 3 — Генерация ордера

- После подтверждения allocation пользователем — создаётся `Order` на каждого задействованного поставщика.
- Документ: PDF (или Word, если нужен фирменный бланк) — таблица позиций, кол-во, цена, итого + доставка, реквизиты.
- Статусная модель: `draft → approved → sent` — аудит-трейл.

## 7. MVP-объём

**В MVP:**
- Импорт PDF → AI-парсинг → ревью → аппрув в БД цен.
- Проект → таблица материалов/количеств.
- Расчёт оптимального распределения по поставщикам с учётом доставки (ILP).
- Ревью и корректировка распределения вручную.
- Генерация ордер-документа по поставщику.

**Осознанно не в MVP (заложить в архитектуру, не переписывать потом):**
- Автоаппрув строк прайса с высоким confidence.
- Мультивалютность с автообновлением курса.
- Частичные/split-поставки одного материала.
- История цен и аналитика.
- Роли/права доступа.
- Интеграция с реальной отправкой ордера поставщику.
