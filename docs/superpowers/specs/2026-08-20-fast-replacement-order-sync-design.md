# Дизайн: быстрый перенос declined-позиции с автосинхронизацией ордера

Дата: 2026-08-20. Статус: одобрено пользователем, готово к ADR + плану реализации.

## Проблема

ADR-0014 (`docs/decisions/0014-declined-order-item-replacement.md`) добавил
на `OrderDetailPage` кнопку "Найти замену", которая переопределяет
`AllocationLine.supplier_id` в текущем плане проекта. Явным решением
ADR-0014 было **не** создавать/обновлять `Order` этому переносу — это
осталось "отдельным ручным шагом" через "Подтвердить и создать ордера" на
экране распределения.

На практике это оказалось нерабочим потоком: после переноса пользователь
видел постоянную пометку "→ Перенесено на {supplier}" со ссылкой на
уже существующий draft-ордер этого поставщика — но эта ссылка вела на
ордер, который **не содержал** перенесённую позицию (она была только в
плане, не в `Order`/`OrderItem`). Чтобы реально добавить позицию в ордер,
нужно было покинуть экран Order, пересчитать распределение и запустить
"Подтвердить и создать ордера" на весь проект — то самое "уйти с экрана
Order", которого ADR-0014 явно хотел избежать.

## Решение

### 1. Один endpoint вместо связки из двух вызовов

```
POST /orders/{order_id}/items/{item_id}/replace-and-order
{ "supplier_id": "<выбранный кандидат>" }
```

Заменяет today's `PATCH .../lines/{line_id}` + отдельный поход за
`latest_allocation_run.id` на фронте. Внутри, одной транзакцией:

1. Находит `line_id` — `AllocationLine` в последнем `AllocationRun`
   проекта для `item.material_id` (та же логика, что уже есть в
   `find_replacement_candidates`, ADR-0014 п.2 — переиспользуется, не
   дублируется).
2. Override `AllocationLine.supplier_id = supplier_id`,
   `overridden_via_order_item_id = item_id` — переиспользует
   существующую `override_allocation_line_supplier()`
   (`backend/app/allocation/service.py`, ADR-0006/0014), не новый код.
3. Ищет `Order` этого `supplier_id` в этом проекте со `status == "draft"`.
   - **Есть один** → добавляет новый `OrderItem` (material_id,
     quantity — из `AllocationLine.quantity`, `quoted_price` — цена
     выбранного кандидата) к этому `Order`. Существующие позиции этого
     ордера (включая их `confirmed_price`/`received_price`) не
     трогаются вообще.
   - **Есть несколько** (см. ADR-0012 "Контекст" — на практике такое
     бывает) → `409 Conflict`, override плана не применяется, ничего
     не создаётся. Молчаливый выбор одного из дублей отклонён — `id`
     (UUID v4) не хронологичен, нет надёжного критерия "какой из них
     правильный"; тот же принцип, что и для дубля `material_id` ниже.
     Разрешение — ручное, не в объёме этой задачи.
   - **Нет ни одного** → создаётся новый `Order(status="draft")` с этой
     одной позицией.
   - **Уже есть `OrderItem` с тем же `material_id`** в целевом draft-ордере
     → `409 Conflict`, ничего не создаётся и не изменяется (ни override
     плана, ни ордер) — редкий случай, требует ручного разбора
     пользователем, не автоматизируется в этой задаче.
4. Пересчитывает `total_amount`/`delivery_fee` **этого одного** `Order`
   по `supplier_summaries` текущего `AllocationRun` для `supplier_id`
   (`goods_total`, `delivery_fee`, `free_shipping_achieved`) — те же
   числа, которые уже видны на `AllocationResultPage` для этого
   поставщика, не пересчитываются заново отдельной формулой.
5. Возвращает обновлённый `OrderItemOut` declined-позиции (тот же набор
   производных полей, что и сейчас — `replaced_by_supplier_id`,
   `replaced_by_supplier_name`, `replacement_draft_order_id`), плюс
   сам факт, что `replacement_draft_order_id` теперь **всегда** ведёт
   на ордер, реально содержащий перенесённую позицию.

**409 из `find_replacement_candidates`** (материал не в текущем плане) —
поведение не меняется, endpoint возвращает ту же ошибку тем же путём.

Старый `PATCH .../lines/{line_id}` с `source_order_item_id` (ADR-0014
п.5) не удаляется — остаётся низкоуровневым примитивом override,
которым продолжает пользоваться обычный ручной override на
`AllocationResultPage`. Новый endpoint — специализированная обёртка
поверх него плюс работа с `Order`, используется только из флоу
"Найти замену".

### 2. Без модального подтверждения

Клик по кандидату сразу выполняет перенос — без промежуточного pop-up.
Обоснование: операция не разрушительна (не удаляет существующие позиции
целевого ордера, не трогает их `confirmed_price`/`received_price`) —
та же логика необратимости, что уже разделяет `draft` без
`confirmed_price` (тривиально восстановим) от `draft` с ним
(ADR-0012 §1) — здесь мы вообще ничего не удаляем, только добавляем
строку. Значит уровень подтверждения ADR-0012 (отдельный pop-up перед
`replace_drafts`) сюда не применяется — тот механизм существует именно
потому, что удаляет данные, этот — нет.

### 3. Что не входит в эту задачу

- Автоматическое создание `approved`/`sent` ордеров — только `draft`,
  как и весь остальной flow создания ордеров в проекте.
- Изменение модели статусов `Order` в зависимости от заполненности
  `received_price`/`confirmed_price` — отдельная задача, обсуждена и
  сознательно отложена в этом же разговоре.
- Полный пересчёт доставки/`min_order_amount` "с нуля" для одного
  ордера отдельной формулой — переиспользуется то, что уже посчитал
  солвер в `supplier_summaries` текущего `AllocationRun`.
- Разрешение конфликта "несколько draft-ордеров одного поставщика" —
  известный риск ADR-0012, не создаётся и не решается этой задачей.

### 4. Frontend

`OrderDetailPage.tsx`: клик по кандидату в панели find-replacement
вызывает `POST .../replace-and-order` вместо сегодняшней связки
`allocationApi.overrideLine` + `projectsApi.get`. После успеха — тот же
принцип, что и сейчас: полный повторный `GET /orders/{id}` (ADR-0014
п.6), без навигации.

Постоянный блок "→ Перенесено на {supplier}" — текст ссылки
возвращается к простому "черновик уже создан »"/"черновик создан »"
(убирается оговорка "позиция пока не добавлена", добавленная как
временное объяснение текущего бага — после этой задачи оговорка станет
неверной, ссылка будет вести на ордер, где позиция реально есть).

## Альтернативы (отклонены)

**Пересоздавать draft целиком через существующий `replace_drafts`
(ADR-0012), примененный к одному поставщику.** Отклонено пользователем
в обсуждении — удаляет и пересоздаёт все существующие позиции
целевого draft-ордера, включая их `confirmed_price`, ради добавления
одной строки; несоразмерный риск потери данных для операции, которая
концептуально должна быть просто "добавить строку".

**Модальное подтверждение перед переносом.** Отклонено — операция
безопасна (ничего не удаляет), pop-up добавил бы трение без причины.

**Дубликат материала в целевом ордере — автообъединение (обновить
quantity/цену существующей строки).** Отклонено — редкий случай,
неочевидно, какое поведение пользователь ожидает (сложить количество?
заменить цену?); проще и безопаснее вернуть 409 и оставить ручной
разбор человеку.
