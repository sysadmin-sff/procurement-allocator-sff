# UI Reference — поведенческая логика экранов

Этот файл описывает КАК себя ведут экраны. КАК они выглядят — в `docs/design/*.html`.
Заполняется/уточняется после каждой генерации в Claude Design и показа пользователям.

## 1. Ревью прайс-листа (`docs/design/01-price-review.html`)

- Строки сортируются по возрастанию confidence (низкая уверенность — наверх).
- Пороги confidence: `>90%` — зелёный, `70–90%` — жёлтый, `<70%` — красный.
- Дельта цены к предыдущей: подсвечивается красным, если рост `>20%` — требует
  осознанного подтверждения, не должно быть "проскроллено мимо".
- Массовое одобрение — только для строк с confidence `>95%`; остальные — построчно.
- Ничего не пишется в `Price` до нажатия "Применить одобренные".
- [ ] уточнить после первого показа пользователю: нужен ли предпросмотр PDF-страницы
      в панели рядом со строкой, или это редко используется.

## 2. Конструктор проекта (`docs/design/02-project-builder.html`)

- Поиск по материалу: минимум 2 символа до появления результатов, показывает
  категорию материала рядом с названием.
- Enter в последней строке таблицы добавляет новую пустую строку.
- Единица измерения подставляется автоматически при выборе материала (readonly).
- Кнопка "Рассчитать закупку" неактивна, если хотя бы одна строка не заполнена
  полностью (материал + количество).
- [ ] уточнить: что происходит при добавлении одного и того же материала дважды —
      сливать строки или разрешать дублирование.

## 3. Результат распределения (`docs/design/03-allocation-result.html`)

- Бейдж "не самая дешёвая цена" показывается для каждой строки, где алгоритм выбрал
  не минимальную цену за единицу; текст объяснения: разница в цене vs. экономия на
  консолидации доставки, в долларах.
- Предупреждение о нехватке материала — красный блок, не скрывается по умолчанию,
  не в конце страницы, а на уровне соответствующей позиции.
- Ручное переопределение поставщика — select прямо в строке; после изменения
  показывается индикатор "изменено вручную" (отдельно от бейджа "не самая
  дешёвая цена" — оба могут быть показаны одновременно, см. ADR-0006), а
  backend пересчитывает и возвращает обновлённые сводки поставщиков (старого
  и нового) — не клиентская арифметика, см. ADR-0006 п.4 (обоснование: money
  math — backend-only, CLAUDE.md принцип 4).
- Переопределение разрешено даже если у нового поставщика явно недостаточное
  `availability` на материал — не блокируется, но строка получает отдельный
  видимый признак риска (не путать с индикатором "изменено вручную"). См.
  ADR-0006 п.2. Реализовано в `AllocationResultPage.tsx` (`LineRow`) как
  отдельная строка текста под ячейкой материала (не бейдж — `display: block`,
  класс `.availabilityRisk`), цвет `--color-danger-text`, видимый текст, не
  `title`-тултип (тот же стандарт, что и для остальных индикаторов строки, см.
  ниже). Текст: "⚠ у поставщика доступно {availability} {unit}, требуется
  {quantity}". Условие показа не привязано к самому факту override — это
  сравнение `Price.availability` **текущего** поставщика строки (кто бы его ни
  назначил, солвер или ручной override) с `line.quantity`, показывается только
  когда `availability` явно задан (не `null`) и меньше требуемого количества —
  симметрично тому, как ADR-0005 трактует `availability IS NULL` как "не
  проверялось", а не как риск.
- Предупреждение о недостижении минимальной суммы заказа поставщика
  (`below_min_order`, возникает как побочный эффект переноса позиции между
  поставщиками) — отдельная текстовая строка **под** заголовком карточки
  поставщика (между именем/доставкой/итогом и таблицей строк), на всю
  ширину карточки, в цвете `--color-danger-text`, без блочного padding
  уровня `warningBlock` (это контекст одной карточки, не событие уровня
  страницы). Текст: "⚠ Сумма заказа {goods_total} меньше минимальной
  {per_order_min_amount} — поставщик может отклонить заказ." Не блокирует
  PATCH переопределения. См. ADR-0006 п.4 за обоснованием, почему не бейдж
  в хедере карточки и не изменение цвета итоговой суммы.
- Кнопка "Подтвердить и создать ордера" — финальный шаг, необратимый (создаёт `Order`).
  Генерация должна читать текущее (с учётом override) состояние
  `AllocationLine`, не исходный результат ILP-расчёта — см. ADR-0006 п.6.
- Повторный запуск ILP с "заморозкой" переопределённой позиции — не в
  объёме; ручное правило — это override, который фиксируется поверх текущего
  состояния строки без пересчёта остального проекта. См. ADR-0006
  "Альтернативы".
- **Модалка конфликта draft-ордеров** (`OrderDraftConflictModal`,
  `frontend/src/components/OrderDraftConflictModal.tsx`) — см. ADR-0012.
  Открывается ИСКЛЮЧИТЕЛЬНО в ответ на реальный `409 draft_orders_exist` от
  `POST .../orders`, не превентивно с фронта (backend — источник истины по
  пересечению поставщиков, ADR-0012 п.3). Клик "Подтвердить и создать
  ордера" сперва всегда шлёт `replace_drafts: false` неявно (обычное
  создание); при `409` вместо `ErrorBanner` показывается эта модалка
  вместо страницы, `ErrorBanner` для этого конкретного случая не
  используется вообще (создание не удалось молча ни разу).
  - Список только тех поставщиков, где есть пересечение (подмножество из
    тела `409`, не все поставщики проекта), для каждого — **все** его
    `existing_draft_orders` (может быть больше одного — не сворачивается
    в один, см. реальный кейс `#20675` в ADR-0012 "Контекст") с суммой
    каждого черновика.
  - Поставщик, у которого хотя бы один `existing_draft_orders[].
    has_confirmed_prices === true`, получает отдельную заметную строку
    предупреждения под его записью (`--color-danger-text` /
    `--color-danger-tint`, тот же язык, что уже применён к
    `below_min_order`/`availabilityRisk` в этом же разделе), текст:
    "в этом черновике уже есть подтверждённые поставщиком цены — они
    будут потеряны при замене".
  - Если хотя бы один поставщик в списке имеет `has_confirmed_prices`,
    кнопка "Заменить черновики" неактивна, пока не отмечен отдельный
    чекбокс подтверждения ("Да, я понимаю, что подтверждённые цены будут
    потеряны…") — общий клик "Заменить" не может случайно стереть
    подтверждённые цены без этого явного шага (ADR-0012 п.1, п.4).
    Без единого подтверждённого поставщика в списке кнопка активна сразу.
  - **Кнопки: только "Отмена" и "Заменить черновики"** — "Создать
    дополнительно" из первоначального текста ADR-0012 п.1/п.4 в модалке
    отсутствует. Обнаружено при живой проверке на `#20675`: ADR
    предполагал, что повторный `POST` с `replace_drafts: false` после
    показа модалки пройдёт "без блокирующего `409`, потому что явное
    согласие уже получено" — но backend не хранит и не принимает такого
    согласия отдельно от `replace_drafts`, поэтому повторный `false`
    при том же конфликте снова получает `409`. Кнопку убрали, а не
    сделали фиктивно рабочей (молча проглатывать повторный `409` и вести
    себя как будто заказ создан было бы хуже — пользователь думал бы,
    что дозаказ создан, хотя ничего не произошло). Возврат этой кнопки
    требовал отдельного backend-поля, отличного от `replace_drafts` —
    **это поле реализовано 2026-08-31** (`acknowledge_conflict` в теле
    `POST .../orders`), но модалка его пока не использует: кнопки
    по-прежнему только «Отмена» и «Заменить черновики». Возврат кнопки —
    отдельная задача, см. `docs/known-issues.md`.
  - Текстовая подсказка внизу модалки проговаривает необратимость замены,
    в тон существующему `footerHint` под основной кнопкой.
  - Конфликт может повториться и на повторном вызове из модалки (гонка:
    кто-то создал ещё один draft между первым `409` и кликом "Заменить
    черновики") — в этом случае модалка обновляется новыми данными
    конфликта, а не откатывается к обычной странице ошибки.

## 4. Список проектов (`ProjectsListPage.tsx`)

- Удаление проекта — через `ConfirmButton` в отдельной ячейке каждой
  строки (клик по строке целиком переходит в проект, `stopPropagation`
  на ячейке удаления не даёт кнопке случайно сработать как переход). См.
  ADR-0009.
- Каскадно удаляются все связанные данные: `PurchaseRecord`, `Order`/
  `OrderItem`, `AllocationRun`/`AllocationLine`, `ProjectItem`.
- Если у проекта есть хотя бы один `Order` со статусом не `draft`
  (уже отправлен поставщику) — `DELETE` возвращает `409`, ничего не
  удаляется (ни для одной таблицы). Сообщение показывается через
  `ErrorBanner` с `conflictMessage`: "У проекта есть отправленные
  поставщику ордера — удаление недоступно." Предупреждения на уровне
  списка *до* клика на удаление нет — список не тянет сводку по ордерам
  ради этого, пользователь узнаёт о блокировке по факту попытки. См.
  ADR-0009 п.1, п.3.

## 5. Фактическая закупка (`PurchaseRecordsPage.tsx`, `/projects/:id/purchases`)

- Экран уровня проекта, не уровня отдельного `Order` — план и факт
  показаны рядом, сгруппированы по поставщику, включая поставщиков без
  `Order` в проекте ("не планировался" — заказали не по плану). См.
  ADR-0008 §2, §5.
- Агрегаты наверху: `purchased_total` по проекту vs сумма
  `Order.total_amount`, дельта в $/%. Если ни для одного поставщика ещё
  нет `Order` — вместо дельты предупреждение "сравнить не с чем" (не
  `0`/`—` молча). См. ADR-0008 §4.
- Таблицы "План" и "Факт" — независимые колонки, без построчного
  автоматического сопоставления между ними (ADR-0008 §3 — явно вне
  объёма). Единственная связь план↔факт — ручная, по инициативе
  пользователя:
  - **Кнопка «→» в конце каждой строки плана.** Копирует
    название/кол-во/цену/`material_id` этой строки плана в форму
    добавления записи факта (не создаёт `PurchaseRecord` сама — форма
    всё равно требует явного нажатия "+ Добавить"), выставляет
    поставщика формы на поставщика текущей карточки и плавно
    прокручивает страницу к форме. Предназначена для случая "всё
    совпало, не хочу перепечатывать вручную" — не автоматическое
    сопоставление (то и другое разные вещи: копирование одной строки по
    явному клику не угадывает соответствие само, только избавляет от
    перепечатывания уже выбранной человеком строки).
  - Опциональный `material_id` в строке факта после такого копирования
    предзаполнен из строки плана (там он не может быть не задан —
    `OrderItem.material_id` обязателен), но остаётся редактируемым и не
    более обязательным, чем при ручном вводе — пользователь может
    очистить поле перед сохранением.
- Правка/удаление записи факта — inline, тот же `ConfirmButton`, что и
  в остальном проекте; форма правки открывается на всю ширину строки
  (не в узких колонках таблицы — 5 полей формы не помещаются в 4 узкие
  колонки отображения).

## 6. Статус проекта на `ProjectDetailPage.tsx` / `ProjectRouterPage.tsx`

- `status === 'draft'` — показывается конструктор (`ProjectBuilderPage`),
  не детальный экран. Переключение целиком по `status`, не по наличию
  `latest_allocation_run` — см. ADR-0011 §7.
- Кнопка «Завершить проект» на `ProjectDetailPage` видна только при
  `status === 'ordered'`. После нажатия `status` становится `completed`
  без возможности вернуться назад — ни повторный расчёт, ни новый ордер
  этого не меняют. См. ADR-0011 §4–5.
- Расчёт со статусом `AllocationRun.status === 'infeasible'` (не
  `Project.status` — разные поля) никогда не двигает `Project.status`, в
  том числе при первом расчёте черновика — черновик остаётся `draft`,
  пока не будет хотя бы одного успешного (`"ok"`) расчёта. См.
  ADR-0011 §2.

## 7. Ордер поставщика — сверка цен (`OrderDetailPage.tsx`, `/orders/:id`)

См. ADR-0007 и ADR-0013 для полной архитектурной мотивации; здесь —
только поведение экрана.

- Таблица позиций: Материал, Кол-во, Отправленная цена (`quoted_price`,
  read-only), **Полученная цена** (`received_price`, inline-редактируемая
  ячейка, тот же паттерн save-on-blur/Enter, что и подтверждённая цена),
  Подтверждённая цена (`confirmed_price`, inline-редактируемая), Расхождение
  (`price_delta`/`price_delta_pct`, read-only, только quoted vs confirmed —
  received не участвует в этом расчёте, см. ADR-0013 п.4), Статус (кнопка
  "Отметить как недоступно" / "Отклонено" + опциональное поле причины).
- `received_price` и `confirmed_price` независимы: можно заполнить любое
  из двух без другого, в любом порядке. Не требуется вводить
  `received_price` перед `confirmed_price`.
- Кнопка "Отметить как недоступно" на строке переключает `declined_at`
  (проставляет/снимает); не блокирует и не требует очистки
  `received_price`/`confirmed_price` — позиция может быть одновременно
  отклонена и иметь введённую цену (случай "отказался, но предложил
  замену"). Строка при `declined_at != null` подсвечивается тем же
  danger-tint языком, что и строка с расхождением >10%; обе подсветки
  независимы и могут применяться к одной строке одновременно.
- Баннер над таблицей суммирует оба сигнала отдельно: "N позиций с
  расхождением цены больше 10%" и "N позиций отклонено поставщиком",
  каждый показывается только если счётчик больше нуля.
- `Order.total_amount` не меняется при отметке `declined_at` — остаётся
  планом (что было отправлено поставщику), не пересчитывается по факту
  отказов.
- **Перенос на другого поставщика (ADR-0014).** На declined-строке
  (`declined_at != null`) рядом со статусом — кнопка "Найти замену". По
  клику — `POST .../items/{item_id}/find-replacement`; результат
  (список кандидатов) открывается инлайн под кнопкой, без перехода на
  другой экран. Повторный клик сворачивает список.
  - Каждый кандидат — имя поставщика и цена; если `availability_risk`
    (backend уже вычислил: `availability` задан и меньше `quantity`
    declined-позиции) — под кандидатом danger-tint предупреждение, тот
    же язык, что `.availabilityRisk` на `AllocationResultPage` (ADR-0006
    §2): "⚠ у поставщика доступно {availability} {unit}, требуется
    {quantity}". `availability = null` — без предупреждения.
  - Клик по кандидату — `PATCH .../lines/{line_id}` (тот же endpoint,
    что ручной override, ADR-0006) с `supplier_id` кандидата и
    `source_order_item_id` = id declined-позиции; `line_id` уже пришёл
    в ответе find-replacement. После успеха — не навигация, а полный
    повторный `GET /orders/{id}` (частичный ответ PATCH не несёт
    `replaced_by_*` полей).
  - `404` от find-replacement ("материал отсутствует в текущем плане
    проекта") — показывается инлайн под кнопкой, не как `ErrorBanner`
    уровня страницы.
  - После успешного переноса — постоянный (не исчезающий) блок "→
    Перенесено на {replaced_by_supplier_name}" рядом со статусом строки:
    если `replacement_draft_order_id` не `null` — ссылка "у поставщика
    есть черновик ордера (позиция пока не добавлена) »". Формулировка
    намеренно не говорит "перенесено в ордер" — `replacement_draft_order_id`
    означает лишь, что у нового поставщика уже есть какой-то черновик
    `Order` в этом проекте (переиспользуется конфликт-проверка ADR-0012),
    не что эта позиция туда попала: перенос меняет только
    `AllocationLine.supplier_id` в текущем плане, создание/обновление
    самого `Order` — отдельный ручной шаг ("Подтвердить и создать
    ордера" на экране распределения), не в объёме ADR-0014. Если
    `replacement_draft_order_id` — `null`, показывается текст "ордер ещё
    не создан". Пропадает сам собой, если строку того же материала
    позже переопределят вручную по несвязанной причине
    (`replaced_by_supplier_id` вернётся `null`) — экран не хранит это
    состояние сам, только отображает то, что отдаёт
    `OrderItemOut` на каждый `GET /orders/{id}`.

### 7а. Распознавание ответа поставщика — загрузка документа (ADR-0018)

Секция на `OrderDetailPage.tsx` (`ParseResponseSection`) между баннером
расхождений и основной таблицей позиций. Без прохода через Claude
Design — собрана из уже установленных примитивов (ADR-0018 §3).

- **Загрузка.** `<input type=file accept=".pdf,image/*">` + кнопка
  "Распознать цены из документа" → `POST .../parse-response`
  (multipart). Кнопка/инпут блокируются на время запроса, рядом текст
  "Обращаемся к ИИ — это может занять несколько секунд…". Файл не
  сохраняется нигде на фронте после ответа (ADR-0018 §7) — инпут
  очищается сразу после запроса вне зависимости от результата.
- **Ошибка распознавания** — текстовый блок в том же
  danger-tint словаре, что и остальные предупреждения экрана,
  сообщение из `ApiError.message` (backend уже формулирует понятный
  текст на 422/502, см. ADR-0018 §6) с фолбэком "Не удалось распознать
  документ. Проверьте качество файла или введите цены вручную
  построчно." Ручной ввод `received_price`/`confirmed_price`/"Отметить
  как недоступно" в основной таблице остаётся доступен как есть,
  независимо от этой ошибки — фича дополняет, не блокирует.
- **Блок "Совпало"** — таблица: наша позиция (по `order_item_id` из
  ответа, название материала берётся из `order.items`, не из
  `raw_description` — это то, что мы заказывали), отправленная цена
  (read-only), полученная цена — inline-редактируемая ячейка,
  предзаполненная ценой из ответа ИИ, тот же паттерн ввода, что и
  колонка "Полученная цена" в основной таблице (§7), но без save-on-blur
  — значение копится в локальном состоянии секции и уходит одним PATCH
  на "Применить все совпадения", не по отдельности. Чекбокс слева от
  строки — включена ли строка в массовое применение, по умолчанию
  включён. Строки с `confidence` `"low"` или `"medium"` (не различаются
  визуально между собой в MVP, см. ADR-0018 §6) подсвечиваются тем же
  `--color-danger-tint`, что и `discrepantRow`/`declinedRow` в основной
  таблице, плюс текст "⚠ низкая уверенность распознавания" и
  `reasoning` от модели показаны под названием позиции.
- **Кнопка "Применить все совпадения"** — `PATCH .../items/{id}` с
  `received_price` в цикле по всем строкам с включённым чекбоксом
  (текущее значение из локального состояния, не обязательно исходное от
  ИИ, если сотрудник поправил). После цикла — полный `GET /orders/{id}`
  (тот же паттерн, что `handleReplacementApplied`, ADR-0014 п.6, не
  частичное обновление по ответам PATCH), и текст-итог "Применено N из
  M" под заголовком блока. Кнопка неактивна, если нет ни одной включённой
  строки.
- **Блок "Отсутствует в ответе"** — список `OrderItem` этого `Order`,
  чей `id` не встретился ни в одной строке "Совпало". Только название
  материала и уже существующая кнопка "Отметить как недоступно"/
  "Отклонено" (тот же компонент/PATCH, что в основной таблице, ADR-0013
  §3) — клик сразу переключает `declined_at` через `PATCH
  .../items/{id}`, без промежуточного подтверждения (сам этот клик и
  есть явное действие сотрудника). Никакого действия по умолчанию при
  массовом применении — категория не участвует в "Применить все
  совпадения" вообще (ADR-0018 §3b).
- **Блок "Лишнее"** — список строк ответа с `matched_order_item_id:
  null`: `raw_description`, цена, количество (инпут — количество от ИИ
  может быть `null`, поле предзаполняется `1` и остаётся редактируемым,
  `PurchaseRecordCreate.quantity` обязателен и `>0`). Кнопка "Добавить"
  на каждой строке по отдельности (не массово, ADR-0018 §4) —
  `POST /projects/{project_id}/purchase-records` с `supplier_id =
  order.supplier_id`, `raw_description`, `quantity`, `unit_price =
  price`, `material_id: null`. После успеха кнопка заменяется на
  постоянную (до перезагрузки экрана) пометку "Добавлено ✓", инпут
  количества блокируется — строка не отправляется повторно случайным
  вторым кликом.
- Все три блока читают текущее `order.items` (а не замороженный снимок
  на момент парсинга) для отображения материала/цены — после "Применить
  все совпадения" или отметки "недоступно" полный `GET` обновляет и
  секцию распознавания, и основную таблицу разом.

## 8. Ревью импорта прайс-листа (ADR-0019, ADR-0020)

Загрузка — секция «Прайс-лист» на `SupplierDetailPage.tsx`
(`/suppliers/:id`): файловый инпут + кнопка «Загрузить прайс-лист» →
`POST /suppliers/{id}/price-lists`. По успеху — переход на
`/price-list-imports/:importId` (`PriceListImportReviewPage.tsx`).
Отдельного пункта в верхней навигации нет — списка импортов не
существует как отдельного экрана, попасть на ревью можно только через
только что выполненную загрузку.

- **`PriceListEntry.action` — не предложение ИИ, а факт применения.**
  Поле `null`, пока строка не решена на экране ревью (см.
  `apply_price_list_entry`); *предложенное* моделью действие выводится
  косвенно: `matched_material_id != null` при `action === null` —
  предложено «match» на этот материал, `matched_material_id === null`
  — предложено «new» (черновой `suggested_internal_sku` — из
  ADR-0019 §4/ADR-0020). Экран не путает эти два состояния —
  «предложено ИИ» и «применено пользователем» показаны по-разному
  (обычная строка формы vs. `resolvedLabel` с ✓/«Пропущено»).
- Сортировка — по возрастанию `confidence` (низкая уверенность
  наверх), как зафиксировано в исходном (не реализованном отдельным
  экраном) варианте `docs/design/01-price-review.html`. Пороги те же,
  что были описаны для того эскиза: `>90%` зелёный, `70–90%` жёлтый,
  `<70%` красный (`.confidenceHigh`/`.confidenceMedium`/`.confidenceLow`);
  строка целиком получает `danger-tint`, если `confidence < 70%`.
- **Группировка `possible_duplicate_of` — и бейдж, и соседство, не
  одно вместо другого** (ADR-0019 §4 явно требует оба сигнала). Сортировка
  по confidence — основная, но пара строк, ссылающихся друг на друга
  через `possible_duplicate_of`, дополнительно подтягивается друг к
  другу (вторая строка пары вставляется сразу за первой, а не на своё
  место по confidence) и обе получают текстовый ⚠-бейдж с именами
  друг друга. Ничего не блокируется — обе можно одобрить как разные
  материалы.
- **Правка предложения ИИ до применения:**
  - Для предложенного «match» — `MaterialCombobox` (тот же компонент,
    что на `ProjectBuilderPage`, поиск от 2 символов) позволяет выбрать
    другой материал вместо предложенного, на случай ошибки матчинга.
  - Для предложенного «new» — поля `internal_sku`/`canonical_name`
    редактируемые, предзаполнены `suggested_internal_sku` (или пусто,
    если ИИ не предложила) и `supplier_raw_name` соответственно;
    `internal_sku`/`canonical_name` обязательны перед применением
    строки (тот же контракт, что `POST /materials`).
- Чекбокс «включить в применение» на каждой ещё не решённой строке,
  по умолчанию включён — тот же паттерн, что ADR-0018 §4 уже установил
  для `ParseResponseSection`.
- **«Применить выбранные»** — цикл `POST .../entries/{id}/apply` по
  каждой включённой нерешённой строке (backend не даёт batch-эндпоинт,
  см. ADR-0019 «Последствия»), с текстом-итогом «Применено N из M»
  после прохода и последующим полным `GET` импорта (тот же паттерн
  полного рефетча, что `OrderDetailPage`/`ParseResponseSection`).
  Ошибка на отдельной строке (например конфликт `internal_sku`)
  показывается инлайн под этой строкой, не блокирует остальные строки
  цикла.
- **«Пропустить»** — отдельная кнопка на строке, вызывает `apply` с
  `action: "skip"` сразу (не через общую кнопку массового применения).
  Строка после этого помечается «Пропущено» и выходит из набора для
  массового применения, но не участвует в блокировке статуса импорта
  иначе, чем любое другое решённое действие — `PriceListImport.status`
  переходит в `approved`, когда не осталось строк с `action == null`
  (см. `maybe_mark_import_approved`), независимо от того, решены ли
  они как match/new/skip.
- Массовое одобрение по порогу confidence — сознательно не реализовано
  (ADR-0019 §4, spec.md §7).
