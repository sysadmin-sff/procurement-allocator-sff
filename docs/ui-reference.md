# UI Reference — поведенческая логика экранов

Этот файл описывает КАК себя ведут экраны. КАК они выглядят — в `docs/design/*.html`.
Заполняется/уточняется после каждой генерации в Claude Design и показа пользователям.

## 1. Ревью прайс-листа (`docs/design/01-price-review.html`)

- Строки сортируются по возрастанию confidence (низкая уверенность — наверх).
- Пороги confidence: `>90%` — зелёный, `70–90%` — жёлтый, `<70%` — красный.
- Дельта цены к предыдущей: подсвечивается красным, если рост `>20%` — требует
  осознанного подтверждения, не должно быть "проскроллено мимо".
- Массовое одобрение — только для строк с confidence `>95%`; остальные — построчно.
- Ничего не пишется в `Price` до нажатия "Применить одобренные".
- [ ] уточнить после первого показа пользователю: нужен ли предпросмотр PDF-страницы
      в панели рядом со строкой, или это редко используется.

## 2. Конструктор проекта (`docs/design/02-project-builder.html`)

- Поиск по материалу: минимум 2 символа до появления результатов, показывает
  категорию материала рядом с названием.
- Enter в последней строке таблицы добавляет новую пустую строку.
- Единица измерения подставляется автоматически при выборе материала (readonly).
- Кнопка "Рассчитать закупку" неактивна, если хотя бы одна строка не заполнена
  полностью (материал + количество).
- [ ] уточнить: что происходит при добавлении одного и того же материала дважды —
      сливать строки или разрешать дублирование.

## 3. Результат распределения (`docs/design/03-allocation-result.html`)

- Бейдж "не самая дешёвая цена" показывается для каждой строки, где алгоритм выбрал
  не минимальную цену за единицу; текст объяснения: разница в цене vs. экономия на
  консолидации доставки, в долларах.
- Предупреждение о нехватке материала — красный блок, не скрывается по умолчанию,
  не в конце страницы, а на уровне соответствующей позиции.
- Ручное переопределение поставщика — select прямо в строке; после изменения
  показывается индикатор "изменено вручную" (отдельно от бейджа "не самая
  дешёвая цена" — оба могут быть показаны одновременно, см. ADR-0006), а
  backend пересчитывает и возвращает обновлённые сводки поставщиков (старого
  и нового) — не клиентская арифметика, см. ADR-0006 п.4 (обоснование: money
  math — backend-only, CLAUDE.md принцип 4).
- Переопределение разрешено даже если у нового поставщика явно недостаточное
  `availability` на материал — не блокируется, но строка получает отдельный
  видимый признак риска (не путать с индикатором "изменено вручную"). См.
  ADR-0006 п.2. Реализовано в `AllocationResultPage.tsx` (`LineRow`) как
  отдельная строка текста под ячейкой материала (не бейдж — `display: block`,
  класс `.availabilityRisk`), цвет `--color-danger-text`, видимый текст, не
  `title`-тултип (тот же стандарт, что и для остальных индикаторов строки, см.
  ниже). Текст: "⚠ у поставщика доступно {availability} {unit}, требуется
  {quantity}". Условие показа не привязано к самому факту override — это
  сравнение `Price.availability` **текущего** поставщика строки (кто бы его ни
  назначил, солвер или ручной override) с `line.quantity`, показывается только
  когда `availability` явно задан (не `null`) и меньше требуемого количества —
  симметрично тому, как ADR-0005 трактует `availability IS NULL` как "не
  проверялось", а не как риск.
- Предупреждение о недостижении минимальной суммы заказа поставщика
  (`below_min_order`, возникает как побочный эффект переноса позиции между
  поставщиками) — отдельная текстовая строка **под** заголовком карточки
  поставщика (между именем/доставкой/итогом и таблицей строк), на всю
  ширину карточки, в цвете `--color-danger-text`, без блочного padding
  уровня `warningBlock` (это контекст одной карточки, не событие уровня
  страницы). Текст: "⚠ Сумма заказа {goods_total} меньше минимальной
  {per_order_min_amount} — поставщик может отклонить заказ." Не блокирует
  PATCH переопределения. См. ADR-0006 п.4 за обоснованием, почему не бейдж
  в хедере карточки и не изменение цвета итоговой суммы.
- Кнопка "Подтвердить и создать ордера" — финальный шаг, необратимый (создаёт `Order`).
  Генерация должна читать текущее (с учётом override) состояние
  `AllocationLine`, не исходный результат ILP-расчёта — см. ADR-0006 п.6.
- Повторный запуск ILP с "заморозкой" переопределённой позиции — не в
  объёме; ручное правило — это override, который фиксируется поверх текущего
  состояния строки без пересчёта остального проекта. См. ADR-0006
  "Альтернативы".
- **Модалка конфликта draft-ордеров** (`OrderDraftConflictModal`,
  `frontend/src/components/OrderDraftConflictModal.tsx`) — см. ADR-0012.
  Открывается ИСКЛЮЧИТЕЛЬНО в ответ на реальный `409 draft_orders_exist` от
  `POST .../orders`, не превентивно с фронта (backend — источник истины по
  пересечению поставщиков, ADR-0012 п.3). Клик "Подтвердить и создать
  ордера" сперва всегда шлёт `replace_drafts: false` неявно (обычное
  создание); при `409` вместо `ErrorBanner` показывается эта модалка
  вместо страницы, `ErrorBanner` для этого конкретного случая не
  используется вообще (создание не удалось молча ни разу).
  - Список только тех поставщиков, где есть пересечение (подмножество из
    тела `409`, не все поставщики проекта), для каждого — **все** его
    `existing_draft_orders` (может быть больше одного — не сворачивается
    в один, см. реальный кейс `#20675` в ADR-0012 "Контекст") с суммой
    каждого черновика.
  - Поставщик, у которого хотя бы один `existing_draft_orders[].
    has_confirmed_prices === true`, получает отдельную заметную строку
    предупреждения под его записью (`--color-danger-text` /
    `--color-danger-tint`, тот же язык, что уже применён к
    `below_min_order`/`availabilityRisk` в этом же разделе), текст:
    "в этом черновике уже есть подтверждённые поставщиком цены — они
    будут потеряны при замене".
  - Если хотя бы один поставщик в списке имеет `has_confirmed_prices`,
    кнопка "Заменить черновики" неактивна, пока не отмечен отдельный
    чекбокс подтверждения ("Да, я понимаю, что подтверждённые цены будут
    потеряны…") — общий клик "Заменить" не может случайно стереть
    подтверждённые цены без этого явного шага (ADR-0012 п.1, п.4).
    Без единого подтверждённого поставщика в списке кнопка активна сразу.
  - **Кнопки: только "Отмена" и "Заменить черновики"** — "Создать
    дополнительно" из первоначального текста ADR-0012 п.1/п.4 в модалке
    отсутствует. Обнаружено при живой проверке на `#20675`: ADR
    предполагал, что повторный `POST` с `replace_drafts: false` после
    показа модалки пройдёт "без блокирующего `409`, потому что явное
    согласие уже получено" — но backend не хранит и не принимает такого
    согласия отдельно от `replace_drafts`, поэтому повторный `false`
    при том же конфликте снова получает `409`. Кнопку убрали, а не
    сделали фиктивно рабочей (молча проглатывать повторный `409` и вести
    себя как будто заказ создан было бы хуже — пользователь думал бы,
    что дозаказ создан, хотя ничего не произошло). Возврат этой кнопки
    требует отдельного backend-поля, отличного от `replace_drafts` —
    см. `docs/known-issues.md`.
  - Текстовая подсказка внизу модалки проговаривает необратимость замены,
    в тон существующему `footerHint` под основной кнопкой.
  - Конфликт может повториться и на повторном вызове из модалки (гонка:
    кто-то создал ещё один draft между первым `409` и кликом "Заменить
    черновики") — в этом случае модалка обновляется новыми данными
    конфликта, а не откатывается к обычной странице ошибки.

## 4. Список проектов (`ProjectsListPage.tsx`)

- Удаление проекта — через `ConfirmButton` в отдельной ячейке каждой
  строки (клик по строке целиком переходит в проект, `stopPropagation`
  на ячейке удаления не даёт кнопке случайно сработать как переход). См.
  ADR-0009.
- Каскадно удаляются все связанные данные: `PurchaseRecord`, `Order`/
  `OrderItem`, `AllocationRun`/`AllocationLine`, `ProjectItem`.
- Если у проекта есть хотя бы один `Order` со статусом не `draft`
  (уже отправлен поставщику) — `DELETE` возвращает `409`, ничего не
  удаляется (ни для одной таблицы). Сообщение показывается через
  `ErrorBanner` с `conflictMessage`: "У проекта есть отправленные
  поставщику ордера — удаление недоступно." Предупреждения на уровне
  списка *до* клика на удаление нет — список не тянет сводку по ордерам
  ради этого, пользователь узнаёт о блокировке по факту попытки. См.
  ADR-0009 п.1, п.3.

## 5. Фактическая закупка (`PurchaseRecordsPage.tsx`, `/projects/:id/purchases`)

- Экран уровня проекта, не уровня отдельного `Order` — план и факт
  показаны рядом, сгруппированы по поставщику, включая поставщиков без
  `Order` в проекте ("не планировался" — заказали не по плану). См.
  ADR-0008 §2, §5.
- Агрегаты наверху: `purchased_total` по проекту vs сумма
  `Order.total_amount`, дельта в $/%. Если ни для одного поставщика ещё
  нет `Order` — вместо дельты предупреждение "сравнить не с чем" (не
  `0`/`—` молча). См. ADR-0008 §4.
- Таблицы "План" и "Факт" — независимые колонки, без построчного
  автоматического сопоставления между ними (ADR-0008 §3 — явно вне
  объёма). Единственная связь план↔факт — ручная, по инициативе
  пользователя:
  - **Кнопка «→» в конце каждой строки плана.** Копирует
    название/кол-во/цену/`material_id` этой строки плана в форму
    добавления записи факта (не создаёт `PurchaseRecord` сама — форма
    всё равно требует явного нажатия "+ Добавить"), выставляет
    поставщика формы на поставщика текущей карточки и плавно
    прокручивает страницу к форме. Предназначена для случая "всё
    совпало, не хочу перепечатывать вручную" — не автоматическое
    сопоставление (то и другое разные вещи: копирование одной строки по
    явному клику не угадывает соответствие само, только избавляет от
    перепечатывания уже выбранной человеком строки).
  - Опциональный `material_id` в строке факта после такого копирования
    предзаполнен из строки плана (там он не может быть не задан —
    `OrderItem.material_id` обязателен), но остаётся редактируемым и не
    более обязательным, чем при ручном вводе — пользователь может
    очистить поле перед сохранением.
- Правка/удаление записи факта — inline, тот же `ConfirmButton`, что и
  в остальном проекте; форма правки открывается на всю ширину строки
  (не в узких колонках таблицы — 5 полей формы не помещаются в 4 узкие
  колонки отображения).

## 6. Статус проекта на `ProjectDetailPage.tsx` / `ProjectRouterPage.tsx`

- `status === 'draft'` — показывается конструктор (`ProjectBuilderPage`),
  не детальный экран. Переключение целиком по `status`, не по наличию
  `latest_allocation_run` — см. ADR-0011 §7.
- Кнопка «Завершить проект» на `ProjectDetailPage` видна только при
  `status === 'ordered'`. После нажатия `status` становится `completed`
  без возможности вернуться назад — ни повторный расчёт, ни новый ордер
  этого не меняют. См. ADR-0011 §4–5.
- Расчёт со статусом `AllocationRun.status === 'infeasible'` (не
  `Project.status` — разные поля) никогда не двигает `Project.status`, в
  том числе при первом расчёте черновика — черновик остаётся `draft`,
  пока не будет хотя бы одного успешного (`"ok"`) расчёта. См.
  ADR-0011 §2.
